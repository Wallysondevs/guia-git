Git push --force-with-lease

Depois de um rebase ou de um --amend num branch que já estava no GitHub, o git push normal é recusado: o seu branch não é mais continuação do que está lá. Para enviar mesmo assim, é preciso forçar. Existem dois jeitos: o --force, que passa por cima de qualquer coisa, inclusive do trabalho de um colega; e o --force-with-lease, que força só se o GitHub ainda estiver como você o viu da última vez. Esta aula mostra os dois com o Git real, inclusive o --force-with-lease recusando de verdade quando o Bruno enviou antes.

Você vai aprender
  • Quando forçar um push é necessário (e quando é sinal de que algo está errado).
  • O que o --force faz com o commit de um colega, com as mensagens reais.
  • Como o --force-with-lease recusa o push (stale info) quando alguém mudou o branch.
  • A armadilha do git fetch e a proteção extra do --force-if-includes.
  • O que fazer depois da recusa.

Todas as sessões rodaram no Git real do Ubuntu, com o "GitHub de mentira" do laboratório do guia: a Ana (ana@notebook) e o Bruno (bruno@notebook) trabalham no repositório ana-souza/receitas. As mensagens do push saem em inglês mesmo com o sistema em português: a tradução do Git no Ubuntu é parcial.

Antes de tudo: a regra de ouro

Forçar um push troca o histórico do GitHub. Isso só é aceitável num branch que só você usa (ou em que a equipe combinou reescrever). No main compartilhado, não force: veja A Regra de Ouro.

A ideia: "só se ninguém mexeu"

A Ana deixou um bilhete na geladeira da república: "comprar leite". Ela quer trocar por "comprar leite e ovos". Há dois jeitos de fazer isso:

  • Arrancar o bilhete e colar o novo, sem olhar. Se o Bruno tinha escrito "e pão" embaixo enquanto ela estava fora, o "e pão" vai para o lixo. Isso é o --force.
  • Olhar antes: "o bilhete ainda está exatamente como eu deixei? Então troco. Mudou? Não mexo, primeiro vou ver o que é". Isso é o --force-with-lease.

Lease, em inglês, é "arrendamento", "aluguel com prazo": a ideia é "eu forço, contanto que o branch lá no GitHub ainda esteja do jeito que eu o vi". O "jeito que eu vi" é o origin/chocolate (ou origin/main…), a anotação que o seu Git guarda de onde o branch do GitHub estava no último fetch, pull ou push (veja git fetch).

1. Quando é preciso forçar

A Ana criou o branch chocolate, commitou o pudim de chocolate e enviou com git push -u origin chocolate (cópia de segurança e, mais tarde, um pull request). Enquanto isso, o main ganhou um commit, os ovos do bolo:

$ git switch chocolate
Switched to branch 'chocolate'
Your branch is up to date with 'origin/chocolate'.
$ git log --oneline --graph --all
* a065dea (HEAD -> chocolate, origin/chocolate) Adiciona o pudim de chocolate
| * 5927fcc (origin/main, main) Adiciona os ovos ao bolo
|/
* c34349b Adiciona a receita de bolo
* 700bbd5 Cria o README

Ela quer o chocolate em cima do main atualizado, em linha reta, e faz o rebase. O push normal é recusado:

$ git rebase main
Successfully rebased and updated refs/heads/chocolate.
$ git push
To https://github.com/ana-souza/receitas.git
 ! [rejected]        chocolate -> chocolate (non-fast-forward)
error: failed to push some refs to 'https://github.com/ana-souza/receitas.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart. If you want to integrate the remote changes,
hint: use 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

O rebase trocou o a065dea por uma cópia nova, e o GitHub ainda tem o a065dea. Um push normal só pode acrescentar commits; este faria o a065dea sumir de lá, por isso rejected … (non-fast-forward) (as linhas uma por uma estão explicadas em A Regra de Ouro). Aqui a dica do git pull não ajuda: ela traria o commit antigo de volta e juntaria com a cópia. O branch é só da Ana; ela sabe que o commit antigo pode sumir. É o caso de forçar, com segurança:

$ git push --force-with-lease

Counting objects: 100% (4/4), done.

Compressing objects: 100% (2/2), done.
Writing objects: 100% (3/3), 338 bytes | 338.00 KiB/s, done.
Total 3 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
To https://github.com/ana-souza/receitas.git
 + a065dea...a398bad chocolate -> chocolate (forced update)
$ git log --oneline --graph --all
* a398bad (HEAD -> chocolate, origin/chocolate) Adiciona o pudim de chocolate
* 5927fcc (origin/main, main) Adiciona os ovos ao bolo
* c34349b Adiciona a receita de bolo
* 700bbd5 Cria o README
git push --force-with-lease
"Envie forçando, contanto que o chocolate do GitHub ainda esteja onde o meu origin/chocolate diz (no a065dea)". Estava, então o Git forçou.
Enumerating objects … Total 3
O progresso do envio, como em qualquer git push.
+ a065dea...a398bad chocolate -> chocolate (forced update)
O + e o (forced update) ("atualização forçada") dizem que o branch foi trocado, não só avançado: era a065dea, agora é a398bad. Os três pontos entre os hashes também indicam isso (num push normal são dois: a065dea..a398bad).

O log confirma: linha reta, e o origin/chocolate anda junto com o chocolate da Ana. A saída é igual à de um --force; a diferença aparece quando alguém mexeu no branch.

Missão: você está no branch chocolate da Ana, que acabou de passar por um rebase (o "GitHub" aqui é a pasta ~/servidor.git). Rode git status para ver a divergência, tente um git push normal para ver a recusa e depois envie com segurança, forçando só se ninguém mexeu no branch.

Agora o GitHub tem a065dea → a6ee809 (a calda). O origin/chocolate da Ana ainda diz a065dea: ela não sabe da calda. A Ana faz o rebase e tenta enviar:

Com --force: o commit do Bruno some

$ git push --force

Nenhum aviso. O único sinal é o hash da esquerda: a6ee809, e não o a065dea que a Ana conhecia. O --force trocou o branch inteiro pelo da Ana, e a calda do Bruno não está mais no GitHub. Quando o Bruno buscar as novidades:

O (forced update) no fetch avisa o Bruno, e o desenho mostra: a calda (a6ee809) só existe no computador dele; o origin/chocolate foi para outro galho. Se o Bruno tivesse apagado a pasta, ou se tivesse sido outra pessoa sem cópia, o trabalho estaria perdido.

Com --force-with-lease: recusado

A mesma situação (o Bruno enviou a calda; a Ana fez o rebase sem saber), agora com o comando certo:

$ git rebase main
Successfully rebased and updated refs/heads/chocolate.
$ git push
To https://github.com/ana-souza/receitas.git
 ! [rejected]        chocolate -> chocolate (fetch first)
error: failed to push some refs to 'https://github.com/ana-souza/receitas.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.
$ git push --force-with-lease
To https://github.com/ana-souza/receitas.git
 ! [rejected]        chocolate -> chocolate (stale info)
error: failed to push some refs to 'https://github.com/ana-souza/receitas.git'
! [rejected] … (fetch first)
O push normal já desconfia: "o remoto tem trabalho que você não tem; busque primeiro". Repare que é diferente do (non-fast-forward) da seção 1: lá o GitHub tinha só o commit antigo da Ana; aqui tem um commit que ela nunca viu.
! [rejected] chocolate -> chocolate (stale info)
"Recusado: informação velha" (stale = "vencido", "passado"). O Git perguntou ao GitHub onde está o chocolate: a6ee809. A Ana esperava a065dea (o origin/chocolate dela). Não bate, então nada foi enviado.
error: failed to push some refs…
O mesmo "falhou ao enviar" de sempre. Sem dicas: o stale info já diz tudo.

O commit do Bruno está salvo no GitHub. A Ana não perdeu nada também: o rebase dela continua no computador. Ela só precisa olhar o que mudou antes de decidir.

Por baixo, o --force-with-lease sem nada depois é um atalho para "o valor esperado é o meu origin/chocolate". Dá para dizer o hash esperado explicitamente, no formato --force-with-lease=BRANCH:HASH; com o hash que a Ana conhecia, o resultado é o mesmo:

$ git push --force-with-lease=chocolate:a065dea
To https://github.com/ana-souza/receitas.git
 ! [rejected]        chocolate -> chocolate (stale info)
error: failed to push some refs to 'https://github.com/ana-souza/receitas.git'

  • git reset --hard origin/chocolate: põe o chocolate da Ana exatamente onde está o do GitHub (com a calda), jogando fora a cópia do rebase (veja reset --hard; o a398bad ainda fica no reflog por um tempo, se ela precisar).
  • git merge --no-edit main: traz os ovos do main com um commit de merge, sem reescrever nada.
  • git push: push normal, com dois pontos (a6ee809..640682b). Nada de força.

Se a Ana e o Bruno tivessem combinado que o branch seria "rebaseado", o caminho seria outro: refazer o rebase incluindo a calda (por exemplo, git reset --hard origin/chocolate e depois git rebase main), enviar com --force-with-lease e avisar o Bruno para atualizar com git pull --rebase.

4. A armadilha do git fetch (e o --force-if-includes)

O --force-with-lease compara o GitHub com o seu origin/chocolate. Mas o origin/chocolate é atualizado por qualquer git fetch, inclusive um que você rodou só para "dar uma olhada" (e alguns editores, como o VS Code, podem buscar sozinhos de tempos em tempos). Veja o que acontece se a Ana faz o rebase, depois um fetch sem prestar atenção, e então o push:

$ git rebase main
Successfully rebased and updated refs/heads/chocolate.
$ git fetch
remote: Enumerating objects: 5, done.
remote: Counting objects: 100% (5/5), done.
remote: Compressing objects: 100% (2/2), done.
remote: Total 3 (delta 1), reused 0 (delta 0), pack-reused 0 (from 0)
Unpacking objects: 100% (3/3), 283 bytes | 283.00 KiB/s, done.
From https://github.com/ana-souza/receitas
   a065dea..a6ee809  chocolate  -> origin/chocolate
$ git push --force-with-lease
Enumerating objects: 4, done.
Counting objects: 100% (4/4), done.
Delta compression using up to 4 threads
Compressing objects: 100% (2/2), done.
Writing objects: 100% (3/3), 338 bytes | 338.00 KiB/s, done.
Total 3 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
To https://github.com/ana-souza/receitas.git
 + a6ee809...a398bad chocolate -> chocolate (forced update)

Passou, e a calda do Bruno sumiu do GitHub, como no --force. O fetch moveu o origin/chocolate para o a6ee809; o GitHub também estava no a6ee809; a "garantia" bateu. O --force-with-lease não sabe se você olhou a calda; só sabe que o seu Git já a tinha baixado.

Para fechar essa brecha existe o --force-if-includes git 2.30+, usado junto com o --force-with-lease. Ele confere se o commit do origin/chocolate já passou pelo seu branch (pelo diário do branch, o mesmo do reflog), ou seja, se você realmente incorporou o que baixou. Na situação logo depois do fetch da seção 3:

$ git push --force-with-lease --force-if-includes
To https://github.com/ana-souza/receitas.git
 ! [rejected]        chocolate -> chocolate (remote ref updated since checkout)
error: failed to push some refs to 'https://github.com/ana-souza/receitas.git'
hint: Updates were rejected because the tip of the remote-tracking branch has
hint: been updated since the last checkout. If you want to integrate the
hint: remote changes, use 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

"Recusado: o branch remoto foi atualizado desde que você o pegou" (remote ref updated since checkout). A dica: "a ponta do branch de rastreamento remoto mudou desde o último checkout; se quiser integrar as mudanças de lá, use git pull antes de enviar de novo". Com os dois juntos, a Ana só consegue forçar depois de trazer a calda para o branch dela (como no git reset --hard origin/chocolate da seção 3).

Um atalho para não esquecer

Muita gente cria um alias e nunca mais digita --force:

$ git config --global alias.pushf 'push --force-with-lease --force-if-includes'
$ git config --global alias.pushf
push --force-with-lease --force-if-includes

A primeira linha cria o atalho (e não mostra nada quando dá certo); a segunda confere o que ficou gravado. Depois disso, git pushf é o "push forçado com as duas travas".

Formas diferentes de fazer a mesma coisa

ComandoForça quando…Use?
git push --force (ou -f)Sempre, sem conferir nadaNão. Só se você tem certeza absoluta de que ninguém mais usa o branch, e mesmo assim prefira o de baixo
git push --force-with-leaseO branch do GitHub ainda está no seu origin/BRANCHSim: o mínimo depois de um rebase
git push --force-with-lease=BRANCH:HASHO branch do GitHub está no HASH que você indicouQuando você quer dizer o valor esperado explicitamente
git push --force-with-lease --force-if-includesComo o anterior e você já incorporou o que baixouSim: o mais seguro (Git 2.30 ou mais novo)
git push origin +chocolateO + antes do nome força só esse branch, como o --forceNão (mesmo perigo do --force); vale reconhecer em tutoriais

E, antes de pensar em forçar, lembre das alternativas que não precisam de força: git merge main no seu branch em vez de rebase (seção 3), ou um commit novo em vez de --amend (veja A Regra de Ouro).

Quando dá errado

! [rejected] … (stale info) 
$ git push --force-with-lease
To https://github.com/ana-souza/receitas.git
 ! [rejected]        chocolate -> chocolate (stale info)
error: failed to push some refs to 'https://github.com/ana-souza/receitas.git'

O que aconteceu: alguém enviou para o mesmo branch depois do seu último fetch/pull. Como confirmar: git fetch e git log --oneline --graph --all: os commits novos aparecem no origin/BRANCH. Como resolver: não troque por --force. Junte o trabalho do colega (merge, ou rebase incluindo os commits dele, como na seção 3) e só então envie.

! [rejected] … (remote ref updated since checkout)

O que aconteceu: com --force-if-includes, o Git percebeu que você baixou commits novos (num fetch) mas não os incorporou ao seu branch. Como resolver: igual ao anterior: olhe o origin/BRANCH e traga esses commits para o seu branch antes de enviar.

"Forcei e apaguei o commit de alguém"

Como confirmar: a saída do seu push mostrou + HASH1...HASH2 … (forced update) com um HASH1 que você não reconhece (no exemplo, a6ee809 em vez de a065dea). Como resolver: o commit ainda existe no computador de quem o fez: peça para a pessoa rodar git fetch, juntar com o seu histórico (por exemplo, git pull --rebase) e enviar de novo. Se você tem o hash antigo (ele aparece na sua saída do push), também pode recuperá-lo enquanto ele estiver no seu computador: depois do fetch que o trouxe, ele fica alcançável pelo reflog do origin/BRANCH (git reflog origin/chocolate).

O push forçado foi recusado pelo próprio GitHub

Repositórios no GitHub podem ter regras de proteção de branch que proíbem push forçado (segundo a documentação, num branch protegido o GitHub bloqueia o push forçado por padrão). Nesse caso, nem o --force passa: o GitHub recusa com uma mensagem remote: … explicando a regra (ilustrativo; o laboratório do guia não imita essas regras; veja "Sobre branches protegidos" em docs.github.com). Isso é bom: é o GitHub aplicando a regra de ouro por você.

Referência rápida

SaídaQuer dizer
+ abc1234...def5678 br -> br (forced update)O push forçado passou; o branch foi trocado de abc1234 para def5678
! [rejected] … (non-fast-forward)Push normal recusado: o seu branch não continua o do GitHub (rebase/amend?)
! [rejected] … (fetch first)Push normal recusado: há commits no GitHub que você nunca baixou
! [rejected] … (stale info)--force-with-lease recusado: o GitHub não está onde o seu origin/BRANCH diz

Resumo

  • Depois de um rebase ou amend em algo já enviado, o push normal é recusado (non-fast-forward), e é preciso forçar, só em branches seus.
  • git push --force troca o branch do GitHub sem conferir nada: apaga em silêncio os commits que outra pessoa enviou.
  • git push --force-with-lease força só se o GitHub ainda estiver onde o seu origin/BRANCH diz; se alguém enviou antes, recusa com (stale info).
  • Um git fetch sem atenção "renova" a garantia; o --force-if-includes (Git 2.30+) fecha essa brecha com (remote ref updated since checkout).
  • Depois de uma recusa: git fetch, olhe o origin/BRANCH e junte o trabalho do colega antes de enviar. Em branch compartilhado, prefira merge e push normal.

Git .gitignore

Todo projeto tem arquivos que não devem ir para o Git: o arquivo com a senha do banco de dados, os registros (logs) que o programa cria sozinho, os seus rascunhos, o lixo que o sistema operacional espalha pelas pastas. Se nada for feito, eles aparecem em todo git status e um dia alguém dá git add . e manda tudo para o GitHub. O .gitignore é um arquivo de texto com a lista do que o Git deve fingir que não vê.

Você vai aprender
  • Por que ignorar arquivos, e quais costumam ser ignorados.
  • Como escrever um .gitignore: comentários, nomes, *.log, pasta/, /só-na-raiz, ** e exceções com !.
  • Como conferir: git status --ignored e git check-ignore -v.
  • Por que o .gitignore não funciona num arquivo que já é rastreado, e como resolver com git rm --cached.
  • Os outros lugares de ignorar: .git/info/exclude e o .gitignore global.

Todas as saídas desta aula saíram do Git do Ubuntu 26.04, na máquina da Ana (usuária ana, computador notebook), com o sistema em português. Algumas mensagens do Git ainda não têm tradução e saem em inglês, como você vai ver.

A ideia: a lista do porteiro

Pense no Git como o porteiro de um prédio. Todo mundo que aparece na portaria (todo arquivo novo na pasta) é anunciado: "tem um tal de erro.log aqui, deixo subir?". Depois de um tempo, o porteiro anuncia as mesmas visitas indesejadas todos os dias. O .gitignore é a lista que você deixa com o porteiro: "esses aqui, nem me avise, e não deixe subir".

1. O problema: um git status poluído

A Ana tem o site de receitas com dois arquivos commitados, index.html e estilo.css. Com o tempo, apareceram na pasta: um .env com a senha do banco de dados, dois logs, uma pasta de rascunhos e um .DS_Store (um arquivo que o macOS cria em toda pasta que você abre; ele veio num pen drive):

$ git status
No ramo main
Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	.DS_Store
	.env
	erro.log
	rascunhos/
	servidor.log

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)

Cinco "visitas" anunciadas, e nenhuma deveria entrar. Pior: um git add . distraído prepararia todas, inclusive a senha.

2. Criando o .gitignore

O .gitignore é um arquivo de texto comum, com esse nome exato (com o ponto na frente, sem extensão), na pasta principal do repositório (a que tem o .git). Crie-o no seu editor (VS Code, gedit, Bloco de Notas…) ou, no terminal, com um printf que escreve uma linha por argumento. O da Ana ficou assim:

# Senhas e configurações locais: nunca no Git
.env

# Registros (logs) gerados pelo programa
*.log

# Rascunhos pessoais
rascunhos/

# Lixo do macOS
.DS_Store
# Senhas e configurações…
Linha que começa com # é comentário: o Git a ignora. Use para explicar o porquê de cada regra. Linhas em branco também são ignoradas e servem para separar grupos.
.env
Um nome exato: ignora qualquer arquivo (ou pasta) chamado .env, em qualquer pasta do projeto.
*.log
O * quer dizer "qualquer sequência de caracteres": todo arquivo que termina em .log (erro.log, servidor.log, 2026-10-15.log…). É o mesmo curinga do terminal (veja O Mínimo de Terminal).
rascunhos/
A barra no fim quer dizer "só pastas": ignora a pasta rascunhos e tudo o que está dentro dela.
.DS_Store
Outro nome exato.

Agora, o mesmo git status:

$ git status
No ramo main
Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	.gitignore

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)

Os cinco sumiram do relatório. Eles continuam na pasta (o .gitignore não apaga nada): o Git só parou de anunciá-los. O único arquivo novo que aparece é o próprio .gitignore.

3. O .gitignore também vai no commit

O .gitignore é parte do projeto: commitado, ele vale para todo mundo que clonar o repositório (o Bruno, o computador do trabalho, o GitHub). Agora até o git add . ("adicione tudo desta pasta") é seguro:

$ git add .
$ git status --short
A  .gitignore
$ git commit -q -m 'Adiciona .gitignore'
$ git log --oneline
bc049e8 Adiciona .gitignore
7d067ed Primeira versão do site
$ git ls-files
.gitignore
estilo.css
index.html

O git add . preparou só o .gitignore (o A é de added, adicionado). O git ls-files lista os arquivos que o Git rastreia: nem sinal do .env ou dos logs.

Missão: o git status do site da Ana mostra a senha (.env) e dois logs. Crie um .gitignore que ignore o .env e todos os arquivos .log (dica: echo '.env' > .gitignore cria o arquivo com uma linha, e echo '*.log' >> .gitignore acrescenta outra), confira com git status e faça o commit do .gitignore. No fim, o git status deve dizer que não há nada a submeter.

4. Conferindo o que está sendo ignorado

git status --ignored

Os ignorados somem do git status, mas você pode pedir para vê-los:

$ git status --ignored
No ramo main
Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	.gitignore

Arquivos ignorados:
  (utilize "git add -f <arquivo>..." para incluir o que será submetido)
	.DS_Store
	.env
	erro.log
	rascunhos/
	servidor.log

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)

(Esta saída é de antes do commit do .gitignore, por isso ele ainda aparece como não monitorado.) Aparece uma seção nova, Arquivos ignorados, com a dica git add -f, que você vai ver na seção 7. No formato curto, git status --short --ignored, os ignorados aparecem com !! (e os não monitorados, como sempre, com ??).

git check-ignore -v: "por que este arquivo está sendo ignorado?"

Num .gitignore comprido, às vezes você não sabe qual regra pegou um arquivo. O git check-ignore responde, e o -v (verbose, detalhado) mostra a regra:

$ git check-ignore -v erro.log
.gitignore:5:*.log	erro.log
$ git check-ignore -v rascunhos/lasanha.txt
.gitignore:8:rascunhos/	rascunhos/lasanha.txt
$ git check-ignore -v index.html
$ echo $?
1
.gitignore
O arquivo onde está a regra.
:5:
O número da linha nesse arquivo (a linha 5 do .gitignore da Ana é o *.log; os comentários e as linhas em branco contam).
*.log
A regra (o padrão) que pegou o arquivo.
erro.log
Depois de uma tabulação, o arquivo que você perguntou.
(nada) e $? = 1
Para o index.html, que não é ignorado, o comando não mostra nada e termina com código 1 ("não"). Para um arquivo ignorado, o código é 0 ("sim").

5. Os padrões, um por um

Para ver cada tipo de regra funcionando, a Ana montou uma pasta de testes, padroes, com arquivos vazios espalhados em subpastas, e este .gitignore:

$ mkdir -p notas fotos/viagem build src/build
$ touch todo.txt notas/todo.txt fotos/praia.jpg fotos/viagem/serra.jpg fotos/capa.png build/site.html src/build/x.o copia.txt~ backup.bak
$ cat .gitignore
/todo.txt
fotos/*.jpg
build/
*~
*.bak
$ git status --short --ignored
?? .gitignore
?? fotos/
?? notas/
!! backup.bak
!! build/
!! copia.txt~
!! fotos/praia.jpg
!! src/
!! todo.txt
$ git check-ignore -v todo.txt notas/todo.txt fotos/praia.jpg fotos/viagem/serra.jpg src/build/x.o copia.txt~
.gitignore:1:/todo.txt	todo.txt
.gitignore:2:fotos/*.jpg	fotos/praia.jpg
.gitignore:3:build/	src/build/x.o
.gitignore:4:*~	copia.txt~

O check-ignore recebeu 6 arquivos e respondeu só sobre 4: os outros dois (notas/todo.txt e fotos/viagem/serra.jpg) não são ignorados. Por quê?

  • /todo.txt: a barra no começo "prende" a regra na pasta onde está o .gitignore. Pega o todo.txt da raiz, mas não o notas/todo.txt. Sem a barra (todo.txt), pegaria os dois.
  • fotos/*.jpg: uma regra com barra no meio também é contada a partir da raiz, e o * não atravessa pastas. Pega fotos/praia.jpg, mas não fotos/viagem/serra.jpg (está uma pasta mais funda). Nem a fotos/capa.png (não termina em .jpg).
  • build/: só barra no fim, então vale em qualquer nível: pegou a build/ da raiz e a src/build/. Como a src/ só tinha a build/ dentro, ela inteira aparece como !! src/.
  • *~ e *.bak: cópias de segurança que alguns editores criam (copia.txt~) e backups.

Para pegar .jpg em qualquer subpasta de fotos, use ** ("qualquer número de pastas, inclusive nenhuma"):

$ printf '%s\n' '/todo.txt' 'fotos/**/*.jpg' 'build/' '*~' '*.bak' > .gitignore
$ git status --short --ignored
?? .gitignore
?? fotos/
?? notas/
!! backup.bak
!! build/
!! copia.txt~
!! fotos/praia.jpg
!! fotos/viagem/
!! src/
!! todo.txt

Agora fotos/viagem/ também aparece com !!: o serra.jpg foi pego.

E pastas vazias?

O Git não guarda pastas, só arquivos (as pastas vêm "de carona" com os arquivos que estão dentro delas). Uma pasta vazia nunca aparece no git status, com ou sem .gitignore: no lab, a Ana criou uma pasta vazia e o git status --short continuou idêntico. Se você precisa que uma pasta vazia exista no repositório, a convenção é pôr um arquivo vazio dentro dela, normalmente chamado .gitkeep.

6. Exceções com !

A Ana ignora todos os *.log, mas quer guardar um deles, o importante.log. Uma linha que começa com ! desfaz o ignorar, e precisa vir depois da regra que ela contraria:

$ echo '!importante.log' >> .gitignore
$ echo 'guardar este' > importante.log
$ git status --short
 M .gitignore
?? importante.log
$ git check-ignore -v importante.log
.gitignore:12:!importante.log	importante.log

O importante.log aparece como ?? (novo, não monitorado): o Git voltou a anunciá-lo, e ele pode receber git add. O check-ignore -v mostra a regra que decidiu, com o ! na frente: aqui, a decisão foi "não ignorar". O M na frente do .gitignore é porque ele mesmo mudou (ganhou uma linha) e precisa de um novo commit.

A exceção não funciona dentro de uma pasta ignorada

Se a regra é rascunhos/ (a pasta inteira), um !rascunhos/lasanha.txt não adianta: o Git nem entra numa pasta ignorada para olhar o que tem dentro. Nesse caso, ignore o conteúdo em vez da pasta (rascunhos/*) e depois faça a exceção (!rascunhos/lasanha.txt).

Missão: o .gitignore desta pasta ignora todos os *.log. Faça uma exceção para o importante.log (sem deixar de ignorar o erro.log) e prepare-o com git add importante.log. Use git status --ignored para conferir.

7. Forçando: git add -f

O que acontece se a Ana tentar preparar um arquivo ignorado?

$ git add .env
Os caminhos a seguir são ignorados por um dos seus arquivos .gitignore:
.env
hint: Use -f if you really want to add them.
hint: Disable this message with "git config set advice.addIgnoredFile false"
$ echo $?
1

O Git recusa e explica: "os caminhos a seguir são ignorados por um dos seus arquivos .gitignore". As duas dicas (hint), ainda em inglês, dizem: "use -f se você realmente quer adicioná-los" e "desative esta mensagem com git config set advice.addIgnoredFile false". O código de saída 1 confirma: nada foi preparado. É uma proteção: o .gitignore segura até um git add com o nome exato.

Se você tem certeza, o -f (de force, "forçar") passa por cima da lista:

$ git add -f servidor.log
$ git status --short
 M .gitignore
A  servidor.log
?? importante.log

O servidor.log foi preparado (A), mesmo ignorado. Depois do commit, ele passa a ser rastreado, e um arquivo rastreado não é mais afetado pelo .gitignore (próxima seção). Use o -f raramente e nunca com senhas. (A Ana desistiu: tirou o log da área de preparo com git restore --staged servidor.log, da aula Tirando da Área de Preparo.)

8. "Pus no .gitignore e o Git continua vendo!"

Esta é a dúvida número um sobre o .gitignore. A Ana tinha um config.txt já commitado e depois resolveu ignorá-lo:

$ echo 'config.txt' >> .gitignore
$ echo 'mudei a config' >> config.txt
$ git status --short
 M .gitignore
 M config.txt
?? importante.log
$ git check-ignore -v config.txt
$ echo $?
1

O config.txt continua aparecendo como modificado (M), e o check-ignore diz que ele não é ignorado. A regra é: o .gitignore só vale para arquivos que o Git ainda não rastreia. Ele é a lista do porteiro para visitas novas; quem já mora no prédio (já foi commitado) entra e sai sem passar pela lista.

O --no-index faz o check-ignore olhar só as regras, sem considerar se o arquivo é rastreado, e confirma que a regra está certa:

$ git check-ignore -v --no-index config.txt
.gitignore:13:config.txt	config.txt

Para o Git parar de rastrear o arquivo, sem apagá-lo da pasta, use git rm --cached:

$ git rm --cached config.txt
rm 'config.txt'
$ git status --short
 M .gitignore
D  config.txt
?? importante.log

O D (de deleted) na primeira coluna diz que, no próximo commit, o config.txt sai do repositório. Mas ele continua na pasta da Ana, e, como está no .gitignore, não aparece mais como ??. Falta só o commit (do .gitignore e da remoção). Os detalhes do git rm --cached estão na próxima aula, git rm.

E se o arquivo era uma senha?

O git rm --cached tira o arquivo dos próximos commits, mas os commits antigos continuam com ele: qualquer um com acesso ao histórico ainda lê a senha. Troque a senha imediatamente e veja Commitei uma Senha! E Agora?. Por isso o .gitignore deve ser o primeiro arquivo de um projeto novo.

O .git/info/exclude já vem criado pelo git init, só com comentários em inglês:

$ cat .git/info/exclude
# git ls-files --others --exclude-from=.git/info/exclude
# Lines that start with '#' are comments.
# For a project mostly in C, the following would be a good set of
# exclude patterns (uncomment them if you want to use them):
# *.[oa]
# *~

Basta acrescentar as suas regras no fim, no mesmo formato do .gitignore.

Para um .gitignore que vale em todos os seus projetos, crie um arquivo (o nome é livre; por exemplo, ~/.gitignore_global) e diga ao Git onde ele está, uma vez só:

$ git config --global core.excludesFile ~/.gitignore_global

(O comando não mostra nada quando dá certo.) A configuração em si está na aula git config.

Quando dá errado

git add recusa: "Os caminhos a seguir são ignorados…" 
$ git add .env
Os caminhos a seguir são ignorados por um dos seus arquivos .gitignore:
.env
hint: Use -f if you really want to add them.
hint: Disable this message with "git config set advice.addIgnoredFile false"

O que aconteceu: o arquivo está na lista. Como confirmar: git check-ignore -v .env mostra a regra e a linha. Como resolver: se ele não deveria ser ignorado, apague ou corrija a regra; se deveria (e é uma senha), comemore: o .gitignore acabou de salvar você. Só use git add -f se tiver certeza.

O arquivo está no .gitignore e continua aparecendo como modificado

O que aconteceu: ele já era rastreado (seção 8). Como confirmar: git ls-files lista o arquivo; git check-ignore -v arquivo não mostra nada, e git check-ignore -v --no-index arquivo mostra a regra. Como resolver: git rm --cached arquivo e commit.

A regra "não pega" arquivos de subpastas

O que aconteceu: a regra tem uma barra no começo ou no meio (/todo.txt, fotos/*.jpg), então vale só a partir da pasta do .gitignore, e o * não entra em subpastas (seção 5). Como confirmar: git check-ignore -v caminho/do/arquivo não responde nada. Como resolver: tire a barra do começo, ou use ** (fotos/**/*.jpg).

O .gitignore não faz efeito nenhum

Confira o nome do arquivo com ls -a: tem de ser exatamente .gitignore. Erros comuns: gitignore sem o ponto, .gitignore.txt (o Bloco de Notas do Windows acrescenta o .txt sozinho; na janela "Salvar como", escolha "Todos os arquivos"), .gitingore (letras trocadas) ou o arquivo salvo fora da pasta do projeto.

Resumo

  • O .gitignore (na raiz, com esse nome exato) lista o que o Git deve fingir que não vê: senhas, arquivos gerados, dependências, lixo do sistema, rascunhos.
  • Regras: # comentário, nome, *.ext, pasta/, /só-na-raiz, ** para qualquer profundidade, !exceção.
  • Commite o .gitignore: as regras passam a valer para todo o projeto.
  • git status --ignored mostra os ignorados; git check-ignore -v mostra qual regra ignorou cada um.
  • O .gitignore não vale para arquivos já rastreados: use git rm --cached (e, se era senha, troque a senha).
  • git add -f força um arquivo ignorado; .git/info/exclude e core.excludesFile guardam regras só suas.

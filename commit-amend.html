Git commit --amend

A Ana acabou de fazer um commit e, um segundo depois, percebeu: escreveu "recieta" na mensagem. Ou pior: esqueceu de incluir um dos arquivos. Ela não precisa fazer um segundo commit só para consertar o primeiro. O Git tem uma opção para isso: git commit --amend (em inglês, amend = "emendar, corrigir"). Ela refaz o último commit, com a mensagem nova, os arquivos que faltavam, ou as duas coisas.

Você vai aprender
  • Como trocar a mensagem do último commit com git commit --amend -m "…".
  • Como colocar no último commit um arquivo que ficou de fora, com git commit --amend --no-edit.
  • Por que o commit corrigido ganha um hash novo: o Git não edita, ele substitui.
  • Como desfazer um --amend feito sem querer.
  • Por que não se emenda um commit que já foi enviado para o GitHub.

Todas as saídas desta aula vieram do Git real da máquina da Ana (usuária ana, computador notebook), com o sistema em português. A tradução do Git que vem no Ubuntu é parcial: algumas mensagens saem em português, outras em inglês, outras misturadas. Elas estão aqui exatamente como saíram (no Windows, no macOS ou com o sistema em inglês, as frases podem ser diferentes; o sentido é o mesmo).

A ideia: refazer a última foto, não tirar outra

Pense numa foto de família. Alguém piscou. Você pode guardar a foto ruim e tirar outra (agora são duas no álbum, uma delas inútil), ou jogar a ruim fora e pôr a boa no lugar. O --amend é a segunda opção: o último commit sai do histórico e entra um commit novo, no mesmo lugar, já corrigido.

Três coisas para guardar desde já:

  • Só funciona para o último commit (o que está no HEAD). Para mexer em commits mais antigos existe o rebase interativo.
  • O commit corrigido é outro commit, com outro hash. O antigo não é apagado na hora: ele só deixa de aparecer no git log.
  • Se o commit já foi enviado (git push) e outras pessoas já o baixaram, emendar complica a vida delas. A regra está na seção Quando dá errado.

1. Corrigindo a mensagem

O repositório receitas da Ana já tinha o primeiro commit (o README). Ela criou a receita de bolo e commitou, com pressa:

$ echo 'Bolo de cenoura: 3 cenouras, 3 ovos, 2 xícaras de açúcar' > bolo.txt
$ git add bolo.txt
$ git commit -m "Adiciona recieta de bolo"
[main cfa022b] Adiciona recieta de bolo
 1 file changed, 1 insertion(+)
 create mode 100644 bolo.txt
$ git log --oneline
cfa022b Adiciona recieta de bolo   « o commit novo, com o erro
fe996fb Primeiro commit

No git log --oneline, cada linha é um commit: o hash curto (o "RG" do commit) e a mensagem. O commit de cima é o mais novo. Lá está o erro: "recieta". Para consertar:

$ git commit --amend -m "Adiciona receita de bolo"
[main 5bc05d8] Adiciona receita de bolo
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+)
 create mode 100644 bolo.txt
git commit
O mesmo comando de sempre (veja git commit).
--amend
"Emende": em vez de criar um commit depois do último, refaça o último. O Git pega o conteúdo da área de preparo (que, aqui, é exatamente o que já estava no commit) e cria um commit novo no lugar do antigo.
-m "Adiciona receita de bolo"
A mensagem nova. Ela substitui a antiga por inteiro.

A resposta do Git tem duas partes:

[main 5bc05d8] Adiciona receita de bolo
O branch (main), o hash curto do commit novo e a mensagem nova.
Date: Thu Oct 15 10:30:00 2026 -0300
Esta linha aparece no --amend (num commit comum, não): o Git avisa que manteve a data de autoria do commit original (quinta-feira, 15 de outubro de 2026, 10:30, no fuso −03:00). Para o Git, você está corrigindo um trabalho feito naquela hora, não fazendo um trabalho novo.
1 file changed, 1 insertion(+)
O resumo do que o commit traz, comparado com o commit anterior (o do README): 1 arquivo mudado, 1 linha acrescentada. É o mesmo resumo de antes: o conteúdo não mudou, só a mensagem.
create mode 100644 bolo.txt
O commit cria o arquivo bolo.txt (o 100644 quer dizer "arquivo comum").

Agora o log:

$ git log --oneline
5bc05d8 Adiciona receita de bolo   « mensagem nova, hash novo
fe996fb Primeiro commit             « este não mudou
$ git status
No ramo main
nothing to commit, working tree clean

Ainda são dois commits, mas o de cima tem mensagem nova e hash novo: era cfa022b, virou 5bc05d8. O commit do README não mudou nada (mesmo hash). E o git status diz que não há nada a commitar e a pasta está limpa (nothing to commit, working tree clean; esta frase o Git do Ubuntu ainda não traduziu): o --amend não mexeu em nenhum arquivo da pasta.

Sem -m, o Git abre o editor

Se você digitar só git commit --amend, o Git abre o editor de texto configurado (no Ubuntu, normalmente o nano; veja git config) já com a mensagem antiga escrita. Corrija o texto, salve e feche o editor (no nano: Ctrl+O, Enter, Ctrl+X), e o commit é refeito. É o jeito mais cômodo quando a mensagem é longa e o erro é uma letra só. Se você fechar o editor com a mensagem apagada, o Git desiste e nada muda.

Missão: o último commit da Ana saiu com a mensagem "Adiciona recieta de bolo". Confira com git log --oneline e corrija a mensagem para "Adiciona receita de bolo" sem criar um terceiro commit. Depois, rode o git log --oneline de novo e compare os hashes.

2. Incluindo o arquivo que ficou de fora

Agora o outro clássico. A Ana escreveu a receita do pudim e a da calda que vai por cima, em dois arquivos. Mas só deu git add no pudim antes de commitar:

$ echo 'Pudim: 1 lata de leite condensado, 3 ovos' > pudim.txt
$ echo 'Calda: 1 xícara de açúcar' > calda.txt
$ git add pudim.txt
$ git commit -m "Adiciona receita de pudim"
[main 118e295] Adiciona receita de pudim
 1 file changed, 1 insertion(+)
 create mode 100644 pudim.txt
$ git status
No ramo main
Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	calda.txt   « ficou de fora!

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)

O git status denuncia: calda.txt ficou como "não rastreado", fora do commit. Os dois arquivos eram para estar juntos, no mesmo commit, porque são a mesma receita. A correção tem dois passos: pôr o arquivo esquecido na área de preparo, e emendar:

$ git add calda.txt
$ git commit --amend --no-edit
[main d5e44e9] Adiciona receita de pudim
 Date: Thu Oct 15 10:30:00 2026 -0300
 2 files changed, 2 insertions(+)   « agora são 2 arquivos
 create mode 100644 calda.txt
 create mode 100644 pudim.txt
$ git log --oneline
d5e44e9 Adiciona receita de pudim   « era 118e295
5bc05d8 Adiciona receita de bolo
fe996fb Primeiro commit
git add calda.txt
Coloca a calda na área de preparo. O --amend usa a área de preparo como ela está: tudo o que já estava no commit mais o que você acabou de adicionar.
--no-edit
"Não edite a mensagem": mantenha a mensagem do commit antigo. Sem essa opção (e sem -m), o Git abriria o editor.

O resumo agora diz 2 files changed: o commit novo traz o pudim e a calda. Confira com o git show:

$ git show --stat HEAD
commit d5e44e9e36d79bfb6837c3912115a4c8fbe27bde
Author: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

    Adiciona receita de pudim

 calda.txt | 1 +
 pudim.txt | 1 +
 2 files changed, 2 insertions(+)
$ git status
No ramo main
nothing to commit, working tree clean

Os dois arquivos estão no commit, a mensagem é a mesma, e o histórico continua com 3 commits. Ninguém vai saber que a calda chegou atrasada.

Dá para fazer as duas coisas de uma vez

git add calda.txt seguido de git commit --amend -m "Adiciona receitas de pudim e calda" inclui o arquivo e troca a mensagem num comando só. E o caminho contrário também existe: para tirar um arquivo que entrou por engano, tire-o do índice com git rm --cached arquivo (veja git rm) e emende.

Missão: a Ana commitou o pudim, mas a calda.txt ficou de fora (veja com git status). Coloque a calda no mesmo commit do pudim, mantendo a mensagem "Adiciona receita de pudim". No fim, devem continuar existindo só 2 commits.

3. O que aconteceu com o commit antigo?

O --amend não editou o commit antigo: commits do Git nunca mudam depois de criados (você vai entender por que em Como o Git Guarda as Coisas). Ele criou um commit novo, com o mesmo "pai" do antigo, e mudou o branch main para apontar para o novo. Em desenho:

Antes do --amend:            Depois do --amend:

A --- B   <- main            A --- B'  <- main
                                \
                                 B    (sem nome; some do git log)

O commit B continua guardado na pasta .git por um tempo (semanas), só que nenhum branch aponta mais para ele. Quem lembra dele é o reflog, o diário de onde o HEAD esteve:

$ git reflog
d5e44e9 HEAD@{0}: commit (amend): Adiciona receita de pudim
118e295 HEAD@{1}: commit: Adiciona receita de pudim     « o pudim sem a calda
5bc05d8 HEAD@{2}: commit (amend): Adiciona receita de bolo
cfa022b HEAD@{3}: commit: Adiciona recieta de bolo      « o "recieta" ainda está aqui
fe996fb HEAD@{4}: commit (initial): Primeiro commit

Leia de baixo para cima: o primeiro commit (initial), o bolo com "recieta", a emenda do bolo (commit (amend)), o pudim sem a calda, e a emenda do pudim. Os commits cfa022b e 118e295 sumiram do git log, mas não do reflog. Cada linha tem o hash e um apelido: HEAD@{0} é "onde o HEAD está agora", HEAD@{1} é "onde ele estava antes do último movimento", e assim por diante. É por isso que um --amend feito sem querer tem conserto (veja o cenário Emendei sem querer).

Formas diferentes de corrigir o último commit

SituaçãoComoResultado no histórico

Faltou um arquivo ou uma mudançagit add … e git commit --amend --no-editO último commit é substituído
Faltou um arquivo, e o commit já foi enviadogit add … e um commit novo: git commit -m "Inclui calda do pudim"Um commit a mais; nada é reescrito

Qual usar: enquanto o commit está só no seu computador, --amend sem medo. Depois do git push, prefira um commit novo de correção (ou o git revert, se a ideia é desfazer).

Quando dá errado

Não há commit para emendar 
$ git add a.txt
$ git commit --amend -m "Primeiro commit"
fatal: You have nothing to amend.

"Você não tem nada para emendar" (esta mensagem sai em inglês mesmo com o sistema em português). Num repositório recém-criado, sem nenhum commit, não existe "último commit" para corrigir. Como resolver: faça o primeiro commit normalmente (git commit -m "…", sem --amend).

Emendei sem querer (ou emendei o commit errado)

A Ana queria fazer um commit novo, mas digitou --amend por hábito e engoliu as mudanças no commit anterior. O commit antigo ainda está no reflog: HEAD@{1} é "onde o HEAD estava antes do amend". Para voltar o branch para ele sem perder as mudanças:

$ echo 'Brigadeiro' > brigadeiro.txt
$ git add brigadeiro.txt
$ git commit --amend -m "Adiciona receita de brigadeiro"   « ops: era para ser um commit novo
[main 5c490a1] Adiciona receita de brigadeiro
 Date: Thu Oct 15 10:30:00 2026 -0300
 3 files changed, 3 insertions(+)
 create mode 100644 brigadeiro.txt
 create mode 100644 calda.txt
 create mode 100644 pudim.txt
$ git log --oneline
5c490a1 Adiciona receita de brigadeiro   « o pudim "virou" brigadeiro
5bc05d8 Adiciona receita de bolo
fe996fb Primeiro commit
$ git reset --soft HEAD@{1}
$ git log --oneline
d5e44e9 Adiciona receita de pudim        « o pudim voltou
5bc05d8 Adiciona receita de bolo
fe996fb Primeiro commit
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	new file:   brigadeiro.txt   « o brigadeiro esperando o commit dele

$ git commit -m "Adiciona receita de brigadeiro"
[main b100c98] Adiciona receita de brigadeiro
 1 file changed, 1 insertion(+)
 create mode 100644 brigadeiro.txt
$ git log --oneline
b100c98 Adiciona receita de brigadeiro
d5e44e9 Adiciona receita de pudim
5bc05d8 Adiciona receita de bolo
fe996fb Primeiro commit

O resumo 3 files changed denunciou o engano: o commit "do brigadeiro" levou junto a calda e o pudim, porque ele substituiu o commit do pudim. O git reset --soft HEAD@{1} põe o main de volta no commit de antes do amend e deixa as mudanças do amend na área de preparo, prontas para o commit novo que ela queria fazer. O reset e o --soft são explicados em git reset e reset --soft, --mixed e --hard.

Emendei um commit que já tinha enviado (push rejeitado) 
$ git push -q -u origin main          « o commit do brigadeiro foi para o GitHub
$ git commit --amend -m "Adiciona a receita de brigadeiro"
[main 608fade] Adiciona a receita de brigadeiro
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+)
 create mode 100644 brigadeiro.txt
$ git push
To https://github.com/ana-souza/receitas.git
 ! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs to 'https://github.com/ana-souza/receitas.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart. If you want to integrate the remote changes,
hint: use 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

(O GitHub desta sessão é o "GitHub de mentira" do laboratório do guia, que se comporta como o de verdade.) [rejected] = "recusado"; non-fast-forward quer dizer que o seu main não é uma continuação do main do GitHub. As dicas (hint:) dizem: "as atualizações foram recusadas porque a ponta do seu branch atual está atrás da sua equivalente remota; se você quer integrar as mudanças remotas, use git pull antes de enviar de novo". O GitHub tem o commit antigo (b100c98); o seu computador tem o emendado (608fade) no lugar dele. Para o Git, os dois históricos divergiram, e o git push recusa para não apagar o commit que está lá. Atenção: aqui o git pull sugerido não é a solução, porque juntaria o commit antigo e o emendado, e a receita apareceria duas vezes no histórico. Como resolver:

  • se o repositório é só seu e ninguém baixou o commit antigo, dá para forçar com git push --force-with-lease (veja push --force-with-lease);
  • se outras pessoas trabalham no mesmo branch, não force: desfaça o amend com git reset --soft HEAD@{1} (como no cenário anterior), o que deixa o seu branch igual ao do GitHub, e faça a correção num commit novo. Essa é a regra de ouro: não reescreva o que já é público.
Esqueci o git add antes do --amend 
$ echo 'Granulado' > granulado.txt
$ git commit --amend --no-edit
[main b100c98] Adiciona receita de brigadeiro
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+)
 create mode 100644 brigadeiro.txt   « nada de granulado.txt
$ git status
No ramo main
Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	granulado.txt

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)

O --amend usa a área de preparo, não a pasta. Como o granulado.txt não foi adicionado, o commit foi refeito sem ele, e o git status continua mostrando o arquivo como não monitorado. Não estragou nada: o commit refeito saiu igual ao anterior. (Aqui saiu até com o mesmo hash, b100c98, porque no laboratório do guia o relógio é fixo; no seu computador a hora do commit muda, e o hash também.) Como resolver: git add granulado.txt e git commit --amend --no-edit de novo.

Resumo

  • git commit --amend refaz o último commit com o que está na área de preparo; -m troca a mensagem, --no-edit mantém a antiga, e sem nenhum dos dois o Git abre o editor.
  • Para incluir um arquivo esquecido: git add arquivo e git commit --amend --no-edit.
  • O commit corrigido é um commit novo, com hash novo; o antigo some do git log, mas fica no git reflog (e dá para voltar com git reset --soft HEAD@{1}).
  • Emende à vontade o que ainda não foi enviado. Depois do git push, prefira um commit novo de correção.

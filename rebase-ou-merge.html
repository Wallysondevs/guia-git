Git Rebase ou Merge?

Você já conhece os dois jeitos de juntar o trabalho de um branch com outro: o git merge, que junta os dois caminhos com um commit de merge, e o git rebase, que refaz os seus commits em cima do outro branch, como se você tivesse começado depois. Os dois chegam aos mesmos arquivos no fim. O que muda é o histórico que fica para contar a história. Esta aula põe os dois lado a lado, na mesma situação, para você saber qual escolher.

Você vai aprender
  • A mesma situação resolvida com merge e com rebase, e o histórico real que cada um deixa.
  • O que muda de verdade: commits novos, hashes, conflitos e o que acontece com quem já baixou seus commits.
  • A regra prática que a maioria das equipes usa: rebase no que é só seu, merge no que é de todos.
  • Como o git pull pergunta qual dos dois você quer, e como responder de uma vez por todas (pull.rebase).

Todas as sessões desta aula rodaram no Git real do Ubuntu, na máquina da Ana (usuária ana, computador notebook), com as mensagens em português. Algumas mensagens saem em inglês (como Already on 'main' e as dicas hint:) ou em português de Portugal ("submissão"): a tradução do Git no Ubuntu é parcial (veja a nota em Seu Primeiro Commit).

A ideia: o diário de viagem e o livro da viagem

A Ana e o Bruno viajaram juntos, mas passaram dois dias separados: ela foi à praia e ele foi à serra. Na volta, cada um tinha anotações no seu caderno. Há dois jeitos de juntar tudo num caderno só:

  • O diário honesto (merge): cola as páginas dos dois cadernos como foram escritas, cada uma com a sua data, e acrescenta uma página dizendo "aqui os dois caminhos se juntaram". Quem ler vê que houve dois caminhos paralelos. Nada foi reescrito.
  • O livro passado a limpo (rebase): reescreve as anotações da Ana como se ela tivesse viajado depois do Bruno, numa sequência só, sem a bifurcação. Fica mais fácil de ler, mas as páginas da Ana foram reescritas: não são mais as originais.

Nenhum dos dois está errado. O diário mostra o que aconteceu; o livro mostra uma história arrumada. A pergunta é: o que é mais útil para quem vai ler depois, e alguém já tinha uma cópia das páginas originais?

O desenho do --graph mostra exatamente a bifurcação: os commits C e D com os hashes originais (ca05c9e e 585943c), o X, e um commit novo, o commit de merge (M), com dois pais, que junta os caminhos:

          C---D

    A---B---X---M   main
  • Nenhum commit que já existia mudou.
  • Apareceu um commit a mais, o de merge (veja Merge de Três Vias).
  • Se houvesse conflito, a Ana resolveria uma vez, no commit de merge.

3. Jeito 2: rebase (e depois um merge que só avança)

$ git switch pudim
Switched to branch 'pudim'
$ git rebase main
Successfully rebased and updated refs/heads/pudim.
$ git switch main
Switched to branch 'main'
$ git merge pudim
Updating f724d33..340b09d
Fast-forward

$ git log --oneline --graph
* 340b09d (HEAD -> main, pudim) Adiciona os ingredientes do pudim   « hash novo
* 3e0849a Adiciona a receita de pudim             « hash novo
* f724d33 Corrige o título do README
* 818e38e Adiciona a receita de bolo
* 0cea70a Cria o README
git rebase main
No branch pudim: "refaça os meus commits em cima da ponta do main". Enquanto trabalha, o Git mostra rapidinho Rebasing (1/2), Rebasing (2/2) na mesma linha, e no fim fica "rebase feito com sucesso, refs/heads/pudim atualizado" (Successfully rebased and updated).
Updating f724d33..340b09d / Fast-forward
De volta ao main, o merge só precisou avançar o main de f724d33 até 340b09d: o pudim agora está "na frente" do main, na mesma linha. É o fast-forward ("avanço rápido").

Agora o histórico é uma linha reta:

    A---B---X---C'---D'   main, pudim
  • O C e o D foram refeitos em cima do X: viraram C' e D', com hashes novos (compare os hashes das duas sessões).
  • Não existe commit de merge. O git merge pudim no fim foi um fast-forward: o main só andou para frente.
  • Se houvesse conflito, a Ana poderia ter de resolver commit por commit (veja Conflitos no Rebase).

Os arquivos são os mesmos

$ diff -r --exclude=.git receitas-merge receitas-rebase && echo 'nenhuma diferença'
nenhuma diferença
$ ls receitas-merge receitas-rebase
receitas-merge:
README.md  bolo.txt  pudim.txt

receitas-rebase:
README.md  bolo.txt  pudim.txt

O diff -r compara as duas pastas inteiras (o --exclude=.git deixa de fora a pasta escondida do Git, onde o histórico é diferente). Ele não mostrou nada, então o echo rodou.

Nenhuma diferença nos arquivos: as duas pastas chegaram ao mesmo lugar. Merge e rebase discordam só sobre como contar a história.

Missão: o main e o pudim se separaram. Traga o pudim para o main deixando o histórico em linha reta, sem commit de merge: faça o rebase do pudim em cima do main e depois avance o main. Confira com git log --oneline --graph. (Se você fizer só git merge pudim no main, vai aparecer um commit de merge, e o main fica com um commit a mais do que a missão pede.)

5. A regra prática

A maioria das equipes usa os dois, cada um no seu lugar:

  1. Rebase no que é só seu. Antes de mostrar o seu branch para alguém (antes do primeiro push, ou antes de abrir um pull request), traga as novidades do main com rebase e, se quiser, arrume os seus commits com o rebase interativo. Ninguém tinha cópia desses commits, então reescrever não atrapalha ninguém.
  2. Merge no que é de todos. Para juntar um branch pronto no main compartilhado, e sempre que os commits já foram enviados e outras pessoas podem ter baixado, use merge. Ele não reescreve nada.
A frase para decorar

Nunca faça rebase de commits que já estão num repositório compartilhado e que outras pessoas podem ter baixado. A próxima aula, A Regra de Ouro, mostra o estrago que isso faz, com as mensagens reais do Git.

No GitHub, o botão de juntar um pull request oferece as duas filosofias (ilustrativo, conforme a documentação em docs.github.com): Create a merge commit (merge), Squash and merge (junta todos os commits num só; veja squash) e Rebase and merge (refaz cada commit no branch de destino, com hashes novos). A equipe escolhe uma e usa sempre a mesma.

6. O git pull também pergunta: merge ou rebase?

O git pull é um git fetch seguido de um jeito de juntar. Quando o seu branch e o do servidor se separaram (você tem commits que o servidor não tem, e vice-versa), o Git precisa saber se junta com merge ou com rebase. Sem nenhuma configuração, ele se recusa a escolher por você.

No exemplo, o repositório receitas da Ana está no GitHub (o "GitHub de mentira" do lab). O Bruno clonou, acrescentou as cenouras ao bolo e enviou. Ao mesmo tempo, a Ana commitou a receita de pudim no computador dela, sem saber do commit do Bruno:

O commit da Ana foi refeito depois do commit do Bruno, em linha reta, e agora ela está 1 commit à frente do GitHub: é só dar git push. O commit do Bruno não foi tocado; o único commit reescrito foi o dela, que ainda não tinha saído do computador.

O pull --rebase é um uso seguro do rebase: os commits refeitos são os seus, que ainda não saíram do seu computador. Muita gente configura git config --global pull.rebase true justamente para não encher o histórico de merges do tipo Merge branch 'main' of ….

Quando dá errado

Pediu "só avanço rápido", mas os branches se separaram

No repositório receitas, a Ana tem o branch chocolate (com o pudim de chocolate), e o main ganhou um commit depois disso ("Adiciona os ovos ao bolo"). No main, ela tentou juntar exigindo linha reta:

$ git merge --ff-only chocolate
hint: Diverging branches can't be fast-forwarded, you need to either:
hint:
hint: 	git merge --no-ff
hint:
hint: or:
hint:
hint: 	git rebase
hint:
hint: Disable this message with "git config set advice.diverging false"
fatal: Not possible to fast-forward, aborting.

"Branches que divergiram não podem avançar rápido; você precisa ou fazer git merge --no-ff, ou git rebase." E: "Não é possível avançar rápido; abortando". Nada mudou. É exatamente a escolha desta aula: o Git está perguntando se você quer o commit de merge ou a linha reta. Como resolver: para merge, rode git merge chocolate (sem o --ff-only); para linha reta, vá para o chocolate, faça git rebase main e volte para o main para o merge.

Fez rebase num branch que já tinha enviado

O chocolate já estava no GitHub (a Ana tinha dado git push -u origin chocolate). Ela fez o rebase mesmo assim e tentou enviar:

Não quer configurar nada agora

O fatal: Need to specify how to reconcile divergent branches. da seção 6 aparece em todo git pull com branches separados até você escolher. Se não quiser decidir de uma vez por todas, escolha a cada vez no próprio comando: git pull --rebase ou git pull --no-rebase. Para ver o que está configurado: git config pull.rebase (sem resposta = nada configurado).

6. Qual destas é uma vantagem do merge sobre o rebase?

Resumo

  • Merge e rebase chegam aos mesmos arquivos; muda o histórico.
  • Merge mantém os commits como foram feitos e acrescenta um commit de merge com dois pais. É seguro para o que é compartilhado.
  • Rebase refaz os seus commits em cima do outro branch (hashes novos) e deixa uma linha reta. Use no que é só seu.
  • Regra prática: rebase antes de compartilhar, merge depois. Nunca rebase em commits que outras pessoas já baixaram.
  • O git pull com branches separados pede uma escolha: pull.rebase true, false ou pull.ff only.

Git bisect

Na versão 1.0, a calculadora de ovos do site de receitas da Ana funcionava: 2 formas de bolo de cenoura, 6 ovos. Hoje ela diz 5 ovos. Entre a 1.0 e hoje há vários commits, e ninguém lembra qual deles estragou a conta. Abrir um por um daria trabalho. O Git tem um comando que acha o culpado fazendo perguntas: o git bisect (de "bissecção", cortar ao meio). Você diz um commit bom e um ruim; ele vai cortando o caminho ao meio até sobrar um só.

Você vai aprender
  • A ideia da busca binária: por que poucos testes bastam para muitos commits.
  • Uma sessão completa à mão: git bisect start, bad, good, até o Git dizer is the first bad commit, e o git bisect reset.
  • Como ver o que foi respondido (git bisect log) e o estado do repositório durante a busca.
  • Como deixar o Git testar sozinho com git bisect run e um script de teste.
  • Os erros reais: bom e ruim trocados, resposta errada, esquecer o reset.

Todos os comandos desta aula rodaram no Git 2.53 do Ubuntu da Ana (usuária ana, computador notebook). As mensagens do git bisect ainda não têm tradução para o português nessa versão e saem em inglês; a aula traduz cada uma.

A ideia: adivinhar um número de 1 a 100

Alguém pensou num número de 1 a 100, e só responde "maior" ou "menor". Chutar 1, 2, 3… pode levar 100 tentativas. O jeito esperto é chutar o meio: 50. "Menor." Agora sobrou de 1 a 49: chute 25. "Maior." Sobrou de 26 a 49: chute 37… A cada pergunta, metade das possibilidades vai embora. Em no máximo 7 perguntas você acha qualquer número de 1 a 100. Isso é a busca binária.

O git bisect faz o mesmo com os commits. Você diz:

  • um commit ruim (bad): onde o defeito já existe, normalmente o atual;
  • um commit bom (good): onde tudo funcionava, por exemplo a tag v1.0.

O Git coloca na pasta o commit do meio do caminho e pergunta, em silêncio: "e aqui, está bom ou ruim?". Você testa e responde. Ele corta o caminho pela metade e repete, até sobrar o primeiro commit ruim, o que introduziu o defeito.

bom                                              ruim
 v1.0 ── c1 ── c2 ── c3 ── c4 ── c5 ── HEAD
                     ▲
              1º teste: o meio. Se estiver ruim, o defeito está de c3 para trás;
              se estiver bom, de c4 para a frente. Metade do caminho foi descartada.

Começa a busca. status: waiting for both good and bad commits: "esperando um commit bom e um ruim".
git bisect bad
"O commit atual é ruim." Sem nada depois, vale para o HEAD (aqui, a06fdb5, onde a Ana viu o 5 ovos). status: waiting for good commit(s), bad commit known: "esperando commit(s) bom(ns); o ruim já é conhecido".
git bisect good v1.0
"A v1.0 é boa." Pode ser uma tag, um hash (79398d7) ou um branch.
Bisecting: 2 revisions left to test after this (roughly 2 steps)
"Bissectando: depois deste, restam 2 commits para testar (cerca de 2 passos)."
[95263d8…] Adiciona receita de quindim
O commit do meio do caminho, que o Git acabou de colocar na sua pasta. Os arquivos agora estão como estavam nesse commit. É ele que você vai testar.

2.3 Durante a busca: onde estou?

Enquanto o bisect não termina (e mesmo depois de achar o culpado, até o reset), o repositório fica num estado especial. O git status avisa:

$ git status
HEAD detached at 9abbd4a
You are currently bisecting, started from branch 'main'.
  (use "git bisect reset" para voltar ao ramo original)

nothing to commit, working tree clean
HEAD detached at 9abbd4a
"HEAD destacado em 9abbd4a": você não está em nenhum branch, e sim num commit solto, o último que o Git colocou na pasta (veja HEAD Destacado).
You are currently bisecting, started from branch 'main'.
"Você está no meio de um bisect, começado a partir do branch main."
(use "git bisect reset" para voltar ao ramo original)
A dica de saída, meio em inglês, meio em português: use git bisect reset para voltar ao branch original.

2.4 Terminar: git bisect reset

$ git bisect reset
Previous HEAD position was 9abbd4a Adiciona receita de brigadeiro
Switched to branch 'main'
$ git status
No ramo main
nothing to commit, working tree clean

"A posição anterior do HEAD era 9abbd4a… Trocou para o branch main." A Ana está de volta onde começou, com todos os commits. Agora ela pode consertar a conta num commit novo (ou desfazer o culpado com git revert). Sempre termine com git bisect reset, inclusive quando desistir no meio.

Missão: no repositório receitas, sh formas.sh 2 diz 5 ovos, mas na tag v1.0 dizia 6 ovos. Ache o commit culpado com git bisect: git bisect start, git bisect bad, git bisect good v1.0; depois, a cada passo, rode sh formas.sh 2 e responda git bisect good (6 ovos) ou git bisect bad (5 ovos), até aparecer is the first bad commit. Não esqueça do git bisect reset depois de ler o resultado.

3. Deixe o Git testar sozinho: git bisect run

Responder à mão é fácil com 3 passos, mas cansa com 10 e é fácil errar uma resposta. Se o teste pode ser feito por um script, o Git roda o script em cada passo e decide sozinho pelo código de saída dele (o $?): 0 quer dizer bom; 1 (ou outro número de 1 a 127, menos o 125) quer dizer ruim. A Ana escreveu um teste de 3 linhas:

$ cat teste.sh
#!/bin/sh
# Teste: 2 formas precisam de 6 ovos
resultado=$(sh formas.sh 2)
echo "Testando: $resultado"
[ "$resultado" = "Para 2 formas: 6 ovos" ]
$ sh teste.sh
Testando: Para 2 formas: 5 ovos
$ echo $?
1                                          « 1 = ruim, como esperado no commit atual
$ git status --short
?? teste.sh                                « o teste não é rastreado: ele não muda quando o Git troca de commit

A última linha do script, [ … = … ], compara o resultado com o esperado e devolve 0 se for igual e 1 se for diferente; como é a última, esse vira o código de saída do script. O teste.sh fica fora do Git de propósito (?? = não rastreado): se ele estivesse no histórico, em commits antigos ele nem existiria.

$ git bisect start HEAD v1.0
Bisecting: 2 revisions left to test after this (roughly 2 steps)

Os códigos de saída que o bisect run entende

0 = bom · 1 a 127, exceto 125 = ruim · 125 = "não dá para testar este commit, pule" (o mesmo que git bisect skip) · acima de 127 = interrompe a busca. Use o 125 quando um commit nem compila ou não tem o arquivo que o teste usa. (Fonte: a documentação oficial, git-scm.com/docs/git-bisect.)

Palavras diferentes de bom/ruimgit bisect old / git bisect newQuando você procura uma mudança que não é um defeito ("quando a receita passou a usar forno elétrico?"): old = antes da mudança, new = depois.

Sem o bisect, a alternativa é procurar o culpado por pistas: git blame (quem mudou esta linha?) e git log -S (em que commit este texto apareceu?). Eles são ótimos quando você sabe qual linha está errada; o bisect brilha quando você só sabe que algo está errado.

Quando dá errado

Respondi errado no meio do caminho

Numa primeira tentativa, a Ana se distraiu: o quindim deu 5 ovos e ela respondeu good.

$ sh formas.sh 2
Para 2 formas: 5 ovos
$ git bisect good                          « resposta errada: 5 ovos é ruim
Bisecting: 0 revisions left to test after this (roughly 1 step)
[809abb21fa431f5ee7962533ea8fb571f6c99089] Adiciona receita de mousse

Ela continuou respondendo certo dali em diante, e o Git acusou um inocente:

$ sh formas.sh 2
Para 2 formas: 5 ovos
$ git bisect bad
Bisecting: 0 revisions left to test after this (roughly 0 steps)
[05b0fcf7c89b8d4938c1f186c63d8bbd631a2ebb] Melhora a descrição do README
$ sh formas.sh 2
Para 2 formas: 5 ovos
$ git bisect bad
05b0fcf7c89b8d4938c1f186c63d8bbd631a2ebb is the first bad commit
commit 05b0fcf7c89b8d4938c1f186c63d8bbd631a2ebb
Author: Ana Souza <ana@exemplo.com>

    Melhora a descrição do README

 README.md | 2 ++

O que aconteceu: o Git confia nas respostas. Um good errado descarta justamente a metade onde estava o culpado. Como desconfiar: o "culpado" só mexeu no README.md, que nada tem a ver com a conta. Como confirmar: o git bisect log mostra cada resposta com o commit. Como resolver: git bisect reset e comece de novo, com mais atenção, ou use o git bisect run, que não se distrai.

Troquei o bom e o ruim 
$ git bisect start
status: waiting for both good and bad commits
$ git bisect good
status: waiting for bad commit, 1 good commit known
$ git bisect bad v1.0
Some good revs are not ancestors of the bad rev.
git bisect cannot work properly in this case.
Maybe you mistook good and bad revs?

"Alguns commits bons não são ancestrais do commit ruim. O git bisect não funciona direito nesse caso. Será que você confundiu os bons e os ruins?" O bom tem de ser mais antigo que o ruim. Como resolver: git bisect reset e recomece na ordem certa. Se você está procurando quando algo passou a funcionar (o contrário de um defeito), use as palavras old e new, que não confundem.

Esqueci o git bisect reset

Sintoma: o git status mostra HEAD detached at … e You are currently bisecting, e os seus commits mais novos "sumiram" da pasta. Eles não sumiram: a pasta só está num commit antigo. Como resolver: git bisect reset leva você de volta ao branch onde começou. Não faça commits durante o bisect: eles ficariam num HEAD destacado.

You need to start by "git bisect start" 
$ git bisect bad
You need to start by "git bisect start"

Do you want me to do it for you [Y/n]? n

"Você precisa começar com git bisect start. Quer que eu faça isso por você [S/n]?" Você respondeu good ou bad sem ter começado (ou depois do reset). Responder Enter ou Y começa o bisect ali mesmo; com n, nada acontece. (Quando o Git não está ligado a um terminal, como num script, ele não faz a pergunta.)

O teste do bisect run sumiu no meio do caminho

Se o script de teste é um arquivo rastreado e foi criado depois do commit bom, nos commits antigos ele não existe: o sh teste.sh falha com "arquivo não encontrado", e o Git conta isso como ruim. Resultado errado, sem aviso. Como evitar: deixe o teste fora do repositório (../teste.sh) ou não rastreado, como a Ana fez.

Resumo

  • git bisect acha o commit que introduziu um defeito por busca binária: a cada teste, metade dos suspeitos é descartada (1000 commits ≈ 10 testes).
  • À mão: git bisect start, git bisect bad (o atual), git bisect good v1.0; teste o commit que o Git colocou na pasta e responda good ou bad até aparecer is the first bad commit.
  • Durante a busca você está num HEAD destacado; git bisect log mostra as respostas; git bisect reset termina e volta ao branch.
  • Automático: git bisect start RUIM BOM e git bisect run sh teste.sh; o script responde pelo código de saída (0 bom, 125 pular, 1–127 ruim). Deixe o teste fora do Git.
  • Uma resposta errada leva a um culpado errado; bom e ruim trocados dão Maybe you mistook good and bad revs?.

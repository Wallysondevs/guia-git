Git Recuperando Commits Perdidos

A Ana rodou um git reset --hard no lugar errado e dois commits do site de receitas sumiram do git log. Em outro dia, apagou um branch com -D achando que já tinha juntado tudo. Respire: quase nada que foi commitado se perde de verdade no Git. Os commits continuam guardados por semanas; o que se perdeu foi só o "caminho" até eles. Esta aula é o kit de resgate: como achar esse caminho de volta em cada situação.

Você vai aprender
  • Por que um commit "sumido" quase sempre ainda existe, e por quanto tempo.
  • A receita de resgate: achar o hash (com o git reflog) e pendurar uma etiqueta nele (um branch).
  • Como recuperar depois de um reset --hard, de um branch -D e de um commit --amend.
  • Como achar até um stash descartado, com git fsck.
  • O que o Git não consegue recuperar.

A ideia: a foto não sumiu, sumiu a etiqueta

Lembre de como o Git guarda as coisas: cada commit é uma fotografia guardada numa caixa, e os branches são etiquetas coladas em algumas fotos. O git log começa na etiqueta e vai seguindo as fotos para trás.

Quando você faz um reset --hard ou apaga um branch, o Git não joga a foto fora: ele só descola a etiqueta. A foto fica no fundo da caixa, sem ninguém apontando para ela. Para o git log, ela "sumiu". Para recuperar, basta descobrir o número da foto (o hash) e colar uma etiqueta nova nela.

E quem lembra o número da foto? O reflog, o diário do HEAD: cada vez que o HEAD ou um branch se move (commit, reset, switch, merge, amend…), o Git anota de onde para onde ele foi.

Por quanto tempo dá para recuperar?

Pela documentação oficial do git gc (git-scm.com/docs/git-gc), as anotações do reflog duram, por padrão, 90 dias, ou 30 dias quando apontam para commits que nenhum branch alcança mais. Depois disso, a faxina automática (git gc) pode apagar os commits sem etiqueta. Na prática: resgate logo, e não rode faxinas "para liberar espaço" enquanto procura algo.

Caso 1: o reset --hard levou dois commits

O repositório da Ana tinha três commits. Ela queria descartar uma mudança no arquivo, mas digitou HEAD~2:

$ git log --oneline
42fd4f8 Adiciona pudim
095ebcf Adiciona bolo de cenoura
0cea70a Cria o README
$ git reset --hard HEAD~2
HEAD is now at 0cea70a Cria o README             « "o HEAD agora está em 0cea70a"
$ git log --oneline
0cea70a Cria o README                            « cadê o bolo e o pudim?!
$ ls
README.md

O git log mostra só o primeiro commit, e os arquivos bolo.txt e pudim.txt sumiram da pasta. Agora, o diário:

$ git reflog
0cea70a HEAD@{0}: reset: moving to HEAD~2        « o movimento errado
42fd4f8 HEAD@{1}: commit: Adiciona pudim         « onde a Ana estava antes!
095ebcf HEAD@{2}: commit: Adiciona bolo de cenoura
0cea70a HEAD@{3}: commit (initial): Cria o README

(As descrições do reflog, como reset: moving to, "reset: movendo para", são sempre em inglês, mesmo com o sistema em português.)

Lendo de cima para baixo (do mais novo para o mais antigo):

  • HEAD@{0} é onde o HEAD está agora; a anotação diz que ele chegou lá por um reset: moving to HEAD~2.
  • HEAD@{1} é onde ele estava um movimento antes: o commit "Adiciona pudim". É exatamente o que a Ana perdeu.
  • As linhas de baixo são os commits, na ordem em que foram feitos.

Resgatando: duas formas

Forma segura: pendure uma etiqueta nova (um branch) no commit perdido. Nada na sua pasta muda, e você olha com calma:

$ git branch resgate HEAD@{1}                    « nenhuma mensagem = deu certo
$ git log --oneline resgate
42fd4f8 Adiciona pudim                           « os commits voltaram a ter etiqueta
095ebcf Adiciona bolo de cenoura
0cea70a Cria o README

Pronto: os commits estão salvos no branch resgate. Agora você pode olhar com git show, trazer só um arquivo, ou juntar com git merge resgate.

Forma direta: se você tem certeza de que quer voltar exatamente para onde estava, mova o main de volta com o próprio reset --hard, apontando para a entrada do diário:

$ git status
No ramo main
nothing to commit, working tree clean           « nada a perder: pode seguir
$ git reset --hard HEAD@{1}
HEAD is now at 42fd4f8 Adiciona pudim
$ git log --oneline
42fd4f8 Adiciona pudim
095ebcf Adiciona bolo de cenoura
0cea70a Cria o README
$ ls
README.md  bolo.txt  pudim.txt                   « os arquivos voltaram

Como o branch resgate já não é necessário, a Ana o apagou com git branch -d resgate (o Git respondeu Deleted branch resgate (was 42fd4f8)., "branch resgate apagado, era 42fd4f8").

git reset --hard
Move o branch atual para o commit indicado e deixa a pasta igual a ele (veja os modos do reset).
HEAD@{1}
"Onde o HEAD estava um movimento atrás", segundo o reflog. Você também pode usar o hash que aparece na linha (os 7 caracteres do começo).
Cuidado: o reset --hard apaga o que não foi commitado

Antes de qualquer reset --hard de resgate, rode git status. Se houver mudanças não commitadas, elas se perdem de verdade (essas não vão para o reflog). Na dúvida, prefira a forma segura, com git branch.

Os números mudam a cada movimento

HEAD@{1} é relativo: depois do resgate, o próprio resgate vira HEAD@{0} e todo o resto desce uma posição. Por isso, sempre rode git reflog de novo antes de usar um HEAD@{n}, ou copie o hash, que nunca muda.

Missão: um reset --hard fez o main perder os commits do bolo e do pudim. Use o git reflog para achar onde o HEAD estava antes e traga o main de volta para lá (3 commits, o último sendo "Adiciona pudim").

Caso 2: apaguei um branch com -D

A Ana criou o branch sobremesas, fez um commit nele, voltou para o main e apagou o branch sem juntar. O -d minúsculo teria recusado; o -D maiúsculo apaga sem perguntar (veja Renomeando e Apagando Branches):

$ git switch -c sobremesas
Switched to a new branch 'sobremesas'
$ echo 'Mousse de maracujá' > mousse.txt
$ git add mousse.txt
$ git commit -m 'Adiciona mousse'
[sobremesas 0b9c470] Adiciona mousse
 1 file changed, 1 insertion(+)
 create mode 100644 mousse.txt
$ git switch main
Switched to branch 'main'
$ git branch -d sobremesas
error: the branch 'sobremesas' is not fully merged                « o -d avisou!
hint: If you are sure you want to delete it, run 'git branch -D sobremesas'
hint: Disable this message with "git config set advice.forceDeleteBranch false"
$ git branch -D sobremesas
Deleted branch sobremesas (was 0b9c470).                          « a pista: o hash
$ git branch
* main

O -d recusou com the branch 'sobremesas' is not fully merged ("o branch não foi totalmente juntado") e a dica sugeriu o -D. A Ana seguiu a dica sem pensar, e o branch se foi.

Repare na própria mensagem do Git: entre parênteses vem o hash do commit para onde o branch apontava (era …). O Git deixou a pista de propósito! Se a mensagem ainda está na tela, o resgate é uma linha:

$ git branch sobremesas 0b9c470
$ git log --oneline sobremesas
0b9c470 Adiciona mousse                          « o branch voltou, com o commit
42fd4f8 Adiciona pudim
095ebcf Adiciona bolo de cenoura
0cea70a Cria o README

Se a mensagem já sumiu da tela, o reflog também guarda a pista. Logo depois de apagar o branch, as três últimas anotações eram estas (-3 limita a três linhas):

$ git reflog -3
42fd4f8 HEAD@{0}: checkout: moving from sobremesas to main     « saiu do branch
0b9c470 HEAD@{1}: commit: Adiciona mousse                      « a ponta do branch apagado
42fd4f8 HEAD@{2}: checkout: moving from main to sobremesas

Procure a linha checkout: moving from sobremesas to … ("saindo de sobremesas para…"): o commit logo abaixo dela é a ponta do branch apagado, aqui o 0b9c470 (ou HEAD@{1}).

Missão: o branch sobremesas foi apagado com -D antes de ser juntado. Use o git reflog para achar o commit "Adiciona mousse" e crie o branch sobremesas de novo apontando para ele. Confira com git log --oneline sobremesas.

Caso 3: o --amend trocou um commit que eu queria

O --amend não edita o commit: ele cria um novo e move o branch para ele. O antigo fica sem etiqueta, mas o reflog o anota:

$ echo 'Pudim de leite condensado' > pudim.txt
$ git commit -q -am 'Muda o pudim'
$ git commit --amend -m 'Troca o pudim por pudim de leite condensado'
[main e54a538] Troca o pudim por pudim de leite condensado
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git reflog -3
e54a538 HEAD@{0}: commit (amend): Troca o pudim por pudim de leite condensado
deda689 HEAD@{1}: commit: Muda o pudim             « o commit de antes do amend
42fd4f8 HEAD@{2}: checkout: moving from sobremesas to main
$ git show HEAD@{1} --stat --oneline
deda689 Muda o pudim                               « ainda existe, inteiro
 pudim.txt | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

A linha commit (amend) é o commit novo; a de baixo, o antigo. Para ver o conteúdo antigo sem mudar nada, use git show com HEAD@{1}; para recuperá-lo, o mesmo git branch nome HEAD@{1} do caso 2.

Caso 4: descartei um stash

O stash também é guardado como commits. Um git stash drop (ou um pop que você desfez sem querer) não fica no reflog do HEAD, mas o Git mostra o hash ao descartar, e o git fsck encontra commits "pendurados", sem etiqueta nenhuma:

$ echo '- 3 ovos' >> bolo.txt
$ git stash
Saved working directory and index state WIP on main: e54a538 Troca o pudim por pudim de leite condensado
$ git stash drop
Dropped refs/stash@{0} (2e8e399d650d551e3975b74d9adbf5674a03d4bb)      « o hash, de novo!
$ git stash list
$ git fsck --unreachable
unreachable blob d70e7e4c64260a3d2e182ed7abe38fc98980afa2
unreachable commit ea0090f0554c16b927307c219232fe90aa5f5862
unreachable commit 2e8e399d650d551e3975b74d9adbf5674a03d4bb          « o stash descartado
unreachable tree 743c0c7a63803359e227cc1c800a502ba35df18d

O git stash drop respondeu Dropped refs/stash@{0} (2e8e399…), "descartei o stash 0", e entre parênteses veio o hash completo. Na lista do fsck, unreachable quer dizer "inalcançável": ninguém aponta para esses objetos. Há dois commits porque o stash guarda dois: um com a área de preparo (ea0090f…) e o stash propriamente dito (2e8e399…), que é o que aparece na mensagem do drop. O blob é o conteúdo novo do bolo.txt e a tree, a "foto da pasta" do stash. Repare que o commit deda689 do caso 3 não aparece: o reflog ainda aponta para ele, então ele não é inalcançável.

$ git stash apply 2e8e399
No ramo main
Changes not staged for commit:
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   bolo.txt                     « a mudança voltou para a pasta

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
$ git diff
diff --git a/bolo.txt b/bolo.txt
index 8f830cf..d70e7e4 100644
--- a/bolo.txt
+++ b/bolo.txt
@@ -1 +1,2 @@
 Bolo de cenoura
+- 3 ovos
git fsck
"File system check": confere a integridade do repositório e lista objetos soltos.
--unreachable
Mostra os objetos que nenhum branch, tag ou reflog alcança. Os de tipo commit são candidatos a resgate. (A opção --lost-found faz algo parecido e ainda copia os achados para .git/lost-found/.)

Com o hash na mão, git stash apply HASH devolve as mudanças à pasta, como se o stash nunca tivesse sido descartado.

O que o Git não recupera

SituaçãoDá para recuperar?Por quê
Commit depois de reset --hard, branch -D, --amend, rebaseSim, pelo reflogO commit existe; só perdeu a etiqueta.
Stash descartadoSim, pelo hash do drop ou com git fsckO stash é um commit.
Arquivo que passou por git add, mas nunca foi commitadoÀs vezes, com git fsck --lost-foundO conteúdo virou um objeto (blob), mas sem nome de arquivo.
Mudança que nunca passou por add nem commit, descartada com restore, reset --hard ou cleanNãoO Git nunca a viu. (Talvez o seu editor tenha um histórico local.)
Commit sem etiqueta há meses, depois de um git gcProvavelmente nãoA faxina apaga o que expirou no reflog.

Moral: commite cedo e com frequência. O que foi commitado é quase impossível de perder; o que não foi, não tem rede de proteção.

Quando dá errado

fatal: log for 'HEAD' only has 11 entries 
$ git reset --hard HEAD@{50}
fatal: log for 'HEAD' only has 11 entries

O que aconteceu: você pediu "50 movimentos atrás", mas o diário só tem 11 anotações ("o registro do HEAD só tem 11 entradas"). Nada foi mudado.

Como resolver: rode git reflog e escolha uma linha que existe, de preferência pelo hash.

fatal: a branch named 'sobremesas' already exists 
$ git branch sobremesas HEAD@{1}
fatal: a branch named 'sobremesas' already exists

O que aconteceu: já existe um branch com esse nome ("um branch chamado 'sobremesas' já existe"); o Git não sobrescreve etiquetas sem você pedir.

Como resolver: use outro nome (git branch resgate2 HEAD@{1}). Só use git branch -f (forçar) se tiver certeza de que quer mover a etiqueta existente.

fatal: a branch is expected, got commit 
$ git switch 0b9c470
fatal: a branch is expected, got commit '0b9c470'
hint: If you want to detach HEAD at the commit, try again with the --detach option.

O que aconteceu: o git switch espera um branch, e você deu um hash ("esperava um branch, recebi o commit"). A dica diz que, para só visitar o commit, use --detach (veja HEAD destacado).

Como resolver: para resgatar, crie um branch e vá para ele de uma vez: git switch -c resgate 0b9c470.

Não acho o commit no reflog

O que aconteceu: o git reflog sem nada mostra só o diário do HEAD. Commits que nunca passaram pelo HEAD (um stash, um commit de outra pasta de worktree) não aparecem ali.

Como resolver: tente o diário de um branch (git reflog show main) e, no fim, git fsck --unreachable. Se o commit nunca existiu (a mudança nunca foi commitada), não há o que achar.

Resumo

  • Commit "perdido" quase sempre ainda existe: só ficou sem etiqueta.
  • O git reflog mostra o hash; HEAD@{n} é "n movimentos atrás".
  • Resgate seguro: git branch resgate HASH. Direto: git reset --hard HASH, com git status limpo.
  • O branch -D e o stash drop já mostram o hash na mensagem; o git fsck --unreachable acha o resto.
  • O reflog dura 90 dias (30 para commits sem etiqueta) por padrão; resgate logo.
  • O que nunca foi adicionado nem commitado não tem volta: commite cedo.

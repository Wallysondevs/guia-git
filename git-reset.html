Git reset

A Ana fez um commit cedo demais: a receita de brigadeiro ainda não estava pronta, e ela preferia que aquele commit nem existisse ainda. O git reset (em inglês, reset = "redefinir, voltar à posição") faz isso: ele leva o branch de volta para um commit anterior, como se os commits de depois não tivessem acontecido. Nesta aula você aprende o uso mais comum e mais seguro dele; os três "modos" (--soft, --mixed e --hard) têm uma aula só para eles, a próxima.

Você vai aprender
  • O que o git reset faz de verdade: muda o commit para onde o branch aponta.
  • Como desfazer o último commit (ou os dois últimos) sem perder o trabalho, com git reset HEAD~1.
  • Como voltar para um commit pelo hash, e como desfazer um reset com ORIG_HEAD.
  • O git reset arquivo, o jeito antigo de tirar um arquivo da área de preparo.
  • Por que não se dá reset em commits que já foram enviados ao GitHub.

Todas as saídas desta aula vieram do Git real da máquina da Ana (usuária ana, computador notebook), com o sistema em português. A tradução do Git que vem no Ubuntu é parcial: algumas mensagens saem em português, outras em inglês, outras misturadas. Elas estão aqui exatamente como saíram (no Windows, no macOS ou com o sistema em inglês, as frases podem ser diferentes; o sentido é o mesmo).

A ideia: o marcador de página

Pense no histórico como um caderno de receitas em que cada página é um commit, e o branch main é um marcador de página que diz "o caderno vai até aqui". Quando você faz um commit, escreve uma página nova e o marcador avança. O git reset puxa o marcador para trás.

Antes:   A --- B --- C --- D   <- main

git reset HEAD~1

Depois:  A --- B --- C         <- main
                      \
                       D        (fora do histórico do main)

A página D não foi rasgada na hora: ela continua guardada na pasta .git por um tempo (e dá para voltar a ela, como você vai ver). Mas, para o git log, o caderno agora termina em C.

E o que acontece com os arquivos de D? Depende do modo. No modo padrão, que é o desta aula, as mudanças de D continuam na pasta, como mudanças ainda não commitadas. Você não perde nada do que escreveu; só "descommita".

1. Desfazendo o último commit

O repositório receitas da Ana tem quatro commits:

$ git log --oneline
a122cf9 Adiciona receita de brigadeiro   « o HEAD está aqui
91591a1 Adiciona receita de pudim
62fc1c8 Adiciona receita de bolo
fe996fb Primeiro commit

Ela quer desfazer o commit do brigadeiro, mas sem perder o arquivo:

$ git reset HEAD~1
git reset
"Leve o branch atual para…".
HEAD~1
"…um commit antes do HEAD". O HEAD é o commit em que você está agora (veja O que é HEAD); o ~1 quer dizer "um passo para trás". HEAD~2 seria dois passos, e assim por diante.

A resposta do Git: nenhuma. Como quase todo comando de terminal, o git reset fica quieto quando dá certo. (Quando algum arquivo que o Git já conhecia fica com mudanças fora da área de preparo, ele lista esses arquivos debaixo de Unstaged changes after reset:; você vai ver isso na seção 4. Aqui, o único arquivo do commit desfeito era novo, então não havia o que listar.) Para ver o que aconteceu, pergunte ao git log e ao git status:

$ git log --oneline
91591a1 Adiciona receita de pudim   « o HEAD agora está aqui
62fc1c8 Adiciona receita de bolo
fe996fb Primeiro commit
$ git status
No ramo main
Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	brigadeiro.txt   « o arquivo continua na pasta

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)

O git log termina no pudim: o commit do brigadeiro saiu do histórico. E o git status mostra o brigadeiro.txt como "não rastreado", exatamente como estava antes de a Ana dar git add nele. O arquivo continua na pasta, com o mesmo conteúdo. Quando a receita ficar pronta, é só git add e git commit de novo:

$ git add brigadeiro.txt
$ git commit -q -m "Adiciona receita de brigadeiro"
$ git log --oneline
a122cf9 Adiciona receita de brigadeiro
91591a1 Adiciona receita de pudim
62fc1c8 Adiciona receita de bolo
fe996fb Primeiro commit

(O -q, de quiet, "quieto", só esconde o resumo do commit. E o hash saiu igual ao de antes, a122cf9, porque o conteúdo, a mensagem e o pai são os mesmos e o relógio do laboratório do guia é fixo; no seu computador, a hora mudaria e o hash também.)

Missão: desfaça o último commit da Ana ("Adiciona receita de brigadeiro") com git reset, sem perder o arquivo. Confira com git log --oneline (devem sobrar 2 commits) e com git status (o brigadeiro.txt deve aparecer como não rastreado).

2. Voltando mais de um commit

Com HEAD~2, o branch volta dois commits, e as mudanças dos dois ficam na pasta:

$ git reset HEAD~2
$ git log --oneline
62fc1c8 Adiciona receita de bolo
fe996fb Primeiro commit
$ git status
No ramo main
Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	brigadeiro.txt
	pudim.txt

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)

O main agora está no commit do bolo, e o pudim e o brigadeiro voltaram a ser arquivos não rastreados. Esse é um jeito comum de juntar commits: desfazer os dois e fazer um commit só com tudo (o nome disso é squash).

Pelo hash

Em vez de contar passos, você pode dizer o hash do commit para onde quer voltar, copiado do git log --oneline: git reset 62fc1c8 teria o mesmo efeito do HEAD~2 acima. Com hash, não tem como errar a conta.

3. Arrependeu-se? ORIG_HEAD

Antes de mover o branch, o git reset anota onde ele estava num apelido especial chamado ORIG_HEAD ("HEAD original"). Para desfazer o reset que acabou de fazer:

$ git reset ORIG_HEAD
$ git log --oneline
a122cf9 Adiciona receita de brigadeiro
91591a1 Adiciona receita de pudim
62fc1c8 Adiciona receita de bolo
fe996fb Primeiro commit
$ git status
No ramo main
nothing to commit, working tree clean

O histórico voltou a ter os quatro commits, com os mesmos hashes de antes: o Git não recriou nada, só levou o marcador de volta para a página que nunca tinha sido rasgada. E a pasta está limpa, porque o conteúdo dos arquivos é igual ao do commit.

O ORIG_HEAD só guarda o último movimento perigoso. Para voltar mais longe, use o git reflog, que lista todos os lugares por onde o HEAD passou (com os apelidos HEAD@{1}, HEAD@{2}…).

4. git reset arquivo: o jeito antigo de "desadicionar"

O git reset tem um segundo uso, bem diferente: com o nome de um arquivo, ele não mexe no branch; só tira o arquivo da área de preparo. A Ana mudou o tempo do bolo e deu git add, mas mudou de ideia sobre colocar isso no próximo commit:

$ echo 'Tempo: 45 minutos' >> bolo.txt
$ git add bolo.txt
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt   « na área de preparo

$ git reset bolo.txt
Unstaged changes after reset:
M	bolo.txt
$ git status
No ramo main
Changes not staged for commit:
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   bolo.txt   « fora da área de preparo

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")

A resposta Unstaged changes after reset: quer dizer "mudanças fora da área de preparo depois do reset", e o M antes do nome quer dizer modified, "modificado". Depois do git reset bolo.txt, o arquivo passou de "Mudanças a serem submetidas" para Changes not staged for commit ("mudanças não preparadas para o commit"; o Git do Ubuntu mistura português e inglês nessas mensagens): saiu da área de preparo, mas a mudança continua no arquivo. É exatamente o que o git restore --staged faz. O git reset arquivo é o jeito antigo, de antes do Git 2.23; você vai encontrá-lo em muitos tutoriais e respostas da internet (às vezes escrito git reset HEAD bolo.txt, que é a mesma coisa). Hoje, o próprio git status sugere o restore --staged.

Quando dá errado

Voltou mais commits do que existem 
$ git reset HEAD~9
fatal: ambiguous argument 'HEAD~9': unknown revision or path not in the working tree.
Use '--' to separate paths from revisions, like this:
'git <command> [<revision>...] -- [<file>...]'

"Argumento ambíguo HEAD~9: revisão desconhecida, ou caminho que não está na árvore de trabalho. Use -- para separar caminhos de revisões." O histórico tem 4 commits; não existe um commit 9 passos antes do HEAD. A mensagem é longa porque o Git não sabe se você quis dizer um commit ou um arquivo chamado HEAD~9; e, como não achou nenhum dos dois, não mexeu em nada. Como resolver: conte os commits no git log --oneline (ou use o hash).

Nome de arquivo ou commit errado 
$ git reset brigadeiro
fatal: ambiguous argument 'brigadeiro': unknown revision or path not in the working tree.
Use '--' to separate paths from revisions, like this:
'git <command> [<revision>...] -- [<file>...]'

Não existe commit nem arquivo chamado brigadeiro (o arquivo é brigadeiro.txt). A mesma mensagem do cenário anterior. Como resolver: confira o nome com git status ou ls.

Dei reset num commit que já tinha enviado

Se o commit já está no GitHub, o reset só muda o seu branch. No próximo git push, o GitHub vai recusar, porque o histórico dele tem um commit que o seu não tem (veja Push Rejeitado). E se você forçar, quem já baixou aquele commit (o Bruno) vai ter um histórico diferente do seu. Como resolver: volte ao estado de antes com git reset ORIG_HEAD (ou pelo git reflog) e desfaça o commit com git revert, que não reescreve nada. A regra completa está em A Regra de Ouro.

"Sumiram" os meus commits depois de um reset

Eles não sumiram: só saíram do histórico do branch. Rode git reflog, ache a linha de antes do reset (o hash do commit mais novo que você tinha) e volte com git reset <hash>. Se foi o último reset, git reset ORIG_HEAD basta. Mais em Recuperando Commits Perdidos.

Missão final: juntando dois commits em um

Missão: a Ana fez dois commits pequenos demais: "Adiciona pudim" e "Adiciona calda". Use git reset para desfazer os dois (sem perder os arquivos) e faça um commit com os dois arquivos e a mensagem "Adiciona receita de pudim com calda". No fim, o histórico deve ter 2 commits.

Resumo

  • git reset <commit> leva o branch atual para aquele commit; os commits de depois saem do histórico (mas continuam guardados por um tempo).
  • No modo padrão, as mudanças dos commits desfeitos ficam na pasta, fora da área de preparo: nada se perde.
  • HEAD~1, HEAD~2… contam para trás a partir do commit atual; o hash também serve.
  • git reset ORIG_HEAD desfaz o último reset; o git reflog leva mais longe.
  • git reset arquivo só tira o arquivo da área de preparo (hoje, git restore --staged).
  • Reset reescreve o histórico: use só em commits que ainda não foram enviados. Para os enviados, git revert.

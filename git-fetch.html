Git fetch

O Bruno enviou uma mudança para o GitHub. Como a Ana fica sabendo? O Git não avisa sozinho: ele só conversa com o remoto quando você pede. O git fetch (em inglês, "ir buscar") é o pedido mais seguro: ele traz os commits novos do remoto para o seu repositório, mas não mexe nos seus arquivos nem nos seus branches. Você olha com calma o que chegou e decide depois o que fazer.

Você vai aprender
  • O que o git fetch traz e por que ele nunca estraga o seu trabalho.
  • O que são origin/main e os branches remotos (git branch -r).
  • Como ver o que chegou: git status, git log main..origin/main e git diff main origin/main.
  • Como juntar o que chegou ao seu branch (git merge origin/main), e por que isso é quase o git pull.
  • Como limpar branches que já foram apagados no remoto: git fetch --prune.

A ideia antes do comando

Pense na caixa de correio do prédio. O git fetch é descer e pegar as cartas: elas agora estão com você, na sua mão. Mas abrir as cartas e colocar as contas na gaveta da cozinha é outra decisão, que você toma depois de ler. O fetch nunca abre carta nenhuma sozinho.

Para guardar as "cartas", o Git usa os branches remotos: origin/main é a cópia local de como estava o main do GitHub na última conversa. Ele não é o seu main, e você não trabalha nele: é uma fotografia do remoto, atualizada a cada fetch, pull ou push.

Antes do fetch                       Depois do fetch
GitHub:   A---B---C   main           GitHub:   A---B---C   main

Ana:      A---B       main           Ana:      A---B       main        (não mudou)
                ↑ origin/main                       \
                                                     C     origin/main (andou)

O comando: git fetch

git fetch
"Busque as novidades" do remoto padrão (o origin, ou o remoto do upstream do branch atual).
git fetch origin
O mesmo, dizendo o nome do remoto.
git fetch --all
Busca de todos os remotos cadastrados (útil quando há mais de um, como num fork).

A história: o Bruno mudou o bolo

A Ana enviou o projeto para o GitHub (veja git push). O Bruno clonou, acrescentou o óleo à receita do bolo e enviou. A Ana, no notebook dela, ainda não sabe de nada:

$ git status
No ramo main
Your branch is up to date with 'origin/main'.          « "em dia"... com a lembrança antiga!

nothing to commit, working tree clean

O git status diz que ela está em dia com o origin/main. É verdade, mas o origin/main é a fotografia da última conversa com o GitHub, de antes do commit do Bruno. O status não consulta a internet. Para atualizar a fotografia:

$ git fetch
remote: Enumerating objects: 5, done.
remote: Counting objects: 100% (5/5), done.
remote: Compressing objects: 100% (3/3), done.
remote: Total 3 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
Unpacking objects: 100% (3/3), 306 bytes | 306.00 KiB/s, done.
From https://github.com/ana-souza/receitas                   « de onde veio
   4f68d0e..3dbde00  main       -> origin/main               « origin/main andou

A saída, linha por linha

LinhaO que quer dizer
remote: Enumerating objects … remote: Total 3O servidor (por isso o remote:) separou e empacotou o que a Ana não tem: 3 objetos (o commit do Bruno, a pasta e o bolo.txt novo).
Unpacking objects: 100% (3/3)O Git da Ana recebeu e desempacotou os 3 objetos.
From https://github.com/ana-souza/receitasDe onde veio ("From" = "de").

Mensagens em inglês? A tradução do Git que o Ubuntu usa é parcial (e às vezes cai no português de Portugal, como "submissões" e "divergiram-se"): num sistema em português, parte das mensagens sai em português e parte em inglês, como acima. O guia mostra exatamente o que o Git escreve.

Agora o git status sabe

$ git status
No ramo main
Seu ramo está atrás de 'origin/main' em 1 submissão, e pode ser avançado.     « 1 commit novo lá
  (use "git pull" to update your local branch)                              « a dica

nothing to commit, working tree clean
  • Seu ramo está atrás de 'origin/main' em 1 submissão: o origin/main tem 1 commit (submissão) que o seu main não tem.
  • e pode ser avançado: o seu main pode simplesmente "andar para a frente" até ele, sem mistura nenhuma (é o fast-forward).
  • (use "git pull" to update your local branch): "use git pull para atualizar o seu branch local".

O fetch não mexeu nos seus arquivos

O commit do Bruno chegou, mas a receita no notebook da Ana continua sem o óleo:

$ cat bolo.txt
Bolo de cenoura
- 3 cenouras                                        « nada de óleo: a pasta não mudou

Isso é o que faz o fetch ser seguro: você pode rodar a qualquer hora, até no meio de um trabalho sem commit, e nada do que está na sua pasta muda.

Olhando o que chegou

Com o origin/main atualizado, a Ana usa os comandos que já conhece, com o nome origin/main:

$ git log --oneline --graph --all
* 3dbde00 (origin/main, origin/HEAD) Adiciona óleo ao bolo       « o commit do Bruno
* 4f68d0e (HEAD -> main) Adiciona receita de bolo               « onde a Ana está
* 0e8cf93 Adiciona README
$ git log --oneline main..origin/main
3dbde00 (origin/main, origin/HEAD) Adiciona óleo ao bolo         « só o que é novo
$ git diff main origin/main
diff --git a/bolo.txt b/bolo.txt
index a302b37..3f3b090 100644
--- a/bolo.txt
+++ b/bolo.txt
@@ -1,2 +1,3 @@
 Bolo de cenoura
 - 3 cenouras
+- 1 xícara de óleo                                              « o que o Bruno mudou
git log --oneline --graph --all
O histórico de todos os branches, inclusive os remotos (veja log --graph).
git log main..origin/main
"Os commits que estão em origin/main e não estão em main": exatamente o que chegou. Os dois pontos querem dizer "de … até".
git diff main origin/main
A diferença entre os arquivos do seu main e os do origin/main (veja git diff).

E o origin/HEAD? É um apelido: "o branch principal do remoto". Aqui, origin/HEAD -> origin/main. O Git cria esse apelido no clone e as versões recentes também o criam no fetch; você pode ignorá-lo.

Juntando o que chegou: git merge origin/main

Gostou do que viu? Agora sim, a Ana traz o commit para o main dela. Como o main só está atrás, é um avanço simples (fast-forward):

$ git merge origin/main
Updating 4f68d0e..3dbde00
Fast-forward                                              « o main só andou para a frente
 bolo.txt | 1 +
 1 file changed, 1 insertion(+)
$ git status
No ramo main
Your branch is up to date with 'origin/main'.             « agora, em dia de verdade

nothing to commit, working tree clean
fetch + merge = pull. Esses dois passos, buscar e juntar, são tão comuns que existe um comando que faz os dois de uma vez: o git pull. A vantagem de fazer separado é poder olhar antes de juntar.

Experimente

Nos terminais abaixo, o "GitHub" é o GitHub de treino do guia: a Ana já clonou o receitas e o Bruno já enviou um commit novo que ela ainda não buscou. No terminal do guia, as linhas de progresso (Enumerating objects…, Writing objects…) não aparecem: ele mostra a versão curta da saída.

Missão: busque as novidades do remoto sem mudar o seu main. Depois, descubra qual commit chegou com git log --oneline main..origin/main e confira com ls que o suco.txt ainda não está na sua pasta.

Missão: agora em dois passos: busque com git fetch, olhe o git status e junte o commit do Bruno ao seu main com git merge.

Branches novos e apagados no remoto

O fetch traz todos os branches do remoto, não só o main. O Bruno criou o branch bebidas e enviou:

$ git fetch
remote: Enumerating objects: 4, done.
remote: Counting objects: 100% (4/4), done.
remote: Compressing objects: 100% (2/2), done.
remote: Total 3 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
Unpacking objects: 100% (3/3), 298 bytes | 298.00 KiB/s, done.
From https://github.com/ana-souza/receitas
 * [new branch]      bebidas    -> origin/bebidas          « um branch que a Ana não conhecia
$ git branch -r
  origin/HEAD -> origin/main
  origin/bebidas
  origin/main

git branch -r (remote) lista os branches remotos; git branch -a (all) lista os seus e os remotos juntos. Para trabalhar no branch do Bruno, a Ana pode rodar git switch bebidas: o Git cria um branch local com esse nome, já ligado ao origin/bebidas (veja upstream).

git fetch --prune: limpando o que foi apagado lá

Dias depois, o Bruno apagou o branch bebidas no GitHub. Um git fetch comum não apaga a lembrança local:

$ git fetch                                       « sem saída: nada novo
$ git branch -r
  origin/HEAD -> origin/main
  origin/bebidas                                   « continua aqui, mas não existe mais lá
  origin/main
$ git fetch --prune
From https://github.com/ana-souza/receitas
 - [deleted]         (none)     -> origin/bebidas     « lembrança apagada
$ git branch -r
  origin/HEAD -> origin/main
  origin/main

Prune é "podar". O sinal - e o [deleted] dizem que o origin/bebidas foi removido porque o branch não existe mais no remoto. Para podar sempre, configure uma vez: git config --global fetch.prune true.

Formas diferentes de fazer

FormaO que fazQuando usar
git fetchBusca do remoto padrãoNo dia a dia
git fetch originBusca de um remoto pelo nomeQuando há mais de um remoto
git fetch --allBusca de todos os remotosFork com origin e upstream
git fetch --pruneBusca e apaga lembranças de branches que sumiram láDe vez em quando, ou sempre com fetch.prune
git fetch + git merge origin/mainBusca, você olha, depois juntaQuando quer conferir antes
git pullBusca e junta de uma vezQuando confia no que vem (veja git pull)

Quando dá errado

"Fiz fetch e nada mudou nos meus arquivos"

O que aconteceu: nada de errado: é assim mesmo. O fetch atualiza só o origin/main (e os outros branches remotos).

Como confirmar: git status mostra "atrás de 'origin/main'"; git log --oneline main..origin/main lista o que chegou.

Como resolver: junte com git merge origin/main, ou use git pull da próxima vez.

O git status diz "em dia", mas o colega jura que enviou

O que aconteceu: o status compara com a lembrança (origin/main), que só se atualiza quando você conversa com o remoto.

Como resolver: git fetch e git status de novo.

"'orgin' does not appear to be a git repository" 
$ git fetch orgin
fatal: 'orgin' does not appear to be a git repository
fatal: Could not read from remote repository.

Please make sure you have the correct access rights
and the repository exists.

O que aconteceu: não existe remoto com esse nome (erro de digitação de origin), ou o repositório não tem remoto nenhum.

Como resolver: git remote -v mostra os nomes certos.

"not a git repository" 
$ git fetch
fatal: not a git repository (or any of the parent directories): .git

O que aconteceu: você não está dentro da pasta do projeto ("não é um repositório git, nem nenhuma das pastas acima").

Como resolver: cd receitas (a pasta do projeto) e rode de novo.

Um branch apagado no GitHub continua aparecendo no git branch -r

O que aconteceu: o fetch comum não apaga lembranças.

Como resolver: git fetch --prune.

Resumo

  • git fetch traz os commits novos do remoto e atualiza os branches remotos (origin/main), sem tocar nos seus arquivos nem no seu main.
  • O git status só sabe que você está atrás depois de um fetch: ele compara com a lembrança, não com a internet.
  • Veja o que chegou com git log main..origin/main e git diff main origin/main; junte com git merge origin/main.
  • git fetch + git merge = git pull.
  • git fetch --prune apaga as lembranças de branches que sumiram do remoto.

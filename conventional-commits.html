Git Conventional Commits

Na aula Boas Mensagens de Commit você aprendeu a escrever mensagens claras. Muitas equipes vão um passo além e combinam um formato fixo para a primeira linha, para que pessoas e programas entendam de cara o tipo de cada mudança. O formato mais usado tem nome e especificação pública: Conventional Commits ("commits convencionais"). Uma mensagem nesse formato se parece com isto: fix(index): corrige link do bolo.

Você vai aprender
  • O formato tipo(escopo): descrição, com corpo e rodapé opcionais.
  • Os tipos feat e fix (os únicos obrigatórios da especificação) e os costumeiros docs, chore, refactor, test…
  • Como marcar uma mudança que quebra compatibilidade: o ! e o rodapé BREAKING CHANGE:, e a ligação com o Versionamento Semântico.
  • Como achar commits por tipo com git log --grep.
  • A armadilha do ! entre aspas duplas no terminal, e como um hook pode recusar mensagens fora do padrão.

Os comandos desta aula rodaram no Git do Ubuntu da Ana (usuária ana, computador notebook). As regras do formato vêm da especificação oficial, a versão 1.0.0, que tem tradução em português: conventionalcommits.org/pt-br.

A ideia: a etiqueta da caixa de mudança

Numa mudança de casa, quem escreve na caixa só "coisas" obriga todo mundo a abrir caixa por caixa. Quem escreve COZINHA – copos (frágil) deixa claro, sem abrir, de que tipo é o conteúdo, de que parte da casa ele é, e se tem algum cuidado especial. A mensagem no padrão Conventional Commits é essa etiqueta:

Na caixaNo commitExemplo
De que tipo éo tipofix (correção)
De que cômodoo escopo, opcional, entre parênteses(index)
Frágil!o !, quando a mudança quebra algo para quem usafeat(busca)!:
O que tem dentroa descriçãocorrige link do bolo

1. O formato

A especificação define esta estrutura:

<tipo>[escopo opcional]: <descrição>

[corpo opcional]

[rodapé(s) opcional(is)]
tipo
Uma palavra que diz o tipo da mudança: feat, fix, docs… (seção 2). Obrigatório.
(escopo)
Opcional: um substantivo entre parênteses dizendo qual parte do projeto mudou: (index), (busca), (pudim). Cada equipe combina a sua lista.
:
Dois-pontos e um espaço. Fazem parte do formato.
descrição
Obrigatória: um resumo curto da mudança. O costume é escrever em minúsculas, no imperativo ou no presente (adiciona, corrige), sem ponto final.
corpo
Opcional, depois de uma linha em branco: texto livre explicando o porquê, com quantos parágrafos quiser.
rodapé
Opcional, depois de outra linha em branco: linhas no formato Palavra-chave: valor (ou Palavra-chave #valor), como Refs: #12, Reviewed-by: Bruno ou BREAKING CHANGE: …. A palavra-chave usa - no lugar de espaços; a única exceção é BREAKING CHANGE.

Na prática, a maioria dos commits tem só a primeira linha. A Ana fez três commits no site de receitas nesse formato:

$ git add pudim.md
$ git commit -m "feat: adiciona receita de pudim"
[main 45d0c75] feat: adiciona receita de pudim
 1 file changed, 1 insertion(+)
 create mode 100644 pudim.md
$ sed -i 's/bolo.htm/bolo.md/' index.md
$ git commit -am "fix(index): corrige link do bolo"
[main 14b8e2b] fix(index): corrige link do bolo
 1 file changed, 1 insertion(+), 1 deletion(-)
$ printf '\nComo contribuir: abra uma issue.\n' >> README.md
$ git commit -am "docs: explica como contribuir no README"
[main a8e5d96] docs: explica como contribuir no README
 1 file changed, 2 insertions(+)

Para o Git, nada mudou: feat: adiciona receita de pudim é uma mensagem como outra qualquer, e ele a guardou do jeito que veio (o sed e o printf só mudam os arquivos pelo terminal; você pode usar o editor). O formato é um combinado entre pessoas, e serve para o que vem depois: ler o histórico, filtrar, gerar a lista de novidades de uma versão.

2. Os tipos

A especificação só define dois tipos e diz o que eles significam; os outros são permitidos e vêm de um costume que começou no projeto Angular:

TipoQuando usarExemplo no site da Ana
featUma funcionalidade nova (de feature). Definido na especificação.feat: adiciona receita de pudim
fixUma correção de defeito. Definido na especificação.fix(index): corrige link do bolo
docsSó documentação (README, comentários)docs: explica como contribuir no README
styleFormatação, espaços, ponto e vírgula, sem mudar o comportamentostyle: alinha a indentação do index
refactorReorganiza o código sem corrigir defeito nem criar funcionalidaderefactor(busca): separa a busca em duas funções
perfMelhora de desempenhoperf: reduz o tamanho das fotos
testTestes novos ou corrigidostest: testa a busca sem resultados
buildO sistema de construção ou as dependênciasbuild: atualiza o gerador do site
ciA integração contínua (veja GitHub Actions)ci: roda os testes em todo pull request
choreTarefas de manutenção que não entram em nenhum dos outroschore: cria o site de receitas
revertDesfaz um commit anterior (veja git revert)revert: volta a busca antiga

Os tipos são escritos em inglês mesmo quando a descrição é em português: eles funcionam como palavras-chave, e as ferramentas que leem o histórico esperam exatamente essas.

3. Mudança que quebra: o ! e o BREAKING CHANGE

Às vezes uma mudança obriga quem usa o projeto a mudar também. O site da Ana tinha uma busca por código de ingrediente (?codigo=12); ela trocou por uma busca por nome, e os links antigos deixaram de funcionar. Isso é uma mudança que quebra compatibilidade (breaking change). A especificação manda marcar de um destes dois jeitos (ou dos dois):

  • um ! logo antes dos dois-pontos: feat(busca)!: …;
  • um rodapé que começa com BREAKING CHANGE: (assim, em maiúsculas), explicando o que quebrou.

Com -m repetido, cada -m vira um parágrafo: o primeiro é o título, o segundo o corpo, o terceiro o rodapé. Repare nas aspas simples; o motivo está logo abaixo.

$ git commit -m 'feat(busca)!: busca receitas pelo nome do ingrediente' -m 'A busca antiga, pelo código do ingrediente, foi removida.' -m 'BREAKING CHANGE: links de busca com ?codigo= deixam de funcionar.'
[main d0e7d7c] feat(busca)!: busca receitas pelo nome do ingrediente
 1 file changed, 1 insertion(+)
 create mode 100644 busca.txt
$ git log -1
commit d0e7d7ce7be446feaf08233756cd5fa4230de6d0 (HEAD -> main)
Author: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

    feat(busca)!: busca receitas pelo nome do ingrediente               « título, com o !

    A busca antiga, pelo código do ingrediente, foi removida.          « corpo

    BREAKING CHANGE: links de busca com ?codigo= deixam de funcionar.  « rodapé
O ! entre aspas duplas dá erro no terminal

Antes, a Ana tinha tentado com aspas duplas:

$ git commit -m "feat(busca)!: busca receitas pelo ingrediente"
bash:  : unrecognized history modifier

O erro é do Bash, não do Git: o commit nem foi tentado. No terminal, o ! dentro de aspas duplas puxa um comando do histórico (é a "expansão de histórico": !! repete o último comando), e o !: confundiu o Bash ("modificador de histórico não reconhecido"). Como resolver: use aspas simples, que desligam esse efeito: git commit -m 'feat(busca)!: …'. Ou rode só git commit e escreva a mensagem no editor, onde o ! não tem nada de especial.

A ligação com o Versionamento Semântico

Aqui está a maior utilidade do formato. No Versionamento Semântico, a versão tem três números, MAIOR.MENOR.CORREÇÃO (em inglês, MAJOR.MINOR.PATCH). Os tipos dos commits dizem qual número sobe na próxima versão:

Commits desde a última versãoO que sobeExemplo, a partir de 1.4.2
Só fixCORREÇÃO (PATCH)1.4.3
Algum featMENOR (MINOR)1.5.0
Algum ! ou BREAKING CHANGE (de qualquer tipo)MAIOR (MAJOR)2.0.0
Só docs, chore, style…Nada, pela especificação—

Como a regra é mecânica, existem programas que leem o histórico e decidem a versão nova e a lista de novidades (o changelog) sozinhos. Eles não vêm com o Git; são instalados à parte, e cada um tem a sua documentação.

4. Filtrando o histórico pelo tipo

Com o formato, o git log vira um índice. O histórico da Ana:

$ git log --oneline
d0e7d7c (HEAD -> main) feat(busca)!: busca receitas pelo nome do ingrediente
a8e5d96 docs: explica como contribuir no README
14b8e2b fix(index): corrige link do bolo
45d0c75 feat: adiciona receita de pudim
8695ad4 chore: cria o site de receitas

A opção --grep mostra só os commits cuja mensagem casa com um padrão (veja git log: Filtros e Formatos). O ^ quer dizer "no começo da linha":

$ git log --oneline --grep="^feat"
d0e7d7c (HEAD -> main) feat(busca)!: busca receitas pelo nome do ingrediente
45d0c75 feat: adiciona receita de pudim
$ git log --oneline --grep="^fix"
14b8e2b fix(index): corrige link do bolo
$ git log --oneline --grep="BREAKING CHANGE"
d0e7d7c (HEAD -> main) feat(busca)!: busca receitas pelo nome do ingrediente     « achou pelo rodapé, que não aparece no --oneline

Em segundos, a Ana sabe o que entrou de novo (feat), o que foi corrigido (fix) e o que pode quebrar para quem usa o site. Com mensagens como "arrumei umas coisas", isso seria impossível.

Missão: no repositório receitas, o arquivo index.md já foi corrigido (o link do pudim estava errado), mas ainda não foi commitado. Faça o commit no padrão Conventional Commits, com o tipo de correção e o escopo index: fix(index): corrige link do pudim. Depois, liste só as correções com git log --oneline --grep="^fix".

Formas diferentes de escrever a mensagem

FormaQuando usar
git commit -m "fix(index): corrige link do bolo"Só o título, sem !: o caso mais comum.
git commit -m 'feat(busca)!: …'Com !: aspas simples, sempre.
git commit -m 'título' -m 'corpo' -m 'BREAKING CHANGE: …'Título, corpo e rodapé sem abrir o editor.
git commit (abre o editor)Mensagens longas: título na 1ª linha, linha em branco, corpo, linha em branco, rodapé.
Extensões de editor e programas como o commitizenPerguntam o tipo, o escopo e a descrição e montam a mensagem. São instalados à parte (não rodaram no laboratório desta aula).

Quando dá errado

Escrevi fora do padrão e o Git aceitou 
$ git commit -am "arrumei umas coisas"
[main fe76230] arrumei umas coisas
 1 file changed, 1 insertion(+)

O que aconteceu: nada de errado, para o Git: ele não conhece o Conventional Commits e aceita qualquer mensagem. Como resolver, se o commit ainda não foi enviado: corrija a mensagem com --amend (veja Corrigindo o Último Commit):

$ git commit --amend -m "fix(pudim): acrescenta o leite condensado"
[main 0234c44] fix(pudim): acrescenta o leite condensado
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+)
$ git log --oneline -2
0234c44 (HEAD -> main) fix(pudim): acrescenta o leite condensado
d0e7d7c feat(busca)!: busca receitas pelo nome do ingrediente

O commit ganhou um hash novo (0234c44 no lugar de fe76230): o --amend troca o commit. Por isso, se ele já foi enviado, deixe como está (veja A Regra de Ouro).

O commit foi recusado: "Mensagem fora do padrão"

Equipes que levam o formato a sério instalam um hook (um script que o Git roda sozinho em certos momentos; veja Git Hooks). O hook commit-msg recebe a mensagem e pode recusar o commit. A Ana instalou um bem simples, em .git/hooks/commit-msg (com permissão de execução):

#!/bin/sh
# Recusa mensagens fora do padrão Conventional Commits
padrao='^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)(\([a-z0-9-]+\))?!?: .+'
if ! head -n 1 "$1" | grep -qE "$padrao"; then
  echo "Mensagem fora do padrão Conventional Commits: $(head -n 1 "$1")" >&2
  echo "Exemplo: feat(busca): adiciona filtro por tempo de preparo" >&2
  exit 1
fi

$ git commit -am "mais leite"
Mensagem fora do padrão Conventional Commits: mais leite
Exemplo: feat(busca): adiciona filtro por tempo de preparo
$ git status --short
 M pudim.md                                  « nada foi commitado: a mudança continua lá
$ git commit -am "Fix: mais leite"
Mensagem fora do padrão Conventional Commits: Fix: mais leite
Exemplo: feat(busca): adiciona filtro por tempo de preparo
$ git commit -am "fix(pudim): acrescenta o leite"
[main 69fa58f] fix(pudim): acrescenta o leite
 1 file changed, 1 insertion(+)

O que aconteceu: as duas primeiras mensagens não casaram com o padrão do hook, e o commit foi cancelado (as duas linhas são do hook, não do Git). O Fix: com F maiúsculo foi recusado porque este hook só aceita minúsculas; a especificação, na verdade, diz que maiúsculas e minúsculas não fazem diferença (exceto em BREAKING CHANGE), mas o costume é escrever o tipo em minúsculas. Como resolver: reescreva a mensagem no formato. As mensagens de erro de verificadores prontos (como o commitlint) são diferentes destas, mas a ideia é a mesma.

bash: !…: event not found ou unrecognized history modifier

É o ! dentro de aspas duplas, como você viu na seção 3. O Bash tentou usar o ! para buscar um comando antigo. Como resolver: troque as aspas duplas por simples ('feat!: …'), ou escreva a mensagem no editor com git commit.

Não sei se é feat ou fix

Pergunte: "quem usa o site ganhou uma coisa que não existia?" Então é feat. "Uma coisa que devia funcionar e não funcionava passou a funcionar?" Então é fix. Se o commit faz as duas coisas, provavelmente devia ser dois commits (veja Boas Práticas).

Resumo

  • Conventional Commits é um formato combinado para a mensagem: tipo(escopo): descrição, com corpo e rodapé opcionais, cada um depois de uma linha em branco.
  • feat = funcionalidade nova; fix = correção. Outros tipos comuns: docs, style, refactor, perf, test, build, ci, chore, revert.
  • Mudança que quebra compatibilidade: ! antes dos dois-pontos e/ou rodapé BREAKING CHANGE:. Pelo Versionamento Semântico: fix sobe o PATCH, feat o MINOR, quebra o MAJOR.
  • O Git aceita qualquer mensagem; quem confere o formato é a equipe, ou um hook commit-msg.
  • git log --oneline --grep="^feat" lista os commits de um tipo.
  • No terminal, mensagem com ! vai entre aspas simples.

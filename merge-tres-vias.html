Git Merge de Três Vias

Na aula Merge Fast-forward, o main ficou parado enquanto o branch andava, e o Git só precisou "empurrar a etiqueta" para a frente. Na vida real, quase sempre os dois lados andam: a Ana cria a receita de bolo num branch e, enquanto isso, acrescenta a receita de pudim no main. Não dá para só empurrar a etiqueta. O Git, então, faz um merge de três vias (em inglês, three-way merge) e cria um commit novo, especial, que junta os dois caminhos.

Você vai aprender
  • Por que o merge se chama "de três vias": as duas pontas e o ancestral comum (git merge-base).
  • Como fazer o merge quando os dois branches andaram, e ler a saída do Git linha por linha.
  • O que é o commit de merge, que tem dois pais, e como vê-lo no git log --graph.
  • Como escolher a mensagem: o editor, -m e --no-edit; e como forçar um commit de merge com --no-ff.
  • Os erros mais comuns: nada para juntar, branch que não existe e mudanças locais que seriam sobrescritas.

Todas as saídas desta aula vieram do Git 2.53.0 da máquina da Ana (usuária ana, computador notebook), com o sistema em português. A tradução do Git para o português do Brasil é incompleta, e quase todas as mensagens do merge saem em inglês, como você vai ver: elas estão copiadas exatamente como saíram, e cada uma ganha tradução na explicação (mais sobre isso em Seu Primeiro Commit).

A ideia: dois cadernos copiados do mesmo original

A Ana tem um caderno de receitas. Ela tira uma cópia dele e entrega ao irmão, que escreve nela a receita de bolo. Enquanto isso, a Ana escreve no original a receita de pudim. No fim do dia, ela quer um caderno só, com as duas receitas. Para não perder nada, ela compara três cadernos:

  1. A cópia de hoje de manhã, como ela era antes de qualquer um escrever: o ponto de partida dos dois.
  2. O caderno dela, agora: o que mudou em relação à cópia de manhã? Entrou o pudim.
  3. O caderno do irmão, agora: o que mudou em relação à cópia de manhã? Entrou o bolo.

Comparando cada lado com o ponto de partida, fica fácil: "o pudim é novidade dela, o bolo é novidade dele; fica com os dois". Sem o caderno da manhã, ela não saberia se o irmão apagou o pudim ou se ele simplesmente nunca existiu na cópia dele.

O Git faz exatamente isso. As "três vias" são:

ViaNo cadernoNo Git
1. A baseA cópia de hoje de manhãO ancestral comum: o último commit que os dois branches têm em comum (em inglês, merge base)
2. O nosso ladoO caderno da AnaA ponta do branch onde você está (o HEAD, aqui o main)
3. O outro ladoO caderno do irmãoA ponta do branch que você está trazendo (aqui o bolo)
          C   ← main (Adiciona a receita de pudim)
         /
    A ──┤          A = base (ancestral comum)
         \
          B   ← bolo (Adiciona a receita de bolo)

depois do merge:

    A ─── C ─── M   ← main
     \         /
      └── B ──┘     ← bolo         M = commit de merge (pais: C e B)

O resultado é um commit novo, o M, que tem dois pais: o C (o main de antes) e o B (a ponta do bolo). Um commit comum tem um pai só; o commit de merge é o "nó" que amarra os dois caminhos.

1. Montando a situação: os dois lados andam

A Ana começa com um repositório de um commit só, cria o branch bolo e faz um commit nele:

$ mkdir receitas
$ cd receitas
$ git init -q
$ printf '# Receitas da Ana\n' > README.md
$ git add README.md
$ git commit -m 'Cria o README'
[main (root-commit) 700bbd5] Cria o README
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
$ git switch -c bolo
Switched to a new branch 'bolo'
$ printf 'Bolo de cenoura\n- 3 cenouras\n- 3 ovos\n- 2 xícaras de açúcar\n' > bolo.txt
$ git add bolo.txt
$ git commit -m 'Adiciona a receita de bolo'
[bolo 6dde70f] Adiciona a receita de bolo
 1 file changed, 4 insertions(+)
 create mode 100644 bolo.txt

Até aqui, nada de novo: o commit 700bbd5 no main e, a partir dele, o commit 6dde70f no branch bolo (o printf só escreve a receita no arquivo; veja O Mínimo de Terminal). Se a Ana fizesse o merge agora, seria um fast-forward, porque o main não andou.

Agora ela volta para o main e, antes de juntar o bolo, faz um commit lá também:

$ git switch main
Switched to branch 'main'
$ printf 'Pudim\n- 1 lata de leite condensado\n- 3 ovos\n' > pudim.txt
$ git add pudim.txt
$ git commit -m 'Adiciona a receita de pudim'
[main 99a4d8c] Adiciona a receita de pudim
 1 file changed, 3 insertions(+)
 create mode 100644 pudim.txt

O desenho mostra os dois galhos. Use --all para ver todos os branches, e não só o atual (veja Vendo os Galhos):

$ git log --oneline --graph --all
* 6dde70f (bolo) Adiciona a receita de bolo
| * 99a4d8c (HEAD -> main) Adiciona a receita de pudim
|/
* 700bbd5 Cria o README
* 6dde70f (bolo)
A ponta do branch bolo: a receita de bolo. Cada * é um commit.
| * 99a4d8c (HEAD -> main)
A ponta do main, onde a Ana está (HEAD -> main): a receita de pudim. Ele aparece numa coluna ao lado porque é outro caminho.
|/
As duas linhas se encontram embaixo: os dois caminhos saíram do mesmo commit.
* 700bbd5 Cria o README
O ponto de partida comum. É o "A" do desenho lá de cima.

Quem é o ancestral comum? git merge-base

O comando git merge-base responde à pergunta "qual é o último commit que estes dois branches têm em comum?". É o caderno da manhã:

$ git merge-base main bolo
700bbd5eb7964a024ce4076aeeb11c490e1bac2e

O git merge-base mostra o hash completo (os 40 caracteres; veja O Hash do Commit). Os 7 primeiros, 700bbd5, são o commit Cria o README: é dele que o Git parte para descobrir o que cada lado mudou. Você não precisa rodar este comando antes de um merge, o Git faz isso sozinho; ele só serve para você ver a base. Em relação a ela, o main ganhou o pudim.txt e o bolo ganhou o bolo.txt. Nenhum dos dois mexeu no que o outro mexeu, então o Git consegue juntar tudo sem perguntar nada.

2. O merge: git merge bolo

O comando é o mesmo da aula git merge: você fica no branch que vai receber as mudanças (o main) e diz qual branch quer trazer.

git
O programa.
merge
"Mesclar, juntar": traz para o branch atual o trabalho de outro branch.
bolo
O branch que vem. O branch atual (main) é o que recebe; o bolo continua existindo, igualzinho.

Quando o Git precisa criar um commit de merge, ele abre o editor de texto (o nano, o vim ou o que você configurou em git config) com uma mensagem pronta, para você confirmar ou mudar. A Ana digitou git merge bolo e o nano abriu com este texto:

Merge branch 'bolo'
# Please enter a commit message to explain why this merge is necessary,
# especially if it merges an updated upstream into a topic branch.
#
# Lines starting with '#' will be ignored, and an empty message aborts
# the commit.

Esse é o arquivo que abre no editor (na máquina da Ana, o nano, com o nome /home/ana/receitas/.git/MERGE_MSG no alto da tela). A primeira linha é a mensagem pronta; as linhas que começam com # são instruções, em inglês, e são jogadas fora. Traduzindo: "Escreva uma mensagem de commit explicando por que este merge é necessário, especialmente se ele junta um upstream atualizado num branch de tópico. Linhas começando com '#' serão ignoradas, e uma mensagem vazia cancela o commit." A Ana salvou e fechou o editor sem mudar nada, e o terminal mostrou:

$ git merge bolo
Merge made by the 'ort' strategy.
 bolo.txt | 4 ++++
 1 file changed, 4 insertions(+)
 create mode 100644 bolo.txt

Linha por linha:

Merge made by the 'ort' strategy.
"Merge feito pela estratégia 'ort'." Esta é a frase que diz que foi um merge de três vias, com commit de merge (no fast-forward, a primeira linha é Fast-forward). O ort é o nome do "motor" de merge que o Git usa desde a versão 2.34; você não precisa escolhê-lo.
bolo.txt | 4 ++++
O que entrou no main com o merge: o bolo.txt, com 4 linhas novas (um + para cada uma). O pudim.txt não aparece porque ele já estava no main.
1 file changed, 4 insertions(+)
"1 arquivo mudado, 4 inserções": o resumo das linhas acima.
create mode 100644 bolo.txt
O bolo.txt é um arquivo novo no main (o 100644 quer dizer "arquivo comum, não executável").

Para aceitar a mensagem pronta, é só salvar e fechar o editor (no nano, Ctrl+O, Enter, Ctrl+X; no vim, Esc e :wq). Enquanto o editor está aberto, o terminal mostra hint: Waiting for your editor to close the file... ("dica: esperando você fechar o arquivo no editor"); essa linha some quando você fecha. E se você apagar a mensagem e salvar o arquivo vazio? Veja em Quando dá errado.

Depois do merge

$ git log --oneline --graph --all
*   abc5385 (HEAD -> main) Merge branch 'bolo'
|\
| * 6dde70f (bolo) Adiciona a receita de bolo
* | 99a4d8c Adiciona a receita de pudim
|/
* 700bbd5 Cria o README
$ ls
README.md  bolo.txt  pudim.txt
$ git status
No ramo main
nothing to commit, working tree clean

O desenho agora tem a forma de um "losango": os dois caminhos saem do 700bbd5 e voltam a se encontrar no abc5385, o commit de merge, com a mensagem Merge branch 'bolo'. O |\ embaixo dele mostra que ele tem duas linhas chegando: dois pais. A pasta tem as duas receitas, e o git status diz No ramo main e nothing to commit, working tree clean ("nada a commitar, pasta de trabalho limpa"): o merge terminou. O branch bolo continua lá, no mesmo commit 6dde70f; se não for mais usar, você pode apagá-lo (aula Renomeando e Apagando Branches).

Por dentro: um commit com dois pais

O git log -1 mostra o último commit. Num commit de merge, aparece uma linha a mais:

$ git log -1
commit abc538510565bd3210cfbc98b5a0cb7d80af4aea (HEAD -> main)
Merge: 99a4d8c 6dde70f
Author: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

    Merge branch 'bolo'

A linha Merge: 99a4d8c 6dde70f lista os dois pais: primeiro o 99a4d8c (o pudim, que era o main, o lado que recebeu), depois o 6dde70f (o bolo, o lado que veio). Essa ordem importa: o primeiro pai é sempre o branch em que você estava. O resto é igual a qualquer commit: autor, data (o Git mostra a data em inglês, Thu Oct 15 = quinta-feira, 15 de outubro) e a mensagem.

Para ver o commit "cru", como o Git guardou (veja Como o Git Guarda as Coisas), use git cat-file -p:

$ git cat-file -p HEAD
tree 3a08b778fd61c7b986381a4e011f5ddfc02eab9c
parent 99a4d8ce4f8a5f275407e07a0c3e7fae9312b448
parent 6dde70ffc7ad8d913422fb63a25d71da2470f9c8
author Ana Souza <ana@exemplo.com> 1792071000 -0300
committer Ana Souza <ana@exemplo.com> 1792071000 -0300

Merge branch 'bolo'

Duas linhas parent ("pai"). Um commit comum tem uma; o primeiro commit do repositório não tem nenhuma; um commit de merge tem duas. É só isso que faz dele um commit de merge. A linha tree aponta para a "fotografia" da pasta com os três arquivos juntos. (O 1792071000 é a data contada em segundos desde 1970, o jeito que o Git guarda datas.) Contando os commits que chegam ao main, agora são 4: os dois do main, o do bolo e o de merge (git rev-list --count HEAD mostrou 4).

Missão: o repositório receitas já está como o da Ana: o main tem o pudim e o branch bolo tem o bolo. Veja os dois galhos com git log --oneline --graph --all, descubra o ancestral comum com git merge-base main bolo e junte o bolo no main com a mensagem padrão (git merge --no-edit bolo). No fim, olhe o desenho de novo e o git log -1.

3. A mensagem do commit de merge: -m e --no-edit

Se você não quer que o editor abra, dê a mensagem na própria linha, como no git commit -m:

$ git merge bolo -m 'Junta a receita de bolo'
Merge made by the 'ort' strategy.
 bolo.txt | 3 +++
 1 file changed, 3 insertions(+)
 create mode 100644 bolo.txt
$ git log --oneline --graph
*   b17594e (HEAD -> main) Junta a receita de bolo
|\
| * cf4d4e0 (bolo) Adiciona a receita de bolo
* | 2240ef2 Adiciona a receita de pudim
|/
* 700bbd5 Cria o README

(Este repositório foi montado de novo, com receitas um pouco mais curtas; por isso os hashes são outros.) O editor não abriu, e o commit de merge ficou com a mensagem que a Ana escreveu. O -m pode vir antes ou depois do nome do branch.

E se a mensagem padrão (Merge branch 'bolo') já serve, --no-edit ("sem editar") aceita-a sem abrir o editor. É o que você vai ver nos exemplos a seguir.

Qual mensagem escrever?

A padrão, Merge branch 'bolo', já diz o essencial e é a mais comum em projetos de verdade. Escreva uma sua quando quiser contar o que entrou: Junta a receita de bolo. Como nos outros commits, use o imperativo (veja Boas Mensagens de Commit).

4. Fast-forward ou três vias? Quem decide é o Git

Você não escolhe o tipo de merge: o Git olha o histórico e decide.

  • Se o branch atual não andou desde que o outro saiu dele, o Git faz fast-forward: só move a etiqueta, sem commit novo (aula Merge Fast-forward).
  • Se os dois andaram, ele faz o merge de três vias e cria o commit de merge.

Dá para pedir um commit de merge mesmo quando o fast-forward seria possível, com --no-ff ("no fast-forward", "sem avanço rápido"). Muitas equipes fazem isso para o histórico mostrar onde cada funcionalidade começou e terminou. A Ana criou o branch suco, fez um commit nele e voltou para o main, que ficou parado:

$ git switch -q -c suco
$ printf 'Suco de laranja\n' > suco.txt
$ git add suco.txt
$ git commit -q -m 'Adiciona o suco'
$ git switch -q main
$ git merge --no-ff --no-edit suco
Merge made by the 'ort' strategy.
 suco.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 suco.txt
$ git log --oneline --graph
*   4715114 (HEAD -> main) Merge branch 'suco'
|\
| * 51df8cd (suco) Adiciona o suco
|/
*   b17594e Junta a receita de bolo
|\
| * cf4d4e0 (bolo) Adiciona a receita de bolo
* | 2240ef2 Adiciona a receita de pudim
|/
* 700bbd5 Cria o README

(O -q, de quiet, "quieto", só esconde as mensagens dos comandos de preparação.) Sem o --no-ff, o Git teria feito fast-forward e o commit 51df8cd ficaria "em linha reta" no main. Com ele, apareceu o commit de merge 4715114, e o desenho mostra uma "bolha" ao lado: dá para ver que o suco foi feito num branch separado. Repare também que o merge do bolo, mais embaixo, continua lá, com a mensagem escolhida pela Ana.

Formas diferentes de fazer a mesma coisa

ComandoO que aconteceQuando usar
git merge boloAbre o editor com Merge branch 'bolo'Quando você quer ler ou ajustar a mensagem
git merge bolo -m "Junta a receita de bolo"Usa a sua mensagem, sem editorQuando a mensagem é curta e você já sabe o que escrever
git merge --no-edit boloAceita a mensagem padrão, sem editorNo dia a dia, quando a padrão serve
git merge --no-ff sucoCria o commit de merge mesmo quando daria fast-forwardQuando a equipe quer ver no histórico cada branch que entrou
git merge --ff-only boloSó aceita fast-forward; se precisar de três vias, desiste com erroQuando você não quer commits de merge (por exemplo, ao atualizar uma cópia)

Quando dá errado

Não tem nada para juntar: Already up to date. 
$ git merge bolo
Already up to date.

"Já está atualizado." A Ana rodou o merge do bolo uma segunda vez. Tudo o que existe no bolo já está no main (o commit 6dde70f é um dos pais do commit de merge), então não há nada para trazer. Não é erro: nada mudou. Como confirmar: o git log --oneline --graph --all mostra a ponta do bolo "dentro" do histórico do main. O mesmo acontece se você fizer o merge de um branch nele mesmo (git merge main estando no main).

O branch não existe: not something we can merge 
$ git merge bolinho
merge: bolinho - not something we can merge

"bolinho: não é algo que possamos juntar". Não existe branch (nem commit, nem tag) com esse nome. Quase sempre é erro de digitação. Como confirmar: git branch lista os branches que existem (aula git branch). Como resolver: rode de novo com o nome certo.

Mudanças não commitadas no caminho: would be overwritten by merge

No branch calda, a Ana acrescentou uma calda ao bolo.txt. No main, ela começou a reescrever o mesmo bolo.txt (um bolo de fubá) e, sem commitar, tentou o merge:

$ git status --short
 M bolo.txt
$ git merge --no-edit calda
error: Your local changes to the following files would be overwritten by merge:
        bolo.txt
Please commit your changes or stash them before you merge.
Aborting
Merge with strategy ort failed.

Linha por linha: "erro: as suas mudanças locais nos arquivos a seguir seriam sobrescritas pelo merge: bolo.txt. Por favor, faça commit das suas mudanças ou guarde-as com stash antes do merge. Cancelando. O merge com a estratégia ort falhou." O Git se recusou a começar para não estragar o trabalho que ainda não está guardado em nenhum commit. Nada mudou: o git status --short continua mostrando o M bolo.txt, e nenhum commit foi criado.

Como resolver, conforme o que você quer fazer com a mudança:

  • quer ficar com ela: faça o commit dela primeiro (git commit) e depois o merge;
  • quer guardar para depois: git stash, o merge, e git stash pop (aula git stash);
  • não quer: descarte com git restore bolo.txt (aula git restore). Foi o que a Ana fez:
$ git restore bolo.txt
$ git merge --no-edit calda
Merge made by the 'ort' strategy.
 bolo.txt | 1 +
 1 file changed, 1 insertion(+)

Regra prática: antes de um merge, git status limpo.

--ff-only com os dois lados andando: Not possible to fast-forward 
$ git merge --ff-only bolo
hint: Diverging branches can't be fast-forwarded, you need to either:
hint:
hint: 	git merge --no-ff
hint:
hint: or:
hint:
hint: 	git rebase
hint:
hint: Disable this message with "git config set advice.diverging false"
fatal: Not possible to fast-forward, aborting.

"Dica: branches que divergiram não podem avançar rápido; você precisa ou fazer git merge --no-ff ou git rebase. (…) Fatal: não é possível avançar rápido, cancelando." Você pediu "só fast-forward", mas os dois lados andaram: o Git não fez nada. Como resolver: se o commit de merge não for problema, rode o merge sem o --ff-only; a outra saída, o git rebase, tem aula própria (git rebase).

Apagou a mensagem no editor: Empty commit message

Se você apagar a linha Merge branch 'bolo' e salvar o arquivo vazio, o Git não cria o commit de merge:

$ git merge bolo
error: Empty commit message.
Not committing merge; use 'git commit' to complete the merge.
$ git status
No ramo main
Todos os conflitos foram corrigidos mas você continua mesclando.
  (use  "git commit" para concluir a mesclagem)

Mudanças a serem submetidas:
        new file:   bolo.txt

"Erro: mensagem de commit vazia. Não vou fazer o commit do merge; use git commit para concluí-lo." Atenção: o merge não foi cancelado. Ele ficou em andamento, com o bolo.txt já preparado, e o git status avisa: "você continua mesclando; use git commit para concluir a mesclagem". Como resolver: para terminar, git commit (ou git commit --no-edit, que usa a mensagem padrão); para desistir, git merge --abort (aula Desistindo de um Merge).

$ git commit --no-edit
[main abc5385] Merge branch 'bolo'

Resumo

  • Quando os dois branches andaram, o Git faz um merge de três vias: compara cada ponta com o ancestral comum (o git merge-base) e junta as mudanças dos dois lados.
  • O resultado é um commit de merge, com dois pais: o git log -1 mostra a linha Merge:, e o git log --graph desenha os galhos se juntando.
  • O git merge abre o editor com a mensagem Merge branch '…'; -m "…" dá outra mensagem, e --no-edit aceita a padrão.
  • Quem decide entre fast-forward e três vias é o Git; --no-ff força o commit de merge e --ff-only o proíbe.
  • Antes de um merge, deixe o git status limpo: mudanças não commitadas nos arquivos que o merge mexe fazem o Git recusar.
  • Quando os dois lados mudam as mesmas linhas, o Git não sabe qual escolher: é o conflito, assunto da próxima aula, Conflitos de Merge.

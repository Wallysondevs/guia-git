Git worktree

A Ana está no meio da receita de pudim, no branch receita-pudim, com arquivos mexidos e nada pronto para commit. O Bruno liga: "o link do bolo no site está quebrado, dá para arrumar agora?". Ela poderia guardar tudo com git stash, trocar de branch, consertar, voltar e tirar do stash. Ou pode simplesmente abrir outra pasta, com a main, ao lado da pasta onde está trabalhando, sem tocar em nada do pudim. É isso que o git worktree faz: várias pastas de trabalho (working trees) ligadas ao mesmo repositório, cada uma num branch.

Você vai aprender
  • O que é uma pasta de trabalho e por que um repositório pode ter várias.
  • Como criar uma com git worktree add, já com um branch novo (-b).
  • Como ver todas (git worktree list) e apagar (git worktree remove, git worktree prune).
  • Por que um branch não pode estar aberto em duas pastas ao mesmo tempo, e os outros erros reais.

Os comandos desta aula rodaram no Git 2.53 do Ubuntu da Ana (usuária ana, computador notebook). As mensagens do git worktree ainda não têm tradução em português nessa versão e saem em inglês; a aula traduz cada uma. O comando existe desde o Git 2.5 git 2.5+.

A ideia: duas mesas, um só arquivo de documentos

Até agora, cada repositório tinha uma pasta de trabalho: a pasta onde você edita os arquivos, que mostra um branch de cada vez. Trocar de branch é como guardar todos os papéis da mesa e espalhar outros. Com o worktree, você monta uma segunda mesa, com outros papéis, e as duas usam o mesmo arquivo de documentos (a pasta .git, com todo o histórico):

/home/ana/receitas/            « a pasta principal, no branch receita-pudim
   ├── .git/                   « o repositório (histórico, branches, tudo)
   ├── pudim.md   (mexido)
   └── notas.txt  (novo)

/home/ana/receitas-corrige/    « a segunda pasta, no branch corrige-link
   ├── .git       (um ARQUIVO que aponta para /home/ana/receitas/.git)
   ├── index.md
   └── …

Um commit feito numa pasta aparece na hora para a outra: o histórico é um só.

$ git status

	notas.txt

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")

O pudim.md está modificado e o notas.txt é novo (veja git status). Nada disso está pronto para um commit, e a Ana não quer mexer nesses arquivos agora.

2. Criar a segunda pasta: git worktree add

$ git worktree add ../receitas-corrige -b corrige-link main
Preparing worktree (new branch 'corrige-link')
HEAD is now at ec8392a Adiciona receita de bolo
git worktree add
"Acrescente uma pasta de trabalho."
../receitas-corrige
Onde criar a pasta nova. O .. quer dizer "ao lado da pasta atual", em /home/ana/receitas-corrige. Evite criar dentro da pasta do repositório: ela apareceria como arquivo não rastreado.

3. Trabalhar na pasta nova

Basta entrar nela. Para o Git, ela é uma pasta de repositório como qualquer outra:

$ cd ../receitas-corrige
$ ls
README.md
bolo.md
index.md                                   « sem pudim.md nem notas.txt: aqui é a main
$ git status
No ramo corrige-link
nothing to commit, working tree clean      « "nada a commitar, pasta limpa"
$ sed -i 's/bolo.htm/bolo.md/' index.md
$ git commit -am "Corrige link do bolo"
[corrige-link b64663e] Corrige link do bolo
 1 file changed, 1 insertion(+), 1 deletion(-)

(O sed -i só troca o texto do link pelo terminal; você pode usar o editor.) E o que é o .git dessa pasta? Não é uma pasta, é um arquivinho de uma linha:

$ cat .git
gitdir: /home/ana/receitas/.git/worktrees/receitas-corrige

"O diretório do Git está em /home/ana/receitas/.git/worktrees/receitas-corrige": a pasta nova não tem histórico próprio; ela usa o da pasta principal. Por isso o commit já aparece lá, e o trabalho do pudim continua intocado:

$ cd ../receitas
$ git status --short
 M pudim.md                                « tudo como a Ana deixou
?? notas.txt
$ git log --oneline --graph --all
* b64663e Corrige link do bolo             « o commit feito na outra pasta
| * 1934126 Começa a receita de pudim
|/
* ec8392a Adiciona receita de bolo
* a56584f Cria o site de receitas

Agora o corrige-link segue o caminho normal: git push -u origin corrige-link e um pull request, como no GitHub Flow. Tudo isso pode ser feito de qualquer uma das duas pastas.

Pratique no seu computador

O terminal simulado do guia não tem o git worktree, então esta prática é no seu terminal de verdade, num repositório de teste:

  1. Num repositório com pelo menos um commit na main, crie um branch e mude de branch: git switch -c rascunho; modifique um arquivo e não faça commit.
  2. Crie a segunda pasta: git worktree add ../teste-corrige -b corrige main.
  3. Entre nela (cd ../teste-corrige), mude um arquivo e faça um commit.
  4. Volte (cd -) e confira: git status mostra a sua mudança intocada, e git log --oneline --graph --all mostra o commit feito na outra pasta.

4. Um branch, uma pasta

Uma regra importante: o mesmo branch não pode estar aberto em duas pastas. Se pudesse, um commit feito numa pasta mudaria o branch "por baixo" da outra, e os arquivos dela ficariam errados. O Git recusa:

$ git worktree add ../outra-pasta receita-pudim
Preparing worktree (checking out 'receita-pudim')
fatal: 'receita-pudim' is already used by worktree at '/home/ana/receitas'

"receita-pudim já está em uso pela pasta de trabalho /home/ana/receitas". Repare na forma do comando: sem -b, o último argumento é um branch que já existe, para abrir na pasta nova. Com um branch livre, como a main, funciona:

$ git worktree add ../outra-pasta main
Preparing worktree (checking out 'main')
HEAD is now at ec8392a Adiciona receita de bolo
$ git worktree list
/home/ana/receitas         1934126 [receita-pudim]
/home/ana/outra-pasta      ec8392a [main]
/home/ana/receitas-corrige b64663e [corrige-link]

A regra também vale para o git switch: enquanto a main estiver aberta em outra pasta, você não consegue trocar para ela na pasta principal (veja Quando dá errado).

5. Apagar a pasta: git worktree remove

Terminado o conserto, a pasta extra pode ir embora. O comando certo é o git worktree remove, que apaga a pasta e avisa o repositório. Ele se recusa se houver algo não salvo lá dentro:

$ echo teste > ../receitas-corrige/teste.txt
$ git worktree remove ../receitas-corrige
fatal: '../receitas-corrige' contains modified or untracked files, use --force to delete it
$ rm ../receitas-corrige/teste.txt
$ git worktree remove ../receitas-corrige
$ git worktree list
/home/ana/receitas    1934126 [receita-pudim]
/home/ana/outra-pasta ec8392a [main]

"../receitas-corrige contém arquivos modificados ou não rastreados; use --force para apagá-la". Havia um teste.txt esquecido lá. A Ana apagou o arquivo e tentou de novo: sem mensagem nenhuma, a pasta foi removida. O branch corrige-link continua existindo, com o commit: apagar a pasta não apaga o branch nem o histórico.

E se a pasta foi apagada à mão? git worktree prune

Se alguém apagar a pasta extra com rm -rf ou pelo gerenciador de arquivos, o repositório continua achando que ela existe:

$ rm -rf ../outra-pasta
$ git worktree list
/home/ana/receitas    1934126 [receita-pudim]
/home/ana/outra-pasta ec8392a [main] prunable       « "podável": a pasta sumiu
$ git worktree prune
$ git worktree list
/home/ana/receitas 1934126 [receita-pudim]

O prunable ("podável") marca uma pasta que não existe mais. O git worktree prune ("podar") limpa esses registros.

Pratique no seu computador

Continuando a prática anterior, no seu terminal: rode git worktree list, apague a pasta extra com git worktree remove ../teste-corrige e confira com git branch que o branch corrige continua lá. Para ver o prunable, crie outra pasta com git worktree add ../teste2 main, apague-a com rm -rf ../teste2 e rode git worktree list e git worktree prune.

A forma curta, só com a pasta:

$ git worktree add ../revisao
Preparing worktree (new branch 'revisao')
HEAD is now at 1934126 Começa a receita de pudim

O Git criou o branch revisao (o nome da pasta) a partir do commit atual, 1934126.

Quando dá errado

fatal: '…' is already used by worktree at '…' 
$ git switch main
fatal: 'main' is already used by worktree at '/home/ana/site-main'

"A main já está em uso pela pasta /home/ana/site-main". O que aconteceu: o branch está aberto em outra pasta de trabalho, e o Git não deixa abrir o mesmo branch em duas. Como confirmar: git worktree list. Como resolver: trabalhe com a main naquela pasta (cd ../site-main), ou remova a pasta extra com git worktree remove ../site-main. Se a pasta foi apagada à mão, rode git worktree prune.

contains modified or untracked files, use --force to delete it

O git worktree remove se recusa a apagar uma pasta com mudanças não commitadas ou arquivos novos (você viu na seção 5). Como resolver: entre na pasta e olhe o git status. Se é trabalho que importa, faça o commit; se é lixo, apague os arquivos. O --force apaga tudo sem perguntar: use só quando tiver certeza.

Apaguei a pasta com rm -rf

Nada se perde do que estava commitado: o histórico e o branch estão na pasta principal. O que estava sem commit naquela pasta, esse sim, foi embora. O git worktree list mostra a pasta como prunable; rode git worktree prune para limpar o registro.

Não acho a pasta principal pelo .git

Na pasta extra, o .git é um arquivo, não uma pasta. Ferramentas antigas que procuram a pasta .git podem estranhar. O cat .git mostra onde está o repositório de verdade, e o git worktree list (de qualquer pasta) mostra todas.

Resumo

  • git worktree abre outro branch numa segunda pasta, ligada ao mesmo repositório: nada de stash nem commit pela metade para atender uma urgência.
  • git worktree add ../pasta -b novo main cria a pasta com um branch novo; git worktree add ../pasta branch abre um branch existente.
  • O histórico é um só: um commit numa pasta aparece na hora nas outras. Na pasta extra, o .git é um arquivo que aponta para o repositório principal.
  • Um branch só pode estar aberto em uma pasta: senão, is already used by worktree at ….
  • git worktree list mostra as pastas; git worktree remove apaga (o branch fica); git worktree prune limpa o registro de pastas apagadas à mão.

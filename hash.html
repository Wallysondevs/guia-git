Git hash

Todo commit tem um "nome" que parece um código secreto: fe996fb8ecae7fe25026045fd46f15ca756bc19c. É o hash do commit (em inglês, hash é "picadinho": o Git "pica" o conteúdo do commit e tira dele um número). Você já usou hashes nas aulas anteriores para apontar commits no git show, no git revert e no git reset. Nesta aula você descobre de onde eles vêm, por que nunca se repetem, e por que os hashes deste guia saem iguais aos que você vê no terminal do guia.

Você vai aprender
  • O que é o hash: a "impressão digital" de 40 caracteres de um commit (ou de qualquer objeto do Git).
  • O hash completo e o hash curto (fe996fb), e como pedir um ou outro (git rev-parse, --abbrev).
  • Como o hash é calculado, conferido com o git hash-object e o sha1sum.
  • Por que mudar uma letra (ou a hora) muda o hash inteiro.
  • O que fazer quando um hash curto é "ambíguo", e o que são os repositórios SHA-256.

Todas as saídas desta aula vieram do Git real da máquina da Ana (usuária ana, computador notebook).

A ideia: a impressão digital do conteúdo

Na aula Como o Git Guarda as Coisas, você viu que tudo o que o Git guarda (o conteúdo de cada arquivo, cada pasta, cada commit) vira um objeto, e que o nome de cada objeto é um hash. O hash funciona como uma impressão digital:

  • o mesmo conteúdo sempre dá a mesma impressão digital, em qualquer computador do mundo;
  • conteúdos diferentes dão impressões digitais diferentes, mesmo que a diferença seja uma vírgula;
  • olhando só a impressão digital, não dá para reconstruir o conteúdo (ela é um resumo, não uma cópia).

A receita matemática que o Git usa para tirar essa impressão digital se chama SHA-1 (de Secure Hash Algorithm 1, "algoritmo de hash seguro"). O resultado tem sempre 160 bits, escritos como 40 caracteres hexadecimais: os algarismos de 0 a 9 e as letras de a a f.

1. O hash completo e o hash curto

$ git commit -m "Primeiro commit"
[main (root-commit) fe996fb] Primeiro commit   « o hash curto
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
$ git log
commit fe996fb8ecae7fe25026045fd46f15ca756bc19c   « o hash completo
Author: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

    Primeiro commit
$ git log --oneline
fe996fb Primeiro commit

O git log mostra o hash completo, com 40 caracteres. O git commit e o git log --oneline mostram só o começo, fe996fb: o hash curto (ou abreviado). Ele tem 7 caracteres no começo de um projeto e o Git o aumenta sozinho quando o repositório cresce tanto que 7 caracteres já não bastam para distinguir os objetos.

Para qualquer comando que pede um commit, os dois servem, e maiúsculas e minúsculas também (FE996FB funciona). Também dá para pedir o hash diretamente:

$ git rev-parse HEAD
fe996fb8ecae7fe25026045fd46f15ca756bc19c
$ git rev-parse --short HEAD
fe996fb
$ git log --oneline --abbrev=4
fe99 Primeiro commit
$ git log --format='%H %s'
fe996fb8ecae7fe25026045fd46f15ca756bc19c Primeiro commit
git rev-parse HEAD
"Traduza este nome para um hash". O rev-parse aceita qualquer jeito de apontar um commit (HEAD, main, HEAD~1, um hash curto) e devolve o hash completo. Útil em scripts.
--short
Devolve o hash curto em vez do completo.
--abbrev=4
No git log, abrevia com no mínimo 4 caracteres (o menor tamanho que o Git aceita).
--format='%H %s'
Um formato próprio para o log: %H é o hash completo, %s é o título da mensagem (mais em git log: Filtros e Formatos).

Missão: o repositório da Ana tem o primeiro commit. Mostre o hash completo dele com git rev-parse. Compare com o que aparece no git log --oneline: o curto é o começo do completo.

2. Calculando um hash: o git hash-object

O comando git hash-object calcula o hash que um conteúdo teria como blob, sem precisar de commit. O README da Ana:

$ git hash-object README.md
2644316531953179572e7fdf95ede19e1b33c399
$ echo '# Receitas da Ana' | git hash-object --stdin
2644316531953179572e7fdf95ede19e1b33c399

O mesmo hash, de dois jeitos: lendo o arquivo, ou lendo o texto pela entrada padrão (--stdin, com o |; veja O Mínimo de Terminal). Para o Git, o que importa é o conteúdo, não o nome do arquivo. Agora, mudando quase nada:

$ echo '# Receitas da ana' | git hash-object --stdin
235cc22c23c6241506c8a2a6239232ead6d9c707   « só o "A" virou "a"
$ echo '# Receitas da Ana!' | git hash-object --stdin
eb8588572260d01a2cbf6ef852a07f3476194d15   « só um "!" a mais

Uma letra minúscula ou um ponto de exclamação, e o hash muda por completo: não sobra nenhuma semelhança com 2644316…. Isso é proposital. Com um hash assim, é impossível alterar um arquivo (ou um commit) "só um pouquinho" sem que todo mundo perceba.

Sem mágica: é o SHA-1 de um textinho

O Git não calcula o SHA-1 do conteúdo puro: antes, ele põe um cabeçalho com o tipo do objeto e o tamanho em bytes, separado por um caractere nulo (\0). O comando sha1sum, que existe em todo Linux e não tem nada a ver com o Git, confirma:

$ printf 'blob 18\0# Receitas da Ana\n' | sha1sum
2644316531953179572e7fdf95ede19e1b33c399  -

blob (o tipo), 18 (o tamanho do conteúdo, como na aula anterior), o nulo, e o conteúdo com a quebra de linha (\n): o mesmo 2644316…. O hash de um commit é calculado do mesmo jeito, a partir do textinho que o git cat-file mostra:

$ git cat-file commit HEAD
tree 2266689caa9ea60c127cd9b491dbe117f9699670
author Ana Souza <ana@exemplo.com> 1792071000 -0300
committer Ana Souza <ana@exemplo.com> 1792071000 -0300

Primeiro commit
$ git cat-file commit HEAD | wc -c
170
$ (printf 'commit 170\0'; git cat-file commit HEAD) | sha1sum
fe996fb8ecae7fe25026045fd46f15ca756bc19c  -

O commit tem 170 bytes (o wc -c conta), e o SHA-1 de commit 170 + nulo + o texto do commit é exatamente fe996fb8…, o hash do primeiro commit da Ana. Não precisa decorar nada disso; o importante é entender o que entra no hash de um commit:

  • a tree (que depende do conteúdo e do nome de todos os arquivos);
  • o pai (o hash do commit anterior, que por sua vez depende do pai dele, e assim até o primeiro commit);
  • o autor e o committer, com nome, e-mail, data e hora;
  • a mensagem.

3. Por que os hashes deste guia são iguais aos seus

Se o hash depende só do conteúdo, dois commits com exatamente o mesmo conteúdo têm o mesmo hash, em qualquer computador. Normalmente isso nunca acontece, porque a data e a hora (com os segundos) são diferentes. Mas no laboratório do guia e no terminal do guia, o nome, o e-mail e a data são fixos (Ana Souza, ana@exemplo.com, 15/10/2026 10:30). Por isso, o primeiro commit do README sai fe996fb nesta aula, na aula Como o Git Guarda as Coisas e em todas as outras.

Basta mudar a hora em um minuto para o hash mudar. A Ana refez o commit com outra hora de commit (a variável GIT_COMMITTER_DATE diz ao Git que data usar):

$ GIT_COMMITTER_DATE='2026-10-15T10:31:00-03:00' git commit --amend --no-edit
[main c2219b0] Primeiro commit
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
$ git cat-file -p HEAD
tree 2266689caa9ea60c127cd9b491dbe117f9699670
author Ana Souza <ana@exemplo.com> 1792071000 -0300
committer Ana Souza <ana@exemplo.com> 1792071060 -0300   « 60 segundos depois

Primeiro commit

Mesma tree, mesmo autor, mesma mensagem; só o committer está 60 segundos depois (1792071060). Resultado: c2219b0, um hash totalmente diferente. É por isso que, no seu computador, com o seu nome e o seu relógio, os hashes saem diferentes dos do guia, e é por isso que o --amend sempre gera um hash novo. (Depois do teste, a Ana voltou ao commit original com git reset -q --hard fe996fb; veja os modos do reset.)

Missão: calcule com git hash-object --stdin o hash do texto # Receitas da ana (com "ana" minúsculo) e veja como ele não tem nada a ver com o hash do README (2644316…). Dica: echo 'texto' | git hash-object --stdin.

4. Quantos caracteres digitar?

Você pode digitar o hash inteiro, o curto, ou ainda menos: o Git aceita o começo do hash a partir de 4 caracteres, desde que só um objeto comece assim.

$ git show --stat fe99
commit fe996fb8ecae7fe25026045fd46f15ca756bc19c
Author: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

    Primeiro commit

 README.md | 1 +
 1 file changed, 1 insertion(+)
$ git show --stat fe9
fatal: ambiguous argument 'fe9': unknown revision or path not in the working tree.
Use '--' to separate paths from revisions, like this:
'git <command> [<revision>...] -- [<file>...]'

Com 4 caracteres (fe99), funcionou. Com 3 (fe9), o Git nem tenta procurar um hash: acha que pode ser o nome de um arquivo ou de um branch, não encontra nenhum, e reclama de "argumento ambíguo". Na prática, use os 7 do git log --oneline: em projetos pequenos e médios, eles bastam; num projeto enorme, o próprio Git passa a mostrar mais caracteres.

5. SHA-1 e SHA-256

O SHA-1 foi criado em 1995 e, em 2017, pesquisadores conseguiram fabricar de propósito dois arquivos diferentes com o mesmo SHA-1. O Git reagiu de dois jeitos: passou a usar uma versão "endurecida" do SHA-1, que detecta esse tipo de ataque, e criou o suporte a SHA-256, uma receita mais forte, com hashes de 64 caracteres. Por enquanto, o padrão continua sendo o SHA-1, e é ele que os serviços como o GitHub usam. Dá para ver qual um repositório usa, e criar um SHA-256 para experimentar:

$ cd receitas
$ git rev-parse --show-object-format
sha1
$ cd ..
$ mkdir receitas2 && cd receitas2
$ git init -q --object-format=sha256
$ echo '# Receitas da Ana' > README.md
$ git add README.md
$ git commit -q -m "Primeiro commit"
$ git log --oneline
2220c93 Primeiro commit
$ git rev-parse HEAD
2220c93091922ec2bbc6bc8e7d52a58e59153aebcdf239d31a7d5f826603112e
$ git rev-parse --show-object-format
sha256

O mesmo commit, com o mesmo conteúdo, a mesma autora e a mesma data, ganhou outro hash, agora com 64 caracteres. O hash curto continua com 7. Para o dia a dia, nada muda: você só vai notar hashes mais compridos. Neste guia, todos os repositórios são SHA-1, o padrão.

Quando dá errado

Hash digitado errado 
$ git show --stat fe996fc
fatal: ambiguous argument 'fe996fc': unknown revision or path not in the working tree.
Use '--' to separate paths from revisions, like this:
'git <command> [<revision>...] -- [<file>...]'

Uma letra trocada (c no lugar do b) e o Git não encontra nada: não há "hash parecido" para o Git, só igual ou diferente. A mensagem é a mesma do hash curto demais: "argumento ambíguo, revisão desconhecida ou caminho fora da árvore de trabalho". Como resolver: copie e cole o hash do git log --oneline em vez de digitar.

Hash curto ambíguo

Para provocar este erro, a Ana guardou 400 blobs de teste (os textos receita 1 a receita 400, com git hash-object -w) num repositório vazio. Dois deles saíram começando com efd9:

$ git cat-file -p efd9
error: short object ID efd9 is ambiguous
hint: The candidates are:
hint:   efd94d7 blob
hint:   efd9c5e blob
fatal: Not a valid object name efd9

"O ID curto de objeto efd9 é ambíguo. Os candidatos são: …". O Git não escolhe por você: mostra os objetos que começam assim, com o tipo de cada um. Como resolver: digite mais caracteres (efd94d7). É por isso que o Git usa 7 caracteres no hash curto, e não 4.

Resumo

  • O hash é a impressão digital de um objeto do Git: 40 caracteres hexadecimais (SHA-1), calculados a partir do conteúdo.
  • O hash curto (fe996fb) é o começo do completo; o Git aceita a partir de 4 caracteres, se não houver ambiguidade.
  • git rev-parse traduz nomes em hashes; git hash-object calcula o hash de um conteúdo.
  • O hash de um commit depende da tree, do pai, do autor, do committer (com a hora) e da mensagem: qualquer mudança gera outro hash.
  • Com nome, e-mail e data fixos, os hashes do guia se repetem; no seu computador, com o seu relógio, serão outros.
  • Repositórios novos podem usar SHA-256 (64 caracteres), mas o padrão ainda é SHA-1.

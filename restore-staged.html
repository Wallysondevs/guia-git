Tirando da Área de Preparo git 2.23+

A Ana deu git add . e, ao conferir com o git status, viu que junto com a receita entrou o arquivo de senhas. Ela não quer apagar nada, nem perder a mudança da receita: só quer tirar o senhas.txt da "mala" antes de fechar o commit. Para isso existe o git restore --staged: ele desfaz um git add, e as mudanças continuam intactas na pasta.

Você vai aprender
  • A tirar um arquivo da área de preparo com git restore --staged arquivo, sem perder as mudanças.
  • A diferença entre git restore --staged (seguro) e git restore (descarta).
  • A tirar tudo de uma vez e a reconhecer o comando antigo, git reset HEAD arquivo.
  • O caso especial do repositório sem nenhum commit (git rm --cached).

Todas as saídas desta aula saíram do Git do Ubuntu 26.04 (Git 2.53), na máquina da Ana (usuária ana, computador notebook), com o sistema em português. Algumas mensagens do Git ainda não têm tradução e saem em inglês.

A ideia: tirar da mala, devolver à cama

Lembra da mala da aula git diff --staged? As roupas separadas na cama são a pasta de trabalho; a mala é a área de preparo; fechar a mala é o commit. Tirar uma camiseta da mala não joga a camiseta fora: ela volta para a cama, do jeito que estava. É isso que o git restore --staged faz.

   último commit        área de preparo          sua pasta
  ┌─────────────┐      ┌──────────────┐       ┌─────────────┐
  │             │ ───► │  senhas.txt  │       │ senhas.txt  │
  │             │      │  (preparado) │       │ (continua!) │
  └─────────────┘      └──────────────┘       └─────────────┘
      git restore --staged: copia o último commit para a área de preparo,
      e NÃO mexe na sua pasta

1. Desfazendo um git add

A Ana acrescentou a farinha no bolo e, sem querer, deixou um senhas.txt na pasta. Um git add . preparou os dois:

$ git add .
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt
	new file:   senhas.txt

O senhas.txt aparece como new file ("arquivo novo") em Mudanças a serem submetidas: ele iria no próximo commit. E a dica logo abaixo do título já diz o que fazer: (use "git restore --staged <file>..." to unstage), "use git restore --staged para tirar da área de preparo" (unstage é o contrário de stage, "preparar"):

$ git restore --staged senhas.txt
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt

Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	senhas.txt

$ cat senhas.txt
SENHA=abacaxi123
git restore
O comando de restaurar (aula git restore).
--staged
"Restaure a área de preparo": ponha nela a versão do último commit, desfazendo o que o git add colocou. A pasta de trabalho não é tocada. Forma curta: -S (maiúsculo).
senhas.txt
O arquivo a tirar. Pode ser mais de um, uma pasta, . ou um padrão.

Resultado: o bolo.txt continua preparado; o senhas.txt voltou a ser um arquivo não monitorado (como era antes do git add), e o cat mostra que o conteúdo está lá, intacto. Para ele não voltar a entrar num git add ., ponha-o no .gitignore.

Missão: o git add . já foi dado e preparou o bolo.txt e o senhas.txt. Tire o senhas.txt da área de preparo (sem apagá-lo) e faça o commit só da mudança do bolo. Use git status antes e depois.

2. Um arquivo já rastreado: a mudança fica na pasta

Com um arquivo que o Git já conhece, tirar da área de preparo devolve a mudança para a seção de "não preparadas". Nada se perde:

$ echo 'calda de caramelo' >> pudim.txt
$ git add pudim.txt
$ git status --short
M  bolo.txt
M  pudim.txt
?? senhas.txt
$ git restore --staged .
$ git status --short
 M bolo.txt
 M pudim.txt
?? senhas.txt
$ git diff --stat
 bolo.txt  | 1 +
 pudim.txt | 1 +
 2 files changed, 2 insertions(+)

Repare no M: antes ele estava na primeira coluna do --short (preparado); depois do git restore --staged ., pulou para a segunda (modificado, não preparado). O . tirou tudo da área de preparo de uma vez. E o git diff --stat confirma que as duas mudanças (a farinha e a calda) continuam na pasta, agora como mudanças não preparadas.

Quando usar
  • Um git add . pegou coisa demais (uma senha, um arquivo de teste, um log).
  • Você quer dividir as mudanças em dois commits: tire tudo da área de preparo e prepare de novo, um grupo por vez (veja Boas Mensagens de Commit: commits pequenos, um assunto cada).
  • O git diff --staged mostrou algo que não devia ir no commit.

Só um pedaço: -p

Como no git add -p e no git restore -p (aula git restore), o git restore --staged -p arquivo mostra cada trecho preparado e pergunta se é para tirá-lo da área de preparo (y) ou mantê-lo (n). Útil quando o mesmo arquivo tem duas mudanças que devem ir em commits separados.

3. git restore --staged × git restore

Os dois comandos se parecem, mas fazem coisas bem diferentes. Confundi-los é a forma mais comum de perder trabalho:

git restore --staged arquivogit restore arquivo
Mexe naárea de preparopasta de trabalho
Desfazo git addas suas edições no arquivo
As mudançascontinuam na pastasão descartadas
Dica do git statusto unstageto discard changes in working directory
Perigonenhum⚠ não tem volta

E os dois juntos (git restore --staged --worktree arquivo) voltam o arquivo ao último commit nos dois lugares, descartando tudo. Veja o mapa do desfazer.

4. O comando antigo: git reset HEAD arquivo

Antes do Git 2.23, a dica do git status era use "git reset HEAD <file>..." to unstage. Esse comando ainda funciona e aparece em muitos tutoriais:

$ git add bolo.txt pudim.txt
$ git reset HEAD pudim.txt
Unstaged changes after reset:
M	pudim.txt
$ git status --short
M  bolo.txt
 M pudim.txt
?? senhas.txt

Mesmo efeito do git restore --staged pudim.txt, só que o git reset fala: Unstaged changes after reset ("mudanças não preparadas depois do reset"), com a lista dos arquivos que ficaram com mudanças fora da área de preparo. O HEAD pode ser omitido (git reset pudim.txt), e sem nenhum nome o git reset tira tudo da área de preparo:

$ git reset
Unstaged changes after reset:
M	bolo.txt
M	pudim.txt
$ git status --short
 M bolo.txt
 M pudim.txt
?? senhas.txt
git reset tem outros usos, bem mais perigosos

Com um nome de arquivo (ou sem nada), o git reset só mexe na área de preparo: é seguro. Mas com outras opções, como git reset --hard, ele apaga mudanças e commits. É por isso que o Git criou o git restore --staged, que só faz a coisa segura. Os outros usos estão em git reset e reset --soft, --mixed e --hard.

5. O caso especial: repositório sem nenhum commit

Num repositório recém-criado, ainda sem commits, o git status dá uma dica diferente:

$ git init -q
$ echo oi > a.txt
$ git add a.txt
$ git status
No ramo main

No commits yet

Mudanças a serem submetidas:
  (utilize "git rm --cached <arquivo>..." para não apresentar)
	new file:   a.txt

No commits yet = "nenhum commit ainda". E a dica agora é git rm --cached. O motivo: o git restore --staged copia "o último commit" para a área de preparo, e aqui não existe último commit. Veja o que acontece se você tentar:

$ git restore --staged a.txt
fatal: could not resolve 'HEAD'
$ git rm --cached a.txt
rm 'a.txt'
$ git status --short
?? a.txt

fatal: could not resolve 'HEAD' = "não foi possível resolver (encontrar) o HEAD": o HEAD ainda não aponta para commit nenhum (veja O que é HEAD). O git rm --cached (aula git rm) tira o arquivo da área de preparo sem apagá-lo da pasta, e o a.txt volta a ser não monitorado (??). Depois do primeiro commit, use o git restore --staged de sempre.

Por que não usar sempre o git rm --cached?

Num arquivo que já está em algum commit, o git rm --cached prepara a remoção do arquivo do repositório (aula git rm), que é outra coisa. Regra: siga a dica que o git status mostrar; ela muda conforme a situação.

Quando dá errado

fatal: could not resolve 'HEAD'

O repositório ainda não tem nenhum commit (seção 5). Como resolver: git rm --cached arquivo, como diz o git status.

error: pathspec '…' did not match any file(s) known to git 
$ git restore --staged nada.txt
error: pathspec 'nada.txt' did not match any file(s) known to git

"O caminho não corresponde a nenhum arquivo conhecido pelo Git": o nome está errado, ou o arquivo nunca foi preparado nem commitado. Como resolver: copie o nome exatamente como aparece no git status.

"Tirei da área de preparo e a mudança sumiu!"

Provavelmente você digitou git restore arquivo, sem o --staged. Aí o Git descartou as mudanças não preparadas da pasta (a versão preparada continuou lá). Como confirmar: git status; se o arquivo ainda aparece em Mudanças a serem submetidas, a parte preparada está salva. Como evitar: confira o comando antes do Enter; o --staged é o que torna a operação segura.

"O arquivo saiu da área de preparo, mas continua aparecendo no git status"

É o esperado: as mudanças continuam na pasta, agora como não preparadas (ou o arquivo como não monitorado). Tirar da área de preparo não é apagar. Se você quer que ele pare de aparecer, use o .gitignore (arquivo novo) ou descarte as mudanças com git restore (arquivo rastreado).

Missão final: dois commits em vez de um

Missão: o git add . juntou duas mudanças sem relação (a farinha do bolo e a calda do pudim). Faça dois commits: primeiro só o bolo, depois só o pudim. Dica: tire o pudim.txt da área de preparo, commite, e depois prepare e commite o pudim.

Resumo

  • git restore --staged arquivo (ou -S) desfaz um git add: tira o arquivo da área de preparo e mantém as mudanças na pasta. É seguro.
  • Não confunda com git restore arquivo, que descarta as mudanças da pasta.
  • git restore --staged . tira tudo; -p escolhe trechos.
  • Em tutoriais antigos: git reset HEAD arquivo (ou git reset arquivo).
  • Sem nenhum commit no repositório, use git rm --cached arquivo (o git status avisa).
  • Siga a dica do git status: ela sempre mostra o comando certo para a situação.

Git diff --staged

Na aula git diff você viu que, depois do git add, o diff "some". As mudanças não sumiram: foram para a área de preparo. Para enxergá-las existe o git diff --staged (staged = "preparado"): ele mostra exatamente o que vai entrar no próximo commit. É a última conferência antes de fotografar.

Você vai aprender
  • O que o git diff --staged compara: a área de preparo com o último commit.
  • Que --staged e --cached são a mesma coisa.
  • A ler o caso em que o mesmo arquivo tem uma parte preparada e outra não.
  • O git diff HEAD: tudo o que mudou desde o último commit, preparado ou não.
  • Como um arquivo novo aparece (new file mode, /dev/null, @@ -0,0 +1 @@).

Todas as saídas desta aula saíram do Git do Ubuntu 26.04, na máquina da Ana (usuária ana, computador notebook), com o sistema em português.

A ideia: conferir a mala antes de fechar

Antes de uma viagem, a Ana separa as roupas na cama (a pasta de trabalho), põe na mala o que vai levar (a área de preparo) e fecha a mala (o commit). Antes de fechar, vale abrir a mala e olhar: "pus mesmo o carregador? Não pus o casaco errado?". O git diff --staged é esse olhar dentro da mala.

   último commit        área de preparo         sua pasta
  ┌─────────────┐      ┌──────────────┐      ┌─────────────┐
  │  bolo.txt   │      │   bolo.txt   │      │  bolo.txt   │
  └─────────────┘      └──────────────┘      └─────────────┘
         └── git diff --staged ──┘└────── git diff ─────┘
         "o que vai no commit"     "o que ainda não preparei"

         └──────────────── git diff HEAD ─────────────────┘
                   "tudo desde o último commit"

Guarde este desenho: os três comandos olham pares diferentes das mesmas três "caixas".

1. O primeiro git diff --staged

A Ana tem a receita de bolo commitada com 4 ovos. Ela muda para 3 ovos e já prepara o arquivo:

$ printf 'Bolo de cenoura\n3 cenouras\n3 ovos\n' > bolo.txt
$ git add bolo.txt
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt

$ git diff
$

O git status diz que o arquivo está pronto para o commit (Mudanças a serem submetidas; "submeter" é como a tradução do Git chama o commit), com a dica, ainda em inglês, (use "git restore --staged <file>..." to unstage): "use git restore --staged para tirar da área de preparo". E o git diff não mostra nada: a pasta e a área de preparo estão iguais. Agora, o comando desta aula:

$ git diff --staged
diff --git a/bolo.txt b/bolo.txt
index 10a5c6d..29056e1 100644
--- a/bolo.txt
+++ b/bolo.txt
@@ -1,3 +1,3 @@
 Bolo de cenoura
 3 cenouras
-4 ovos
+3 ovos
git diff
O comando de comparar.
--staged
"Compare a área de preparo com o último commit", em vez de comparar a pasta com a área de preparo.

O formato é o mesmo diff unificado da aula anterior: o a/ é a versão do último commit, o b/ é a versão preparada, -4 ovos saiu e +3 ovos entrou. Se você ainda não sabe ler cada linha, volte em git diff.

--cached: o nome antigo

$ git diff --cached
diff --git a/bolo.txt b/bolo.txt
index 10a5c6d..29056e1 100644
--- a/bolo.txt
+++ b/bolo.txt
@@ -1,3 +1,3 @@
 Bolo de cenoura
 3 cenouras
-4 ovos
+3 ovos

Saída idêntica. --cached é o nome original da opção (a área de preparo já foi chamada de cache e de index); --staged chegou depois, como sinônimo mais fácil de lembrar. Você vai ver os dois em tutoriais.

Missão: o bolo.txt já foi preparado. Rode git diff (vazio!) e depois git diff --staged para ver o que vai entrar no commit.

2. O mesmo arquivo, preparado e não preparado

Agora o caso que confunde todo iniciante. Depois do git add, a Ana lembrou da farinha e acrescentou mais uma linha, sem dar git add de novo:

$ echo '2 xícaras de farinha' >> bolo.txt
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt

Changes not staged for commit:
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   bolo.txt

O bolo.txt aparece duas vezes: uma em Mudanças a serem submetidas e outra em Changes not staged for commit ("mudanças não preparadas para o commit"; essa parte da tradução ainda não existe e sai em inglês). Não é defeito: o Git guardou na área de preparo a versão do momento do git add (com 3 ovos), e a pasta já tem uma versão mais nova (com a farinha). Os três diffs mostram isso com clareza:

$ git diff --staged
diff --git a/bolo.txt b/bolo.txt
index 10a5c6d..29056e1 100644
--- a/bolo.txt
+++ b/bolo.txt
@@ -1,3 +1,3 @@
 Bolo de cenoura
 3 cenouras
-4 ovos
+3 ovos

O que vai no commit: só a troca dos ovos. A farinha ainda não está na mala.

$ git diff
diff --git a/bolo.txt b/bolo.txt
index 29056e1..c8726b3 100644
--- a/bolo.txt
+++ b/bolo.txt
@@ -1,3 +1,4 @@
 Bolo de cenoura
 3 cenouras
 3 ovos
+2 xícaras de farinha

O que está na pasta e ainda não foi preparado: só a farinha. Repare que, aqui, a linha de contexto já é 3 ovos: a comparação parte da versão preparada, não do commit.

$ git diff HEAD
diff --git a/bolo.txt b/bolo.txt
index 10a5c6d..c8726b3 100644
--- a/bolo.txt
+++ b/bolo.txt
@@ -1,3 +1,4 @@
 Bolo de cenoura
 3 cenouras
-4 ovos
+3 ovos
+2 xícaras de farinha

Tudo desde o último commit: os ovos e a farinha. HEAD é o nome do último commit do branch atual (veja O que é HEAD); git diff HEAD compara a pasta com ele, passando por cima da área de preparo.

Se a Ana fizer o commit agora…

…o commit leva só os ovos. A farinha fica de fora, ainda como mudança não preparada. Quem esquece disso acha que "o Git perdeu uma mudança". Por isso o hábito: git diff --staged logo antes de git commit. Se faltou algo, mais um git add bolo.txt resolve.

Os três resumos lado a lado

$ git diff --staged --stat
 bolo.txt | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git diff --stat
 bolo.txt | 1 +
 1 file changed, 1 insertion(+)
$ git diff HEAD --stat
 bolo.txt | 3 ++-
 1 file changed, 2 insertions(+), 1 deletion(-)

O --stat (e as outras opções da aula anterior, como --name-only e --word-diff) funciona do mesmo jeito com --staged e com HEAD.

Missão: o bolo.txt está meio preparado (os ovos sim, a farinha não). Compare git diff --staged com git diff, prepare o resto e faça um commit que leve as duas mudanças. No fim, o git status deve dizer que não há nada a submeter.

3. Arquivo novo na área de preparo

Um arquivo que nunca foi commitado não aparece no git diff (aula anterior), mas aparece no --staged assim que recebe git add:

$ echo 'Pudim de leite' > pudim.txt
$ git add pudim.txt
$ git diff --staged
diff --git a/bolo.txt b/bolo.txt
index 10a5c6d..29056e1 100644
--- a/bolo.txt
+++ b/bolo.txt
@@ -1,3 +1,3 @@
 Bolo de cenoura
 3 cenouras
-4 ovos
+3 ovos
diff --git a/pudim.txt b/pudim.txt
new file mode 100644
index 0000000..8499e03
--- /dev/null
+++ b/pudim.txt
@@ -0,0 +1 @@
+Pudim de leite
new file mode 100644
"Arquivo novo, do tipo arquivo comum". Aparece no lugar da informação de tipo do index.
index 0000000..8499e03
O hash "antes" é só zeros: antes, não existia conteúdo.
--- /dev/null
/dev/null é o "arquivo vazio" do Linux, o nada. A versão antiga desse arquivo é... nada.
@@ -0,0 +1 @@
Antes: zero linhas a partir da linha 0. Depois: a partir da linha 1, com 1 linha (quando o número de linhas é 1, o Git omite o ,1).
+Pudim de leite
Todas as linhas de um arquivo novo começam com +.
$ git diff --staged --name-status
M	bolo.txt
A	pudim.txt

Com --name-status: M de modificado (o bolo) e A de added, adicionado (o pudim).

Depois do commit

$ git commit -q -m 'Menos ovos e receita de pudim'
$ git diff --staged
$ git diff
diff --git a/bolo.txt b/bolo.txt
index 29056e1..c8726b3 100644
--- a/bolo.txt
+++ b/bolo.txt
@@ -1,3 +1,4 @@
 Bolo de cenoura
 3 cenouras
 3 ovos
+2 xícaras de farinha
$ git status --short
 M bolo.txt

O commit levou o que estava na área de preparo, e agora ela está igual ao novo HEAD: o --staged fica vazio. A farinha, que nunca foi preparada, continua lá, no git diff e no git status (o M na segunda coluna do --short quer dizer "modificado e não preparado").

4. Outra forma: git status -v

O -v (de verbose, "detalhado") faz o git status mostrar, embaixo do relatório de sempre, o diff do que está preparado, o mesmo do git diff --staged. Veja como fica no momento da seção 1, com só a troca dos ovos preparada:

$ git status -v
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt

diff --git a/bolo.txt b/bolo.txt
index 10a5c6d..29056e1 100644
--- a/bolo.txt
+++ b/bolo.txt
@@ -1,3 +1,3 @@
 Bolo de cenoura
 3 cenouras
-4 ovos
+3 ovos

Com git commit -v acontece algo parecido: o diff aparece no editor onde você escreve a mensagem do commit, como lembrete (essas linhas não entram na mensagem). Veja git commit.

Formas diferentes, e qual usar

ComandoComparaResponde
git diffpasta × área de preparo"O que eu mudei e ainda não preparei?"
git diff --staged ou --cachedárea de preparo × último commit"O que vai entrar no próximo commit?"
git diff HEADpasta × último commit"O que mudou desde o último commit, ao todo?"
git status -vo mesmo do --staged, junto com o status"Status e o que vai no commit, de uma vez"
git showum commit × o commit anterior"O que o último commit mudou?" (aula git show)

O ritual de todo commit fica assim: git status → git diff → git add → git diff --staged → git commit.

Quando dá errado

"O --staged não mostra a mudança que eu acabei de fazer"

Você mudou o arquivo depois do git add (seção 2). A área de preparo guarda a versão do momento do add. Como confirmar: o git status mostra o arquivo nas duas listas. Como resolver: git add arquivo de novo.

Errou o nome da opção 
$ git diff --stage
error: invalid option: --stage
usage: git diff [<options>] [<commit>] [--] [<path>...]
   or: git diff [<options>] --cached [--merge-base] [<commit>] [--] [<path>...]
   or: git diff [<options>] [--merge-base] <commit> [<commit>...] <commit> [--] [<path>...]
   or: git diff [<options>] <commit>...<commit> [--] [<path>...]
   or: git diff [<options>] <blob> <blob>
   or: git diff [<options>] --no-index [--] <path> <path> [<pathspec>...]

common diff options:
  -z            output diff-raw with lines terminated with NUL.
…  (mais umas 25 linhas com opções)

error: invalid option: --stage = "erro: opção inválida". Faltou o d: é --staged. Depois do erro, o Git mostra o modo de usar (usage) do git diff, em inglês. Repare na segunda linha: ali aparece o --cached, o outro nome da opção. O mesmo acontece com --cache (sem o d) e --stagged (com dois g). Como resolver: digite --staged ou --cached, com o d no fim.

git diff HEAD num repositório sem commits 
$ git diff HEAD
fatal: ambiguous argument 'HEAD': unknown revision or path not in the working tree.
Use '--' to separate paths from revisions, like this:
'git <command> [<revision>...] -- [<file>...]'
$ git diff --staged
diff --git a/a.txt b/a.txt
new file mode 100644
index 0000000..c09fc3c
--- /dev/null
+++ b/a.txt
@@ -0,0 +1 @@
+oi

Num repositório recém-criado, que ainda não tem nenhum commit, o HEAD ainda não aponta para commit nenhum. O Git procura algo chamado HEAD, não acha nem um commit nem um arquivo com esse nome e reclama: "argumento ambíguo 'HEAD': versão desconhecida ou caminho fora da árvore de trabalho". Já o git diff --staged funciona: sem commit anterior, ele compara a área de preparo com "nada", e todo arquivo preparado aparece como novo. Como resolver: faça o primeiro commit (aula Seu Primeiro Commit); antes disso, use git diff --staged.

Preparei uma coisa que não devia

O git diff --staged mostrou uma mudança que você não queria no commit (uma senha, um arquivo de teste)? Tire-a da área de preparo com git restore --staged arquivo: as mudanças continuam na pasta, só saem da "mala". É o assunto da aula Tirando da Área de Preparo.

Resumo

  • git diff --staged (ou --cached) mostra o que está na área de preparo, comparado com o último commit: é o que vai entrar no próximo commit.
  • git diff mostra o que ainda não foi preparado; git diff HEAD mostra tudo desde o último commit.
  • O mesmo arquivo pode ter uma parte preparada e outra não: o git add guarda a versão daquele momento. Mudou depois? git add de novo.
  • Arquivo novo no diff: new file mode, --- /dev/null e todas as linhas com +.
  • Ritual antes de cada commit: git diff --staged. E, para tirar algo da mala, git restore --staged.

Git reset --soft, --mixed e --hard

Na aula git reset, você viu que o git reset HEAD~1 desfaz o último commit e deixa as mudanças na pasta. Esse é só um dos três jeitos de dar reset. A diferença entre eles é até onde o reset volta: só o histórico (--soft), o histórico e a área de preparo (--mixed, o padrão), ou tudo, inclusive os arquivos da pasta (--hard). Nesta aula você vê os três lado a lado, com o estado real de cada lugar depois de cada um.

Você vai aprender
  • Os três lugares onde o Git guarda uma versão de cada arquivo: o commit (HEAD), a área de preparo e a pasta.
  • Como espiar cada um deles com git show HEAD:arquivo, git show :arquivo e cat.
  • O que --soft, --mixed e --hard fazem com cada lugar, na tabela clássica e no laboratório.
  • Por que o --hard é o único perigoso, e o que ele apaga para sempre.
  • Qual modo usar em cada situação.

Todas as saídas desta aula vieram do Git real da máquina da Ana (usuária ana, computador notebook), com o sistema em português. A tradução do Git que vem no Ubuntu é parcial: algumas mensagens saem em português, outras em inglês, outras misturadas. Elas estão aqui exatamente como saíram (no Windows, no macOS ou com o sistema em inglês, as frases podem ser diferentes; o sentido é o mesmo).

A ideia: três gavetas

Para cada arquivo, o Git tem três versões guardadas em três lugares diferentes. Pense em três gavetas:

  1. A pasta de trabalho (working tree): os arquivos que você vê e edita. É a gaveta da mesa, a do rascunho.
  2. A área de preparo (staging area, também chamada de índice, index): o que vai entrar no próximo commit. É a caixa "para enviar" (veja A Área de Preparo).
  3. O commit atual (HEAD): a versão guardada no último commit do branch. É o arquivo morto, passado a limpo (veja O que é HEAD).

Quando tudo está commitado e o git status diz working tree clean, as três gavetas têm o mesmo conteúdo. O git add copia da pasta para a área de preparo; o git commit copia da área de preparo para um commit novo. O git reset faz o caminho inverso, e o modo diz quantas gavetas ele arruma:

                 HEAD (o branch)   área de preparo   pasta de trabalho
git reset --soft      volta           não mexe          não mexe
git reset --mixed     volta           volta             não mexe
git reset --hard      volta           volta             volta

Os três sempre fazem a primeira coisa: levar o branch (e, com ele, o HEAD) para o commit indicado. A diferença está no que vem depois.

1. Espiando as três gavetas

Para ver o efeito de cada modo, a Ana precisa olhar as três versões do arquivo. Três comandos fazem isso:

git show HEAD:bolo.txt
Mostra o bolo.txt como ele está no commit HEAD. O formato é commit:caminho; funciona com qualquer commit (git show HEAD~1:bolo.txt, git show 62fc1c8:bolo.txt).
git show :bolo.txt
Com os dois-pontos e nada antes, mostra o bolo.txt como ele está na área de preparo.
cat bolo.txt
O comando do terminal que mostra o arquivo da pasta (veja O Mínimo de Terminal).

O repositório da Ana tem três commits. No último, ela aumentou o tempo do bolo de 40 para 45 minutos. Com tudo commitado, as três gavetas concordam:

$ git log --oneline
2b77e82 (HEAD -> main) Aumenta tempo do bolo para 45 minutos
62fc1c8 Adiciona receita de bolo
fe996fb Primeiro commit
$ git show HEAD:bolo.txt
Bolo de cenoura
Tempo: 45 minutos
$ git show :bolo.txt
Bolo de cenoura
Tempo: 45 minutos
$ cat bolo.txt
Bolo de cenoura
Tempo: 45 minutos

Agora a Ana vai desfazer o último commit três vezes, uma com cada modo, e olhar as gavetas depois de cada uma. Entre uma e outra, ela volta tudo ao normal com o ORIG_HEAD (o apelido de "onde o branch estava antes do reset"; veja git reset).

2. --soft: só o histórico volta

$ git reset --soft HEAD~1
$ git log --oneline
62fc1c8 (HEAD -> main) Adiciona receita de bolo
fe996fb Primeiro commit
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt   « a mudança está PREPARADA

$ git show HEAD:bolo.txt
Bolo de cenoura
Tempo: 40 minutos   « o commit: voltou
$ git show :bolo.txt
Bolo de cenoura
Tempo: 45 minutos   « a área de preparo: não mexeu
$ cat bolo.txt
Bolo de cenoura
Tempo: 45 minutos   « a pasta: não mexeu
--soft
"Suave": só move o branch. A área de preparo e a pasta ficam como estavam.

O commit sumiu do histórico, mas a mudança dele está inteirinha na área de preparo, como se a Ana tivesse acabado de dar git add e ainda não tivesse commitado. Um git commit agora recria o commit (com a mensagem que ela quiser). É o modo para refazer um commit: trocar a mensagem, juntar com outra mudança, ou juntar vários commits em um (git reset --soft HEAD~3 e um git commit só).

De volta ao normal:

$ git reset --soft ORIG_HEAD
$ git log --oneline
2b77e82 (HEAD -> main) Aumenta tempo do bolo para 45 minutos
62fc1c8 Adiciona receita de bolo
fe996fb Primeiro commit

Missão: desfaça o último commit da Ana com o modo que deixa a mudança na área de preparo. Confira com git status (o bolo.txt deve aparecer em "Mudanças a serem submetidas") e com git show HEAD:bolo.txt.

3. --mixed: o histórico e a área de preparo voltam

Este é o modo padrão: git reset HEAD~1, sem opção, é a mesma coisa que git reset --mixed HEAD~1.

$ git reset --mixed HEAD~1
Unstaged changes after reset:
M	bolo.txt
$ git log --oneline
62fc1c8 (HEAD -> main) Adiciona receita de bolo
fe996fb Primeiro commit
$ git status
No ramo main
Changes not staged for commit:
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   bolo.txt   « a mudança NÃO está preparada

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
$ git show HEAD:bolo.txt
Bolo de cenoura
Tempo: 40 minutos   « o commit: voltou
$ git show :bolo.txt
Bolo de cenoura
Tempo: 40 minutos   « a área de preparo: voltou
$ cat bolo.txt
Bolo de cenoura
Tempo: 45 minutos   « a pasta: não mexeu
--mixed
"Misto": move o branch e copia o commit para a área de preparo. A pasta fica como estava.
Unstaged changes after reset: / M bolo.txt
"Mudanças não preparadas depois do reset": o Git lista os arquivos em que a pasta ficou diferente da área de preparo. O M é de modified, "modificado".

A mudança dos 45 minutos continua no arquivo, mas fora da área de preparo, como se a Ana tivesse editado o arquivo e ainda não tivesse dado git add. É o modo para "descommitar" e repensar: escolher de novo o que vai em cada commit, dividir um commit grande em dois, ou simplesmente continuar trabalhando antes de commitar.

De volta ao normal (o git reset ORIG_HEAD, sem opção, é um --mixed: o branch e a área de preparo voltam para o commit dos 45 minutos, e a pasta, que já dizia 45, fica igual):

$ git reset ORIG_HEAD
$ git status
No ramo main
nothing to commit, working tree clean

4. --hard: tudo volta, inclusive a pasta

$ git reset --hard HEAD~1
HEAD is now at 62fc1c8 Adiciona receita de bolo
$ git log --oneline
62fc1c8 (HEAD -> main) Adiciona receita de bolo
fe996fb Primeiro commit
$ git status
No ramo main
nothing to commit, working tree clean   « nenhuma mudança em lugar nenhum
$ git show HEAD:bolo.txt
Bolo de cenoura
Tempo: 40 minutos   « o commit: voltou
$ git show :bolo.txt
Bolo de cenoura
Tempo: 40 minutos   « a área de preparo: voltou
$ cat bolo.txt
Bolo de cenoura
Tempo: 40 minutos   « a pasta: voltou também
--hard
"Duro": move o branch, copia o commit para a área de preparo e para a pasta. As três gavetas ficam iguais ao commit indicado.
HEAD is now at 62fc1c8 Adiciona receita de bolo
"O HEAD agora está em 62fc1c8", com a mensagem desse commit. É o único dos três modos que avisa alguma coisa.

O git status diz que está tudo limpo, e o arquivo da pasta voltou a dizer 40 minutos. A mudança dos 45 minutos não está em gaveta nenhuma. É o modo para jogar fora um trabalho: "aqueles commits foram um experimento que não deu certo; quero o projeto exatamente como estava naquele commit".

Aqui, o commit dos 45 minutos ainda existe dentro do .git, então o ORIG_HEAD o traz de volta, com pasta e tudo:

$ git reset --hard ORIG_HEAD
HEAD is now at 2b77e82 Aumenta tempo do bolo para 45 minutos
$ git log --oneline
2b77e82 (HEAD -> main) Aumenta tempo do bolo para 45 minutos
62fc1c8 Adiciona receita de bolo
fe996fb Primeiro commit
$ cat bolo.txt
Bolo de cenoura
Tempo: 45 minutos
O que o --hard apaga para sempre

Commits desfeitos com --hard têm volta (pelo ORIG_HEAD ou pelo git reflog), porque estão guardados no .git. Já as mudanças que nunca foram commitadas não têm: o --hard sobrescreve os arquivos da pasta, e o Git não guardou cópia nenhuma delas. Olhe:

$ echo 'Cobertura: chocolate' >> bolo.txt
$ git status --short
 M bolo.txt
$ git reset --hard
HEAD is now at 2b77e82 Aumenta tempo do bolo para 45 minutos
$ git status
No ramo main
nothing to commit, working tree clean
$ cat bolo.txt
Bolo de cenoura
Tempo: 45 minutos   « a cobertura sumiu, e não há reflog que a traga

O git reset --hard sem commit (o mesmo que git reset --hard HEAD) não muda o histórico: só joga fora todas as mudanças não commitadas, de todos os arquivos rastreados, sem perguntar. Antes de um --hard, rode git status e pergunte-se se há algo ali que você quer guardar (um git stash resolve). Arquivos não rastreados (novos, nunca adicionados) o --hard não apaga; para eles existe o git clean.

Missão: a Ana testou um bolo de micro-ondas em dois commits, e ficou horrível. Jogue fora os dois commits e as mudanças deles, deixando o projeto exatamente como estava no commit "Adiciona receita de bolo". No fim, cat bolo.txt deve mostrar 40 minutos e o git status, nada a fazer.

Qual modo usar

Você quer…Use
Refazer o último commit (outra mensagem, mais um arquivo) ou juntar vários commits em umgit reset --soft HEAD~N e git commit
"Descommitar" e escolher de novo o que vai em cada commitgit reset HEAD~N (--mixed)
Jogar fora commits e mudanças, voltando o projeto a um commitgit reset --hard <commit> (confira o git status antes!)
Jogar fora só as mudanças não commitadas de todos os arquivosgit reset --hard, ou o mais moderno e seletivo git restore arquivo (veja git restore)
Tirar um arquivo da área de preparogit restore --staged arquivo (ou o antigo git reset arquivo)
Só trocar a mensagem do último commitgit commit --amend (veja --amend): é um reset --soft HEAD~1 + commit num comando só
Desfazer commits que já foram enviados ao GitHubNenhum dos três: use git revert

Quando dá errado

--soft ou --hard com nome de arquivo 
$ git reset --soft bolo.txt
fatal: Cannot do soft reset with paths.
$ git reset --hard bolo.txt
fatal: Cannot do hard reset with paths.

"Não é possível fazer um reset suave/duro com caminhos." Os modos --soft e --hard movem o branch inteiro; eles não funcionam para um arquivo só. Como resolver: para tirar um arquivo da área de preparo, git restore --staged bolo.txt; para descartar as mudanças de um arquivo da pasta, git restore bolo.txt.

--mixed com nome de arquivo 
$ git reset --mixed -- bolo.txt
warning: --mixed with paths is deprecated; use 'git reset -- <paths>' instead.

"Aviso: --mixed com caminhos está obsoleto; use git reset -- <caminhos>." Funcionou (é só um aviso), mas o jeito certo é sem o --mixed: git reset bolo.txt, ou melhor ainda, git restore --staged bolo.txt.

Dei --hard e perdi commits

Se foram commits, eles ainda estão no .git. O git reset --hard ORIG_HEAD desfaz o último reset (como na seção 4). Se você já fez outras coisas depois, procure o commit no git reflog, que registra cada movimento do HEAD:

$ git reflog -5
2b77e82 (HEAD -> main) HEAD@{0}: reset: moving to HEAD
2b77e82 (HEAD -> main) HEAD@{1}: reset: moving to HEAD
2b77e82 (HEAD -> main) HEAD@{2}: reset: moving to ORIG_HEAD
62fc1c8 HEAD@{3}: reset: moving to HEAD~1
2b77e82 (HEAD -> main) HEAD@{4}: reset: moving to ORIG_HEAD

Cada linha é um reset desta aula (moving to … = "indo para …"). Ache o hash de antes do desastre e volte com git reset --hard <hash>. O passo a passo completo está em Recuperando Commits Perdidos.

Dei --hard e perdi mudanças que não tinham sido commitadas

Estas, infelizmente, não voltam pelo Git: ele nunca guardou uma cópia delas (veja o aviso da seção 4). Se o arquivo ainda está aberto no editor de texto, o "desfazer" do editor (Ctrl+Z) pode salvar o dia. Se você tinha dado git add nelas antes, o conteúdo pode estar perdido dentro do .git (o comando avançado git fsck --lost-found procura). A lição: git status antes de todo --hard.

Resumo

  • O Git guarda três versões de cada arquivo: no commit (HEAD), na área de preparo e na pasta. Espie com git show HEAD:arquivo, git show :arquivo e cat arquivo.
  • --soft só move o branch: a mudança fica preparada. Bom para refazer ou juntar commits.
  • --mixed (o padrão) move o branch e arruma a área de preparo: a mudança fica na pasta, não preparada.
  • --hard arruma as três gavetas: a mudança some. Commits desfeitos voltam com ORIG_HEAD ou git reflog; mudanças nunca commitadas, não.
  • Nenhum dos três é para commits já enviados ao GitHub: para esses, git revert.

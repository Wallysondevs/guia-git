Git O GitHub Flow

Você já sabe criar branches, enviar com git push e abrir um pull request. Falta juntar tudo numa rotina: em que ordem fazer as coisas, todo dia, para que duas ou dez pessoas mexam no mesmo projeto sem pisar no pé uma da outra. O jeito mais simples e mais usado no GitHub tem nome: GitHub Flow ("o fluxo do GitHub"). Ele cabe em uma frase: a main está sempre funcionando, e toda mudança nasce num branch e entra por um pull request.

Você vai aprender
  • A regra de ouro do GitHub Flow: a main está sempre pronta para ir ao ar.
  • Os seis passos: criar o branch, fazer commits, enviar, abrir o pull request, revisar e mesclar, apagar o branch.
  • Os comandos de cada passo, com as saídas reais do Git, e o que acontece no site do GitHub.
  • Como deixar o seu computador em dia depois do merge (git pull, git branch -d, git fetch --prune).
  • Os tropeços mais comuns: commitar direto na main, branch que vive demais, push rejeitado.

Os comandos desta aula rodaram no Git do Ubuntu da Ana (usuária ana, computador notebook), com as mensagens em português. O GitHub da aula é um "GitHub de mentira" do laboratório: o Git conversa com ele do mesmo jeito que conversaria com o de verdade. O que acontece no site do GitHub (botões, telas) está marcado como ilustrativo e segue a documentação oficial (docs.github.com/pt).

A ideia: a cozinha do restaurante

Num restaurante, o balcão é onde ficam os pratos prontos para ir à mesa. Ninguém monta um prato novo em cima do balcão: cada cozinheiro prepara o seu prato na própria bancada. Quando termina, o chefe prova; se estiver bom, o prato vai para o balcão. Se não estiver, volta para a bancada para um ajuste.

Na cozinhaNo GitHub Flow
O balcão, só com pratos prontosO branch main, sempre funcionando
A bancada de cada cozinheiroUm branch para cada tarefa (receita-pudim, corrige-titulo)
"Chefe, prova aqui?"O pull request (o pedido para juntar o branch na main)
O chefe prova e comentaA revisão de código
O prato vai para o balcãoO merge do pull request na main
A bancada é limpa para o próximo pratoO branch é apagado

Repare no que não existe aqui: não há um balcão "de quase pronto", nem uma bancada que dura meses. O GitHub Flow tem um branch permanente (a main) e muitos branches curtos, que vivem horas ou poucos dias. Fluxos com mais branches fixos (como o Git Flow) estão na próxima aula, Git Flow e Outros Fluxos.

main:     A───B───────────M───────N        « só entra coisa revisada (M e N são merges)
               \         /       /
receita-pudim:  C───D───┘       /          « o branch vive o tempo da tarefa
                     \         /
corrige-titulo:       E───────┘

Os seis passos, de uma vez

  1. Crie um branch a partir da main atualizada, com um nome curto que diga a tarefa.
  2. Faça commits pequenos nesse branch.
  3. Envie o branch para o GitHub (git push), quantas vezes quiser.
  4. Abra um pull request para pedir revisão.
  5. Revise, ajuste e mescle: os ajustes são novos commits no mesmo branch; aprovado, o pull request é mesclado na main.
  6. Apague o branch e deixe o seu computador em dia.

A partir daqui, a Ana vai fazer um ciclo inteiro: ela vai acrescentar a receita de pudim no site de receitas que mantém com o Bruno.

Passo 1: crie um branch para a tarefa

$ git switch -c receita-pudim
Switched to a new branch 'receita-pudim'           « "trocou para um branch novo"
$ git status
No ramo receita-pudim
nothing to commit, working tree clean              « "nada a commitar, pasta limpa"

O branch novo nasceu exatamente onde a main estava (no commit c451956), por isso ainda não há nada de diferente nele.

Troca de branch (veja git switch).
-c
De create, "criar": cria o branch e já entra nele.
receita-pudim
O nome do branch. No GitHub Flow, o nome conta a tarefa: quem olhar a lista de branches no GitHub sabe o que está sendo feito sem abrir nada.
Nomes de branch que ajudam

Curtos, em minúsculas, com hífen no lugar de espaço: receita-pudim, corrige-link-contato, atualiza-readme. Muitas equipes põem um prefixo com o tipo da tarefa: feature/receita-pudim, fix/link-contato (a barra é permitida em nomes de branch). Evite nomes como teste, ana ou branch2: daqui a uma semana nem você vai saber o que tinha neles.

Passo 2: faça commits pequenos

A Ana cria a receita e faz o primeiro commit. Depois, lembra de pôr o link no índice e faz um segundo commit. Cada commit é uma mudança completa e pequena, com uma mensagem clara (veja Boas Mensagens de Commit):

$ printf '# Pudim de leite\n\n- 1 lata de leite condensado\n- 2 medidas de leite\n- 3 ovos\n' > pudim.md
$ git add pudim.md
$ git commit -m "Adiciona receita de pudim"
[receita-pudim b093628] Adiciona receita de pudim          « o commit foi para o branch receita-pudim
 1 file changed, 5 insertions(+)

$ printf -- '- [Pudim de leite](pudim.md)\n' >> index.md
$ git commit -am "Adiciona pudim ao índice"
[receita-pudim 8ef4f17] Adiciona pudim ao índice

$ git log --oneline --graph --all --decorate
* 8ef4f17 (HEAD -> receita-pudim) Adiciona pudim ao índice
* b093628 Adiciona receita de pudim
* c451956 (origin/main, origin/HEAD, main) Adiciona receita de brigadeiro

O printf só cria o arquivo pelo terminal; você pode usar o seu editor de texto. O -am do segundo commit junta o git add dos arquivos já rastreados com o -m (veja git commit). No desenho do histórico, o branch receita-pudim (onde está o HEAD) está 2 commits à frente da main, que ficou parada em c451956, junto com a origin/main. Nada disso chegou ao GitHub ainda: está só no computador da Ana.

Enviar cedo é uma boa prática: o trabalho fica guardado fora do seu computador, e quem quiser pode dar uma olhada. Enquanto o pull request não for mesclado, você pode continuar fazendo commits e git push no mesmo branch quantas vezes quiser.

Passo 4: abra o pull request (no site, ilustrativo)

O pull request é feito no site do GitHub (ou com o GitHub CLI). O passo a passo completo está na aula Pull Request; em resumo:

  1. Abra o endereço que o git push mostrou (…/pull/new/receita-pudim). Ou, na página do repositório, use o aviso sobre o branch que acabou de receber push, com o botão Compare & pull request; ou ainda a aba Pull requests → New pull request, escolhendo base: main ← compare: receita-pudim.
  2. Escreva um título e uma descrição: o que mudou e por quê. Se o pull request resolve uma issue, escreva Closes #12 (ou Fixes #12) na descrição: ao mesclar, a issue é fechada sozinha.
  3. Peça a revisão do Bruno (campo Reviewers) e clique em Create pull request. Se ainda não está pronto para revisão, dá para criar como rascunho (draft).

O site do GitHub é em inglês; a documentação em português traduz os nomes (por exemplo, "solicitação de pull" para pull request).

Passo 5: revise, ajuste e mescle

O Bruno leu o pull request e comentou: "Faltou o tempo de forno." No GitHub Flow, a resposta a um comentário é um novo commit no mesmo branch. Não é preciso abrir outro pull request: ele se atualiza sozinho com o push.

$ printf -- '- Forno a 180 °C por 50 minutos, em banho-maria\n' >> pudim.md
$ git commit -am "Adiciona tempo de forno do pudim"

Desta vez bastou git push, sem -u nem nomes: o branch já estava ligado ao do GitHub desde o Passo 3.

Aprovado, o pull request é mesclado na main pelo botão Merge pull request e depois Confirm merge (ilustrativo; a documentação em português chama de "Mesclar pull request" e "Confirmar mesclagem"). Por baixo, o GitHub faz um merge que sempre cria um commit de merge (como um git merge --no-ff), com a mensagem Merge pull request #1 from ana-souza/receita-pudim. Há também as opções Squash and merge (junta tudo num commit só, veja squash) e Rebase and merge; o dono do repositório escolhe quais ficam disponíveis.

No laboratório, o Bruno fez o papel do botão: mesclou o branch com --no-ff e essa mensagem e enviou a main. Depois do merge, o histórico do GitHub ficou assim:

O merge é o momento em que o prato chega ao balcão. Por isso o pull request é revisado antes, e muitas equipes rodam testes automáticos nele (veja GitHub Actions). Em muitas empresas, o que entra na main vai ao ar logo depois, às vezes automaticamente.

git switch main
Volta para a main. O up to date ainda é o "em dia" da última vez que o Git conversou com o GitHub.
git pull
Traz o commit de merge a8d3cfd: a main da Ana agora tem o pudim. Repare no create mode 100644 pudim.md: na main, o arquivo é novo.
git branch -d receita-pudim
Apaga o branch local. O -d só apaga se o trabalho já estiver mesclado; como o merge chegou com o pull, o Git apagou sem reclamar: Deleted branch receita-pudim (was 0def83b) ("branch apagado; ele apontava para 0def83b").

O git branch -a (de all, "todos") mostra também os branches remotos que o Git da Ana conhece. O origin/receita-pudim ainda aparece porque o Git não fica sabendo sozinho que o branch foi apagado no GitHub.
git fetch --prune
"Buscar e podar": busca as novidades e apaga as cópias de branches que não existem mais no GitHub. A linha - [deleted] (none) -> origin/receita-pudim diz que a cópia foi apagada.

Pronto: um ciclo completo. Para a próxima tarefa, a Ana começa de novo do Passo 0.

Missão: você está no repositório receitas, na main. Siga o GitHub Flow até o push: crie o branch receita-bolo, crie o arquivo bolo.md com qualquer texto, faça o commit e envie o branch para o origin com git push -u origin receita-bolo. A main não pode ganhar commits.

Quando dá errado

Fiz o commit direto na main

A Ana esqueceu o Passo 1 e commitou a receita de mousse direto na main. Ainda bem que ela olhou o git status antes de enviar:

$ git commit -m "Adiciona receita de mousse"
[main 3f3c516] Adiciona receita de mousse
 1 file changed, 1 insertion(+)
 create mode 100644 mousse.md
$ git status
No ramo main
Seu ramo está à frente de 'origin/main' por 1 submissão.
  (use "git push" to publish your local commits)

nothing to commit, working tree clean

O que aconteceu: o [main 3f3c516] mostra que o commit foi para a main, e o git status diz "o seu ramo está à frente da origin/main por 1 submissão" (submissão é como a tradução do Git chama o commit). Como resolver, se ainda não enviou: crie o branch onde você está (ele leva o commit junto), devolva a main ao que está no GitHub e vá para o branch:

$ git branch receita-mousse
$ git reset --hard origin/main
HEAD is now at a8d3cfd Merge pull request #1 from ana-souza/receita-pudim
$ git switch receita-mousse
Switched to branch 'receita-mousse'
$ git log --oneline --graph --all --decorate -3
* 3f3c516 (HEAD -> receita-mousse) Adiciona receita de mousse
*   a8d3cfd (origin/main, origin/HEAD, main) Merge pull request #1 from ana-souza/receita-pudim
|\

O commit 3f3c516 agora está só no branch receita-mousse, e a main voltou a ser igual à origin/main. O git reset --hard joga fora o que não foi commitado, por isso use-o só com o git status limpo (veja reset --soft, --mixed e --hard). Se você já enviou a main, não reescreva: use git revert e combine com a equipe. Para isso nunca acontecer, o GitHub permite proteger a main (regras de proteção de branch) e exigir pull request.

git push sem o -u no branch novo 
$ git push
fatal: The current branch receita-mousse has no upstream branch.
To push the current branch and set the remote as upstream, use

    git push --set-upstream origin receita-mousse

To have this happen automatically for branches without a tracking
upstream, see 'push.autoSetupRemote' in 'git help config'.

"O branch atual receita-mousse não tem branch de rastreamento (upstream). Para enviar o branch atual e ligar o remoto a ele, use git push --set-upstream origin receita-mousse." O --set-upstream é o nome comprido do -u. Como resolver: rode o comando que ele sugere, ou git push -u origin receita-mousse. A última frase sugere a configuração push.autoSetupRemote, que faz isso sozinha no primeiro push de cada branch (veja Branch de Rastreamento).

git branch -d não quer apagar 
$ git branch -d receita-quindim
error: the branch 'receita-quindim' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D receita-quindim'
hint: Disable this message with "git config set advice.forceDeleteBranch false"

"O branch não foi totalmente mesclado." O que aconteceu: o branch tem commits que não estão na main do seu computador. Duas causas comuns: você esqueceu o git pull depois do merge no GitHub, ou o pull request foi mesclado com Squash and merge (o GitHub criou um commit novo na main, e os commits do branch, do ponto de vista do Git, nunca entraram). Como resolver: faça o git pull na main e tente de novo. Se o pull request foi mesmo mesclado (confira no GitHub), use o -D que a dica sugere. Se ele não foi mesclado, pare: o -D apagaria trabalho que só existe ali.

O branch ficou semanas aberto e agora tem conflito

Enquanto o branch esperava, a main andou, e o pull request passou a mostrar que há conflitos. Como resolver: traga a main para dentro do branch (git switch main, git pull, git switch receita-pudim, git merge main), resolva os conflitos (veja Resolvendo Conflitos) e dê git push. Para evitar: branches curtos, pull requests pequenos e revisão rápida. É a ideia central do GitHub Flow.

Resumo

  • No GitHub Flow, a main está sempre funcionando; toda mudança nasce num branch curto e entra por um pull request.
  • O ciclo: git switch main + git pull → git switch -c tarefa → commits → git push -u origin tarefa → pull request → revisão (ajustes são novos commits no mesmo branch) → merge → apagar o branch.
  • Depois do merge: git switch main, git pull, git branch -d tarefa e, de vez em quando, git fetch --prune.
  • Um branch por tarefa, e branches que vivem pouco: quanto mais tempo longe da main, maiores os conflitos.
  • Nunca commite direto na main compartilhada; se acontecer, crie o branch a partir dali e volte a main com cuidado (veja Quando dá errado).

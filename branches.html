Git Branches

Até aqui, todos os seus commits ficaram numa fila só, um atrás do outro. Mas e se a Ana quiser testar uma ideia nova no site de receitas (uma seção de sobremesas, por exemplo) sem bagunçar a versão que já funciona? Para isso existem os branches (em inglês, "galhos" ou "ramos"). Um branch é uma linha de trabalho separada: você faz commits nele à vontade e a linha principal fica intacta. Esta aula explica a ideia e o que o Git faz por baixo; as próximas mostram cada comando em detalhe.

Você vai aprender
  • O que é um branch: uma etiqueta com nome, que aponta para um commit.
  • O que é o main, e por que ele é só um branch como outro qualquer.
  • Como o HEAD diz em qual branch você está, e como cada commit novo empurra a etiqueta para frente.
  • Por que criar um branch é instantâneo (o Git só grava um arquivinho com um hash).
  • Como ler o desenho dos ramos no git log --oneline --graph --all.

Todas as saídas desta aula vieram do Git real do Ubuntu 26.04, na máquina da Ana (usuária ana, computador notebook), com o sistema em português. Com o sistema em inglês, as mensagens saem em inglês (por exemplo, No ramo main vira On branch main).

A ideia: o caderno de receitas e o caderno de rascunho

A Ana tem um caderno de receitas passado a limpo, que a família toda consulta. Ela quer inventar uma seção de sobremesas, mas ainda não sabe se vai dar certo. Ela tem duas opções:

  1. Escrever direto no caderno bom. Se a ideia não prestar, vai ter de rasurar páginas, e enquanto isso o caderno fica pela metade.
  2. Tirar uma cópia do caderno e rabiscar na cópia. Se der certo, ela passa as páginas novas para o caderno bom. Se não der, joga a cópia fora. O caderno bom nunca ficou bagunçado.

Um branch é a opção 2, com uma vantagem enorme: o Git não copia nada. Ele só põe uma etiqueta nova na última página, dizendo "a partir daqui, este é o caderno de sobremesas". Por isso criar um branch leva uma fração de segundo, mesmo num projeto gigante.

Palavras desta aula

branch = "ramo" ou "galho" (no português do Git, as mensagens dizem ramo: No ramo main). main = "principal", o nome do branch que o git init cria. HEAD = "cabeça", o marcador de "onde você está agora" (veja O que é HEAD).

1. O repositório da Ana, antes de qualquer branch

A Ana criou a pasta receitas e fez três commits, um por arquivo (você aprendeu a fazer isso em Seu Primeiro Commit):

$ git log --oneline --graph --all
* 0244251 (HEAD -> main) Adiciona receita de pão de queijo   « o mais novo, em cima
* 7225e04 Adiciona receita de bolo
* 700bbd5 Cria o README                                          « o primeiro commit
$ git branch
* main                                                           « o único branch, e o atual (*)
$ git status
No ramo main
nothing to commit, working tree clean

O pedaço (HEAD -> main) do git log é a parte importante desta aula. Ele diz: "o branch main aponta para este commit, e o HEAD aponta para o main". (O nothing to commit, working tree clean é "nada a commitar, pasta limpa": algumas mensagens do Git continuam em inglês mesmo com o sistema em português, porque a tradução do Git para o português ainda não cobre todas.)

Mesmo sem ter criado nenhum branch, ela já está num: o main. O git init cria esse branch sozinho, e todo commit que você fez até hoje entrou nele. O desenho do histórico, com o commit mais antigo à esquerda:

A---B---C   ← main ← HEAD

A = 700bbd5  Cria o README
B = 7225e04  Adiciona receita de bolo
C = 0244251  Adiciona receita de pão de queijo

Cada letra é um commit, e as linhas --- ligam um commit ao anterior (o "pai" dele). A etiqueta main está grudada no commit mais novo, e o HEAD aponta para o main: quer dizer "você está no branch main".

Por dentro: um branch é um arquivo com um hash

Dá para ver com os próprios olhos o que é um branch. Ele mora dentro da pasta escondida .git:

$ cat .git/HEAD
ref: refs/heads/main
$ cat .git/refs/heads/main
0244251e6b6cd5cbf4b8c82f8ba2557b6cf3878b
cat .git/HEAD → ref: refs/heads/main
O arquivo HEAD não guarda um commit, guarda o nome de um branch: "estou em refs/heads/main". É assim que o Git sabe em qual ramo você está.
cat .git/refs/heads/main
O branch main é um arquivinho de texto com uma linha só: o hash completo do último commit do ramo (os 7 primeiros caracteres são os que o git log --oneline mostra; veja O Hash do Commit).

É só isso. Um branch não é uma pasta, nem uma cópia dos arquivos: é um nome que aponta para um commit. Os commits em si continuam guardados uma vez só, e cada um sabe quem é o seu pai. Seguindo os pais a partir da etiqueta, o Git reconstrói a história do ramo inteiro.

Só olhe, não mexa

Abrimos os arquivos da pasta .git com cat para você ver como é simples. Nunca edite esses arquivos à mão: use sempre os comandos do Git, que conferem tudo antes de mudar.

2. Criando um branch: uma etiqueta nova no mesmo lugar

A Ana cria o branch sobremesas com git branch sobremesas (o comando tem aula própria: git branch):

$ git branch sobremesas
$ git branch
* main                « o * continua aqui
  sobremesas          « o branch novo
$ git log --oneline --graph --all
* 0244251 (HEAD -> main, sobremesas) Adiciona receita de pão de queijo
* 7225e04 Adiciona receita de bolo
* 700bbd5 Cria o README
$ cat .git/refs/heads/sobremesas
0244251e6b6cd5cbf4b8c82f8ba2557b6cf3878b
$ ls .git/refs/heads/
main  sobremesas

Repare em três coisas:

  • O git branch sobremesas não mostrou nada: no Git, silêncio quer dizer "deu certo".
  • Na lista, o * continua no main. Criar um branch não muda você para ele.
  • No git log, o commit 0244251 agora tem duas etiquetas: (HEAD -> main, sobremesas).
  • O arquivo .git/refs/heads/sobremesas tem o mesmo hash do main: as duas etiquetas apontam para o mesmo commit. Criar o branch custou um arquivinho de 41 bytes (40 caracteres do hash e uma quebra de linha), nada de cópia.

Antes e depois:

Antes:   A---B---C   ← main ← HEAD

Depois:  A---B---C   ← main ← HEAD
                     ← sobremesas

3. Mudando de branch: o HEAD troca de etiqueta

Para trabalhar no ramo novo, a Ana muda para ele com git switch (aula: Trocando de Branch):

$ git switch sobremesas
Switched to branch 'sobremesas'          « "mudado para o ramo 'sobremesas'"
$ cat .git/HEAD
ref: refs/heads/sobremesas               « o HEAD agora aponta para o branch novo
$ git status
No ramo sobremesas
nothing to commit, working tree clean

A frase Switched to branch 'sobremesas' ("mudado para o ramo 'sobremesas'"; essa mensagem ainda não tem tradução e sai em inglês) confirma a troca. O arquivo HEAD agora diz refs/heads/sobremesas, e o git status também: No ramo sobremesas. Nenhum arquivo da pasta mudou, porque os dois ramos apontam para o mesmo commit. Só o HEAD trocou de etiqueta:

Antes:   A---B---C   ← main ← HEAD
                     ← sobremesas

Depois:  A---B---C   ← main
                     ← sobremesas ← HEAD

4. O commit empurra a etiqueta do branch atual

Agora a Ana faz um commit no ramo sobremesas:

$ echo 'Pudim de leite' > pudim.txt
$ git add pudim.txt
$ git commit -m 'Adiciona receita de pudim'
[sobremesas d6f2336] Adiciona receita de pudim     « entrou no ramo sobremesas
 1 file changed, 1 insertion(+)
 create mode 100644 pudim.txt
$ git log --oneline --graph --all
* d6f2336 (HEAD -> sobremesas) Adiciona receita de pudim
* 0244251 (main) Adiciona receita de pão de queijo   « o main ficou aqui
* 7225e04 Adiciona receita de bolo
* 700bbd5 Cria o README

A primeira linha da resposta do git commit começa com [sobremesas …]: o Git avisa em qual ramo o commit entrou. E no desenho do git log, o sobremesas andou para o commit novo, enquanto o main ficou para trás:

Antes:   A---B---C   ← main
                     ← sobremesas ← HEAD

Depois:  A---B---C   ← main
                  \
                   D   ← sobremesas ← HEAD     (D = d6f2336, o pudim)

(O git log --graph ainda desenha tudo numa linha reta, porque por enquanto a história é uma fila só: o D vem depois do C. A diferença é só onde as etiquetas estão.)

Esta é a regra de ouro dos branches: um commit novo sempre entra no branch em que o HEAD está, e só a etiqueta desse branch anda. As outras etiquetas ficam paradas onde estavam.

5. Voltando para o main: os arquivos mudam

A Ana volta para o main e lista a pasta:

$ git switch main
Switched to branch 'main'
$ ls
README.md  bolo.txt  pao.txt                 « cadê o pudim.txt?
$ git log --oneline --graph --all
* d6f2336 (sobremesas) Adiciona receita de pudim
* 0244251 (HEAD -> main) Adiciona receita de pão de queijo
* 7225e04 Adiciona receita de bolo
* 700bbd5 Cria o README
$ git log --oneline
0244251 (HEAD -> main) Adiciona receita de pão de queijo
7225e04 Adiciona receita de bolo
700bbd5 Cria o README
$ git log --oneline sobremesas
d6f2336 (sobremesas) Adiciona receita de pudim
0244251 (HEAD -> main) Adiciona receita de pão de queijo
7225e04 Adiciona receita de bolo
700bbd5 Cria o README

A---B---C   ← main ← HEAD
         \
          D   ← sobremesas

O pudim.txt sumiu da pasta! Calma: ele não foi apagado. Ao trocar de branch, o Git deixa a pasta exatamente como ela está no commit para onde o ramo novo aponta, e no commit C o pudim ainda não existia. Quando a Ana voltar para sobremesas, o arquivo reaparece.

Note também que o git log --oneline sem --all mostra só a história do ramo atual. Para ver a de outro ramo, dê o nome dele no fim.

6. Os ramos se separam

Ainda no main, a Ana adiciona a receita de feijoada:

$ echo 'Feijoada' > feijoada.txt
$ git add feijoada.txt && git commit -q -m 'Adiciona receita de feijoada'
$ git log --oneline --graph --all
* 1077f55 (HEAD -> main) Adiciona receita de feijoada
| * d6f2336 (sobremesas) Adiciona receita de pudim
|/
* 0244251 Adiciona receita de pão de queijo           « onde os ramos se separam
* 7225e04 Adiciona receita de bolo
* 700bbd5 Cria o README

Agora o desenho tem dois galhos de verdade: cada ramo tem um commit que o outro não tem. No git log --graph, cada * é um commit, e as barras | e / são as linhas da história. Leia de baixo para cima: A, B e C são comuns; a partir de C, a linha da esquerda é o main (com a feijoada) e a da direita é o sobremesas (com o pudim). O |/ é o ponto onde o galho da direita "brota" do tronco.

Antes:   A---B---C   ← main ← HEAD
                  \
                   D   ← sobremesas

Depois:  A---B---C---E   ← main ← HEAD     (E = 1077f55, a feijoada)
                  \
                   D   ← sobremesas

O commit C, onde os ramos se separaram, é o ancestral comum dos dois. Para juntar o trabalho dos dois ramos de novo, existe o git merge, assunto do próximo grupo de aulas.

7. Para que servem os branches no dia a dia

SituaçãoComo os branches ajudam
Testar uma ideia que talvez não dê certoFaça num branch. Se não prestar, apague o branch (Renomeando e Apagando Branches); o main nem ficou sabendo.
Uma funcionalidade nova que vai levar diasTrabalhe num branch próprio; o main continua sempre funcionando.
Um defeito urgente no meio de outra tarefaVolte para o main, crie um branch para o conserto, resolva e volte para a tarefa: nada se mistura.
Trabalhar em dupla com o BrunoCada um no seu branch; depois os dois juntam o trabalho com merge ou pull request (Pull Request).
O main não tem nada de especial

Para o Git, main é só o nome do primeiro branch, igual a qualquer outro. É uma combinação entre as pessoas que ele guarde a versão boa, a que "vai para o ar". Em projetos antigos, o primeiro branch se chama master; o lab da Ana usa init.defaultBranch=main (veja Criando um Repositório).

Quando dá errado

Criei o branch, mas o commit foi parar no main

O erro de iniciante mais comum com branches: criar com git branch e esquecer de mudar para ele.

$ git branch sobremesas
$ echo 'Pudim de leite' > pudim.txt
$ git add pudim.txt
$ git commit -m 'Adiciona receita de pudim'
[main d6f2336] Adiciona receita de pudim         « main, e não sobremesas!
 1 file changed, 1 insertion(+)
 create mode 100644 pudim.txt
$ git log --oneline --graph --all
* d6f2336 (HEAD -> main) Adiciona receita de pudim
* 0244251 (sobremesas) Adiciona receita de pão de queijo
* 7225e04 Adiciona receita de bolo
* 700bbd5 Cria o README

O que aconteceu: o git branch sobremesas criou a etiqueta, mas o HEAD continuou no main, e o commit entrou nele. Como perceber: o começo da resposta do commit ([main …]) e a primeira linha do git status (No ramo main) dizem onde você está. Como resolver (o commit não se perde): leve a etiqueta sobremesas até o commit novo, mude para ela e devolva o main um commit para trás. O -f (de force, "forçar") do git branch move uma etiqueta que já existe; ele não funciona no branch atual, por isso a troca vem no meio:

$ git branch -f sobremesas
$ git switch sobremesas
Switched to branch 'sobremesas'
$ git branch -f main main~1
$ git log --oneline --graph --all
* d6f2336 (HEAD -> sobremesas) Adiciona receita de pudim
* 0244251 (main) Adiciona receita de pão de queijo
* 7225e04 Adiciona receita de bolo
* 700bbd5 Cria o README

(main~1 = "um commit antes do main".) Para não cair nisso, crie e mude de uma vez com git switch -c sobremesas (aula git switch).

"Troquei de branch e meu arquivo sumiu!"

Como na seção 5: o pudim.txt não aparece no ls depois do git switch main. O que aconteceu: o arquivo só existe nos commits do outro ramo. Como confirmar: git log --oneline --graph --all mostra o commit do pudim no sobremesas, e git log --oneline sobremesas também. Como resolver: nada a resolver; git switch sobremesas traz o arquivo de volta. Só perde de verdade o que nunca foi commitado e você mesmo descartou; o Git se recusa a trocar de branch quando isso poderia apagar uma mudança sua (veja git switch).

Resumo

  • Um branch (ramo) é uma linha de trabalho separada. Por dentro, é só um nome que aponta para um commit: o arquivo .git/refs/heads/NOME, com um hash.
  • O git init cria o branch main; você já trabalhava nele sem saber.
  • O HEAD aponta para o branch atual. git branch NOME cria uma etiqueta nova, mas o HEAD continua onde estava; git switch NOME muda o HEAD.
  • Cada commit novo entra no branch do HEAD, e só a etiqueta dele anda.
  • Trocar de branch troca os arquivos da pasta para a versão daquele ramo; nada é perdido.
  • Quando os dois ramos ganham commits diferentes, a história se divide a partir do ancestral comum. O git log --oneline --graph --all desenha isso.

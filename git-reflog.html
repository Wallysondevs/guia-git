Git reflog: O Diário do HEAD

A Ana rodou um git reset --hard com o número errado e o commit do brigadeiro sumiu do git log. O arquivo também sumiu da pasta. Bate o desespero: "perdi tudo?". Quase nunca. O Git guarda um diário de todos os lugares por onde o HEAD passou: cada commit, cada troca de branch, cada reset. Esse diário é o git reflog, e com ele dá para achar e trazer de volta commits que pareciam perdidos.

Você vai aprender
  • O que o git reflog guarda e como ler cada linha (HEAD@{0}, HEAD@{1}…).
  • A desfazer um git reset --hard errado com git reset --hard HEAD@{1}.
  • A recuperar um branch apagado com git branch -D.
  • O reflog de um branch (git reflog show main) e o git log -g.
  • Os limites do reflog: é só seu (não vai para o GitHub) e não guarda para sempre.

As saídas desta aula saíram do Git 2.53 do Ubuntu 26.04, num terminal de verdade da máquina da Ana. Algumas mensagens, como HEAD is now at, aparecem em inglês: o Git do Ubuntu é só parcialmente traduzido.

A ideia: o histórico do navegador

Você fechou sem querer a aba de uma página importante. Ela sumiu da tela, mas não do histórico do navegador: lá está a lista de todas as páginas que você visitou, da mais recente para a mais antiga. É só achar e abrir de novo.

O git log é como as abas abertas: mostra o caminho atual do branch. O git reflog é o histórico do navegador: mostra tudo por onde você passou, inclusive os commits que já não estão em nenhum branch. O nome vem de reference log, "diário das referências" (o HEAD e os branches são referências: etiquetas que apontam para commits).

1. O primeiro git reflog

O repositório de receitas tem 3 commits:

$ git log --oneline
abceaaf (HEAD -> main) Adiciona a receita de brigadeiro
c34349b Adiciona a receita de bolo
700bbd5 Cria o README
$ git reflog
abceaaf (HEAD -> main) HEAD@{0}: commit: Adiciona a receita de brigadeiro
c34349b HEAD@{1}: commit: Adiciona a receita de bolo
700bbd5 HEAD@{2}: commit (initial): Cria o README

Por enquanto, o diário conta a mesma história do git log. Pegue a primeira linha:

abceaaf
O commit em que o HEAD ficou depois desse passo.
(HEAD -> main)
As etiquetas de sempre: você está no main, que aponta para esse commit.
HEAD@{0}
O "apelido" desse momento do diário: HEAD@{0} é agora, HEAD@{1} é "onde o HEAD estava 1 passo atrás", HEAD@{2}, 2 passos atrás, e assim por diante. Esses nomes funcionam em qualquer comando do Git, no lugar de um hash.
commit: Adiciona a receita de brigadeiro
O que aconteceu nesse passo: um commit, com a mensagem dele. No primeiro de todos, commit (initial), o commit inicial.

A diferença aparece quando o HEAD anda para trás ou pula de galho. Aí o git log esquece, e o reflog lembra.

2. O resgate depois de um reset --hard

A Ana queria desfazer uma mudança que ainda não tinha commit, mas digitou git reset --hard HEAD~1: isso volta o branch 1 commit e apaga as mudanças da pasta (veja reset --soft, --mixed e --hard).

$ git reset --hard HEAD~1
HEAD is now at c34349b Adiciona a receita de bolo
$ git log --oneline
c34349b (HEAD -> main) Adiciona a receita de bolo
700bbd5 Cria o README
$ ls
README.md  bolo.txt

"HEAD is now at c34349b": o HEAD agora está no commit do bolo. O commit do brigadeiro não aparece mais no git log, e o brigadeiro.txt sumiu da pasta. Mas o commit não foi apagado: ele só ficou sem nenhum branch apontando para ele. O diário mostra onde ele está:

$ git reflog
c34349b (HEAD -> main) HEAD@{0}: reset: moving to HEAD~1
abceaaf HEAD@{1}: commit: Adiciona a receita de brigadeiro     «
c34349b (HEAD -> main) HEAD@{2}: commit: Adiciona a receita de bolo
700bbd5 HEAD@{3}: commit (initial): Cria o README
HEAD@{0}: reset: moving to HEAD~1
O passo mais recente: o reset que "moveu para HEAD~1". Os números de todo mundo andaram uma casa: o que era HEAD@{0} virou HEAD@{1}.
abceaaf HEAD@{1}: commit: …brigadeiro
Onde o HEAD estava antes do reset: o commit do brigadeiro, com o hash abceaaf. É ele que a Ana quer de volta.

Para voltar, basta fazer outro reset, agora para esse ponto do diário. Dá para usar o apelido HEAD@{1} ou o hash abceaaf:

$ git reset --hard HEAD@{1}
HEAD is now at abceaaf Adiciona a receita de brigadeiro
$ git log --oneline
abceaaf (HEAD -> main) Adiciona a receita de brigadeiro
c34349b Adiciona a receita de bolo
700bbd5 Cria o README
$ ls
README.md  bolo.txt  brigadeiro.txt

O commit voltou para o main, e o brigadeiro.txt voltou para a pasta, do jeito que estava no commit.

O que o reflog não salva

O reflog guarda commits. Mudanças que você nunca commitou (arquivos editados e não salvos num commit) não entram no diário: se um git reset --hard ou um git restore as apagou, o reflog não traz de volta. Mais um motivo para fazer commits pequenos e frequentes.

Missão: a Ana acabou de rodar git reset --hard HEAD~1 por engano e o commit do brigadeiro sumiu do git log. Olhe o diário com git reflog e traga o commit de volta para o main.

3. O resgate de um branch apagado

A Ana criou o branch doces, fez um commit com o beijinho, voltou para o main… e apagou o branch com -D (o "apagar mesmo que não esteja juntado"; veja Apagando Branches), achando que era outro.

$ git switch -c doces
Switched to a new branch 'doces'
$ printf 'Beijinho\n' > beijinho.txt
$ git add beijinho.txt
$ git commit -q -m 'Adiciona a receita de beijinho'
$ git switch main
Switched to branch 'main'
$ git branch -D doces
Deleted branch doces (was e26a98a).
$ git log --oneline --all
abceaaf (HEAD -> main) Adiciona a receita de brigadeiro
c34349b Adiciona a receita de bolo
700bbd5 Cria o README

Nem o --all mostra o beijinho: sem o branch, nenhuma etiqueta aponta para o commit. Repare, porém, que o próprio Git deixou uma pista: "Deleted branch doces (was e26a98a)", "branch doces apagado (estava em e26a98a)". Se a mensagem já saiu da tela, o reflog tem a mesma informação:

$ git reflog -3
abceaaf (HEAD -> main) HEAD@{0}: checkout: moving from doces to main
e26a98a HEAD@{1}: commit: Adiciona a receita de beijinho     «
abceaaf (HEAD -> main) HEAD@{2}: checkout: moving from main to doces
-3
Só os 3 passos mais recentes, como no git log.
checkout: moving from main to doces
Uma troca de branch: "saindo do main para o doces". O reflog chama de checkout mesmo quando você usou o git switch.
e26a98a HEAD@{1}: commit: …beijinho
O commit que a Ana fez no doces, antes de voltar para o main.

Para ressuscitar o branch, crie um branch novo apontando para esse commit:

$ git branch doces HEAD@{1}
$ git log --oneline --graph --all
* e26a98a (doces) Adiciona a receita de beijinho
* abceaaf (HEAD -> main) Adiciona a receita de brigadeiro
* c34349b Adiciona a receita de bolo
* 700bbd5 Cria o README

O git branch NOME PONTO cria um branch em qualquer ponto: um hash, um HEAD@{n}, outro branch. O doces voltou, com o commit do beijinho, como se nada tivesse acontecido. (Com git switch -c doces HEAD@{1}, você cria o branch e já vai para ele.)

Cuidado: os números andam

Cada comando que move o HEAD acrescenta uma linha no topo do diário, e todos os HEAD@{n} ganham +1. O HEAD@{1} de agora pode ser o HEAD@{2} daqui a pouco. Antes de usar o apelido, rode git reflog de novo; ou, mais seguro, use o hash (git branch doces e26a98a), que nunca muda.

Missão: a Ana acabou de apagar o branch doces, que tinha a receita de beijinho. Ache o commit no git reflog e recrie o branch doces nele, continuando no main.

4. Cada branch tem o seu diário

Além do diário do HEAD, cada branch tem um diário próprio, com tudo o que aconteceu com aquele branch: git reflog show NOME.

$ git reflog show main
abceaaf (HEAD -> main) main@{0}: reset: moving to HEAD@{1}
c34349b main@{1}: reset: moving to HEAD~1
abceaaf (HEAD -> main) main@{2}: commit: Adiciona a receita de brigadeiro
c34349b main@{3}: commit: Adiciona a receita de bolo
700bbd5 main@{4}: commit (initial): Cria o README

Aqui não aparecem as trocas de branch (o main não se mexeu quando a Ana foi para o doces), só os commits e os dois resets. Os apelidos são main@{0}, main@{1}…: "onde o main estava n passos atrás".

O diário de um branch é apagado junto com o branch. Depois do git branch -D doces, o diário dele já não existia (o Git nem reconhecia mais o nome):

$ git reflog show doces
fatal: ambiguous argument 'doces': unknown revision or path not in the working tree.
Use '--' to separate paths from revisions, like this:
'git <command> [<revision>...] -- [<file>...]'

Por isso, para achar o commit de um branch apagado, procure no diário do HEAD (o git reflog sem nada), como na seção 3.

O reflog com cara de git log: -g

O git reflog é um atalho para git log -g --oneline (o -g é de walk reflogs, "andar pelos diários"). Com o git log -g, valem os formatos e filtros do git log:

$ git log -g --oneline -3
abceaaf (HEAD -> main) HEAD@{0}: checkout: moving from doces to main
e26a98a (doces) HEAD@{1}: commit: Adiciona a receita de beijinho
abceaaf (HEAD -> main) HEAD@{2}: checkout: moving from main to doces
$ git reflog --date=iso -2
abceaaf (HEAD -> main) HEAD@{2026-10-15 10:30:00 -0300}: checkout: moving from doces to main
e26a98a (doces) HEAD@{2026-10-15 10:30:00 -0300}: commit: Adiciona a receita de beijinho

Com --date=iso, cada passo mostra quando aconteceu, no lugar do número. No seu computador, isso responde a perguntas como "onde eu estava ontem às 15h?". (Na máquina da Ana, o relógio está parado em 15/10/2026 10:30, então todos os passos têm a mesma hora.)

5. Os limites do reflog

  • É só seu. O reflog fica dentro da pasta .git do seu computador. Ele não vai para o GitHub no git push e não vem no git clone: quem clona o repositório começa com um diário novo. Se você apagar a pasta do projeto, o diário vai junto.
  • Não é para sempre. O Git faz faxina de vez em quando (o git gc, que roda sozinho). Por padrão, as linhas do diário duram 90 dias, e as de commits que não estão em nenhum branch (como o brigadeiro depois do reset), 30 dias (as configurações gc.reflogExpire e gc.reflogExpireUnreachable, no manual git help gc). Depois disso, um commit sem branch pode ser apagado de verdade. Resgate cedo.
  • Só guarda commits. Como você viu, mudanças nunca commitadas não aparecem.

Quando dá errado

fatal: log for 'HEAD' only has 8 entries 
$ git reflog HEAD@{99}
fatal: log for 'HEAD' only has 8 entries

O que aconteceu: "o diário do HEAD só tem 8 entradas", e você pediu a 99ª. O número depois do @ passou do fim do diário.

Como resolver: rode git reflog sem nada para ver os números que existem (vão de HEAD@{0} até HEAD@{7}, aqui).

fatal: ambiguous argument 'HEAD@{abc}' 
$ git show HEAD@{abc}
fatal: ambiguous argument 'HEAD@{abc}': unknown revision or path not in the working tree.
Use '--' to separate paths from revisions, like this:
'git <command> [<revision>...] -- [<file>...]'

O que aconteceu: dentro das chaves vai um número (HEAD@{2}) ou uma data em inglês (HEAD@{yesterday}, "onde o HEAD estava ontem"). Com outra coisa, o Git não entende o nome.

Como resolver: confira as chaves e o número no git reflog. Ou copie o hash da linha, que é mais seguro.

Resetou para o número errado do diário

Os números andam a cada comando (seção 3). Se o git reset --hard HEAD@{1} levou você para um lugar inesperado, não se assuste: esse reset também entrou no diário. Rode git reflog de novo, ache a linha certa (pela mensagem) e faça o reset para o hash dela.

O commit não aparece no reflog

O que pode ter acontecido: o commit foi feito em outro computador (o reflog é local), em outro clone do projeto, ou faz mais de 30/90 dias. Ou a mudança nunca virou commit.

Como resolver: se o commit foi enviado para o GitHub, ele ainda pode estar lá (veja git fetch). Se nunca virou commit, o Git não tem como trazê-lo.

Resumo

  • git reflog é o diário do HEAD: cada commit, troca de branch e reset, do mais recente (HEAD@{0}) para o mais antigo.
  • Um commit que "sumiu" do git log quase sempre está no reflog.
  • Reset errado: git reset --hard HEAD@{1} (ou o hash). Branch apagado: git branch NOME HASH.
  • Cada branch tem o seu diário (git reflog show main), que é apagado junto com o branch.
  • Os números andam a cada comando: confira de novo, ou use o hash.
  • O reflog é local, guarda só commits e dura 90 dias (30 para commits fora de branches).

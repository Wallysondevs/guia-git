Git Projeto: Lançando uma Versão com Tags

O site de receitas da Ana tem página inicial, README e a primeira receita. Está pronto para o mundo. Ela quer marcar este momento: "esta é a versão 1.0.0". Daqui a um mês, quando alguém disser "na versão 1.0.0 o tempo do bolo estava errado", ela vai saber exatamente de qual commit se trata. Para isso, o Git tem as tags (etiquetas): um nome fixo, colado num commit, que nunca sai do lugar. Neste projeto, a Ana lança a 1.0.0, uma correção (1.0.1) e uma novidade (1.1.0), e você faz cada etapa no terminal do guia.

Você vai aprender (na prática)
  • Criar uma tag anotada com git tag -a e ver o que ela guarda com git show.
  • Enviar tags para o GitHub (e por que o git push sozinho não envia).
  • Escolher o número da próxima versão: correção, novidade ou mudança grande.
  • Descobrir "em que versão estou" com git describe e visitar uma versão antiga.
  • Marcar um commit antigo, e apagar uma tag no seu computador e no GitHub.

Este projeto põe em prática Marcando Versões (git tag) e Versionamento Semântico. As saídas saíram do Git 2.53 do Ubuntu, na máquina da Ana, com o sistema em português e um GitHub de treino.

A ideia: a etiqueta no pote de geleia

Pense na Ana fazendo geleia para vender. Cada leva vai para potes com uma etiqueta: "Lote 1 — outubro". Ela continua fazendo geleia, a receita melhora, mas o pote do lote 1 continua com a etiqueta do lote 1. Se um cliente reclamar do lote 1, ela sabe exatamente qual receita usou.

  • Um branch é uma etiqueta que anda: a cada commit, o main passa para o commit novo.
  • Uma tag é uma etiqueta que fica parada: a v1.0.0 aponta para o mesmo commit para sempre.

Que número usar? (versionamento semântico)

Os números de versão seguem uma convenção muito usada, o versionamento semântico: MAIOR.MENOR.CORREÇÃO.

O que mudouNúmero que sobeExemplo no site
Só uma correção, nada novoO último (correção)1.0.0 → 1.0.1: tempo de forno corrigido
Algo novo, e o que existia continua funcionandoO do meio (menor), e o último volta a 01.0.1 → 1.1.0: receita nova de pudim
Mudança que quebra o que existiaO primeiro (maior), e os outros voltam a 01.1.0 → 2.0.0: site todo reorganizado, links antigos não funcionam mais

O v na frente (v1.0.0) não faz parte da versão; é só um costume nos nomes de tag, que ajuda a reconhecer que aquilo é uma versão.

O ponto de partida

O repositório ~/receitas tem três commits e já está ligado ao GitHub (como no projeto da dupla). Ainda não existe nenhuma tag: o git tag sem argumentos lista as tags, e não mostra nada.

$ git log --oneline
fef29c2 (HEAD -> main, origin/main) Adiciona a receita de bolo
4f5e50e Cria a página inicial
700bbd5 Cria o README
$ git tag

Etapa 1: marcar a versão 1.0.0

git tag
O comando das tags. Sem argumentos, lista; com um nome, cria.
-a
De annotated, "anotada": a tag guarda também quem marcou, quando e uma mensagem. É a recomendada para versões.
v1.0.0
O nome da tag.
-m '…'
A mensagem da tag, como no commit. Sem o -m, o Git abre o editor para você escrever.

Sem dizer qual commit, a tag vai no commit atual (o HEAD).

$ git tag -a v1.0.0 -m 'Primeira versão do site de receitas'
$ git tag
v1.0.0
$ git log --oneline
fef29c2 (HEAD -> main, tag: v1.0.0, origin/main) Adiciona a receita de bolo      « a etiqueta nova
4f5e50e Cria a página inicial
700bbd5 Cria o README
$ git show v1.0.0
tag v1.0.0      « primeiro, a tag…
Tagger: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

Primeira versão do site de receitas

commit fef29c22790bb36cd7ba2069e3df7a1b90aaf222 (HEAD -> main, tag: v1.0.0, origin/main)      « …depois, o commit
Author: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

    Adiciona a receita de bolo

diff --git a/bolo.txt b/bolo.txt

  • Criar a tag não mostra nada: no Git, silêncio quer dizer sucesso.
  • No git log, o último commit ganhou a etiqueta tag: v1.0.0, ao lado do HEAD -> main.
  • O git show v1.0.0 mostra primeiro a tag (tag v1.0.0, Tagger = quem marcou, a data e a mensagem) e, depois, o commit para onde ela aponta, com as mudanças dele.

Missão 1: o site está pronto. Marque o commit atual com a tag anotada v1.0.0, com uma mensagem. Confira com git tag, git log --oneline e git show v1.0.0.

Etapa 2: enviar a tag para o GitHub

A Ana confere o git status e tenta um git push:

$ git status
No ramo main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean
$ git push
Everything up-to-date      « nenhuma tag foi enviada
$ git push origin v1.0.0
Enumerating objects: 1, done.
Counting objects: 100% (1/1), done.
Writing objects: 100% (1/1), 179 bytes | 179.00 KiB/s, done.
Total 1 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
To https://github.com/ana-souza/receitas.git
 * [new tag]         v1.0.0 -> v1.0.0      « agora sim
  • Your branch is up to date with 'origin/main'. e Everything up-to-date ("tudo em dia"): para o git push, não há nada a enviar, porque ele envia branches. As tags ficam no seu computador até você mandar.
  • git push origin v1.0.0 envia aquela tag: * [new tag] v1.0.0 -> v1.0.0 ("tag nova"). O único objeto enviado é a própria tag anotada; o commit já estava lá.

No site do GitHub, as tags aparecem na página do repositório, e cada uma pode virar um release ("lançamento"), com notas da versão e arquivos para baixar (ilustrativo; veja "Sobre versões" em docs.github.com/pt).

Etapa 3: a 1.0.1 e a 1.1.0

Uma semana depois, a Ana percebe que o bolo fica pronto em 35 minutos, não 40. É só uma correção: versão 1.0.1. Em seguida, ela acrescenta a receita de pudim. É uma novidade que não quebra nada: versão 1.1.0.

$ git commit -qam 'Corrige o tempo de forno do bolo'
$ git tag -a v1.0.1 -m 'Corrige o tempo de forno'

Missão 2: a v1.0.0 já existe, mas a receita diz 40 minutos e o certo é 35. Corrija o bolo.txt (por exemplo, printf 'Bolo de cenoura\nForno: 180 graus por 35 minutos\nCobertura: chocolate\n' > bolo.txt), faça o commit e marque a nova versão com o número certo para uma correção.

Etapa 4: "em que versão eu estou?"

O git describe responde com a tag anotada mais próxima do commit atual. A Ana pergunta logo depois da 1.1.0, e de novo depois de mais um commit:

$ git describe
v1.1.0
$ echo '<p>Fotos novas toda semana</p>' >> index.html
$ git commit -qam 'Avisa das fotos novas'
$ git describe
v1.1.0-1-ga3eba83      « v1.1.0 + 1 commit, no a3eba83
$ git tag -l 'v1.0*'
v1.0.0
v1.0.1
  • Logo depois de marcar, a resposta é só v1.1.0: o commit atual é a versão 1.1.0.
  • Depois de mais um commit, v1.1.0-1-ga3eba83 se lê assim: "a partir da v1.1.0, 1 commit depois, e o commit atual é o a3eba83" (o g vem de "git" e não faz parte do hash). Muitos projetos usam isso para mostrar a versão no rodapé do site.
  • git tag -l 'v1.0*' lista só as tags que combinam com o padrão (-l de list).

Etapa 5: visitar uma versão antiga

Alguém pergunta: "como era o bolo na versão 1.0.0?". A Ana pode olhar a pasta exatamente como estava naquela versão:

$ git switch v1.0.0
fatal: a branch is expected, got tag 'v1.0.0'
hint: If you want to detach HEAD at the commit, try again with the --detach option.
$ git switch --detach v1.0.0
HEAD is now at fef29c2 Adiciona a receita de bolo
$ cat bolo.txt
Bolo de cenoura
Forno: 180 graus por 40 minutos      « como era na 1.0.0
Cobertura: chocolate
$ ls
README.md  bolo.txt  index.html
$ git status
HEAD detached at v1.0.0
nothing to commit, working tree clean
$ git switch main
Previous HEAD position was fef29c2 Adiciona a receita de bolo
Switched to branch 'main'
Seu ramo está à frente de 'origin/main' por 1 submissão.
  (use "git push" to publish your local commits)
  • O git switch v1.0.0 foi recusado: a branch is expected, got tag 'v1.0.0' ("esperava um branch, recebeu a tag"). O switch só entra em branches, para você não cair sem querer num lugar onde os commits não têm branch.
  • Com --detach, ele aceita: HEAD is now at fef29c2 ("o HEAD agora está em fef29c2"). É o HEAD destacado: você está num commit, e não num branch. Ótimo para olhar; se for mudar algo, crie um branch antes.
  • A receita voltou a dizer 40 minutos, e o pudim.txt não existe: é a versão 1.0.0, inteira. O git status confirma: HEAD detached at v1.0.0.
  • git switch main traz tudo de volta.

Missão 3: o repositório já tem as tags v1.0.0, v1.0.1 e v1.1.0. Visite a versão v1.0.0 para ver como era a receita de bolo (tente primeiro sem o --detach e leia a mensagem). Confira com cat bolo.txt e git status.

Etapa 6: marcar um commit antigo, e apagar uma tag

A Ana lembra que gostaria de ter marcado o primeiro commit, só com o README, como v0.1.0. Basta dizer o hash do commit depois do nome. Ela marca e envia, mas logo se arrepende (essa versão nunca foi publicada de verdade) e apaga, no GitHub e no computador:

$ git tag -a v0.1.0 700bbd5 -m 'Só o README'
$ git log --oneline
a3eba83 (HEAD -> main) Avisa das fotos novas
24ccd78 (tag: v1.1.0, origin/main) Adiciona a receita de pudim
e7306bd (tag: v1.0.1) Corrige o tempo de forno do bolo
fef29c2 (tag: v1.0.0) Adiciona a receita de bolo
4f5e50e Cria a página inicial
700bbd5 (tag: v0.1.0) Cria o README      « no commit antigo
$ git push origin v0.1.0
Enumerating objects: 1, done.
Counting objects: 100% (1/1), done.
Writing objects: 100% (1/1), 166 bytes | 166.00 KiB/s, done.
Total 1 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
To https://github.com/ana-souza/receitas.git
 * [new tag]         v0.1.0 -> v0.1.0
$ git push origin --delete v0.1.0
To https://github.com/ana-souza/receitas.git
 - [deleted]         v0.1.0      « apagada no GitHub
$ git tag -d v0.1.0
Deleted tag 'v0.1.0' (was b384d12)      « apagada no computador
$ git tag
v1.0.0
v1.0.1
v1.1.0
  • Com o hash (700bbd5) depois do nome, a tag vai naquele commit, não no atual.
  • git push origin --delete v0.1.0 apaga a tag no GitHub: - [deleted].
  • git tag -d v0.1.0 apaga no computador. O hash da mensagem (b384d12) é o da própria tag anotada (ela é um objeto do Git, com hash próprio), não o do commit.
Tag publicada não se muda. Se outras pessoas já baixaram a v1.0.0, apagar e recriar a tag noutro commit vai confundir todo mundo (o Git delas não atualiza tags existentes sozinho). Errou numa versão publicada? Lance a próxima (1.0.1) com a correção.

Tag anotada × tag leve

Sem o -a (e sem -m), o Git cria uma tag leve (lightweight): só um nome apontando para o commit, sem autor, data ou mensagem. Veja a diferença:

$ git tag rascunho
$ git cat-file -t rascunho
commit
$ git cat-file -t v1.0.0
tag
$ git show rascunho
commit a3eba83c8317bbae639898b2d61ad6a136964f81 (HEAD -> main, tag: rascunho)      « direto no commit
Author: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

    Avisa das fotos novas

diff --git a/index.html b/index.html
index 9090d6e..62667e5 100644
--- a/index.html
+++ b/index.html
@@ -1,2 +1,3 @@
 <h1>Receitas da Ana</h1>
 <p>Bolo de cenoura</p>
+<p>Fotos novas toda semana</p>
$ git tag -d rascunho
Deleted tag 'rascunho' (was a3eba83)
  • git cat-file -t diz o tipo do objeto: a tag leve rascunho é apenas um apelido para um commit; a v1.0.0 é um objeto tag de verdade.
  • O git show rascunho vai direto para o commit, sem a parte Tagger.
  • O git describe (sem opções) só considera tags anotadas.
Anotada (-a)Leve
Guarda autor, data e mensagemSimNão
Uso típicoVersões publicadasMarcadores pessoais e temporários

Formas diferentes de enviar tags

ComandoEnviaQuando usar
git push origin v1.0.0Só aquela tagO mais seguro: você sabe exatamente o que publicou.
git push --tagsTodas as tags locais que o remoto não tem (inclusive as leves)Quando você tem certeza de que todas devem ir.
git push --follow-tagsOs commits do branch e as tags anotadas que apontam para elesPara enviar commits e versões juntos, deixando de fora as tags leves.

Quando dá errado

"fatal: tag 'v1.0.0' already exists" 
$ git tag -a v1.0.0 -m 'De novo'
fatal: tag 'v1.0.0' already exists

O que aconteceu: já existe uma tag com esse nome ("a tag já existe"). Tags são únicas.

Como resolver: se a ideia era lançar uma versão nova, use o próximo número (v1.0.1). Se a tag foi criada no commit errado e ainda não foi enviada, apague com git tag -d v1.0.0 e crie de novo. (Existe o -f, que substitui a tag, mas evite em tags já publicadas.)

"fatal: Failed to resolve '9f0c742' as a valid ref." 
$ git tag -a v0.1.0 9f0c742 -m 'Só o README'
fatal: Failed to resolve '9f0c742' as a valid ref.

O que aconteceu: não existe commit com esse hash neste repositório ("não consegui entender '9f0c742' como uma referência válida"). Aqui, a Ana copiou o hash de outro repositório.

Como resolver: pegue o hash certo no git log --oneline do próprio repositório e tente de novo.

"fatal: a branch is expected, got tag 'v1.0.0'"

É o da etapa 5. O que aconteceu: o git switch só troca para branches. Como resolver: para olhar, git switch --detach v1.0.0. Para trabalhar a partir daquela versão (por exemplo, corrigir algo na 1.0.x), crie um branch a partir da tag: git switch -c corrige-1.0 v1.0.0.

"error: unable to delete 'v0.1.0': remote ref does not exist" 
$ git push origin --delete v0.1.0
error: unable to delete 'v0.1.0': remote ref does not exist
error: failed to push some refs to 'https://github.com/ana-souza/receitas.git'

O que aconteceu: a tag não existe no GitHub ("não foi possível apagar: a referência remota não existe"), talvez porque nunca foi enviada. Nada mudou.

Como confirmar: git ls-remote --tags origin lista as tags que o remoto tem.

"error: tag 'v0.1.0' not found." 
$ git tag -d v0.1.0
error: tag 'v0.1.0' not found.

O que aconteceu: não há tag com esse nome no seu computador ("tag não encontrada"). Confira o nome exato com git tag (maiúsculas, o v, os pontos).

Resumo

  • Tag = etiqueta fixa num commit. Para versões, use tag anotada: git tag -a v1.0.0 -m '…'.
  • Versionamento semântico: MAIOR.MENOR.CORREÇÃO. Correção sobe o último número; novidade sobe o do meio; mudança que quebra sobe o primeiro.
  • O git push não envia tags: git push origin v1.0.0, git push --tags ou git push --follow-tags.
  • git describe diz a versão mais próxima; git switch --detach v1.0.0 visita a versão; git switch main volta.
  • Apagar: git tag -d (local) e git push origin --delete (remoto). Versão já publicada não se refaz: lance a próxima.

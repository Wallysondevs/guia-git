Git Commitei uma Senha! E Agora?

Acontece com todo mundo: a Ana fez git add ., commitou, e junto foi o arquivo .env com a chave da API do site de receitas. Em outro dia, pior: enviou para o GitHub um arquivo com a senha do painel. Esta aula é o plano de ação, na ordem certa. Spoiler do passo mais importante: ele não tem nada a ver com o Git.

Você vai aprender
  • Por que o primeiro passo é sempre trocar (revogar) a senha, e não mexer no histórico.
  • Como tirar o arquivo do commit quando você ainda não fez push (git rm --cached, .gitignore e --amend).
  • Por que git rm sozinho não apaga a senha do histórico.
  • Como limpar o histórico depois do push com o git filter-repo, e o que fazer com o GitHub e os colegas.
  • Como evitar que aconteça de novo.
As senhas desta aula são inventadas

chave-de-exemplo-0000 e senha-de-exemplo-123 são exemplos, não servem para nada. Nunca use uma senha de verdade para "testar" estes comandos.

A ideia: trocar a fechadura, não só esconder a chave

Imagine que a Ana perdeu a chave de casa numa praça. Ela pode voltar à praça e procurar a chave, mas não tem como saber se alguém já pegou, copiou e devolveu. O que resolve de verdade é trocar a fechadura: a chave antiga passa a não abrir nada.

Com senhas no Git é igual. Depois que um commit sai do seu computador (push), você não sabe quem já viu: robôs varrem o GitHub atrás de senhas e chaves o tempo todo. Por isso a documentação do GitHub (Removendo dados confidenciais de um repositório) manda, como primeira etapa, revogar e/ou alterar o segredo: depois disso, ele não serve mais para acessar nada. E diz mais: com o segredo revogado, pode nem ser necessário reescrever o histórico.

O mapa da decisão

Commitei uma senha.
│
├─ 1. SEMPRE: troque/revogue a senha no serviço dela.   (se já fez push: agora!)
│
├─ Ainda NÃO fiz push?
│    └─ Tire o arquivo do commit (git rm --cached + .gitignore + --amend).   ← fácil
│
└─ JÁ fiz push?
     ├─ A senha foi revogada? Talvez baste isso + um commit que remove o arquivo.
     └─ Precisa sumir do histórico? git filter-repo + push --force --mirror
        + avisar colegas + suporte do GitHub.                                ← trabalhoso

Passo 1: revogue a senha (fora do Git)

Onde trocar depende de que senha é:

O que vazouOnde resolver
Um token de acesso do GitHubNas configurações da sua conta do GitHub, na parte de tokens: apague o token e gere outro.
Uma chave SSH privadaRemova a chave pública correspondente da sua conta do GitHub (e de servidores) e gere um par novo.
Chave de API (mapas, pagamentos, e-mail…)No painel do serviço que emitiu a chave: revogue e gere outra.
Senha de banco de dados, painel, e-mailTroque a senha no próprio sistema. Se ela é usada em outro lugar, troque lá também.

Depois, atualize os programas que usavam a senha antiga, e só então cuide do histórico.

Caso A: ainda não fiz push

Esse é o caso feliz: o commit só existe no computador da Ana. Ela tinha acabado de commitar:

$ git add .                                     « o "." levou tudo, inclusive o .env

Para consertar, são três movimentos: tirar o .env do Git (sem apagar o arquivo da pasta), mandar o Git ignorá-lo daqui em diante e refazer o último commit.

git rm --cached .env
Tira o arquivo da área de preparo e do próximo commit, mas deixa o arquivo na pasta (--cached = "só no Git, não no disco"). Veja git rm.
echo '.env' >> .gitignore
Acrescenta a linha .env ao .gitignore, para o Git nunca mais oferecê-lo.
git commit --amend --no-edit
Refaz o último commit com o que está preparado agora, mantendo a mensagem (--no-edit). Veja --amend.
$ git rm --cached .env
rm '.env'                                        « saiu do Git (não do disco)
$ echo '.env' >> .gitignore
$ git add .gitignore
$ git status
No ramo main

  (use "git push" to publish your local commits)

	new file:   .gitignore

$ cat .env
CHAVE_API=chave-de-exemplo-0000                  « o arquivo continua na pasta

Linha por linha:

  • rm '.env': o git rm confirma o que tirou. Com --cached, foi só do Git: o ls -a e o cat no fim mostram que o arquivo continua lá.
  • deleted: .env: "apagado", comparando com o último commit (que tinha o .env). Depois do --amend, esse commit é substituído.
  • Seu ramo está à frente de 'origin/main' por 1 submissão: confirma que o commit ainda não foi enviado. É o que torna este caso fácil.
  • [main 2790fde]: o commit novo tem outro hash; o antigo (db57cbc, com a chave) ficou sem etiqueta e só existe no seu computador, no reflog, até a faxina automática do Git apagá-lo.
E se o commit com a senha não é o último?

Se ainda não houve push, você pode reescrever os commits locais com o rebase interativo (marcando o commit com edit e fazendo o mesmo git rm --cached + --amend nele), ou usar o git filter-repo do caso B, que funciona igual sem push.

Missão: o último commit ("Adiciona busca de receitas") levou o arquivo .env com uma chave (de exemplo), e ainda não houve push. Tire o .env do commit sem apagá-lo da pasta, faça o Git ignorá-lo com o .gitignore e refaça o último commit com --amend (o repositório deve continuar com 2 commits). Confira com git show --stat HEAD.

Caso B: já fiz push

Semana passada, antes de criar o .gitignore, a Ana enviou ao GitHub o arquivo credenciais.txt, com a senha do painel. Depois disso vieram mais commits. Passo 1 feito: ela já trocou a senha do painel. Agora, o histórico.

Por que git rm não basta

O primeiro impulso é apagar o arquivo e commitar. Veja o que acontece:

$ git log --oneline -- credenciais.txt
b81e404 Adiciona dados do painel                 « o commit que criou o arquivo
$ git rm -q credenciais.txt
$ git commit -m 'Remove as credenciais'
[main 3bf4b84] Remove as credenciais
 1 file changed, 1 deletion(-)
 delete mode 100644 credenciais.txt
$ git push -q
$ ls
bolo.txt  busca.js  index.html  pudim.txt        « sumiu da pasta…
$ git log --oneline -- credenciais.txt
3bf4b84 Remove as credenciais
b81e404 Adiciona dados do painel                 « …mas o commit antigo continua lá
$ git show b81e404:credenciais.txt
SENHA_DO_PAINEL=senha-de-exemplo-123             « qualquer um com o repositório lê
git log --oneline -- credenciais.txt
Mostra só os commits que mexeram nesse arquivo (o -- separa as opções do caminho).
git show b81e404:credenciais.txt
Mostra o arquivo como ele era no commit b81e404. Qualquer pessoa que clonar o repositório pode fazer isso.

O Git guarda todas as versões: apagar o arquivo hoje não apaga as fotos de ontem. Para a senha sumir, é preciso reescrever o histórico: refazer todos os commits desde o b81e404, como se o arquivo nunca tivesse existido.

Reescrever histórico público é sério

É o que a Regra de Ouro manda evitar: todos os commits a partir do vazamento ganham hashes novos, e quem tem uma cópia antiga fica com um histórico diferente. Faça só quando a senha precisa mesmo sumir (revogar nem sempre é possível; dados pessoais, por exemplo, não se "revogam"), e combine antes com a equipe.

A ferramenta recomendada: git filter-repo

O git filter-repo não vem com o Git: é um programa à parte, recomendado pela documentação do GitHub e pelo próprio projeto Git (no lugar do antigo git filter-branch). No Ubuntu 26.04 ele está no pacote git-filter-repo (versão 2.47.0), que se instala com sudo apt install git-filter-repo. A opção --sensitive-data-removal, feita exatamente para senhas vazadas, exige a versão 2.47 ou mais nova.

A recomendação é trabalhar numa cópia nova, clonada do GitHub, e não na sua pasta do dia a dia:

Repare que o commit "Adiciona dados do painel" sumiu do histórico: ele só tinha o arquivo da senha, então ficou vazio e o filter-repo o descartou. O commit "Remove as credenciais" também sumiu, pelo mesmo motivo.

--force
Aceita substituir o histórico do servidor (normalmente o Git recusa, veja push rejeitado). Aqui é um dos raros casos em que o --force é a ferramenta certa.
--mirror
Envia todas as referências (branches, tags…), deixando o servidor igual à sua cópia. A documentação do GitHub observa que o --force já está implícito no --mirror; ela o escreve mesmo assim, como lembrete de que tudo será sobrescrito.

No GitHub real, a documentação avisa que esse comando falha ao enviar as referências que começam com refs/pull/ (as dos pull requests), que são só de leitura, e que branches protegidos podem precisar de ajuste temporário (ilustrativo: o "GitHub de mentira" do laboratório não tem pull requests).

Não siga a dica do git pull aqui! Juntar o histórico velho com o novo traria a senha de volta, e o próximo push a mandaria de novo ao GitHub. A saída segura é jogar a cópia antiga fora e usar a limpa:

$ cd ~
$ rm -rf receitas
$ mv receitas-limpeza receitas
$ cd receitas
$ git status
No ramo main

O Bruno, e todo mundo que tinha clonado, faz o mesmo: apaga a cópia antiga e clona de novo (salvando antes, à parte, o trabalho que ainda não tinha enviado).

O que fica fora do seu alcance (ilustrativo)

Segundo a documentação do GitHub:

  • Forks: se o commit com a senha existe num fork, ele continua acessível lá; você precisa falar com o dono do fork.
  • Pull requests: os hashes mudam, o que pode bagunçar pull requests abertos; a recomendação é juntar ou fechar os pull requests abertos antes da limpeza.
  • Cópias guardadas pelo GitHub: para remover visualizações em cache e referências de pull requests, é preciso entrar em contato com o suporte do GitHub, informando o repositório e os "First Changed Commit(s)" que o filter-repo mostrou.

É por isso que o passo 1 importa tanto: o histórico limpo reduz o estrago, mas só a senha trocada garante que a antiga não abre mais nada.

Para não acontecer de novo

  1. Senha fora do código: guarde-as em variáveis de ambiente ou num arquivo .env que está no .gitignore desde o primeiro commit.
  2. Um modelo sem senha: commite um .env.exemplo com CHAVE_API=coloque-sua-chave-aqui, para os colegas saberem o que preencher.
  3. Olhe antes de commitar: git status e git diff --staged mostram exatamente o que vai entrar. Cuidado com git add . e git commit -a, que levam tudo.
  4. Deixe uma máquina vigiar: um hook pre-commit ou ferramentas como gitleaks e git-secrets procuram senhas antes do commit. No GitHub, a proteção por push bloqueia pushes que contêm segredos conhecidos (veja a documentação de verificação de segredos; ilustrativo).

Quando dá errado

git: 'filter-repo' não é um comando git 
$ git filter-repo --invert-paths --path credenciais.txt
git: 'filter-repo' não é um comando git. Veja 'git --help'.

O que aconteceu: o git filter-repo não vem com o Git e não está instalado.

Como resolver: no Ubuntu, sudo apt install git-filter-repo. Confira se a sua versão aceita --sensitive-data-removal (2.47 ou mais nova); se não aceitar, instale uma mais nova pelas instruções do projeto.

Apaguei o arquivo e commitei, mas a senha "ainda está lá"

O que aconteceu: git rm + commit apaga a versão de hoje; os commits antigos continuam com o arquivo (git show HASH:arquivo mostra, como acima).

Como resolver: revogue a senha; se ela precisa sumir do histórico, use o git filter-repo (caso B).

Usei git rm sem --cached e o arquivo sumiu da pasta

O que aconteceu: sem --cached, o git rm tira o arquivo do Git e do disco.

Como resolver: se o arquivo estava em algum commit, traga-o de volta para a pasta com git restore --source=HEAD~1 .env (ou do commit onde ele estava; veja git restore), e garanta que ele está no .gitignore.

A senha voltou ao GitHub depois da limpeza

O que aconteceu: alguém (às vezes você mesmo) fez git pull e git push numa cópia antiga, juntando o histórico velho ao novo.

Como confirmar: git log --oneline --all -- credenciais.txt volta a mostrar commits.

Como resolver: repita a limpeza numa cópia nova e peça, de novo e com mais ênfase, que todos apaguem as cópias antigas e clonem outra vez.

Exercícios

1. Só do Git, não do disco

git rm .env

2. Refazer o último commit

Complete para refazer o último commit mantendo a mensagem:

git commit --amend

3. Remover o arquivo de todo o histórico

Complete a opção que faz o filter-repo remover o caminho, em vez de manter só ele:

git filter-repo --sensitive-data-removal --path credenciais.txt

4. Você descobriu que enviou um token do GitHub num commit. Qual é o primeiro passo?

5. A Ana rodou git rm credenciais.txt, commitou e fez push. A senha ainda pode ser lida?

6. Depois da limpeza com filter-repo e do push, o git status da cópia antiga diz que os branches "divergiram". O que fazer?

Resumo

  • Primeiro, revogue/troque a senha. Só isso garante que a antiga não abre mais nada.
  • Sem push: git rm --cached, .gitignore e git commit --amend.
  • git rm + commit não apaga a senha dos commits antigos.
  • Com push: numa cópia nova, git filter-repo --sensitive-data-removal --invert-paths --path ARQ, depois git push --force --mirror origin.
  • Todos reclonam; forks, pull requests e cópias em cache do GitHub exigem contato com donos e suporte.
  • Prevenção: .gitignore desde o início, .env.exemplo, git diff --staged antes de commitar, proteção por push.

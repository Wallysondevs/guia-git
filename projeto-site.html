Git Projeto: Versionando um Site

O site de receitas da Ana já existe: uma página inicial, uma folha de estilo e uma página por receita. Até hoje, cada mudança era feita "no escuro": se algo quebrasse, não havia como voltar. Neste projeto, a Ana coloca o site que já existe no Git, versiona cada mudança, desfaz um erro do jeito seguro, marca a primeira versão oficial, envia tudo ao GitHub e recebe uma correção do Bruno. São cinco missões encadeadas: faça junto.

Neste projeto você vai praticar
  • Colocar uma pasta com arquivos e subpastas no Git, ignorando o que não deve entrar (.gitignore).
  • Commits pequenos: um para a cor, outro para a página nova (com dois arquivos juntos, porque são um assunto só).
  • Desfazer um commit com git revert, sem apagar o histórico.
  • Marcar a versão com git tag, enviar com git push e receber com git pull.
Antes de começar

Este projeto continua o Seu Primeiro Repositório do Zero. Se o ciclo status → add → commit ainda é novidade, faça aquele primeiro. Cada missão daqui começa pronta, no ponto onde a etapa anterior terminou.

O site da Ana

A pasta ~/site tem estes arquivos. Os de dentro de rascunhos/ são ideias que a Ana não quer publicar:

$ find . -type f
./rascunhos/ideias.txt
./css/estilo.css
./receitas/bolo.html
./index.html

<h1>Receitas da Ana</h1>

Português e inglês misturados? A tradução do Git que vem no Ubuntu é parcial: algumas mensagens saem em português, outras em inglês (e algumas em português de Portugal, como "submissões"). As saídas abaixo estão exatamente como apareceram; as mensagens em inglês ganham tradução no texto. Em outros sistemas, as frases podem sair diferentes ou todas em inglês.

Etapa 1: o site entra no Git

Primeiro o git init, e logo depois um git status para ver o que o Git encontrou:

$ git init
Repositório vazio Git inicializado em  /home/ana/site/.git/
$ git status
No ramo main

No commits yet

Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	css/
	index.html
	rascunhos/                               « isto não deve ir para o site!
	receitas/

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)

Para pastas novas, o Git mostra só o nome da pasta (css/), não cada arquivo. Antes de qualquer git add, a Ana cria o .gitignore com a pasta de rascunhos (a barra no fim quer dizer "a pasta e tudo o que há dentro"):

$ echo 'rascunhos/' > .gitignore
$ git status
No ramo main

No commits yet

Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	.gitignore
	css/
	index.html
	receitas/                                « rascunhos/ sumiu da lista

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)
$ git add .
$ git status
No ramo main

No commits yet

Mudanças a serem submetidas:
  (utilize "git rm --cached <arquivo>..." para não apresentar)
	new file:   .gitignore
	new file:   css/estilo.css
	new file:   index.html
	new file:   receitas/bolo.html               « agora aparecem os arquivos, um por um

$ git commit -m 'Versão inicial do site'
[main (root-commit) 10874b7] Versão inicial do site
 4 files changed, 14 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 css/estilo.css
 create mode 100644 index.html
 create mode 100644 receitas/bolo.html

O git add . ("adicione tudo desta pasta para baixo") é seguro aqui por dois motivos: o .gitignore já estava pronto e a Ana conferiu a lista com git status antes do commit. O 4 files changed, 14 insertions(+) confirma: quatro arquivos, 14 linhas, nenhum rascunho.

Missão 1: você está na pasta ~/site, que ainda não é um repositório. Crie o repositório, faça o Git ignorar a pasta rascunhos/ e faça o primeiro commit com todo o resto. Confira com git status antes do commit: nada de rascunhos/ na lista.

Etapa 2: uma mudança de estilo

A Ana quer o título verde. Ela troca a cor no CSS (aqui com sed, que substitui texto num arquivo; no dia a dia, ela usaria o editor) e confere a diferença:

$ sed -i 's/#c0392b/#27ae60/' css/estilo.css
$ git diff
diff --git a/css/estilo.css b/css/estilo.css
index ff7aefe..28b20c5 100644
--- a/css/estilo.css
+++ b/css/estilo.css
@@ -1,2 +1,2 @@
 body { font-family: sans-serif; }
-h1 { color: #c0392b; }                         « a linha antiga (vermelho)
+h1 { color: #27ae60; }                         « a linha nova (verde)
$ git commit -am 'Muda a cor do título para verde'
[main 0ebfbdd] Muda a cor do título para verde
 1 file changed, 1 insertion(+), 1 deletion(-)

Uma linha trocada aparece no Git como uma remoção (-) mais uma inclusão (+): daí o 1 insertion(+), 1 deletion(-). O -am é -a (prepara sozinho os arquivos já rastreados que mudaram) mais -m (a mensagem): um atalho que só é seguro quando você acabou de ver o git diff.

Missão 2: troque a cor do título de #c0392b para #27ae60 no css/estilo.css (use o sed da etapa), confira com git diff e commite.

Etapa 3: uma página nova (dois arquivos, um assunto)

A Ana cria a página do pudim e coloca o link na página inicial. São dois arquivos, mas um assunto só: um sem o outro deixaria o site quebrado (um link para página inexistente, ou uma página sem link). Por isso, vão juntos no mesmo commit:

$ git status
No ramo main
Changes not staged for commit:
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   index.html                       « o link novo

Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	receitas/pudim.html                          « a página nova

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
$ git diff
diff --git a/index.html b/index.html
index 040fc49..abb816a 100644
--- a/index.html
+++ b/index.html
@@ -4,4 +4,5 @@
 <h1>Receitas da Ana</h1>
 <ul>
   <li><a href="receitas/bolo.html">Bolo de cenoura</a></li>
+  <li><a href="receitas/pudim.html">Pudim de leite</a></li>
 </ul>
$ git add index.html receitas/pudim.html
$ git commit -m 'Adiciona a página do pudim'
[main 580b96c] Adiciona a página do pudim
 2 files changed, 5 insertions(+)
 create mode 100644 receitas/pudim.html

Repare: o git diff mostrou só o index.html. Arquivos novos (não rastreados) não aparecem no git diff; para eles, o git status é quem avisa. E aqui o atalho -a não serviria: ele não pega arquivos novos, e o pudim.html ficaria de fora.

Missão 3: a página receitas/pudim.html já foi criada e o link já está no index.html. Faça um único commit com os dois arquivos. Dica: o git commit -am não serve aqui. Por quê?

Etapa 4: um erro, desfeito com segurança

Num impulso, a Ana trocou o nome do site para "Receitas da Vovó" e commitou. No dia seguinte, desistiu. Como esse commit pode já estar no GitHub (e no computador do Bruno), ela não apaga nada: cria um commit que desfaz o outro, com o git revert:

$ git log --oneline -1
98a83bd (HEAD -> main) Muda o título para Receitas da Vovó
$ git revert --no-edit HEAD
[main 80103de] Revert "Muda o título para Receitas da Vovó"
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 2 insertions(+), 2 deletions(-)
$ git log --oneline
80103de (HEAD -> main) Revert "Muda o título para Receitas da Vovó"     « o commit que desfaz
98a83bd Muda o título para Receitas da Vovó              « o erro continua no histórico
580b96c Adiciona a página do pudim
0ebfbdd Muda a cor do título para verde
10874b7 Versão inicial do site
$ grep Receitas index.html
<title>Receitas da Ana</title>                       « o nome voltou
<h1>Receitas da Ana</h1>
git revert
Cria um commit novo com o contrário das mudanças do commit indicado.
--no-edit
Aceita a mensagem automática (Revert "…") sem abrir o editor.
HEAD
O commit a desfazer: aqui, o último. Pode ser qualquer hash, por exemplo git revert 98a83bd.

O histórico conta a verdade: houve uma mudança e ela foi desfeita. Ninguém que já tinha o commit 98a83bd é prejudicado. (Para erros que nunca saíram do seu computador, há outras ferramentas: veja Desfazendo: o Mapa.)

Missão 4: o último commit trocou o nome do site para "Receitas da Vovó". Desfaça-o sem apagar o histórico, com um commit novo que faz o contrário. Confira com git log --oneline e grep Receitas index.html.

Etapa 5: a versão 1.0

O site está pronto para ir ao ar. A Ana marca este ponto do histórico com uma tag, uma etiqueta que, ao contrário de um branch, nunca anda:

$ git tag -a v1.0 -m 'Primeira versão no ar'
$ git tag
v1.0
$ git log --oneline --decorate -2
80103de (HEAD -> main, tag: v1.0) Revert "Muda o título para Receitas da Vovó"
98a83bd Muda o título para Receitas da Vovó

O -a cria uma tag "anotada" (com autor, data e a mensagem do -m), a recomendada para versões. No git log --decorate, a linha do commit mostra as etiquetas presas a ele: o branch main (com o HEAD) e a tag v1.0. O nome segue o versionamento semântico.

Missão 5: marque o commit atual com a tag anotada v1.0 e a mensagem "Primeira versão no ar". Confira com git tag e git log --oneline --decorate.

Etapa 6: para o GitHub

A Ana criou no GitHub um repositório vazio chamado site-receitas (veja Criando um Repositório no GitHub; a tela do site é descrita lá). Agora ela conecta a pasta ao GitHub e envia o branch e a tag:

$ git remote add origin https://github.com/ana-souza/site-receitas.git
$ git remote -v

origin	https://github.com/ana-souza/site-receitas.git (push)
$ git push -u origin main

nothing to commit, working tree clean
  • git remote add origin URL: dá o apelido origin ao endereço do GitHub (veja git remote).
  • -u no primeiro push: liga o main local ao origin/main (upstream), e daí em diante basta git push e git pull.
  • git push origin v1.0: o git push comum não envia tags; é preciso enviá-las pelo nome (ou todas com --tags).

(As saídas desta etapa e da próxima vieram do laboratório, com um "GitHub de mentira" local. Para o site aparecer na internet, o próximo passo é ativar o GitHub Pages.)

Missão 6: o repositório vazio ana-souza/site-receitas já existe no GitHub do terminal. Dê a ele o apelido origin, envie o main (ligando-o ao origin/main com -u) e depois envie a tag v1.0. Confira com git status. (O terminal do guia mostra a versão curta do push, sem as linhas de progresso Enumerating objects….)

Cada commit conta um passo do site, até o erro e o conserto. Se um dia a página do pudim der problema, a Ana sabe exatamente qual commit olhar.

Quando dá errado neste projeto

Commitei a pasta rascunhos/ sem querer

O que aconteceu: o git add . veio antes do .gitignore.

Como resolver: crie o .gitignore, tire a pasta do Git sem apagá-la do disco com git rm -r --cached rascunhos e commite (veja git rm). Se havia algo sensível lá e você já fez push, veja Commitei uma Senha!.

O git commit -am não levou a página nova

O que aconteceu: o -a só prepara arquivos já rastreados; arquivos novos ficam de fora.

Como resolver: git add receitas/pudim.html e, se o commit anterior ainda não foi enviado, junte ao último com git commit --amend --no-edit (veja --amend).

A tag não aparece no GitHub

O que aconteceu: o git push comum não envia tags.

Como resolver: git push origin v1.0 (ou git push --tags).

O git push foi rejeitado

O que aconteceu: alguém (o Bruno) enviou commits que você ainda não tem.

Como resolver: git pull primeiro, depois git push. Os detalhes e as mensagens estão em Push Rejeitado.

Resumo

  • Para colocar um projeto que já existe no Git: git init, .gitignore antes do git add ., git status e o primeiro commit.
  • Um assunto por commit, mesmo que envolva vários arquivos; o -a não pega arquivos novos.
  • Erro que pode estar publicado: git revert, que desfaz com um commit novo.
  • Versões: git tag -a v1.0 -m '…' e git push origin v1.0.
  • GitHub: git remote add origin URL, git push -u origin main e, para receber o trabalho dos outros, git pull.

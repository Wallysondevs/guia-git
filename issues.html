Git Issues

Um leitor do site de receitas da Ana achou um erro: o link da receita de bolo não abre. Ele poderia mandar um e-mail, que ia se perder na caixa de entrada. No GitHub, o lugar certo para isso é uma issue (em inglês, "questão" ou "assunto"; a documentação em português do GitHub chama de "problema"). Issue é um cartão de tarefa ligado ao repositório: um bug para consertar, uma ideia nova, uma dúvida. Cada uma tem número, conversa, responsável e, no fim, é fechada quando o trabalho termina.

Você vai aprender
  • O que é uma issue e para que ela serve (bugs, ideias, tarefas, dúvidas).
  • Como abrir uma issue que alguém consegue resolver: título, descrição, passos para reproduzir.
  • Rótulos (labels), responsáveis (assignees), marcos (milestones) e menções com @ e #.
  • Como fechar uma issue automaticamente escrevendo Closes #N no pull request ou na mensagem do commit.
Esta aula é do site do GitHub

Issues não fazem parte do Git: elas moram no site do GitHub (o GitLab e outros sites têm coisa parecida). Por isso, as telas e botões descritos aqui são ilustrativos, baseados na documentação oficial (docs.github.com/pt/issues). O site do GitHub é em inglês; quando a documentação em português traduz um nome, ele aparece entre parênteses. Os comandos git desta aula rodaram de verdade no Git do Ubuntu da Ana (usuária ana, computador notebook).

A ideia: o quadro de avisos da cozinha

Na cozinha do restaurante há um quadro com bilhetes: "o forno 2 está esquentando demais", "testar receita de pudim sem lactose", "acabou a farinha". Cada bilhete diz o que é, alguém escreve embaixo quem vai cuidar, e quando está resolvido o bilhete sai do quadro. As issues são esse quadro, só que:

  • cada bilhete ganha um número (#1, #2, #3…) para ser citado em qualquer lugar;
  • embaixo de cada bilhete há uma conversa (comentários) que fica guardada;
  • o bilhete pode ser ligado ao código: o commit ou o pull request que resolveu o problema.

1. Onde ficam as issues

Na página de qualquer repositório do GitHub há uma aba Issues, ao lado de Code e Pull requests. Ela mostra a lista de issues abertas (Open) e fechadas (Closed), com filtros por rótulo, responsável e autor. Em repositórios públicos, qualquer pessoa com conta no GitHub pode abrir uma issue; quem mantém o projeto decide o que fazer com ela. (O dono do repositório pode desligar a aba nas configurações.)

2. Abrindo uma issue (ilustrativo)

  1. No repositório, clique na aba Issues.
  2. Clique em New issue ("Novo problema"). Se o repositório tiver modelos de issue, o GitHub mostra a lista deles; escolha um, ou a opção de issue em branco.
  3. Preencha o título e a descrição. A descrição aceita Markdown: listas, `código`, imagens arrastadas para a caixa.
  4. Se você mantém o projeto, escolha também responsáveis, rótulos e marco (seção 4).
  5. Clique no botão de criar ("Enviar novo problema", na documentação em português).

A issue ganha o próximo número livre do repositório. Issues e pull requests dividem a mesma numeração: se o último pull request foi o #7, a próxima issue é a #8.

3. Uma boa issue

Compare as duas issues que o site da Ana recebeu:

RuimBoa
Título: não funciona
Descrição: o site está quebrado, arrumem!!		Título: Link "Bolo de cenoura" na página inicial dá erro 404
Descrição: veja abaixo
## O que acontece
Na página inicial, clicar em "Bolo de cenoura" abre uma página de erro 404.

## Como reproduzir
1. Abra https://ana-souza.github.io/receitas/
2. Clique em "Bolo de cenoura", na lista de bolos

## O que eu esperava
Abrir a receita do bolo de cenoura.

## Onde
Firefox 140, no Ubuntu. No celular acontece o mesmo.

A boa issue diz o que acontece, como fazer acontecer de novo (os "passos para reproduzir") e o que se esperava. Com isso, quem for consertar não precisa adivinhar nada. Antes de abrir, procure na lista (inclusive nas fechadas) se alguém já não abriu a mesma: issue repetida ganha o rótulo duplicate e é fechada.

Uma issue, um assunto

Como uma aula deste guia: se você achou dois erros diferentes, abra duas issues. Assim cada uma pode ser fechada quando o seu conserto entrar, por pessoas diferentes, em dias diferentes.

4. Organizando: rótulos, responsáveis e marcos

Labels (rótulos)
Etiquetas coloridas para classificar. Todo repositório novo já vem com dez: bug, documentation, duplicate, enhancement (pedido de funcionalidade nova), good first issue (boa para quem está começando no projeto), help wanted, invalid, question, wontfix (não vai ser feito) e accessibility. Dá para criar os seus (receita, layout…).
Assignees (responsáveis)
Quem vai cuidar da issue. Evita que duas pessoas consertem a mesma coisa sem saber.
Milestone (marco)
Agrupa issues numa meta, como "Versão 1.0" ou "Lançamento de dezembro", e mostra quanto dela já foi fechado.
@nome
Em qualquer comentário, @bruno-lima menciona e avisa a pessoa.
#número
Escrever #12 num comentário vira um link para a issue (ou pull request) 12 do mesmo repositório. Para outro repositório: dono/repositorio#12.
- [ ] tarefa
Uma lista de tarefas em Markdown na descrição vira caixinhas de marcar, e a lista mostra o progresso.

5. Fechando a issue sozinha com Closes #N

O jeito mais elegante de fechar uma issue é ligá-la ao conserto. Se a descrição de um pull request disser Closes #12, a issue 12 é fechada sozinha no momento em que o pull request é mesclado no branch padrão (a main). As palavras que funcionam são:

Palavras-chaveExemplo
close, closes, closedCloses #12
fix, fixes, fixedFixes #12
resolve, resolves, resolvedResolves #12
Issue de outro repositórioFixes ana-souza/receitas#12

Elas podem estar em maiúsculas ou minúsculas e ser seguidas de dois-pontos (Closes: #12). Em português não funciona: "Fecha #12" vira só um link, sem fechar nada.

Na mensagem do commit

A mesma palavra-chave funciona na mensagem do commit: quando o commit chega ao branch padrão no GitHub, a issue é fechada. O costume é deixar o título do commit para dizer o que mudou e pôr o Closes numa linha do corpo da mensagem. Um jeito de fazer isso na linha de comando é usar -m duas vezes: o primeiro vira o título, o segundo vira um parágrafo do corpo:

$ git add index.html
$ git commit -m "Corrige link do bolo de cenoura" -m "Closes #12"
[main dfa1484] Corrige link do bolo de cenoura
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git log -1
commit dfa1484bd25c156903b4954b398b582e80878e1f
Author: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

    Corrige link do bolo de cenoura           « o título
    
    Closes #12                                « o corpo: o GitHub lê esta linha
$ git log --oneline
dfa1484 Corrige link do bolo de cenoura       « no resumo, só o título aparece
e29acb6 Primeira versão do site
-m "Corrige link do bolo de cenoura"
O título do commit (a primeira linha), o que aparece no git log --oneline.
-m "Closes #12"
Um segundo parágrafo, separado do título por uma linha em branco. É aqui que o GitHub procura a palavra-chave.

O git log -1 (só o último commit) mostra a mensagem inteira: o título, uma linha em branco que o próprio Git pôs entre os dois -m, e o corpo com Closes #12. Para o Git, Closes #12 é um texto como outro qualquer: quem entende a palavra-chave é o GitHub, quando o commit chegar lá com o git push e entrar na main. Se você prefere escrever mensagens longas no editor, rode só git commit (sem -m): a primeira linha é o título, deixe uma linha em branco e escreva o corpo embaixo (veja Boas Mensagens de Commit).

Só no branch padrão

A issue só fecha sozinha quando o pull request (ou o commit) entra no branch padrão do repositório. Um pull request para a develop (no Git Flow) com Closes #12 não fecha nada: as palavras-chave são ignoradas.

Missão: o arquivo index.md do repositório receitas já foi corrigido e está na área de preparo. Faça o commit com o título Corrige link do pudim e, no corpo, a linha Closes #3, para a issue 3 fechar sozinha quando o commit chegar à main do GitHub. Confira com git log -1.

Fechando à mão

Também dá para fechar uma issue pelo botão Close issue ("Fechar problema") no fim da página dela (ilustrativo). Uma setinha ao lado do botão deixa escolher o motivo do fechamento, por exemplo, se foi resolvida ou se não vai ser feita. Uma issue fechada não some: ela vai para a lista Closed e pode ser reaberta.

Quando dá errado

Escrevi Closes #12 e a issue não fechou

O que aconteceu: quase sempre, o pull request foi mesclado num branch que não é o padrão (por exemplo, a develop), ou a palavra estava em português ("Fecha #12"), ou faltou o #. Como confirmar: na página do pull request, a issue ligada aparece na barra lateral, em Development (ilustrativo); se ela não está lá, o GitHub não reconheceu a ligação. Como resolver: feche a issue à mão, com um comentário citando o pull request (Resolvido em #15), ou ligue os dois pela barra lateral.

Fechei a issue errada

Abra a issue fechada (lista Closed) e use o botão de reabrir no fim da página. Nada se perde: os comentários continuam lá.

Não vejo a aba Issues

O dono do repositório desligou as issues nas configurações (alguns projetos usam outro sistema). Procure no README onde o projeto recebe relatos de erros.

Coloquei uma senha numa issue

Em repositório público, tudo o que está numa issue fica visível para o mundo e pode ser copiado em segundos. Apague o trecho, mas considere a senha vazada e troque-a imediatamente (veja Commitei uma Senha!).

Resumo

  • Issue é um cartão de tarefa do repositório no GitHub: bug, ideia, tarefa ou dúvida, com número, conversa e responsável. Não faz parte do Git.
  • Boa issue: título específico, o que acontece, passos para reproduzir, o que se esperava. Um assunto por issue; procure duplicadas antes.
  • Rótulos classificam, responsáveis dizem quem cuida, marcos agrupam numa meta; @nome avisa uma pessoa e #12 vira link.
  • Closes/Fixes/Resolves #12 no pull request ou na mensagem do commit fecha a issue quando o trabalho entra no branch padrão.
  • Issues e pull requests dividem a numeração do repositório.

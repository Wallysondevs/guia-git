Git Pull Request

Um pull request (muitas vezes abreviado PR) é um pedido que você faz no GitHub: "Bruno, por favor, puxe (pull) as mudanças do meu branch para o seu repositório". Ele não é um comando do Git: é uma página no site, com a descrição do que você mudou, as diferenças linha por linha, uma conversa e, no fim, um botão para juntar tudo. É o jeito padrão de contribuir com projetos de outras pessoas (depois de um fork) e também o jeito como muitas equipes trabalham no mesmo repositório.

Você vai aprender
  • O que é um pull request e o que acontece em cada etapa dele.
  • Como preparar o branch no terminal e enviá-lo, e o aviso real Create a pull request.
  • Como abrir o pull request no site (passo a passo da documentação oficial).
  • Como atualizar o pull request depois de um pedido de mudança: é só commitar e enviar de novo.
  • O que fazer no seu computador depois que o pull request é aceito.
O que é real e o que é ilustrativo nesta aula

Tudo o que acontece no site do GitHub (abrir o pull request, os botões, o merge) é ilustrativo: descrito conforme a documentação oficial, em docs.github.com. O site é em inglês; os nomes aparecem como estão nele, com a tradução ao lado. Todos os comandos rodaram de verdade no Git do Ubuntu, com o "GitHub de mentira" do laboratório do guia. Como o laboratório não tem a página do pull request, o merge do Bruno foi imitado com um git merge --no-ff no computador dele, com a mesma mensagem que o botão do GitHub usa.

A ideia: a sugestão por escrito

Lembra da Ana e do caderno da cantina do Bruno (aula Fork)? Ela escreveu a receita de sexta na cópia dela. Agora ela não chega dizendo "copia aí". Ela entrega uma folha de sugestão:

  • O que ela quer mudar (as páginas novas, marcadas);
  • Por que (um bilhete explicando);
  • um espaço para o Bruno comentar ("e quem não come carne?"), para ela ajustar e entregar de novo;
  • e, no fim, o Bruno aceita (copia para o caderno oficial) ou recusa.

O pull request é essa folha. Ele fica aberto enquanto a conversa acontece e, no fim, é mesclado (merged) ou fechado sem merge.

As etapas

  1. No terminal: branch novo, commits, git push do branch para o fork.
  2. No site: abrir o pull request, do branch do fork para o main do original.
  3. No site: revisão (aula Revisão de Código); se pedirem mudanças, volte ao passo 1 no mesmo branch.
  4. No site: quem cuida do repositório faz o merge.
  5. No terminal: atualize o seu main e apague o branch.

1. Preparando o branch (no terminal)

A Ana já tem o clone do fork, com o origin (o fork dela) e o upstream (o original do Bruno). Antes de começar, ela garante que o main está em dia com o original, e só então cria o branch da contribuição:

$ git switch main
Already on 'main'
Your branch is up to date with 'origin/main'.
$ git pull upstream main
From https://github.com/bruno-lima/cardapio
 * branch            main       -> FETCH_HEAD
Already up to date.
$ git switch -c receita-sexta
Switched to a new branch 'receita-sexta'
$ echo 'Sexta: pizza de calabresa' >> cardapio.txt
$ git commit -am 'Adiciona a sexta-feira'
[receita-sexta 9298686] Adiciona a sexta-feira
 1 file changed, 1 insertion(+)
  • git pull upstream main: busca o main do original e junta no main da Ana. Aqui, Already up to date ("já está atualizado"). A linha * branch main -> FETCH_HEAD diz que o branch buscado ficou guardado com o nome temporário FETCH_HEAD.
  • git switch -c receita-sexta: um branch só para esta contribuição, com um nome que diz o que ela é. Um pull request = um branch = um assunto.

O main tem de continuar sem a sexta. (No terminal do guia não há GitHub: o git push -u origin receita-sexta você faz no seu computador.)

2. Abrindo o pull request (no site, ilustrativo)

Conforme a documentação do GitHub, para um pull request a partir de um fork:

  1. Abra o repositório original (github.com/bruno-lima/cardapio). Logo depois do push, costuma aparecer uma faixa amarela acima da lista de arquivos com o botão Compare & pull request ("Comparar e criar pull request"). Clique nele (ou use o endereço que o git push mostrou).
  2. Se a página não estiver comparando o fork, clique em compare across forks ("comparar entre forks").
  3. Escolha para onde vão as mudanças: no menu base branch, o main do repositório do Bruno.
  4. Escolha de onde vêm: no menu head fork, o fork da Ana (ana-souza/cardapio); no menu compare branch, o receita-sexta.
  5. Escreva um título e uma descrição.
  6. Se quiser que o Bruno possa fazer pequenos ajustes direto no seu branch, deixe marcado Allow edits from maintainers ("Permitir edições dos mantenedores").
  7. Clique em Create Pull Request ("Criar pull request"). Para um PR que ainda não está pronto, a seta ao lado do botão oferece Create Draft Pull Request ("Criar pull request de rascunho"): um rascunho não pode ser mesclado até ser marcado como pronto.

Um bom título e uma boa descrição

O título segue as mesmas regras de uma boa mensagem de commit: curto, no imperativo, dizendo o que muda. A descrição responde o que o revisor vai querer saber:

Adiciona a sexta-feira ao cardápio

O cardápio parava na quinta. Esta mudança acrescenta a sexta-feira
com pizza de calabresa.

Como conferir: abrir o cardapio.txt e ver a última linha.

Closes #3

A última linha usa uma palavra-chave do GitHub: Closes #3 ("fecha a issue 3") faz a issue número 3 ser fechada sozinha quando o pull request for mesclado no branch padrão. Funcionam também close/closed, fix/fixes/fixed e resolve/resolves/resolved (conforme a documentação de issues).

O que tem na página do pull request

Segundo a documentação, a página tem quatro abas:

AbaO que mostra
Conversation ("Conversa")A descrição, a linha do tempo, os comentários e as revisões; no fim, o botão de merge
CommitsOs commits do branch, inclusive os que chegarem depois
Checks ("Verificações")Testes automáticos, quando o repositório tem (veja GitHub Actions)
Files changed ("Arquivos alterados")As diferenças linha por linha, como um git diff; é onde a revisão acontece

Rebase no branch do pull request?

Às vezes o dono do projeto pede "atualize o seu branch com o main" ou "junte os commits num só". Se você fizer isso com rebase, o push vai precisar de --force-with-lease. Isso é aceitável num branch de pull request que só você usa (veja A Regra de Ouro); se outra pessoa commitou no seu branch, prefira merge.

4. O merge (no site, ilustrativo)

Quando o Bruno está satisfeito, ele usa o botão de merge no fim da aba Conversation. Segundo a documentação, há três jeitos, escolhidos na setinha ao lado do botão:

Opção no siteO que faz no histórico
Create a merge commit (o botão Merge pull request)Junta todos os commits do branch com um commit de merge (como git merge --no-ff)
Squash and mergeJunta todos os commits do branch num commit só (veja squash)
Rebase and mergeRefaz cada commit em cima do branch de destino, com hashes novos (veja Rebase ou Merge?)

Depois de escolher, ele confirma (Confirm merge, "Confirmar merge"). O Bruno usou o merge comum. No laboratório, isso foi imitado no computador dele com um git merge --no-ff e a mensagem padrão do GitHub, Merge pull request #1 from ana-souza/receita-sexta, seguida de um push.

  2. O log --graph mostra o trabalho da Ana (9298686 e 790bbdf) dentro do histórico oficial, com o commit de merge do pull request.
  3. git push origin main: atualiza o main do fork.

Formas diferentes de fazer a mesma coisa

SituaçãoComo fica o pull request
Contribuir com o projeto de outra pessoaFork → branch no fork → PR do fork para o original (esta aula)
Equipe com permissão no mesmo repositórioSem fork: branch no próprio repositório (git push -u origin receita-sexta) → PR do branch para o main do mesmo repositório (veja O GitHub Flow)
Abrir o PR sem sair do terminalgh pr create, do GitHub CLI (ilustrativo)
O trabalho ainda não está pronto, mas você quer mostrarCreate Draft Pull Request (rascunho)
Pediram ajustesNovos commits no mesmo branch + git push; o PR se atualiza

Quando dá errado

fatal: The current branch … has no upstream branch.

O primeiro git push de um branch novo (seção 1). Como resolver: git push -u origin NOME-DO-BRANCH, como o próprio Git sugere. Se quiser que o Git faça isso sozinho sempre, a dica cita a configuração push.autoSetupRemote (git config --global push.autoSetupRemote true; veja Configurações Úteis).

Fiz os commits no main, e não num branch

O pull request funciona mesmo assim (do main do fork para o main do original), mas fica difícil: enquanto ele está aberto, o seu main não pode receber as novidades do original sem misturar, e você não consegue começar outra contribuição separada. Como resolver antes do push: crie o branch onde você está (git branch receita-sexta), volte o main para o original (git reset --hard upstream/main; veja git reset) e vá para o branch (git switch receita-sexta). Os commits ficam no branch.

O pull request mostra commits que não são meus

O que aconteceu: o seu branch foi criado de um main desatualizado, ou de outro branch. Como confirmar: git log --oneline upstream/main..HEAD lista só os commits que o seu branch tem a mais que o original (depois de um git fetch upstream). Como evitar: sempre git switch main + git pull upstream main antes do git switch -c.

O site avisa que o pull request tem conflitos

O site avisa (ilustrativo) quando o main do original mudou nas mesmas linhas que o seu branch, e o merge pelo botão fica bloqueado. Como resolver no terminal: no seu branch, git fetch upstream e git merge upstream/main; resolva os conflitos como em Resolvendo Conflitos, commite e dê git push. O pull request se atualiza e o aviso some.

Resumo

  • Um pull request é um pedido, no site do GitHub, para juntar as mudanças de um branch em outro, com descrição, diferenças, conversa e revisão.
  • No terminal: main em dia, git switch -c NOME, commits, git push -u origin NOME. O GitHub responde com o endereço para criar o PR.
  • No site: Compare & pull request, base = main do original, head = o seu branch, título e descrição, Create Pull Request.
  • Ajustes pedidos: mais commits no mesmo branch e git push.
  • Depois do merge: git pull upstream main, git push origin main, git branch -d e git push origin --delete.

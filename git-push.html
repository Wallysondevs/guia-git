Git push

Até aqui, todos os commits da Ana moram só no notebook dela. Se o notebook cair no chão, o histórico vai junto; e o Bruno, que trabalha com ela no site de receitas, não vê nada. O git push (em inglês, "empurrar") é o comando que envia os seus commits para o repositório remoto, por exemplo no GitHub, onde ficam guardados e onde os colegas podem buscá-los.

Você vai aprender
  • O que o git push envia (e o que ele não envia).
  • Como fazer o primeiro push com -u e por que, depois dele, basta digitar git push.
  • O que quer dizer cada linha da saída: Enumerating objects, To, * [new branch], main -> main.
  • Como enviar um branch novo e uma tag.
  • Os erros mais comuns do push e como sair de cada um.

A ideia antes do comando

Pense num álbum de fotos da família guardado na casa da avó. Você tira fotos no celular (os commits, feitos no seu computador) e, de vez em quando, leva as novas para colar no álbum (o remoto). Levar as fotos é o push. Três detalhes dessa comparação valem para o Git:

  • Você só leva fotos já reveladas: o push envia commits. Arquivo modificado e não commitado, ou só preparado com git add, fica no seu computador.
  • Você não leva o álbum inteiro de novo: o Git envia só o que o remoto ainda não tem.
  • Se alguém colou fotos novas no álbum depois da sua última visita, você precisa vê-las antes de colar as suas (é o push rejeitado).
Notebook da Ana                    GitHub (origin)
A---B---C---D   main     push →    A---B   main
                                   (recebe C e D)

Nesta aula, a Ana já tem o repositório receitas no notebook e um remoto chamado origin (veja git remote e git clone). O "GitHub" dos exemplos é um servidor de treino do laboratório do guia: as mensagens do Git são as mesmas de um push para o GitHub de verdade.

A forma completa: git push origin main

git
O programa Git.
push
O subcomando: "envie meus commits".
origin
Para onde: o nome do remoto. origin é o nome que o git clone dá (e o que todo tutorial usa no git remote add).
main
O quê: o branch que vai ser enviado. O Git envia os commits do seu main para o main de lá.

O primeiro push, com -u

A Ana criou o repositório no notebook, fez dois commits e cadastrou o remoto. Antes de enviar, ela confere o que tem:

$ git log --oneline
4f68d0e (HEAD -> main) Adiciona receita de bolo        « dois commits, só no notebook
0e8cf93 Adiciona README
$ git remote -v
origin  https://github.com/ana-souza/receitas.git (fetch)     « o remoto já está cadastrado
origin  https://github.com/ana-souza/receitas.git (push)
$ git status
No ramo main
nothing to commit, working tree clean                  « nenhuma palavra sobre o remoto (ainda)

O repositório no GitHub foi criado vazio (veja Criando um Repositório no GitHub). Agora, o envio:

$ git push -u origin main
Enumerating objects: 6, done.
Counting objects: 100% (6/6), done.
Delta compression using up to 4 threads
Compressing objects: 100% (3/3), done.
Writing objects: 100% (6/6), 504 bytes | 504.00 KiB/s, done.

 * [new branch]      main -> main                            « o branch main foi criado lá
branch 'main' set up to track 'origin/main'.                  « efeito do -u
$ git status
No ramo main
Your branch is up to date with 'origin/main'.                 « linha nova!

nothing to commit, working tree clean
Por que tanta coisa em inglês? O Git do Ubuntu sai em português quando o sistema está em português, mas a tradução que o Ubuntu usa não está completa (e às vezes cai no português de Portugal, como em "submissão"): muitas mensagens, sobretudo as do push, continuam em inglês. Em outros sistemas (Windows, macOS) as frases podem ser diferentes ou todas em inglês. É exatamente isso que você vai ver no seu terminal, e o guia mostra as mensagens como elas saem. Com o sistema em inglês, tudo sai em inglês (por exemplo, No ramo main vira On branch main).

A saída, linha por linha

LinhaO que quer dizer
Enumerating objects: 6, done."Contando os objetos": o Git listou o que precisa ir. Dois commits viram 6 objetos (cada commit, cada pasta e cada arquivo é um objeto; veja Como o Git Guarda as Coisas).
Counting objects, Delta compression, Compressing objectsPreparação do pacote: o Git compacta os objetos para gastar menos internet. "using up to 4 threads" = usou até 4 núcleos do processador (o número muda de computador para computador).
Writing objects: 100% (6/6), 504 bytesO envio de verdade: 6 objetos, 504 bytes ao todo. Num projeto grande, você vê a porcentagem subindo.
Total 6 (delta 0), reused 0 …Estatística do pacote. Pode ignorar.
To https://github.com/ana-souza/receitas.gitPara onde foi ("To" = "para").
* [new branch] main -> mainO asterisco e o [new branch] dizem que o branch não existia lá e foi criado. main -> main = "o meu main foi para o main de lá".
branch 'main' set up to track 'origin/main'."O branch main agora acompanha o origin/main": é o -u trabalhando.

E o git status ganhou uma linha: Your branch is up to date with 'origin/main', "seu branch está em dia com o origin/main". O origin/main é a lembrança que o seu Git guarda de como estava o main do GitHub na última conversa entre os dois.

Para que serve o -u? O -u (forma longa: --set-upstream) liga o seu main ao main do origin. O Git anota que eles são um par. É ele que permite, daqui para a frente, digitar só git push e git pull, sem dizer para onde, e faz o git status contar quantos commits você está à frente ou atrás. O assunto tem aula própria: Branch de Rastreamento (upstream).

Os próximos pushes: só git push

A Ana escreve uma receita nova e faz o commit. O git status avisa que ela tem algo que o remoto ainda não tem:

$ printf 'Pudim\n- 1 lata de leite condensado\n' > pudim.txt
$ git add pudim.txt
$ git commit -m 'Adiciona receita de pudim'
[main b830dc1] Adiciona receita de pudim

$ git status
No ramo main
Seu ramo está à frente de 'origin/main' por 1 submissão.      « 1 commit que o GitHub não tem
  (use "git push" to publish your local commits)              « a dica: use git push

nothing to commit, working tree clean

"Submissão" é a palavra que a tradução do Git usa para commit. A dica em inglês diz: "use git push para publicar seus commits locais". Como o main já está ligado ao origin/main, não precisa dizer para onde:

$ git push
Enumerating objects: 4, done.
Counting objects: 100% (4/4), done.
Delta compression using up to 4 threads
Compressing objects: 100% (2/2), done.
Writing objects: 100% (3/3), 346 bytes | 346.00 KiB/s, done.
Total 3 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
To https://github.com/ana-souza/receitas.git
   4f68d0e..b830dc1  main -> main                « o main de lá andou de 4f68d0e para b830dc1
$ git status
No ramo main
Your branch is up to date with 'origin/main'.          « em dia de novo

nothing to commit, working tree clean

Repare na diferença: desta vez não há * [new branch], porque o branch já existia lá. No lugar, aparece 4f68d0e..b830dc1: "o main do GitHub estava no commit 4f68d0e e agora está no b830dc1". Só foram 3 objetos (o commit novo, a pasta e o pudim.txt): o Git não reenviou o que o GitHub já tinha.

Push sem nada novo: Everything up-to-date

$ git push
Everything up-to-date                                  « "tudo em dia": nada para enviar

Não é erro: o Git só avisa que o GitHub já tem todos os seus commits.

Antes e depois: o que o push muda (e o que não muda)

A pegadinha mais comum de quem começa: mudar um arquivo, dar git push e achar que mandou. Veja a Ana acrescentando um ingrediente ao bolo sem commitar:

$ echo '- 2 xícaras de farinha' >> bolo.txt
$ git push
Everything up-to-date                                  « nada foi enviado!
$ git status
No ramo main
Your branch is up to date with 'origin/main'.

  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")

O push enviou... nada. A farinha não é um commit: está só na pasta de trabalho. Para ela ir, é o caminho de sempre: git add, git commit e depois git push.

Enviando um branch novo

O push envia um branch por vez, e cada branch novo precisa do seu primeiro push com -u. A Ana cria o branch salgados para testar receitas novas sem mexer no main (veja git switch) e tenta enviar:

$ git switch -c salgados
Switched to a new branch 'salgados'
$ printf 'Coxinha\n- 500 g de frango\n' > coxinha.txt
$ git add coxinha.txt
$ git commit -qm 'Adiciona receita de coxinha'
$ git push
fatal: The current branch salgados has no upstream branch.          « o branch não tem par lá
To push the current branch and set the remote as upstream, use

    git push --set-upstream origin salgados                         « o comando pronto

To have this happen automatically for branches without a tracking
upstream, see 'push.autoSetupRemote' in 'git help config'.

Traduzindo: "o branch atual, salgados, não tem branch upstream (um par no remoto). Para enviar o branch atual e definir o remoto como upstream, use git push --set-upstream origin salgados". O Git até escreveu o comando. --set-upstream é a forma longa do -u:

$ git push -u origin salgados
Enumerating objects: 4, done.
Counting objects: 100% (4/4), done.
Delta compression using up to 4 threads
Compressing objects: 100% (2/2), done.
Writing objects: 100% (3/3), 370 bytes | 370.00 KiB/s, done.
Total 3 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
remote:                                                               « linhas "remote:" = recado do servidor
remote: Create a pull request for 'salgados' on GitHub by visiting:
remote:      https://github.com/ana-souza/receitas/pull/new/salgados
remote:
To https://github.com/ana-souza/receitas.git
 * [new branch]      salgados -> salgados
branch 'salgados' set up to track 'origin/salgados'.
$ git branch -vv
  main     b830dc1 [origin/main] Adiciona receita de pudim
* salgados 47962c1 [origin/salgados] Adiciona receita de coxinha     « cada branch com o seu par

As linhas que começam com remote: não são do seu Git: são um recado do servidor. Aqui o GitHub oferece um link para abrir um pull request com o branch novo. O git branch -vv mostra, entre colchetes, o par de cada branch.

Enviando tags

As tags (etiquetas de versão) não vão com o git push normal: é preciso pedir. A Ana marca a versão 1.0 do site e envia a tag pelo nome:

$ git switch -q main
$ git tag v1.0
$ git push origin v1.0
Total 0 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)     « 0 objetos: o commit já estava lá
To https://github.com/ana-souza/receitas.git
 * [new tag]         v1.0 -> v1.0                                  « a tag foi criada lá
$ git push --tags
Everything up-to-date                                              « nenhuma tag nova para enviar

git push --tags envia todas as tags que o remoto ainda não tem. É prático, mas manda junto qualquer tag de teste esquecida; por isso, prefira enviar pelo nome.

Quando dá errado

"The current branch … has no upstream branch"

O que aconteceu: é o primeiro push deste branch, e ele não tem par no remoto. O Git não sabe para onde mandar.

Como resolver: rode o comando que a mensagem sugere: git push -u origin NOME-DO-BRANCH (ou git push --set-upstream origin NOME-DO-BRANCH). Exemplo completo em "Enviando um branch novo", acima.

"src refspec main does not match any" 
$ git init -q lojinha && cd lojinha
$ git remote add origin https://github.com/ana-souza/lojinha.git
$ git push -u origin main
error: src refspec main does not match any
error: failed to push some refs to 'https://github.com/ana-souza/lojinha.git'

O que aconteceu: "a origem main não corresponde a nada": no seu repositório não existe nenhum branch chamado main. Duas causas: (1) o repositório ainda não tem commit (o main só passa a existir no primeiro commit), como acima; (2) você digitou o nome errado, como em git push origin mian, ou o seu branch se chama master.

$ git push origin mian
error: src refspec mian does not match any
error: failed to push some refs to 'https://github.com/ana-souza/receitas.git'

Como confirmar: git log --oneline (tem commit?) e git branch (qual é o nome do branch?).

Como resolver: faça o primeiro commit, ou use o nome que aparece no git branch.

"'orign' does not appear to be a git repository" 
$ git push orign main
fatal: 'orign' does not appear to be a git repository
fatal: Could not read from remote repository.

Please make sure you have the correct access rights
and the repository exists.

O que aconteceu: "orign não parece ser um repositório git": não há remoto com esse nome (aqui, um erro de digitação de origin). A segunda parte, "não foi possível ler do repositório remoto; confira se você tem permissão e se o repositório existe", é genérica e aparece em vários erros.

Como confirmar: git remote -v lista os nomes que existem. Se não listar nada, o repositório ainda não tem remoto: cadastre com git remote add origin URL.

"Repository not found" 
$ git push https://github.com/ana-souza/receita.git main
remote: Repository not found.
fatal: repository 'https://github.com/ana-souza/receita.git/' not found

O que aconteceu: o endereço está errado (aqui, receita sem o "s"), o repositório não foi criado no GitHub, ou é privado e você não tem acesso a ele.

Como resolver: confira o endereço na página do repositório e corrija o remoto com git remote set-url origin URL-CERTA (veja git remote).

"! [rejected] … (fetch first)" 
$ git push
To https://github.com/ana-souza/receitas.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/ana-souza/receitas.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

O que aconteceu: o Bruno enviou um commit para o main depois da última vez que a Ana conversou com o GitHub. O remoto tem trabalho que ela não tem, e o Git se recusa a apagá-lo.

Como resolver: git pull (traz e junta o trabalho do Bruno) e depois git push de novo. Não use git push --force: ele apagaria o commit do Bruno. O passo a passo completo está em Push Rejeitado: o que Fazer.

O terminal pede usuário e senha, e a senha não funciona

O que aconteceu: no GitHub de verdade, o push precisa provar quem você é, e a senha da conta não é aceita pelo terminal. (Ilustrativo: o servidor de treino do guia não pede senha.)

Como resolver: configure uma chave SSH ou um token de acesso.

Resumo

  • git push envia commits para o remoto; mudanças não commitadas ficam no seu computador.
  • O primeiro push de cada branch: git push -u origin NOME. Depois, basta git push.
  • Na saída, To diz para onde foi, * [new branch] que o branch foi criado lá e a1b2c3d..e4f5g6h main -> main de qual commit a qual o branch remoto andou.
  • Everything up-to-date = não havia nada novo para enviar (você esqueceu o commit?).
  • Push rejeitado não é o fim do mundo: traga o trabalho dos outros com git pull e envie de novo. Nunca use --force num branch compartilhado.

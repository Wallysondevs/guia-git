Git Rebase Interativo (-i)

O git commit --amend (aula Corrigindo o Último Commit) conserta só o último commit. E se o erro de digitação estiver na mensagem de três commits atrás? E se você fez um commit "teste" que não devia existir, ou quer trocar a ordem de dois commits? Para isso existe o rebase interativo, git rebase -i: o Git abre no editor uma lista de tarefas com os seus commits, você escreve o que quer fazer com cada um, salva, e ele refaz o histórico seguindo a lista.

Você vai aprender
  • Abrir o rebase interativo (git rebase -i main ou git rebase -i HEAD~3) e ler a lista que aparece no editor.
  • O que faz cada comando da lista: pick, reword, edit, squash, fixup, drop (e exec, break).
  • Apagar um commit, corrigir uma mensagem antiga, trocar a ordem e parar num commit para emendá-lo.
  • Os erros mais comuns: comando digitado errado, lista vazia, rebase sem dizer a base.

Todos os comandos rodaram no Git 2.53 da máquina da Ana (usuária ana, computador notebook), com o sistema em português. A lista do rebase interativo e várias mensagens dele saem em inglês (não há tradução no Git do Ubuntu): tudo está traduzido no texto. Para colher as saídas, o laboratório usou um truque explicado na seção 7: em vez de abrir o editor, a lista foi mostrada (GIT_SEQUENCE_EDITOR=cat) ou editada por um comando (sed).

A ideia: arrumar o álbum de fotos antes de mostrar

Depois de uma viagem, você tem 40 fotos no celular. Antes de mandar para a família, você arruma o álbum: apaga a foto tremida, junta as três fotos repetidas do mesmo prato numa só, corrige uma legenda, troca a ordem para contar a viagem do começo ao fim. As fotos boas continuam lá; o álbum só fica mais fácil de entender.

O rebase interativo é a arrumação do álbum. Você faz commits pequenos e bagunçados enquanto trabalha (o que é ótimo!) e, antes de compartilhar, arruma a sequência. Como todo rebase, ele cria commits novos (hashes novos), então vale a regra: só arrume o que ainda não foi enviado (aula A Regra de Ouro).

1. A situação: o branch doces bagunçado

A Ana fez quatro commits no branch doces, a partir do main:

$ git log --oneline
bf43330 Acrescenta a calda do pudim
b46ad5f Adiciona receita de brigadeiro
c55f4ed teste                                 « um commit de teste que não devia ficar
0c2cdd3 Adiciona recita de pudim              « "recita": erro de digitação
8bf5d5b Adiciona receita de bolo              « o main: a base

Três problemas: o commit teste não devia existir, a mensagem do pudim tem um erro de digitação, e a calda do pudim ficaria melhor logo depois do pudim, não depois do brigadeiro.

2. Abrindo o rebase interativo e lendo a lista

$ git rebase -i main
git rebase
O rebase (aula git rebase).
-i
De interactive, "interativo": antes de refazer os commits, o Git mostra a lista e deixa você decidir.
main
A base. O Git lista os commits que estão no branch atual e não estão no main: os quatro do doces. A base continua a mesma; só os commits depois dela são refeitos.

O editor do Git (no Ubuntu da Ana, o nano) abre com este texto, gerado pelo Git:

pick 0c2cdd3 # Adiciona recita de pudim
pick c55f4ed # teste
pick b46ad5f # Adiciona receita de brigadeiro
pick bf43330 # Acrescenta a calda do pudim

# Rebase 8bf5d5b..bf43330 onto 8bf5d5b (4 commands)
#
# Commands:
# p, pick <commit> = use commit
# r, reword <commit> = use commit, but edit the commit message
# e, edit <commit> = use commit, but stop for amending
# s, squash <commit> = use commit, but meld into previous commit
# f, fixup [-C | -c] <commit> = like "squash" but keep only the previous
#                    commit's log message, unless -C is used, in which case
#                    keep only this commit's message; -c is same as -C but
#                    opens the editor
# x, exec <command> = run command (the rest of the line) using shell
# b, break = stop here (continue rebase later with 'git rebase --continue')
# d, drop <commit> = remove commit
# l, label <label> = label current HEAD with a name
# t, reset <label> = reset HEAD to a label
# m, merge [-C <commit> | -c <commit>] <label> [# <oneline>]
#         create a merge commit using the original merge commit's
#         message (or the oneline, if no original merge commit was
#         specified); use -c <commit> to reword the commit message
# u, update-ref <ref> = track a placeholder for the <ref> to be updated
#                       to this position in the new commits. The <ref> is
#                       updated at the end of the rebase
#
# These lines can be re-ordered; they are executed from top to bottom.
#
# If you remove a line here THAT COMMIT WILL BE LOST.
#
# However, if you remove everything, the rebase will be aborted.
#

Lendo a lista

  • As linhas de cima são as tarefas, uma por commit: o comando (pick), o hash curto e, depois do #, a mensagem (só para você se achar).
  • A ordem é do mais antigo para o mais novo, ao contrário do git log. A lista é uma receita executada de cima para baixo ("These lines can be re-ordered; they are executed from top to bottom": "estas linhas podem ser reordenadas; são executadas de cima para baixo").
  • # Rebase 8bf5d5b..bf43330 onto 8bf5d5b (4 commands): "rebase dos commits depois do 8bf5d5b até o bf43330, sobre o 8bf5d5b (4 tarefas)". A base não muda: o objetivo aqui é arrumar, não mudar de base.
  • Tudo o que começa com # é comentário: o Git ignora.
  • Os três avisos do fim: "se você apagar uma linha aqui, AQUELE COMMIT SERÁ PERDIDO"; "mas, se você apagar tudo, o rebase será cancelado".

Os comandos, um por um

Comando (e atalho)O que o Git dizEm português
pick (p)use commit"Pegar": usa o commit como está. É o padrão de todas as linhas.
reword (r)use commit, but edit the commit message"Reescrever": usa o commit, mas abre o editor para você mudar a mensagem.
edit (e)use commit, but stop for amending"Editar": usa o commit e para logo depois, para você emendá-lo (mudar arquivos, dividir em dois…).
squash (s)use commit, but meld into previous commit"Espremer": funde este commit no da linha de cima e abre o editor para você escrever a mensagem do commit juntado (aula squash).
fixup (f)like "squash" but keep only the previous commit's log message"Consertar": igual ao squash, mas joga fora a mensagem deste commit e fica só com a de cima, sem abrir o editor (com -C, fica com a deste).

exec (x)run command … using shellRoda um comando do terminal naquele ponto (por exemplo, os testes do projeto).

Para usar um comando, troque a palavra pick do começo da linha (pode usar o atalho de uma letra), salve e feche o editor (no nano: Ctrl+O, Enter, Ctrl+X). Se você fechar sem mudar nada, todos são pick: o Git refaz tudo igual e responde Successfully rebased and updated refs/heads/doces. sem mudar nenhum hash.

3. drop: apagando o commit "teste"

A Ana troca o pick da linha do teste por drop, salva e fecha:

pick 0c2cdd3 # Adiciona recita de pudim
drop c55f4ed # teste
pick b46ad5f # Adiciona receita de brigadeiro
pick bf43330 # Acrescenta a calda do pudim

$ git rebase -i main
Rebasing (3/4)Rebasing (4/4)Successfully rebased and updated refs/heads/doces.
$ git log --oneline
b023d49 Acrescenta a calda do pudim           « hash novo
b5d1e50 Adiciona receita de brigadeiro        « hash novo
0c2cdd3 Adiciona recita de pudim              « o MESMO hash
8bf5d5b Adiciona receita de bolo
$ ls

  • O commit teste sumiu, e o arquivo teste.txt, que só ele criava, também.
  • O progresso começou em (3/4): as tarefas 1 e 2 não precisaram refazer nada. O commit do pudim ficou igual (0c2cdd3), porque nada antes dele mudou; o Git só o reaproveitou. Já os dois de cima têm pai novo e, por isso, hashes novos.
  • Num terminal, o contador Rebasing (3/4)… se apaga, e sobra só o Successfully rebased….

Apagar a linha inteira tem o mesmo efeito do drop ("se você apagar uma linha aqui, aquele commit será perdido"). O drop é melhor porque deixa claro que foi de propósito.

Missão: apague o commit teste do branch doces com um rebase interativo sobre o main (troque o pick dele por drop). Se o editor não abrir no terminal do guia, use o jeito sem editor da seção 7: GIT_SEQUENCE_EDITOR='sed -i /teste/s/^pick/drop/' git rebase -i main. Confira com git log --oneline e ls.

5. Trocando a ordem

Para mudar a ordem, basta mudar a ordem das linhas. A Ana sobe a calda para logo depois do pudim:

pick 31f4dad # Adiciona receita de pudim
pick 9d5bd3d # Acrescenta a calda do pudim
pick 123c8e8 # Adiciona receita de brigadeiro

$ git rebase -i main
Rebasing (2/3)Rebasing (3/3)Successfully rebased and updated refs/heads/doces.
$ git log --oneline
235db56 Adiciona receita de brigadeiro
9280e8c Acrescenta a calda do pudim
31f4dad Adiciona receita de pudim
8bf5d5b Adiciona receita de bolo

Agora o histórico conta a história na ordem certa: o pudim, a calda dele, depois o brigadeiro. Trocar a ordem só funciona sem conflito quando os commits mexem em coisas diferentes (aqui, arquivos diferentes). Se dois commits mudam a mesma linha, trocar a ordem pode dar conflito: resolva como na aula Conflitos no Rebase.

6. edit: parar num commit para emendá-lo

A Ana percebe que a receita de brigadeiro ficou sem os ingredientes. Em vez de fazer um commit novo "esqueci os ingredientes", ela quer pôr os ingredientes dentro do commit do brigadeiro. Ela marca a linha com edit:

pick 31f4dad # Adiciona receita de pudim
pick 9280e8c # Acrescenta a calda do pudim
edit 235db56 # Adiciona receita de brigadeiro

"Parei no 235db56. Você pode emendar o commit agora, com git commit --amend. Quando estiver satisfeita, rode git rebase --continue." O rebase está pausado logo depois do commit do brigadeiro. A Ana acrescenta os ingredientes e emenda o commit (aula --amend):

$ echo 'Leite condensado, chocolate e manteiga' >> brigadeiro.txt
$ git add brigadeiro.txt
$ git commit --amend --no-edit
[detached HEAD 6ce862f] Adiciona receita de brigadeiro

O --no-edit mantém a mensagem. O commit do brigadeiro agora cria o arquivo já com os ingredientes, como se tivesse sido feito certo da primeira vez. Se houvesse commits depois dele, o --continue os refaria em cima.

Com git rebase -i HEAD~2, a lista mostra só os dois últimos commits (aqui, antes da arrumação):

pick b46ad5f # Adiciona receita de brigadeiro
pick bf43330 # Acrescenta a calda do pudim

A variável GIT_SEQUENCE_EDITOR diz ao Git qual programa usar para a lista; a GIT_EDITOR, qual usar para as mensagens (o reword e o squash). Escritas antes do comando, na mesma linha, valem só para aquele comando.

Quando dá errado

Rodou git rebase -i sem dizer a base 
$ git rebase -i
There is no tracking information for the current branch.
Please specify which branch you want to rebase against.
See git-rebase(1) for details.

    git rebase '<branch>'

If you wish to set tracking information for this branch you can do so with:

    git branch --set-upstream-to=<remote>/<branch> doces

"Não há informação de rastreamento para o branch atual. Diga sobre qual branch fazer o rebase." Sem argumento, o Git usa o branch remoto que o seu branch acompanha (aula upstream), e o doces não acompanha nenhum. Como resolver: diga a base: git rebase -i main ou git rebase -i HEAD~3.

Escreveu o comando errado na lista 
$ git rebase -i main
error: invalid command 'pik'
error: invalid line 1: pik 31f4dad # Adiciona receita de pudim
error: invalid command 'pik'
error: invalid line 2: pik 9280e8c # Acrescenta a calda do pudim
error: invalid command 'pik'
error: invalid line 3: pik 6ce862f # Adiciona receita de brigadeiro
You can fix this with 'git rebase --edit-todo' and then run 'git rebase --continue'.
Or you can abort the rebase with 'git rebase --abort'.

"Comando inválido: pik", com o número de cada linha errada. O rebase fica em andamento, esperando (o git status mostra interactive rebase in progress). Como resolver: "conserte com git rebase --edit-todo" (que reabre a lista no editor) "e rode git rebase --continue", ou desista com git rebase --abort.

Apagou todas as linhas 
$ git rebase -i main
error: nothing to do

"Nada a fazer": como a própria lista avisa, apagar tudo cancela o rebase. Nenhum commit foi apagado; o git log continua igual. (Para apagar todos os commits do branch de verdade, use drop em cada linha.)

Apagou o commit errado com drop

O commit some do branch, mas não do Git, por enquanto: ele aparece no git reflog (aula git reflog). Logo depois do rebase, o atalho ORIG_HEAD aponta para onde o branch estava antes, e git reset --hard ORIG_HEAD volta tudo (aula git reset; cuidado: o --hard descarta mudanças não commitadas). A aula Recuperando Commits Perdidos mostra o caminho completo.

Parou com conflito

Ao trocar a ordem ou apagar commits, um commit seguinte pode depender do que mudou e dar conflito. É o mesmo procedimento da aula Conflitos no Rebase: resolva, git add, git rebase --continue; ou git rebase --abort para voltar ao começo.

Resumo

  • git rebase -i main (ou HEAD~N) abre no editor a lista de tarefas: um pick por commit, do mais antigo ao mais novo, executada de cima para baixo.
  • Troque o pick por reword (mensagem), edit (parar e emendar), squash/fixup (fundir no de cima), drop (apagar); mude a ordem das linhas para mudar a ordem dos commits.
  • Salve e feche o editor para o Git executar. Apagar todas as linhas cancela (error: nothing to do).
  • Os commits refeitos ganham hashes novos: arrume só o que ainda não foi compartilhado.
  • Se algo parar: git status mostra onde; --continue segue, --abort volta ao começo, --edit-todo reabre a lista.

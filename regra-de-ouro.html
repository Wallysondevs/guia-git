Git A Regra de Ouro

Nas últimas aulas você aprendeu a reescrever o histórico: corrigir o último commit com --amend, refazer commits com rebase, juntar vários com squash, voltar no tempo com reset. São ferramentas ótimas, com uma condição que todo mundo que usa Git aprende (às vezes do jeito difícil): não reescreva commits que outras pessoas já baixaram. Esta aula mostra, com o Git real, o que acontece com o colega quando essa regra é quebrada, e o que fazer no lugar.

Você vai aprender
  • A regra de ouro e quais comandos "reescrevem" o histórico.
  • Por que o git push recusa um histórico reescrito, e o que o --force faz.
  • O que o colega vê depois: push recusado, branches divergentes e um conflito num arquivo que ele nem tocou.
  • Como o colega sai dessa com git pull --rebase.
  • O que fazer no lugar: um commit novo de correção, ou git revert.

Todas as sessões desta aula rodaram no Git real do Ubuntu, com o "GitHub de mentira" do laboratório do guia: a Ana (ana@notebook) e o Bruno (bruno@notebook, o computador dele) trabalham no mesmo repositório ana-souza/receitas. As mensagens saem em português, mas a tradução do Git não cobre todas as frases: as que aparecem em inglês saíram assim mesmo.

A ideia: o caderno da turma

A turma da Ana tem um caderno de receitas que passa de mão em mão. Cada um copia o caderno inteiro para casa e continua escrevendo na sua cópia. Um dia, a Ana percebe um erro na página 3, que ela mesma escreveu. Ela tem duas opções:

  • Arrancar a página 3 e colar uma nova no lugar. No caderno dela fica bonito. Mas o Bruno já tinha copiado a página 3 antiga e escrito a página 4 logo depois. Agora o caderno do Bruno e o da Ana não batem mais: a página 3 dele é diferente da dela, e ninguém sabe qual é "a certa" sem comparar linha por linha.
  • Escrever uma página nova: "Correção da página 3: onde se lê leiet, leia leite". Nada do que os outros copiaram muda. Quem atualizar a cópia só ganha uma página a mais.

Arrancar a página é reescrever o histórico. Enquanto o caderno é só seu, você arranca o que quiser. Depois que outras pessoas copiaram, escreva páginas novas.

A regra de ouro

Não reescreva commits que já foram enviados para um repositório compartilhado e que outras pessoas podem ter baixado. Para corrigir o que já é público, faça um commit novo.

O que conta como "reescrever"

Reescrever é qualquer coisa que troca commits existentes por outros (com hashes novos) ou tira commits do branch. Lembre de O Hash do Commit: mudar qualquer coisa num commit (a mensagem, um arquivo, o pai) cria outro commit, com outro hash.

Reescreve o históricoNão reescreve (só acrescenta)
git commit --amend (troca o último commit)git commit
git rebase e git rebase -i (refaz commits; squash, reword, drop…)git merge
git reset para um commit anterior (tira commits do branch)git revert (desfaz com um commit novo)
git push --force depois de qualquer um dessesgit cherry-pick (cria cópias novas, não troca as antigas)

Os comandos da esquerda são seguros enquanto os commits só existem no seu computador. O problema começa quando o commit reescrito já estava no GitHub.

1. A situação

A Ana enviou a receita de pudim para o GitHub, com um erro de digitação ("leiet"). O Bruno clonou o repositório e começou a trabalhar em cima: commitou a receita de brigadeiro no computador dele, mas ainda não enviou.

$ git log --oneline
14fffbd Adiciona a receita de pudim
c34349b Adiciona a receita de bolo
700bbd5 Cria o README

$ git log --oneline
52e2dc5 Adiciona a receita de brigadeiro
14fffbd Adiciona a receita de pudim
c34349b Adiciona a receita de bolo
700bbd5 Cria o README

O primeiro terminal é o da Ana; o segundo, o do Bruno. Os três commits de baixo são os mesmos nos dois computadores (mesmos hashes), e o 52e2dc5 do Bruno foi feito em cima do 14fffbd da Ana:

GitHub e Ana:   A---B---P
Bruno:          A---B---P---G

(P = pudim, G = brigadeiro.)

2. A Ana reescreve um commit que já era público

A Ana viu o "leiet" e, em vez de fazer um commit de correção, preferiu deixar o histórico "limpo": corrigiu o arquivo e trocou o último commit com --amend (o -a prepara o arquivo mudado; o --no-edit mantém a mesma mensagem):

$ sed -i 's/leiet/leite/' pudim.txt
$ git commit -q -a --amend --no-edit
$ git log --oneline
fa7fe1f Adiciona a receita de pudim             « hash novo: o 14fffbd sumiu do branch
c34349b Adiciona a receita de bolo
700bbd5 Cria o README
$ git status
No ramo main
O seu branch e 'origin/main' divergiram-se,
e cada um tem 1 e 1 submissões, respectivamente.
  (use "git pull" if you want to integrate the remote branch with yours)

nothing to commit, working tree clean

O status já avisa: o branch da Ana e o origin/main (o que o GitHub tem) divergiram: cada um tem 1 commit que o outro não tem. Do ponto de vista do Git, o fa7fe1f não é "o mesmo commit corrigido"; é outro commit, e o 14fffbd que está no GitHub ficou sem par.

GitHub:   A---B---P       (P = 14fffbd, com "leiet")
Ana:      A---B---P'      (P' = fa7fe1f, com "leite")

O push recusa

$ git push
To https://github.com/ana-souza/receitas.git
 ! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs to 'https://github.com/ana-souza/receitas.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart. If you want to integrate the remote changes,
hint: use 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.
! [rejected] main -> main (non-fast-forward)
"Recusado: não é avanço rápido". O GitHub só aceita um push que acrescenta commits depois do que ele já tem. O branch da Ana não tem o 14fffbd, então aceitar o push faria esse commit sumir do GitHub.
error: failed to push some refs…
"Falhou ao enviar algumas referências" (aqui, o branch main). Nada foi enviado.
hint: Updates were rejected…
"As atualizações foram recusadas porque a ponta do seu branch está atrás da do remoto. Se quiser integrar as mudanças de lá, use git pull antes de enviar de novo." O Git não sabe que foi um --amend; ele só vê que falta um commit.

Essa recusa é o Git protegendo o histórico compartilhado. É aqui que a tentação aparece: "e se eu forçar?".

O --force passa por cima

$ git push --force
To https://github.com/ana-souza/receitas.git
 + 14fffbd...fa7fe1f main -> main (forced update)

O + no começo e o (forced update) ("atualização forçada") dizem que o main do GitHub foi trocado: antes apontava para o 14fffbd, agora aponta para o fa7fe1f. Repare nos três pontos (...) entre os hashes: num push normal são dois (.., "de … até …"); três pontos indicam que um não é continuação do outro. No computador da Ana, tudo parece resolvido. O problema agora é do Bruno.

3. O que acontece com o Bruno

O Bruno terminou o brigadeiro e foi enviar:

$ git push
To https://github.com/ana-souza/receitas.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/ana-souza/receitas.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

Recusado com (fetch first), "busque primeiro": "o remoto tem trabalho que você não tem; normalmente é outra pessoa que enviou para o mesmo branch". Até aqui, parece um push rejeitado comum (veja Push Rejeitado). O Bruno faz o que a dica manda:

$ git pull
From https://github.com/ana-souza/receitas
 + 14fffbd...fa7fe1f main       -> origin/main  (forced update)

hint: You can do so by running one of the following commands sometime before
hint: your next pull:
hint:

hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
hint:

hint: preference for all repositories. You can also pass --rebase, --no-rebase,
hint: or --ff-only on the command line to override the configured default per
hint: invocation.
fatal: Need to specify how to reconcile divergent branches.

A primeira linha entrega o que aconteceu: + 14fffbd...fa7fe1f … (forced update), o main do GitHub foi forçado. O resto é o aviso de branches divergentes (explicado em Rebase ou Merge?). O Bruno escolhe o merge, o padrão de muita gente:

$ git pull --no-rebase
Mesclagem automática de pudim.txt
CONFLITO (adicionar/adicionar): conflito de mesclagem em pudim.txt
Automatic merge failed; fix conflicts and then commit the result.
$ git status

e cada um tem 2 e 1 submissões, respectivamente.
  (use "git pull" if you want to integrate the remote branch with yours)

<<<<<<< HEAD

>>>>>>> fa7fe1f1b47a6eb6e5715d4470c2e7013d4e1d1d

Um conflito no pudim.txt, um arquivo que o Bruno nunca tocou. Linha por linha:

CONFLITO (adicionar/adicionar)
"Os dois lados criaram o arquivo." Para o Git, o pudim.txt nasceu duas vezes: uma no 14fffbd (que o Bruno tem) e outra no fa7fe1f (que o GitHub tem agora), cada uma com um conteúdo. O ponto em comum dos dois lados é o commit do bolo, quando o pudim ainda nem existia.
cada um tem 2 e 1 submissões
O Bruno tem 2 commits que o GitHub não tem (o 14fffbd antigo da Ana e o brigadeiro dele); o GitHub tem 1 que o Bruno não tem (o fa7fe1f).
ambos adicionaram: pudim.txt
O mesmo "adicionar/adicionar", no status.

Se o Bruno resolvesse esse conflito e enviasse, o main do GitHub passaria a ter os dois commits "Adiciona a receita de pudim" (o antigo, com "leiet", e o novo) mais um commit de merge. O 14fffbd que a Ana quis apagar voltaria para o GitHub. Numa equipe de cinco pessoas, cada uma passaria por isso.

O Bruno desistiu do merge (veja Desistindo de um Merge) e olhou o desenho:

$ git merge --abort
$ git log --oneline --graph --all
* 52e2dc5 Adiciona a receita de brigadeiro
* 14fffbd Adiciona a receita de pudim             « o pudim antigo, que só o Bruno ainda tem
| * fa7fe1f Adiciona a receita de pudim           « o pudim reescrito (origin/main)
|/
* c34349b Adiciona a receita de bolo
* 700bbd5 Cria o README

Duas versões do mesmo commit, em dois galhos. É o "caderno que não bate mais" da comparação lá de cima.

4. Como o Bruno sai dessa

O que o Bruno quer é: "pegue o main do GitHub como está agora e ponha só o meu brigadeiro em cima". É exatamente o que o git pull --rebase faz:

$ git pull --rebase
Successfully rebased and updated refs/heads/main.
$ git log --oneline --graph --all
* c9c0c26 Adiciona a receita de brigadeiro
* fa7fe1f Adiciona a receita de pudim
* c34349b Adiciona a receita de bolo
* 700bbd5 Cria o README
$ git push
To https://github.com/ana-souza/receitas.git
   fa7fe1f..c9c0c26  main -> main

O rebase refez só o brigadeiro (agora c9c0c26) em cima do fa7fe1f e deixou o 14fffbd antigo de fora, sem conflito. Como o Git soube? O Bruno tinha baixado o 14fffbd pelo origin/main, e o Git guarda um diário de por onde o origin/main passou (o mesmo tipo de diário do git reflog). Com ele, o pull --rebase percebe que o 14fffbd veio do GitHub e não é trabalho do Bruno. O push final é um push normal, com dois pontos.

Nem sempre é tão limpo

Aqui deu certo porque o Bruno não tinha mexido no pudim.txt e baixou o commit antigo pelo próprio origin/main. Se ele tivesse editado o pudim, ou se tivesse feito o merge e enviado antes de perceber, o conserto seria bem mais trabalhoso. E cada pessoa da equipe que tinha o commit antigo precisa fazer esse conserto. Por isso a regra é não reescrever, e não "reescrever e explicar para todo mundo como consertar".

5. O que a Ana deveria ter feito

Voltando ao começo (pudim com "leiet" já no GitHub, brigadeiro do Bruno ainda não enviado). Em vez do --amend, a Ana faz um commit novo de correção, a "página nova" do caderno:

$ sed -i 's/leiet/leite/' pudim.txt
$ git commit -q -am 'Corrige erro de digitação no pudim'
$ git push
To https://github.com/ana-souza/receitas.git
   14fffbd..dc121d5  main -> main
$ git log --oneline
dc121d5 Corrige erro de digitação no pudim
14fffbd Adiciona a receita de pudim
c34349b Adiciona a receita de bolo
700bbd5 Cria o README

Push normal, sem força: 14fffbd..dc121d5, dois pontos, "do 14fffbd até o dc121d5". E do lado do Bruno, que tem o brigadeiro ainda não enviado:

$ git pull --rebase
From https://github.com/ana-souza/receitas
   14fffbd..dc121d5  main       -> origin/main
Successfully rebased and updated refs/heads/main.
$ git log --oneline --graph --all
* ab8f560 Adiciona a receita de brigadeiro
* dc121d5 Corrige erro de digitação no pudim
* 14fffbd Adiciona a receita de pudim
* c34349b Adiciona a receita de bolo
* 700bbd5 Cria o README

Sem forced update, sem conflito, sem commit duplicado. O histórico ganhou um commit a mais ("Corrige erro de digitação"), e tudo bem: é a história verdadeira.

Para desfazer um commit público inteiro (e não só corrigir um detalhe), a ferramenta é o git revert: ele cria um commit novo que faz o contrário do commit escolhido, sem tirar nada do histórico.

Missão: o commit "Adiciona a receita de pudim" já foi enviado (o "servidor" aqui é a pasta ~/servidor.git, que faz o papel do GitHub), e o pudim.txt tem "leiet". Corrija para "leite" sem reescrever o histórico: um commit novo e um git push normal. (Dica: sed -i 's/leiet/leite/' pudim.txt troca o texto.) Se você usar --amend, o push vai ser recusado; e a missão confere que o commit original continua lá.

6. Quando reescrever é tranquilo

A regra é sobre commits que outras pessoas podem ter baixado. Nos outros casos, reescrever é normal e até recomendado:

SituaçãoPode reescrever?
Commits que ainda não saíram do seu computador (antes do push)Sim, à vontade: amend, rebase -i, squash
Um branch só seu, que você enviou só como cópia de segurança (ou para um pull request) e que ninguém mais usaSim, com cuidado: depois, envie com push --force-with-lease
Um branch de pull request em que a equipe combinou "faça rebase antes do merge"Sim, é o combinado; avise se mais alguém commitou no branch
O main (ou qualquer branch) que a equipe inteira usaNão. Commit novo ou git revert
Uma senha commitada e enviadaCaso especial: troque a senha primeiro; veja Commitei uma Senha!
Na dúvida, pergunte ao status

Antes de um amend ou rebase, rode git status. Se ele disser Your branch is up to date with 'origin/main', o último commit já está no GitHub: pense duas vezes. Se disser "à frente de 'origin/main' por N submissões", esses N commits mais recentes ainda são só seus.

Formas diferentes de fazer a mesma coisa

Para cada vontade de "arrumar o histórico", a versão que respeita a regra de ouro:

Você quer…Se o commit ainda é só seuSe o commit já é público
Corrigir um erro do último commitgit commit --amendCommit novo de correção
Desfazer um commitgit resetgit revert
Juntar vários commits pequenosgit rebase -i (squash)Deixe como está (ou Squash and merge no pull request, que cria um commit novo no branch de destino)
Atualizar seu branch com o maingit rebase maingit merge main
Mudar a mensagem de um commitgit commit --amend ou rebase -i (reword)Deixe como está

Quando dá errado

"Fiz amend (ou rebase) e o push foi recusado" 
$ git push
To https://github.com/ana-souza/receitas.git
 ! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs to 'https://github.com/ana-souza/receitas.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart. If you want to integrate the remote changes,
hint: use 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

O que aconteceu: você reescreveu um commit que já estava no GitHub. Como confirmar: o git status diz que o branch e o origin/main "divergiram-se". Como resolver: pare e pergunte "alguém mais usa este branch?". Se for o main compartilhado: não force. Desfaça a reescrita (o commit antigo continua acessível pelo origin/main e pelo reflog; por exemplo, git reset --hard origin/main volta o seu branch para o que está no GitHub, perdendo a correção, que você refaz como commit novo). Se o branch é só seu: git push --force-with-lease (próxima aula).

"Conflito num arquivo que eu nem mexi" depois de um pull 
$ git pull --no-rebase
Mesclagem automática de pudim.txt
CONFLITO (adicionar/adicionar): conflito de mesclagem em pudim.txt
Automatic merge failed; fix conflicts and then commit the result.

O que aconteceu: alguém reescreveu e forçou um branch que você já tinha baixado. Como confirmar: procure (forced update) na saída do pull/fetch, e o git log --oneline --graph --all mostra dois commits com a mesma mensagem em galhos diferentes. Como resolver: git merge --abort e depois git pull --rebase, como o Bruno na seção 4. E converse com quem forçou.

"Forcei e o commit do colega sumiu do GitHub"

Se o Bruno já tivesse enviado o brigadeiro antes do git push --force da Ana, o force teria trocado o main do GitHub pelo da Ana, que não tem o brigadeiro: o commit do Bruno sumiria de lá, sem aviso nenhum para a Ana. Como resolver: o commit ainda existe no computador do Bruno; ele roda git pull --rebase e git push de novo. Como evitar: nunca --force puro; o --force-with-lease recusa exatamente esse caso. A aula push --force-with-lease mostra a recusa de verdade.

Resumo

  • Regra de ouro: não reescreva commits que outras pessoas podem ter baixado.
  • Reescrevem: --amend, rebase (e rebase -i/squash), reset para trás. Só acrescentam: commit, merge, revert.
  • O push recusa um histórico reescrito (non-fast-forward). O --force passa por cima, e quem já tinha os commits antigos fica com branches divergentes e conflitos estranhos (adicionar/adicionar).
  • Quem foi atingido sai com git merge --abort + git pull --rebase.
  • Para corrigir o que é público: commit novo; para desfazer: git revert. Reescrever fica para o que ainda é só seu (e, num branch só seu já enviado, push --force-with-lease).

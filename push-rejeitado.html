Git Push Rejeitado: o que Fazer

Mais cedo ou mais tarde, você vai dar git push e ver um ! [rejected] em vez do "pronto". Calma: nada se perdeu. O push rejeitado é o Git protegendo o trabalho de outra pessoa. Nesta aula você entende por que ele acontece, como ler a mensagem e a receita para sair dele em dois comandos. E vê, na prática, por que o atalho --force é uma péssima ideia.

Você vai aprender
  • Por que o Git recusa um push: o remoto tem commits que você não tem.
  • A ler as variações: (fetch first), (non-fast-forward) e (stale info).
  • A receita: git pull e depois git push.
  • O que o git push --force faz com o trabalho do colega (com a prova) e a alternativa segura.
  • O caso clássico do repositório criado com README no GitHub: refusing to merge unrelated histories.

A ideia antes do comando

Volte ao álbum de fotos da avó, da aula de git push. Você chega para colar as suas fotos e descobre que, desde a sua última visita, o seu primo colou fotos novas na página seguinte. Se você colasse as suas por cima, as dele sumiriam. O certo é olhar as fotos dele, encaixar as suas depois delas e só então colar.

O Git faz exatamente isso. O push só é aceito se for um avanço (fast-forward) do branch remoto: tudo o que está lá precisa estar também no que você envia. Se o remoto tem um commit que você não tem, aceitar o push apagaria esse commit. Então o Git recusa.

GitHub:  A---B---S          main   (S = sal, do Bruno)
Ana:     A---B---M          main   (M = mousse, da Ana)
                            push de M?  aceitar = apagar S  →  rejeitado

Acontecendo de verdade

O Bruno acrescentou sal ao bolo e enviou. A Ana, sem saber, fez o commit da mousse e tentou enviar:

$ git push
To https://github.com/ana-souza/receitas.git
 ! [rejected]        main -> main (fetch first)                   « recusado
error: failed to push some refs to 'https://github.com/ana-souza/receitas.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

O git status não sabia de nada

$ git status
No ramo main
Seu ramo está à frente de 'origin/main' por 1 submissão.         « só sabe da mousse
  (use "git push" to publish your local commits)

nothing to commit, working tree clean

O status compara com a lembrança do remoto (origin/main), que ainda não tem o sal do Bruno. Por isso, ele manda dar push, e o push é recusado de novo, quantas vezes você tentar. Depois de um git fetch, o quadro fica claro:

$ git fetch -q
$ git status
No ramo main
O seu branch e 'origin/main' divergiram-se,
e cada um tem 1 e 1 submissões, respectivamente.                « 1 da Ana, 1 do Bruno
  (use "git pull" if you want to integrate the remote branch with yours)

nothing to commit, working tree clean
$ git log --oneline --graph --all
* 455dc5d (HEAD -> main) Adiciona receita de mousse
| * 8689ab9 (origin/main, origin/HEAD) Adiciona sal ao bolo
|/
* 4f68d0e Adiciona receita de bolo
* 0e8cf93 Adiciona README

A mesma recusa, com outro nome: (non-fast-forward)

Agora que o Git da Ana conhece o commit do Bruno, o push recusado ganha outra explicação:

$ git push
To https://github.com/ana-souza/receitas.git
 ! [rejected]        main -> main (non-fast-forward)              « não é um avanço
error: failed to push some refs to 'https://github.com/ana-souza/receitas.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart. If you want to integrate the remote changes,
hint: use 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

"As atualizações foram recusadas porque a ponta do seu branch atual está atrás do par remoto". A diferença entre as duas é só o que o seu Git já sabe: fetch first quando ele nem viu o commit novo; non-fast-forward quando já viu. A solução é a mesma.

A receita: git pull, depois git push

  1. Traga e junte o trabalho do remoto: git pull (escolhendo merge ou rebase; veja git pull).
  2. Se der conflito, resolva (veja Resolvendo Conflitos).
  3. Envie: git push. Agora é um avanço, e o Git aceita.

Experimente

No terminal abaixo, o "GitHub" é uma pasta de treino (~/servidor/receitas.git). A Ana fez o commit do pudim, mas o Bruno enviou o do suco antes.

Missão: tente git push e leia a recusa. Depois, siga a receita: traga o commit do Bruno (git pull --rebase ou git pull --no-rebase) e envie de novo, até o remoto ter o suco e o pudim.

O atalho proibido: git push --force

Na internet, muita gente "resolve" o push rejeitado com git push --force (force = "forçar"). Ele manda o remoto aceitar o seu branch do jeito que está, mesmo que isso apague commits de lá. Veja o que acontece. O Bruno enviou o commit dos ovos; a Ana, sem buscar, fez o do pavê e forçou:

$ git push --force
Enumerating objects: 17, done.
Counting objects: 100% (17/17), done.
Delta compression using up to 4 threads
Compressing objects: 100% (11/11), done.
Writing objects: 100% (17/17), 1.47 KiB | 753.00 KiB/s, done.
Total 17 (delta 3), reused 0 (delta 0), pack-reused 0 (from 0)
To https://github.com/ana-souza/receitas.git
 + 71e8d25...1958348 main -> main (forced update)                « + e "forced update" = sobrescrito

Repare nos detalhes: o + no começo, os três pontos (...) em vez de dois e o (forced update), "atualização forçada". Todos querem dizer: o branch de lá não avançou, foi substituído. O histórico do GitHub, antes e depois (visto direto no servidor de treino):

Antes do --force                                Depois do --force
* 71e8d25 Adiciona ovos ao bolo     « do Bruno   * 1958348 Adiciona receita de pavê   « da Ana
*   fec59c7 Merge branch 'main' of …            *   fec59c7 Merge branch 'main' of …
…                                               …
                                                (o commit dos ovos sumiu do GitHub)

O commit do Bruno sumiu do GitHub. Ele ainda existe no computador dele, mas o histórico do GitHub não bate mais com o dele, e alguém vai ter de resgatar o trabalho à mão. Por isso a regra do guia: nunca use --force num branch que outras pessoas usam. Veja A Regra de Ouro.

A versão segura: --force-with-lease

Existem situações legítimas para sobrescrever o remoto (por exemplo, depois de um rebase no seu branch). Para elas existe o --force-with-lease ("forçar, com garantia"): ele só sobrescreve se o remoto estiver exatamente como o seu Git lembra. Se alguém enviou algo que você ainda não viu, ele recusa:

$ git push --force-with-lease
To https://github.com/ana-souza/receitas.git
 ! [rejected]        main -> main (stale info)                    « informação desatualizada
error: failed to push some refs to 'https://github.com/ana-souza/receitas.git'

stale info = "informação velha": o Bruno enviou um commit que a lembrança da Ana (origin/main) não tem, e o Git se recusou a apagá-lo. Os detalhes estão em push --force-with-lease.

O caso clássico: criei o repositório no GitHub com README

Formas diferentes de sair do push rejeitado

FormaResultadoQuando usar
git pull --no-rebase + git pushJunta com commit de mesclagemSempre funciona; histórico mostra o que aconteceu
git pull --rebase + git pushSeus commits replantados em cima dos do colegaEquipes que preferem histórico em linha reta
git fetch, olhar, git merge origin/main + git pushIgual ao primeiro, conferindo antesQuando quer ver o que o colega mudou
git push --force-with-leaseSobrescreve, mas só se ninguém enviou nada novoSó no seu branch, depois de reescrever o histórico
git push --forceSobrescreve sem perguntarEvite. Apaga o trabalho dos outros

Quando dá errado

Fiz o pull e deu conflito

O que aconteceu: você e o colega mudaram as mesmas linhas.

Como resolver: resolva o conflito, git add, git commit (ou git rebase --continue, se usou --rebase) e só então git push. Para desistir: git merge --abort ou git rebase --abort. Veja Resolvendo Conflitos.

O pull respondeu "Need to specify how to reconcile divergent branches"

O que aconteceu: o Git quer que você escolha entre merge e rebase.

Como resolver: git pull --no-rebase ou git pull --rebase; e, para não ser perguntado de novo, git config --global pull.rebase false (ou true). Veja git pull.

Rejeitado depois de um commit --amend ou de um rebase

O que aconteceu: você reescreveu um commit que já tinha enviado (veja --amend). Para o GitHub, o seu branch agora é outro histórico, e o push vira non-fast-forward.

Como resolver: se o branch é só seu, git push --force-with-lease. Se outras pessoas usam o branch, não reescreva: desfaça com git revert. Veja A Regra de Ouro.

Usei --force e apaguei o commit do colega

O que aconteceu: o remoto foi sobrescrito.

Como resolver: avise o colega na hora. O commit ainda existe no computador dele: com o git log ele acha o hash, traz o main novo do remoto e copia o commit para cima dele com cherry-pick, e depois envia com git push. No seu computador, o reflog também guarda por onde o origin/main passou.

3. Históricos sem parentesco

4. Por que o Git rejeita o push quando o remoto tem um commit que você não tem?

5. A Ana viu ! [rejected] main -> main (fetch first) e o git status diz "à frente de 'origin/main' por 1". Por que o status não fala do commit do Bruno?

Resumo

  • Push rejeitado = o remoto tem commits que você não tem; aceitar o push apagaria esses commits.
  • (fetch first) e (non-fast-forward) têm a mesma solução: git pull (merge ou rebase) e depois git push.
  • O git status só percebe o problema depois de um fetch.
  • git push --force apaga o trabalho dos outros: nunca num branch compartilhado. Se precisar sobrescrever o seu próprio branch, use --force-with-lease.
  • Repositório criado com README e projeto já existente: git pull --allow-unrelated-histories, ou crie o repositório vazio da próxima vez.

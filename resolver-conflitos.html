Git Resolvendo Conflitos

Na aula Conflitos de Merge, o merge do branch forno parou no meio: o main dizia "180 graus por 45 minutos", o forno dizia "200 graus por 30 minutos", e o Git escreveu as duas versões dentro do bolo.txt, entre marcadores. Agora é com você. Resolver um conflito é só isto: deixar o arquivo do jeito que ele deve ficar, avisar o Git com git add e terminar o merge com git commit. Nesta aula você vai fazer isso de vários jeitos e olhar o git status em cada passo.

Você vai aprender
  • O roteiro completo: editar o arquivo, apagar os marcadores, git add e git commit, com o git status em cada etapa.
  • Como ficar com um lado inteiro: --ours ("o nosso") e --theirs ("o deles").
  • Como voltar atrás numa escolha e recriar os marcadores (git restore --merge, git checkout -m).
  • Como o VS Code mostra um conflito (ilustrativo) e as opções -X ours e -X theirs do git merge.
  • Como achar marcadores esquecidos antes que eles entrem num commit (git diff --check).

Todas as saídas desta aula vieram do Git 2.53.0 da máquina da Ana (usuária ana, computador notebook), com o sistema em português. A tradução do Git no Ubuntu é incompleta: várias mensagens saem em inglês. Elas estão copiadas como saíram e ganham tradução na explicação.

A ideia: quem decide a receita é você

Lembra dos dois bilhetes na geladeira, um dizendo "45 minutos" e o outro "200 graus por 30 minutos"? Quem passa a receita a limpo tem três caminhos:

  1. Escrever uma versão nova, misturando as duas: "200 graus por 35 minutos". (Editar à mão.)
  2. Ficar com um dos bilhetes inteiro e jogar o outro fora. (--ours ou --theirs.)
  3. Pedir ajuda a um programa que mostra os dois lado a lado e tem botões para escolher. (Um editor como o VS Code.)

Em qualquer caminho, o fim é o mesmo: o arquivo fica sem marcadores, do jeito certo; você avisa o Git com git add; e o git commit cria o commit de merge que estava faltando.

0. O ponto de partida

O repositório é o da aula anterior: o main e o forno mudaram a última linha do bolo.txt, e o forno também criou a cobertura.txt. A Ana começa o merge:

$ git merge forno
Mesclagem automática de bolo.txt
CONFLITO (conteúdo): conflito de mesclagem em bolo.txt
Automatic merge failed; fix conflicts and then commit the result.
$ git status --short
UU bolo.txt
A  cobertura.txt

O git status --short (o status resumido, uma linha por arquivo; veja git status) mostra o mesmo que o git status completo, em duas letras:

UU bolo.txt
U de unmerged, "não mesclado". As duas letras UU querem dizer "mudado dos dois lados, com conflito": é o ambos modificados do git status completo. É este que você vai resolver.
A cobertura.txt
A de added, "adicionado" à área de preparo. O Git já juntou esse arquivo sozinho; ele vai entrar no commit de merge sem você fazer nada.

1. Resolvendo à mão (o jeito que sempre funciona)

Passo 1: abrir o arquivo e decidir

Abra o bolo.txt no seu editor de texto (o nano, o VS Code, o que você usa). Ele está assim:

Bolo de cenoura
- 3 cenouras
- 3 ovos
- 2 xícaras de açúcar
<<<<<<< HEAD
Forno: 180 graus por 45 minutos
=======
Forno: 200 graus por 30 minutos
>>>>>>> forno

A Ana conversa com o irmão e eles chegam a um acordo: forno mais quente, como no forno, mas com 35 minutos, porque 30 deixava o meio cru. A linha certa não é nenhuma das duas: é uma terceira.

Passo 2: escrever a versão final e apagar os marcadores

No editor, ela apaga as cinco linhas do trecho em conflito (as duas versões e os três marcadores) e escreve no lugar a linha combinada. Os marcadores têm de sumir todos: o <<<<<<< HEAD, o ======= e o >>>>>>> forno. O Git não os apaga por você. (Aqui, para a aula, a Ana escreveu o arquivo inteiro com printf; no dia a dia você usa o editor.)

$ printf 'Bolo de cenoura\n- 3 cenouras\n- 3 ovos\n- 2 xícaras de açúcar\nForno: 200 graus por 35 minutos\n' > bolo.txt
$ cat bolo.txt
Bolo de cenoura
- 3 cenouras
- 3 ovos
- 2 xícaras de açúcar
Forno: 200 graus por 35 minutos

Passo 3: o git status ainda reclama?

$ git status
No ramo main
Você tem caminhos não mesclados.
  (fixar conflitos e executar "git commit")
  (use "git merge --abort" to abort the merge)

Mudanças a serem submetidas:
        new file:   cobertura.txt

Caminhos não mesclados:
  (usar "git add <arquivo>..." para marcar resolução)
        ambos modificados:   bolo.txt

Sim, e isso confunde muita gente. O arquivo já está certo, mas o bolo.txt continua em "Caminhos não mesclados". O Git não lê o arquivo para saber se você terminou: ele espera que você avise. A dica diz como: (usar "git add <arquivo>..." para marcar resolução).

Antes de avisar, vale conferir o que você fez. O git diff, durante o conflito, compara o arquivo com os dois lados:

$ git diff
diff --cc bolo.txt
index 798cdff,e6355df..0000000
--- a/bolo.txt
+++ b/bolo.txt
@@@ -2,4 -2,4 +2,4 @@@ Bolo de cenour
  - 3 cenouras
  - 3 ovos
  - 2 xícaras de açúcar
- Forno: 180 graus por 45 minutos
 -Forno: 200 graus por 30 minutos
++Forno: 200 graus por 35 minutos

As duas colunas de sinais da aula anterior: - na primeira coluna é a linha do nosso lado (o main) que saiu; - na segunda, a linha do lado deles (o forno) que saiu; e ++ é a linha nova, que não existia em nenhum dos dois. Nenhum marcador sobrou. Tudo certo.

Passo 4: git add para marcar como resolvido

$ git add bolo.txt
$ git status
No ramo main
Todos os conflitos foram corrigidos mas você continua mesclando.
  (use  "git commit" para concluir a mesclagem)

Mudanças a serem submetidas:
        modified:   bolo.txt
        new file:   cobertura.txt
Todos os conflitos foram corrigidos mas você continua mesclando.
Não há mais arquivos em conflito, mas o merge ainda está em andamento: o commit de merge não existe.
(use "git commit" para concluir a mesclagem)
O próximo passo. (O espaço duplo depois do use é da tradução, não erro de cópia.)
modified: bolo.txt / new file: cobertura.txt
O que vai entrar no commit de merge: o bolo.txt com a sua versão (modified = "modificado") e a cobertura.txt que veio do forno (new file = "arquivo novo").

No caso de um arquivo apagado de um lado e mudado do outro (o excluídos por eles da aula anterior), o aviso é o mesmo, com o comando conforme a decisão: git add pudim.txt para ficar com o arquivo, ou git rm pudim.txt para aceitar que ele saia.

Passo 5: git commit para terminar o merge

Basta git commit, sem -m: o Git abre o editor com uma mensagem pronta. A Ana usou o truque GIT_EDITOR=cat, que "abre" a mensagem no cat (só mostra e aceita), para você ver aqui o que aparece no editor:

$ GIT_EDITOR=cat git commit
hint: Waiting for your editor to close the file... Merge branch 'forno'

# Conflicts:
#       bolo.txt
#
# It looks like you may be committing a merge.
# If this is not correct, please run
#       git update-ref -d MERGE_HEAD
# and try again.


# Please enter the commit message for your changes. Lines starting
# with '#' will be ignored, and an empty message aborts the commit.
#
# No ramo main
# Todos os conflitos foram corrigidos mas você continua mesclando.
#
# Mudanças a serem submetidas:
#       modified:   bolo.txt
#       new file:   cobertura.txt
#
[main f43ce70] Merge branch 'forno'
Merge branch 'forno'
A mensagem pronta, a mesma de um merge sem conflito. Se quiser, troque por algo como Junta o forno: 200 graus por 35 minutos.
# Conflicts: # bolo.txt
"Conflitos: bolo.txt". Um lembrete de quais arquivos tiveram conflito. Como começa com #, não entra na mensagem; se quiser guardar essa informação, apague o # do começo dessas linhas.
# It looks like you may be committing a merge. …
"Parece que você está fazendo o commit de um merge. Se isso não estiver certo, rode git update-ref -d MERGE_HEAD e tente de novo." É só uma confirmação; aqui está certo, então ignore.
# Please enter the commit message …
As instruções de sempre do git commit: linhas com # são ignoradas e uma mensagem vazia cancela o commit. Embaixo, uma cópia do git status.
[main f43ce70] Merge branch 'forno'
O commit de merge nasceu: f43ce70, no main. O merge acabou.

No seu computador, sem o truque, o editor abre com esse texto: salve e feche para aceitar (no nano, Ctrl+O, Enter, Ctrl+X). Para não abrir o editor, use git commit --no-edit (aceita a mensagem pronta) ou git commit -m "sua mensagem".

Depois do commit

$ git log --oneline --graph
*   f43ce70 (HEAD -> main) Merge branch 'forno'
|\
| * 70c15e0 (forno) Assa mais quente e mais rápido
* | aa84752 Aumenta o tempo de forno
|/
* a071866 Adiciona a receita de bolo
$ git status
No ramo main
nothing to commit, working tree clean
$ git show --stat HEAD
commit f43ce70cd5d01a3dafd2008fa45c7f623d1a460c (HEAD -> main)
Merge: aa84752 70c15e0
Author: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

    Merge branch 'forno'

 bolo.txt      | 2 +-
 cobertura.txt | 1 +
 2 files changed, 2 insertions(+), 1 deletion(-)

O mesmo "losango" de um merge sem conflito (veja Merge de Três Vias): ninguém olhando o desenho sabe que houve conflito. O git status está limpo (nothing to commit, working tree clean: "nada a commitar, pasta limpa"). E o git show --stat mostra o que o merge mudou em relação ao main de antes (o primeiro pai): uma linha trocada no bolo.txt (2 +-: uma entrou, uma saiu) e a cobertura.txt nova.

Missão: o merge do forno já começou e parou num conflito no bolo.txt (veja com git status e cat bolo.txt). Resolva à mão: o arquivo deve ficar com uma linha só, Forno: 190 graus, sem marcadores (dica: echo 'Forno: 190 graus' > bolo.txt). Depois marque como resolvido e termine o merge com a mensagem padrão (git commit --no-edit). Olhe o git status antes e depois do git add.

2. Ficando com um lado inteiro: --ours e --theirs

Às vezes a decisão é simples: "o lado do forno está certo, joga o meu fora". Em vez de editar, peça ao Git a versão de um dos lados:

  • --ours ("a nossa"): a versão do branch onde você está, a de cima dos marcadores (HEAD);
  • --theirs ("a deles"): a versão do branch que está chegando, a de baixo (forno).

Dois comandos fazem isso: o moderno git restore (Git 2.23+, aula git restore) e o antigo git checkout, que você vai encontrar em tutoriais. A Ana, com o conflito de novo aberto, experimentou os dois:

$ git checkout --theirs bolo.txt
Updated 1 path from the index
$ cat bolo.txt
Bolo de cenoura
- 3 cenouras
- 3 ovos
- 2 xícaras de açúcar
Forno: 200 graus por 30 minutos
$ git checkout --ours bolo.txt
Updated 1 path from the index
$ cat bolo.txt
Bolo de cenoura
- 3 cenouras
- 3 ovos
- 2 xícaras de açúcar
Forno: 180 graus por 45 minutos
$ git restore --theirs bolo.txt
$ cat bolo.txt
Bolo de cenoura
- 3 cenouras
- 3 ovos
- 2 xícaras de açúcar
Forno: 200 graus por 30 minutos
git checkout --theirs bolo.txt
Troca o arquivo da pasta pela versão deles (o forno): os marcadores somem, e a linha do forno fica 200 graus por 30 minutos. O Git responde Updated 1 path from the index, "1 caminho atualizado a partir do índice" (o índice é a área de preparo, onde o Git guardou as duas versões durante o conflito).
git checkout --ours bolo.txt
Agora a versão nossa (o main): 180 graus por 45 minutos. Dá para trocar de ideia quantas vezes quiser: nada está decidido até o git add.
git restore --theirs bolo.txt
O mesmo que o git checkout --theirs, com o comando moderno. Ele não mostra mensagem nenhuma.

Repare: a escolha vale para o arquivo inteiro, não só para o trecho em conflito. Num arquivo com uma parte juntada sem conflito e outra em conflito, o --theirs descarta também o que o seu lado mudou sem conflito. Para escolher trecho por trecho, edite à mão (ou use o VS Code, logo abaixo).

Depois de escolher, o resto é igual: git add e terminar o merge. Para terminar, além do git commit, existe o git merge --continue, que faz o mesmo (ele confere se há mesmo um merge em andamento e chama o git commit):

$ git add bolo.txt
$ git merge --continue
[main 7877581] Merge branch 'forno'
$ cat bolo.txt
Bolo de cenoura
- 3 cenouras
- 3 ovos
- 2 xícaras de açúcar
Forno: 200 graus por 30 minutos

(O git merge --continue também abre o editor com a mensagem; a Ana salvou e fechou sem mudar.)

No rebase, "ours" e "theirs" se invertem

Tudo nesta aula vale para o merge. Durante um git rebase, o "nosso" e o "deles" trocam de lugar, e isso confunde até gente experiente. Os detalhes estão em Conflitos no Rebase.

Missão: o mesmo conflito, mas agora a Ana decidiu que o branch forno está certo. Fique com a versão deles sem editar o arquivo (git restore --theirs ou git checkout --theirs), marque como resolvido e termine o merge com a mensagem padrão.

3. Errei a escolha! Recriando o conflito

Escolheu o lado errado, ou apagou um pedaço que não devia? Enquanto o merge estiver em andamento, dá para pôr os marcadores de volta no arquivo:

$ git restore --merge bolo.txt
$ cat bolo.txt
Bolo de cenoura
- 3 cenouras
- 3 ovos
- 2 xícaras de açúcar
<<<<<<< ours
Forno: 180 graus por 45 minutos
=======
Forno: 200 graus por 30 minutos
>>>>>>> theirs

O conflito voltou, só que os marcadores agora dizem ours e theirs em vez de HEAD e forno. O sentido é o mesmo. O comando antigo, com a opção de ver também a base (o estilo diff3 da aula anterior), é o git checkout --conflict=diff3:

$ git checkout --conflict=diff3 bolo.txt
Recreated 1 merge conflict
$ cat bolo.txt
Bolo de cenoura
- 3 cenouras
- 3 ovos
- 2 xícaras de açúcar
<<<<<<< ours
Forno: 180 graus por 45 minutos
||||||| base
Forno: 180 graus por 40 minutos
=======
Forno: 200 graus por 30 minutos
>>>>>>> theirs

Recreated 1 merge conflict: "1 conflito de merge recriado". E se você já tinha feito o git add? Ainda dá: o git checkout -m bolo.txt (-m de merge) recria o conflito e devolve o arquivo para "Caminhos não mesclados". A Ana tinha marcado como resolvido um arquivo errado:

$ git status --short
M  bolo.txt
A  cobertura.txt
$ git checkout -m bolo.txt
Recreated 1 merge conflict
$ git status --short
UU bolo.txt
A  cobertura.txt

O M ("modificado e preparado") voltou a ser UU (em conflito). Depois do git commit, não tem mais volta por aqui: o merge terminou. Aí a saída é desfazer o merge inteiro (aula Desistindo de um Merge) ou corrigir com um commit novo.

4. No VS Code (ilustrativo)

Editores modernos reconhecem os marcadores e ajudam. No VS Code, ao abrir um arquivo em conflito, você vê (esta parte é ilustrativa: o VS Code não roda no laboratório da Ana; os nomes seguem a documentação do VS Code, em inglês, como aparecem no editor sem pacote de idioma):

  • a parte "Current Change" ("mudança atual", o nosso lado, HEAD) pintada de uma cor, e a "Incoming Change" ("mudança que chega", o lado deles) de outra;
  • em cima do trecho, uma linha de links: Accept Current Change (fica com o nosso), Accept Incoming Change (fica com o deles), Accept Both Changes (fica com as duas versões, uma embaixo da outra) e Compare Changes (mostra as duas lado a lado);
  • um botão para abrir o editor de merge de três painéis (o nosso, o deles e o resultado embaixo).

Esses botões só editam o arquivo por você: apagam os marcadores e a versão que você não quis. Ainda é preciso salvar, marcar como resolvido (git add, ou o + no painel de controle de versão do VS Code) e fazer o commit. O que acontece no Git é exatamente o da seção 1. Mais sobre isso em Git no VS Code e em Outros Programas.

A tabela mostra o que cada botão deixa no arquivo da Ana:

Botão do VS CodeA última linha do bolo.txt fica…Equivale, no terminal, a…
Accept Current ChangeForno: 180 graus por 45 minutoseditar e ficar com a parte de cima (neste arquivo, igual a git restore --ours)
Accept Incoming ChangeForno: 200 graus por 30 minutoseditar e ficar com a parte de baixo (neste arquivo, igual a git restore --theirs)

Cuidado com o Accept Both Changes: numa receita, ficar com "45 minutos" e "30 minutos" não faz sentido. Ele serve quando as duas versões se completam (por exemplo, duas receitas novas acrescentadas no mesmo lugar da lista).

5. Resolvendo na hora do merge: -X ours e -X theirs

Se você já sabe, antes do merge, que em todo conflito quer ficar com um dos lados, pode avisar no próprio git merge com -X (uma "opção da estratégia" de merge):

$ git merge --no-edit -X theirs forno
Mesclagem automática de bolo.txt
Merge made by the 'ort' strategy.
 bolo.txt      | 2 +-
 cobertura.txt | 1 +
 2 files changed, 2 insertions(+), 1 deletion(-)
 create mode 100644 cobertura.txt
$ cat bolo.txt
Bolo de cenoura
- 3 cenouras
- 3 ovos
- 2 xícaras de açúcar
Forno: 200 graus por 30 minutos

Nada de CONFLITO: no trecho em conflito, o Git ficou com o lado deles, e o merge terminou direto. Com -X ours (a Ana desfez o merge acima e tentou de novo), fica o nosso lado:

$ git merge --no-edit -X ours forno
Mesclagem automática de bolo.txt
Merge made by the 'ort' strategy.
 cobertura.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 cobertura.txt
$ cat bolo.txt
Bolo de cenoura
- 3 cenouras
- 3 ovos
- 2 xícaras de açúcar
Forno: 180 graus por 45 minutos
$ ls
bolo.txt  cobertura.txt

Repare que a cobertura.txt, que vinha do forno sem conflito, entrou mesmo com -X ours. Diferente do --ours da seção 2 (que pega o arquivo inteiro), o -X só decide os trechos em conflito; o resto é juntado normalmente. É prático, mas perigoso: o Git escolhe sem você olhar. Use só quando tiver certeza.

6. Achando marcadores esquecidos

O erro mais comum ao resolver conflitos é esquecer um marcador no arquivo. E o Git não impede: o git add aceita um arquivo com marcadores. A Ana fez isso de propósito, com o arquivo ainda cheio de marcadores (o da seção 3), e depois pediu ao Git para conferir:

$ git add bolo.txt
$ git diff --cached --check
bolo.txt:5: leftover conflict marker
bolo.txt:7: leftover conflict marker
bolo.txt:9: leftover conflict marker
bolo.txt:11: leftover conflict marker
$ git status --short
M  bolo.txt
A  cobertura.txt

O git add não reclamou, e o git status --short mostra o arquivo como resolvido (M). Mas o git diff --check ("confira") achou: leftover conflict marker, "marcador de conflito esquecido", nas linhas 5, 7, 9 e 11 (os quatro marcadores do estilo diff3). O --cached confere o que já está na área de preparo (veja git diff --staged, que é o mesmo que --cached); sem ele, o que ainda não foi preparado. Foi aqui que a Ana usou o git checkout -m da seção 3 para recomeçar.

Três jeitos de procurar, antes do git add:

$ grep -n '<<<<<<<\|>>>>>>>' bolo.txt
5:<<<<<<< HEAD
9:>>>>>>> forno
$ git diff --check
bolo.txt:5: leftover conflict marker
bolo.txt:7: leftover conflict marker
bolo.txt:9: leftover conflict marker
$ git diff --name-only --diff-filter=U
bolo.txt
grep -n '…' bolo.txt
Procura as linhas com os marcadores de começo e fim, com o número da linha (-n). O grep é um programa do terminal, não do Git, e serve em qualquer arquivo de texto.
git diff --check
O Git procura marcadores nos arquivos ainda não preparados e mostra arquivo e linha. Se não achar nada, não mostra nada.
git diff --name-only --diff-filter=U
Lista só os nomes dos arquivos ainda em conflito (U = unmerged). Útil quando o merge tem muitos arquivos.

Quando dá errado

Commitou antes do git add: Committing is not possible because you have unmerged files 
$ git commit --no-edit
U       bolo.txt
error: Committing is not possible because you have unmerged files.
hint: Fix them up in the work tree, and then use 'git add/rm <file>'
hint: as appropriate to mark resolution and make a commit.
fatal: Exiting because of an unresolved conflict.

"Não é possível commitar porque você tem arquivos não mesclados (U bolo.txt). Conserte-os e use git add/git rm para marcar a resolução." Mesmo que você já tenha editado o arquivo, o Git só sabe que terminou depois do git add. Como resolver: confira o arquivo (sem marcadores?), git add bolo.txt e git commit de novo.

Os marcadores foram parar num commit

O git add aceitou um arquivo com marcadores (seção 6), e o commit também aceita. O sintoma aparece depois: a página do site mostrando <<<<<<< HEAD, o programa que deixa de rodar. Como confirmar: grep -n '<<<<<<<' bolo.txt. Como resolver: o merge já terminou, então corrija o arquivo, e faça um commit novo (git commit -am "Remove marcadores de conflito esquecidos"). Como evitar: rode git diff --check antes do git add e leia o git diff antes do commit.

"Resolvi, mas o status ainda diz ambos modificados"

Você editou o arquivo, apagou os marcadores, salvou… e o git status continua com o arquivo em "Caminhos não mesclados" (seção 1, passo 3). Não é erro: faltou o git add. O Git não olha o conteúdo para decidir se você terminou.

Escolheu --ours achando que era o outro lado

É fácil confundir: num merge, --ours é o branch em que você está (o que aparece em No ramo main), e --theirs é o branch que você escreveu no git merge. Como confirmar: cat no arquivo depois da escolha. Como resolver: antes do commit, é só escolher de novo (git restore --theirs), ou recriar o conflito (git restore --merge).

Resumo

  • Resolver um conflito é: deixar o arquivo como deve ficar, sem marcadores; git add para marcar como resolvido; git commit (ou git commit --no-edit, ou git merge --continue) para criar o commit de merge.
  • O git status guia cada passo: "Caminhos não mesclados" → "Todos os conflitos foram corrigidos mas você continua mesclando" → nothing to commit, working tree clean.
  • Para ficar com um lado inteiro: git restore --ours (o branch onde você está) ou --theirs (o que está chegando); o antigo git checkout --ours/--theirs faz o mesmo.
  • Escolheu errado? git restore --merge ou git checkout -m recriam os marcadores, enquanto o merge não terminou.
  • O VS Code mostra botões (Accept Current, Incoming, Both) que só editam o arquivo; o git add e o commit continuam sendo seus.
  • O Git aceita marcadores esquecidos no git add e no commit: confira antes com git diff --check.

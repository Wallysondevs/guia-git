Git Conflitos de Merge

Na aula Merge de Três Vias, os dois branches mudaram arquivos diferentes, e o Git juntou tudo sozinho. Mas e se a Ana, no main, mudar o tempo de forno do bolo para 45 minutos e, no outro branch, o tempo virar 30 minutos? O Git não tem como saber qual dos dois está certo. Ele para no meio do merge e pede ajuda: é o conflito (em inglês, merge conflict). Conflito não é erro nem defeito: é o Git sendo honesto e deixando a decisão com você.

Você vai aprender
  • Quando um conflito acontece (e quando não acontece).
  • A mensagem CONFLITO do git merge e o git status durante o conflito, linha por linha.
  • Como ler os marcadores que o Git escreve dentro do arquivo: <<<<<<<, ======= e >>>>>>>.
  • Outros tipos de conflito: arquivo apagado de um lado e mudado do outro, e arquivo criado nos dois lados.
  • O que o Git não deixa fazer enquanto o conflito existe. (Resolver é a próxima aula: Resolvendo Conflitos.)

Todas as saídas desta aula vieram do Git 2.53.0 da máquina da Ana (usuária ana, computador notebook), com o sistema em português. A tradução do Git no Ubuntu é incompleta: algumas mensagens do conflito saem em português, outras em inglês, às vezes no mesmo bloco. Elas estão copiadas como saíram, e as frases em inglês ganham tradução na explicação.

A ideia: dois bilhetes para o mesmo bolo

A Ana deixa a receita de bolo colada na geladeira com "forno: 180 graus por 40 minutos". De manhã, ela risca e escreve "45 minutos". À tarde, o irmão, que não viu o bilhete novo, pega uma cópia antiga e escreve "200 graus por 30 minutos". Quem passa a receita a limpo à noite fica com dois bilhetes que discordam na mesma linha. Não dá para ficar com os dois; alguém precisa decidir.

No Git é igual. No merge de três vias, o Git compara cada lado com o ancestral comum, linha por linha:

O que aconteceu com uma linhaO que o Git faz
Ninguém mudouMantém a linha
Só um lado mudouFica com a mudança desse lado, sozinho
Os dois mudaram, e ficou igual nos doisFica com essa versão, sozinho
Os dois mudaram, cada um de um jeitoConflito: para e pergunta a você

Repare: conflito tem a ver com a mesma parte do mesmo arquivo (a mesma linha, ou linhas vizinhas). Duas pessoas mexendo no mesmo arquivo, em partes diferentes, não dá conflito.

1. Montando o conflito

A receita de bolo começa assim, num único commit no main:

Bolo de cenoura
- 3 cenouras
- 3 ovos
- 2 xícaras de açúcar
Forno: 180 graus por 40 minutos

No branch forno, a Ana troca a última linha para 200 graus por 30 minutos e cria a cobertura.txt. Depois, no main, troca a mesma linha para 180 graus por 45 minutos:

$ git switch -c forno
Switched to a new branch 'forno'
$ sed -i 's/180 graus por 40/200 graus por 30/' bolo.txt
$ printf 'Cobertura de chocolate\n' > cobertura.txt
$ git add bolo.txt cobertura.txt
$ git commit -q -m 'Assa mais quente e mais rápido'
$ git switch main
Switched to branch 'main'
$ sed -i 's/180 graus por 40/180 graus por 45/' bolo.txt
$ git commit -q -am 'Aumenta o tempo de forno'

$ git log --oneline --graph --all
* 70c15e0 (forno) Assa mais quente e mais rápido
| * aa84752 (HEAD -> main) Aumenta o tempo de forno
|/
* a071866 Adiciona a receita de bolo

O sed -i 's/velho/novo/' troca um texto dentro do arquivo, como o "Localizar e substituir" de um editor; aqui ele só serve para a Ana mudar a linha do forno sem abrir o editor (você pode mudar a linha no editor que preferir). O -am do último commit prepara e commita de uma vez o arquivo já rastreado (aula git commit). O desenho é o mesmo "Y" da aula anterior: o main e o forno saíram do a071866 e andaram, cada um com um commit. A diferença é que, agora, os dois mudaram a última linha do bolo.txt, cada um de um jeito.

2. O merge que para no meio

$ git merge forno
Mesclagem automática de bolo.txt
CONFLITO (conteúdo): conflito de mesclagem em bolo.txt
Automatic merge failed; fix conflicts and then commit the result.
$ echo $?
1

Linha por linha:

Mesclagem automática de bolo.txt
"Mesclando automaticamente o bolo.txt". O Git percebeu que os dois lados mexeram nesse arquivo e tentou juntá-los sozinho, linha por linha. (Em inglês: Auto-merging bolo.txt.)
CONFLITO (conteúdo): conflito de mesclagem em bolo.txt
Não deu. Há um conflito de conteúdo: as mesmas linhas foram mudadas dos dois lados. (Em inglês: CONFLICT (content): Merge conflict in bolo.txt.) Num merge com vários arquivos, aparece uma linha CONFLITO para cada arquivo com problema.
Automatic merge failed; fix conflicts and then commit the result.
"O merge automático falhou; conserte os conflitos e depois faça o commit do resultado." Esta frase está em inglês mesmo no sistema em português. Ela já diz o que fazer: consertar e commitar.
echo $? → 1
O código de saída do git merge (veja O Mínimo de Terminal). 0 seria "deu certo"; 1 avisa que o merge não terminou. Scripts usam isso para saber que precisam de uma pessoa.
O merge ficou pela metade

Depois dessa mensagem, o repositório está num estado especial: "merge em andamento". O commit de merge ainda não existe. O Git juntou o que conseguiu, deixou o resto para você e está esperando. Enquanto isso, nada de trocar de branch ou fazer outro merge: primeiro termine (próxima aula) ou desista (Desistindo de um Merge).

3. O git status durante o conflito

Na dúvida, git status. Durante um conflito, ele é o seu guia:

$ git status
No ramo main
Você tem caminhos não mesclados.
  (fixar conflitos e executar "git commit")
  (use "git merge --abort" to abort the merge)

Mudanças a serem submetidas:
        new file:   cobertura.txt

Caminhos não mesclados:
  (usar "git add <arquivo>..." para marcar resolução)
        ambos modificados:   bolo.txt
Você tem caminhos não mesclados.
"Você tem caminhos (arquivos) que não foram juntados." É o jeito do git status dizer que há um merge em andamento, com conflito. (Em inglês: You have unmerged paths.)
(fixar conflitos e executar "git commit")
A primeira saída: conserte os conflitos e rode git commit. É o que você vai fazer na próxima aula.
(use "git merge --abort" to abort the merge)
A outra saída: "use git merge --abort para cancelar o merge" e voltar a como estava antes. Aula Desistindo de um Merge.
Mudanças a serem submetidas: new file: cobertura.txt
O que o Git conseguiu juntar sozinho já está na área de preparo (new file = "arquivo novo"). A cobertura.txt só existia do lado do forno, então não tem conflito: ela vai entrar no commit de merge.
Caminhos não mesclados:
A lista do que você precisa resolver. A dica embaixo diz como avisar o Git que um arquivo foi resolvido: git add <arquivo> ("para marcar resolução").
ambos modificados: bolo.txt
O tipo do conflito: o arquivo foi modificado pelos dois lados (em inglês, both modified). Mais adiante você vê outros tipos.

4. Dentro do arquivo: os marcadores de conflito

O Git não deixa o arquivo como estava: ele escreve as duas versões da parte em conflito dentro do próprio arquivo, separadas por marcadores. Veja o bolo.txt agora:

$ cat bolo.txt
Bolo de cenoura
- 3 cenouras
- 3 ovos
- 2 xícaras de açúcar
<<<<<<< HEAD
Forno: 180 graus por 45 minutos
=======
Forno: 200 graus por 30 minutos
>>>>>>> forno

Os marcadores dividem o trecho em conflito em duas partes:

<<<<<<< HEAD
Sete sinais de "menor que" e o nome HEAD: começa o trecho em conflito. Daqui até o ======= vem a versão do HEAD, isto é, do branch em que você está (o main): 180 graus por 45 minutos.
=======
Sete sinais de igual: a divisa entre as duas versões.
>>>>>>> forno
Sete sinais de "maior que" e o nome do branch que está chegando: fecha o trecho. Entre o ======= e esta linha vem a versão do forno: 200 graus por 30 minutos.
<<<<<<< HEAD                         ┐
Forno: 180 graus por 45 minutos       │ a NOSSA versão (main, onde você está)
=======                               ┤
Forno: 200 graus por 30 minutos       │ a versão DELES (o branch forno)
>>>>>>> forno                        ┘

Tudo o que está fora dos marcadores (as quatro primeiras linhas) não teve conflito: os dois lados concordam. Num arquivo grande, pode haver vários trechos com marcadores; o resto do arquivo já está juntado.

"Nosso" e "deles"

Nos merges, a parte de cima (HEAD) é a nossa (em inglês, ours): o branch em que você está, que recebe o merge. A parte de baixo é a deles (theirs): o branch que está chegando. Esses dois nomes voltam na próxima aula, nas opções --ours e --theirs.

O git diff durante o conflito

$ git diff
diff --cc bolo.txt
index 798cdff,e6355df..0000000
--- a/bolo.txt
+++ b/bolo.txt
@@@ -2,4 -2,4 +2,8 @@@ Bolo de cenour
  - 3 cenouras
  - 3 ovos
  - 2 xícaras de açúcar
++<<<<<<< HEAD
 +Forno: 180 graus por 45 minutos
++=======
+ Forno: 200 graus por 30 minutos
++>>>>>>> forno

Durante o conflito, o git diff mostra um formato especial, o diff combinado (diff --cc), com duas colunas de sinais no começo de cada linha: a primeira compara o arquivo com o nosso lado (o HEAD), a segunda com o lado deles (o forno). Um + numa coluna quer dizer "esta linha não existe naquele lado". Assim, +Forno: 180… (espaço, depois +) existe no nosso lado e não no deles; + Forno: 200… existe no deles e não no nosso; e ++ marca as linhas que não existem em nenhum dos dois: os marcadores, que o Git inventou. Não precisa decorar: o que importa é que o git diff mostra só os trechos com conflito, o que ajuda muito num arquivo grande. (O git diff normal está em git diff.)

E a cobertura.txt?

$ cat cobertura.txt
Cobertura de chocolate

Arquivo inteiro, sem nenhum marcador: ele não tem conflito. O merge não é "tudo ou nada": o Git faz tudo o que consegue e só deixa para você o que não sabe decidir. E o histórico? Um git log --oneline --graph --all agora mostra exatamente o mesmo desenho de antes do merge: o commit de merge ainda não existe. Ele só nasce quando você terminar.

Missão: no repositório receitas, o main e o branch forno mudaram a mesma linha do bolo.txt. Faça o merge do forno no main, leia o git status e veja os marcadores com cat bolo.txt. (Não precisa resolver: isso é a próxima aula.)

5. Vendo a base também: o estilo diff3

Os marcadores normais mostram "o nosso" e "o deles", mas não mostram como era antes. Às vezes é exatamente isso que falta para decidir. Com a configuração merge.conflictStyle, o Git mostra também a versão do ancestral comum:

$ git config merge.conflictStyle diff3
$ git merge forno
Mesclagem automática de bolo.txt
CONFLITO (conteúdo): conflito de mesclagem em bolo.txt
Automatic merge failed; fix conflicts and then commit the result.
$ cat bolo.txt
Bolo de cenoura
- 3 cenouras
- 3 ovos
- 2 xícaras de açúcar
<<<<<<< HEAD
Forno: 180 graus por 45 minutos
||||||| a071866
Forno: 180 graus por 40 minutos
=======
Forno: 200 graus por 30 minutos
>>>>>>> forno

(Para repetir o merge com o estilo novo, a Ana primeiro desistiu do anterior com git merge --abort, da aula Desistindo de um Merge.) Apareceu um trecho a mais, entre ||||||| (sete barras verticais) e o =======: a linha como ela era no ancestral comum, o commit a071866. Agora a história fica clara: era 180 graus por 40 minutos; no main, a Ana só mudou o tempo (45); no forno, mudaram a temperatura e o tempo (200 e 30). Com a base à vista, fica mais fácil decidir. Existe também o estilo zdiff3 (do Git 2.35 em diante), que faz o mesmo e tira do trecho em conflito as linhas que ficaram iguais nos dois lados; neste exemplo, de uma linha só, a saída foi idêntica. Para usar sempre, em todos os repositórios: git config --global merge.conflictStyle zdiff3 (veja Configurações Úteis). Para voltar ao estilo normal: git config --unset merge.conflictStyle.

6. Outros tipos de conflito

Nem todo conflito é "a mesma linha mudada dos dois lados". A Ana preparou outra situação: no branch limpeza, ela apagou o pudim.txt e criou uma compras.txt; no main, ela mudou o pudim.txt e criou outra compras.txt, com conteúdo diferente:

$ git merge limpeza
Mesclagem automática de compras.txt
CONFLITO (adicionar/adicionar): conflito de mesclagem em compras.txt
CONFLICT (modify/delete): pudim.txt deleted in limpeza and modified in HEAD.  Version HEAD of pudim.txt left in tree.
Automatic merge failed; fix conflicts and then commit the result.
$ git status
No ramo main
Você tem caminhos não mesclados.
  (fixar conflitos e executar "git commit")
  (use "git merge --abort" to abort the merge)

Caminhos não mesclados:
  (use "git add/rm <file>..." as appropriate to mark resolution)
        ambos adicionaram:   compras.txt
        excluídos por eles:  pudim.txt

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
$ cat compras.txt
Lista de compras
<<<<<<< HEAD
- farinha
=======
- ovos
>>>>>>> limpeza
CONFLITO (adicionar/adicionar) … compras.txt
Os dois lados criaram um arquivo com o mesmo nome, com conteúdos diferentes (em inglês, add/add). No git status: ambos adicionaram. Dentro do arquivo, os marcadores de sempre: a primeira linha, igual nos dois, ficou fora deles.
CONFLICT (modify/delete): pudim.txt deleted in limpeza and modified in HEAD.
"O pudim.txt foi apagado no limpeza e modificado no HEAD." Um lado jogou o arquivo fora, o outro continuou mexendo nele. Não há linha para marcar: a dúvida é se o arquivo fica ou sai.
Version HEAD of pudim.txt left in tree.
"A versão do HEAD do pudim.txt foi deixada na pasta." Por segurança, o Git deixou na pasta o arquivo com as mudanças do main. No git status: excluídos por eles (o lado "deles", o limpeza, apagou). Se fosse o contrário, apareceria excluídos por nós.
(use "git add/rm <file>..." as appropriate to mark resolution)
"Use git add ou git rm, conforme o caso, para marcar a resolução": git add pudim.txt para manter o arquivo, git rm pudim.txt para aceitar que ele saia (aula git rm).
nenhuma modificação adicionada à submissão
Desta vez, nada entrou sozinho na área de preparo: os dois arquivos que mudaram estão em conflito.

Quando dá errado

No conflito em si, nada deu "errado": é o funcionamento normal do Git. O que dá errado é tentar seguir a vida como se o conflito não existisse. Enquanto o merge está em andamento, o Git recusa vários comandos. Todas as mensagens abaixo saíram no repositório do bolo.txt, com o conflito ainda aberto.

Tentou commitar sem resolver: Committing is not possible because you have unmerged files 
$ git commit -m 'teste'
U       bolo.txt
error: Committing is not possible because you have unmerged files.
hint: Fix them up in the work tree, and then use 'git add/rm <file>'
hint: as appropriate to mark resolution and make a commit.
fatal: Exiting because of an unresolved conflict.

O U (de unmerged, "não mesclado") marca o arquivo com problema. "Erro: não é possível commitar porque você tem arquivos não mesclados. Dica: conserte-os na pasta de trabalho e use git add/git rm para marcar a resolução e fazer o commit. Fatal: saindo por causa de um conflito não resolvido." Como resolver: resolva o arquivo e rode git add bolo.txt antes do git commit (aula Resolvendo Conflitos).

Tentou trocar de branch: cannot switch branch while merging 
$ git switch forno
fatal: cannot switch branch while merging
Consider "git merge --quit" or "git worktree add".

"Fatal: não dá para trocar de branch durante um merge. Considere git merge --quit ou git worktree add." Trocar de branch agora deixaria o merge pela metade, perdido. As duas sugestões do Git são para casos avançados (veja git worktree); para quem está começando, as saídas são terminar o merge ou desistir dele com git merge --abort (aula Desistindo de um Merge), e só então trocar de branch.

Tentou outro merge por cima: Merging is not possible because you have unmerged files 
$ git merge forno
error: Merging is not possible because you have unmerged files.
hint: Fix them up in the work tree, and then use 'git add/rm <file>'
hint: as appropriate to mark resolution and make a commit.
fatal: Exiting because of an unresolved conflict.

"Não é possível fazer merge porque você tem arquivos não mesclados." Um merge de cada vez: termine ou desista deste antes de começar outro.

"O que é isso no meu arquivo?" Marcadores esquecidos

Se você fechar o terminal e voltar no dia seguinte, o merge continua em andamento, e os marcadores continuam dentro do arquivo. Um site com <<<<<<< HEAD no meio da página, um programa que não roda mais: quase sempre é um conflito que ficou para trás. Como confirmar: git status (procure "Caminhos não mesclados") e um cat no arquivo. Como resolver: a próxima aula, Resolvendo Conflitos, que também mostra como o Git ajuda a achar marcadores esquecidos.

Onde o Git guarda o merge em andamento?

Dentro da pasta .git apareceram arquivos novos durante o conflito. O MERGE_HEAD guarda o hash do commit que está chegando, e o MERGE_MSG, a mensagem que o commit de merge vai ter, já com a lista dos arquivos que tiveram conflito:

$ cat .git/MERGE_HEAD
70c15e0ba234b92f9d26aee6ba628f258e86a718
$ cat .git/MERGE_MSG
Merge branch 'forno'

# Conflicts:
#       bolo.txt

É pela existência do MERGE_HEAD que o git status sabe que você "continua mesclando". Não mexa nesses arquivos à mão: o git commit e o git merge --abort cuidam deles.

Resumo

  • Conflito acontece quando os dois lados de um merge mudam a mesma parte do mesmo arquivo, cada um de um jeito. Partes diferentes do mesmo arquivo o Git junta sozinho.
  • O git merge avisa com CONFLITO e para no meio: o merge fica em andamento, sem commit de merge.
  • O git status lista os arquivos em conflito em "Caminhos não mesclados" e ensina as saídas: resolver e git commit, ou git merge --abort.
  • Dentro do arquivo, <<<<<<< HEAD abre a nossa versão, ======= separa, e >>>>>>> forno fecha a versão deles. Com merge.conflictStyle diff3, aparece também a base (|||||||).
  • Também há conflito quando um lado apaga um arquivo que o outro mudou, ou quando os dois criam o mesmo arquivo com conteúdos diferentes.
  • Como resolver, na próxima aula: Resolvendo Conflitos.

Git Por que Controle de Versão

Todo mundo que já escreveu um trabalho grande conhece a pasta cheia de final.docx, final2.docx e final-agora-vai.docx. Um sistema de controle de versão é a solução organizada para esse problema: ele guarda cada versão, diz o que mudou, quem mudou, quando e por quê. Nesta aula você vai ver o problema, a solução e onde o Git se encaixa.

Você vai aprender
  • Os problemas de guardar versões "na mão", com cópias de arquivos.
  • As quatro perguntas que um controle de versão responde: o quê, quem, quando e por quê.
  • Os três tipos de controle de versão: local, centralizado e distribuído.
  • Por que o Git, um sistema distribuído, virou o padrão.

O problema: a pasta do "final de verdade"

A Ana está escrevendo o TCC. Com medo de estragar o texto, ela faz uma cópia a cada mudança grande. Depois de um mês, a pasta está assim (o -1 do ls pede um nome por linha):

$ ls -1
tcc-final-2.docx
tcc-final-agora-vai.docx
tcc-final-de-verdade.docx
tcc-final.docx
tcc-revisado-bruno.docx
tcc-v2.docx
tcc-v3-depois-da-reuniao.docx
tcc.docx

Repare nas perguntas que essa pasta não responde:

  • Qual é a versão certa? final-de-verdade é mais nova que agora-vai? Só olhando a data de cada arquivo, e torcendo para nenhuma cópia ter sido aberta e salva de novo.
  • O que mudou de uma para outra? Seria preciso abrir as duas lado a lado e procurar as diferenças no olho.
  • Por que mudou? O nome do arquivo não diz que a v3 foi "a versão depois da reunião com o orientador".
  • E quando o Bruno ajudar? Ele manda tcc-revisado-bruno por e-mail, a Ana continuou mexendo na dela… e agora alguém tem de juntar as duas à mão.

Além disso, cada cópia ocupa espaço inteiro, mesmo quando só uma vírgula mudou.

A solução: um sistema que guarda a história

Um sistema de controle de versão (em inglês, version control system, ou VCS) é um programa que fica de olho numa pasta e, quando você pede, registra como ela está. Em vez de dez cópias, existe uma pasta só, com o arquivo atual, e um "cofre" escondido com todas as versões anteriores.

Pense no caderno de um laboratório de ciências: cada experimento é anotado com data, nome de quem fez e o que observou. Ninguém arranca páginas; para corrigir, escreve-se uma anotação nova. O controle de versão é esse caderno, só que preenchido automaticamente para os seus arquivos.

Esta é a mesma história do TCC, guardada pelo Git. O comando git log mostra os registros do mais novo para o mais antigo:

$ ls
tcc.md
$ git log

Author: Ana Souza <ana@exemplo.com>                 « quem
Date:   Thu Oct 15 10:30:00 2026 -0300                « quando

    Acrescenta a conclusão pedida pelo orientador     « por quê

commit 68319cf9b38aa303504ef8453cb8d9a6f79e30f2
Author: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

    Acrescenta a metodologia

commit a65079a47fe7e5727e5276a4914f18eee2557865      « o primeiro registro
Author: Ana Souza <ana@exemplo.com>

    Começa o TCC com o título e a introdução

Cada registro (cada commit) responde às quatro perguntas:

PerguntaOnde está a resposta
Quem mudou?Na linha Author: ("autor"): nome e e-mail de quem fez o commit.
Quando?Na linha Date: ("data"), com dia, hora e fuso horário.
Por quê?Na mensagem, escrita por quem fez o commit, logo abaixo da data.
O quê?O Git sabe exatamente que linhas entraram e saíram. O git log --stat (abaixo) resume; o git diff e o git show mostram linha por linha.

Todas as datas são iguais porque o relógio da máquina da Ana, no laboratório deste guia, está parado em 15/10/2026 10:30; num computador de verdade, cada commit tem a hora em que foi feito. O número comprido depois de commit é o hash, a identidade do registro (aula O Hash do Commit). E a pasta tem um arquivo só, o tcc.md: as versões antigas estão guardadas pelo Git, não espalhadas em cópias.

"O quê": o resumo do que mudou

Com a opção --stat ("estatística"), o git log diz também que arquivos cada commit mudou e quantas linhas entraram (+) e saíram (-):

$ git log --stat -1
commit 892a4d1065f3139eabb59162b1d124940102da90
Author: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

    Acrescenta a conclusão pedida pelo orientador

 tcc.md | 2 ++                                        « o arquivo tcc.md ganhou 2 linhas
 1 file changed, 2 insertions(+)                      « "1 arquivo mudou, 2 linhas inseridas"
git log
Mostra o histórico.
--stat
Acrescenta, a cada commit, a lista de arquivos alterados e a contagem de linhas.
-1
Mostra só 1 commit, o mais recente. (-3 mostraria os três últimos.)

Missão: o terminal está na pasta tcc, já com três commits. Rode git log e responda para você mesma: qual foi o primeiro commit, e por que o último foi feito? Depois experimente git log --stat e git log --oneline.

Os três tipos de controle de versão

Os sistemas de controle de versão evoluíram em três "gerações". Saber a diferença ajuda a entender por que o Git funciona do jeito que funciona.

1. Local: tudo no seu computador

Os primeiros sistemas, como o RCS (de 1982), guardavam as versões de cada arquivo numa pasta do próprio computador. Resolviam o "final_v2", mas não ajudavam a trabalhar em equipe.

  seu computador
  ┌──────────────────────────┐
  │ arquivo  ◄──  versões    │
  └──────────────────────────┘

2. Centralizado: um servidor guarda a história

Sistemas como o CVS (anos 1990) e o Subversion, ou SVN (2000), guardam a história num servidor central. Cada pessoa tem só a versão atual dos arquivos e pede ao servidor para registrar cada mudança. É simples de entender, mas: sem conexão com o servidor, não dá para registrar nada nem ver o histórico; e, se o servidor perde os dados, a história toda vai junto.

        ┌──────────────┐
        │   servidor   │  ◄── a história fica só aqui
        │  (história)  │
        └──────┬───────┘
     ┌─────────┼─────────┐
   Ana       Bruno     Carla     ◄── cada um tem só os arquivos atuais

3. Distribuído: cada um tem a história inteira

No Git (e no Mercurial, que nasceu na mesma época), cada pessoa tem uma cópia completa do repositório, com toda a história. Commits, histórico, branches: tudo funciona sem internet, e rápido, porque é tudo local. Para trocar trabalho, as cópias conversam entre si; na prática, quase todo mundo combina um ponto de encontro, como o GitHub.

            ┌──────────────┐
            │    GitHub    │
            │  (história)  │
            └──────┬───────┘
       ┌───────────┼───────────┐
  Ana (história)  Bruno (história)  Carla (história)
Local (RCS)Centralizado (SVN)Distribuído (Git)
Onde fica a históriaNo seu computadorSó no servidorEm todas as cópias
Funciona sem internet?SimSó para editar arquivosSim, para quase tudo
Trabalho em equipeNãoSimSim
Se um computador quebraPerde tudoSe for o servidor, perde tudoQualquer outra cópia tem tudo
Criar e juntar ramos—Possível, mas trabalhosoRápido e do dia a dia
Controle de versão não é só para programadores

Ele serve para qualquer coisa feita de arquivos de texto: o TCC escrito em Markdown ou LaTeX, a documentação de uma empresa, as receitas da Ana, as configurações de um servidor, até livros. Este guia mesmo é guardado num repositório Git.

Quando dá errado

Rodei git log numa pasta que não é um repositório 
$ git log
fatal: not a git repository (or any of the parent directories): .git

O que aconteceu: o controle de versão não "liga sozinho" em todas as pastas. A pasta tcc-sem-git nunca foi transformada em repositório, então o Git não tem história nenhuma para mostrar. A mensagem saiu em inglês (o Git 2.53 ainda não traduz esta) e quer dizer: "fatal: não é um repositório git (nem nenhuma das pastas acima dela): .git". O .git é a pasta escondida onde o Git guarda a história; ele procurou nela e nas pastas acima e não achou.

Como resolver: entre na pasta certa (cd ~/tcc) ou, se é um projeto novo, crie o repositório com git init (aula Criando um Repositório).

"Usei controle de versão e mesmo assim perdi o trabalho"

O que aconteceu: o Git só guarda o que você registra. Mudanças que nunca entraram num commit não estão na história. Se a Ana escreveu o capítulo inteiro durante uma semana sem fazer nenhum commit e apagou o arquivo, o Git não tem como devolver.

Como evitar: faça commits pequenos e frequentes, sempre que terminar uma parte que faz sentido sozinha. A aula Boas Práticas volta a esse assunto.

2. Num sistema centralizado, como o SVN, o que acontece se o servidor ficar fora do ar?

3. A Ana passou uma semana escrevendo sem fazer nenhum commit e apagou o arquivo sem querer. O Git consegue devolver esse texto?

4. Só o último

Complete para ver só o commit mais recente, com a lista de arquivos alterados:

git log --stat

Resumo

  • Guardar versões com cópias (final, final2…) não diz o que mudou, por que, nem quem mudou, e complica o trabalho em equipe.
  • Um sistema de controle de versão guarda cada registro com o quê, quem, quando e por quê, numa pasta só.
  • Há três tipos: local, centralizado (a história num servidor) e distribuído (a história em todas as cópias).
  • O Git é distribuído: funciona sem internet e cada cópia é um backup completo.
  • O Git só guarda o que você registra: faça commits pequenos e frequentes.

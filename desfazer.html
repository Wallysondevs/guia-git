Desfazendo: o Mapa

O maior medo de quem começa no Git é "estraguei tudo". A boa notícia: quase tudo no Git pode ser desfeito. A má notícia: existem vários comandos de desfazer, cada um para uma situação, e usar o errado pode piorar as coisas. Esta página é o mapa: você diz o que quer desfazer, ele diz qual comando usar e em qual aula aprender. As aulas seguintes deste grupo ensinam cada comando em detalhe.

Você vai aprender
  • As três perguntas que decidem qual comando usar.
  • Onde a mudança está (pasta, área de preparo, commit, GitHub) e como desfazer em cada lugar.
  • Uma tabela "o que você quer desfazer → qual comando", com links para as aulas.
  • Quais comandos são seguros e quais jogam trabalho fora sem volta.
  • A ler as dicas de desfazer que o próprio git status mostra.

As saídas desta página saíram do Git do Ubuntu 26.04 (git version 2.53.0), na máquina da Ana (usuária ana, computador notebook), com o sistema em português.

A ideia: onde está a mudança?

Pense numa carta. Enquanto ela está no rascunho, você apaga e reescreve à vontade. Depois de passada a limpo e posta no envelope, ainda dá para abrir e trocar. Depois de colocada na caixa do correio, você já não pega de volta: o que dá para fazer é mandar uma segunda carta, "desconsidere a anterior".

No Git, uma mudança passa pelos mesmos lugares, e o jeito de desfazer depende de onde ela está:

  sua pasta            área de preparo         histórico (commits)        GitHub
 (o rascunho)          (o envelope)            (a carta enviada a você)   (o correio)
 ┌──────────┐ git add  ┌──────────┐ git commit ┌──────────┐  git push   ┌──────────┐
 │ mudanças │ ───────► │ mudanças │ ─────────► │  commit  │ ──────────► │  commit  │
 └──────────┘          └──────────┘            └──────────┘             └──────────┘
   desfazer:             desfazer:               desfazer:                desfazer:
   git restore           git restore --staged    commit --amend           git revert
   git clean (novos)                             git reset                (um commit novo
                                                 git revert                que desfaz)

Quanto mais à direita, mais cuidado: o que já foi enviado para o GitHub pode já estar no computador de outras pessoas.

As três perguntas

  1. A mudança já foi commitada? Rode git status. Se o arquivo aparece lá, a mudança ainda não foi commitada (está na pasta ou na área de preparo). Se o git status está limpo, ela está num commit: veja o git log --oneline.
  2. Se foi commitada: o commit já foi enviado (git push)? Se não, você pode reescrever o histórico local (--amend, reset). Se sim, desfaça com um commit novo (revert) e não reescreva o que é público (veja A Regra de Ouro).
  3. Você quer manter as mudanças ou jogá-las fora? Muitos comandos têm uma versão que só "tira do lugar" (as mudanças continuam na pasta) e outra que apaga. Na dúvida, prefira a que mantém.

O git status já diz como desfazer

Antes de procurar na internet, leia o git status: ele mostra, entre parênteses, o comando de desfazer de cada situação. A Ana preparou uma mudança no bolo, mudou o pudim sem preparar e criou uma lasanha nova:

$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt

Changes not staged for commit:
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   pudim.txt

Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	lasanha.txt
(use "git restore --staged <file>..." to unstage)
Na seção do que está preparado: "use git restore --staged para tirar da área de preparo" (unstage = "despreparar"). As mudanças voltam a ser só da pasta; nada se perde. Aula Tirando da Área de Preparo.
(use "git restore <file>..." to discard changes in working directory)
Na seção do que não está preparado: "use git restore para descartar as mudanças na pasta de trabalho". O arquivo volta a ser como no último commit, e as mudanças se perdem. Aula git restore.
Arquivos não monitorados
Aqui o Git não sugere desfazer: arquivos novos ele não conhece. Para apagá-los, o rm comum ou o git clean.

Seguindo as dicas:

$ git restore pudim.txt
$ git restore --staged bolo.txt
$ git status --short
 M bolo.txt
?? lasanha.txt

O pudim voltou ao último commit (sumiu da lista); a mudança do bolo saiu da área de preparo, mas continua na pasta ( M, na segunda coluna: modificado e não preparado); a lasanha continua como estava.

Em tutoriais antigos

O git restore existe desde o Git 2.23 (de 2019). Antes, as dicas do git status eram git checkout -- <file> (no lugar de git restore) e git reset HEAD <file> (no lugar de git restore --staged). Esses comandos ainda funcionam, e você vai encontrá-los em respostas antigas na internet; as aulas git restore e Tirando da Área de Preparo mostram os dois jeitos.

Missão: rode git status e siga as dicas dele: descarte a mudança do pudim.txt (a "calda estragada") e tire da área de preparo a mudança do bolo.txt, sem perdê-la (a farinha deve continuar no arquivo).

O que o Git não consegue desfazer

O Git guarda o que foi commitado (e, por um tempo, até commits "apagados", pelo reflog). O que nunca foi commitado nem preparado não tem cópia em lugar nenhum. Por isso os comandos marcados com ⚠ (git restore sem --staged, git clean -f, git reset --hard) são os perigosos: eles jogam fora trabalho que o Git nunca guardou. Na dúvida, faça um commit (ou um git stash) antes: um commit a mais é fácil de desfazer; trabalho perdido, não.

O fluxograma

Quero desfazer uma mudança.
│
├─ Aparece no git status? (ainda não commitei)

│   └─ Está em "Arquivos não monitorados" (novo)

│
└─ Não aparece: já está num commit
    ├─ Ainda não dei git push
    │     ├─ é o último commit e só quero corrigir ... git commit --amend
    │     └─ quero tirar o(s) commit(s) .............. git reset (--soft / --mixed / --hard)
    └─ Já dei git push ................................ git revert COMMIT

O mesmo desfazer, de formas diferentes

Muitas situações têm um comando novo e um antigo. As aulas usam os novos, mas você vai encontrar os antigos:

SituaçãoComando novo (Git 2.23+)Comando antigo, equivalente
Descartar mudanças de um arquivogit restore arquivogit checkout -- arquivo
Tirar da área de preparogit restore --staged arquivogit reset arquivo ou git reset HEAD arquivo
Pegar um arquivo de um commit antigogit restore --source=COMMIT arquivogit checkout COMMIT -- arquivo (que também prepara o arquivo)

O git checkout antigo fazia coisas demais (trocar de branch, descartar mudanças, pegar arquivos antigos), e um pequeno erro de digitação trocava uma coisa pela outra. Por isso o Git dividiu o trabalho entre git switch (branches; aula git switch) e git restore (arquivos). Mais em git checkout: o Comando Antigo.

Quando dá errado

"Rodei um comando de desfazer e piorou"

Pare e não rode mais nada às pressas. Rode git status e git log --oneline para ver onde você está. Se o problema é um commit que sumiu, o git reflog quase sempre o encontra. Se o problema é uma mudança que nunca foi commitada e foi descartada com git restore, git reset --hard ou git clean -f, o Git não tem cópia: procure no histórico do seu editor (o VS Code guarda um "Histórico Local" dos arquivos; ilustrativo) ou numa cópia de segurança.

"Não sei se já dei push"

Rode git status: num branch ligado ao GitHub, ele diz se o seu branch está à frente do remoto, isto é, se há commits que ainda não foram enviados. Veja Branch de Rastreamento. Na dúvida, trate como enviado e use git revert.

Resumo

  • Antes de desfazer, responda: já commitei? Já enviei? Quero manter as mudanças?
  • Não commitado: git restore (descarta), git restore --staged (só tira da área de preparo), git clean (arquivos novos).
  • Commitado e não enviado: git commit --amend ou git reset.
  • Já enviado: git revert.
  • Desfez demais? git reflog. O que nunca foi commitado, porém, não tem volta: na dúvida, commite ou faça git stash antes.
  • O git status mostra as dicas de desfazer: leia-o sempre.

Git revert

Três commits atrás, a Ana mudou o tempo do bolo de 40 para 90 minutos. Foi um erro: o bolo queimou. Desde então ela já fez outros commits, e o repositório já está no GitHub, onde o Bruno também trabalha. Ela não quer apagar nada do histórico; quer só desfazer aquela mudança. É para isso que serve o git revert (em inglês, revert = "reverter, voltar atrás"): ele cria um commit novo que faz exatamente o contrário do commit errado.

Você vai aprender
  • O que o git revert faz: um commit "ao contrário", que desfaz outro sem apagar nada.
  • Como reverter o último commit e um commit do meio do histórico.
  • Como ler a mensagem Revert "…" que o Git cria, e como desfazer o desfazer.
  • O que fazer quando o revert dá conflito (e como desistir com --abort).
  • Quando usar revert e quando usar reset.

Todas as saídas desta aula vieram do Git real da máquina da Ana (usuária ana, computador notebook), com o sistema em português. A tradução do Git que vem no Ubuntu é parcial: algumas mensagens saem em português, outras em inglês, outras misturadas. Elas estão aqui exatamente como saíram (no Windows, no macOS ou com o sistema em inglês, as frases podem ser diferentes; o sentido é o mesmo).

A ideia: o lançamento de estorno

No extrato do banco, quando uma compra é cobrada errado, o banco não apaga a linha da cobrança. Ele lança uma linha nova, um estorno, com o mesmo valor ao contrário. O saldo volta ao normal, e o extrato continua contando a história inteira: a cobrança errada e a correção.

O git revert é o estorno do Git:

  • o commit errado continua no histórico;
  • um commit novo entra no topo, desfazendo as mudanças dele (o que foi acrescentado é tirado, o que foi tirado volta);
  • nenhum commit existente muda, então quem já baixou o histórico (o Bruno, o GitHub) não tem problema nenhum: recebe só mais um commit.

2. Revertendo um commit do meio

Para apontar o commit errado, a Ana pode usar o hash dele (f5b361b) ou o apelido HEAD~1 ("um commit antes do HEAD"; veja O que é HEAD). Ela usa a opção --no-edit para aceitar a mensagem que o Git sugere:

$ git revert --no-edit HEAD~1
[main 188c31a] Revert "Muda tempo do bolo para 90 minutos"
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+), 1 deletion(-)
git revert
O comando: "crie um commit que desfaça…".
--no-edit
Aceite a mensagem automática sem abrir o editor. Sem essa opção, o Git abre o editor (no Ubuntu, normalmente o nano) com a mensagem já escrita, para você completar com o porquê; basta salvar e fechar.
HEAD~1
O commit a desfazer. Pode ser o hash (git revert f5b361b), o hash curto, ou qualquer outro jeito de nomear um commit.

Linha por linha da resposta:

[main 188c31a]
Um commit novo foi criado no branch main, com o hash 188c31a.
Revert "Muda tempo do bolo para 90 minutos"
A mensagem automática: "Reverte" e, entre aspas, o título do commit desfeito.
Date: …
A data do commit novo (no laboratório do guia, o relógio é fixo em 15/10/2026 10:30).
1 file changed, 1 insertion(+), 1 deletion(-)
Um arquivo mudou: uma linha entrou (a dos 40 minutos) e uma saiu (a dos 90).

Agora o histórico e o arquivo:

$ git log --oneline
188c31a Revert "Muda tempo do bolo para 90 minutos"   « o estorno
8b27670 Adiciona receita de brigadeiro
f5b361b Muda tempo do bolo para 90 minutos            « continua aqui
44ce6c7 Adiciona receita de pudim
da935f4 Adiciona receita de bolo

$ cat bolo.txt

$ git status

nothing to commit, working tree clean

Seis commits: os cinco de antes, intactos (mesmos hashes), e o estorno no topo. O bolo.txt voltou a dizer 40 minutos. E o brigadeiro, que veio depois do commit errado, continua lá: o revert desfaz só as mudanças daquele commit, não "volta no tempo".

A mensagem tem duas partes: o título Revert "Muda tempo do bolo para 90 minutos" e o corpo This reverts commit … ("isto reverte o commit …"), com o hash completo do commit desfeito. Essa mensagem sai em inglês mesmo com o sistema em português: é um texto fixo do Git, e é bom que seja assim, porque ferramentas e pessoas do mundo inteiro reconhecem um revert por ele. A mudança é o espelho do commit original: o que era + virou -, e vice-versa.

Diga o porquê

A mensagem automática diz o que foi desfeito, mas não por que. Sem o --no-edit, o editor abre e você pode acrescentar uma linha como "O bolo queima em 90 minutos; o certo é 40." Quem ler o histórico daqui a um ano vai agradecer (veja Boas Mensagens de Commit).

Missão: desfaça o commit "Muda tempo do bolo para 90 minutos" com git revert, sem perder o brigadeiro que veio depois. Use git log --oneline para achar o commit. No fim, cat bolo.txt deve mostrar 40 minutos.

3. Desfazendo o desfazer

E se a Ana mudar de ideia (o forno dela era fraco, e 90 minutos estava certo)? Um revert é um commit como outro qualquer, e também pode ser revertido:

$ git revert --no-edit HEAD
[main 4b4fbf8] Reapply "Muda tempo do bolo para 90 minutos"
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+), 1 deletion(-)
$ cat bolo.txt
Bolo de cenoura
Forno: 180 graus
Tempo: 90 minutos
$ git log --oneline
4b4fbf8 Reapply "Muda tempo do bolo para 90 minutos"
188c31a Revert "Muda tempo do bolo para 90 minutos"
8b27670 Adiciona receita de brigadeiro
f5b361b Muda tempo do bolo para 90 minutos
44ce6c7 Adiciona receita de pudim
da935f4 Adiciona receita de bolo
fe996fb Primeiro commit

O Git percebeu que é um revert de revert e escreveu Reapply "…" ("aplica de novo") no título. (Gits mais antigos, de antes da versão 2.43, escreviam Revert "Revert "…"", com as aspas dobradas; você pode ver as duas formas em projetos por aí.) O tempo voltou a 90 minutos, e o histórico conta tudo o que aconteceu: a mudança, o estorno e a volta. Nenhuma informação se perdeu em nenhum momento.

4. Revertendo sem commitar na hora: --no-commit

Com -n (ou --no-commit), o Git aplica as mudanças "ao contrário" na pasta e na área de preparo, mas não cria o commit. Serve para desfazer vários commits e juntar tudo num estorno só, ou para conferir o resultado antes. A Ana testou num outro repositório, o r2, cujo último commit (7564c62) ajusta o tempo do bolo para 50 minutos (é o mesmo repositório da próxima seção):

$ git revert -n HEAD
$ git status
No ramo main
You are currently reverting commit 7564c62.
  (all conflicts fixed: run "git revert --continue")
  (use "git revert --skip" to skip this patch)
  (use "git revert --abort" to cancel the revert operation)

Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt

O git revert -n não mostrou nada, e nenhum commit foi criado. O git status conta o resto (essas linhas o Git do Ubuntu ainda não traduziu): "você está revertendo o commit 7564c62", com as três saídas possíveis entre parênteses, e o bolo.txt modificado na área de preparo. As mudanças estão preparadas, e o Git avisa que há um revert em andamento. A partir daqui, há duas saídas: git commit (ou git revert --continue) para criar o commit, ou git revert --abort para desistir e voltar a tudo como estava.

5. Quando o revert dá conflito

O revert tenta aplicar "o contrário" de um commit antigo no código de hoje. Se, depois do commit errado, alguém mexeu nas mesmas linhas, o Git não sabe o que fazer e para no meio, com um conflito. Num outro repositório, a Ana mudou o tempo de 40 para 90 e, depois, de 90 para 50. Agora ela tenta reverter o "90":

$ git log --oneline
7564c62 Ajusta tempo do bolo para 50 minutos
aa77c8f Muda tempo do bolo para 90 minutos     « quer desfazer este
5209e42 Adiciona receita de bolo
$ git revert --no-edit HEAD~1

As dicas (em inglês): "depois de resolver os conflitos, marque-os com git add/git rm e rode git revert --continue; você pode pular este commit com git revert --skip; para desistir e voltar ao estado de antes do git revert, rode git revert --abort". A última linha ensina a desligar essas dicas.

Dentro do arquivo, as marcas do conflito: em cima, a linha de hoje (HEAD: 50 minutos); embaixo, o que o revert queria pôr (a versão do "pai" do commit desfeito: 40 minutos).

Desfazer o "90" significaria pôr "40" no lugar de "90"; mas a linha agora diz "50". Qual deve ficar? Só a Ana sabe. Ela tem duas saídas:

  • resolver: editar o bolo.txt, deixar a linha certa, apagar as marcas <<<<<<<, ======= e >>>>>>>, e então git add bolo.txt e git revert --continue (o passo a passo de resolver está em Resolvendo Conflitos);
  • desistir: git revert --abort, que volta tudo ao estado de antes do revert:

$ git status

$ git log --oneline
7564c62 Ajusta tempo do bolo para 50 minutos

Tudo como antes: nenhum commit novo, pasta limpa.

Revert ou reset?

Os dois "desfazem commits", de jeitos opostos:

git revertgit reset
O que fazCria um commit novo, ao contrárioMove o branch para trás; os commits de depois saem do histórico
HistóricoSó cresce; nada é reescritoÉ reescrito
Commit do meioDesfaz só ele; os de depois ficamLeva junto todos os que vieram depois
Já foi enviado (push)?Seguro: os outros recebem só mais um commitPerigoso: exige push --force e atrapalha quem já baixou
Quando usarCommits já compartilhados; desfazer um commit específicoCommits só seus, ainda não enviados

Regra prática: se o commit já foi para o GitHub, revert. Se ainda está só no seu computador, tanto faz, e o reset deixa o histórico mais limpo. O mapa completo de "como desfazer cada coisa" está em Desfazendo: o Mapa.

O git revert precisa saber qual commit desfazer. Sem isso, ele mostra o jeito de usar (uso:): git revert [opções] <commit>..., ou uma das quatro saídas de um revert em andamento. Repare em -n, --no-commit ("não commitar automaticamente") e -e, --[no-]edit ("editar a mensagem"), que você viu nesta aula. Como resolver: git revert HEAD para o último commit, ou o hash do commit (pegue no git log --oneline).

Hash errado ou digitado pela metade 
$ git revert abc1234
fatal: bad revision 'abc1234'

"Revisão inválida": o Git não achou nenhum commit com esse nome (revision, para o Git, é qualquer jeito de apontar um commit). Como resolver: copie o hash do git log --oneline; bastam os 7 primeiros caracteres (veja O Hash do Commit).

Tentou reverter com mudanças não commitadas 
$ echo "Cobertura: chocolate" >> bolo.txt
$ git status --short
 M bolo.txt
$ git revert --no-edit HEAD
error: Your local changes to the following files would be overwritten by merge:
	bolo.txt
Please commit your changes or stash them before you merge.
Aborting
fatal: revert failed
$ git status --short
 M bolo.txt   « a mudança da Ana continua aqui

"Suas mudanças locais nos seguintes arquivos seriam sobrescritas: bolo.txt. Por favor, commite suas mudanças ou guarde-as com stash antes. Abortando. O revert falhou." O revert precisa mexer no bolo.txt, e a Ana tem uma mudança ainda não commitada nesse arquivo; ela seria perdida, e o Git se recusa (sem mexer em nada: a mudança continua lá). Como resolver: commite as mudanças, guarde-as com git stash, ou descarte-as com git restore, e rode o revert de novo.

Conflito no meio do revert

Veja a seção Quando o revert dá conflito: git status para ver os arquivos em conflito, depois resolver e git revert --continue, ou desistir com git revert --abort.

E os commits de merge?

Para reverter um commit de merge (que tem dois "pais"), o Git pede que você diga qual dos lados manter, com a opção -m 1. Isso fica para quando você conhecer os branches; por ora, saiba reconhecer a mensagem:

$ git revert --no-edit HEAD
error: commit 77071b9898241a0a18d812ede2db00b1a4eab26b is a merge but no -m option was given.
fatal: revert failed

"O commit … é um merge, mas a opção -m não foi dada. O revert falhou." Nada foi mudado.

Resumo

  • git revert <commit> cria um commit novo que faz o contrário do commit indicado. Nada é apagado; o histórico só cresce.
  • Dá para reverter qualquer commit, até um do meio: os commits de depois continuam lá.
  • A mensagem automática é Revert "…" + This reverts commit <hash>.; sem --no-edit, o editor abre para você explicar o porquê.
  • Se der conflito: resolva, git add e git revert --continue, ou desista com git revert --abort.
  • Commit já enviado ao GitHub? Use revert. Commit só seu? reset também serve.

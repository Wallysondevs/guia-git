Git Configurações Úteis

Na aula git config, a Ana ensinou ao Git o nome e o e-mail dela. Mas o Git tem centenas de outras configurações, e algumas poucas deixam o dia a dia bem mais confortável: um editor que você sabe usar, o Git corrigindo um comando digitado errado, o push de um branch novo sem aquele erro chato, conflitos mais fáceis de entender. Esta aula mostra as que valem a pena, uma por uma, com o efeito real de cada uma.

Você vai aprender
  • Onde cada configuração fica guardada e como descobrir de onde ela veio (--show-origin, --show-scope).
  • Como escolher o editor (core.editor) e fazer o Git corrigir comandos digitados errado (help.autocorrect).
  • Como mandar um branch novo para o GitHub com um simples git push (push.autoSetupRemote).
  • Como ver, num conflito, também como o texto era antes (merge.conflictstyle zdiff3).
  • Um ~/.gitconfig pronto para começar, e os erros que o git config deixa passar em silêncio.

Todas as saídas desta aula vieram do Git 2.53 do Ubuntu na máquina da Ana (usuária ana, computador notebook), com o sistema em português. Algumas mensagens do Git ainda saem em inglês nessa versão, porque a tradução não está completa: a aula traduz cada uma.

A ideia: as preferências do celular novo

Quando a Ana compra um celular novo, ele funciona de fábrica. Mas ela logo muda meia dúzia de coisas: o teclado, o toque, o brilho automático. Não é obrigatório, mas o celular fica do jeito dela. E algumas preferências são do aparelho todo (o idioma), enquanto outras são de um aplicativo só (as notificações do banco).

O Git é igual. Ele funciona sem nada, e cada configuração tem um alcance:

  • global (--global): vale para todos os repositórios da Ana. Fica no arquivo ~/.gitconfig.
  • local (o padrão, ou --local): vale só para um repositório. Fica em .git/config, dentro dele.
  • system (--system): vale para todos os usuários do computador. Quase ninguém usa.

Quando a mesma configuração aparece em dois lugares, a mais perto ganha: a local passa na frente da global, que passa na frente da do sistema.

1. Vendo o que está configurado, e de onde veio

$ git config --list --show-origin
file:/home/ana/.gitconfig	user.name=Ana Souza
file:/home/ana/.gitconfig	user.email=ana@exemplo.com
file:/home/ana/.gitconfig	init.defaultbranch=main
file:/home/ana/.gitconfig	core.editor=nano
--list
Lista todas as configurações que valem aqui, no formato seção.nome=valor.
--show-origin
Mostra, na frente de cada uma, o arquivo de onde ela veio. Aqui, tudo veio do ~/.gitconfig da Ana.
init.defaultbranch
Repare: o nome sai em minúsculas. O Git não diferencia maiúsculas no nome das configurações (init.defaultBranch e init.defaultbranch são a mesma coisa), e a documentação escreve com maiúsculas no meio para ficar legível.

Dentro de um repositório, aparecem também as configurações locais. Com --show-scope, o Git mostra o alcance em vez do arquivo:

$ git config --list --show-scope
global	user.name=Ana Souza
global	user.email=ana@exemplo.com
global	init.defaultbranch=main
global	core.editor=nano
local	core.repositoryformatversion=0         « estas quatro o git init criou
local	core.filemode=true
local	core.bare=false
local	core.logallrefupdates=true

Uma configuração só para um repositório

A Ana usa o e-mail pessoal em tudo, menos no repositório do trabalho. Sem --global, a configuração fica só no repositório atual e passa na frente da global:

$ git config --local user.email ana.trabalho@exemplo.com
$ git config user.email
ana.trabalho@exemplo.com                 « a local ganhou
$ git config --show-origin user.email
file:.git/config	ana.trabalho@exemplo.com
$ cat .git/config
[core]
	repositoryformatversion = 0
	filemode = true
	bare = false
	logallrefupdates = true
[user]
	email = ana.trabalho@exemplo.com

Quando uma configuração "não pega", o --show-origin é a primeira coisa a olhar: muitas vezes existe outra, mais perto, passando na frente.

2. O editor: core.editor

Quando você roda git commit sem -m, um git rebase -i ou um merge com mensagem, o Git abre um editor de texto. Se ninguém escolheu, ele usa o padrão do sistema, que muitas vezes é o vim, e muita gente fica presa nele sem saber sair. A Ana já tinha escolhido o nano, que mostra os atalhos na parte de baixo da tela:

$ git config --global core.editor nano
$ git config --global core.editor
nano
EditorValor do core.editor
nano (simples, no terminal)nano
vimvim
VS Code"code --wait"

No VS Code, o --wait é obrigatório: ele faz o terminal esperar você fechar a aba da mensagem. Sem ele, o VS Code abre, o Git acha que você já terminou, recebe uma mensagem vazia e cancela o commit. Mais sobre o VS Code em Git no VS Code e em Outros Programas.

3. O Git corrige o que você digitou errado: help.autocorrect

Sem configuração nenhuma, o Git só sugere:

$ git stauts
git: 'stauts' não é um comando git. Veja 'git --help'.

The most similar command is
	status

"O comando mais parecido é status." Com o help.autocorrect, ele pode fazer mais que sugerir. Há três jeitos úteis:

Perguntar antes (prompt). O Git pergunta e espera você responder y (sim) ou n (não):

$ git config --global help.autocorrect prompt
$ git stauts
WARNING: You called a Git command named 'stauts', which does not exist.
Run 'status' instead [y/N]? n

"Aviso: você chamou um comando do Git chamado stauts, que não existe. Rodar status no lugar? [s/N]". O N maiúsculo quer dizer que, se você só apertar Enter, a resposta é "não".

Esperar um pouco e corrigir (um número, em décimos de segundo). Com 30, o Git espera 3 segundos, tempo para você apertar Ctrl+C se não era isso:

$ git config --global help.autocorrect 30
$ git stauts
WARNING: You called a Git command named 'stauts', which does not exist.
Continuing in 3.0 seconds, assuming that you meant 'status'.
No ramo promocao
Your branch is up to date with 'origin/promocao'.

nothing to commit, working tree clean

"Continuando em 3 segundos, supondo que você quis dizer status." E o status rodou.

Corrigir na hora (immediate), sem esperar:

$ git config --global help.autocorrect immediate
$ git stauts
WARNING: You called a Git command named 'stauts', which does not exist.
Continuing under the assumption that you meant 'status'.
No ramo main
nothing to commit, working tree clean
Prefira prompt

Corrigir sozinho é cômodo com o status, mas o Git pode adivinhar errado: na aula Atalhos, um git sts foi "corrigido" para stash, que guarda as suas mudanças e limpa a pasta. Com prompt, você sempre vê o palpite antes.

4. git push num branch novo: push.autoSetupRemote

A Ana criou o branch promocao na lojinha e fez um commit. Na hora de enviar (veja git push e Branch de Rastreamento), o primeiro push de um branch novo sempre dava este erro:

$ git push
fatal: The current branch promocao has no upstream branch.
To push the current branch and set the remote as upstream, use

    git push --set-upstream origin promocao

To have this happen automatically for branches without a tracking
upstream, see 'push.autoSetupRemote' in 'git help config'.

"O branch atual, promocao, não tem branch de rastreamento (upstream). Para enviar e ligar os dois, use git push --set-upstream origin promocao. Para isso acontecer automaticamente, veja push.autoSetupRemote." O próprio Git sugere a configuração. Com ela ligada git 2.37+, o mesmo git push funciona de primeira:

$ git config --global push.autoSetupRemote true
$ git push
Enumerating objects: 4, done.
Counting objects: 100% (4/4), done.
Delta compression using up to 4 threads
Compressing objects: 100% (2/2), done.
Writing objects: 100% (3/3), 298 bytes | 298.00 KiB/s, done.
Total 3 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
To /home/ana/servidor/lojinha.git
 * [new branch]      promocao -> promocao
branch 'promocao' set up to track 'origin/promocao'.
$ git status
No ramo promocao
Your branch is up to date with 'origin/promocao'.

nothing to commit, working tree clean
Enumerating objects … Total 3
O progresso do envio: o Git conta, comprime e manda os objetos do commit novo (cada linha está explicada em git push). O terminal do guia não mostra essas linhas.
To /home/ana/servidor/lojinha.git
Para onde foi. Neste exemplo, o "servidor" da lojinha é uma pasta no próprio computador da Ana; com o GitHub, aparece o endereço https://github.com/….
* [new branch] promocao -> promocao
"Branch novo": o promocao da Ana virou o promocao do servidor.
branch 'promocao' set up to track 'origin/promocao'.
"O branch promocao foi configurado para rastrear origin/promocao": exatamente o que o --set-upstream faria. Daqui para a frente, git push e git pull sabem para onde ir.
Your branch is up to date with 'origin/promocao'.
"O seu branch está igual ao origin/promocao": o git status agora compara com o servidor.

5. Conflitos mais fáceis de ler: merge.conflictstyle zdiff3

Num conflito (veja Conflitos de Merge), o Git mostra as duas versões, a sua e a do outro branch. A Ana tinha trocado o açúcar por "3 xícaras de açúcar mascavo"; no branch menos-acucar, a linha virou "1 xícara de açúcar". No estilo padrão (merge), o arquivo ficou assim:

$ git merge menos-acucar
Mesclagem automática de bolo.txt
CONFLITO (conteúdo): conflito de mesclagem em bolo.txt
Recorded preimage for 'bolo.txt'
Automatic merge failed; fix conflicts and then commit the result.
$ cat bolo.txt
Bolo de cenoura
3 cenouras
<<<<<<< HEAD
3 xícaras de açúcar mascavo
=======
1 xícara de açúcar
>>>>>>> menos-acucar

Dá para ver as duas versões, mas não o que cada lado mudou: as duas pessoas mexeram na quantidade? Só uma? Com o estilo zdiff3 git 2.35+, o Git mostra também como a linha era antes dos dois mexerem (a base):

$ git merge --abort
$ git config --global merge.conflictstyle zdiff3
$ git merge menos-acucar
Mesclagem automática de bolo.txt
CONFLITO (conteúdo): conflito de mesclagem em bolo.txt
Recorded preimage for 'bolo.txt'
Automatic merge failed; fix conflicts and then commit the result.
$ cat bolo.txt
Bolo de cenoura
3 cenouras
<<<<<<< HEAD
3 xícaras de açúcar mascavo      « a versão da Ana
||||||| eed6175
2 xícaras de açúcar              « como era antes (a base, no commit eed6175)
=======
1 xícara de açúcar               « a versão do branch menos-acucar
>>>>>>> menos-acucar

Agora a história fica clara: era "2 xícaras de açúcar"; a Ana mudou a quantidade e o tipo (mascavo); o outro branch só diminuiu a quantidade. Com isso a Ana resolve com segurança: "1 xícara de açúcar mascavo", juntando as duas intenções. O "z" do nome quer dizer que, quando o começo ou o fim das duas versões são iguais, o Git tira essas linhas iguais de dentro do conflito, para ele ficar menor.

As mensagens do merge: "Automatic merge failed; fix conflicts and then commit the result" = "o merge automático falhou; resolva os conflitos e faça o commit do resultado". A linha "Recorded preimage" aparece por causa da próxima configuração.

Lembrando como você resolveu: rerere.enabled

rerere vem de reuse recorded resolution: "reutilizar a resolução gravada". Com git config --global rerere.enabled true, o Git grava cada conflito ("Recorded preimage for 'bolo.txt'" = "registrei como o conflito de bolo.txt começou") e, depois, como você o resolveu. Se o mesmo conflito aparecer de novo (comum quando você desiste de um merge e tenta outra vez, ou num rebase repetido), o Git aplica a mesma resolução sozinho. Você ainda confere e faz o commit.

O ~/.gitconfig da Ana, pronto

Depois de ligar tudo isso com git config --global …, o arquivo dela ficou assim (é texto comum: dá para copiar as partes que você quiser para o seu, com git config --global --edit):

$ cat ~/.gitconfig
[user]
	name = Ana Souza
	email = ana@exemplo.com
[init]
	defaultBranch = main
[core]
	editor = nano
[push]
	autoSetupRemote = true
[pull]
	rebase = false
[fetch]
	prune = true
[branch]
	sort = -committerdate
[column]
	ui = auto
[merge]
	conflictstyle = zdiff3
[diff]
	algorithm = histogram
[rerere]
	enabled = true
[commit]
	verbose = true

Cada [seção] agrupa as configurações com o mesmo começo: push.autoSetupRemote virou autoSetupRemote = true dentro de [push].

Missão: ligue, para todos os repositórios, o push.autoSetupRemote (valor true) e o estilo de conflito zdiff3. Depois confira com git config --global --list.

Quando dá errado

Esqueceu a seção 
$ git config --global editor vim
error: key does not contain a section: editor

"A chave não contém uma seção." Toda configuração tem a forma seção.nome. Como resolver: git config --global core.editor vim.

Errou o nome, e o Git aceitou 
$ git config --global corre.editor vim
$ git config --global core.editor
nano

O que aconteceu: a Ana digitou corre em vez de core. O Git não confere se a configuração existe: ele guardou um corre.editor que ninguém nunca vai ler, sem reclamar, e o editor continuou o nano. Como confirmar: git config --global --list mostra a linha errada. Como resolver: apague a errada (git config --global --unset corre.editor) e grave a certa. Na dúvida sobre um nome, consulte git help config ou a referência de configurações.

O --unset não fez nada 
$ git config --global --unset nao.existe
$ echo $?
5

Não há mensagem nenhuma, mas o código de saída 5 quer dizer "essa configuração não existia". Confira o nome e o alcance: uma configuração local (.git/config) não sai com --global --unset; use git config --show-origin nome para ver onde ela está.

"Mudei a configuração e nada aconteceu"

Quase sempre é uma configuração local passando na frente da global, como o e-mail do trabalho da Ana na seção 1. Como confirmar: git config --show-origin nome. Como resolver: mude no arquivo que aparece ali, ou apague a local com git config --local --unset nome.

Resumo

  • Configuração global fica em ~/.gitconfig; local, em .git/config; a local passa na frente. --show-origin mostra de onde veio.
  • core.editor: o editor das mensagens (nano, "code --wait"…).
  • help.autocorrect prompt: o Git pergunta antes de corrigir um comando digitado errado.
  • push.autoSetupRemote true: o primeiro git push de um branch novo já cria o rastreamento.
  • merge.conflictstyle zdiff3: o conflito mostra também a base; rerere.enabled reaproveita resoluções.
  • O git config aceita nomes errados sem reclamar: confira com --list.

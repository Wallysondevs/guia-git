Git Arquivos Grandes (Git LFS)

O Git foi feito para arquivos de texto: código, receitas, páginas. Ele guarda todas as versões de tudo, para sempre. Com um vídeo de 20 MB, isso vira um problema: cada versão nova do vídeo fica guardada inteira, e quem clona o repositório baixa todas. O Git LFS (Large File Storage, "armazenamento de arquivos grandes") resolve isso guardando os arquivos grandes num lugar separado e deixando no Git só uma "etiqueta" que aponta para eles.

Você vai aprender
  • Por que arquivos grandes incham o repositório, com uma medida real.
  • A ideia do LFS: o arquivo ponteiro no Git e o arquivo de verdade no servidor.
  • Os comandos: git lfs install, git lfs track e o .gitattributes que ele escreve.
  • Os limites do GitHub para arquivos grandes.
  • O que acontece quando alguém da equipe não tem o LFS instalado.
O que nesta aula é real e o que é ilustrativo

O Git LFS é um programa à parte, que não vem com o Git. A máquina da Ana usada no guia (o Git 2.53 do Ubuntu, usuária ana, computador notebook) não tem o LFS: por isso as saídas das seções 1 e 5 são reais, e os comandos git lfs das seções 3 e 4 são ilustrativos, baseados na documentação oficial (git-lfs.com e docs.github.com/pt). A versão atual do Git LFS, quando esta aula foi escrita, era a 3.8.

A ideia: o guarda-volumes

No museu, ninguém entra com a mala: você a deixa no guarda-volumes e recebe uma ficha com um número. Você anda pelo museu leve, só com a ficha. Quando precisa da mala, entrega a ficha e a recebe de volta.

O Git LFS faz isso com os arquivos grandes:

  • a "mala" (o vídeo de 20 MB) vai para um servidor LFS (no GitHub, ele já vem junto com o repositório);
  • no repositório Git fica só a "ficha": um arquivo ponteiro de três linhas, com o número que identifica o vídeo;
  • quando você faz clone, pull ou troca de branch, o LFS troca as fichas pelas malas, mas só as da versão que você está usando.

1. O problema, medido

A Ana começou a guardar os vídeos do canal de receitas no Git. Ela commitou um vídeo de 20 MB e, depois, duas versões corrigidas dele. (Os "vídeos" aqui são 20 MB de bytes aleatórios, que se comportam como um vídeo de verdade: não dá para comprimir.)

$ ls -lh bolo.mp4
-rw-rw-r-- 1 ana ana 20M Oct 15 10:29 bolo.mp4
$ git add bolo.mp4 && git commit -q -m 'Adiciona vídeo do bolo'
$ head -c 20000000 /dev/urandom > bolo.mp4
$ git add bolo.mp4 && git commit -q -m 'Corrige o vídeo do bolo'
$ head -c 20000000 /dev/urandom > bolo.mp4
$ git add bolo.mp4 && git commit -q -m 'Vídeo do bolo com legenda'
$ git count-objects -vH
count: 12
size: 57.28 MiB                « as três versões, inteiras
in-pack: 0
packs: 0
size-pack: 0 bytes
prune-packable: 0
garbage: 0
size-garbage: 0 bytes
$ du -sh .git
58M	.git

Um vídeo de 20 MB, três versões, e a pasta .git já tem 58 MB: o Git guardou cada versão inteira (veja Como o Git Guarda as Coisas). E apagar o vídeo não ajuda:

$ git rm -q bolo.mp4 && git commit -q -m 'Remove o vídeo'
$ du -sh .git
58M	.git

Continua com 58 MB, porque os commits antigos ainda têm o vídeo, e o Git nunca esquece um commit. Quem clonar este repositório vai baixar os 58 MB, mesmo que só queira o README. Com dezenas de vídeos e centenas de versões, o repositório fica impossível de clonar.

2. O que o LFS guarda no Git: o ponteiro

Com o LFS, no lugar do vídeo, o Git guarda um arquivo de texto pequeno como este (o exemplo é o da especificação oficial do Git LFS):

version https://git-lfs.github.com/spec/v1
oid sha256:4d7a214614ab2935c943f9e0ff69d22eadbb8f32b1258daaa5e2ca24d17e2393
size 12345
version
Qual versão do formato de ponteiro é esta.
oid sha256:…
A "ficha do guarda-volumes": o hash do conteúdo do arquivo de verdade (parecido com o hash do commit). É por ele que o LFS acha o arquivo no servidor.
size
O tamanho do arquivo de verdade, em bytes.

Três versões do vídeo viram três ponteiros de umas 130 letras cada no histórico. Os 20 MB de cada versão ficam no servidor LFS, e o seu computador só baixa a versão que você está usando. Na sua pasta, você continua vendo e abrindo o bolo.mp4 normal: o LFS faz a troca sozinho.

3. Instalando e ligando o LFS (ilustrativo)

Primeiro, instale o programa. No Ubuntu, ele vem no pacote git-lfs (sudo apt install git-lfs); no Windows, o instalador do Git para Windows já traz o LFS; para outros sistemas, veja git-lfs.com. Antes de instalar, o Git não conhece o comando:

$ git lfs install
git: 'lfs' não é um comando git. Veja 'git --help'.

The most similar command is
	refs

(Saída real da máquina da Ana, que não tem o LFS. A sugestão refs é só o comando de nome mais parecido.) Depois de instalado, o primeiro comando liga o LFS uma vez por usuário:

git lfs install

Ele acrescenta ao seu ~/.gitconfig a configuração do "filtro" lfs (é ela que troca arquivos por ponteiros e vice-versa). Dentro de um repositório, o LFS também instala alguns hooks, como um pre-push que envia os arquivos grandes junto com o push.

Dizendo quais arquivos vão para o LFS: git lfs track

Dentro do repositório, diga quais tipos de arquivo o LFS deve cuidar. A documentação do GitHub mostra assim:

$ git lfs track "*.psd"
> Tracking "*.psd"

"Rastreando *.psd." As aspas são importantes: sem elas, o terminal trocaria *.psd pelos nomes dos arquivos .psd da pasta, antes de o comando ver o padrão. O git lfs track não guarda nada escondido: ele escreve uma linha no .gitattributes:

*.psd filter=lfs diff=lfs merge=lfs -text
*.psd
O padrão: todos os arquivos do Photoshop.
filter=lfs
"Ao guardar, passe o arquivo pelo filtro lfs", que troca o conteúdo pelo ponteiro. É o coração do LFS.
diff=lfs merge=lfs
Como mostrar diferenças e como juntar versões desses arquivos: pelo LFS, e não linha por linha.
-text
"Não é texto": o Git nunca mexe no fim de linha dele.

Para conferir, a Ana pediu ao Git os atributos de um .psd com esse .gitattributes (saída real; para isso não é preciso ter o LFS):

$ git check-attr -a -- capa.psd
capa.psd: diff: lfs
capa.psd: merge: lfs
capa.psd: text: unset
capa.psd: filter: lfs

Missão: o terminal do guia não tem o LFS, mas você pode escrever à mão a linha que o git lfs track "*.mp4" escreveria. Crie o .gitattributes com a linha *.mp4 filter=lfs diff=lfs merge=lfs -text e faça o commit dele.

4. Usando no dia a dia (ilustrativo)

Depois do track, o trabalho é o de sempre. Do jeito da documentação do Git LFS:

git add .gitattributes
git add capa.psd
git commit -m "Adiciona a capa"
git push origin main

A única diferença aparece no push: antes de mandar os commits, o LFS envia os arquivos grandes. A documentação do GitHub mostra o progresso assim:

> Sending file.psd
> 44.74 MB / 81.04 MB  55.21 % 14s
> 64.74 MB / 81.04 MB  79.21 % 3s

Outros comandos úteis do LFS (veja git lfs help depois de instalar):

ComandoO que faz
git lfs track (sem nada)Lista os padrões que o LFS está cuidando
git lfs ls-filesLista os arquivos que estão no LFS
git lfs pullBaixa os arquivos grandes que faltam (troca os ponteiros pelos arquivos)
git lfs migrateReescreve o histórico para mover para o LFS arquivos que já foram commitados sem ele (cuidado: veja A Regra de Ouro)
git lfs track --lockable "*.psd"Arquivos que só uma pessoa pode editar por vez (útil para binários, que não dá para mesclar)
Os limites do GitHub (ilustrativo, de docs.github.com/pt)
  • Arquivo maior que 50 MiB: o push funciona, mas o Git mostra um aviso.
  • Arquivo maior que 100 MiB: o GitHub bloqueia o push. Para arquivos assim, só com o Git LFS.
  • Pelo site (arrastando o arquivo no navegador), o limite é de 25 MiB.
  • O LFS do GitHub tem uma cota de armazenamento e de download; confira os números atuais na documentação de cobrança do GitHub antes de colocar muitos gigabytes.

Formas diferentes de fazer a mesma coisa

SituaçãoQual usar
Imagens pequenas de um site (alguns KB, mudam pouco)Git normal, com binary no .gitattributes
Vídeos, PSDs, modelos 3D, áudio, que mudam várias vezesGit LFS (git lfs track)
Arquivos gerados (o programa compilado, o zip do site)Nem Git nem LFS: .gitignore, e gere de novo quando precisar
Dados enormes que ninguém edita (backups, bases de dados)Fora do Git: um serviço de armazenamento de arquivos, com o link no README
Um arquivo grande já está no históricogit lfs migrate (reescreve o histórico; combine com a equipe)

Quando dá errado

O .gitattributes diz LFS, mas o LFS não está instalado 
$ echo '*.psd filter=lfs diff=lfs merge=lfs -text' > .gitattributes
$ head -c 1000 /dev/urandom > capa.psd          « um "PSD" de mentira, de 1000 bytes
$ git add .gitattributes capa.psd
$ git commit -q -m 'Adiciona capa'
$ git show --stat HEAD
commit 8a2e32579478c4fcb9aa88045ae6b306caae8e79
Author: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

    Adiciona capa

 .gitattributes |   1 +
 capa.psd       | Bin 0 -> 1000 bytes        « o arquivo inteiro, não o ponteiro
 2 files changed, 1 insertion(+)

O que aconteceu: o computador não tem o LFS, então o Git não sabe o que é o filtro lfs, ignora a linha sem avisar e guarda o arquivo inteiro, como se o LFS não existisse. O Bin 0 -> 1000 bytes mostra o arquivo de verdade (um ponteiro seria texto, com umas 130 letras). Como resolver: instale o LFS e rode git lfs install antes de commitar arquivos grandes. Se já commitou, git lfs migrate pode consertar o histórico.

git-lfs: not found 
$ git add fundo.psd
git-lfs filter-process: 1: git-lfs: not found
fatal: the remote end hung up unexpectedly

O que aconteceu: aqui a configuração do LFS existe no ~/.gitconfig (por exemplo, copiada de outro computador, ou o programa foi desinstalado depois do git lfs install), mas o programa git-lfs não está instalado. O Git tentou chamar o filtro e não achou ("not found" = "não encontrado"); a segunda linha ("a outra ponta desligou inesperadamente") é só o Git percebendo que o filtro morreu. Como resolver: instale o git-lfs (no Ubuntu, sudo apt install git-lfs).

O arquivo abriu e tem só três linhas de texto

O que aconteceu: você clonou sem o LFS instalado (ou o download dos arquivos grandes falhou), e na pasta ficaram os ponteiros (version https://git-lfs.github.com/spec/v1…), e não os arquivos. Como resolver: instale o LFS, rode git lfs install e depois git lfs pull.

O push foi recusado por causa de um arquivo grande (ilustrativo)

Se um commit tem um arquivo de mais de 100 MiB sem LFS, o GitHub recusa o push inteiro. Não basta apagar o arquivo num commit novo: ele continua nos commits antigos (como os 58 MB da seção 1). Como resolver: tire o arquivo dos commits que ainda não foram enviados (com --amend, se for o último, ou rebase interativo) ou use git lfs migrate, e envie de novo.

Resumo

  • O Git guarda todas as versões inteiras: arquivos grandes que mudam incham o repositório para sempre (três versões de 20 MB = 58 MB).
  • O Git LFS guarda os arquivos grandes num servidor à parte e deixa no Git só um ponteiro (versão, hash e tamanho).
  • git lfs install (uma vez), git lfs track "*.mp4" (por repositório), commit do .gitattributes, e daí em diante add/commit/push normais.
  • No GitHub, arquivos acima de 100 MiB só entram com LFS.
  • Sem o LFS instalado, o Git ignora o filter=lfs em silêncio: todo mundo da equipe precisa instalar.

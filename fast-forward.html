Git Merge Fast-forward

Na aula git merge, o primeiro merge da Ana respondeu com uma palavra curiosa: Fast-forward ("avanço rápido", como o botão ⏩ de um player). É o merge mais simples que existe: o Git não junta nada, não cria commit, só empurra a etiqueta do branch para frente. Esta aula mostra quando isso acontece, por que é seguro, e as duas opções que controlam esse comportamento: --no-ff e --ff-only.

Você vai aprender
  • Quando um merge pode ser fast-forward: o branch atual não andou desde que o outro nasceu.
  • O que muda por dentro: só o arquivo do branch, que passa a ter outro hash.
  • --no-ff: criar um commit de merge mesmo assim, para o desenho guardar "aqui entrou um branch".
  • --ff-only: aceitar só fast-forward, e o erro real Not possible to fast-forward, aborting.
  • A configuração merge.ff e qual estilo escolher.

As saídas vieram do Git 2.53 do Ubuntu 26.04, na máquina da Ana, com o sistema em português. As mensagens desta aula saem em inglês (a tradução do Git no Ubuntu ainda não as cobre); cada uma vem traduzida aqui.

A ideia: a fila que só cresceu de um lado

Imagine o main como um marcador numa fila de commits. A Ana criou o branch sobremesas no fim da fila e continuou a fila por ele: mais dois commits. Enquanto isso, o main ficou parado. Na hora de juntar, não há nada para "misturar": tudo o que o main tem, o sobremesas também tem, e mais um pouco. Basta arrastar o marcador do main até o fim da fila.

Antes:   A---B---C   ← main
                  \
                   D---E   ← sobremesas

Depois:  A---B---C---D---E   ← main
                             ← sobremesas

A regra: o merge é fast-forward quando o commit do branch atual é um antepassado do commit do outro branch. Em outras palavras: quando dá para chegar de um ao outro só andando para frente pela história.

1. Um fast-forward, visto por dentro

O repositório da Ana: três commits no main e dois no sobremesas, que nasceu no fim do main. Ela está no main:

$ git log --oneline --graph --all
* ae456dd (sobremesas) Adiciona receita de brigadeiro
* d6f2336 Adiciona receita de pudim
* 0244251 (HEAD -> main) Adiciona receita de pão de queijo
* 7225e04 Adiciona receita de bolo
* 700bbd5 Cria o README
$ cat .git/refs/heads/main
0244251e6b6cd5cbf4b8c82f8ba2557b6cf3878b         « o main aponta para C

O desenho do git log --graph é uma linha reta: o main está no meio da fila do sobremesas. Isso já anuncia o fast-forward. Agora o merge:

$ git merge sobremesas
Updating 0244251..ae456dd
Fast-forward
 brigadeiro.txt | 1 +
 pudim.txt      | 1 +
 2 files changed, 2 insertions(+)
 create mode 100644 brigadeiro.txt
 create mode 100644 pudim.txt
$ cat .git/refs/heads/main
ae456dd1e4da87e84d6eeb2c13cd07b4037c70b9         « agora aponta para E
$ cat .git/refs/heads/sobremesas
ae456dd1e4da87e84d6eeb2c13cd07b4037c70b9         « o mesmo hash
$ git log --oneline --graph --all
* ae456dd (HEAD -> main, sobremesas) Adiciona receita de brigadeiro
* d6f2336 Adiciona receita de pudim
* 0244251 Adiciona receita de pão de queijo
* 7225e04 Adiciona receita de bolo
* 700bbd5 Cria o README
Updating 0244251..ae456dd
"Atualizando de 0244251 para ae456dd": de onde a etiqueta sai e para onde ela vai.
Fast-forward
"Avanço rápido": nenhum commit novo; só a etiqueta andou.
cat .git/refs/heads/main
A prova: o arquivo do branch main trocou de hash, e agora é igual ao do sobremesas. O fast-forward inteiro foi isso: reescrever uma linha num arquivinho (e atualizar a pasta com os arquivos novos).

Repare que nenhum hash novo apareceu no git log: os commits são os mesmos de antes. O diário do HEAD (git reflog) registra o que aconteceu com todas as letras:

$ git reflog -3
ae456dd (HEAD -> main, sobremesas) HEAD@{0}: merge sobremesas: Fast-forward
0244251 HEAD@{1}: checkout: moving from sobremesas to main
ae456dd (HEAD -> main, sobremesas) HEAD@{2}: commit: Adiciona receita de brigadeiro
Por que o fast-forward é tão seguro?

Porque ele não inventa nada: não há commit novo, não há combinação de arquivos, não pode haver conflito. A pasta fica exatamente igual à do último commit do outro branch, que você já tinha testado lá. É também o que acontece num git pull quando só o colega mexeu: Updating … Fast-forward.

2. --no-ff: quero um commit de merge mesmo assim

O fast-forward tem um efeito colateral: depois dele, o desenho da história é uma linha reta, e ninguém sabe mais que o pudim e o brigadeiro foram feitos num branch separado. Algumas equipes querem guardar essa informação: "aqui entrou a funcionalidade X, inteira". Para isso existe o --no-ff ("sem fast-forward"), que sempre cria um commit de merge.

A Ana fez um branch bebidas com um suco. O main não andou, então daria fast-forward, mas ela pede --no-ff:

$ git switch -q -c bebidas
$ echo 'Suco de laranja' > suco.txt
$ git add suco.txt && git commit -q -m 'Adiciona suco'
$ git switch -q main
$ git merge --no-ff bebidas -m 'Junta o ramo bebidas'
Merge made by the 'ort' strategy.
 suco.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 suco.txt
$ git log --oneline --graph --all
*   33670d7 (HEAD -> main) Junta o ramo bebidas      « commit de merge, com dois pais
|\
| * f23e6d2 (bebidas) Adiciona suco
|/
* ae456dd (sobremesas) Adiciona receita de brigadeiro
* d6f2336 Adiciona receita de pudim
* 0244251 Adiciona receita de pão de queijo
* 7225e04 Adiciona receita de bolo
* 700bbd5 Cria o README

Antes:   A---B---C---D---E   ← main ← HEAD
                          \
                           S   ← bebidas            (S = f23e6d2, o suco)

Depois:  A---B---C---D---E-------M   ← main ← HEAD  (M = 33670d7, o commit de merge)
                          \     /
                           S----   ← bebidas

Em vez de Fast-forward, a saída diz Merge made by the 'ort' strategy. ("merge feito pela estratégia 'ort'"), e o desenho ganhou uma "bolha": o galho do suco entra e sai, e o commit de merge marca onde o branch foi juntado. Sem o -m, o Git abriria o editor com a mensagem Merge branch 'bebidas', como na aula git merge.

Com esses commits de merge, o git log --first-parent ("só o primeiro pai") mostra a história do main como uma lista de "o que entrou", pulando os commits de dentro dos branches. Você vai ver no fim da seção 4.

3. --ff-only: só se for fast-forward

O contrário: aceitar o merge somente se ele for fast-forward. Se precisar de um commit de merge, o Git recusa e não muda nada. Com um branch lanches que nasceu no fim do main, passa:

$ git switch -q -c lanches
$ echo 'Coxinha' > coxinha.txt
$ git add coxinha.txt && git commit -q -m 'Adiciona coxinha'
$ git switch -q main
$ git merge --ff-only lanches
Updating 33670d7..515a758
Fast-forward
 coxinha.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 coxinha.txt

Agora um caso em que os dois andaram: a Ana criou o branch chas com um chá e, no main, commitou uma feijoada:

$ git switch -q -c chas
$ echo 'Chá de hortelã' > cha.txt
$ git add cha.txt && git commit -q -m 'Adiciona chá'
$ git switch -q main
$ echo 'Feijoada' > feijoada.txt
$ git add feijoada.txt && git commit -q -m 'Adiciona receita de feijoada'
$ git log --oneline --graph --all -5
* 10b309b (chas) Adiciona chá
| * 13932f0 (HEAD -> main) Adiciona receita de feijoada
|/
* 515a758 (lanches) Adiciona coxinha
*   33670d7 Junta o ramo bebidas
|\
| * f23e6d2 (bebidas) Adiciona suco
|/
$ git merge --ff-only chas
hint: Diverging branches can't be fast-forwarded, you need to either:
hint:
hint:   git merge --no-ff
hint:
hint: or:
hint:
hint:   git rebase
hint:
hint: Disable this message with "git config set advice.diverging false"
fatal: Not possible to fast-forward, aborting.

       ...---L---F   ← main ← HEAD     (L = 515a758, a coxinha; F = 13932f0, a feijoada)
              \
               T   ← chas              (T = 10b309b, o chá)

O main não está no caminho do chas: não dá para "só andar para frente".

Linha por linha:

hint: Diverging branches can't be fast-forwarded, you need to either:
"Branches que divergiram não podem ser avançados rapidamente; você precisa ou:"
hint: git merge --no-ff
"…fazer um merge com commit de merge…" (um git merge chas normal, sem o --ff-only, também faz isso).
hint: or: git rebase
"…ou reorganizar os seus commits por cima do outro branch" (git rebase, nível avançado).
fatal: Not possible to fast-forward, aborting.
"Não é possível avançar rapidamente; abortando". Nada mudou.

Para que serve então? Para ter certeza de que um merge não vai criar commit nem conflito. Por exemplo, para atualizar o seu main com o do GitHub só quando você não tem nada local no meio (git pull --ff-only, veja git pull).

4. Deixando a escolha configurada: merge.ff

Se você sempre quer um dos dois comportamentos, configure o repositório (ou todos, com --global; veja git config):

ConfiguraçãoEfeito no git merge
(nenhuma, o padrão)Fast-forward quando dá; commit de merge quando precisa
git config merge.ff falseSempre commit de merge (como --no-ff)
git config merge.ff onlySó fast-forward (como --ff-only)
git config --unset merge.ffVolta ao padrão

Com merge.ff only, um merge comum do chas dá o mesmo erro da seção 3:

$ git config merge.ff only
$ git merge chas
hint: Diverging branches can't be fast-forwarded, you need to either:
hint:
hint:   git merge --no-ff
hint:
hint: or:
hint:
hint:   git rebase
hint:
hint: Disable this message with "git config set advice.diverging false"
fatal: Not possible to fast-forward, aborting.
$ git config --unset merge.ff

E com merge.ff false, um branch sucos que daria fast-forward ganha um commit de merge, sem precisar escrever --no-ff:

$ git config merge.ff false
$ git switch -q -c sucos HEAD
$ echo 'Suco de uva' > uva.txt
$ git add uva.txt && git commit -q -m 'Adiciona suco de uva'
$ git switch -q main
$ git merge sucos -m 'Junta o ramo sucos'
Merge made by the 'ort' strategy.
 uva.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 uva.txt
$ git config --unset merge.ff
$ git log --oneline --graph --all -8
* 10b309b (chas) Adiciona chá
| *   cdadcee (HEAD -> main) Junta o ramo sucos
| |\
| | * fb5a342 (sucos) Adiciona suco de uva
| |/
| * 13932f0 Adiciona receita de feijoada
|/
* 515a758 (lanches) Adiciona coxinha
*   33670d7 Junta o ramo bebidas
|\
| * f23e6d2 (bebidas) Adiciona suco
|/
* ae456dd (sobremesas) Adiciona receita de brigadeiro

Agora compare a história do main com --first-parent, que segue só o primeiro pai de cada commit de merge (o lado do main):

$ git log --oneline --graph --first-parent -6
* cdadcee (HEAD -> main) Junta o ramo sucos
* 13932f0 Adiciona receita de feijoada
* 515a758 (lanches) Adiciona coxinha
* 33670d7 Junta o ramo bebidas
* ae456dd (sobremesas) Adiciona receita de brigadeiro
* d6f2336 Adiciona receita de pudim

Os commits do suco de laranja e do suco de uva sumiram dessa visão: aparecem só os commits de merge que os trouxeram (Junta o ramo …). Já a coxinha, o pudim e o brigadeiro, que entraram por fast-forward, aparecem como se tivessem sido feitos direto no main. Essa é a diferença prática entre os dois estilos.

Experimente

O terminal está na pasta receitas. Use git log --oneline --graph --all antes e depois de cada merge, e compare o desenho.

Missão: junte o sobremesas no main exigindo que seja fast-forward. Depois, confira com git log --oneline --graph --all que as duas etiquetas estão no mesmo commit e que nenhum commit novo apareceu.

Missão: agora o contrário: junte o bebidas no main criando um commit de merge, mesmo que desse fast-forward, com a mensagem Junta o ramo bebidas. Veja a "bolha" no git log --oneline --graph --all.

Formas diferentes: qual estilo usar?

ComandoSe dá fast-forwardSe os dois andaram
git merge NOMEFast-forwardCommit de merge
git merge --no-ff NOMECommit de mergeCommit de merge
git merge --ff-only NOMEFast-forwardRecusa (Not possible to fast-forward)
  • Projeto pessoal, branches curtos: o padrão (git merge NOME) está ótimo. A história fica simples.
  • Equipe que quer ver cada funcionalidade como um bloco: --no-ff (ou merge.ff false). É o que muitos fluxos de trabalho pedem (Fluxos de Trabalho); o botão de merge de pull request do GitHub também cria commit de merge por padrão (ilustrativo; Pull Request).
  • Quando um merge "de verdade" seria uma surpresa: --ff-only, como no git pull --ff-only para atualizar o main.

Quando dá errado

fatal: Not possible to fast-forward, aborting.

Você usou --ff-only (ou tem merge.ff only configurado) e os dois branches andaram. Como confirmar: git log --oneline --graph --all mostra os dois galhos depois do ponto de separação; git config merge.ff mostra se a configuração está ligada. Como resolver: se um commit de merge serve, rode o merge sem --ff-only (com a configuração ligada, git merge --no-ff NOME). A outra saída da dica, o git rebase, fica para o nível avançado.

"Fiz o merge e o histórico não mostra que existiu um branch"

Foi um fast-forward: os commits do branch agora estão em linha reta no main. Não é erro, e nada se perdeu. Para a próxima: use --no-ff. (Dá para refazer um merge já feito, mas mexer em história que já foi para o GitHub é perigoso: veja a regra de ouro.)

"Esperava fast-forward e abriu o editor"

O Git abriu o editor com Merge branch '…', então ele vai criar um commit de merge: o branch atual tinha commits que o outro não tinha. Como confirmar: saia sem gravar nada diferente e veja o git log --oneline --graph --all; ou, antes do merge, rode git log --oneline main..NOME e git log --oneline NOME..main (se o segundo mostrar commits, não dá fast-forward). Também pode ser a configuração merge.ff false.

Resumo

  • Fast-forward é o merge em que o branch atual não andou: o Git só empurra a etiqueta para frente (Updating X..Y, Fast-forward). Sem commit novo, sem conflito possível.
  • Por dentro, muda só o arquivo .git/refs/heads/NOME, que passa a ter o hash do último commit do outro branch.
  • --no-ff cria um commit de merge mesmo assim, para o desenho mostrar que existiu um branch.
  • --ff-only só aceita fast-forward; se os branches divergiram: fatal: Not possible to fast-forward, aborting., sem mudar nada.
  • git config merge.ff false ou only deixa uma dessas opções como padrão; --unset volta ao normal.

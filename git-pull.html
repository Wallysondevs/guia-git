Git pull

Na aula de git fetch, a Ana trouxe o commit do Bruno em dois passos: buscar (git fetch) e juntar (git merge origin/main). O git pull (em inglês, "puxar") faz os dois de uma vez. É o comando que você vai digitar toda manhã, antes de começar a trabalhar num projeto em equipe.

Você vai aprender
  • O que o git pull faz por dentro: fetch + merge (ou rebase).
  • O caso fácil: o pull que só avança o seu branch (fast-forward).
  • O caso que assusta: branches divergentes, a mensagem Need to specify how to reconcile divergent branches e as três escolhas (--no-rebase, --rebase, --ff-only).
  • O que fazer quando o pull dá conflito.
  • Os erros mais comuns e como sair de cada um.

A ideia antes do comando

Volte à caixa de correio da aula de fetch. O fetch é pegar as cartas. O pull é pegar as cartas e já guardar tudo no lugar: as contas na gaveta, os convites na geladeira. É mais rápido, mas você não olha antes. Na maior parte dos dias, tudo bem.

git pull   =   git fetch            +   git merge origin/main
               (busca os commits)       (junta no seu branch)
git pull
Busca e junta, usando o par do branch atual (o upstream, configurado no git push -u ou no git clone).
git pull origin main
O mesmo, dizendo de onde: o branch main do remoto origin.

O caso fácil: só avançar

O Bruno enviou o óleo do bolo. A Ana não fez nada de novo desde a última vez. Um comando:

$ git pull
remote: Enumerating objects: 5, done.                          « parte 1: o fetch
remote: Counting objects: 100% (5/5), done.
remote: Compressing objects: 100% (3/3), done.
remote: Total 3 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
Unpacking objects: 100% (3/3), 306 bytes | 306.00 KiB/s, done.
From https://github.com/ana-souza/receitas
   4f68d0e..3dbde00  main       -> origin/main                « origin/main andou
Updating 4f68d0e..3dbde00                                       « parte 2: o merge
Fast-forward                                                    « só avançou
 bolo.txt | 1 +
 1 file changed, 1 insertion(+)
$ cat bolo.txt
Bolo de cenoura
- 3 cenouras
- 1 xícara de óleo                                              « a mudança do Bruno, na pasta
$ git log --oneline
3dbde00 (HEAD -> main, origin/main, origin/HEAD) Adiciona óleo ao bolo
4f68d0e Adiciona receita de bolo
0e8cf93 Adiciona README

A saída tem duas metades. Até a linha 4f68d0e..3dbde00 main -> origin/main, é o fetch (igual ao da aula anterior). De Updating para baixo, é o merge: Updating 4f68d0e..3dbde00 ("atualizando de … até …"), Fast-forward ("avanço rápido": o main só andou para a frente, sem commit de mesclagem) e o resumo dos arquivos mudados. No fim, main e origin/main estão no mesmo commit.

Mensagens em inglês? A tradução do Git que o Ubuntu usa é parcial (e às vezes cai no português de Portugal, como "submissões" e "divergiram-se"): num sistema em português, parte das mensagens sai em português e parte em inglês. O guia mostra o que o Git realmente escreve.

Experimente

Nos terminais abaixo, o "GitHub" é o GitHub de treino do guia, e o Bruno já enviou um commit que a Ana não tem. No terminal do guia, as linhas de progresso (Enumerating objects…, Writing objects…) não aparecem: ele mostra a versão curta da saída.

Missão: traga o commit do Bruno para o seu main com um comando só. Depois, confira com ls e git log --oneline.

O caso que assusta: branches divergentes

Agora as duas pessoas trabalharam ao mesmo tempo: a Ana fez o commit do pudim (sem enviar) e o Bruno enviou uma explicação no README. Cada lado tem um commit que o outro não tem: os branches divergiram.

             /
A---B---(óleo)
             \
              D   origin/main (Bruno: README)

Calma: nada se perdeu. O fetch foi feito (o origin/main andou), mas o Git parou antes de juntar, porque existem jeitos diferentes de juntar e ele quer que você escolha. Traduzindo a dica:

  • "Você tem branches divergentes e precisa dizer como reconciliá-los. Rode um destes comandos antes do próximo pull:"
  • git config pull.rebase false # merge: juntar com um commit de mesclagem.
  • git config pull.rebase true # rebase: replantar os seus commits em cima dos do remoto.
  • git config pull.ff only # fast-forward only: só aceitar o caso fácil; recusar quando divergir.
  • "Troque git config por git config --global para valer em todos os repositórios. Você também pode passar --rebase, --no-rebase ou --ff-only só neste pull."

Escolha 1: juntar com merge (--no-rebase)

$ git pull --no-rebase
Merge made by the 'ort' strategy.                              « commit de mesclagem criado

$ git log --oneline --graph
*   f3dead1 (HEAD -> main) Merge branch 'main' of https://github.com/ana-souza/receitas    « o commit de mesclagem
|\
| * 9b05483 (origin/main, origin/HEAD) Explica o projeto no README     « o do Bruno
* | b2e2cc4 Adiciona receita de pudim                          « o da Ana
|/
* 3dbde00 Adiciona óleo ao bolo
* 4f68d0e Adiciona receita de bolo
* 0e8cf93 Adiciona README
$ git status
No ramo main
Seu ramo está à frente de 'origin/main' por 2 submissões.      « o pudim e a mesclagem
  (use "git push" to publish your local commits)

nothing to commit, working tree clean

O Git criou um commit de mesclagem (veja Merge de Três Vias), com a mensagem automática Merge branch 'main' of …. No seu terminal, o editor de texto pode abrir com essa mensagem já escrita: é só salvar e fechar. O histórico ganha um "losango" e a Ana fica 2 commits à frente: falta só o git push.

Escolha 2: replantar com rebase (--rebase)

Na mesma situação (pudim da Ana × README do Bruno), outra forma:

$ git pull --rebase
Successfully rebased and updated refs/heads/main.              « commit da Ana replantado
$ git log --oneline --graph
* dbf0f16 (HEAD -> main) Adiciona receita de pudim             « o da Ana, agora por último (hash novo)
* 9b05483 (origin/main, origin/HEAD) Explica o projeto no README   « o do Bruno
* 3dbde00 Adiciona óleo ao bolo
* 4f68d0e Adiciona receita de bolo
* 0e8cf93 Adiciona README

O Git tirou o commit da Ana do caminho, aplicou o do Bruno e replantou o da Ana em cima (por isso o hash mudou: era b2e2cc4, virou dbf0f16). O histórico fica uma linha reta, sem commit de mesclagem, como se a Ana tivesse começado o pudim depois do Bruno. É o que muita equipe prefere. Os detalhes estão em git rebase e em Rebase ou Merge?.

Escolha 3: só o caso fácil (--ff-only)

hint:
hint:   git merge --no-ff
hint:

"Branches divergentes não podem ser avançados; você precisa fazer git merge --no-ff ou git rebase". O --ff-only é o modo cauteloso: ele só junta quando é para avançar e, se houver divergência, para e deixa você decidir com calma.

Escolha uma vez e esqueça. Para quem está começando, uma boa escolha é o merge, que nunca reescreve commits: git config --global pull.rebase false. Se a sua equipe pedir histórico linear, use git config --global pull.rebase true. Depois disso, o git pull sozinho não mostra mais a dica.

Missão: a Ana fez o commit do pudim e o Bruno enviou o do suco: os branches divergiram. Rode git pull e leia a dica. Depois, junte os dois trabalhos com git pull --rebase (ou git pull --no-rebase) e confira o resultado com git log --oneline --graph.

Quando o pull dá conflito

Divergir em arquivos diferentes é tranquilo. Mas e se os dois mudaram a mesma linha? A Ana trocou "3 cenouras" por "2 cenouras"; o Bruno, por "4 cenouras".

$ git pull --no-rebase
remote: Enumerating objects: 5, done.
remote: Counting objects: 100% (5/5), done.
remote: Compressing objects: 100% (3/3), done.
remote: Total 3 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
Unpacking objects: 100% (3/3), 329 bytes | 329.00 KiB/s, done.
From https://github.com/ana-souza/receitas
   dbf0f16..22ed7d7  main       -> origin/main
Mesclagem automática de bolo.txt
CONFLITO (conteúdo): conflito de mesclagem em bolo.txt         « a mesma linha, dos dois lados
Automatic merge failed; fix conflicts and then commit the result.
$ git status
No ramo main
O seu branch e 'origin/main' divergiram-se,
e cada um tem 1 e 1 submissões, respectivamente.
  (use "git pull" if you want to integrate the remote branch with yours)

Você tem caminhos não mesclados.
  (fixar conflitos e executar "git commit")
  (use "git merge --abort" to abort the merge)

Caminhos não mesclados:

        ambos modificados:   bolo.txt                     « os dois mexeram aqui

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
$ cat bolo.txt
Bolo de cenoura
<<<<<<< HEAD
- 2 cenouras                                                    « a versão da Ana
=======
- 4 cenouras                                                    « a versão do Bruno
>>>>>>> 22ed7d7c61a6d29fec3f46f623892220ca183a41    « o commit do Bruno
- 1 xícara de óleo                                              « fora do conflito: igual nos dois

"A mesclagem automática falhou; corrija os conflitos e faça o commit do resultado". É um conflito de merge comum, só que veio pelo pull. Você tem duas saídas:

  • Resolver: editar o bolo.txt deixando a versão certa (sem as linhas <<<<<<<, ======= e >>>>>>>), git add bolo.txt e git commit. Passo a passo em Resolvendo Conflitos.
  • Desistir e voltar a como estava antes do pull: git merge --abort, como a própria dica diz (veja Desistindo de um Merge). O fetch fica feito; só o merge é desfeito.

Quando dá errado

"Need to specify how to reconcile divergent branches"

O que aconteceu: você e o remoto têm commits diferentes, e o Git não sabe se você prefere merge ou rebase. O fetch foi feito; o merge, não.

Como resolver: rode de novo com git pull --no-rebase ou git pull --rebase, e configure a preferência de uma vez com git config --global pull.rebase false (ou true).

        bolo.txt

$ git status --short
 M bolo.txt                                              « a mudança da Ana continua intacta

O que aconteceu: "suas mudanças locais nos arquivos abaixo seriam sobrescritas pelo merge". A Ana tem uma mudança sem commit no bolo.txt, e o commit que chegou também mexe nele. Para não apagar o trabalho dela, o Git abortou (Aborting) e não mudou nada.

Como resolver: "faça o commit das suas mudanças ou guarde-as com stash antes do merge": git commit -am "…" e git pull de novo; ou git stash, git pull, git stash pop (veja git stash).

"There is no tracking information for the current branch" 
$ git switch -c teste
Switched to a new branch 'teste'
$ git pull
There is no tracking information for the current branch.
Please specify which branch you want to merge with.
See git-pull(1) for details.

    git pull <remote> <branch>

If you wish to set tracking information for this branch you can do so with:

    git branch --set-upstream-to=origin/<branch> teste

O que aconteceu: "não há informação de rastreamento para o branch atual": o branch teste foi criado no notebook e não tem par no remoto, então o Git não sabe de onde puxar.

Como resolver: diga de onde (git pull origin main), ou ligue o branch a um branch remoto com git branch --set-upstream-to=origin/NOME (veja upstream). Se o branch ainda não existe no remoto, envie com git push -u origin teste.

Conflito no meio do pull

O que aconteceu: você e o colega mudaram as mesmas linhas.

Como resolver: resolva o conflito e faça o commit, ou desista com git merge --abort (no pull com merge) ou git rebase --abort (no pull com rebase). Veja "Quando o pull dá conflito", acima.

Resumo

  • git pull = git fetch + juntar (merge ou rebase) no branch atual.
  • Se só o remoto andou, o pull é um fast-forward: o seu branch só avança.
  • Se os dois lados têm commits novos, os branches divergiram: escolha --no-rebase (merge), --rebase (linha reta) ou --ff-only (recusar), e configure a preferência com pull.rebase.
  • Conflito no pull é conflito de merge: resolva e faça o commit, ou git merge --abort.
  • Com mudanças sem commit que o pull sobrescreveria, ele para sem estragar nada: faça o commit ou o stash antes.

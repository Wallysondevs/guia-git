Git Hooks

Um hook (em inglês, "gancho") é um pequeno programa que o Git roda sozinho num momento certo: antes de cada commit, depois de escrever a mensagem, antes de um push. Com ele você ensina o Git a conferir as coisas por você, por exemplo, a recusar um commit que tenha uma senha dentro. Nesta aula a Ana cria um hook de verdade e vê o Git bloqueando o commit dela.

Você vai aprender
  • O que é um hook e onde ele mora: a pasta .git/hooks.
  • Como escrever um pre-commit que cancela o commit quando acha senha= nos arquivos.
  • Como um commit-msg recusa mensagens curtas demais.
  • Como pular um hook (--no-verify) e quando isso é aceitável.
  • Por que os hooks não vão junto no clone, e como dividir com a equipe usando core.hooksPath.

Todas as saídas desta aula vieram do Git real do Ubuntu na máquina da Ana (usuária ana, computador notebook), com o sistema em português. Com o sistema em inglês, as mensagens do Git saem em inglês, mas as do hook são as que você escreveu.

A ideia: o porteiro do prédio

No prédio da Ana, todo mundo que entra passa pelo porteiro. Ele tem uma lista curta: "entregador sem nome do morador? não entra". Os moradores não precisam lembrar de nada: o porteiro confere toda vez, sem esquecer.

Um hook é esse porteiro, contratado por você:

  • Quando ele trabalha depende do nome do arquivo: o pre-commit ("antes do commit") trabalha logo depois de você digitar git commit e antes de o commit existir.
  • O que ele confere é você que escreve: é um script comum (aqui, um script de shell, como os do terminal).
  • A decisão vem do código de saída do script: terminou com exit 0, "pode passar"; terminou com qualquer outro número (como exit 1), "não passa", e o Git cancela o commit.

1. Onde os hooks moram: .git/hooks

Todo repositório criado com git init já vem com uma pasta de exemplos dentro do .git. A Ana criou o repositório do site de receitas e olhou:

$ mkdir receitas && cd receitas && git init -q
$ echo '# Receitas da Ana' > README.md
$ git add README.md && git commit -q -m 'Primeiro commit'
$ ls .git/hooks
applypatch-msg.sample
commit-msg.sample                 « exemplo de commit-msg (seção 4)
fsmonitor-watchman.sample
post-update.sample
pre-applypatch.sample
pre-commit.sample                 « exemplo de pre-commit (seção 2)
pre-merge-commit.sample
pre-push.sample
pre-rebase.sample
pre-receive.sample
prepare-commit-msg.sample
push-to-checkout.sample
sendemail-validate.sample
update.sample

São exemplos, todos terminados em .sample ("amostra"). O Git ignora qualquer arquivo com essa terminação: eles estão ali só para você ler e copiar. Para um hook valer de verdade, ele precisa de duas coisas:

  1. o nome exato, sem extensão: pre-commit, e não pre-commit.sample nem pre-commit.sh;
  2. a permissão de execução (o chmod +x), senão o Git não o roda (veja Quando dá errado).
Por que fica dentro do .git?

Porque é uma configuração da sua cópia do repositório, como o .git/config. Nada dentro do .git entra nos commits, então o hook não vai para o GitHub e não chega a quem clona. A seção 6 mostra como dividir hooks com a equipe mesmo assim.

2. O primeiro hook: um pre-commit que barra senhas

A Ana tem medo de um dia commitar, sem querer, um arquivo com a senha do banco de dados (veja Commitei uma Senha!: depois de publicada, desfazer dá muito trabalho). Ela decidiu: nenhum commit passa se algum arquivo preparado tiver senha=. Ela criou o arquivo .git/hooks/pre-commit com o editor:

#!/bin/sh
# pre-commit: roda antes de cada commit.
# Se algum arquivo preparado tiver "senha=", o commit é cancelado.
if git diff --cached | grep -q '^+.*senha='; then
  echo "pre-commit: encontrei 'senha=' nos arquivos preparados."
  echo "pre-commit: commit cancelado. Tire a senha e tente de novo."
  exit 1
fi
exit 0
#!/bin/sh
A primeira linha (o shebang) diz qual programa roda o script: aqui, o shell sh. Hooks podem ser escritos em qualquer linguagem (Python, Node…), basta trocar esta linha.
git diff --cached
Mostra o que está na área de preparo, ou seja, exatamente o que vai entrar no commit (é o mesmo que git diff --staged). As linhas acrescentadas começam com +.
grep -q '^+.*senha='
Procura uma linha que começa com + (linha nova) e tem senha= em algum lugar. O -q ("quieto") não mostra nada: só responde "achei" ou "não achei".
if … then … fi
Se achou, mostra duas linhas de aviso (o echo) e termina com exit 1.
exit 1
"Não passa." Qualquer código diferente de 0 faz o Git cancelar o commit.
exit 0
"Pode passar." O Git segue e cria o commit.

Depois de salvar, ela deu a permissão de execução e conferiu com o ls -l:

$ chmod +x .git/hooks/pre-commit
$ ls -l .git/hooks/pre-commit
-rwxrwxr-x 1 ana ana 322 Oct 15 10:29 .git/hooks/pre-commit

Os x em -rwxrwxr-x são o "pode ser executado". Agora o porteiro está trabalhando.

O hook em ação: o commit bloqueado

Para testar, a Ana criou um config.txt com uma senha, preparou e tentou commitar:

$ echo 'senha=batata123' > config.txt
$ git add config.txt
$ git commit -m 'Adiciona configuração'
pre-commit: encontrei 'senha=' nos arquivos preparados.
pre-commit: commit cancelado. Tire a senha e tente de novo.
$ echo $?
1

Linha por linha:

pre-commit: encontrei 'senha=' …
Não é o Git falando: são os dois echo do hook da Ana. O Git rodou o pre-commit e mostrou o que ele escreveu.
(nenhuma linha [main …])
Num commit que dá certo, o Git mostra [main 9183582] Adiciona configuração e um resumo. Aqui não aparece nada disso: como o hook terminou com exit 1, o Git parou antes de criar o commit.
echo $? → 1
O código de saída do git commit foi 1, "deu errado". Um script que chama o Git percebe que o commit não saiu.

O histórico e a área de preparo continuam como estavam: o commit não foi criado, e o arquivo segue preparado, esperando:

$ git log --oneline
fe996fb Primeiro commit
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	new file:   config.txt          « continua preparado

(Algumas dicas do git status ainda saem em inglês no Git 2.53 do Ubuntu, mesmo com o sistema em português: a tradução do Git não está completa. "to unstage" é "para tirar da área de preparo", e "new file" é "arquivo novo".)

O git log continua com um commit só, e o git status mostra o config.txt em "Mudanças a serem submetidas": nada se perdeu, só não entrou no histórico.

Consertando e commitando

A Ana trocou a senha por uma linha inofensiva, preparou de novo e commitou. Desta vez o hook rodou, não achou nada e terminou com exit 0, sem dizer nada:

$ echo 'usuario=ana' > config.txt
$ git add config.txt
$ git commit -m 'Adiciona configuração'
[main 9183582] Adiciona configuração
 1 file changed, 1 insertion(+)
 create mode 100644 config.txt
$ git log --oneline
9183582 Adiciona configuração
fe996fb Primeiro commit
Um bom hook é rápido e quieto

O pre-commit roda em todo commit. Se ele demorar 30 segundos, você vai odiá-lo (e acabar desligando). Quando tudo está certo, não precisa dizer nada; quando barrar, diga o quê e como resolver, como o da Ana.

Missão: o repositório receitas já tem o arquivo .git/hooks/pre-commit da Ana, mas ela esqueceu de dar a permissão de execução. Veja o arquivo (cat .git/hooks/pre-commit), confira a permissão com ls -l .git/hooks e deixe o hook executável.

Limite do terminal do guia

O Git do terminal do guia é uma imitação em JavaScript e não roda hooks: lá, depois do chmod +x, um commit com senha= ainda passa (e o git hook run não existe). A missão confere só a permissão. Para ver o porteiro barrando o commit, como nas saídas desta aula, repita os passos num Git de verdade, no seu computador.

3. Pulando o porteiro: --no-verify

Às vezes você sabe que o hook está errado naquele caso (um arquivo de teste com senha=exemplo, por exemplo). Para fazer um commit sem rodar o pre-commit (nem o commit-msg), use --no-verify (a forma curta é -n):

$ echo 'senha=batata123' >> config.txt
$ git add config.txt
$ git commit --no-verify -m 'Teste sem o porteiro'
[main 8b62765] Teste sem o porteiro
 1 file changed, 1 insertion(+)
$ git log --oneline
8b62765 Teste sem o porteiro          « passou, com a senha dentro
9183582 Adiciona configuração
fe996fb Primeiro commit

O commit passou, mesmo com senha= no arquivo. Por isso um hook local é uma ajuda, não uma garantia: quem quiser, pula. Regras que não podem ser puladas ficam no servidor (no GitHub, nas proteções de branch e nas verificações do GitHub Actions).

Use --no-verify com consciência

Se você pula o hook toda hora, ou ele está errado (conserte-o), ou você está fazendo algo arriscado. A Ana, no caso acima, estava só testando: na vida real, aquele commit com senha deveria ser desfeito antes de qualquer push (veja --amend e git reset).

Rodando um hook na mão: git hook run git 2.36+

Para testar o hook sem tentar um commit, peça ao Git para rodá-lo:

$ git hook run pre-commit
$ echo $?
0

O git hook run roda o hook como o git commit rodaria e devolve o código de saída dele. O commit de teste da seção anterior deixou senha= no histórico, mas o hook olha só a área de preparo, que está vazia: por isso ele não achou nada e o código de saída foi 0.

4. O commit-msg: conferindo a mensagem

O pre-commit olha os arquivos. Para olhar a mensagem do commit, existe o commit-msg. O Git escreve a mensagem num arquivo temporário e passa o caminho desse arquivo para o hook, como o primeiro argumento ($1). A Ana quer recusar mensagens preguiçosas como ajuste (veja Boas Mensagens de Commit):

#!/bin/sh
# commit-msg: recebe o caminho do arquivo com a mensagem em $1.
mensagem=$(head -n 1 "$1")
if [ ${#mensagem} -lt 10 ]; then
  echo "commit-msg: a mensagem \"$mensagem\" é curta demais (mínimo 10 letras)."
  exit 1
fi
$1
O caminho do arquivo com a mensagem (normalmente .git/COMMIT_EDITMSG).
head -n 1 "$1"
Pega só a primeira linha: o título do commit.
${#mensagem}
O tamanho do texto, em letras.
-lt 10
"Menor que 10" (less than). Sem exit no fim, o script termina com o código do último comando, que é 0 quando o if não entra.
$ chmod +x .git/hooks/commit-msg
$ echo 'tempo=40min' >> README.md
$ git add README.md
$ git commit -m 'ajuste'
commit-msg: a mensagem "ajuste" é curta demais (mínimo 10 letras).
$ git commit -m 'Anota o tempo de preparo no README'
[main dae2d72] Anota o tempo de preparo no README
 1 file changed, 1 insertion(+)
$ git log --oneline
dae2d72 Anota o tempo de preparo no README
8b62765 Teste sem o porteiro
9183582 Adiciona configuração
fe996fb Primeiro commit

A mensagem ajuste tem 6 letras: barrada. A segunda, descritiva, passou pelos dois porteiros (o pre-commit e o commit-msg).

5. Os hooks mais usados

O nome do arquivo decide o momento. Os do lado do cliente (o seu computador) são os que você vai usar:

HookQuando rodaPode cancelar?Uso típico
pre-commitLogo no git commit, antes de pedir a mensagemSimBarrar senhas, rodar o formatador, rodar testes rápidos
prepare-commit-msgAntes de abrir o editor da mensagemSimPré-preencher a mensagem (por exemplo, com o nome do branch)
commit-msgDepois que a mensagem foi escritaSimConferir o formato da mensagem (Conventional Commits)
post-commitDepois que o commit foi criadoNãoAvisar, registrar
pre-pushNo git push, antes de enviarSimRodar a bateria de testes completa antes de publicar
post-checkout / post-mergeDepois de trocar de branch / depois de um merge (inclusive o do pull)NãoReinstalar dependências, limpar arquivos gerados
pre-rebaseAntes de um git rebaseSimImpedir rebase de branches publicados

Existem também hooks do lado do servidor (pre-receive, update, post-receive), que rodam no repositório que recebe o push. No GitHub você não instala hooks de servidor: o equivalente são as regras de proteção de branch e o GitHub Actions. A lista completa está em git help githooks (veja git help).

6. Dividindo os hooks com a equipe: core.hooksPath

Como a pasta .git/hooks não é versionada, o Bruno, que clonou o repositório, não tem o porteiro da Ana. A solução comum é guardar os hooks numa pasta versionada (por exemplo, .githooks) e dizer ao Git para procurá-los lá, com a configuração core.hooksPath git 2.9+:

$ mkdir .githooks
$ cp .git/hooks/pre-commit .githooks/pre-commit
$ chmod +x .githooks/pre-commit
$ git config core.hooksPath .githooks
$ git config core.hooksPath
.githooks
$ echo 'tchau' >> a.txt
$ git add a.txt
$ git commit -m 'Segundo commit da loja'
pre-commit: conferindo...
$ git log --oneline
0d93a28 Primeiro commit da loja          « o segundo commit foi barrado

Aqui a Ana usou o repositório da lojinha, cujo pre-commit de teste só escreve pre-commit: conferindo... e termina com exit 1.

git config core.hooksPath .githooks
"Procure os hooks na pasta .githooks, e não mais em .git/hooks." Um caminho relativo vale a partir da raiz do repositório.
pre-commit: conferindo...
O hook da pasta nova rodou (e, como esse exemplo termina com exit 1, barrou o commit).

A pasta .githooks entra nos commits como qualquer outra. Quem clonar ainda precisa rodar uma vez o git config core.hooksPath .githooks (por segurança, o Git nunca liga hooks sozinho num clone: seria um jeito de rodar programas no computador de quem clonou). Costuma-se pôr esse comando no README.

Ferramentas prontas (ilustrativo)

Em projetos maiores, as equipes usam programas que instalam e organizam os hooks: o pre-commit (pre-commit.com, comum em projetos Python), o Husky (comum em projetos JavaScript) e o Lefthook. Eles fazem o mesmo que você fez aqui: colocam um script no lugar certo e rodam verificações. Estude a documentação de cada um quando precisar.

Quando dá errado

O hook "não roda": falta o chmod +x 
$ printf '#!/bin/sh\necho "pre-commit: commit cancelado"\nexit 1\n' > .git/hooks/pre-commit
$ echo 'Capítulo 1' > tcc.txt
$ git add tcc.txt
$ git commit -m 'Começa o TCC'
hint: The '.git/hooks/pre-commit' hook was ignored because it's not set as executable.
hint: You can disable this warning with `git config set advice.ignoredHook false`.
[main (root-commit) d0d7fc0] Começa o TCC
 1 file changed, 1 insertion(+)
 create mode 100644 tcc.txt
$ ls -l .git/hooks/pre-commit
-rw-rw-r-- 1 ana ana 53 Oct 15 10:29 .git/hooks/pre-commit

As duas linhas hint: ("dica:") ainda não têm tradução no Git do Ubuntu e saem em inglês: "O hook .git/hooks/pre-commit foi ignorado porque não está marcado como executável" e "Você pode desligar este aviso com git config set advice.ignoredHook false".

O que aconteceu: o arquivo tem o nome certo, mas não tem permissão de execução (-rw-rw-r--, sem nenhum x), então o Git ignorou o hook, avisou com o hint e fez o commit, que o hook deveria ter barrado. Como resolver: chmod +x .git/hooks/pre-commit. Não desligue o aviso: ele é o que mostra que o seu porteiro está dormindo.

O nome está errado: pre-commit.sh

O que aconteceu: o Git procura o nome exato (pre-commit, sem extensão). Com pre-commit.sh, ou pre-commit.sample, ele não acha nada e não avisa nada: o commit passa em silêncio. Como resolver: mv .git/hooks/pre-commit.sh .git/hooks/pre-commit (e o chmod +x).

O commit "não sai" e você não entende por quê

Se um git commit volta para o prompt sem criar nada, procure uma mensagem de hook logo acima, como a pre-commit: … da Ana. Como confirmar: ls .git/hooks (procure arquivos sem .sample) e git config core.hooksPath (se responder algo, os hooks estão naquela pasta). Como resolver: leia o hook com cat, conserte o que ele aponta e commite de novo.

"Permission denied" ou "bad interpreter" ao rodar o hook

Se o hook foi escrito no Windows, ele pode ter fim de linha CRLF, e a primeira linha vira #!/bin/sh\r, um programa que não existe. Como resolver: salve o arquivo com fim de linha LF (veja Fim de Linha e .gitattributes).

Resumo

  • Hook = script que o Git roda sozinho num momento certo. Mora em .git/hooks, com o nome exato e chmod +x.
  • pre-commit confere os arquivos; commit-msg confere a mensagem (em $1). exit diferente de 0 cancela, e nada se perde.
  • git commit --no-verify pula os hooks: eles ajudam, mas não garantem. Regras obrigatórias ficam no servidor.
  • .git/hooks não vai no clone. Para a equipe: pasta versionada + git config core.hooksPath.
  • Hook sem x é ignorado (com um aviso hint:); hook com o nome errado é ignorado em silêncio.

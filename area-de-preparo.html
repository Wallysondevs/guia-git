Git Área de Preparo (staging)

Quem vem de outros programas estranha: por que o Git não tem um botão "salvar versão"? Por que é preciso git add e depois git commit? A resposta é a área de preparo (em inglês, staging area; nos textos técnicos, também index, "índice"). Ela é o lugar onde você monta o próximo commit, com calma, escolhendo o que entra. Esta aula explica a ideia, mostra as três versões que um arquivo pode ter ao mesmo tempo e ensina a usar a área de preparo a seu favor.

Você vai aprender
  • O que é a área de preparo e por que ela existe.
  • Como separar mudanças misturadas em commits com um assunto só.
  • As três versões de um arquivo (pasta, área de preparo, último commit) e como ver a diferença entre elas com git diff e git diff --staged.
  • Como preparar só um pedaço de um arquivo com git add -p.
  • Como pular a área de preparo com git commit -a, e quando isso dá errado.

As saídas são reais, do Git 2.53 da máquina da Ana (Ubuntu 26.04, em português; parte das mensagens do Git ainda sai em inglês, porque a tradução está incompleta). Esta aula usa o git status e o git add: se ainda não viu essas aulas, comece por elas.

A ideia: a caixa do correio

A Ana vende doces pela internet. No fim do dia, ela monta as caixas para o correio. Na bancada (a pasta de trabalho) tem de tudo: bolos prontos, um pudim pela metade, embalagens. Ela não despacha a bancada inteira: pega uma caixa (a área de preparo), põe dentro só o pedido da dona Maria, confere, fecha, cola a etiqueta e despacha (o commit). Depois monta a caixa do próximo pedido.

  pasta de trabalho          área de preparo            histórico
  (a bancada)                (a caixa aberta)           (o que já foi despachado)

  você edita aqui  ──git add──▶  você monta aqui  ──git commit──▶  fica guardado
                   ◀──git restore --staged──

Sem a caixa, cada despacho levaria tudo o que está na bancada. Com ela, você decide. No Git é igual: você pode ter mexido em cinco arquivos, mas fazer um commit só com os dois que tratam do mesmo assunto.

1. Para que serve: commits com um assunto só

A Ana fez duas coisas que não têm nada a ver uma com a outra: acrescentou os ovos na receita de bolo e pôs o e-mail de contato no README.

$ echo 'Contato: ana@exemplo.com' >> README.md
$ printf 'Bolo de cenoura\n3 cenouras\n2 xícaras de açúcar\n3 ovos\n' > bolo.txt
$ git status -s
 M README.md
 M bolo.txt

Ela poderia fazer um commit só, com a mensagem "Muda o bolo e o README". Mas, se um dia quiser desfazer só a mudança do bolo, ou procurar quando o contato entrou, vai ser mais fácil se cada assunto tiver o seu commit. Com a área de preparo, isso é simples:

$ git add bolo.txt
$ git commit -m "Acrescenta os ovos no bolo"
[main 10fedce] Acrescenta os ovos no bolo
 1 file changed, 1 insertion(+)                « só o bolo.txt entrou
$ git add README.md
$ git commit -m "Adiciona o contato no README"
[main 6d6ce07] Adiciona o contato no README
 1 file changed, 1 insertion(+)
$ git log --oneline
6d6ce07 (HEAD -> main) Adiciona o contato no README
10fedce Acrescenta os ovos no bolo
7ffc6d7 Primeira versão

O 1 file changed do primeiro commit confirma: o README.md também estava modificado, mas não estava na caixa, então não foi despachado. Ele esperou o commit seguinte.

Um commit, um assunto

É uma das boas práticas mais importantes do Git: cada commit deve fazer uma coisa, que caiba numa mensagem curta (aula Boas Mensagens de Commit). Se a mensagem precisa de um "e" ("Muda o bolo e o README"), talvez sejam dois commits. A área de preparo existe para isso.

Missão: o README.md e o bolo.txt foram modificados. Faça dois commits: primeiro só o bolo.txt, depois só o README.md. Confira com git log --oneline e com o git status entre um commit e outro.

2. A área de preparo não fica vazia depois do commit

Um engano comum é achar que, depois do commit, a área de preparo fica vazia. Ela não fica: ela guarda uma cópia de todos os arquivos rastreados, do jeito que vão estar no próximo commit. Logo depois de um commit, essa cópia é igual ao commit, e por isso o git status não mostra nada nela. O comando git ls-files lista os arquivos que estão na área de preparo:

$ git status
No ramo main
nothing to commit, working tree clean
$ git ls-files
README.md
bolo.txt

O git status diz "nada a commitar", mas o git ls-files mostra que os dois arquivos estão lá. O git status mostra diferenças, não o conteúdo: em "Mudanças a serem submetidas" aparece só o que, na área de preparo, é diferente do último commit.

Por isso, "preparar" um arquivo é trocar a cópia dele na área de preparo pela versão da pasta. E o próximo commit é, sempre, uma fotografia da área de preparo inteira (não só do que você preparou agora).

3. As três versões de um arquivo

Então um mesmo arquivo pode existir em três versões ao mesmo tempo: a do último commit, a da área de preparo e a da pasta. Veja o bolo.txt da Ana: ela acrescentou o óleo, preparou, e depois acrescentou o forno:

$ echo '1 xícara de óleo' >> bolo.txt
$ git add bolo.txt
$ echo 'Forno a 180 graus' >> bolo.txt
$ git status -s
MM bolo.txt
Último commitÁrea de preparoPasta de trabalho

O MM do formato curto é exatamente isso: o primeiro M diz que a área de preparo é diferente do commit; o segundo, que a pasta é diferente da área de preparo. Dois comandos mostram o que mudou em cada passo:

$ git diff
diff --git a/bolo.txt b/bolo.txt
index 7b5e30a..21c5954 100644

+++ b/bolo.txt
@@ -3,3 +3,4 @@ Bolo de cenoura

+Forno a 180 graus              « pasta × área de preparo: o que ainda NÃO foi preparado
$ git diff --staged
diff --git a/bolo.txt b/bolo.txt
index 4f7a1aa..7b5e30a 100644
--- a/bolo.txt
+++ b/bolo.txt
@@ -2,3 +2,4 @@ Bolo de cenoura
 3 cenouras
 2 xícaras de açúcar

+1 xícara de óleo               « área de preparo × último commit: o que VAI entrar no commit
git diff
Compara a pasta com a área de preparo: mostra o que você mudou e ainda não preparou. Aqui, só o forno.
git diff --staged
Compara a área de preparo com o último commit: mostra o que vai entrar no próximo commit. Aqui, só o óleo. (--cached é outro nome para a mesma opção.)
linhas com +
Linhas acrescentadas. As linhas sem sinal, em volta, são o contexto, para você se localizar. A leitura completa da saída do diff está nas aulas git diff e git diff --staged.

Se a Ana fizer o commit agora, ele leva o óleo e não leva o forno. Para levar os dois, git add bolo.txt de novo.

4. Preparar só um pedaço do arquivo: git add -p

Às vezes as duas mudanças estão no mesmo arquivo. A Ana mudou o título da receita para "Bolo de cenoura da vó" e, no fim, acrescentou o tempo de forno. Ela quer um commit só com o tempo de forno. O git add -p (de patch, "remendo") mostra cada pedaço modificado e pergunta, um por um, se é para preparar:

$ git status -s
MM bolo.txt
(1/2)
Pedaço 1 de 2. O Git divide as mudanças do arquivo em pedaços (hunks) separados por linhas que não mudaram.
Stage this hunk
"Preparar este pedaço?"
y / n
As respostas que você mais vai usar: y (yes) prepara o pedaço; n (no) deixa de fora.

q sai (o que já foi respondido fica); a prepara este e todos os seguintes do arquivo; d nenhum dos seguintes; s divide o pedaço em pedaços menores, quando dá; e abre o pedaço no editor; ? mostra a ajuda com todas as letras. A lista muda de um pedaço para outro: o k ("volta ao anterior"), por exemplo, não aparece no último.

O git add -p é interativo: ele precisa de você no teclado, respondendo. Por isso ele não está nas missões do terminal do guia; experimente no seu computador. Sem nenhuma mudança para mostrar, ele responde só No changes. ("nenhuma mudança").

5. Tirar da área de preparo

Pôs na caixa o que não devia? Tire antes de despachar. Num repositório em que a Ana tinha acabado de criar o bolo.txt e apagar o pudim.txt, ela rodou git add . e o rascunho dela foi junto. A própria dica do git status mostra o comando para tirar:

$ echo 'ligar pro Bruno' > rascunho.txt
$ git add .
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	new file:   bolo.txt
	deleted:    pudim.txt
	new file:   rascunho.txt

$ git restore --staged rascunho.txt
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	new file:   bolo.txt
	deleted:    pudim.txt

Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	rascunho.txt

O git restore --staged devolve a cópia da área de preparo ao que estava no último commit. O arquivo da pasta não muda: nenhuma edição se perde. Os detalhes estão em Tirando da Área de Preparo.

6. Pular a área de preparo: git commit -a

Quando tudo o que mudou é de um assunto só, preparar arquivo por arquivo dá trabalho. O git commit -a (de all, "todos") prepara todos os arquivos rastreados que mudaram e faz o commit, de uma vez. Mas atenção ao "rastreados":

$ echo 'Pudim de leite' > pudim.txt
$ echo 'Site de receitas' >> README.md
$ git status -s
 M README.md
?? pudim.txt
$ git commit -a -m "Atualiza o README"
[main efb72c3] Atualiza o README
 1 file changed, 1 insertion(+)              « só o README
$ git status -s
?? pudim.txt                                  « o arquivo novo ficou de fora

O pudim.txt era novo (??), então o -a não o pegou. Arquivo novo sempre precisa de um git add na primeira vez. A aula git commit mostra o -a com mais detalhes.

Missão: há duas mudanças em arquivos rastreados e um arquivo novo (pudim.txt). Faça um commit que leve as três coisas, usando o git commit -a. Dica: o que o -a não pega sozinho?

Quando dá errado

"Preparei, mas o commit não levou a última mudança"

Você preparou o arquivo e o editou de novo antes do commit (seção 3). O commit leva a cópia da área de preparo. Como confirmar: depois do commit, o git status ainda mostra o arquivo como modificado, e o git diff mostra a linha que ficou de fora. Como resolver: git add arquivo e outro commit; ou, se ainda não enviou para o GitHub, junte ao commit anterior com git commit --amend.

Respondi n para tudo no git add -p e o commit não aconteceu 
$ git commit -q -m "Adiciona a cobertura"
No ramo main
Changes not staged for commit:
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   bolo.txt

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")

A caixa estava vazia: nenhum pedaço foi preparado, então não há o que commitar, e o Git mostra o git status no lugar do commit (mesmo com o -q, que só silencia o commit bem-sucedido). Como resolver: rode o git add -p de novo e responda y nos pedaços que devem entrar, ou git add arquivo para o arquivo inteiro.

O git commit -a deixou um arquivo de fora

Era um arquivo novo (seção 6): o -a só pega os rastreados. Como resolver: git add arquivo-novo e outro commit.

Resumo

  • A área de preparo (staging area, ou index) é onde você monta o próximo commit. O commit é uma fotografia dela inteira.
  • Ela existe para você escolher o que entra: um commit, um assunto, mesmo que tenha mexido em muita coisa.
  • Ela nunca fica vazia: guarda uma cópia de todos os arquivos rastreados. O git status mostra só as diferenças.
  • Um arquivo pode ter três versões: último commit, área de preparo e pasta. git diff --staged mostra o que vai entrar; git diff, o que ainda não foi preparado.
  • git add -p prepara pedaço por pedaço; git restore --staged tira da área de preparo; git commit -a pula o preparo, mas só para arquivos rastreados.

Git add

O git add ("adicionar") é o comando que diz ao Git: "esta mudança vai entrar no próximo commit". Ele põe o arquivo na área de preparo, a mesa onde você arruma o que vai sair na próxima fotografia do projeto. Nesta aula você vai ver todas as formas de usar o git add: um arquivo, vários, uma pasta inteira, tudo de uma vez, só o que já era rastreado, e o que acontece com arquivos apagados.

Você vai aprender
  • O que o git add faz de verdade: guarda uma cópia do arquivo como ele está naquele momento.
  • Preparar um arquivo, vários, uma pasta e tudo com git add . e git add -A.
  • A diferença entre git add ., git add -A e git add -u.
  • Ver o que o comando fez com -v, e o que ele faria com --dry-run.
  • Os erros reais: pathspec … did not match any files, o arquivo ignorado e o caminho fora do repositório.

As saídas são reais, do Git da máquina da Ana, em português. O git status aparece depois de cada git add, porque o add não mostra nada quando dá certo; se ainda não sabe ler o painel, veja antes a aula git status.

A ideia: a mesa da foto

Lembre da confeitaria de Seu Primeiro Commit: a cozinha é a pasta de trabalho, a mesa da foto é a área de preparo, o álbum é o histórico. O git add leva um bolo da cozinha para a mesa.

Um detalhe importante: o Git não põe o arquivo na mesa, põe uma cópia do conteúdo dele, do jeito que está no instante do git add. É como fotografar o bolo para o rascunho do cardápio: se depois você muda a cobertura, o rascunho continua com a cobertura antiga, até você fotografar de novo. Você vai ver isso acontecer na seção Editei depois do add.

1. Um arquivo

A Ana tem o repositório receitas com um commit (o README.md). Ela cria a receita de bolo:

$ echo 'Bolo de cenoura' > bolo.txt
$ git status
No ramo main
Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	bolo.txt

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)
$ git add bolo.txt
$ git status
No ramo main
Mudanças a serem submetidas:                        « agora está na área de preparo
  (use "git restore --staged <file>..." to unstage)
	new file:   bolo.txt
git
O programa Git.
add
O subcomando: "adicionar à área de preparo".
bolo.txt
O caminho do arquivo, a partir da pasta onde você está. Se o arquivo estivesse numa subpasta, seria doces/bolo.txt.

Repare: o git add não escreveu nada. No terminal, silêncio é sucesso. O git status confirma que o arquivo passou de Arquivos não monitorados para Mudanças a serem submetidas, com a etiqueta novo arquivo.

Ver o que foi feito: -v

Se você prefere uma confirmação, o -v (de verbose, "falante") faz o git add dizer cada arquivo que preparou. Para ver, a Ana tirou o bolo.txt da área de preparo (com o git restore --staged, que a dica do git status acabou de mostrar) e preparou de novo:

$ git restore --staged bolo.txt
$ git add -v bolo.txt
add 'bolo.txt'

add 'bolo.txt': "adicionado o bolo.txt". A palavra add não é traduzida.

2. Vários arquivos de uma vez

Basta listar, separados por espaço:

$ echo 'Pudim de leite' > pudim.txt
$ echo 'Brigadeiro' > brigadeiro.txt
$ git add pudim.txt brigadeiro.txt
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	new file:   bolo.txt               « já estava preparado
	new file:   brigadeiro.txt
	new file:   pudim.txt

A área de preparo vai acumulando: o bolo.txt, preparado antes, continua lá. O git status lista os arquivos em ordem alfabética, não na ordem em que você os preparou. A Ana commita os três (git commit -m "Adiciona as receitas").

Também dá para usar um curinga do terminal: git add *.txt prepara todos os arquivos terminados em .txt da pasta atual. Quem troca o *.txt pela lista de nomes é o terminal, antes de o Git rodar (veja os curingas no Guia Bash).

3. Uma pasta inteira

Se você der o nome de uma pasta, o Git prepara tudo o que mudou dentro dela (e das pastas dentro dela). A Ana cria uma pasta para os doces:

$ mkdir doces
$ echo 'Cocada' > doces/cocada.txt
$ echo 'Quindim' > doces/quindim.txt
$ git status
No ramo main
Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	doces/                                « a pasta inteira é nova

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)
$ git add doces/
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	new file:   doces/cocada.txt              « cada arquivo, com o caminho
	new file:   doces/quindim.txt

Antes do add, o git status resumia a pasta nova como doces/; depois, mostra cada arquivo preparado. A barra no fim de doces/ é opcional no comando (git add doces dá no mesmo). A Ana commita (git commit -m "Adiciona a pasta de doces").

4. Tudo: git add . e git add -A

O ponto (.) quer dizer "a pasta onde estou". Então git add . prepara tudo o que mudou na pasta atual e nas de dentro: arquivos novos, modificados e apagados. A Ana muda o bolo, cria uma receita nova dentro de doces/ e apaga o brigadeiro:

$ echo 'Com cobertura' >> bolo.txt
$ echo 'Mousse' > doces/mousse.txt
$ rm brigadeiro.txt
$ git status
No ramo main
Changes not staged for commit:
  (utilize "git add/rm <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   bolo.txt
	deleted:    brigadeiro.txt

Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	doces/mousse.txt

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
$ git add .
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt               « modificado
	deleted:    brigadeiro.txt         « apagado
	new file:   doces/mousse.txt       « novo, numa subpasta

Um comando só preparou as três coisas. O git add -A (de all, "todos"; também se escreve --all) faz o mesmo, mas no repositório inteiro, não importa em que subpasta você esteja. Na pasta principal do repositório, os dois dão o mesmo resultado. A diferença só aparece dentro de uma subpasta. A Ana desfaz a preparação (git restore --staged .) e entra em doces/ para comparar, usando o formato curto do git status (-s: ?? = novo,  M/ D = modificado/apagado não preparado, letra na 1ª coluna = preparado; veja git status):

$ git restore --staged .
$ git status -s
 M bolo.txt
 D brigadeiro.txt
?? doces/mousse.txt
$ cd doces
$ git add .
$ git status -s
 M ../bolo.txt              « fora da pasta doces: ficou de fora
 D ../brigadeiro.txt        « idem
A  mousse.txt               « dentro da pasta doces: preparado
$ git restore --staged mousse.txt
$ git add -A
$ git status -s
M  ../bolo.txt              « o -A pegou o repositório inteiro
D  ../brigadeiro.txt
A  mousse.txt

Dentro de doces/, o git add . só preparou o mousse.txt, porque o ponto quer dizer "esta pasta". O git add -A preparou tudo, inclusive o que estava na pasta de cima. (Repare que, numa subpasta, o git status mostra os caminhos a partir de onde você está: ../bolo.txt é "o bolo.txt da pasta de cima".)

Olhe antes de usar o ponto

git add . é prático, mas pega tudo, inclusive o que não devia entrar: um arquivo com senha, um rascunho, um arquivo gigante. Rode git status antes e, para arquivos que nunca devem entrar, use o .gitignore. Uma senha que entrou num commit dá muito trabalho para tirar (aula Commitei uma Senha!).

5. Só o que já era rastreado: git add -u

O -u (de update, "atualizar") prepara as mudanças e os apagamentos dos arquivos que o Git já conhece, e deixa de fora os arquivos novos. De volta à pasta principal, na mesma situação:

$ cd ..
$ git restore --staged .
$ git status -s
 M bolo.txt
 D brigadeiro.txt
?? doces/mousse.txt
$ git add -u
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt
	deleted:    brigadeiro.txt

Arquivos não monitorados:                « o novo ficou de fora
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	doces/mousse.txt

O -u é útil quando a pasta tem arquivos novos que você ainda não quer commitar, mas quer guardar todas as mudanças dos que já existiam. (O git commit -a, da aula git commit, faz um git add -u e o commit de uma vez só.)

6. Arquivos apagados também se "adicionam"

Parece estranho, mas apagar um arquivo também é uma mudança, e mudanças entram no commit pelo git add. Num outro repositório, a Ana apaga o pudim.txt (que estava no último commit) com o rm do terminal:

$ rm pudim.txt
$ git status -s
 D pudim.txt            « apagado, não preparado
$ git add pudim.txt
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	deleted:    pudim.txt

O arquivo não existe mais, e mesmo assim o git add pudim.txt funcionou: o que ele preparou foi a falta do arquivo. No próximo commit, o pudim.txt sai do projeto (ele continua guardado nos commits antigos). Existe um atalho que apaga e prepara de uma vez só, o git rm (aula Apagando Arquivos).

7. Ver antes de fazer: --dry-run

O -n (ou --dry-run, "ensaio") mostra o que o git add faria, sem fazer nada. De volta à situação da seção 4 (bolo modificado, brigadeiro apagado, mousse novo):

$ git add -n .
add 'bolo.txt'
remover 'brigadeiro.txt'           « o apagamento aparece como "remover"
add 'doces/mousse.txt'
$ git status -s
 M bolo.txt                        « nada mudou: foi só um ensaio
 D brigadeiro.txt
?? doces/mousse.txt
$ git add -v .
add 'bolo.txt'
remover 'brigadeiro.txt'
add 'doces/mousse.txt'

O -n é bom antes de um git add . numa pasta que você não conhece bem: ele mostra a lista, e você decide. O -v mostra a mesma lista, mas fazendo.

Editei depois do add

A Ana preparou o bolo.txt e, antes de commitar, acrescentou mais um ingrediente:

$ echo '4 ovos' >> bolo.txt
$ git add bolo.txt
$ echo '1 colher de fermento' >> bolo.txt
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt                « a versão com os ovos

Changes not staged for commit:
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   bolo.txt                « o fermento, escrito depois do add

$ git status -s
MM bolo.txt
$ git add bolo.txt
$ git status -s
M  bolo.txt                             « agora a versão com o fermento está preparada

O bolo.txt apareceu nos dois blocos (e com MM no formato curto): a área de preparo tinha a cópia do momento do primeiro git add, com os ovos; o fermento, escrito depois, estava só na pasta. Se a Ana commitasse naquele momento, o fermento ficaria de fora. Um segundo git add bolo.txt atualizou a cópia. Regra prática: rode git status logo antes do git commit.

Missão: o bolo.txt foi preparado e editado de novo (rode git status para ver ele em dois blocos). Prepare a versão nova e faça o commit: ele tem de levar o bolo com os ovos, e a pasta tem de ficar limpa.

Formas diferentes

git add .simsimsima pasta atual e as de dentro

Qual usar? Comece nomeando os arquivos (git add bolo.txt): você vê exatamente o que entra, e os commits saem pequenos e com um assunto só. Use git add . quando o git status mostrar que tudo o que mudou é do mesmo assunto. Para escolher só algumas linhas de um arquivo, existe o git add -p, que aparece em A Área de Preparo.

Missão: rode git status: o bolo.txt foi modificado, o README.md foi apagado e o pudim.txt é novo. Com um só git add, prepare a modificação e o apagamento, mas deixe o pudim.txt de fora.

Quando dá errado

"pathspec … did not match any files" 
$ git add pudin.txt
fatal: pathspec 'pudin.txt' não encontrou nenhum arquivo
$ git add Bolo.txt
fatal: pathspec 'Bolo.txt' não encontrou nenhum arquivo

"O caminho (pathspec) não corresponde a nenhum arquivo". No primeiro, um erro de digitação (pudin em vez de pudim); no segundo, a letra maiúscula: no Linux, Bolo.txt e bolo.txt são nomes diferentes. Nada foi preparado. Como resolver: confira o nome com ls ou git status, e use a tecla Tab para completar nomes.

O arquivo está no .gitignore 
$ echo 'senha123' > senha.txt
$ echo 'senha.txt' > .gitignore
$ git add senha.txt
Os caminhos a seguir são ignorados por um dos seus arquivos .gitignore:
senha.txt
hint: Use -f if you really want to add them.
hint: Disable this message with "git config set advice.addIgnoredFile false"

"Os caminhos a seguir são ignorados por um dos seus arquivos .gitignore". A Ana tinha mandado o Git ignorar o senha.txt (aula Ignorando Arquivos), e ele obedeceu: não preparou. As linhas hint: ("dica") dizem: "use -f se você quer mesmo adicioná-los" e "desligue esta mensagem com git config set advice.addIgnoredFile false". Como resolver: normalmente, não resolva: é para o arquivo ficar de fora mesmo (senha não vai para o Git). Se ele foi ignorado por engano, corrija o .gitignore; o git add -f (de force, "forçar") passa por cima, mas use só se tiver certeza.

Caminho fora do repositório 
$ git add ../notas.txt
fatal: ../notas.txt: '../notas.txt' is outside repository at '/home/ana/receitas'

"O ../notas.txt está fora do repositório que fica em /home/ana/receitas". Um repositório só cuida dos arquivos que estão dentro da pasta dele (e das subpastas). O notas.txt está na pasta de cima. Como resolver: se o arquivo é do projeto, copie ou mova para dentro da pasta do repositório e prepare de lá (cp ../notas.txt ., depois git add notas.txt).

"not a git repository" 
$ cd ~
$ git add receitas/bolo.txt
fatal: not a git repository (or any of the parent directories): .git

"Não é um repositório Git (nem nenhuma das pastas acima)". O Git decide em qual repositório trabalhar pela pasta onde você está, não pelo caminho do arquivo. Na pasta pessoal não existe repositório. Como resolver: cd receitas e então git add bolo.txt.

A pasta vazia não entra 
$ mkdir fotos
$ git add fotos
$ git status -s
A  .gitignore
M  bolo.txt

Nenhum erro, mas também nada de fotos na área de preparo (o .gitignore e o bolo.txt foram preparados antes). O Git guarda arquivos; uma pasta só existe para ele se tiver algum arquivo dentro. Como resolver: ponha um arquivo nela. Quando a pasta precisa existir vazia no projeto, o costume é criar dentro dela um arquivo vazio chamado .gitkeep (touch fotos/.gitkeep) e preparar esse arquivo. O nome é só uma convenção: o Git não trata ele de um jeito especial.

Preparei um arquivo que não devia 
$ echo 'ligar pro Bruno' > rascunho.txt
$ git add .
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	new file:   bolo.txt
	deleted:    pudim.txt
	new file:   rascunho.txt            « este não era para entrar

$ git restore --staged rascunho.txt
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	new file:   bolo.txt
	deleted:    pudim.txt

Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	rascunho.txt                        « voltou a ser não rastreado

O git add . pegou o rascunho junto. Antes do commit, isso se desfaz com a própria dica do git status: git restore --staged rascunho.txt. O arquivo continua na pasta, intacto; só saiu da área de preparo. Para o rascunho nunca mais aparecer, ponha-o no .gitignore. (Antes do primeiro commit do repositório, o comando é git rm --cached arquivo, como a dica daquele momento mostra.)

Missão final: dois commits, dois assuntos

Missão: há duas receitas novas (bolo.txt e pudim.txt) e uma mudança no README.md. Faça dois commits: um só com as receitas e outro só com o README (com uma mensagem que fale do README). No fim, a pasta deve estar limpa.

Resumo

  • git add põe uma cópia do arquivo, como ele está agora, na área de preparo. Editou depois? Rode git add de novo.
  • Aceita um arquivo, vários, curingas e pastas. git add . pega tudo da pasta atual; git add -A, tudo do repositório; git add -u, só o que já era rastreado.
  • Apagar um arquivo também é uma mudança: ela entra no commit com git add (ou git rm).
  • Sem -v, o git add não mostra nada quando dá certo: confira com git status.
  • Para desfazer um git add: git restore --staged arquivo.

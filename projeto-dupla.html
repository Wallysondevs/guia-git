Git Projeto: Trabalhando em Dupla

Até aqui, a Ana trabalhou sozinha. Agora o amigo dela, o Bruno, vai ajudar no site de receitas: ele também quer acrescentar receitas e mexer nas páginas. Cada um trabalha no seu computador, e os dois se encontram num repositório no GitHub. Neste projeto você acompanha a dupla do primeiro push até o primeiro conflito entre duas pessoas: o push recusado, o git pull que pede uma configuração, e a mesma linha mudada pelos dois. Tudo com as saídas reais do Git.

Você vai aprender (na prática)
  • Enviar um repositório para o GitHub pela primeira vez (git remote add e git push -u).
  • Como o colega pega uma cópia (git clone) e envia o trabalho dele.
  • Por que o seu git push é recusado quando o colega enviou antes, e como resolver com git pull.
  • O aviso "divergent branches" do git pull e a configuração pull.rebase.
  • Resolver um conflito entre duas pessoas e manter os dois computadores em dia.

Este projeto põe em prática Repositórios Remotos, git clone, git push, git pull, Push Rejeitado e Resolvendo Conflitos. As saídas saíram do Git 2.53 do Ubuntu, com o sistema em português, no laboratório do guia: duas máquinas (a da Ana e a do Bruno) e um GitHub de treino que responde como o de verdade. O que acontece no site do GitHub (telas e botões) está descrito de forma ilustrativa, com base na documentação oficial.

Duas pessoas, dois terminais. Os terminais da Ana aparecem com o prompt ana@notebook; os do Bruno, com bruno@notebook (cada um no seu computador). Preste atenção em quem está digitando.

A ideia: o caderno de receitas da família

Imagine um caderno de receitas que fica na casa da avó. A Ana e o Bruno moram longe e cada um tem uma cópia dele em casa. Quando a Ana inventa uma receita, ela escreve na cópia dela e, no domingo, leva a novidade para o caderno da avó. O Bruno faz o mesmo.

  • O caderno da avó é o repositório no GitHub (o "remoto", chamado origin).
  • As cópias em casa são os repositórios locais de cada um.
  • Levar as novidades para a avó é o git push ("empurrar"); trazer as novidades da avó para casa é o git pull ("puxar").

E a regra da avó: ninguém escreve por cima do que o outro já levou. Se o Bruno levou uma receita no sábado, a Ana precisa primeiro copiar essa receita para a cópia dela, juntar com o que ela fez, e só então levar a dela. Isso é o "push rejeitado" que você vai ver na etapa 3.

Etapa 0: o repositório no GitHub (ilustrativo)

No site do GitHub, entrando com a conta ana-souza, a Ana criou um repositório vazio chamado receitas, sem README (ela já tem um no computador; veja Criando um Repositório no GitHub). O endereço dele é:

https://github.com/ana-souza/receitas.git

Depois, nas configurações do repositório, na parte de colaboradores, ela convidou o usuário do Bruno (bruno-lima), que aceitou o convite. A partir daí, o GitHub deixa os dois enviarem para o repositório. (Os nomes exatos das telas mudam com o tempo; a documentação oficial, em docs.github.com/pt, mostra o caminho atual: procure por "Convidar colaboradores para um repositório pessoal".)

Senha ou chave? Para o git push funcionar no GitHub de verdade, o seu computador precisa provar quem é você: com uma chave SSH ou com um token de acesso (a senha da conta não serve no terminal). Neste projeto, isso já está configurado nos dois computadores, então o Git não pergunta nada.

Etapa 1: a Ana envia o site

O repositório local da Ana tem um commit, com o README, a página inicial e a receita de bolo. Ela liga o repositório local ao do GitHub e envia:

git remote add
"Acrescentar um remoto": dar um apelido a um endereço (git remote).
origin
O apelido. origin ("origem") é o nome que todo mundo usa para o remoto principal.
https://github.com/…
O endereço do repositório no GitHub.
git push -u origin main
Enviar o branch main para o origin. O -u (de upstream) grava a ligação "o meu main acompanha o main do origin": dos próximos em diante, basta git push e git pull, sem nomes.
$ git log --oneline

$ git remote add origin https://github.com/ana-souza/receitas.git
$ git remote -v

origin  https://github.com/ana-souza/receitas.git (push)
$ git push -u origin main

Missão 1: o repositório local da Ana já tem um commit. No treino, o "GitHub" é uma pasta do próprio computador: ~/github/ana-souza/receitas.git (o Git aceita uma pasta como endereço de remoto, do mesmo jeito que aceita um https). Ligue o repositório a esse endereço com o apelido origin e envie o main com -u. Depois, confira com git status.

Etapa 3: o push da Ana é recusado

Enquanto isso, sem saber do pudim, a Ana mudou a página inicial e fez um commit. Na hora de enviar:

$ echo '<p>Fotos novas toda semana</p>' >> index.html
$ git add index.html
$ git commit -m 'Avisa das fotos novas na página inicial'

hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.

Linha por linha:

  • ! [rejected] main -> main (fetch first): "recusado (busque primeiro)". O GitHub tem um commit (o do Bruno) que a Ana não tem.
  • error: failed to push some refs: "falhou ao enviar algumas referências". Nada foi enviado e nada se perdeu.
  • As dicas (hint) explicam: "o remoto contém trabalho que você não tem localmente; isso costuma acontecer quando outro repositório enviou para a mesma referência; para integrar as mudanças do remoto, use git pull antes de enviar de novo".

Por que o GitHub recusa? Se aceitasse, o main do GitHub passaria a ser o da Ana, e o commit do pudim do Bruno sumiria do histórico. O Git protege o trabalho do colega.

Não "resolva" com --force. Um git push --force faria exatamente o que o GitHub está evitando: apagaria o commit do Bruno. O caminho certo é trazer o trabalho dele primeiro (veja push --force-with-lease para os raros casos em que forçar faz sentido).

  • A primeira parte funcionou: o Git baixou o commit do Bruno (502c5a9..b1b6024 main -> origin/main).
  • Mas parou com fatal: Need to specify how to reconcile divergent branches.: "é preciso dizer como conciliar branches que divergiram". A rotina da dupla

  1. Começou a trabalhar? git pull.
  2. Trabalhe em commits pequenos, com mensagens claras.
  3. Vai enviar? git pull de novo (alguém pode ter enviado enquanto isso), resolva o que precisar, e então git push.
  4. Push recusado? Não force: git pull, resolva, git push.
  5. Conflito? Converse com o colega antes de decidir a versão da linha.

Formas diferentes de fazer

JeitoComoResultado
Pull com merge (o deste projeto)git config --global pull.rebase false e git pullCria um commit de merge quando os dois lados andaram. O histórico mostra os galhos.
Pull com rebasegit pull --rebase (ou pull.rebase true)Reaplica os seus commits depois dos do colega: histórico em linha reta, sem commit de merge. Veja Rebase ou Merge?.
Só avanço rápidogit pull --ff-only (ou pull.ff only)Recusa o pull se houver algo a juntar: você decide na hora o que fazer.

Cada um no seu branchBranches + pull requests no GitHubO jeito mais comum em equipes: ninguém envia direto no main (veja O GitHub Flow).

Quando dá errado

"! [rejected] … (fetch first)" no git push

É o da etapa 3. O que aconteceu: alguém enviou commits que você não tem. Como confirmar: git fetch e depois git status (vai dizer que os branches divergiram). Como resolver: git pull, resolva conflitos se houver, e git push. Mais detalhes em Push Rejeitado: o que Fazer.

"fatal: Need to specify how to reconcile divergent branches."

É o da etapa 3, no git pull. O que aconteceu: os dois lados andaram e o Git não sabe se você prefere merge ou rebase. O download já foi feito; só a junção não. Como resolver: escolha uma vez, para sempre: git config --global pull.rebase false (merge). Ou escolha só naquele pull: git pull --no-rebase (merge) ou git pull --rebase.

"error: remote origin already exists." 
$ git remote add origin https://github.com/ana-souza/receitas.git
error: remote origin already exists.

O que aconteceu: o repositório já tem um remoto chamado origin ("o remoto origin já existe"); talvez você já tenha rodado esse comando, ou o repositório veio de um git clone.

Como confirmar: git remote -v mostra para onde o origin aponta.

Como resolver: se o endereço está certo, não precisa fazer nada. Se está errado, troque com git remote set-url origin NOVO-ENDEREÇO (veja git remote).

"fatal: The current branch … has no upstream branch." 
$ git switch -q -c teste
$ git push
fatal: The current branch teste has no upstream branch.
To push the current branch and set the remote as upstream, use

    git push --set-upstream origin teste

To have this happen automatically for branches without a tracking
upstream, see 'push.autoSetupRemote' in 'git help config'.

O que aconteceu: o branch teste é novo e ainda não tem ligação com nenhum branch do GitHub ("não tem branch de upstream"). Um git push sem nomes não sabe para onde ir.

Como resolver: faça o primeiro envio com o nome, como a própria mensagem sugere: git push --set-upstream origin teste (ou a forma curta, git push -u origin teste). Veja Branch de Rastreamento (upstream).

"remote: Repository not found." 
$ git push https://github.com/ana-souza/receitass.git main
remote: Repository not found.
fatal: repository 'https://github.com/ana-souza/receitass.git/' not found

O que aconteceu: o endereço está errado (aqui, receitass com dois "s"), o repositório não existe, ou (no GitHub de verdade) a sua conta não tem acesso a ele: um repositório privado aparece como "não encontrado" para quem não tem permissão.

Como resolver: confira o endereço com git remote -v e na página do repositório no GitHub. Se o Bruno recebe esse erro no repositório da Ana, confira se o convite de colaborador foi aceito.

Exercícios

1. Primeiro envio

Complete para enviar o main pela primeira vez e gravar a ligação com o origin:

git push origin main

2. Escolher o merge no pull

Complete para que o git pull junte com merge em todos os seus repositórios:

git config --global false

3. Pegar a cópia

Complete o comando que o Bruno usa para baixar o repositório da Ana pela primeira vez:

git https://github.com/ana-souza/receitas.git

4. O git push da Ana mostrou ! [rejected] main -> main (fetch first). O que ela deve fazer?

5. O git pull do Bruno mostrou Fast-forward. O que isso quer dizer?

6. Por que o GitHub recusa o push quando o colega enviou antes?

Resumo

  • Cada pessoa tem o repositório completo no seu computador; o GitHub (origin) é o ponto de encontro.
  • Primeiro envio: git remote add origin URL + git push -u origin main. Quem chega depois: git clone URL.
  • Push recusado com (fetch first) = o colega enviou antes. Nunca force: git pull, e depois git push.
  • Se os dois lados andaram, o git pull do Git atual pede que você escolha como juntar: git config --global pull.rebase false (merge) é a escolha deste guia para começar.
  • Conflito entre duas pessoas se resolve igual ao de dois branches: arquivo sem marcadores, git add, git commit, e então git push. O colega recebe a resolução pronta no próximo git pull.
  • Hábito de ouro: git pull antes de começar e antes de enviar.

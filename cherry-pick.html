Git cherry-pick

Às vezes um branch tem um commit de que você precisa agora, no meio de vários outros que ainda não estão prontos. Juntar o branch inteiro com git merge traria tudo junto. O git cherry-pick resolve isso: ele copia um commit escolhido de qualquer lugar do histórico e o aplica no branch em que você está. O nome vem do inglês cherry-pick, "colher a cereja": escolher a dedo só a fruta que interessa.

Você vai aprender
  • O que o git cherry-pick faz e por que o commit copiado ganha um hash novo.
  • Como achar o commit certo com o git log e copiá-lo para o main.
  • Como copiar vários commits de uma vez, anotar de onde veio a cópia (-x) e aplicar sem commitar (-n).
  • O que fazer quando a cópia dá conflito: --continue, --abort e --skip.
  • Quando o cherry-pick é a ferramenta certa, e quando um merge é melhor.

Todas as sessões desta aula rodaram no Git real do Ubuntu, na máquina da Ana (usuária ana, computador notebook), com as mensagens em português. Se o seu sistema estiver em inglês, as mensagens saem em inglês; a seção Quando dá errado mostra a versão em inglês das mais importantes.

A ideia: copiar uma receita de um caderno para o outro

A Ana tem dois cadernos de receitas. O caderno passado a limpo é o que ela mostra para a família (o branch main). O caderno de rascunho é onde ela testa um visual novo para o site (o branch novo-layout). Enquanto mexia no rascunho, ela percebeu que a receita de bolo estava com um erro de acento ("açucar") e corrigiu lá no rascunho.

O visual novo ainda não está pronto, mas a correção do acento está, e ela quer essa correção no caderno passado a limpo hoje. O que ela faz no papel?

  1. Abre o rascunho na página da correção.
  2. Copia só aquela correção para o caderno passado a limpo, com a mesma anotação ("Corrige o acento de açúcar").
  3. O rascunho continua igual: a página original não sai de lá.

Três detalhes desse jeito de copiar valem para todo cherry-pick:

  • O que se copia é a mudança (o "troque açucar por açúcar"), não o caderno inteiro.
  • A cópia é uma página nova no caderno de destino. No Git, isso quer dizer um commit novo, com hash novo (veja O Hash do Commit), mesmo com a mesma mensagem e o mesmo conteúdo.
  • O original fica onde estava. Nada some do branch de origem.

1. A situação da Ana

O repositório receitas começou com dois commits no main. A partir deles, a Ana criou o branch novo-layout e fez três commits nele. Depois voltou ao main e acrescentou a receita de pudim. Ela está no main; o git log sem nada mostra o histórico do branch atual, e com o nome de um branch mostra o histórico daquele branch:

$ git log --oneline

e0ec859 Adiciona a receita de bolo
700bbd5 Cria o README
$ git log --oneline novo-layout
ac783ac (novo-layout) Deixa os títulos roxos
d07edbe Corrige o acento de açúcar           « este é o commit que a Ana quer
7664ece Começa o novo layout
e0ec859 Adiciona a receita de bolo
700bbd5 Cria o README
$ git log --oneline --graph --all

Os nomes entre parênteses mostram onde cada branch aponta: HEAD -> main quer dizer "você está no main, e ele está aqui"; novo-layout marca a ponta do outro branch. O --graph --all desenha todos os branches juntos (veja Vendo os Galhos). Desenhando com letras, que são só apelidos para os commits:

          C---D---E   novo-layout
         /
    A---B---X         main
  • C = "Começa o novo layout" (cria o estilo.css) — não está pronto.
  • D = "Corrige o acento de açúcar" (muda o bolo.txt) — está pronto, e é este que a Ana quer no main.
  • E = "Deixa os títulos roxos" — não está pronto.
  • X = "Adiciona a receita de pudim", feito no main depois que os caminhos se separaram.

Um git merge novo-layout traria os três. A Ana quer só o D.

2. O primeiro cherry-pick

O cherry-pick sempre traz para o branch atual. Então o primeiro passo é ir para o branch que vai receber a cópia, o main (veja git switch), e só depois chamar o cherry-pick com o hash do commit escolhido:

$ git switch main
Already on 'main'
$ git cherry-pick d07edbe
[main 92c2d52] Corrige o acento de açúcar
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+), 1 deletion(-)
git
O programa Git.
cherry-pick
O subcomando: "copie este commit para cá".
d07edbe
O commit a copiar, pelo hash abreviado que o git log --oneline mostrou. Pode ser qualquer forma de apontar um commit: o hash inteiro, um nome de branch (que quer dizer "a ponta do branch") ou novo-layout~1 ("um antes da ponta do novo-layout"). Veja Formas diferentes.

Linha por linha, o que o Git respondeu:

Already on 'main'
"Já está no main": a Ana já estava lá, então o switch não fez nada. Não custa conferir antes. (Esta e outras mensagens do Git saem em inglês mesmo com o sistema em português: a tradução do Git para o português do Brasil não cobre todas as frases.)
[main 92c2d52]
O commit novo foi criado no branch main e ganhou o hash 92c2d52. Repare: não é o d07edbe que a Ana pediu.
Corrige o acento de açúcar
A mensagem do commit, copiada do original.
Date: Thu Oct 15 10:30:00 2026 -0300
A data do autor, também copiada do original (quinta-feira, 15 de outubro de 2026, 10:30, fuso −03:00). O Git mostra essa linha porque, num commit copiado, a data de quando a mudança foi escrita pode ser bem anterior à de hoje.
1 file changed, 1 insertion(+), 1 deletion(-)
"1 arquivo mudou, 1 linha entrou, 1 linha saiu": a linha do açúcar trocada.

Antes e depois

$ git status

nothing to commit, working tree clean
$ git log --oneline --graph --all
* 92c2d52 (HEAD -> main) Corrige o acento de açúcar   « a cópia, no main
* 74a4b0b Adiciona a receita de pudim
| * ac783ac (novo-layout) Deixa os títulos roxos
| * d07edbe Corrige o acento de açúcar        « o original continua aqui
| * 7664ece Começa o novo layout

$ cat bolo.txt

- 3 cenouras
- 4 ovos

O git status diz "nada a commitar, pasta de trabalho limpa" (nothing to commit, working tree clean): o cherry-pick já fez o commit sozinho, não sobrou nada para você fazer.

O desenho, agora:

          C---D---E   novo-layout
         /
    A---B---X---D'    main

O D' ("D linha") é a cópia: mesma mudança, mesma mensagem, commit diferente. O novo-layout não mudou nada, e o estilo.css não veio junto, porque ele nasceu no commit C, que a Ana não escolheu.

Copia a mudança, não o arquivo

O cherry-pick pega a diferença que o commit escolhido fez em relação ao commit anterior a ele (o que o git show mostra) e repete essa diferença no branch atual. Se o bolo.txt do main tivesse outras linhas diferentes das do novo-layout, elas continuariam lá: só a linha do açúcar muda.

Missão: você está no main da Ana. Olhe o histórico do novo-layout com git log --oneline novo-layout, ache o commit "Corrige o acento de açúcar" e copie só ele para o main. No fim, confira com cat bolo.txt e git log --oneline.

3. A cópia tem hash novo (e a opção -x)

Compare os dois commits lado a lado. O formato fuller ("mais completo") do git log mostra, além do autor, quem fez o commit e quando:

$ git log -1 --format=fuller d07edbe
commit d07edbe144d7abd72bc3e14c1c416d2b8f7fa3cc
Author:     Ana Souza <ana@exemplo.com>
AuthorDate: Thu Oct 15 10:30:00 2026 -0300
Commit:     Ana Souza <ana@exemplo.com>
CommitDate: Thu Oct 15 10:30:00 2026 -0300

    Corrige o acento de açúcar
$ git log -1 --format=fuller HEAD
commit 92c2d525f4e6f947e211abbc95655605a94f0624 (HEAD -> main)
Author:     Ana Souza <ana@exemplo.com>
AuthorDate: Thu Oct 15 10:30:00 2026 -0300
Commit:     Ana Souza <ana@exemplo.com>
CommitDate: Thu Oct 15 10:30:00 2026 -0300

    Corrige o acento de açúcar
Author / AuthorDate
Quem escreveu a mudança, e quando. O cherry-pick copia os dois do original: se a Ana copiasse um commit do Bruno, o autor continuaria sendo o Bruno.
Commit / CommitDate
Quem gravou este commit, e quando. Num cherry-pick, é quem rodou o comando, na hora em que rodou. No lab do guia o relógio está parado em 15/10/2026 10:30, por isso as duas datas coincidem; no seu computador, a CommitDate da cópia seria a hora do cherry-pick.

Autor, mensagem e mudança iguais; hash diferente. Por quê? O hash é calculado a partir de tudo o que o commit guarda, e isso inclui quem é o commit pai. O pai do original d07edbe é o 7664ece ("Começa o novo layout"); o pai da cópia 92c2d52 é o 74a4b0b ("Adiciona a receita de pudim"). Pai diferente, hash diferente, mesmo com tudo o mais igual. (No seu computador ainda tem a data diferente, mais um motivo.)

Daqui a seis meses, como a Ana vai saber que o commit do main é uma cópia de outro? Com a opção -x, o Git acrescenta uma linha na mensagem dizendo de onde a cópia veio:

Para mostrar, a Ana desfez a cópia (com git reset --hard HEAD~1, que joga fora o último commit; veja git reset) e copiou de novo, agora com -x:

$ git reset --hard HEAD~1
HEAD is now at 74a4b0b Adiciona a receita de pudim
$ git cherry-pick -x d07edbe
[main 105eea3] Corrige o acento de açúcar
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git log -1
commit 105eea3748859636df346d08d8485b664affd935 (HEAD -> main)
Author: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

    Corrige o acento de açúcar

    (cherry picked from commit d07edbe144d7abd72bc3e14c1c416d2b8f7fa3cc)

Repare que o hash mudou de novo (105eea3, e não 92c2d52): a mensagem agora tem uma linha a mais, e a mensagem também entra na conta do hash. A linha (cherry picked from commit …) ("colhido do commit …") traz o hash inteiro do original. Use -x quando o commit original está num branch que outras pessoas também veem (por exemplo, quando você copia uma correção do main para o branch de uma versão antiga). Se o original estava num branch só seu, que vai ser apagado, a linha aponta para um commit que ninguém mais vai achar; aí não vale a pena.

4. Vários commits de uma vez

O cherry-pick aceita mais de um commit. Eles são copiados na ordem em que você escreve, um commit novo para cada. A Ana voltou o main para o pudim de novo e testou copiar o C e o E, pulando o D:

$ git reset --hard HEAD~1
HEAD is now at 74a4b0b Adiciona a receita de pudim
$ git cherry-pick 7664ece ac783ac
[main 121406f] Começa o novo layout
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+)
 create mode 100644 estilo.css
[main d95fb33] Deixa os títulos roxos
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+)
$ git log --oneline
d95fb33 (HEAD -> main) Deixa os títulos roxos
121406f Começa o novo layout
74a4b0b Adiciona a receita de pudim
e0ec859 Adiciona a receita de bolo
700bbd5 Cria o README

Um bloco [main …] para cada commit copiado. O create mode 100644 estilo.css avisa que o commit criou um arquivo novo (o 100644 é o tipo: arquivo comum, sem permissão de execução).

Para uma sequência de commits seguidos, existe a escrita com dois pontos, A..B. Atenção a um detalhe que confunde todo mundo: A..B quer dizer "os commits depois de A até B", ou seja, o A fica de fora. Para incluir o A, escreva A^..B (o ^ quer dizer "o pai de A"):

$ git reset --hard HEAD~2
HEAD is now at 74a4b0b Adiciona a receita de pudim
$ git cherry-pick 7664ece^..ac783ac
[main 121406f] Começa o novo layout
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+)
 create mode 100644 estilo.css
[main a751422] Corrige o acento de açúcar
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+), 1 deletion(-)
[main f45de4c] Deixa os títulos roxos
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+)
$ git log --oneline
f45de4c (HEAD -> main) Deixa os títulos roxos
a751422 Corrige o acento de açúcar
121406f Começa o novo layout
74a4b0b Adiciona a receita de pudim
e0ec859 Adiciona a receita de bolo
700bbd5 Cria o README

Os três vieram, em ordem. (Se a Ana tivesse escrito 7664ece..ac783ac, sem o ^, o "Começa o novo layout" teria ficado de fora.)

Você escreveO Git copia
git cherry-pick Csó o C
git cherry-pick C Eo C e depois o E (pula o D)
git cherry-pick C..Eo D e o E (o C fica de fora)
git cherry-pick C^..Eo C, o D e o E

5. Aplicar sem commitar: -n

Com -n (ou --no-commit, "sem commit"), o Git aplica a mudança na pasta e na área de preparo, mas não cria o commit. Serve para revisar antes, para ajustar algo, ou para juntar vários commits copiados num commit só:

$ git reset --hard HEAD~3
HEAD is now at 74a4b0b Adiciona a receita de pudim
$ git cherry-pick -n d07edbe
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt

$ git diff --staged
diff --git a/bolo.txt b/bolo.txt
index f32f198..ea7e3b4 100644
--- a/bolo.txt
+++ b/bolo.txt
@@ -1,4 +1,4 @@
 Bolo de cenoura
 - 3 cenouras
 - 4 ovos
-- 2 xícaras de açucar
+- 2 xícaras de açúcar
$ git commit -m 'Corrige o acento de açúcar'
[main 92c2d52] Corrige o acento de açúcar
 1 file changed, 1 insertion(+), 1 deletion(-)

O cherry-pick -n não mostrou nada: não houve commit para anunciar. O git status mostra o bolo.txt em "Mudanças a serem submetidas" (a área de preparo), com a dica de como tirá-lo de lá. O git diff --staged confirma que a mudança é exatamente a do commit escolhido. Aí a Ana fez o commit com a mensagem que quis.

Daí em diante é o fluxo de sempre: mude o que quiser, git add, git commit. Parecido, o -e (--edit) cria o commit, mas antes abre o editor para você mudar a mensagem.

6. Quando a cópia dá conflito

O cherry-pick repete uma mudança num lugar diferente de onde ela nasceu. Se, no branch atual, as mesmas linhas foram mudadas de outro jeito, o Git não sabe qual das duas vale e para no meio, com um conflito (o mesmo tipo de conflito do merge: veja Conflitos de Merge).

No exemplo, a Ana voltou o main para o pudim e, antes de copiar a correção, mexeu no main na mesma linha do açúcar: escreveu "açucar refinado" (ainda sem o acento) e commitou. Aí pediu o cherry-pick:

$ git reset --hard HEAD~1
HEAD is now at 74a4b0b Adiciona a receita de pudim
$ sed -i 's/açucar/açucar refinado/' bolo.txt
$ git commit -q -am 'Especifica o açúcar refinado'
$ git cherry-pick d07edbe
Mesclagem automática de bolo.txt
CONFLITO (conteúdo): conflito de mesclagem em bolo.txt
error: não foi possível aplicar d07edbe... Corrige o acento de açúcar
hint: After resolving the conflicts, mark them with
hint: "git add/rm <pathspec>", then run
hint: "git cherry-pick --continue".
hint: You can instead skip this commit with "git cherry-pick --skip".
hint: To abort and get back to the state before "git cherry-pick",
hint: run "git cherry-pick --abort".
hint: Disable this message with "git config set advice.mergeConflict false"

(O sed -i só trocou o texto dentro do arquivo, como se a Ana tivesse editado no editor. O -q deixa o commit quieto, e o -a do -am prepara sozinho os arquivos já rastreados.) Linha por linha, o que o cherry-pick disse:

Mesclagem automática de bolo.txt
O Git tentou juntar sozinho a mudança do commit com o bolo.txt do main.
CONFLITO (conteúdo): conflito de mesclagem em bolo.txt
Não conseguiu: o conteúdo da mesma linha mudou dos dois lados.
error: não foi possível aplicar d07edbe... Corrige o acento de açúcar
Por isso o commit d07edbe ainda não foi copiado. O cherry-pick está parado no meio, esperando você.
hint: After resolving the conflicts…
As dicas (em inglês, porque não estão traduzidas): "depois de resolver os conflitos, marque-os com git add/rm <caminho> e rode git cherry-pick --continue"; "em vez disso, você pode pular este commit com git cherry-pick --skip"; "para desistir e voltar ao estado de antes do git cherry-pick, rode git cherry-pick --abort".
hint: Disable this message…
"Desligue esta mensagem com …": para quem já sabe tudo isso e não quer mais ver as dicas. Deixe ligado.

O git status lembra a situação a qualquer momento:

$ git status
No ramo main
You are currently cherry-picking commit d07edbe.
  (fix conflicts and run "git cherry-pick --continue")
  (use "git cherry-pick --skip" to skip this patch)
  (use "git cherry-pick --abort" to cancel the cherry-pick operation)

Caminhos não mesclados:
  (usar "git add <arquivo>..." para marcar resolução)
	ambos modificados:   bolo.txt

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")

"Você está no meio do cherry-pick do commit d07edbe" (You are currently cherry-picking commit), com as mesmas três saídas. Embaixo, em "Caminhos não mesclados", o arquivo com conflito: ambos modificados quer dizer que os dois lados (o main e o commit copiado) mexeram nele.

O arquivo tem as marcas de conflito, como num merge:

$ cat bolo.txt
Bolo de cenoura
- 3 cenouras
- 4 ovos
<<<<<<< HEAD
- 2 xícaras de açucar refinado                 « como está no main (HEAD)
=======
- 2 xícaras de açúcar                          « como ficou no commit copiado
>>>>>>> d07edbe (Corrige o acento de açúcar)

A Ana resolve como em Resolvendo Conflitos: edita o arquivo deixando a versão certa (com o acento e o "refinado"), sem as marcas, e marca como resolvido com git add. Depois, em vez de git commit, ela continua o cherry-pick:

$ printf 'Bolo de cenoura\n- 3 cenouras\n- 4 ovos\n- 2 xícaras de açúcar refinado\n' > bolo.txt
$ git add bolo.txt
$ git status
No ramo main
You are currently cherry-picking commit d07edbe.
  (all conflicts fixed: run "git cherry-pick --continue")
  (use "git cherry-pick --skip" to skip this patch)
  (use "git cherry-pick --abort" to cancel the cherry-pick operation)

Mudanças a serem submetidas:
	modified:   bolo.txt

$ git cherry-pick --continue --no-edit
[main b58ddf9] Corrige o acento de açúcar
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git log --oneline
b58ddf9 (HEAD -> main) Corrige o acento de açúcar
662fdfb Especifica o açúcar refinado
74a4b0b Adiciona a receita de pudim
e0ec859 Adiciona a receita de bolo
700bbd5 Cria o README
  • O printf escreveu o arquivo inteiro já resolvido (no seu dia a dia, você faria isso no editor de texto).
  • Depois do git add, o status mudou para "todos os conflitos resolvidos: rode git cherry-pick --continue" (all conflicts fixed).
  • O --no-edit usa a mensagem do commit original sem perguntar. Sem ele, o --continue abre o seu editor de texto com a mensagem já escrita: é só salvar e fechar (no nano, Ctrl+O, Enter, Ctrl+X).

As três saídas de um cherry-pick parado

ComandoO que fazQuando usar
git cherry-pick --continueCria o commit com o que você resolveu (e segue para o próximo, se você pediu vários)Você resolveu o conflito e deu git add
git cherry-pick --abortDesiste de tudo e volta o branch para como estava antes do cherry-pickVocê se arrependeu ou escolheu o commit errado
git cherry-pick --skipPula só o commit atual e segue para o próximo da listaVários commits: este não faz falta
git cherry-pick --quitSai do modo cherry-pick e deixa a pasta como estáRaro: você quer terminar na mão

7. Copiar um commit que já está lá

Se a mudança do commit escolhido já existe no branch atual (a Ana copiou duas vezes, ou já tinha feito a mesma correção na mão), sobra um commit sem mudança nenhuma, e o Git para para perguntar:

$ git reset --hard HEAD~1
HEAD is now at 74a4b0b Adiciona a receita de pudim
$ git cherry-pick d07edbe
[main 92c2d52] Corrige o acento de açúcar
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git cherry-pick d07edbe
The previous cherry-pick is now empty, possibly due to conflict resolution.
If you wish to commit it anyway, use:

    git commit --allow-empty

Otherwise, please use 'git cherry-pick --skip'
No ramo main
You are currently cherry-picking commit d07edbe.
  (all conflicts fixed: run "git cherry-pick --continue")
  (use "git cherry-pick --skip" to skip this patch)
  (use "git cherry-pick --abort" to cancel the cherry-pick operation)

nothing to commit, working tree clean
$ git cherry-pick --skip
$ git log --oneline
92c2d52 (HEAD -> main) Corrige o acento de açúcar
74a4b0b Adiciona a receita de pudim
e0ec859 Adiciona a receita de bolo
700bbd5 Cria o README

Em português: "o cherry-pick anterior agora está vazio (empty), possivelmente por causa da resolução de conflitos. Se mesmo assim você quiser commitá-lo, use git commit --allow-empty. Senão, use git cherry-pick --skip". Embaixo, o Git já mostra o status: o cherry-pick está parado, sem nada a commitar. Gravar um commit vazio quase nunca é o que você quer; a Ana pulou com --skip, e o histórico ficou com uma cópia só.

Formas diferentes de fazer a mesma coisa

O commit pode ser escolhido de vários jeitos; todos apontam para o mesmo D:

EscritaQuer dizer
git cherry-pick d07edbepelo hash abreviado (o jeito mais comum)

E há outros caminhos para levar trabalho de um branch para outro. Qual usar:

SituaçãoUse
Você quer tudo o que o branch temgit merge (ou git rebase): o cherry-pick copiaria um por um e deixaria commits duplicados
Um ou poucos commits prontos num branch que ainda não está prontogit cherry-pick
Uma correção do main que também precisa ir para o branch de uma versão antigagit cherry-pick -x (o caso clássico)
Você quer o arquivo inteiro como está no outro branch, não a mudança de um commitgit restore --source=novo-layout bolo.txt (veja git restore)
Commitou no branch errado e quer levar o commit para o certogit cherry-pick no branch certo e, depois, tirar do errado (veja git reset)
Não transforme o cherry-pick em hábito

Cada cópia é um commit novo. Se mais tarde a Ana juntar o novo-layout inteiro no main com merge, o D e o D' fazem a mesma mudança, e o Git costuma perceber isso sem conflito; mas o histórico fica com a mesma correção duas vezes, com hashes diferentes. Para alguns commits soltos, tudo bem. Para levar um branch inteiro, use merge ou rebase (a aula Rebase ou Merge? compara os dois).

Quando dá errado

O commit não existe (hash ou nome errado) 
$ git cherry-pick novo-layot
fatal: bad revision 'novo-layot'
$ git cherry-pick 1234567
fatal: bad revision '1234567'

"Revisão inválida": o Git não achou nenhum commit com esse nome. No primeiro, faltou um u em novo-layout; no segundo, o hash foi digitado errado (ou é de outro repositório). Como confirmar: git log --oneline --all lista os commits de todos os branches. Como resolver: copie o hash da lista, em vez de digitar de memória.

Mudanças não commitadas no mesmo arquivo 
$ echo '- 1 pitada de sal' >> bolo.txt
$ git status --short
 M bolo.txt
$ git cherry-pick d07edbe
error: Your local changes to the following files would be overwritten by merge:
	bolo.txt
Please commit your changes or stash them before you merge.
Aborting
fatal: cherry-pick failed

"As suas mudanças locais nestes arquivos seriam sobrescritas: bolo.txt. Faça commit delas ou guarde-as com stash antes. Abortando. O cherry-pick falhou." A Ana tinha uma linha nova no bolo.txt que ainda não foi commitada, e o commit escolhido mexe no mesmo arquivo. O Git se recusa a começar para não estragar o seu trabalho (nada foi mudado). Como resolver: commite a mudança, ou guarde-a com git stash, ou descarte-a com git restore, e rode o cherry-pick de novo. (Se as suas mudanças estiverem em outros arquivos, que o commit não toca, o cherry-pick funciona normalmente e elas ficam lá.)

Tentou copiar um commit de merge 
$ git log --oneline --graph main
*   bcbdba7 (HEAD -> main) Merge branch 'pudim-de-chocolate'
|\
| * e3da56a (pudim-de-chocolate) Adiciona o pudim de chocolate
|/
* 74a4b0b Adiciona a receita de pudim
* e0ec859 Adiciona a receita de bolo
* 700bbd5 Cria o README
$ git switch -q novo-layout
$ git cherry-pick main
error: commit bcbdba7ca038f5377d6085bdc17d8cd218925e41 is a merge but no -m option was given.
fatal: cherry-pick failed

"O commit … é um merge, mas a opção -m não foi dada." Um commit de merge tem dois pais, e o cherry-pick copia "a diferença em relação ao pai"; com dois pais, o Git não sabe qual usar. Como resolver: quase sempre, o melhor é copiar os commits de dentro do branch que foi juntado (aqui, o e3da56a). Se você quer mesmo o merge inteiro, diga qual pai é a base com -m 1 (o 1 é o branch que recebeu o merge, o main):

$ git cherry-pick -m 1 main
[novo-layout c22b7cb] Merge branch 'pudim-de-chocolate'
 Date: Thu Oct 15 10:30:00 2026 -0300
 1 file changed, 1 insertion(+)
 create mode 100644 pudim-chocolate.txt

Repare que o resultado é um commit comum (um pai só) com a mensagem do merge, o que confunde quem lê o histórico depois. Prefira copiar os commits de dentro.

Referência rápida

ComandoO que faz
git cherry-pick HASHCopia o commit para o branch atual, como um commit novo
git cherry-pick A B CCopia vários, nessa ordem
git cherry-pick A..BCopia os commits depois de A até B (sem o A)
git cherry-pick A^..BCopia de A até B, com o A
git cherry-pick -x HASHAcrescenta "(cherry picked from commit …)" na mensagem
git cherry-pick -n HASHAplica a mudança sem commitar (fica na área de preparo)
git cherry-pick -e HASHAbre o editor para mudar a mensagem antes de commitar
git cherry-pick --continueSegue depois de resolver o conflito e dar git add
git cherry-pick --abortDesiste e volta tudo como estava
git cherry-pick --skipPula o commit atual (conflito ou vazio)

Resumo

  • git cherry-pick HASH copia a mudança de um commit para o branch em que você está, criando um commit novo.
  • A cópia tem a mesma mensagem, o mesmo autor e a mesma mudança, mas outro hash (porque tem outro pai). O original continua no branch de origem.
  • -x anota na mensagem de onde a cópia veio; -n aplica sem commitar; vários commits vão na ordem escrita, e A..B deixa o A de fora.
  • Conflito: resolva, git add, git cherry-pick --continue. Para desistir, --abort; para pular um, --skip.
  • Use para alguns commits soltos. Para um branch inteiro, prefira merge ou rebase.

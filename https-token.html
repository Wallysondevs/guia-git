Git HTTPS e Token de Acesso

Existem dois "caminhos" para o seu Git conversar com o GitHub: o SSH, com uma chave guardada no seu computador (aula Chave SSH para o GitHub), e o HTTPS, o mesmo protocolo das páginas da web. O HTTPS é o caminho do endereço que o GitHub mostra primeiro, e funciona até em redes que bloqueiam o SSH. Mas tem uma pegadinha que derruba todo iniciante: quando o Git pede a Password (senha), a senha da sua conta não funciona. No lugar dela vai um token de acesso. Esta aula mostra o que é esse token, como criá-lo e como fazer o Git lembrar dele.

Você vai aprender
  • A diferença entre o endereço HTTPS e o SSH de um repositório, e como trocar um pelo outro com git remote set-url.
  • O que é um personal access token (token de acesso pessoal) e por que ele substitui a senha.
  • Como criar um token no site do GitHub (o "refinado" e o "clássico").
  • O que digitar quando o Git pergunta Username e Password.
  • Como o Git guarda o token para não perguntar toda vez: credential.helper com cache e store, e os riscos de cada um.

Os comandos desta aula rodaram no Git 2.53 da máquina da Ana (usuária ana, computador notebook), com o sistema em português. As telas do site do GitHub não rodam no laboratório: elas estão descritas com base na documentação oficial (docs.github.com/pt) e marcadas como ilustrativas. Todos os tokens desta página são inventados: nenhum deles funciona. As mensagens do Git saem parte em português, parte em inglês: a tradução do Git no Ubuntu é parcial (veja a nota em Seu Primeiro Commit).

A ideia: o crachá de visitante

Pense num prédio comercial. Você, o dono da sala, tem a chave mestra (a senha da conta do GitHub): ela abre tudo, inclusive a porta para trocar a fechadura. Você não entrega a chave mestra para o motoboy que traz uma encomenda. Na portaria, ele ganha um crachá de visitante:

  • o crachá só abre as portas que você liberou (por exemplo, só a sala 302);
  • ele vence no fim do dia (ou da semana);
  • se ele for perdido, você cancela só aquele crachá, sem trocar a chave mestra.

O token de acesso pessoal (personal access token, ou PAT) é esse crachá. É um texto comprido e aleatório que o GitHub gera para você, com permissões escolhidas (só ler? ler e enviar? quais repositórios?) e uma data de validade. Você usa o token no Git; a senha de verdade fica só com você, para entrar no site.

Por que a senha não serve?

A documentação do GitHub diz: "A autenticação baseada em senha para o Git foi removida em favor de métodos de autenticação mais seguros." Desde 2021, o GitHub recusa a senha da conta em git push, git pull e git clone por HTTPS. Quando o Git pede a Password, o GitHub espera um token.

1. HTTPS ou SSH: olhe o endereço do remoto

O que decide o caminho é o endereço do remoto (veja git remote). A Ana tinha ligado o repositório receitas ao GitHub com o endereço SSH:

$ git remote -v
origin	git@github.com:ana-souza/receitas.git (fetch)
origin	git@github.com:ana-souza/receitas.git (push)

Os dois formatos lado a lado:

CaminhoEndereçoComo você prova quem é
HTTPShttps://github.com/ana-souza/receitas.gitNome de usuário + token
SSHgit@github.com:ana-souza/receitas.gitChave SSH (aula Chave SSH)

No site do GitHub, o botão verde Code de um repositório mostra os dois endereços, em abas (ilustrativo). Quem escolhe é você.

Trocando de SSH para HTTPS: git remote set-url

A Ana está no computador da biblioteca, onde a rede bloqueia o SSH. Ela troca o endereço do origin para o HTTPS:

$ git remote set-url origin https://github.com/ana-souza/receitas.git
$ git remote -v
origin	https://github.com/ana-souza/receitas.git (fetch)
origin	https://github.com/ana-souza/receitas.git (push)
git remote
O comando que cuida dos remotos (os "endereços" de outros repositórios).
set-url
"Definir o endereço": troca a URL de um remoto que já existe. Não cria nem apaga nada.
origin
O nome do remoto que vai mudar.
https://github.com/ana-souza/receitas.git
O novo endereço: https://, o site, o dono (ana-souza) e o repositório (receitas.git).

O comando não mostra nada quando dá certo (o silêncio é sucesso, como em muitos comandos do Git). O git remote -v confirma: as duas linhas, a de buscar (fetch) e a de enviar (push), agora apontam para o HTTPS. Nenhum commit mudou: só o endereço.

Missão: o repositório receitas está ligado ao GitHub pelo endereço SSH. Confira com git remote -v, troque o origin para o endereço HTTPS https://github.com/ana-souza/receitas.git e rode git remote -v de novo para conferir.

2. Criando o token no site do GitHub (ilustrativo)

O GitHub tem dois tipos de token pessoal. A documentação recomenda o refinado (fine-grained), que só abre os repositórios escolhidos; o clássico (classic) é o mais antigo, com permissões mais largas, e ainda aparece em muitos tutoriais.

Token refinado (fine-grained)

Os passos, segundo a documentação oficial (os nomes das telas podem aparecer em inglês, conforme o idioma da sua conta):

  1. Confirme o seu e-mail na conta, se ainda não confirmou.
  2. No canto superior direito, clique na sua foto de perfil e depois em Configurações (Settings).
  3. Na barra lateral esquerda, clique em Developer settings ("configurações do desenvolvedor", lá no fim).
  4. Em Personal access tokens, clique em tokens granulares (Fine-grained tokens).
  5. Clique em Gerar novo token.
  6. Em Nome do token, escreva para que ele serve: notebook da Ana.
  7. Em Validade, escolha um prazo (30 dias, 90 dias…). Prazo curto é mais seguro.
  8. Em Acesso ao repositório, escolha só os repositórios que o token vai usar (a documentação recomenda o mínimo necessário): aqui, ana-souza/receitas.
  9. Em Permissões, dê ao token acesso de leitura e escrita ao conteúdo do repositório (Contents), que é o que o git push precisa.
  10. Clique em Gerar token.

O GitHub mostra o token uma única vez. Ele tem esta cara (este é inventado):

github_pat_EXEMPLO_0000_nao_e_um_token_de_verdade

O começo diz o tipo: github_pat_ é um token refinado, e ghp_ é um token clássico (a documentação lista esses prefixos). Copie o token e guarde num gerenciador de senhas: se você fechar a página sem copiar, não dá para ver de novo; só gerar outro.

Token clássico (classic)

O caminho é o mesmo até Personal access tokens; ali você escolhe Tokens (clássico), depois Gerar novo token → Gerar novo token (clássico). Dê um nome no campo "Observação" (Note), escolha a validade e marque o escopo repo, que a documentação indica para acessar repositórios pela linha de comando. Repare a diferença: o escopo repo vale para todos os seus repositórios. Por isso o refinado é melhor quando dá para usar.

Token é senha

Quem tem o seu token faz o que ele permite, em seu nome. Nunca cole o token num commit, num README, num print de tela nem num grupo de mensagens. Se ele vazar, apague-o no GitHub (na mesma tela onde você o criou) e gere outro. A aula Commitei uma Senha! E Agora? conta o que fazer se ele entrar no histórico.

3. Usando o token: o que digitar no Username e no Password

Com o endereço HTTPS, na primeira vez que o Git precisa falar com o GitHub (um push, por exemplo), ele pergunta quem é você. A Ana envia o repositório receitas pela primeira vez, e cola o token no Password:

$ git push -u origin main
Username for 'https://github.com': ana-souza
Password for 'https://ana-souza@github.com':                « o token foi colado aqui (não aparece)
Enumerating objects: 3, done.
Counting objects: 100% (3/3), done.
Writing objects: 100% (3/3), 224 bytes | 224.00 KiB/s, done.
Total 3 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
To https://github.com/ana-souza/receitas.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
  • Username for 'https://github.com': "nome de usuário para o github.com": digite o seu usuário do GitHub (ana-souza). Ele não é o e-mail.
  • Password for 'https://ana-souza@github.com': "senha para ana-souza no github.com": aqui vai o token, não a senha da conta. Ao colar, nada aparece na tela, nem asteriscos: é normal, o terminal esconde o que você digita. Cole (no terminal do Ubuntu, Ctrl+Shift+V) e aperte Enter.
  • Depois, o envio acontece como na aula git push: o branch main foi criado no GitHub.

As perguntas são do Git e não têm tradução no Git do Ubuntu, por isso saem em inglês mesmo com o sistema em português.

Atalho: a GitHub CLI ou o Git Credential Manager

A documentação do GitHub sugere duas ferramentas que fazem esse trabalho por você: a GitHub CLI (gh auth login, escolhendo HTTPS; veja GitHub CLI (gh)) e o Git Credential Manager, que abre o navegador para você entrar na conta e guarda a credencial no sistema. Com eles, você nem precisa criar o token à mão. Os dois são programas à parte, que não vêm com o Git do Ubuntu.

4. Fazendo o Git lembrar do token: credential.helper

Sem nenhuma configuração, o Git pergunta usuário e token a cada push (e a cada pull de um repositório privado). Para não colar o token toda hora, o Git usa um ajudante de credenciais (credential helper): um programinha que guarda o usuário e o token e os entrega ao Git quando ele precisa. O Git já vem com dois:

AjudanteOnde guardaPor quanto tempoRisco
cacheNa memória15 minutos (o padrão), ou o tempo de --timeoutBaixo: nada vai para o disco
storeNo arquivo ~/.git-credentialsPara sempreAlto: o token fica em texto puro no disco

Primeiro, veja se há algum configurado:

$ git config --global credential.helper
$ echo $?
1

Nada aparece e o código de saída é 1: o git config avisa assim que a configuração não existe. Sem ajudante, o Git pergunta toda vez.

O cache: lembrar por um tempo

$ git config --global credential.helper 'cache --timeout=3600'
$ git config --global --get credential.helper
cache --timeout=3600
git config --global
Grava no seu arquivo de configuração pessoal (~/.gitconfig), que vale para todos os repositórios (aula git config).
credential.helper
A configuração que diz qual ajudante usar.
'cache --timeout=3600'
O ajudante cache, guardando por 3600 segundos (1 hora). As aspas são necessárias por causa do espaço. Sem --timeout, o padrão é 900 segundos (15 minutos).

Agora o Git pergunta uma vez; durante a próxima hora, os push e pull seguintes usam o token guardado na memória. Desligou o computador? A memória se apaga, e o Git pergunta de novo. É o meio-termo seguro.

O store: lembrar para sempre (num arquivo)

$ git config --global credential.helper store
$ git config --global credential.helper
store

Com o store, o Git ainda pergunta uma vez. Depois do primeiro push que der certo, ele grava o usuário e o token no arquivo ~/.git-credentials, e não pergunta mais:

$ git push -u origin main
Username for 'https://github.com': ana-souza
Password for 'https://ana-souza@github.com':
…                                                    « o envio, como na seção 3
$ cat ~/.git-credentials
https://ana-souza:github_pat_EXEMPLO_0000_nao_e_um_token_de_verdade@github.com
$ git push                                           « um commit novo depois: nenhuma pergunta
Enumerating objects: 4, done.
Counting objects: 100% (4/4), done.
Delta compression using up to 4 threads
Compressing objects: 100% (2/2), done.
Writing objects: 100% (3/3), 296 bytes | 296.00 KiB/s, done.
Total 3 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
To https://github.com/ana-souza/receitas.git
   f0c33ea..934a161  main -> main

O arquivo também pode ser gravado sem um push, com o git credential approve (o mesmo passo que o push faz sozinho depois de entrar com sucesso). Veja as permissões dele:

$ printf 'protocol=https\nhost=github.com\nusername=ana-souza\npassword=github_pat_EXEMPLO_0000_nao_e_um_token_de_verdade\n\n' | git credential approve
$ ls -l ~/.git-credentials
-rw------- 1 ana ana 79 Oct 15 10:29 /home/ana/.git-credentials
  • -rw-------: só a Ana pode ler e escrever o arquivo; o Git cria assim de propósito.
  • A linha guardada é um endereço com o usuário e o token à vista, depois do :. Qualquer programa que rode como a Ana (ou quem pegar o notebook dela destravado, ou um backup do disco) pode ler o token.

A própria documentação do Git avisa que esse ajudante guarda as senhas "sem criptografia no disco, protegidas só pelas permissões do sistema de arquivos", e sugere o cache no lugar. Prefira o cache, o Git Credential Manager ou o SSH. Se usar o store, use um token refinado, só com os repositórios necessários e com validade curta.

Esquecendo um token guardado

Trocou o token (o antigo venceu, ou vazou)? Peça para o Git esquecer o antigo com git credential reject; no próximo push, ele pergunta de novo:

$ printf 'protocol=https\nhost=github.com\n\n' | git credential fill
protocol=https
host=github.com
username=ana-souza
password=github_pat_EXEMPLO_0000_nao_e_um_token_de_verdade
$ printf 'protocol=https\nhost=github.com\nusername=ana-souza\n\n' | git credential reject
$ cat ~/.git-credentials

O primeiro comando mostra o que o ajudante tem guardado para o github.com (o mesmo que ele entregaria a um push). O reject ("rejeitar") não mostra nada, e o cat não mostra nada também.

O arquivo ficou vazio. Com o cache, desligar o computador já basta (ou git credential-cache exit, que esvazia a memória na hora).

Quando dá errado

Digitou a senha da conta no lugar do token

O GitHub recusa, e a resposta dele (as linhas remote:, que vêm do servidor, em inglês) explica o motivo:

$ git push -u origin main
Username for 'https://github.com': ana-souza
Password for 'https://ana-souza@github.com':
remote: Support for password authentication was removed on August 13, 2021.
remote: Please see https://docs.github.com/get-started/getting-started-with-git/about-remote-repositories#cloning-with-https-urls for information on currently recommended modes of authentication.
fatal: Authentication failed for 'https://github.com/ana-souza/receitas.git/'

"O suporte à autenticação por senha foi removido em 13 de agosto de 2021", e o servidor indica uma página da documentação. A última linha é do Git: "a autenticação falhou" (essa mensagem não tem tradução no Git do Ubuntu, por isso sai em inglês mesmo com o sistema em português). Como resolver: rode o comando de novo e cole o token no Password. Se o store guardou a senha errada, apague-a antes com o git credential reject da seção 4. A mesma mensagem aparece quando o token venceu ou foi apagado: gere outro.

could not read Username: não havia onde perguntar

Quando o Git precisa do usuário mas não está num terminal onde dê para perguntar (um script, um programa que roda o Git por baixo), ele desiste:

$ printf 'protocol=https\nhost=github.com\n\n' | git credential fill
fatal: could not read Username for 'https://github.com': Endereço ou dispositivo inexistente

"Não consegui ler o Username para o github.com". O Git queria perguntar o Username, mas não havia terminal para isso (no laboratório, o comando rodou sem terminal, como roda um script). A primeira parte da mensagem fica em inglês; o fim, "Endereço ou dispositivo inexistente", é o sistema explicando que não achou o terminal. Como resolver: rode o comando num terminal normal uma vez (com o cache ou o store ligado, ele guarda o token), ou use o SSH.

Erro de digitação no endereço 
$ git remote set-url origin htps://github.com/ana-souza/receitas.git
$ git push -u origin main
git: 'remote-htps' não é um comando git. Veja 'git --help'.

The most similar command is
	remote-https
fatal: remote helper 'htps' aborted session

Faltou um t em https. O set-url aceitou sem reclamar (ele não confere o endereço); o erro só aparece no push. Para cada tipo de endereço, o Git chama um "ajudante de remoto" com o nome do protocolo (remote-https); como htps não existe, ele não achou o remote-htps, sugeriu o parecido (remote-https) e desistiu. Como confirmar: git remote -v mostra o endereço com o erro. Como resolver: git remote set-url origin https://github.com/ana-souza/receitas.git, com o endereço certo.

Nome do site errado (ou sem internet) 
$ git remote set-url origin https://githb.com/ana-souza/receitas.git
$ git push -u origin main
fatal: não foi possível acessar 'https://githb.com/ana-souza/receitas.git/': Could not resolve host: githb.com

"Não foi possível acessar … : não consegui descobrir onde fica o githb.com" (faltou o u). Não é problema de token: o Git nem chegou a um servidor. A mesma mensagem, com github.com, aparece quando o computador está sem internet. Como resolver: confira o endereço com git remote -v e a conexão, e corrija com git remote set-url.

Resumo

  • O endereço do remoto decide o caminho: https://github.com/… é HTTPS; git@github.com:… é SSH. Troque com git remote set-url origin NOVO-ENDEREÇO e confira com git remote -v.
  • Por HTTPS, o GitHub não aceita a senha da conta: no Password vai um token de acesso pessoal, criado em Configurações → Developer settings → Personal access tokens (ilustrativo).
  • Prefira o token refinado (github_pat_…), só com os repositórios necessários e com validade; o clássico (ghp_…) com repo abre todos.
  • O credential.helper faz o Git lembrar: cache guarda na memória por um tempo (padrão 15 min); store guarda para sempre em ~/.git-credentials, em texto puro.
  • Token é senha: nunca o commite, nunca o mostre. Vazou? Apague no GitHub e gere outro.

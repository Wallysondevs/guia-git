Git Revisão de Código

Antes de um pull request entrar no projeto, alguém lê as mudanças: procura erros, pergunta o que não entendeu, sugere melhorias e, no fim, aprova ou pede ajustes. Isso é a revisão de código (em inglês, code review). Ela pega erros que o autor não viu, espalha o conhecimento pela equipe e ensina dos dois lados. Esta aula mostra a revisão no site do GitHub e no seu computador, com o Git.

Você vai aprender
  • O que um revisor procura num pull request.
  • Como comentar uma linha, sugerir uma mudança e enviar a revisão no site (aprovar, comentar ou pedir mudanças).
  • Como revisar no seu computador: git fetch, git log main..branch e git diff main...branch.
  • Como o autor responde: mais commits no mesmo branch.
  • Como escrever comentários que ajudam, e não magoam.
O que é real e o que é ilustrativo nesta aula

Os passos no site do GitHub são ilustrativos, descritos conforme a documentação oficial, em docs.github.com; o site é em inglês, e os nomes aparecem como estão nele, com a tradução ao lado. Os comandos rodaram de verdade no Git do Ubuntu, com o "GitHub de mentira" do laboratório do guia: o Bruno (bruno@notebook) revisa o branch receita-sexta do fork da Ana (ana-souza/cardapio). As mensagens do Git saem parte em português, parte em inglês: a tradução do Git no Ubuntu é parcial (veja a nota em Seu Primeiro Commit).

A ideia: a redação com a caneta verde

Na escola, a professora devolve a redação com anotações na margem: "essa frase está confusa", "excessão é com ç", "ótimo exemplo!". A redação não é jogada fora: a aluna corrige e entrega de novo. Algumas observações são obrigatórias (o erro de ortografia), outras são sugestões ("talvez um exemplo a mais aqui"), e algumas são só elogios.

A revisão de código é igual, com duas diferenças: qualquer pessoa da equipe pode ser "a professora", e quem revisa também aprende com o código dos outros. O objetivo não é achar culpados; é deixar o projeto melhor.

1. Revisando no site (ilustrativo)

Segundo a documentação do GitHub, o Bruno abre o pull request da Ana e:

  1. Vai para a aba Files changed ("Arquivos alterados"): as diferenças de cada arquivo, com as linhas removidas e as acrescentadas, como no git diff.
  2. Para comentar uma linha, passa o mouse sobre o número da linha e clica no ícone de comentário azul que aparece. (Para várias linhas, arrasta sobre os números, ou clica na primeira e, segurando Shift, na última.)
  3. Escreve o comentário e clica em Start a review ("Iniciar uma revisão"). Os próximos comentários vão com Add review comment ("Adicionar comentário à revisão"). Os comentários ficam pendentes: só o Bruno os vê até enviar a revisão.
  4. Para propor um texto exato, usa o ícone Suggestion ("Sugestão") e edita o trecho dentro do bloco de sugestão (exemplo logo abaixo).
  5. Depois de ler um arquivo inteiro, marca Viewed ("Visualizado") no cabeçalho dele, e o arquivo é recolhido. Se o arquivo mudar depois, a marca sai sozinha.
  6. No fim, clica em Review changes ("Revisar alterações"), escreve um resumo e escolhe uma das três opções. Depois, Submit review ("Enviar revisão").
OpçãoQuer dizerQuando usar
Comment ("Comentar")Só comentários, sem decisãoDúvidas, ou uma revisão parcial
Approve ("Aprovar")"Pode juntar"Está bom (talvez com detalhes opcionais)
Request changes ("Solicitar alterações")"Precisa mudar antes de juntar"Há um erro ou algo que não pode entrar assim

A sugestão de mudança

Ao clicar no ícone de sugestão numa linha, o campo do comentário ganha um bloco com o texto atual da linha, para o revisor editar. O comentário do Bruno ficou assim (é texto em Markdown, como no README):

Calabresa é com s.

```suggestion
Sexta: pizza de calabresa
```

Na página, o bloco aparece como a troca da linha antiga pela nova. A Ana, como autora, pode aceitar direto no site: segundo a documentação, o botão Commit suggestion ("Fazer commit da sugestão") cria um commit com aquela troca no branch dela; com várias sugestões, Add suggestion to batch ("Adicionar sugestão ao lote") junta todas e Commit suggestions faz um commit só. Depois disso, ela precisa dar git pull no branch, porque o commit foi feito lá no GitHub.

2. Revisando no seu computador

O site basta para mudanças pequenas. Para uma revisão mais cuidadosa (rodar o projeto, abrir os arquivos no editor, testar), o revisor traz o branch para o computador. O branch está no fork da Ana, então o Bruno acrescenta o fork como um remoto (o nome ana é escolha dele; veja git remote) e busca:

$ git remote add ana https://github.com/ana-souza/cardapio.git
$ git fetch ana

remote: Compressing objects: 100% (6/6), done.

Unpacking objects: 100% (6/6), 621 bytes | 621.00 KiB/s, done.

Agora ele tem ana/receita-sexta, uma cópia somente leitura do branch dela. Primeiro, quais commits o PR traz:

$ git log --oneline main..ana/receita-sexta
2234ff5 (ana/receita-sexta) Adiciona o sábado
25de730 Adiciona a sexta-feira

main..ana/receita-sexta (dois pontos) quer dizer "os commits que estão em ana/receita-sexta e não estão no main": exatamente o que o pull request acrescenta (veja git log: Filtros). Dois commits: a sexta e… um sábado que a descrição não mencionava. Ponto para perguntar.

O resumo: quais arquivos mudaram e quantas linhas. Bom para ter a noção do tamanho antes de ler.

No git diff, três pontos querem dizer "o que o branch mudou desde que se separou do main". É o mesmo que a aba Files changed mostra. Com dois pontos, o diff compararia as duas pontas, e as mudanças que entraram no main depois apareceriam ao contrário, como se o PR as desfizesse.

As linhas acrescentadas (veja git diff).

Para ver o projeto inteiro como ficaria, o Bruno troca para o branch. Como só o remoto ana tem um receita-sexta, o git switch cria o branch local já ligado a ele:

Ele lê, testa o que for preciso e volta ao main. Os comentários, ele escreve no site (seção 1): "calabresa é com s" (com a sugestão) e "o sábado não estava na descrição; é de propósito?". Como há um erro, ele envia a revisão com Request changes.

Com o GitHub CLI

Quem usa o GitHub CLI traz o branch de um pull request com um comando só, pelo número do PR: gh pr checkout 1 (ilustrativo; o gh não roda no laboratório do guia).

4. Comentários que ajudam

Revisão é conversa entre pessoas. O mesmo problema pode ser apontado de um jeito que ensina ou de um jeito que magoa:

Em vez de…Prefira…Por quê
"Isso está errado.""Calabresa é com s. Deixei uma sugestão."Diz o quê, e já oferece a solução
"Por que você fez isso???""Não entendi por que o sábado entrou aqui. É de propósito?"Pergunta de verdade, sem acusar
"Eu faria diferente.""Opcional: dá para pôr os dias em ordem alfabética? Não bloqueia."Separa o obrigatório do gosto pessoal
(silêncio sobre o que está bom)"Gostei da opção vegetariana!"Elogio também é revisão

Comente o código, não a pessoa. E, do lado do autor: não leve para o lado pessoal, agradeça, e responda a cada comentário (concordando, explicando ou perguntando).

Para facilitar a vida de quem revisa

  • PRs pequenos, com um assunto só (um branch por assunto).
  • Commits com boas mensagens (veja Boas Mensagens de Commit): o revisor lê o git log como um roteiro.
  • Descrição que diga o que muda, por que, e como conferir.
  • Revise você primeiro: antes de abrir o PR, rode o mesmo git diff main...SEU-BRANCH e leia como se fosse de outra pessoa. Muitos erros aparecem aí.

Quando dá errado

O git diff main..branch mostra mudanças que o PR não fez

O que aconteceu: com dois pontos, o git diff compara as duas pontas. Se o main recebeu commits depois que o branch foi criado, essas mudanças aparecem invertidas (como linhas removidas), como se o PR as desfizesse. Como resolver: use três pontos, git diff main...branch, que compara com o ponto em que o branch se separou. (No git log é o contrário: os dois pontos são os que você quer na revisão.)

"Eu já tinha aplicado a sugestão no site, e agora o meu push foi recusado"

O que aconteceu: o Commit suggestion criou um commit no seu branch, lá no GitHub. O seu branch local não tem esse commit, e o push é recusado com ! [rejected] … (fetch first) (veja Push Rejeitado). Como resolver: git pull no branch (para os seus commits locais, git pull --rebase deixa o histórico em linha reta) e depois git push.

O PR ficou parado, sem revisão

Não é erro do Git, mas acontece muito. Como resolver: confira se o PR não está como rascunho (draft), peça a revisão a alguém específico pelo site e, se o PR for grande, considere dividi-lo em dois. Uma mensagem educada na conversa ("quando der, pode dar uma olhada?") também ajuda.

Resumo

  • Revisão de código é outra pessoa ler as suas mudanças antes de elas entrarem no projeto, para achar erros, tirar dúvidas e melhorar o código.
  • No site: aba Files changed, comentários nas linhas (Start a review), sugestões, e no fim Review changes → Comment, Approve ou Request changes → Submit review.
  • No computador: git fetch do fork, git log --oneline main..BRANCH (os commits) e git diff main...BRANCH (as mudanças, com três pontos).
  • O autor responde com commits novos no mesmo branch e git push; o PR se atualiza.
  • Comente o código, não a pessoa: diga o quê, por quê, e ofereça um caminho.

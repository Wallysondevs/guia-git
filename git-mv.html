Git mv

O nome bolo.txt ficou vago: a Ana já tem três bolos em mente. Ela quer chamá-lo de bolo-de-cenoura.txt e, mais tarde, guardar todos os doces numa pasta doces. O git mv (de move, "mover") renomeia ou move um arquivo e já prepara a mudança para o próximo commit, como o git rm faz com as remoções.

Você vai aprender
  • Como renomear e mover arquivos e pastas com git mv.
  • A ler o renamed do git status e o R do --short.
  • Um segredo do Git: ele não guarda "renomeações"; ele as deduz comparando conteúdos (o similarity index).
  • Por que mv + git add dá no mesmo, e como seguir a história de um arquivo renomeado (git log --follow).
  • As opções -n, -v, -f, -k e os erros reais do Git.

Todas as saídas desta aula saíram do Git do Ubuntu 26.04, na máquina da Ana (usuária ana, computador notebook), com o sistema em português. Algumas mensagens do Git ainda não têm tradução e saem em inglês.

A ideia: trocar a etiqueta da pasta do arquivo

Num arquivo de aço de escritório, renomear uma pasta é trocar a etiqueta; mover é tirá-la de uma gaveta e pôr em outra. O conteúdo não muda. No Git é igual: o conteúdo do arquivo continua o mesmo; o que muda é o caminho (o nome e a pasta). E, como toda mudança, ela precisa ser preparada e commitada.

1. Renomeando um arquivo

$ git mv bolo.txt bolo-de-cenoura.txt
$ ls
LEIAME.txt  bolo-de-cenoura.txt  pudim.txt
git mv
O comando: "mova (ou renomeie) e registre no Git".
bolo.txt
A origem (em inglês, source): o arquivo como ele se chama agora. Precisa ser um arquivo que o Git rastreia.
bolo-de-cenoura.txt
O destino (destination): o nome novo.

O git mv não mostra nada quando dá certo. O ls confirma: o arquivo já tem o nome novo na pasta. E o git status:

$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	renamed:    bolo.txt -> bolo-de-cenoura.txt

renamed = "renomeado", com a seta -> indo do nome antigo para o novo. A renomeação já está em Mudanças a serem submetidas (preparada). Falta o commit:

$ git commit -q -m 'Renomeia bolo.txt para bolo-de-cenoura.txt'
$ git log --oneline --stat -1
3f91a55 Renomeia bolo.txt para bolo-de-cenoura.txt
 bolo.txt => bolo-de-cenoura.txt | 0
 1 file changed, 0 insertions(+), 0 deletions(-)

No --stat, a renomeação aparece com =>, e o 0 diz que nenhuma linha do conteúdo mudou: só o nome.

Missão: o GitHub mostra na página do repositório um arquivo chamado README.md (aula O README e o Markdown). Renomeie o LEIAME.txt para README.md com git mv, confira o renamed no git status e faça o commit.

2. Movendo para outra pasta

Agora a Ana quer os doces numa pasta doces. Quando o destino é uma pasta que já existe, o arquivo vai para dentro dela, com o mesmo nome:

$ mkdir doces
$ git mv pudim.txt doces/
$ git mv bolo-de-cenoura.txt doces
$ ls doces
bolo-de-cenoura.txt  pudim.txt
$ git status --short
R  bolo-de-cenoura.txt -> doces/bolo-de-cenoura.txt
R  pudim.txt -> doces/pudim.txt
$ git commit -q -m 'Move os doces para a pasta doces'

Com ou sem a barra no fim (doces/ ou doces), o resultado é o mesmo, porque a pasta existe. No git status --short, o R (de renamed) na primeira coluna quer dizer "renomeado e preparado". Para o Git, mover é renomear: o "nome completo" do arquivo passou de pudim.txt para doces/pudim.txt.

A pasta precisa existir

O git mv não cria pastas. Por isso o mkdir doces veio antes (veja o erro em Quando dá errado). Você também pode mover vários arquivos de uma vez para uma pasta: git mv pudim.txt bolo.txt doces/.

Renomeando uma pasta inteira

Uma pasta também pode ser renomeada. Todos os arquivos de dentro mudam de caminho:

$ git mv doces sobremesas
$ git status --short
R  doces/bolo-de-cenoura.txt -> sobremesas/bolo-de-cenoura.txt
R  doces/pudim.txt -> sobremesas/pudim.txt

(A Ana preferiu o nome doces e desfez, antes do commit, com o mesmo comando ao contrário: git mv sobremesas doces.)

3. O segredo: o Git deduz as renomeações

Aqui está uma coisa que surpreende: o Git não guarda a informação "este arquivo foi renomeado". Um commit só guarda uma fotografia dos arquivos com os seus nomes (veja Como o Git Guarda as Coisas). Quando o Git compara duas fotografias e vê que sumiu um bolo.txt e apareceu um bolo-de-cenoura.txt com conteúdo igual ou muito parecido, ele conclui: "isto foi uma renomeação". O git diff --staged mostra essa conclusão (num repositório de testes, com uma receita de bolo de 7 linhas):

$ git mv bolo.txt bolo-de-cenoura.txt
$ git diff --staged
diff --git a/bolo.txt b/bolo-de-cenoura.txt
similarity index 100%
rename from bolo.txt
rename to bolo-de-cenoura.txt
diff --git a/bolo.txt b/bolo-de-cenoura.txt
Agora o a/ (antes) e o b/ (depois) têm nomes diferentes.
similarity index 100%
"Índice de semelhança": o quanto o conteúdo novo se parece com o antigo. 100% = idêntico.
rename from / rename to
"Renomeado de" / "renomeado para".

E se a Ana renomear e mudar o conteúdo antes do commit? Neste exemplo, o bolo tem 7 linhas e ela trocou uma (4 ovos por 3 ovos):

$ sed -i 's/4 ovos/3 ovos/' bolo-de-cenoura.txt
$ git add bolo-de-cenoura.txt
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	renamed:    bolo.txt -> bolo-de-cenoura.txt

$ git diff --staged
diff --git a/bolo.txt b/bolo-de-cenoura.txt
similarity index 94%
rename from bolo.txt
rename to bolo-de-cenoura.txt
index ad2414d..73b54e6 100644
--- a/bolo.txt
+++ b/bolo-de-cenoura.txt
@@ -1,6 +1,6 @@
 Bolo de cenoura
 3 cenouras
-4 ovos
+3 ovos
 2 xícaras de farinha
 1 xícara de óleo
 2 xícaras de açúcar

Continua sendo renamed, agora com similarity index 94%, e o diff mostra a linha que mudou (o sed -i só fez a troca no arquivo, como a Ana faria no editor). Depois do commit, o git show --stat resume assim: bolo.txt => bolo-de-cenoura.txt | 2 +-. O Git considera renomeação quando a semelhança é de 50% ou mais (o padrão). Se o conteúdo mudar quase todo, a "renomeação" vira duas coisas separadas: um arquivo apagado e um novo. Foi o que aconteceu quando a Ana trocou o pudim por um flan:

$ mv Pudim.txt flan.txt
$ echo 'Calda de caramelo' > flan.txt
$ git add -A
$ git status --short
D  Pudim.txt
A  flan.txt

Nenhuma linha em comum: o Git vê um D (apagado) e um A (novo). Moral: renomeie num commit e mude o conteúdo em outro. Assim a história do arquivo fica fácil de seguir.

4. Renomeei com o mv comum. E agora?

Como a renomeação é deduzida, não importa como você renomeou: o mv do terminal, o gerenciador de arquivos, o VS Code. Mas, sem o git mv, o Git primeiro enxerga duas coisas soltas:

$ mv LEIAME.txt README.md
$ git status
No ramo main
Changes not staged for commit:
  (utilize "git add/rm <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	deleted:    LEIAME.txt

Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	README.md

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")

Um LEIAME.txt apagado (deleted) e um README.md novo, não monitorado. É só preparar os dois (o antigo, para registrar que saiu, e o novo):

$ git add LEIAME.txt README.md
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	renamed:    LEIAME.txt -> README.md

Na área de preparo, o Git juntou as duas metades e reconheceu a renomeação. Ou seja: git mv a b = mv a b + git add a b. O git mv só economiza passos (e o risco de esquecer uma das metades).

Não prepare só a metade

Se a Ana desse só git add README.md e fizesse o commit, o repositório ficaria com os dois arquivos: o README.md novo e o LEIAME.txt antigo (cuja remoção ficou sem preparar). Confira sempre com o git status que aparece renamed.

5. A história de um arquivo renomeado: git log --follow

Ao pedir o histórico de um arquivo só, o git log procura por aquele nome. O doces/pudim.txt só tem esse nome desde o commit que o moveu:

$ git log --oneline
868d7c4 LEIAME vira README
7b21503 Move os doces para a pasta doces
3f91a55 Renomeia bolo.txt para bolo-de-cenoura.txt
1921d35 Receitas iniciais
$ git log --oneline -- doces/pudim.txt
7b21503 Move os doces para a pasta doces
$ git log --oneline --follow -- doces/pudim.txt
7b21503 Move os doces para a pasta doces
1921d35 Receitas iniciais

Sem --follow, a história parece começar na mudança de pasta. Com o --follow ("seguir"), o Git detecta a renomeação e continua procurando pelo nome antigo (pudim.txt), achando o commit em que o arquivo nasceu. O -- separa as opções do nome do arquivo (veja git log).

6. Opções úteis: -n, -v, -f e -k

$ git mv -n README.md LEIA.md
Checking rename of 'README.md' to 'LEIA.md'
Renaming README.md to LEIA.md
$ git mv -v README.md Leia-me.md
Renaming README.md to Leia-me.md
-n
Dry run, ensaio: mostra o que faria ("verificando a renomeação de… para…", "renomeando… para…") sem fazer nada. O README.md continuou com o mesmo nome.
-v
Verbose, detalhado: faz de verdade e conta o que fez.
-f
Force: renomeia mesmo que o destino já exista, substituindo o arquivo de destino (veja o erro abaixo).
-k
Pula, em silêncio, os arquivos que dariam erro (útil ao mover muitos de uma vez): git mv -k nada.txt outro.txt não reclama e termina com código 0, sem mover nada.

Formas diferentes, e qual usar

Você quer…Use
Renomear ou mover e já preparargit mv origem destino
Já renomeou com mv, no gerenciador ou no editorgit add nome-antigo nome-novo (ou git add -A)
Mover vários arquivos para uma pastagit mv a.txt b.txt pasta/ (a pasta precisa existir)
Renomear uma pastagit mv pasta-velha pasta-nova
Ver o histórico de um arquivo, antes e depois da renomeaçãogit log --follow -- arquivo

Quando dá errado

fatal: bad source 
$ git mv nada.txt outro.txt
fatal: bad source, source=nada.txt, destination=outro.txt
$ git mv Readme.md README.md
fatal: bad source, source=Readme.md, destination=README.md

"Origem ruim": o Git não achou a origem entre os arquivos que ele rastreia. Causas: nome errado (maiúsculas contam: Readme.md não é README.md), o arquivo já foi renomeado, ou é um arquivo novo que nunca recebeu git add. Como resolver: confira com ls e git status; para um arquivo não rastreado, use o mv comum.

fatal: destination exists 
$ git mv README.md doces/pudim.txt
fatal: destination exists, source=README.md, destination=doces/pudim.txt

"O destino já existe": já há um doces/pudim.txt, e o Git se recusa a escrever por cima dele. Como resolver: escolha outro nome. Só use -f se quiser mesmo substituir o destino: com git mv -f README.md doces/pudim.txt, a receita de pudim é trocada pelo conteúdo do README, e o git status --short mostra D README.md e M doces/pudim.txt (a Ana desfez com git restore --staged --worktree doces/pudim.txt README.md, da aula git restore).

fatal: destination directory does not exist 
$ git mv pudim.txt naoexiste/
fatal: destination directory does not exist, source=pudim.txt, destination=naoexiste/
$ git mv pudim.txt naoexiste/pudim.txt
fatal: renaming 'pudim.txt' failed: Arquivo ou diretório inexistente

"A pasta de destino não existe". Sem a barra, com o nome completo, a mensagem é outra: "falhou ao renomear: arquivo ou diretório inexistente". Como resolver: crie a pasta antes: mkdir naoexiste.

Faltou o destino 
$ git mv pudim.txt
uso: git mv [-v] [-f] [-n] [-k] <source> <destination>
   ou: git mv [-v] [-f] [-n] [-k] <source>... <destination-directory>

    -v, --[no-]verbose    detalhado
    -n, --[no-]dry-run    dry run
    -f, --[no-]force      force move/rename even if target exists
    -k                    skip move/rename errors
    --[no-]sparse         allow updating entries outside of the sparse-checkout cone

Com um nome só, o Git mostra o modo de usar: git mv sempre precisa de uma origem e um destino (ou várias origens e uma pasta de destino).

Só mudar maiúsculas no Windows e no macOS

No Linux, pudim.txt e Pudim.txt são nomes diferentes, e git mv pudim.txt Pudim.txt funciona normalmente (no lab, deu R pudim.txt -> Pudim.txt). No Windows e no macOS, que normalmente tratam os dois nomes como o mesmo arquivo, renomear pelo gerenciador de arquivos pode não ser percebido pelo Git. Use sempre o git mv para isso (ilustrativo: não testado nesses sistemas).

Resumo

  • git mv origem destino renomeia ou move um arquivo (ou pasta) e já prepara a mudança; depois, git commit.
  • No git status, aparece renamed: velho -> novo; no --short, R.
  • O Git não guarda renomeações: ele as deduz pela semelhança do conteúdo (similarity index, 50% ou mais). Renomeie e mude o conteúdo em commits separados.
  • mv + git add nos dois nomes dá no mesmo que git mv.
  • git log --follow -- arquivo mostra a história atravessando renomeações.
  • Erros comuns: bad source (origem não rastreada ou nome errado), destination exists (use outro nome ou -f), destination directory does not exist (crie a pasta).

Git Projeto: Portfólio no GitHub Pages

A Ana quer um lugar na internet para mostrar quem ela é e o que já fez: um portfólio. Ela não quer pagar hospedagem, e não precisa: o GitHub Pages publica de graça um site feito de arquivos HTML e CSS, direto de um repositório. O endereço vai ser https://ana-souza.github.io. Neste último projeto, você junta quase tudo do guia: criar o repositório do zero, ignorar um arquivo pessoal, fazer o primeiro commit, enviar para o GitHub, ligar o Pages e atualizar o site com novos commits e um branch.

Você vai aprender (na prática)
  • Montar um repositório novo do zero, com .gitignore para o que não deve ir para a internet.
  • Usar o nome especial usuario.github.io para o site pessoal.
  • Ligar o GitHub Pages para publicar a partir do branch main (ilustrativo).
  • Atualizar o site: cada git push no main vira uma nova versão no ar.
  • Testar uma mudança num branch antes de pôr no ar.

Este projeto põe em prática git init, .gitignore, git push e Publicando um Site (GitHub Pages). As saídas do terminal saíram do Git 2.53 do Ubuntu, na máquina da Ana, com um GitHub de treino. O que acontece no site do GitHub (criar o repositório, ligar o Pages, ver o site no ar) é ilustrativo, baseado na documentação oficial (docs.github.com/pt).

Português e inglês misturados? A tradução do Git que vem no Ubuntu é parcial: algumas mensagens saem em português, outras em inglês. As saídas abaixo estão exatamente como apareceram; as mensagens em inglês ganham tradução no texto.

A ideia: a vitrine da loja

Pense numa loja de bolos. Na cozinha (o computador da Ana), ela testa, erra, guarda rascunhos. Na vitrine (o site no ar), só entra o que está pronto. O caminho da cozinha para a vitrine é sempre o mesmo: git commit (o bolo está pronto) e git push (leva para a vitrine). O GitHub Pages é o funcionário que, toda vez que chega bolo novo no main do GitHub, arruma a vitrine sozinho.

computador da Ana  --git push-->  GitHub (main)  --Pages-->  https://ana-souza.github.io

Etapa 1: o repositório no GitHub (ilustrativo)

Para um site pessoal, o nome do repositório tem de ser exatamente usuario.github.io, em letras minúsculas. Como o usuário da Ana é ana-souza, o repositório se chama ana-souza.github.io. Pela documentação ("Criar um site do GitHub Pages"), o caminho é: no ícone + do canto superior direito, criar um novo repositório, escolher o dono (a conta da Ana), digitar o nome, deixar público (no plano gratuito, o Pages exige repositório público) e criar.

A documentação sugere marcar a opção de criar um README junto. A Ana não marca: ela vai criar os arquivos no computador e enviar tudo de lá, e um repositório vazio aceita o primeiro git push sem conflito (veja Criando um Repositório no GitHub).

Site de projeto × site pessoal. Qualquer repositório pode ter um site, mas ele fica num endereço com o nome do repositório: o receitas viraria https://ana-souza.github.io/receitas/. Só o repositório com o nome ana-souza.github.io ganha o endereço "raiz".

Etapa 2: os arquivos e o primeiro commit

No computador, a Ana cria a pasta e o repositório:

$ mkdir portfolio
$ cd portfolio
$ git init
Repositório vazio Git inicializado em  /home/ana/portfolio/.git/

No editor, ela escreve três arquivos. A página:

<body>
<h1>Ana Souza</h1>

O estilo:

body { font-family: sans-serif; max-width: 40em; margin: auto; }

E o README, que aparece na página do repositório no GitHub:

# Portfólio da Ana Souza

Na mesma pasta, ela guarda um arquivo notas-pessoais.txt com ideias soltas, que não deve ir para a internet. Tudo o que vai para um repositório público fica visível para o mundo. Por isso, antes do primeiro git add, ela cria o .gitignore:

notas-pessoais.txt
$ touch notas-pessoais.txt
$ echo 'notas-pessoais.txt' > .gitignore
$ git status

No commits yet

        .gitignore

        estilo.css
        index.html      « o notas-pessoais.txt não aparece

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)
$ git add .
$ git status

No commits yet

Mudanças a serem submetidas:
  (utilize "git rm --cached <arquivo>..." para não apresentar)
        new file:   .gitignore

        new file:   index.html

$ git commit -m 'Cria o portfólio'
[main (root-commit) aaa5fb9] Cria o portfólio
 4 files changed, 11 insertions(+)

 create mode 100644 README.md
 create mode 100644 estilo.css

$ git log --oneline
aaa5fb9 (HEAD -> main) Cria o portfólio
  • No primeiro git status, a lista de "Arquivos não monitorados" tem o .gitignore, o README, o CSS e o HTML, mas não o notas-pessoais.txt: o .gitignore já está funcionando.
  • O git add . (o ponto é "a pasta atual inteira") preparou os quatro arquivos, e só eles. O new file: quer dizer "arquivo novo".
  • [main (root-commit) aaa5fb9]: o root-commit é o primeiro commit do repositório, o que não tem pai.
Confira antes do primeiro push. Num repositório público, até um arquivo apagado depois continua no histórico. Rode git status e leia a lista antes do git add .: nada de senhas, documentos pessoais ou arquivos enormes (veja Commitei uma Senha! E Agora?).

Missão 1: a pasta portfolio já é um repositório e tem o index.html, o estilo.css, o README.md e o arquivo pessoal notas-pessoais.txt. Faça o notas-pessoais.txt ser ignorado (com um .gitignore) e faça o primeiro commit com todo o resto. No fim, o git status tem de estar limpo.

Etapa 3: enviar para o GitHub

Igual ao projeto da dupla: ligar o repositório local ao do GitHub e fazer o primeiro envio com -u.

$ git remote add origin https://github.com/ana-souza/ana-souza.github.io.git
$ git push -u origin main

* [new branch] main -> main: o main nasceu no GitHub. Os arquivos já estão no repositório, mas o site ainda não está no ar: falta ligar o Pages.

Missão 2: o portfólio já tem o primeiro commit. No treino, o "GitHub" é a pasta ~/github/ana-souza/ana-souza.github.io.git (o Git aceita uma pasta como endereço de remoto). Ligue o repositório a ela com o apelido origin e envie o main com -u. Confira com git status.

Etapa 4: ligar o GitHub Pages (ilustrativo)

Esta parte acontece no site do GitHub. Pela documentação ("Configurar uma fonte de publicação para o site do GitHub Pages"), os passos são:

  1. Na página do repositório ana-souza.github.io, abrir a aba Settings (configurações).
  2. Na barra lateral, na seção de código e automação, clicar em Pages (páginas).
  3. Em Build and deployment (build e implantação), no campo Source (fonte), escolher Deploy from a branch (implantar a partir de um branch).
  4. No menu de branch, escolher main; na pasta, / (root) (a raiz do repositório, onde está o index.html).
  5. Clicar em Save (salvar).

O GitHub monta o site e o publica. Segundo a documentação, pode levar até 10 minutos depois de um push para as mudanças aparecerem. Quando estiver pronto, a mesma página de configurações do Pages mostra o endereço, com a opção de visitar o site: https://ana-souza.github.io.

Os nomes dos botões do site do GitHub mudam com o tempo e dependem do idioma da interface (a documentação em português traduz os nomes; o site costuma aparecer em inglês). Se não encontrar algo, procure "GitHub Pages" em docs.github.com/pt: a página é atualizada junto com o site. Mais detalhes em Publicando um Site (GitHub Pages).

Etapa 6: testar num branch antes de pôr no ar

A Ana quer experimentar um tema escuro, mas sem arriscar a vitrine: o Pages publica o main, então ela trabalha num branch (como no projeto da funcionalidade). Ela envia o branch também, para guardar uma cópia no GitHub e poder mostrar a alguém:

  • O branch tema-escuro não aparece no site: o Pages só olha o main.

Gostou do tema. Hora de pôr no ar: juntar no main, enviar, e apagar o branch nos dois lugares.

$ git merge tema-escuro

$ git push
Total 0 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)

   cd808fc..e1e8a2e  main -> main      « o tema escuro vai para o site
$ git push origin --delete tema-escuro
To https://github.com/ana-souza/ana-souza.github.io.git
 - [deleted]         tema-escuro
$ git branch -d tema-escuro
Deleted branch tema-escuro (was e1e8a2e).
$ git log --oneline --graph --all

No ramo main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean
  • Fast-forward: o main não tinha andado, então só avançou até o commit do tema (sem commit de merge; veja Merge Fast-forward).
  • Total 0 no push: nenhum objeto novo precisou ir, porque o commit do tema já tinha sido enviado junto com o branch. O GitHub só moveu o main (cd808fc..e1e8a2e). É nesse momento que o tema escuro vai para o site.
  • git push origin --delete tema-escuro apaga o branch no GitHub (- [deleted]); git branch -d, no computador.

Quando dá errado

"remote: Repository not found." no primeiro push

O que aconteceu: o endereço do origin não bate com o repositório criado (um erro de digitação no nome, por exemplo ana-souza.github.com em vez de .io), ou o repositório não foi criado. A mensagem completa está no projeto da dupla.

Como resolver: confira com git remote -v e corrija com git remote set-url origin https://github.com/ana-souza/ana-souza.github.io.git.

"! [rejected] … (fetch first)" no primeiro push

O que aconteceu: o repositório do GitHub foi criado com README (ou licença, ou .gitignore), então ele já tem um commit que o seu computador não tem. É o mesmo push recusado do projeto da dupla.

Como resolver: traga o commit do GitHub e junte: git pull --no-rebase --allow-unrelated-histories origin main (as duas histórias começaram separadas, por isso a opção extra), resolva conflitos se houver (provavelmente no README) e git push -u origin main. Para evitar: crie o repositório vazio quando os arquivos já existem no computador.

Enviei, mas o site não mudou (ou mostra 404)

O que aconteceu (ilustrativo): as causas mais comuns são: o Pages ainda não terminou de publicar (até 10 minutos, pela documentação); o Pages não foi ligado ou aponta para outro branch ou pasta; não há index.html (ou README.md) na pasta publicada; ou o navegador está mostrando uma cópia antiga (recarregue sem cache).

Como confirmar: do lado do Git, git status deve dizer Your branch is up to date with 'origin/main' (tudo enviado) e git log --oneline -1 origin/main mostra o último commit que o GitHub tem. Do lado do site, a página de configurações do Pages mostra a situação da publicação.

Mandei sem querer um arquivo pessoal para o repositório público

O que aconteceu: o arquivo foi commitado antes de entrar no .gitignore. Colocar o nome no .gitignore depois não tira o arquivo do repositório.

Como resolver: git rm --cached notas-pessoais.txt (para de rastrear, mas mantém na pasta), acrescente ao .gitignore, commite e envie. Ele continua nos commits antigos: se for algo sensível (senha, token, documento), siga Commitei uma Senha! E Agora?.

Resumo

  • Site pessoal no GitHub Pages: repositório público chamado usuario.github.io, com um index.html na raiz.
  • Antes do primeiro git add ., um .gitignore para o que é pessoal; e um git status para conferir a lista.
  • Primeiro envio: git remote add origin URL e git push -u origin main. Depois, ligar o Pages no site (Settings → Pages → main, raiz).
  • Publicar = git commit + git push no main. O site atualiza em alguns minutos.
  • Experimentos vão num branch; o Pages só publica o main. Junte e envie quando estiver pronto.

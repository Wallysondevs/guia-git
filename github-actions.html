Git GitHub Actions

Toda vez que a Ana faz git push do site de receitas, ela abre o site para ver se nada quebrou. Um dia ela esquece, e o site fica uma semana sem a página inicial. O GitHub Actions resolve isso: é um "robô" do GitHub que roda os comandos que você mandar a cada push, num computador do próprio GitHub, e avisa se algo falhar. Nesta aula você vai escrever o seu primeiro robô, commitá-lo como qualquer outro arquivo e entender onde ver o resultado.

Você vai aprender
  • O que é o GitHub Actions e o vocabulário dele: fluxo de trabalho, evento, trabalho, etapa, executor e ação.
  • Onde mora o arquivo do robô (.github/workflows/) e como ler cada linha dele.
  • Que o robô é só um arquivo do repositório: você o cria, faz git add, git commit e git push.
  • Onde ver o resultado no site (a aba Ações) e como reproduzir uma falha no seu próprio terminal.
  • Os erros mais comuns: pasta com nome errado, recuo errado no YAML e o token sem a permissão workflow.
O que roda e o que não roda aqui

O GitHub Actions roda nos computadores do GitHub, não no seu. Os comandos de Git desta aula (criar a pasta, git add, git commit, git push) saíram do laboratório, com as mensagens reais em português. Já as telas do site (a aba Ações, os logs da execução) são descritas com base na documentação oficial, docs.github.com/pt/actions, e são ilustrativas: o GitHub muda o visual de vez em quando.

A ideia: um provador na cozinha

Imagine que a Ana tem um restaurante. Cada prato que sai da cozinha passa por um provador, que segue uma lista fixa: "está quente? tem sal? está no prato certo?". Se algo falhar, o prato volta e a Ana é avisada. O provador não cozinha nada: só confere, sempre do mesmo jeito, sem esquecer.

O GitHub Actions é esse provador. A "lista" é um arquivo de texto que fica dentro do seu repositório. O "prato saindo da cozinha" é um evento, como um git push. Quando o evento acontece, o GitHub liga um computador temporário, baixa o seu repositório nele, segue a lista e mostra se cada passo deu certo (✓) ou errado (✗).

Esse tipo de conferência automática tem um nome que você vai ver muito por aí: CI, de Continuous Integration ("integração contínua"): integrar o trabalho de todo mundo várias vezes ao dia, com uma verificação automática a cada envio.

O arquivo do robô

Um fluxo de trabalho é um arquivo em formato YAML (extensão .yml ou .yaml) guardado numa pasta com nome exato: .github/workflows/ na raiz do repositório. O ponto no começo de .github faz dela uma pasta "escondida" (o ls comum não mostra; o ls -a mostra).

Este é o robô da Ana. Ele confere duas coisas simples a cada push: que a página inicial index.html existe e que ela tem um título (<title>):

name: Verificar site
on: [push]
jobs:
  verificar:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - run: ls -l
      - run: test -f index.html
      - run: grep -q "<title>" index.html
name: Verificar site
O nome do fluxo. É o que aparece na lista da aba Ações do site.
on: [push]
O evento: "rode quando alguém fizer push". Outros comuns: pull_request (quando abrirem um pull request) e workflow_dispatch (um botão para rodar à mão).
jobs:
A lista de trabalhos. Aqui só há um, chamado verificar (o nome é escolha sua).
runs-on: ubuntu-latest
O executor: uma máquina Ubuntu nova, emprestada pelo GitHub, que é apagada no fim.
steps:
As etapas, em ordem. Cada uma começa com - (um item de lista no YAML).
- uses: actions/checkout@v6
Usa uma ação pronta, a checkout, que baixa o seu repositório para dentro da máquina. Sem ela, a máquina começa vazia! O @v6 é a versão da ação (a usada no exemplo da documentação oficial).
- run: ls -l
Roda um comando de shell. Aqui só lista os arquivos, para aparecer no registro (log).
- run: test -f index.html
O test -f termina com código 0 se o arquivo existe e 1 se não existe. No Actions, uma etapa que termina com código diferente de 0 falha, e o trabalho para ali.
- run: grep -q "<title>" index.html
O grep -q procura o texto em silêncio: código 0 se achou, 1 se não achou.
No YAML, o recuo (espaços) faz parte da gramática

Os espaços no começo das linhas dizem "isto está dentro daquilo". Use espaços, nunca Tab, e mantenha o mesmo recuo para itens do mesmo nível. Um espaço a mais ou a menos muda o sentido do arquivo, e o GitHub recusa o fluxo.

Passo 1: criar a pasta e o arquivo

No repositório da Ana (que já tem o index.html commitado e um remoto origin no GitHub), ela cria a pasta com mkdir -p (o -p cria as duas, .github e workflows, de uma vez) e escreve o arquivo no editor:

$ mkdir -p .github/workflows
$ nano .github/workflows/verificar.yml          « escreve o arquivo acima e salva
$ ls
index.html                                      « o ls comum não mostra pastas com ponto
$ ls -a
.  ..  .git  .github  index.html                « com -a, a .github aparece
$ ls .github/workflows
verificar.yml
$ git status
No ramo main
Your branch is up to date with 'origin/main'.

Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
        .github/                                « a pasta nova inteira

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)

Repare na linha do git status: o Git mostra só a pasta .github/, e não o arquivo lá dentro. Quando uma pasta inteira é nova, o Git resume assim. Para ele, o robô é um arquivo qualquer: ainda não rastreado, igual a uma receita nova.

Passo 2: commitar e enviar

O robô só passa a existir para o GitHub depois que o arquivo chega lá. Então o caminho é o de sempre: git add, git commit e git push.

$ git add .github
$ git status
No ramo main
Your branch is up to date with 'origin/main'.

Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
        new file:   .github/workflows/verificar.yml      « agora o Git mostra o arquivo

$ git commit -m 'Adiciona verificação automática do site'
[main e7e122e] Adiciona verificação automática do site
 1 file changed, 10 insertions(+)
 create mode 100644 .github/workflows/verificar.yml
$ git push
Enumerating objects: 6, done.
Counting objects: 100% (6/6), done.
Delta compression using up to 8 threads
Compressing objects: 100% (3/3), done.
Writing objects: 100% (5/5), 538 bytes | 538.00 KiB/s, done.
Total 5 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
To https://github.com/ana-souza/receitas.git
   0b71801..e7e122e  main -> main                « o robô chegou ao GitHub

Linha por linha do que importa:

  • new file: .github/workflows/verificar.yml: depois do git add .github, o Git lista cada arquivo da pasta. (Algumas frases do Git do Ubuntu ainda saem metade em inglês, como new file, "arquivo novo", e to unstage, "para tirar da área de preparo": é a tradução que vem com o Git, não um erro seu.)
  • create mode 100644 .github/workflows/verificar.yml: o commit criou o arquivo, com permissão de arquivo comum (100644).
  • 0b71801..e7e122e main -> main: o main do GitHub andou do commit antigo para o novo. A partir deste momento o GitHub "vê" a pasta .github/workflows e dispara o fluxo.

Daqui em diante, cada push para o GitHub dispara o fluxo, inclusive este push que acabou de levar o arquivo.

Passo 3: ver o resultado no site (ilustrativo)

Segundo a documentação oficial, para ver as execuções:

  1. Abra a página principal do repositório no GitHub.
  2. Clique na aba Ações (em inglês, Actions).
  3. Na barra lateral esquerda, clique no nome do fluxo, Verificar site.
  4. Na lista de execuções, clique na execução que você quer ver (o título é a mensagem do commit).
  5. Em Jobs, clique no trabalho verificar e expanda as etapas para ver a saída de cada comando, como se fosse um terminal.

Ao lado de cada execução aparece um símbolo: ✓ verde (deu tudo certo), ✗ vermelho (alguma etapa falhou) ou um círculo amarelo (ainda rodando). O mesmo símbolo aparece ao lado do commit na página do repositório e nos pull requests, e o GitHub pode mandar um e-mail quando uma execução falha.

Custa alguma coisa?

Segundo a documentação de cobrança do GitHub, o uso do GitHub Actions é grátis em repositórios públicos (com os executores padrão do GitHub). Em repositórios privados, a conta gratuita (GitHub Free) inclui uma cota de minutos por mês (2.000 minutos, na tabela da documentação quando esta aula foi escrita). Confira os valores atuais em docs.github.com/pt/billing.

Missão: a Ana baixou o arquivo verificar.yml, mas ele está solto na raiz do repositório, onde o GitHub não procura. Crie a pasta .github/workflows, mova o arquivo para lá (mv) e commite. Confira com git status e cat .github/workflows/verificar.yml.

Quando o robô reclama: reproduza no seu terminal

A melhor coisa sobre etapas com run: é que elas são comandos comuns. Se o GitHub disser que a etapa test -f index.html falhou, você pode rodar o mesmo comando no seu computador e ver o mesmo resultado. Foi o que a Ana fez quando o Bruno renomeou a página inicial para inicio.html:

$ ls
inicio.html                                     « não existe mais index.html
$ test -f index.html
$ echo $?
1                                               « 1 = falhou, igual à etapa do robô
$ git mv inicio.html index.html
$ git commit -m 'Volta o nome index.html para o robô passar'
[main c540300] Volta o nome index.html para o robô passar
 1 file changed, 0 insertions(+), 0 deletions(-)
 rename inicio.html => index.html (100%)
$ test -f index.html
$ echo $?
0                                               « 0 = passou
$ grep -q "<title>" index.html
$ echo $?
0                                               « a última etapa também passa

O $? mostra o código de saída do último comando: 1 é exatamente o que fez a etapa falhar no GitHub. A correção é desfazer o nome com git mv, commitar e enviar de novo. O próximo push dispara o fluxo outra vez, e o ✗ vira ✓.

Missão: o robô da Ana está vermelho. Rode a mesma etapa dele, test -f index.html, e veja o código com echo $?. Depois, devolva o nome index.html à página com git mv e commite, para o próximo push passar.

Quando dá errado

Fiz push, mas nada aparece na aba Ações 
$ git ls-files .github
.github/workflow/verificar.yml                  « workflow, sem o "s"!
$ git mv .github/workflow .github/workflows
$ git commit -m 'Corrige o nome da pasta dos fluxos'
[main 19b135e] Corrige o nome da pasta dos fluxos
 1 file changed, 0 insertions(+), 0 deletions(-)
 rename .github/{workflow => workflows}/verificar.yml (100%)
$ git ls-files .github
.github/workflows/verificar.yml

O que aconteceu: a pasta se chama .github/workflow (sem o s). O GitHub só procura fluxos em .github/workflows, com esse nome exato; em qualquer outro lugar, o arquivo é só um arquivo.

Como confirmar: git ls-files .github mostra o caminho exato que está no repositório.

Como resolver: renomeie com git mv .github/workflow .github/workflows, commite e faça push. Outros motivos possíveis, segundo a documentação: o Actions desativado nas configurações do repositório, ou um evento on: que não combina com o que você fez (por exemplo, on: [pull_request] e você só fez push).

O fluxo aparece com erro antes de rodar qualquer etapa (ilustrativo) 
name: Verificar site
on: [push]
jobs:
  verificar:
  runs-on: ubuntu-latest
    steps:
      - run: test -f index.html

O que aconteceu: o runs-on ficou com o mesmo recuo de verificar:, então deixou de estar "dentro" do trabalho. O arquivo não é mais um fluxo válido, e o GitHub mostra a execução como falha com um aviso sobre o arquivo de fluxo de trabalho, em vez de rodar as etapas.

Como resolver: confira o recuo linha por linha (dois espaços a cada nível), sem Tab. Editores como o VS Code destacam erros de YAML; muita gente compara com o exemplo da documentação.

O push foi recusado por falta da permissão workflow (ilustrativo) 
$ git push
…
 ! [remote rejected] main -> main (refusing to allow a Personal Access Token to create or update workflow `.github/workflows/verificar.yml` without `workflow` scope)

O que aconteceu: você envia por HTTPS com um token de acesso pessoal que não tem a permissão (scope) workflow. O GitHub protege os fluxos de propósito: um token vazado não pode criar um robô que roda comandos na sua conta. Esta mensagem vem do servidor do GitHub (por isso está em inglês) e não roda no laboratório.

Como resolver: gere um token novo marcando a permissão workflow (nos tokens clássicos) ou use SSH, que não tem essa restrição por token.

Uma etapa falhou (✗ vermelho)

O que aconteceu: um comando terminou com código diferente de 0. O registro da etapa, na aba Ações, mostra a saída do comando e a linha Error: Process completed with exit code 1. (ilustrativo).

Como resolver: rode o mesmo comando no seu terminal, como na seção acima, corrija, commite e faça push. Não há botão mágico: o robô roda de novo a cada push.

Resumo

  • O GitHub Actions roda comandos automaticamente em máquinas do GitHub quando um evento acontece (por exemplo, um push).
  • Um fluxo de trabalho é um arquivo YAML em .github/workflows/, com name, on, jobs, runs-on e steps.
  • Para o Git, o fluxo é um arquivo comum: git add, git commit, git push.
  • O resultado aparece na aba Ações: ✓ deu certo, ✗ alguma etapa terminou com código diferente de 0.
  • Etapas run: são comandos comuns: rode-os no seu terminal para entender uma falha.
  • Recuo com espaços no YAML; pasta com o nome exato; token HTTPS precisa da permissão workflow.

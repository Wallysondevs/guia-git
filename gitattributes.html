Git Fim de Linha e .gitattributes

Todo arquivo de texto tem um caractere invisível no fim de cada linha, que diz "aqui acaba a linha". O problema: o Windows usa um, o Linux e o macOS usam outro. Quando a Ana (no Linux) e o Bruno (no Windows) trabalham no mesmo repositório, isso causa diffs estranhos, com o arquivo "inteiro modificado" sem ninguém ter mudado nada, e scripts que param de funcionar. O arquivo .gitattributes resolve isso de uma vez para a equipe toda, e ainda diz ao Git quais arquivos são binários.

Você vai aprender
  • O que são LF e CRLF, e como vê-los com file, cat -A e git ls-files --eol.
  • Por que trocar o fim de linha faz o git diff mostrar o arquivo inteiro mudado.
  • Como escrever um .gitattributes: text=auto, eol=lf, eol=crlf e binary.
  • Como arrumar um repositório que já tem arquivos misturados (git add --renormalize).
  • O core.autocrlf, o jeito antigo, e o erro /bin/sh^M: interpretador incorreto.

Todas as saídas desta aula vieram do Git 2.53 do Ubuntu na máquina da Ana (usuária ana, computador notebook), com o sistema em português. Os arquivos "do Windows" foram criados com printf, escrevendo o \r\n de propósito, para imitar o que o Bloco de Notas faz.

A ideia: a máquina de escrever

Na máquina de escrever, terminar uma linha eram dois movimentos: puxar a alavanca que leva o papel de volta para a esquerda (o retorno do carro, em inglês carriage return, CR) e girar o rolo para descer uma linha (a alimentação de linha, line feed, LF).

Os computadores herdaram isso, cada um do seu jeito:

SistemaFim de linhaEscrito como
Linux, macOSLF (só desce a linha)\n
WindowsCRLF (volta e desce)\r\n

Para o Git, um arquivo é uma sequência de bytes. Se o Bruno salva Caneca\r\n e a Ana salva Caneca\n, são linhas diferentes, mesmo que na tela pareçam iguais.

1. Vendo o fim de linha

O Bruno criou a lista de produtos da lojinha no Windows. A Ana olhou o arquivo no Linux:

$ file produtos.txt
produtos.txt: ASCII text, with CRLF line terminators
$ cat -A produtos.txt
Lista de produtos^M$
Caneca^M$
Camiseta^M$
file produtos.txt
O comando file descobre o tipo do arquivo. "with CRLF line terminators" = "com fins de linha CRLF": foi feito no Windows.
cat -A
Mostra os caracteres invisíveis. O ^M é o CR (\r), e o $ marca o LF (\n). Num arquivo do Linux, cada linha terminaria só com $.

O próprio Git também mostra, com git ls-files --eol (eol = end of line, "fim de linha"), depois que o arquivo foi commitado:

$ git add produtos.txt
$ git commit -q -m 'Adiciona produtos (feito no Windows)'
$ git ls-files --eol
i/crlf  w/crlf  attr/                 	produtos.txt
i/crlf
No índice (o que o Git guardou no repositório), o arquivo tem CRLF.
w/crlf
Na pasta de trabalho (working tree, o arquivo que você abre no editor), também CRLF.
attr/
Nenhum atributo de .gitattributes vale para ele (ainda).

2. O problema: "mudou o arquivo inteiro"

A Ana abriu o produtos.txt num editor configurado para salvar com LF e salvou sem mudar nenhuma letra. (Aqui, o sed faz o mesmo que o editor dela: tira o \r do fim de cada linha.)

$ sed -i 's/\r$//' produtos.txt
$ file produtos.txt
produtos.txt: ASCII text
$ git status -s
 M produtos.txt
$ git diff
diff --git a/produtos.txt b/produtos.txt
index 495395c..4d2b0ac 100644
--- a/produtos.txt
+++ b/produtos.txt
@@ -1,3 +1,3 @@
-Lista de produtos               « tinha \r no fim
-Caneca
-Camiseta
+Lista de produtos               « agora não tem
+Caneca
+Camiseta
$ git diff --stat
 produtos.txt | 6 +++---
 1 file changed, 3 insertions(+), 3 deletions(-)

O Git diz que todas as linhas mudaram, e as linhas apagadas e as novas parecem idênticas: a diferença é o \r, que não aparece na tela. Num arquivo de 500 linhas, um commit desses esconde a mudança de verdade no meio de 500 linhas "mudadas", atrapalha o git blame e gera conflitos à toa. Para confirmar que é só fim de linha, peça ao diff para ignorar o \r:

$ git diff --ignore-cr-at-eol
$ git restore produtos.txt

Nenhuma diferença: era só o fim de linha. A Ana desfez a mudança com git restore e foi resolver direito.

3. A solução: o arquivo .gitattributes

O .gitattributes é um arquivo de texto na raiz do repositório, parecido com o .gitignore: cada linha tem um padrão de nomes e os atributos que valem para esses arquivos. Como ele é commitado, vale para todo mundo que clonar, no Linux, no Windows ou no macOS. A Ana criou este:

# Deixe o Git cuidar do fim de linha dos arquivos de texto
* text=auto
# Scripts de shell: sempre LF (senão não rodam no Linux)
*.sh text eol=lf
# Scripts do Windows: sempre CRLF
*.bat text eol=crlf
# Imagens: binário (nunca mexer no conteúdo)
*.png binary
*
O padrão: "todos os arquivos". *.sh é "todos os que terminam em .sh". Quando mais de uma linha vale para um arquivo, a de baixo ganha.
text=auto
"Git, descubra sozinho se o arquivo é texto. Se for, guarde no repositório com LF e, na pasta de trabalho, use o fim de linha do sistema." É a linha mais importante.
text eol=lf
"É texto, e na pasta de trabalho use sempre LF, até no Windows." Para scripts de shell, que não funcionam com CRLF.
text eol=crlf
"Na pasta de trabalho, sempre CRLF, até no Linux." Para arquivos que só programas do Windows leem, como o .bat.
binary
"Não é texto: nunca mexa no fim de linha, e não tente mostrar o diff linha por linha." É um atalho para -text -diff -merge.

Conferindo os atributos: git check-attr

Antes de commitar, a Ana perguntou ao Git quais atributos valem para cada arquivo. Os arquivos nem precisam existir:

$ git check-attr -a produtos.txt
produtos.txt: text: auto
$ git check-attr text eol -- instalar.sh rodar.bat logo.png
instalar.sh: text: set
instalar.sh: eol: lf
rodar.bat: text: set
rodar.bat: eol: crlf
logo.png: text: unset              « binary desligou o "text"
logo.png: eol: unspecified

-a pede todos os atributos de um arquivo; text eol pede só esses dois; o -- separa os atributos dos nomes de arquivo. set quer dizer "ligado", unset, "desligado", e unspecified, "ninguém disse nada".

Arrumando o que já foi commitado: --renormalize

O .gitattributes vale para o que entrar daqui para a frente. O produtos.txt já estava no repositório com CRLF. Para o Git reaplicar as regras em tudo que já é rastreado, use git add --renormalize . git 2.16+:

$ git add .gitattributes
$ git add --renormalize .
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	new file:   .gitattributes
	modified:   produtos.txt                 « o Git converteu para LF
$ git commit -q -m 'Normaliza fins de linha com .gitattributes'
$ git ls-files --eol
i/lf    w/lf    attr/text=auto        	.gitattributes
i/lf    w/crlf  attr/text=auto        	produtos.txt

(Algumas linhas do git status saem em inglês no Git 2.53 do Ubuntu, porque a tradução não está completa: "new file" = "arquivo novo", "modified" = "modificado".)

Repare na última linha: no repositório o produtos.txt agora tem LF (i/lf), mas o arquivo da pasta continua com CRLF (w/crlf): o Git só reescreve o arquivo da pasta quando precisa tirá-lo do repositório de novo. Para ver isso acontecer, a Ana apagou o arquivo e pediu de volta:

$ rm produtos.txt
$ git restore produtos.txt
$ git ls-files --eol
i/lf    w/lf    attr/text=auto        	.gitattributes
i/lf    w/lf    attr/text=auto        	produtos.txt
$ file produtos.txt
produtos.txt: ASCII text

Agora ele está com LF, o fim de linha do Linux. No computador do Bruno, o mesmo text=auto entrega o arquivo com CRLF, o do Windows. No repositório, fica sempre LF, e o diff "do arquivo inteiro" não acontece mais.

Crie o .gitattributes no primeiro commit

Num repositório novo, o .gitattributes com * text=auto deveria entrar junto com o .gitignore, antes de qualquer arquivo do Windows. Assim você nunca precisa do --renormalize, que gera um commit grande mexendo em muitos arquivos.

Missão: na lojinha, crie um .gitattributes com a linha *.sh text eol=lf (scripts de shell sempre com LF) e faça o commit dele.

4. Scripts de shell e o ^M

O Bruno escreveu um script de instalação no Windows e mandou para a Ana. No Linux, ele não roda:

$ chmod +x instalar.sh
$ ./instalar.sh
bash: ./instalar.sh: /bin/sh^M: interpretador incorreto: Arquivo ou diretório inexistente

"Interpretador incorreto": a primeira linha, #!/bin/sh, terminou com \r, e o Linux procurou um programa chamado /bin/sh + CR (o ^M), que não existe. Com o *.sh text eol=lf do .gitattributes, o Git avisa no add e conserta no repositório:

$ git add instalar.sh
warning: in the working copy of 'instalar.sh', CRLF will be replaced by LF the next time Git touches it
$ git commit -q -m 'Adiciona instalar.sh'
$ git ls-files --eol instalar.sh
i/lf    w/crlf  attr/text eol=lf      	instalar.sh
$ rm instalar.sh
$ git restore instalar.sh
$ ./instalar.sh
Instalando a loja
warning: in the working copy of 'instalar.sh', CRLF will be replaced by LF the next time Git touches it
"Aviso: na cópia de trabalho de instalar.sh, o CRLF será trocado por LF na próxima vez que o Git mexer nele." Não é erro: o Git já guardou com LF no repositório (i/lf) e avisa que o arquivo da pasta (w/crlf) vai mudar quando ele for reescrito.
rm + git restore
Fizeram o Git reescrever o arquivo, agora com LF. O script rodou.

No Bruno, que usa Windows, o mesmo eol=lf garante que o script sai do Git com LF, pronto para rodar num servidor Linux. O rodar.bat segue a regra contrária: o Git avisa que vai entregá-lo com CRLF.

$ git add rodar.bat
warning: in the working copy of 'rodar.bat', LF will be replaced by CRLF the next time Git touches it

5. Arquivos binários

Imagens, PDFs e planilhas não têm "linhas". O Git normalmente percebe sozinho (um arquivo com bytes nulos é tratado como binário), e o binary no .gitattributes deixa isso garantido. O diff de um binário não mostra linhas, só avisa que mudou:

$ git diff
diff --git a/logo.png b/logo.png
index d9d6533..71b06a2 100644
Binary files a/logo.png and b/logo.png differ

"Os arquivos binários a/logo.png e b/logo.png são diferentes." Num conflito de merge, o Git também não tenta juntar dois binários: você escolhe uma das versões. Se os binários forem grandes (vídeos, modelos 3D), veja Arquivos Grandes (Git LFS), que também usa o .gitattributes.

Formas diferentes de fazer a mesma coisa

Antes do .gitattributes, o jeito era a configuração core.autocrlf, que cada pessoa liga no próprio computador:

$ git config core.autocrlf true
$ git add teste.txt
warning: in the working copy of 'teste.txt', LF will be replaced by CRLF the next time Git touches it

Com true (pensado para o Windows), o Git guarda com LF e entrega com CRLF; com input (pensado para Linux e macOS), guarda com LF e não mexe na entrega. Funciona, mas depende de cada pessoa da equipe configurar certo. O .gitattributes vai no repositório e passa na frente do core.autocrlf.

SituaçãoQual usar
Qualquer repositório com gente em sistemas diferentes.gitattributes com * text=auto
Scripts que precisam de LF (.sh, Makefile)*.sh text eol=lf
Arquivos que precisam de CRLF (.bat, .cmd)*.bat text eol=crlf
Imagens, PDFs, executáveis*.png binary
Um repositório que não é seu e não tem .gitattributesgit config --global core.autocrlf true no Windows, input no Linux/macOS

Outros atributos que você vai encontrar

O .gitattributes não é só para fim de linha. export-ignore deixa um arquivo fora do git archive (o zip do projeto); filter=lfs é o que o Git LFS escreve; e o GitHub lê atributos próprios, como linguist-generated (esconde arquivos gerados no diff do pull request) e linguist-language (corrige a linguagem detectada). Esses do GitHub são ilustrativos aqui; os detalhes estão na documentação do GitHub, em docs.github.com/pt.

Quando dá errado

/bin/sh^M: interpretador incorreto 
$ ./instalar.sh
bash: ./instalar.sh: /bin/sh^M: interpretador incorreto: Arquivo ou diretório inexistente

O que aconteceu: o script tem CRLF. Como confirmar: file instalar.sh diz "with CRLF line terminators". Como resolver: ponha *.sh text eol=lf no .gitattributes, rode git add --renormalize ., commite e reescreva o arquivo (rm instalar.sh e git restore instalar.sh). Fora do Git, sed -i 's/\r$//' instalar.sh tira o \r.

O diff mostra o arquivo inteiro mudado

O que aconteceu: alguém salvou com outro fim de linha. Como confirmar: git diff --ignore-cr-at-eol não mostra nada (ou mostra só a mudança de verdade). Como resolver: se a mudança ainda não foi commitada, git restore arquivo; para o futuro, o .gitattributes com * text=auto.

"Criei o .gitattributes e nada mudou"

O que aconteceu: o .gitattributes só vale para o que o Git guardar ou reescrever depois dele. Como confirmar: git ls-files --eol ainda mostra i/crlf. Como resolver: git add --renormalize . e commit. E confira os padrões com git check-attr -a arquivo: um erro de digitação no padrão faz a linha não valer para nada.

"warning: … LF will be replaced by CRLF"

Não é erro. O Git está avisando que, por causa do .gitattributes ou do core.autocrlf, o arquivo da pasta vai mudar de fim de linha na próxima vez que ele for reescrito. O commit foi feito normalmente.

Resumo

  • Linux e macOS terminam as linhas com LF (\n); o Windows, com CRLF (\r\n). Para o Git, são linhas diferentes.
  • Veja com file, cat -A (o ^M) e git ls-files --eol.
  • .gitattributes com * text=auto: LF no repositório, o fim de linha de cada sistema na pasta. eol=lf para scripts de shell, eol=crlf para .bat, binary para imagens.
  • Arquivos já commitados: git add --renormalize ..
  • core.autocrlf é o jeito antigo, por pessoa; o .gitattributes vale para a equipe toda.

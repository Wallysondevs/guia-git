Git restore git 2.23+

A Ana mexeu na receita de bolo, testou, e o bolo virou uma pedra: 12 ovos e sal. Ela quer o arquivo de volta exatamente como estava no último commit. Sem Git, seria apagar linha por linha tentando lembrar do original. Com Git, é um comando: git restore bolo.txt (restore = "restaurar"). Ele também traz de volta arquivos apagados e versões de commits antigos.

Você vai aprender
  • A descartar as mudanças de um arquivo com git restore arquivo (e por que isso não tem volta).
  • A recuperar um arquivo apagado sem querer.
  • A restaurar vários arquivos de uma vez (. e '*.txt') ou só alguns trechos (-p).
  • A pegar a versão de um commit antigo com --source.
  • O que o git restore faz quando o arquivo também está na área de preparo, e o comando antigo, git checkout -- arquivo.

Todas as saídas desta aula saíram do Git do Ubuntu 26.04 (Git 2.53), na máquina da Ana (usuária ana, computador notebook), com o sistema em português. Algumas mensagens do Git ainda não têm tradução e saem em inglês. O git restore existe desde o Git 2.23 (de 2019); se o seu Git for mais antigo, use o git checkout -- arquivo da seção 7.

A ideia: o "voltar ao salvo" do videogame

Num videogame, você salva antes de enfrentar o chefão. Se tudo dá errado, você carrega o jogo salvo e volta àquele ponto, como se a luta desastrosa nunca tivesse acontecido. O commit é o jogo salvo; o git restore é o "carregar".

E, como no videogame, o que você fez depois de salvar se perde. As mudanças descartadas pelo git restore nunca foram commitadas, então o Git não tem cópia delas. Antes de restaurar, sempre olhe o que vai perder com git diff.

1. Descartando as mudanças de um arquivo

A versão commitada do bolo.txt tem 4 linhas. A Ana mexeu, e o git status e o git diff mostram o estrago:

$ git status
No ramo main
Changes not staged for commit:
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   bolo.txt

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
$ git diff
diff --git a/bolo.txt b/bolo.txt
index 2fc5146..73525db 100644
--- a/bolo.txt
+++ b/bolo.txt
@@ -1,4 +1,4 @@
 Bolo de cenoura
 3 cenouras
-4 ovos
-2 xícaras de farinha
+12 ovos
+sal a gosto

Repare na segunda dica do git status: (use "git restore <file>..." to discard changes in working directory), "use git restore para descartar as mudanças na pasta de trabalho". É exatamente o que a Ana quer:

$ git restore bolo.txt
$ cat bolo.txt
Bolo de cenoura
3 cenouras
4 ovos
2 xícaras de farinha
$ git status
No ramo main
nothing to commit, working tree clean
git restore
O comando: "restaure".
bolo.txt
O arquivo a restaurar. Sem outras opções, o git restore copia a versão da área de preparo por cima do arquivo da pasta. Como a Ana não tinha dado git add, a área de preparo tem a versão do último commit.

O git restore não mostra nada quando dá certo. O cat mostra a receita original, e o git status diz nothing to commit, working tree clean ("nada a submeter, pasta de trabalho limpa"; esta frase ainda não tem tradução). Os 12 ovos sumiram para sempre.

Não há "desfazer o restore"

As mudanças descartadas não vão para lixeira nenhuma: o Git nunca as guardou. Se você não tem certeza, em vez de descartar, guarde-as com um commit num branch à parte ou com o git stash. E sempre confira antes com git diff arquivo o que vai embora.

Missão: o bolo.txt foi estragado. Veja o que mudou com git diff e devolva o arquivo ao último commit com git restore. Confira com cat bolo.txt e git status.

2. Recuperando um arquivo apagado

Apagar um arquivo também é uma "mudança na pasta", e o git restore desfaz:

$ rm pudim.txt
$ ls
bolo.txt
$ git status
No ramo main
Changes not staged for commit:
  (utilize "git add/rm <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	deleted:    pudim.txt

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
$ git restore pudim.txt
$ ls
bolo.txt  pudim.txt
$ cat pudim.txt
Pudim de leite
1 lata de leite condensado
3 ovos

O pudim voltou, com o conteúdo do último commit. Isso vale para qualquer arquivo que o Git rastreia, apagado pelo rm, pela lixeira ou pelo editor. (Se a remoção foi feita com git rm, ela também está preparada, e é preciso desfazer nos dois lugares: veja a seção 6.)

3. Vários arquivos de uma vez

Como o git add, o git restore aceita vários nomes, uma pasta ou um padrão:

$ echo 'linha estragada' >> bolo.txt
$ echo 'linha estragada' >> pudim.txt
$ git status --short
 M bolo.txt
 M pudim.txt
$ git restore .
$ git status --short
$

O . quer dizer "a pasta atual e tudo dentro dela". Com um padrão entre aspas, como git restore '*.txt', só os arquivos que casam são restaurados (o Git expande o * entre os arquivos que ele rastreia, inclusive em subpastas).

git restore . é uma borracha grande

Ele descarta todas as mudanças não preparadas de todos os arquivos rastreados da pasta, de uma vez. Rode git status e git diff antes. Arquivos novos (não rastreados) não são afetados; para eles existe o git clean.

A pergunta (1/2) Discard this hunk from worktree quer dizer "(trecho 1 de 2) descartar este trecho da pasta de trabalho?". As respostas principais: y (yes, sim: descarta), n (no, não: mantém), q (quit: para de perguntar), a (descarta este e todos os seguintes do arquivo), d (não descarta nenhum dos seguintes) e ? (mostra a ajuda com todas as letras). A Ana respondeu y para a caneca e n para o frete: o git diff seguinte mostra que só sobrou a mudança boa. (Os trechos são os mesmos @@ da aula git diff.)

4. Pegando a versão de um commit antigo: --source

Por padrão, o git restore busca o conteúdo na área de preparo (que, sem git add, é igual ao último commit). Com --source ("origem"), você escolhe de qual commit pegar. A Ana commitou a mudança de 4 para 3 ovos e agora quer reconsiderar:

$ git log --oneline
8b163ca Menos ovos no bolo
9d54245 Receitas iniciais
$ git restore --source=HEAD~1 bolo.txt
$ cat bolo.txt
Bolo de cenoura
3 cenouras
4 ovos
2 xícaras de farinha
$ git status --short
 M bolo.txt
$ git diff
diff --git a/bolo.txt b/bolo.txt
index c8726b3..2fc5146 100644
--- a/bolo.txt
+++ b/bolo.txt
@@ -1,4 +1,4 @@
 Bolo de cenoura
 3 cenouras
-3 ovos
+4 ovos
 2 xícaras de farinha
--source=HEAD~1
"Pegue o conteúdo do commit HEAD~1": o commit anterior ao último (HEAD é o último; o ~1 quer dizer "um para trás"; veja O que é HEAD). Também vale o hash: --source=9d54245. A forma curta é -s HEAD~1.

O arquivo da pasta ficou como no commit antigo, mas o histórico não mudou: o commit Menos ovos no bolo continua lá. Para o Git, é só uma mudança nova na pasta ( M), e o diff mostra a volta dos 4 ovos. Se a Ana gostar, faz git add e um commit novo; se não gostar, git restore bolo.txt volta ao último commit. É uma forma segura de "voltar no tempo" com um arquivo só, sem mexer no histórico.

Recuperando um arquivo apagado num commit

Se a remoção já foi commitada, o arquivo não está mais no último commit, e o git restore simples não o encontra. Mas ele existe no commit de antes:

$ git rm -q promocao.txt
$ git commit -q -m 'Fim da promoção'
$ git restore promocao.txt
error: pathspec 'promocao.txt' did not match any file(s) known to git
$ git restore --source=HEAD~1 promocao.txt
$ git status --short
 M produtos.txt
?? promocao.txt
$ cat promocao.txt
promo

O promocao.txt voltou para a pasta como um arquivo novo (??), porque no último commit ele não existe. Se quiser que ele volte ao projeto, git add e commit. (O M produtos.txt é a mudança do frete, que ficou pendente da seção 3.)

5. Quando o arquivo também está na área de preparo

Lembre: sem opções, o git restore copia a versão da área de preparo para a pasta. Quando o arquivo tem uma parte preparada e outra não, isso faz diferença:

$ echo 'Mudança A' >> bolo.txt
$ git add bolo.txt
$ echo 'Mudança B' >> bolo.txt
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt

Changes not staged for commit:
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   bolo.txt

Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	lasanha.txt

$ git restore bolo.txt
$ cat bolo.txt
Bolo de cenoura
3 cenouras
3 ovos
2 xícaras de farinha
Mudança A
$ git status --short
M  bolo.txt
?? lasanha.txt

A Mudança B (não preparada) sumiu, mas a Mudança A (preparada) ficou: o git restore só descartou o que não estava na área de preparo. O M na primeira coluna confirma que a Mudança A continua pronta para o commit. (A lasanha.txt é um arquivo novo da Ana, que o git restore não toca.)

Descartando tudo: --staged --worktree

Para voltar ao último commit nos dois lugares (área de preparo e pasta), diga isso ao git restore:

$ git restore --staged --worktree bolo.txt
$ cat bolo.txt
Bolo de cenoura
3 cenouras
3 ovos
2 xícaras de farinha
$ git status --short
?? lasanha.txt
--staged
(ou -S) Restaura a área de preparo, copiando o último commit para ela. Sozinho, é o "tirar da área de preparo" da próxima aula, Tirando da Área de Preparo.
--worktree
(ou -W) Restaura a pasta de trabalho (working tree). É o que o git restore faz quando você não diz nada.
juntos
As duas coisas: a Mudança A e qualquer outra mudança no arquivo se vão. Forma curta: git restore -SW bolo.txt.

6. Desfazendo um git rm

O git rm (aula git rm) apaga da pasta e prepara a remoção. Para desfazer antes do commit, restaure os dois lugares: git restore --staged --worktree arquivo. Na aula do git rm você vê isso passo a passo.

7. O comando antigo: git checkout -- arquivo

Antes do Git 2.23, o jeito de descartar mudanças era o git checkout, e você ainda vai vê-lo em muitos tutoriais:

$ printf '3 cenouras\n4 ovos\n' > bolo.txt
$ git checkout -- bolo.txt
$ git status --short
?? lasanha.txt
$ cat bolo.txt
Bolo de cenoura
3 cenouras
3 ovos
2 xícaras de farinha

Mesmo efeito do git restore bolo.txt. O -- separa as opções do nome do arquivo, e é importante aqui: o git checkout também troca de branch (git checkout main), e sem o -- um arquivo com o mesmo nome de um branch confundiria o comando. Foi para acabar com essa confusão que o Git criou o git restore (só arquivos) e o git switch (só branches). Veja git checkout: o Comando Antigo.

Quando dá errado

error: pathspec '…' did not match any file(s) known to git 
$ echo 'Lasanha' > lasanha.txt
$ git restore lasanha.txt
error: pathspec 'lasanha.txt' did not match any file(s) known to git
$ git restore nada.txt
error: pathspec 'nada.txt' did not match any file(s) known to git

"O caminho não corresponde a nenhum arquivo conhecido pelo Git" (esta mensagem ainda não tem tradução). Três causas: o nome está errado (nada.txt); o arquivo é novo e nunca foi commitado (lasanha.txt: não existe "versão anterior" para restaurar); ou ele foi apagado num commit (use --source, seção 4). Como resolver: confira o nome com git status; para apagar um arquivo novo, use o rm comum ou o git clean.

Num repositório sem nenhum commit 
$ git init -q
$ echo oi > a.txt
$ git restore a.txt
error: pathspec 'a.txt' did not match any file(s) known to git

Sem commit e sem git add, o Git não conhece nenhuma versão do arquivo. Não há para onde "voltar".

"Rodei git restore e a mudança não saiu"

A mudança provavelmente estava preparada (seção 5): o git restore sozinho copia a área de preparo para a pasta, e a mudança está justamente lá. Como confirmar: git status mostra o arquivo em Mudanças a serem submetidas. Como resolver: git restore --staged --worktree arquivo.

"Descartei sem querer!"

O Git não tem cópia de mudanças que nunca foram preparadas nem commitadas. Tente o Ctrl+Z do editor (se o arquivo ainda estiver aberto nele) ou o histórico local do editor. Se você tinha dado git add antes, e depois o git restore --staged --worktree apagou também a área de preparo, o conteúdo ainda pode estar nos objetos internos do Git por um tempo, mas a recuperação é trabalhosa (assunto avançado; veja Recuperando Commits Perdidos). Moral: commits frequentes.

Resumo

  • git restore arquivo descarta as mudanças não preparadas e devolve o arquivo à versão da área de preparo (sem git add, a do último commit). Também recupera arquivos apagados.
  • As mudanças descartadas não têm volta: confira com git diff antes.
  • git restore . restaura tudo; -p pergunta trecho por trecho.
  • --source=COMMIT pega a versão de um commit antigo, sem mexer no histórico.
  • --staged --worktree volta ao último commit nos dois lugares; --staged sozinho só tira da área de preparo (próxima aula).
  • Em tutoriais antigos: git checkout -- arquivo.

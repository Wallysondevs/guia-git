Git rebase

A Ana criou um branch para a receita de pudim. Enquanto ela trabalhava nele, o main andou: entrou a receita de pão de queijo. Agora os dois caminhos estão separados. Você já conhece um jeito de juntá-los: o git merge, que cria um commit de junção. O git rebase é o outro jeito: ele muda a base do branch, como se a Ana tivesse começado o pudim depois do pão de queijo. O resultado é um histórico em linha reta, sem o "galho" e sem commit de junção.

Você vai aprender
  • O que quer dizer "base" de um branch e o que o git rebase main faz com ela.
  • Como ler o histórico antes e depois com git log --oneline --graph --all.
  • Por que os commits ganham hashes novos no rebase (e por que isso importa).
  • Como levar o branch para o main depois do rebase: o merge fast-forward.
  • Os erros reais mais comuns e como sair deles.

Todos os comandos desta aula rodaram no Git 2.53 da máquina da Ana (usuária ana, computador notebook), com o sistema em português. Algumas mensagens do rebase saem em inglês, porque a tradução do Git do Ubuntu não cobre todas: cada uma está traduzida no texto.

A ideia: replantar a muda

Imagine um galho que nasceu do tronco de uma árvore. Enquanto o galho crescia, o tronco também cresceu, para cima. O jardineiro corta o galho e o replanta mais alto, no topo do tronco atual. O galho é o mesmo (as mesmas folhas, na mesma ordem), mas agora ele sai do ponto mais novo do tronco.

No Git, o tronco é o main, o galho é o seu branch, e o ponto onde o galho nasceu é a base do branch. Antes do rebase, desenhado de lado:

          D---E   pudim
         /
A---B---C         main

O pudim nasceu do commit B; depois disso, o main ganhou o C. O git rebase main, rodado no pudim, refaz o D e o E em cima do C:

A---B---C---D'---E'   pudim
        ↑
       main

Repare nos apóstrofos: D' e E' têm as mesmas mudanças e as mesmas mensagens do D e do E, mas são commits novos. É isso que "reescrever o histórico" quer dizer, e é por isso que esta aula abre o grupo "Reescrevendo o Histórico".

1. A situação: dois caminhos separados

A Ana fez dois commits no branch pudim. Depois voltou ao main e commitou a receita de pão de queijo. Agora, de volta ao pudim, ela olha o desenho de todos os branches (aula Vendo os Galhos):

$ git switch pudim
Switched to branch 'pudim'
$ git log --oneline --graph --all --decorate
* c07c3d1 (main) Adiciona receita de pão de queijo
| * d2f91d9 (HEAD -> pudim) Acrescenta a calda do pudim
| * d08fcd4 Adiciona receita de pudim
|/
* 934a161 Adiciona receita de bolo                « a base do pudim: onde o galho nasceu
* f0c33ea Primeiro commit
  • A linha da esquerda é o main: f0c33ea → 934a161 → c07c3d1.
  • A da direita (depois do |) é o pudim, com os dois commits dele. O |/ mostra onde ele saiu do main: do 934a161.
  • (HEAD -> pudim): a Ana está no pudim (aula O que é HEAD).
  • O pudim não tem o pao.txt: ele nasceu antes da receita de pão de queijo existir.

2. O rebase

$ git rebase main
Successfully rebased and updated refs/heads/pudim.
git rebase
"Mudar a base". Sempre age sobre o branch atual (aqui, o pudim).
main
A nova base: o branch em cima do qual os commits vão ser refeitos. Em inglês, a documentação chama esse argumento de upstream.

A mensagem quer dizer "rebase feito com sucesso; o refs/heads/pudim (o branch pudim) foi atualizado". Por baixo, o Git fez três coisas:

  1. Separou os commits do pudim que o main não tem: d08fcd4 e d2f91d9.
  2. Foi para o último commit do main (c07c3d1).
  3. Refez os dois commits, um de cada vez, na ordem, em cima dele, e moveu o pudim para o último.

Se a saída não for para um terminal (num script, por exemplo), aparece também o progresso, um commit por vez: Rebasing (1/2)Rebasing (2/2)Successfully rebased…. No terminal, esse contador é apagado da tela assim que termina, e sobra só a última frase.

O histórico depois:

$ git log --oneline --graph --all --decorate
* 7b4845b (HEAD -> pudim) Acrescenta a calda do pudim     « era d2f91d9
* 55ba953 Adiciona receita de pudim                        « era d08fcd4
* c07c3d1 (main) Adiciona receita de pão de queijo         « a nova base
* 934a161 Adiciona receita de bolo
* f0c33ea Primeiro commit
$ ls
README.md
bolo.txt
pao.txt
pudim.txt
  • Uma linha só: o galho sumiu. O pudim agora sai do c07c3d1, o commit mais novo do main.
  • Os dois commits do pudim têm hashes novos (55ba953 e 7b4845b). As mensagens são as mesmas.
  • O pao.txt apareceu na pasta: o pudim agora contém tudo o que o main tem, mais as duas receitas dele.
  • O main não mudou: continua no c07c3d1. O rebase só mexe no branch atual.

Por que os hashes mudaram?

O hash de um commit é calculado a partir de tudo o que ele guarda: os arquivos, a mensagem, o autor, a data e o commit pai (aula O Hash do Commit). O d08fcd4 tinha como pai o 934a161; o novo commit tem como pai o c07c3d1. Mudou o pai, muda o hash: é outro commit. Os antigos (d08fcd4 e d2f91d9) não foram apagados na hora; só ficaram sem branch apontando para eles. O diário do HEAD mostra o rebase passo a passo (aula git reflog):

$ git reflog -4
7b4845b HEAD@{0}: rebase (finish): returning to refs/heads/pudim     « 4) volta ao pudim, que agora aponta para cá
7b4845b HEAD@{1}: rebase (pick): Acrescenta a calda do pudim          « 3) refez o 2º commit
55ba953 HEAD@{2}: rebase (pick): Adiciona receita de pudim            « 2) refez o 1º commit
c07c3d1 HEAD@{3}: rebase (start): checkout main                       « 1) começou indo para o main

Leia de baixo para cima. Cada pick ("pegar") é um commit refeito. Se você se arrepender do rebase, o d2f91d9 ainda está lá no reflog, alguns passos acima.

Hash novo = commit novo: cuidado com o que já foi enviado

Se o branch já estava no GitHub e alguém já baixou os commits antigos, o rebase cria uma versão diferente da história. O git push comum vai ser recusado, e quem tinha os antigos fica com dois históricos misturados. Por isso a regra: faça rebase só em commits que ainda não foram enviados (ou num branch só seu). A aula A Regra de Ouro explica em detalhe, e a push --force-with-lease mostra como enviar com segurança quando precisar.

Missão: você está no branch pudim, e o main andou desde que ele nasceu. Veja os dois caminhos com git log --oneline --graph --all, faça o rebase do pudim em cima do main e olhe o desenho de novo: tem de ficar uma linha só, e o pao.txt tem de aparecer no ls.

3. Levando o branch para o main: o fast-forward

O rebase arrumou o pudim, mas o main ainda não tem o pudim. Agora o pudim está exatamente "na frente" do main, na mesma linha. Então o merge não precisa juntar nada: basta avançar o main (aula Merge Fast-forward):

$ git switch main
Switched to branch 'main'
$ git merge pudim
Updating c07c3d1..7b4845b
Fast-forward                                « "avanço rápido": só moveu o main para a frente
 pudim.txt | 2 ++
 1 file changed, 2 insertions(+)
 create mode 100644 pudim.txt
$ git log --oneline --graph --decorate
* 7b4845b (HEAD -> main, pudim) Acrescenta a calda do pudim
* 55ba953 Adiciona receita de pudim
* c07c3d1 Adiciona receita de pão de queijo
* 934a161 Adiciona receita de bolo
* f0c33ea Primeiro commit

Nenhum commit de junção: o main e o pudim apontam para o mesmo commit, e o histórico é uma linha reta, fácil de ler. Essa dupla, rebase no branch + merge fast-forward no main, é o jeito mais comum de usar o rebase no dia a dia.

Missão completa: faça o rebase do pudim sobre o main, volte ao main e traga o pudim com um merge. O git merge tem de dizer Fast-forward, e o último commit do main tem de ser o do pudim.

Quando dá errado

fatal: invalid upstream 'mian' 
$ git rebase mian
fatal: invalid upstream 'mian'

"Base inválida: mian". O Git não achou nenhum branch (nem commit) com esse nome: foi um erro de digitação. Nada mudou. Como confirmar: git branch lista os nomes certos. Como resolver: git rebase main.

cannot rebase: You have unstaged changes 
$ git rebase main
error: cannot rebase: You have unstaged changes.
error: Please commit or stash them.
$ git status --short
 M bolo.txt
?? brigadeiro.txt

"Não dá para fazer o rebase: há mudanças fora da área de preparo. Faça um commit delas ou guarde-as com stash." O rebase vai trocar os arquivos da pasta várias vezes, e o Git se recusa a fazer isso por cima de uma mudança não salva (o M do bolo.txt). O arquivo novo (??, não rastreado) não atrapalha. Como resolver: faça o commit da mudança, ou guarde-a com git stash (aula git stash), rode o rebase e depois traga de volta com git stash pop.

Current branch … is up to date: nada aconteceu 
$ git rebase main
Current branch pudim is up to date.

"O branch atual, pudim, já está em dia." Ele já sai do último commit do main: não há nada para replantar. Isso também aparece quando você roda o rebase estando no próprio main (Current branch main is up to date.): você mudou a base do main para… o main. Confira em que branch está com git status.

Se o main que você esperava ver tem commits novos no GitHub, lembre que o rebase usa o main do seu computador: traga as novidades antes (aula git pull).

O rebase parou no meio com CONFLICT

Se o seu branch e o main mudaram a mesma linha do mesmo arquivo, o Git para no commit que deu problema e espera você resolver. É assunto da próxima aula: Conflitos no Rebase. Para desistir e voltar exatamente para onde estava: git rebase --abort.

Resumo

  • git rebase main refaz os commits do branch atual, um a um, em cima do último commit do main: muda a base do branch.
  • O resultado é um histórico em linha reta; depois, um git merge no main é só um fast-forward.
  • Os commits refeitos têm hashes novos (o pai mudou). Os antigos ficam no git reflog por um tempo.
  • Só faça rebase de commits que ainda não foram compartilhados.
  • Erros comuns: nome errado (invalid upstream), mudanças não salvas (cannot rebase: You have unstaged changes), nada a fazer (is up to date). Para desistir no meio: git rebase --abort.

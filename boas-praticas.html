Git Boas Práticas

O Git deixa você fazer quase tudo de quase qualquer jeito. Mas, seis meses depois, a Ana vai abrir o histórico do site de receitas para descobrir quando o bolo começou a dar errado, e o Bruno vai precisar entender o que ela fez sem perguntar. É aí que as boas práticas pagam a conta. Esta aula reúne as principais, sempre com o porquê e com um exemplo real, e aponta a aula de cada assunto para você se aprofundar.

Você vai aprender
  • Como fazer commits pequenos e de um assunto só, mesmo quando você mexeu em várias coisas.
  • O que é uma boa mensagem de commit, e por que asdf e final2 custam caro.
  • O hábito de conferir (git status, git diff --staged) antes de cada commit.
  • O que nunca deve entrar no repositório, e como o .gitignore ajuda.
  • As regras de convivência com outras pessoas: branches, pull, push e histórico público.

A ideia: um caderno que outra pessoa vai ler

Pense no histórico do Git como o caderno de receitas da família, que passa de mão em mão. Se cada página tiver uma receita só, com título claro ("Bolo de cenoura da vó"), qualquer um acha o que quer. Se as páginas tiverem três receitas misturadas e títulos como "coisas", "mais coisas" e "agora vai", o caderno existe, mas não serve para nada.

Quem vai ler o seu histórico é, quase sempre, você mesmo no futuro. As práticas abaixo são gentilezas com essa pessoa.

1. Um commit = um assunto

Um commit deve contar uma mudança completa: "adiciona a farinha ao bolo", não "farinha + README + conserto do pudim". Por quê?

  • Se a mudança der problema, você desfaz só ela com git revert, sem levar o resto junto.
  • O git bisect aponta o commit culpado; se o commit tem um assunto só, o culpado fica óbvio.
  • Quem revisa o seu pull request entende cada passo.

Na prática, você vai mexer em várias coisas ao mesmo tempo, e tudo bem: o segredo é a área de preparo. Você escolhe o que entra em cada commit. A Ana mexeu no bolo e no README:

$ git status
No ramo main
Changes not staged for commit:
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   README.md                  « assunto 1: a descrição do site
	modified:   bolo.txt                   « assunto 2: a receita

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
$ git add bolo.txt                              « só o bolo
$ git commit -m 'Adiciona a farinha à receita de bolo'
[main 69e7cac] Adiciona a farinha à receita de bolo
 1 file changed, 1 insertion(+)
$ git add README.md                             « agora o README
$ git commit -m 'Descreve o site no README'
[main 6cf7a44] Descreve o site no README
 1 file changed, 1 insertion(+)
$ git log --oneline
6cf7a44 Descreve o site no README
69e7cac Adiciona a farinha à receita de bolo
14654f8 Corrige a quantidade de ovos do pudim
fcea9c3 Adiciona receita de pudim
44f770a Cria o README e a receita de bolo

Dois commits, cada um com um assunto. Se as duas mudanças estivessem no mesmo arquivo, o git add -p deixaria você escolher pedaço por pedaço (veja git add).

Missão: a Ana mudou o bolo.txt e o README.md. Faça dois commits, um para cada assunto: primeiro o do bolo, depois o do README, com mensagens claras. Confira com git log --oneline e git show --stat.

2. Mensagens que explicam

Compare dois históricos reais, do laboratório:

$ git log --oneline
69115fb final2
d485feb agora vai
d952ff8 mudanças
098d740 asdf
9814226 arrumei
$ git log --oneline
14654f8 Corrige a quantidade de ovos do pudim
fcea9c3 Adiciona receita de pudim
44f770a Cria o README e a receita de bolo

No primeiro, para saber o que cada commit fez, só abrindo um por um. No segundo, o git log --oneline já é a história do projeto. As regras de bolso (detalhadas em Boas Mensagens de Commit):

  • Verbo no imperativo ou no presente, completando a frase "este commit…": "Adiciona", "Corrige", "Remove".
  • Uma primeira linha curta (até uns 50 caracteres), que diz o quê; se precisar, uma linha em branco e um parágrafo com o porquê.
  • Se a equipe usa um padrão, como os Conventional Commits (feat:, fix:), siga o padrão.

3. Confira antes de commitar

O git status diz quais arquivos vão entrar; o git diff --staged diz o que mudou dentro deles. Juntos, levam cinco segundos e evitam a maioria dos acidentes. Veja o que a conferência pegou:

$ git add .
$ git diff --staged
diff --git a/bolo.txt b/bolo.txt
index 3b56571..0c9fbf0 100644
--- a/bolo.txt
+++ b/bolo.txt
@@ -1,3 +1,4 @@
 Bolo de cenoura
 - 3 cenouras
 - 2 xícaras de farinha
+- 1 colher de fermento                          « isto era para entrar
diff --git a/busca.js b/busca.js
new file mode 100644
index 0000000..f7bda0a
--- /dev/null
+++ b/busca.js
@@ -0,0 +1 @@
+console.log("teste")                           « isto não: era um teste
$ git restore --staged busca.js                 « tira o teste da área de preparo
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt                   « só o que interessa vai para o commit

Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	busca.js

O git add . pegou tudo, inclusive um arquivo de teste. A conferência mostrou, e o git restore --staged o tirou da área de preparo sem apagar nada. Por isso, cuidado com atalhos que pulam a conferência, como git commit -a e git add . seguido direto de commit.

4. O que nunca entra no repositório

Não commitePor quêO que fazer
Senhas, tokens, chaves (.env, credenciais.txt)Quem tiver o repositório tem a senha, para sempre no histórico..gitignore + um .env.exemplo sem senha. Se aconteceu: Commitei uma Senha!
Arquivos gerados (*.log, node_modules/, build/, *.class)Podem ser recriados a qualquer momento; só incham o repositório e causam conflitos..gitignore (há modelos em Modelos de .gitignore).
Arquivos do seu computador (.DS_Store, Thumbs.db, configurações do editor)Não têm a ver com o projeto.Um .gitignore global (veja Configurações Úteis).
Arquivos grandes (vídeos, bancos de dados, ZIPs)Cada versão fica para sempre no histórico, e todo clone baixa tudo.Deixe fora, ou use o Git LFS.

O melhor momento para o .gitignore é antes do primeiro git add: o .gitignore não tira do Git o que já foi commitado. Veja o efeito na lista curta do git status (--short, em que ?? quer dizer "não rastreado"):

$ git status --short
?? .env                                         « a chave da API
?? busca.js
?? debug.log                                    « um log de erro
$ printf '*.log\n.env\n' > .gitignore
$ git status --short
?? .gitignore                                   « o .env e o log sumiram da lista
?? busca.js

Missão: a lojinha da Ana ainda não tem nenhum commit. Antes do primeiro, crie um .gitignore que ignore os arquivos .log e o .env. Depois, faça o primeiro commit com o index.html e o .gitignore. Use git status --short para conferir que só eles vão entrar.

Formas diferentes: o mínimo × o completo

Ninguém precisa seguir tudo no primeiro dia. Uma sugestão de por onde começar:

NívelHábitos
Primeira semanagit status antes de tudo; mensagens claras; .gitignore no primeiro commit; nada de senhas.
Primeiro mêsCommits de um assunto só (git add arquivo, git add -p); git diff --staged antes do commit; pull antes, push sempre.
Trabalhando em equipeBranch por tarefa e pull request; nada de reescrever o que é público; --force-with-lease; tags nas versões; um padrão de mensagens combinado.

Quando dá errado

Commitei duas coisas juntas

O que aconteceu: o último commit misturou assuntos.

Como resolver: se ainda não fez push, desfaça só o commit mantendo as mudanças (git reset HEAD~1, veja os modos do reset) e refaça em dois commits, como na seção 1. Se já fez push, deixe como está: reescrever histórico público é pior que um commit misturado.

Coloquei no .gitignore, mas o arquivo continua aparecendo

O que aconteceu: o arquivo já tinha sido commitado; o .gitignore só vale para arquivos não rastreados.

Como resolver: git rm --cached arquivo e um commit (veja .gitignore). Se era uma senha, siga Commitei uma Senha!.

A mensagem do último commit ficou ruim

Como resolver: antes do push, git commit --amend -m 'Mensagem melhor' (veja --amend). Depois do push, deixe estar e capriche na próxima.

Resumo

  • Um commit, um assunto: use a área de preparo para separar (git add arquivo, git add -p).
  • Mensagens claras, no imperativo, que digam o quê (e, se preciso, o porquê).
  • git status e git diff --staged antes de cada commit.
  • .gitignore antes do primeiro commit; senhas, arquivos gerados e grandes ficam fora.
  • Branch por tarefa, pull antes, push sempre, tags nas versões.
  • Não reescreva o que é público; se precisar forçar, --force-with-lease.

Git Projeto: Salvando o Dia com reflog

Sexta-feira, fim de tarde. A Ana quer jogar fora uma linha de rascunho que escreveu no index.html, lembra de um comando que viu num fórum, digita rápido… e três receitas somem do histórico. Depois, para piorar, ela apaga um branch inteiro achando que era outro. Parece o fim do mundo, mas não é: o Git tem um diário onde anota cada passo que o HEAD deu, o git reflog. Neste projeto você vê os dois desastres acontecerem, com as saídas reais, e salva o dia junto com a Ana.

Você vai aprender (na prática)
  • O que é o reflog e como ler cada linha dele (HEAD@{0}, HEAD@{1}…).
  • Desfazer um git reset --hard errado, voltando o branch para onde estava.
  • Recuperar um branch apagado com git branch -D.
  • O que o reflog não salva: mudanças que nunca foram commitadas.

Este projeto põe em prática O Diário do HEAD (git reflog), git reset e Recuperando Commits Perdidos. As saídas saíram do Git 2.53 do Ubuntu, na máquina da Ana, com o sistema em português.

A ideia: o histórico do navegador

Você fecha sem querer a aba de uma receita que estava lendo. Ela sumiu da tela, mas o navegador guarda o histórico: "às 18h02 você estava nesta página, às 18h05 naquela". É só procurar e abrir de novo.

O reflog é o histórico do navegador do Git. Cada vez que o HEAD se move (um commit, uma troca de branch, um reset, um merge), o Git anota numa linha: para onde ele foi e por quê. Os commits "sumidos" continuam guardados dentro do repositório; o que sumiu foi só a etiqueta que apontava para eles. O reflog mostra onde eles estão.

SituaçãoO reflog salva?
Commits "sumidos" depois de um reset --hardSim
Branch apagado com git branch -DSim
Commit substituído por um --amend ou perdido num rebaseSim
Mudança que nunca foi commitada e foi descartadaNão: o Git nunca a guardou

O ponto de partida

O repositório ~/receitas tem cinco commits: README, página inicial e três receitas.

$ git log --oneline
a939be6 (HEAD -> main) Adiciona a receita de brigadeiro
71692df Adiciona a receita de pudim
33cecd7 Adiciona a receita de bolo
4f5e50e Cria a página inicial
700bbd5 Cria o README

Desastre 1: o reset --hard errado

A Ana escreveu "rascunho" no fim do index.html e quer jogar essa linha fora. No fórum, alguém disse "use git reset --hard". Ela acrescentou um HEAD~3 por conta própria, achando que era "desfazer as últimas 3 linhas":

$ echo 'rascunho' >> index.html
$ git reset --hard HEAD~3
HEAD is now at 4f5e50e Cria a página inicial
$ git log --oneline
4f5e50e (HEAD -> main) Cria a página inicial      « cadê as receitas?!
700bbd5 Cria o README
$ ls
README.md  index.html
  • HEAD is now at 4f5e50e Cria a página inicial: "o HEAD agora está em 4f5e50e". O HEAD~3 quer dizer "três commits antes do atual": o main voltou três commits.
  • O git log só mostra dois commits. O ls confirma: bolo.txt, pudim.txt e brigadeiro.txt sumiram da pasta.

Ela queria o git restore index.html (veja git restore). Mas calma: não faça mais nada antes de olhar o reflog.

Lendo o diário

$ git reflog
4f5e50e (HEAD -> main) HEAD@{0}: reset: moving to HEAD~3      « o desastre
a939be6 HEAD@{1}: commit: Adiciona a receita de brigadeiro      « logo antes dele
71692df HEAD@{2}: commit: Adiciona a receita de pudim
33cecd7 HEAD@{3}: commit: Adiciona a receita de bolo
4f5e50e (HEAD -> main) HEAD@{4}: commit: Cria a página inicial
700bbd5 HEAD@{5}: commit (initial): Cria o README

Cada linha é um passo do HEAD, do mais novo (em cima) para o mais antigo:

4f5e50e
O commit onde o HEAD ficou depois daquele passo.
HEAD@{0}
"Onde o HEAD está agora". HEAD@{1} é "onde ele estava um passo antes", HEAD@{2}, dois passos antes, e assim por diante.
reset: moving to HEAD~3
O que causou o passo: aqui, o reset desastroso ("movendo para HEAD~3").

A linha HEAD@{1} diz: logo antes do reset, o HEAD estava em a939be6, o commit do brigadeiro. É para lá que a Ana quer voltar.

A recuperação

O mesmo git reset --hard que causou o problema resolve, apontando para o lugar certo:

$ git reset --hard HEAD@{1}
HEAD is now at a939be6 Adiciona a receita de brigadeiro
$ git log --oneline
a939be6 (HEAD -> main) Adiciona a receita de brigadeiro
71692df Adiciona a receita de pudim
33cecd7 Adiciona a receita de bolo
4f5e50e Cria a página inicial
700bbd5 Cria o README
$ ls
README.md  bolo.txt  brigadeiro.txt  index.html  pudim.txt      « tudo de volta
$ git reflog -3
a939be6 (HEAD -> main) HEAD@{0}: reset: moving to HEAD@{1}      « a recuperação
4f5e50e HEAD@{1}: reset: moving to HEAD~3
a939be6 (HEAD -> main) HEAD@{2}: commit: Adiciona a receita de brigadeiro
  • HEAD is now at a939be6 Adiciona a receita de brigadeiro: o main voltou para o commit do brigadeiro.
  • Os cinco commits e os cinco arquivos estão de volta.
  • O reflog anotou também a recuperação (reset: moving to HEAD@{1}). Repare que, agora, HEAD@{1} já é outro lugar (o estado do desastre): os números mudam a cada passo. Por isso, se for demorar entre olhar e agir, use o hash (git reset --hard a939be6), que nunca muda.
E o "rascunho" do index.html? Esse se perdeu de verdade. Ele nunca foi commitado, então o Git nunca guardou uma cópia, e o reset --hard o apagou (era o que a Ana queria, mas imagine se fosse um trabalho de horas). Antes de qualquer --hard, rode git status: o que aparecer como modificado vai embora sem volta.

Missão 1: o terminal já está logo depois do git reset --hard HEAD~3 desastroso: o git log só mostra dois commits. Use o git reflog para descobrir onde o main estava antes e traga os três commits de volta. No fim, o ls tem de mostrar as três receitas.

Desastre 2: o branch apagado

Recuperada do susto, a Ana começa a página "Sobre" num branch novo. Commita, volta ao main… e, achando que pagina-sobre era um branch velho de teste, apaga. O -d recusa; ela, impaciente, usa o -D que a dica sugeriu:

$ git switch -c pagina-sobre
Switched to a new branch 'pagina-sobre'
$ echo '<h1>Sobre a Ana</h1>' > sobre.html
$ git add sobre.html
$ git commit -m 'Cria a página Sobre'
[pagina-sobre b5e4717] Cria a página Sobre
 1 file changed, 1 insertion(+)
 create mode 100644 sobre.html
$ git switch main
Switched to branch 'main'
$ git branch -d pagina-sobre
error: the branch 'pagina-sobre' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D pagina-sobre'
hint: Disable this message with "git config set advice.forceDeleteBranch false"
$ git branch -D pagina-sobre
Deleted branch pagina-sobre (was b5e4717).      « a pista: b5e4717
$ git branch
* main
  • O -d avisou: the branch 'pagina-sobre' is not fully merged ("não foi totalmente juntado"). Era o Git tentando salvar a Ana.
  • O -D apagou assim mesmo. A mensagem Deleted branch pagina-sobre (was b5e4717). ("branch apagado, era b5e4717") já traz a pista: o hash do último commit do branch.

A recuperação

Um branch é só uma etiqueta num commit. Para "desapagar", basta criar uma etiqueta nova com o mesmo nome, no mesmo commit. Se a mensagem do -D já saiu da tela, o reflog tem o hash:

$ git reflog -4
a939be6 (HEAD -> main) HEAD@{0}: checkout: moving from pagina-sobre to main
b5e4717 HEAD@{1}: commit: Cria a página Sobre      « o último commit do branch apagado
a939be6 (HEAD -> main) HEAD@{2}: checkout: moving from main to pagina-sobre
a939be6 (HEAD -> main) HEAD@{3}: reset: moving to HEAD@{1}
$ git branch pagina-sobre HEAD@{1}
$ git branch
* main
  pagina-sobre      « de volta
$ git log --oneline pagina-sobre -2
b5e4717 (pagina-sobre) Cria a página Sobre
a939be6 (HEAD -> main) Adiciona a receita de brigadeiro
  • HEAD@{0}: checkout: moving from pagina-sobre to main: a volta para o main (o git switch aparece no reflog como checkout).
  • HEAD@{1}: commit: Cria a página Sobre: o último commit feito no branch apagado, b5e4717.
  • git branch pagina-sobre HEAD@{1} cria o branch apontando para esse commit. O git log mostra o commit da página Sobre no topo do branch: ele está de volta, inteiro.

Missão 2: a Ana acabou de apagar o branch pagina-sobre com git branch -D. Encontre no git reflog o último commit dele (o da página Sobre) e recrie o branch pagina-sobre apontando para esse commit. Confira com git log --oneline pagina-sobre.

O que o reflog não salva

Para fechar o dia, a Ana testa a regra do aviso lá de cima. Ela acrescenta uma linha no bolo.txt, não commita, e roda git reset --hard (sem nada depois, que quer dizer "volte para o HEAD, descartando as mudanças"):

$ echo 'Rende 12 fatias' >> bolo.txt
$ git reset --hard
HEAD is now at a939be6 Adiciona a receita de brigadeiro
$ cat bolo.txt
Bolo de cenoura
Forno: 180 graus por 35 minutos      « a linha nova sumiu
$ git reflog -2
a939be6 (HEAD -> main) HEAD@{0}: reset: moving to HEAD
a939be6 (HEAD -> main) HEAD@{1}: checkout: moving from pagina-sobre to main
  • A linha "Rende 12 fatias" sumiu do arquivo.
  • O reflog anotou o reset, mas a linha HEAD@{0} aponta para o mesmo commit de antes (a939be6). Não existe nenhum commit com a linha perdida para onde voltar.

Moral: commit é seguro; mudança não commitada não é. Na dúvida antes de um comando perigoso, commite (dá para desfazer depois) ou guarde com git stash.

Formas diferentes de recuperar

Para…ComandoObservação
Voltar o branch atual para onde estavagit reset --hard HEAD@{1} ou git reset --hard a939be6Confira o git status antes: o --hard descarta mudanças não commitadas.
Recriar um branch apagadogit branch pagina-sobre b5e4717O hash vem da mensagem do -D ou do reflog.
Recriar e já entrar nelegit switch -c pagina-sobre b5e4717Igual ao anterior, trocando para o branch.
Só olhar o commit perdido, sem mexer em nadagit show a939be6 ou git switch --detach a939be6Bom para conferir antes de recuperar.
Recuperar só um arquivo de um commit perdidogit restore --source=a939be6 brigadeiro.txtTraz o arquivo para a pasta sem mexer no histórico.
Ver o reflog com data e horagit reflog --date=isoÚtil para achar "onde eu estava ontem às 17h".
O reflog é só seu e não é eterno. Ele fica no seu computador (não vai para o GitHub, não vem num git clone). E o Git limpa entradas antigas: pela documentação do git gc, o padrão é 90 dias para entradas comuns e 30 dias para as que apontam para commits que nenhum branch alcança, como os do desastre. Não deixe para recuperar no mês que vem.

Quando dá errado

A recuperação foi para o lugar errado

O que aconteceu: os números HEAD@{n} mudam a cada passo do HEAD. Se você rodou outros comandos entre ler o reflog e recuperar (um git switch, outro reset), o HEAD@{1} agora é outro lugar.

Como resolver: rode git reflog de novo e use o hash da linha certa. Se a recuperação foi para o lugar errado, não tem problema: ela também entrou no reflog, e dá para repetir com o hash certo.

Fiz o reset, o commit voltou, mas o meu arquivo não

O que aconteceu: o arquivo era uma mudança não commitada que o --hard descartou (a seção "O que o reflog não salva"). O reflog só guarda commits.

Como resolver: no Git, não há como. Verifique se o seu editor tem histórico local (o VS Code tem a "Linha do tempo" do arquivo; veja Git no VS Code) ou se há uma cópia de segurança.

O commit sumido também não aparece no reflog

O que aconteceu: o reflog é deste repositório. Se o commit foi feito noutro computador (ou noutro clone), procure lá. Se o repositório foi apagado e clonado de novo, o reflog antigo foi junto. E, depois de muito tempo, as entradas expiram.

Como resolver: se o commit chegou a ir para o GitHub, ele pode estar em outro branch remoto (git log --oneline --all depois de um git fetch). Veja também Recuperando Commits Perdidos.

Resumo

  • O reflog é o diário do HEAD: cada commit, troca de branch, reset e merge vira uma linha, do mais novo ao mais antigo.
  • Sumiu commit? git reflog, ache a linha de antes do desastre e git reset --hard para ela (de preferência pelo hash).
  • Apagou branch? O hash está na mensagem do -D e no reflog: git branch nome HASH.
  • O reflog só guarda commits. Mudança não commitada e descartada não volta: commite ou faça git stash antes de comandos perigosos.
  • O reflog é local e expira (por padrão, 90 e 30 dias). Recupere logo.

Git por dentro

Até aqui você usou o Git "por fora": add, commit, log, reset. Nesta aula você abre a tampa e olha dentro da pasta .git, onde o Git guarda tudo. Não é preciso saber isso para usar o Git no dia a dia, mas quem entende o que tem lá dentro para de ter medo: fica claro por que um commit "nunca se perde", por que o --amend muda o hash, e o que o reset realmente move. E é bem mais simples do que parece: são só três tipos de objeto.

Você vai aprender
  • Que o Git guarda fotografias (snapshots) do projeto inteiro, não listas de diferenças.
  • O que há dentro da pasta .git, e o que é a pasta .git/objects.
  • Os três tipos de objeto: blob (conteúdo de arquivo), tree (pasta) e commit.
  • Como espiar cada objeto com git cat-file -t e git cat-file -p.
  • Por que arquivos iguais ocupam espaço uma vez só, e por que um commit nunca pode ser alterado.

Todas as saídas desta aula vieram do Git real da máquina da Ana (usuária ana, computador notebook). Como o laboratório do guia usa o mesmo nome, o mesmo e-mail e a mesma data fixa em todos os commits (15/10/2026, 10:30), os hashes que você vê aqui saem iguais se você repetir os mesmos passos no terminal do guia. A próxima aula, O Hash do Commit, explica por quê.

A ideia: um álbum de fotos, não um diário de mudanças

Há dois jeitos de guardar a história de um projeto:

  • Diário de mudanças: guardar o projeto original e, a cada versão, anotar só o que mudou ("linha 2: troquei 40 por 45"). Para ver a versão 50, é preciso partir do original e aplicar 49 anotações.
  • Álbum de fotografias: a cada versão, tirar uma foto do projeto inteiro. Para ver a versão 50, basta abrir a foto 50.

O Git usa o álbum: cada commit é uma fotografia completa (em inglês, snapshot) de todos os arquivos naquele momento. "Mas isso não ocupa um espaço enorme?" Não, por causa de um truque: se um arquivo não mudou de uma foto para a outra, o Git não guarda outra cópia; a foto nova só aponta para o mesmo conteúdo da foto anterior. Você vai ver isso acontecer com os próprios olhos.

(As diferenças que o git diff e o git show mostram não estão guardadas em lugar nenhum: o Git as calcula na hora, comparando duas fotografias.)

1. Dentro da pasta .git

Um repositório recém-criado tem só a pasta .git (o ls -A mostra também os nomes que começam com ponto):

$ mkdir receitas && cd receitas
$ git init -q
$ ls -A
.git
$ ls .git
HEAD  config  description  hooks  info  objects  refs
HEAD
Um arquivinho de texto que diz em que branch você está (veja O que é HEAD).
config
As configurações deste repositório (as que você faz com git config sem --global; veja git config).
description, hooks, info
Arquivos de apoio: uma descrição usada por ferramentas antigas, os hooks (scripts que rodam em certos momentos) e regras locais de exclusão.
objects
O banco de dados do Git. Todo conteúdo de arquivo, toda pasta e todo commit que você já fez está aqui, cada um num "objeto".
refs
As etiquetas com nome: os branches (refs/heads/) e as tags (refs/tags/). Cada uma é só um arquivinho com o hash de um commit.
Olhe, mas não mexa

Espiar a pasta .git é seguro. Editar ou apagar arquivos lá dentro à mão pode estragar o repositório. Use sempre os comandos do Git. E apagar a pasta .git inteira apaga todo o histórico do projeto (os arquivos da pasta de trabalho ficam, mas sem nenhum commit).

2. O primeiro objeto: o blob

A pasta objects começa vazia. A Ana cria o README e dá git add, e algo aparece lá dentro:

$ find .git/objects -type f
$ echo '# Receitas da Ana' > README.md
$ git add README.md
$ find .git/objects -type f
.git/objects/26/44316531953179572e7fdf95ede19e1b33c399

O primeiro find (que lista os arquivos de uma pasta e das subpastas) não mostrou nada. Depois do git add, apareceu um arquivo com um nome estranho: 26/44316531953179572e7fdf95ede19e1b33c399. Juntando a pasta (26) e o nome do arquivo, dá 2644316531953179572e7fdf95ede19e1b33c399: 40 caracteres, o hash desse objeto, uma espécie de "impressão digital" do conteúdo (explicada em O Hash do Commit). O Git separa os dois primeiros caracteres numa pasta só para não juntar milhares de arquivos numa pasta só.

Repare: o objeto foi criado no git add, não no git commit. Preparar um arquivo já guarda o conteúdo dele no banco de dados.

Para perguntar ao Git o que é esse objeto, existe o git cat-file:

$ git cat-file -t 2644316
blob
$ git cat-file -p 2644316
# Receitas da Ana
$ git cat-file -s 2644316
18
git cat-file
"Mostre um objeto do banco de dados". É um comando de "encanamento" (plumbing): feito para olhar as entranhas do Git, não para o uso diário.
-t
De type: mostra o tipo do objeto. Aqui, blob.
-p
De pretty-print, "mostrar bonito": mostra o conteúdo do objeto, num formato legível.
-s
De size: o tamanho do conteúdo em bytes. 18: os 17 caracteres de # Receitas da Ana mais a quebra de linha.
2644316
O hash do objeto. Não precisa dos 40 caracteres: basta o começo (no mínimo 4), desde que nenhum outro objeto comece igual.

Blob (de binary large object, "objeto binário grande") é o tipo de objeto que guarda o conteúdo de um arquivo. Só o conteúdo: o blob não sabe o nome do arquivo, nem em que pasta ele está, nem quando foi criado. Quem sabe disso é a tree.

Lá dentro, comprimido

Se você abrir o arquivo do objeto com o cat, não vai ler nada: o Git guarda os objetos comprimidos (com o zlib, o mesmo método dos arquivos .zip). O comando file confirma:

$ file .git/objects/26/44316531953179572e7fdf95ede19e1b33c399
.git/objects/26/44316531953179572e7fdf95ede19e1b33c399: zlib compressed data

Por isso se usa o git cat-file: ele descomprime e mostra.

3. O commit e a tree

Agora a Ana faz o primeiro commit e olha a pasta objects de novo:

$ git commit -q -m "Primeiro commit"
$ find .git/objects -type f | sort
.git/objects/22/66689caa9ea60c127cd9b491dbe117f9699670
.git/objects/26/44316531953179572e7fdf95ede19e1b33c399
.git/objects/fe/996fb8ecae7fe25026045fd46f15ca756bc19c
$ git log --oneline
fe996fb (HEAD -> main) Primeiro commit

Apareceram mais dois objetos. Um deles, fe996fb…, tem o mesmo começo do hash que o git log mostra: é o commit. Vamos abri-lo:

$ git cat-file -t fe996fb
commit
$ git cat-file -p fe996fb
tree 2266689caa9ea60c127cd9b491dbe117f9699670
author Ana Souza <ana@exemplo.com> 1792071000 -0300
committer Ana Souza <ana@exemplo.com> 1792071000 -0300

Primeiro commit

Um commit, por dentro, é um textinho:

tree 2266689…
A fotografia: o hash da tree (a pasta principal do projeto) naquele momento. É o terceiro objeto que apareceu.
author Ana Souza <ana@exemplo.com> 1792071000 -0300
Quem escreveu a mudança, e quando. A data está em "segundos desde 1º de janeiro de 1970" (o jeito como os computadores contam o tempo): 1792071000 é 15 de outubro de 2026, 10:30, no fuso -0300.
committer …
Quem gravou o commit, e quando. Quase sempre é a mesma pessoa e a mesma hora do author; eles diferem, por exemplo, depois de um --amend feito mais tarde, ou quando alguém aplica a mudança de outra pessoa.
(linha em branco) Primeiro commit
A mensagem do commit.

E a tree:

$ git cat-file -p HEAD^{tree}
100644 blob 2644316531953179572e7fdf95ede19e1b33c399	README.md

O HEAD^{tree} quer dizer "a tree do commit HEAD" (poderia ser o hash 2266689, dá no mesmo). Uma tree ("árvore") é uma pasta: uma lista de nomes, cada um apontando para um blob (arquivo) ou para outra tree (subpasta). Cada linha tem:

100644
O modo: 100644 é arquivo comum, 100755 é arquivo executável, 040000 é pasta.
blob
O tipo do objeto apontado.
2644316…
O hash do objeto: o blob do README, aquele criado no git add.
README.md
O nome do arquivo. É aqui, na tree, que o nome fica guardado.

Em desenho, o primeiro commit da Ana é assim:

commit fe996fb  ("Primeiro commit", Ana Souza, 15/10/2026 10:30)
   │
   └── tree 2266689  (a pasta receitas/)
          │
          └── README.md → blob 2644316  ("# Receitas da Ana")

Missão: o repositório da Ana já tem o primeiro commit. Abra o objeto do commit com git cat-file -p (use HEAD ou o hash do git log --oneline) e encontre a linha tree. Depois, se quiser, abra a tree com git cat-file -p e o hash dela.

4. O segundo commit: o "pai" e o reaproveitamento

A Ana cria a receita de bolo e uma pasta doces com a receita de pudim, e commita:

$ mkdir doces
$ printf 'Bolo de cenoura\nTempo: 40 minutos\n' > bolo.txt
$ echo 'Pudim de leite' > doces/pudim.txt
$ git add bolo.txt doces
$ git commit -q -m "Adiciona bolo e pudim"
$ git log --oneline
eaac340 (HEAD -> main) Adiciona bolo e pudim
fe996fb Primeiro commit
$ git cat-file -p HEAD
tree 6121a7a2f681a5065c3bc3e562f8d47d034b6f33
parent fe996fb8ecae7fe25026045fd46f15ca756bc19c
author Ana Souza <ana@exemplo.com> 1792071000 -0300
committer Ana Souza <ana@exemplo.com> 1792071000 -0300

Adiciona bolo e pudim

Este commit tem uma linha nova: parent ("pai"), com o hash do commit anterior. É assim que o histórico é montado: cada commit aponta para o seu pai, que aponta para o pai dele, até o primeiro commit (que não tem parent). O git log nada mais faz do que seguir essa corrente de trás para a frente, a partir do HEAD.

$ git cat-file -p HEAD^{tree}
100644 blob 2644316531953179572e7fdf95ede19e1b33c399	README.md   « o MESMO blob do 1º commit
100644 blob af7ede1618b0cda974c838541f4c1ffe7ecd76d3	bolo.txt
040000 tree 198812946935d95e835d760523d1b97e58bd8f57	doces       « uma subpasta
$ git cat-file -p 1988129
100644 blob 8499e03b32d8e828d20f94e1a73945e1103973f3	pudim.txt
$ git cat-file -p 8499e03
Pudim de leite

Duas coisas para reparar:

  • A pasta doces virou uma tree dentro da tree (040000 tree), que por sua vez aponta para o blob do pudim.txt. Pastas dentro de pastas viram trees dentro de trees.
  • O README.md aponta para o blob 2644316…, exatamente o mesmo do primeiro commit. O README não mudou, então o Git não guardou outra cópia: a fotografia nova reaproveita o conteúdo da antiga.
commit eaac340 ("Adiciona bolo e pudim")
   │  parent ─────────────────────────►  commit fe996fb ("Primeiro commit")
   │                                         │
   └── tree 6121a7a                          └── tree 2266689
          ├── README.md → blob 2644316 ◄─────────────┘ (o mesmo blob)
          ├── bolo.txt  → blob af7ede1
          └── doces/    → tree 1988129
                            └── pudim.txt → blob 8499e03

Conte os objetos: 3 do primeiro commit + 5 novos (o commit, a tree principal, o blob do bolo, a tree doces e o blob do pudim) = 8. O git count-objects confirma:

$ find .git/objects -type f | sort
.git/objects/19/8812946935d95e835d760523d1b97e58bd8f57
.git/objects/22/66689caa9ea60c127cd9b491dbe117f9699670
.git/objects/26/44316531953179572e7fdf95ede19e1b33c399
.git/objects/61/21a7a2f681a5065c3bc3e562f8d47d034b6f33
.git/objects/84/99e03b32d8e828d20f94e1a73945e1103973f3
.git/objects/af/7ede1618b0cda974c838541f4c1ffe7ecd76d3
.git/objects/ea/ac34092a80e72af8d9bd6c9c1525f501f88267
.git/objects/fe/996fb8ecae7fe25026045fd46f15ca756bc19c
$ git count-objects
8 objects, 32 kilobytes

Conteúdo igual, objeto igual

O reaproveitamento não depende do nome. A Ana copiou o README para um arquivo novo e deu git add:

$ cp README.md copia.txt
$ git add copia.txt
$ git count-objects
8 objects, 32 kilobytes   « nenhum objeto novo!
$ git hash-object copia.txt
2644316531953179572e7fdf95ede19e1b33c399

O git hash-object calcula o hash que um arquivo teria como blob: 2644316…, o mesmo do README. Conteúdo igual dá hash igual, e hash igual é o mesmo objeto; o Git não guardou nada novo. (Depois do teste, a Ana desfez com git restore --staged copia.txt e rm copia.txt.)

5. Mudando um arquivo: só o que mudou é novo

$ sed -i 's/40 minutos/45 minutos/' bolo.txt
$ git commit -q -am "Aumenta tempo do bolo"
$ git cat-file -p HEAD
tree d8a6700698bd6cc7dff33d519dfd993644d7b4e3
parent eaac34092a80e72af8d9bd6c9c1525f501f88267
author Ana Souza <ana@exemplo.com> 1792071000 -0300
committer Ana Souza <ana@exemplo.com> 1792071000 -0300

Aumenta tempo do bolo
$ git cat-file -p HEAD^{tree}
100644 blob 2644316531953179572e7fdf95ede19e1b33c399	README.md   « igual
100644 blob a6fb0850dd0fcdd6ab633bf07ddd563ca2e65ff8	bolo.txt    « blob NOVO
040000 tree 198812946935d95e835d760523d1b97e58bd8f57	doces       « igual
$ git count-objects
11 objects, 44 kilobytes

(O sed -i troca um texto dentro do arquivo; o -am do commit adiciona e commita os arquivos rastreados de uma vez.) O bolo mudou, então ganhou um blob novo. O README e a pasta doces não mudaram, e a tree nova aponta para os mesmos objetos de antes. Foram só 3 objetos novos (o blob do bolo, a tree principal e o commit): 8 + 3 = 11.

E as duas versões do bolo continuam guardadas, cada uma no seu blob. Com commit:caminho, o git cat-file navega pela fotografia de qualquer commit:

$ git cat-file -p HEAD:bolo.txt
Bolo de cenoura
Tempo: 45 minutos
$ git cat-file -p HEAD~1:bolo.txt
Bolo de cenoura
Tempo: 40 minutos
$ git cat-file -p HEAD:doces
100644 blob 8499e03b32d8e828d20f94e1a73945e1103973f3	pudim.txt

HEAD~1 é "o pai do HEAD" (veja O que é HEAD). É exatamente isso que o git restore --source, o git show HEAD~1:bolo.txt e o git reset usam por baixo: buscar o blob certo na fotografia certa.

Missão: o bolo.txt da pasta diz 45 minutos. Sem mudar nada na pasta, mostre a versão antiga do bolo, guardada no commit anterior, com git cat-file -p e o formato commit:caminho.

6. Por que um commit nunca muda

O nome de cada objeto (o hash) é calculado a partir do conteúdo dele. O conteúdo de um commit inclui a tree, o pai, o autor, a data e a mensagem. Então:

  • se qualquer coisa mudasse num commit (uma letra da mensagem, um byte de um arquivo), o hash mudaria, e ele seria outro objeto;
  • por isso "editar" um commit é impossível: o --amend, o rebase e companhia sempre criam commits novos, e movem o branch para eles;
  • e, como o commit aponta para o pai pelo hash, mudar um commit antigo obriga a recriar todos os commits que vieram depois dele (os filhos apontam para o hash velho).

Os commits antigos, "abandonados", continuam na pasta objects até o Git fazer uma faxina automática (normalmente, depois de semanas). É por isso que o reflog consegue trazê-los de volta.

Os três objetos, lado a lado

ObjetoGuardaAponta paraCriado quando
blobO conteúdo de um arquivo (sem nome, sem data)nadano git add
treeUma pasta: nomes, modos e hashesblobs (arquivos) e trees (subpastas)no git commit
commitAutor, data, mensagemuma tree (a fotografia) e o(s) pai(s)no git commit

(Existe um quarto tipo, o objeto tag, criado pelas tags anotadas; veja git tag.) E os branches? Não são objetos: são só arquivos em .git/refs/heads/ com o hash de um commit. A aula O que é HEAD mostra isso.

Quando dá errado

Objeto que não existe (ou hash curto demais) 
$ git cat-file -p 2644
# Receitas da Ana
$ git cat-file -p 264
fatal: Not a valid object name 264
$ git cat-file -t banana
fatal: Not a valid object name banana

"Nome de objeto inválido." Com 4 caracteres (2644) o Git achou o blob; com 3, não: o mínimo para um hash abreviado é 4. E banana não é hash nem nome de branch. Como resolver: copie o hash do git log --oneline, do find .git/objects ou de outro git cat-file -p.

Esqueceu o -p (ou o -t) 
$ git cat-file README.md
fatal: only two arguments allowed in <type> <object> mode, not 1

uso: git cat-file <type> <object>
   ou: git cat-file (-e | -p | -t | -s) <object>
…

O git cat-file precisa saber o que mostrar (-p, -t, -s) e de qual objeto. E ele trabalha com objetos, não com arquivos da pasta: para ver o README guardado no último commit, é git cat-file -p HEAD:README.md. (A mensagem continua com uma longa lista de opções, cortada aqui no ….)

Resumo

  • O Git guarda fotografias completas do projeto (snapshots); as diferenças são calculadas na hora.
  • Tudo fica em .git/objects, em objetos comprimidos cujo nome é o hash do conteúdo.
  • blob = conteúdo de arquivo (criado no git add); tree = pasta (nomes + hashes); commit = tree + pai + autor + data + mensagem.
  • Conteúdo igual vira o mesmo objeto: arquivos que não mudaram não ocupam espaço de novo.
  • git cat-file -t mostra o tipo; git cat-file -p mostra o conteúdo; commit:caminho navega na fotografia.
  • Como o hash depende do conteúdo, um commit nunca muda: "mudar" é criar outro.

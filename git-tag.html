Git Marcando Versões (git tag)

O site de receitas da Ana chegou a um ponto bonito: bolo e pudim, tudo funcionando. Ela quer marcar esse momento para sempre: "esta é a versão 1.0". Daqui a três meses, com vinte commits a mais, ela vai poder dizer "me mostra como estava a 1.0" sem procurar hash nenhum. É para isso que serve a tag (em inglês, "etiqueta"): um nome fixo, como v1.0, colado num commit.

Você vai aprender
  • O que é uma tag e qual a diferença para um branch.
  • Os dois tipos: a tag leve e a tag anotada (-a -m), e quando usar cada uma.
  • Como listar, ver (git show), marcar um commit antigo e apagar tags.
  • Como enviar tags para o GitHub (o git push comum não envia!).
  • Como visitar uma versão antiga e o que o git describe conta.

Todas as saídas desta aula vieram do Git 2.53.0 da máquina da Ana (usuária ana, computador notebook), com o sistema em português, e do "GitHub de mentira" do laboratório. A tradução do Git no Ubuntu é incompleta: quase todas as mensagens desta aula saem em inglês, copiadas como saíram e traduzidas na explicação.

A ideia: a etiqueta na caixa de fotos

Pense nos commits como fotos numa caixa, em ordem. Você cola uma etiqueta numa delas: "Formatura". A etiqueta não muda de foto: daqui a dez anos, "Formatura" continua sendo aquela foto, por mais fotos que você ponha na caixa depois.

Um branch também é um nome colado num commit, mas é uma etiqueta que anda: a cada commit novo, o main passa para o commit mais recente (aula O que é um Branch). A tag não anda. É por isso que ela serve para versões:

                 v0.9        v1.0
                  │           │
    700bbd5 ─── c34349b ─── bbf4ec7 ─── 4949f73
                                           │
                                         main  (anda a cada commit)

1. A tag leve: só um nome

O repositório da Ana tem três commits. O git tag sozinho lista as tags; ainda não há nenhuma, então ele não mostra nada. Com um nome, ele cria uma tag no commit atual (o HEAD):

$ git tag
$ git tag revisado
$ git tag
revisado
git tag
Sem argumentos: lista as tags, em ordem alfabética.
git tag revisado
Cria a tag revisado no commit atual. Não mostra nada quando dá certo. Este é o tipo leve (em inglês, lightweight): só um nome, mais nada.

Num terminal de verdade, o git log mostra as tags ao lado dos commits:

$ git log --oneline
bbf4ec7 (HEAD -> main, tag: revisado) Adiciona a receita de pudim
c34349b Adiciona a receita de bolo
700bbd5 Cria o README

O tag: revisado está colado no bbf4ec7, o commit onde a Ana estava. E o git show com o nome da tag mostra o commit:

$ git show revisado
commit bbf4ec7677f7e692ad5643513bfad21c6657510a
Author: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

    Adiciona a receita de pudim

diff --git a/pudim.txt b/pudim.txt
new file mode 100644
index 0000000..533e6e4
--- /dev/null
+++ b/pudim.txt
@@ -0,0 +1 @@
+Pudim

Exatamente o mesmo que git show bbf4ec7 (aula git show): a tag leve é só um apelido para o commit. Tags leves servem para marcações pessoais e temporárias ("revisado", "antes-da-mudança").

2. A tag anotada: nome, autor, data e mensagem

Para versões de verdade, use a tag anotada (em inglês, annotated). Ela guarda também quem criou, quando e uma mensagem, como um commit:

$ git tag -a v1.0 -m 'Primeira versão do site: bolo e pudim'
$ git tag
revisado
v1.0
-a
De annotated, "anotada": cria uma tag com autor, data e mensagem.
v1.0
O nome. O v de "versão" na frente é um costume muito comum (v1.0, v2.3.1); a próxima aula, Versionamento Semântico, explica o que os números querem dizer.
-m '…'
A mensagem, como no git commit -m. Sem o -m, o Git abre o editor para você escrevê-la (no terminal do guia não há editor: use sempre -m).
$ git show v1.0
tag v1.0
Tagger: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

Primeira versão do site: bolo e pudim

commit bbf4ec7677f7e692ad5643513bfad21c6657510a
Author: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

    Adiciona a receita de pudim

diff --git a/pudim.txt b/pudim.txt
new file mode 100644
index 0000000..533e6e4
--- /dev/null
+++ b/pudim.txt
@@ -0,0 +1 @@
+Pudim

Agora o git show tem duas partes:

tag v1.0 / Tagger / Date / mensagem
A tag em si: o nome, quem a criou (Tagger, "quem etiquetou"), quando e a mensagem.
commit bbf4ec7… e o resto
O commit para onde ela aponta, igual ao da tag leve.

Por dentro, a diferença é que a tag anotada é um objeto próprio no repositório (veja Como o Git Guarda as Coisas), enquanto a leve é só um nome que aponta direto para o commit. O git cat-file -t ("tipo do objeto") mostra isso:

$ git cat-file -t revisado
commit
$ git cat-file -t v1.0
tag
Qual usar?

Para versões (o que você lança, publica, entrega): tag anotada, sempre. Ela diz quem lançou, quando e o que mudou, e alguns comandos (como o git describe, na seção 6) só olham para as anotadas. Para marcações pessoais e passageiras: a leve serve.

Missão: o site da Ana está pronto para a primeira versão. Crie uma tag anotada chamada v1.0 no commit atual, com a mensagem Primeira versão do site. Depois, veja-a com git tag e git show v1.0.

3. Marcando um commit antigo

Esqueceu de marcar uma versão na hora? Dê o commit no fim do comando: um hash, ou um caminho como HEAD~1 ("um antes do HEAD"). A Ana quer marcar como v0.9 o commit em que o site só tinha o bolo:

$ git tag -a v0.9 -m 'Versão de teste, só com o bolo' HEAD~1
$ git log --oneline
bbf4ec7 (HEAD -> main, tag: v1.0, tag: revisado) Adiciona a receita de pudim
c34349b (tag: v0.9) Adiciona a receita de bolo
700bbd5 Cria o README

O tag: v0.9 foi parar no c34349b, um commit atrás. Repare também que um commit pode ter várias tags (o bbf4ec7 tem v1.0 e revisado).

4. Listando e apagando

$ git tag -n
revisado        Adiciona a receita de pudim
v0.9            Versão de teste, só com o bolo
v1.0            Primeira versão do site: bolo e pudim
$ git tag -l 'v1.*'
v1.0
$ git tag -d revisado
Deleted tag 'revisado' (was bbf4ec7)
$ git tag
v0.9
v1.0
git tag -n
Lista as tags com a primeira linha da mensagem. Para a tag leve (revisado), que não tem mensagem própria, mostra a mensagem do commit.
git tag -l 'v1.*'
-l de list: lista só as tags que combinam com o padrão. O * quer dizer "qualquer coisa": v1.* pega v1.0, v1.1, v1.10… As aspas impedem o terminal de tentar interpretar o *.
git tag -d revisado
-d de delete: apaga a tag. Deleted tag 'revisado' (was bbf4ec7): "apaguei a tag revisado (ela apontava para o bbf4ec7)". Só o nome some; o commit continua lá.

5. Enviando as tags para o GitHub

Uma surpresa para quase todo mundo: o git push comum não envia as tags. A Ana ligou o repositório ao GitHub (aula git remote) e enviou o main:

$ git push -u origin main
Enumerating objects: 9, done.
Counting objects: 100% (9/9), done.
Delta compression using up to 4 threads
Compressing objects: 100% (5/5), done.
Writing objects: 100% (9/9), 716 bytes | 716.00 KiB/s, done.
Total 9 (delta 1), reused 0 (delta 0), pack-reused 0 (from 0)
To https://github.com/ana-souza/receitas.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
$ git ls-remote --tags origin

O git ls-remote --tags origin lista as tags que existem no GitHub: nenhuma. O push só levou o branch ([new branch]). Para enviar tags, peça:

$ git push origin v1.0
Enumerating objects: 1, done.
Counting objects: 100% (1/1), done.
Writing objects: 100% (1/1), 182 bytes | 182.00 KiB/s, done.
Total 1 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
To https://github.com/ana-souza/receitas.git
 * [new tag]         v1.0 -> v1.0
$ git push --tags
Enumerating objects: 1, done.
Counting objects: 100% (1/1), done.
Writing objects: 100% (1/1), 180 bytes | 180.00 KiB/s, done.
Total 1 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
To https://github.com/ana-souza/receitas.git
 * [new tag]         v0.9 -> v0.9
$ git ls-remote --tags origin
39c889654be05ba63ad0996475045aac51e879a4        refs/tags/v0.9
c34349be182fbe4bb6cb8705c96e597cf72fccb4        refs/tags/v0.9^{}
9578fdc8f57c2c659f999087460aa4280d8a4709        refs/tags/v1.0
bbf4ec7677f7e692ad5643513bfad21c6657510a        refs/tags/v1.0^{}
git push origin v1.0
Envia uma tag. A saída termina com [new tag] v1.0 -> v1.0: "tag nova". (Os números do Writing objects mudam a cada vez; o "1 objeto" enviado é o objeto da tag anotada, porque o commit já estava lá.)
git push --tags
Envia todas as tags que o GitHub ainda não tem: aqui, só faltava a v0.9. Cuidado: ele envia também tags leves e pessoais que você talvez não quisesse publicar.
refs/tags/v1.0 e refs/tags/v1.0^{}
Cada tag anotada aparece duas vezes: a primeira linha é o objeto da tag; a segunda, com ^{}, é o commit para onde ela aponta (o bbf4ec7, como você viu no git show).

Apagando uma tag que já está no GitHub

O git tag -d só apaga na sua máquina. Para apagar no GitHub, use o push com --delete:

$ git push origin --delete v0.9
To https://github.com/ana-souza/receitas.git
 - [deleted]         v0.9
$ git tag -d v0.9
Deleted tag 'v0.9' (was 39c8896)
$ git ls-remote --tags origin
9578fdc8f57c2c659f999087460aa4280d8a4709        refs/tags/v1.0
bbf4ec7677f7e692ad5643513bfad21c6657510a        refs/tags/v1.0^{}

- [deleted] v0.9: "apagada" no GitHub. Depois, a Ana apagou também a sua cópia local. Repare que o was 39c8896 é o hash do objeto da tag anotada (o mesmo da primeira linha do ls-remote), e não o do commit.

Não mude uma versão publicada

Apagar e recriar uma tag com o mesmo nome em outro commit é possível, mas quem já baixou a v1.0 antiga continua com ela, e as duas "v1.0" passam a ser diferentes. Se a versão publicada tinha um erro, lance outra: v1.0.1. É a mesma ideia da Regra de Ouro.

No site do GitHub, as tags enviadas aparecem na página do repositório, e a partir de uma tag dá para criar uma release ("lançamento"): uma página com notas da versão e arquivos para baixar. Essa parte é ilustrativa (o site não roda no laboratório); veja "Sobre versões" na documentação do GitHub (docs.github.com/pt).

6. Visitando uma versão e o git describe

Voltando no tempo para ver a v0.9

Antes de apagar a v0.9, a Ana quis ver como o site era nela. Como a tag não é um branch, o git switch reclama:

$ git switch v0.9
fatal: a branch is expected, got tag 'v0.9'
hint: If you want to detach HEAD at the commit, try again with the --detach option.
$ git switch --detach v0.9
HEAD is now at c34349b Adiciona a receita de bolo
$ git status
HEAD detached at v0.9
nothing to commit, working tree clean
$ ls
README.md
bolo.txt
$ git switch main
Previous HEAD position was c34349b Adiciona a receita de bolo
Switched to branch 'main'
fatal: a branch is expected, got tag 'v0.9'
"Era esperado um branch, recebi a tag v0.9." A dica sugere o --detach.
git switch --detach v0.9
Vai até o commit da tag, em modo HEAD destacado: você está num commit, não num branch (aula HEAD Destacado). O git status confirma: HEAD detached at v0.9.
ls
A pasta como era na v0.9: só o README e o bolo; o pudim ainda não existia.
git switch main
Volta ao presente. Previous HEAD position was …: "a posição anterior do HEAD era…".

O comando antigo, git checkout v0.9, vai direto (sem precisar de --detach) e mostra um aviso longo sobre o detached HEAD, explicado na aula HEAD Destacado. Para mudar uma versão antiga (corrigir um erro na v1.0, por exemplo), crie um branch a partir dela: git switch -c correcao-v1 v1.0.

"Em que versão eu estou?" git describe

$ git describe
v1.0
$ printf 'Brigadeiro\n' > brigadeiro.txt
$ git add brigadeiro.txt
$ git commit -q -m 'Adiciona o brigadeiro'
$ git describe
v1.0-1-g4949f73

O git describe descreve o commit atual a partir da tag anotada mais próxima. No commit da tag, a resposta é só v1.0. Depois de um commit novo, é v1.0-1-g4949f73: "v1.0, mais 1 commit, e o commit atual é o 4949f73" (o g na frente do hash é de "git"). Muitos projetos usam isso para mostrar a versão exata no rodapé de um programa.

Quando dá errado

A tag já existe: fatal: tag 'v1.0' already exists 
$ git tag v1.0
fatal: tag 'v1.0' already exists

"A tag v1.0 já existe." Duas tags não podem ter o mesmo nome. Como confirmar: git tag ou git show v1.0. Como resolver: se é uma versão nova, use outro nome (v1.1); se a tag foi criada no commit errado e ainda não foi enviada, apague e crie de novo (git tag -d v1.0 e git tag -a v1.0 -m "…"). Existe o -f ("forçar"), que move a tag, mas não o use em tags já publicadas.

Nome inválido: is not a valid tag name 
$ git tag 'versão 1'
fatal: 'versão 1' is not a valid tag name.

"versão 1 não é um nome de tag válido." Nomes de tag não podem ter espaços (nem alguns símbolos, como ~, ^, : e ?). Como resolver: use pontos, hífens ou nada: v1, versao-1, v1.0.0.

Commit que não existe: Failed to resolve 'HEAD~9' as a valid ref 
$ git tag teste HEAD~9
fatal: Failed to resolve 'HEAD~9' as a valid ref.

"Não consegui entender HEAD~9 como uma referência válida." O repositório não tem 9 commits antes do atual. Como resolver: confira o commit no git log --oneline e use o hash dele.

"Criei a tag, mas ela não aparece no GitHub"

O git push comum não envia tags (seção 5). Como confirmar: git ls-remote --tags origin. Como resolver: git push origin v1.0.

Resumo

  • Uma tag é um nome fixo colado num commit; diferente do branch, ela não anda. Serve para marcar versões.
  • git tag nome cria uma tag leve (só o nome); git tag -a v1.0 -m "…" cria uma anotada (com autor, data e mensagem): use a anotada para versões.
  • git tag, -n e -l 'padrão' listam; git show v1.0 mostra; git tag -d apaga; um commit no fim do comando marca um commit antigo.
  • O git push comum não envia tags: git push origin v1.0 ou git push --tags; para apagar no GitHub, git push origin --delete v1.0.
  • git switch --detach v1.0 visita uma versão; git describe diz a que distância você está da última tag anotada.

Git merge

Branches servem para trabalhar separado. Mas, um dia, o trabalho separado tem de voltar para a linha principal: a seção de sobremesas ficou pronta e precisa entrar no site. O comando que junta o trabalho de um branch no outro é o git merge (em inglês, "mesclar", "fundir"). Ele traz os commits de outro branch para o branch em que você está.

Você vai aprender
  • Como juntar um branch no main com git merge NOME, e em que branch você precisa estar.
  • Ler a saída do merge: Updating, Fast-forward, a lista de arquivos, Merge made by the 'ort' strategy.
  • Os dois jeitos de o Git juntar: só andar com a etiqueta (fast-forward) ou criar um commit de merge, com dois pais.
  • O editor que abre no merge, e como evitá-lo com --no-edit ou -m.
  • Os erros reais: branch que não existe, mudanças locais no caminho e (uma prévia do) conflito.

As saídas vieram do Git 2.53 do Ubuntu 26.04, na máquina da Ana, com o sistema em português. Várias mensagens do merge saem em inglês, porque a tradução do Git no Ubuntu é parcial; cada uma vem traduzida aqui.

A ideia: passar o rascunho a limpo

A Ana escreveu as sobremesas num caderno de rascunho (o branch sobremesas). Ficou bom. Agora ela abre o caderno oficial (o main) e passa para ele as páginas novas do rascunho. O rascunho continua existindo, intacto; quem ganhou páginas foi o caderno oficial.

O git merge funciona igual, e a frase para guardar é: "estando no branch que vai receber, faça merge do branch que tem o trabalho".

  1. git switch main: vá para quem recebe.
  2. git merge sobremesas: traga o trabalho do sobremesas.

1. Antes do merge

O repositório receitas da Ana tem três commits no main. Ela criou o branch sobremesas e fez dois commits nele:

$ git switch -c sobremesas
Switched to a new branch 'sobremesas'
$ echo 'Pudim de leite' > pudim.txt
$ git add pudim.txt && git commit -q -m 'Adiciona receita de pudim'
$ echo 'Brigadeiro' > brigadeiro.txt
$ git add brigadeiro.txt && git commit -q -m 'Adiciona receita de brigadeiro'
$ git log --oneline --graph --all
* ae456dd (HEAD -> sobremesas) Adiciona receita de brigadeiro
* d6f2336 Adiciona receita de pudim
* 0244251 (main) Adiciona receita de pão de queijo     « o main ficou aqui
* 7225e04 Adiciona receita de bolo
* 700bbd5 Cria o README

A---B---C   ← main
         \
          D---E   ← sobremesas ← HEAD

A = 700bbd5 (README)  B = 7225e04 (bolo)  C = 0244251 (pão de queijo)
D = d6f2336 (pudim)   E = ae456dd (brigadeiro)

2. O merge

Primeiro, a Ana vai para quem recebe, o main. As sobremesas não estão lá:

$ git switch main
Switched to branch 'main'
$ ls
README.md  bolo.txt  pao.txt

Agora, o merge:

$ git merge sobremesas
Updating 0244251..ae456dd
Fast-forward
 brigadeiro.txt | 1 +
 pudim.txt      | 1 +
 2 files changed, 2 insertions(+)
 create mode 100644 brigadeiro.txt
 create mode 100644 pudim.txt
$ ls
README.md  bolo.txt  brigadeiro.txt  pao.txt  pudim.txt     « as sobremesas chegaram
git merge sobremesas
"Junte no branch atual (main) o trabalho do sobremesas".
Updating 0244251..ae456dd
"Atualizando de 0244251 para ae456dd": o main estava no commit C e vai para o E.
Fast-forward
"Avanço rápido". O main não tinha nenhum commit novo desde que o sobremesas nasceu, então o Git não precisou juntar nada: só empurrou a etiqueta main para frente. É o caso mais simples, com aula própria: Merge Fast-forward.
brigadeiro.txt | 1 + …
O resumo do que mudou na pasta, como no git diff --stat: cada arquivo, quantas linhas, e um + por linha acrescentada.
2 files changed, 2 insertions(+)
"2 arquivos mudados, 2 linhas inseridas".
create mode 100644 pudim.txt
"Arquivo criado" (o 100644 é o tipo: arquivo comum, não executável).
$ git log --oneline --graph --all
* ae456dd (HEAD -> main, sobremesas) Adiciona receita de brigadeiro
* d6f2336 Adiciona receita de pudim
* 0244251 Adiciona receita de pão de queijo
* 7225e04 Adiciona receita de bolo
* 700bbd5 Cria o README

Antes:   A---B---C   ← main ← HEAD
                  \
                   D---E   ← sobremesas

Depois:  A---B---C---D---E   ← main ← HEAD
                             ← sobremesas

Nenhum commit novo foi criado: as duas etiquetas apontam para o mesmo commit, E. O sobremesas não mudou; quem andou foi o main.

Rodar de novo não faz mal

$ git merge sobremesas
Already up to date.

"Já está atualizado": tudo o que o sobremesas tem, o main já tem.

3. Quando os dois branches andaram: o commit de merge

Agora o caso mais comum no trabalho de verdade. A Ana criou o branch salgados e commitou uma coxinha nele. Enquanto isso, no main, ela commitou uma feijoada. Os dois ramos têm um commit que o outro não tem:

$ git switch -c salgados
Switched to a new branch 'salgados'
$ echo 'Coxinha' > coxinha.txt
$ git add coxinha.txt && git commit -q -m 'Adiciona coxinha'
$ git switch -q main
$ echo 'Feijoada' > feijoada.txt
$ git add feijoada.txt && git commit -q -m 'Adiciona receita de feijoada'
$ git log --oneline --graph --all
* abee64f (HEAD -> main) Adiciona receita de feijoada
| * c8eefba (salgados) Adiciona coxinha
|/
* ae456dd (sobremesas) Adiciona receita de brigadeiro
* d6f2336 Adiciona receita de pudim
* 0244251 Adiciona receita de pão de queijo
* 7225e04 Adiciona receita de bolo
* 700bbd5 Cria o README

A---B---C---D---E---F   ← main ← HEAD      (F = abee64f, a feijoada)
                 \
                  G   ← salgados          (G = c8eefba, a coxinha; o salgados nasceu em E)

Aqui não dá para "só empurrar a etiqueta": se o main pulasse para G, a feijoada ficaria de fora. O Git precisa criar um commit novo, que junta as duas linhas. Esse é o commit de merge, e ele precisa de uma mensagem. Por isso, quando a Ana roda git merge salgados, o Git abre o editor de texto (o nano, configurado na máquina dela) com uma mensagem pronta:

  GNU nano 8.7.1           /home/ana/receitas/.git/MERGE_MSG
Merge branch 'salgados'
# Please enter a commit message to explain why this merge is necessary,
# especially if it merges an updated upstream into a topic branch.
#
# Lines starting with '#' will be ignored, and an empty message aborts
# the commit.

                               [ 6 linhas lidas ]
^G Ajuda     ^O Gravar    ^F Onde está?^K Recortar  ^T Executar  ^C Local
^X Sair      ^R Ler o arq ^\ Substituir^U Colar     ^J Justificar^/ Ir p/ linha
Merge branch 'salgados'
A mensagem sugerida: "junta o branch 'salgados'". Na maioria das vezes, ela basta.
# Please enter a commit message …
"Escreva uma mensagem de commit explicando por que este merge é necessário…". As linhas que começam com # são comentários e não entram na mensagem; uma mensagem vazia cancela o commit.
^X Sair
Para aceitar a mensagem como está, aperte Ctrl+X. Se você mudou o texto, grave antes com Ctrl+O (o ^O Gravar do rodapé) e Enter, e depois saia com Ctrl+X.

Para não abrir o editor, aceite a mensagem pronta com --no-edit (ou dê a sua com -m, como no git commit). O resultado é o mesmo de sair do nano sem mudar nada:

$ git merge salgados --no-edit
Merge made by the 'ort' strategy.
 coxinha.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 coxinha.txt
$ git log --oneline --graph --all
*   bf9e22e (HEAD -> main) Merge branch 'salgados'      « o commit de merge
|\
| * c8eefba (salgados) Adiciona coxinha
* | abee64f Adiciona receita de feijoada
|/
* ae456dd (sobremesas) Adiciona receita de brigadeiro
* d6f2336 Adiciona receita de pudim
* 0244251 Adiciona receita de pão de queijo
* 7225e04 Adiciona receita de bolo
* 700bbd5 Cria o README
$ ls
README.md  brigadeiro.txt  feijoada.txt  pudim.txt
bolo.txt   coxinha.txt     pao.txt
Merge made by the 'ort' strategy.
"Merge feito pela estratégia 'ort'". ort é o nome do algoritmo que o Git usa para juntar; você não precisa escolher nada. O que importa: desta vez não foi Fast-forward, foi um merge com commit novo.
coxinha.txt | 1 +
O que o merge trouxe para o main: a coxinha. (A feijoada já estava aqui.)
* bf9e22e … Merge branch 'salgados'
No desenho, o commit de merge é onde as duas linhas se encontram: o |\ logo abaixo mostra que ele tem dois pais.
Antes:   A---B---C---D---E---F   ← main ← HEAD
                          \
                           G   ← salgados

Depois:  A---B---C---D---E---F---M   ← main ← HEAD    (M = bf9e22e, o commit de merge)
                          \     /
                           G----     ← salgados  (continua em G)

O commit de merge tem dois pais

$ git show --stat HEAD
commit bf9e22e411e6342f039b0e6f4414ff7bae43897b (HEAD -> main)
Merge: abee64f c8eefba                     « os dois pais: a feijoada e a coxinha
Author: Ana Souza <ana@exemplo.com>
Date:   Thu Oct 15 10:30:00 2026 -0300

    Merge branch 'salgados'

 coxinha.txt | 1 +
 1 file changed, 1 insertion(+)

Todo commit comum tem um pai (o anterior). O commit de merge tem dois: a linha Merge: abee64f c8eefba mostra os dois. O primeiro é o commit onde o main estava; o segundo, o do branch que foi juntado. Como o Git encontra o ponto de partida comum e combina as mudanças dos dois lados é o assunto da aula Merge de Três Vias.

A direção importa

Repare no desenho: o salgados continua em c8eefba, sem a feijoada. O merge só muda o branch atual. Se o Bruno, no salgados, também quisesse a feijoada, ele faria o merge ao contrário: git switch salgados e git merge main.

4. E as mudanças que ainda não foram commitadas?

Como no git switch: se elas não estão no caminho, o merge acontece e elas continuam lá. A Ana estava mexendo no feijoada.txt (sem commitar) e juntou um branch bebidas, que só traz um suco:

$ git status --short
 M feijoada.txt
$ git merge bebidas --no-edit
Updating bf9e22e..9547811
Fast-forward
 suco.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 suco.txt
$ git status --short
 M feijoada.txt                    « a mudança continua aqui, não commitada

Se o merge precisasse mexer num arquivo que você mudou, o Git se recusa (seção Quando dá errado). Mesmo assim, o melhor hábito é: git status limpo antes de todo merge. Fica muito mais fácil entender o resultado, e desfazer se precisar.

5. Depois do merge: arrumar a casa

Com o trabalho dentro do main, os branches juntados podem ser apagados. O git branch --merged lista quais (veja git branch):

$ git branch --merged
  bebidas
  chas
* main
  salgados
  sobremesas

Todos esses aceitam git branch -d sem reclamar (Renomeando e Apagando Branches). Os commits ficam no main; só as etiquetas somem.

Experimente

O terminal está na pasta receitas. Antes e depois de cada merge, olhe git log --oneline --graph --all e ls.

Missão: a Ana está no branch sobremesas, que tem duas receitas novas. Leve essas receitas para o main (lembre: vá para quem recebe e faça merge de quem tem o trabalho). Repare na palavra Fast-forward.

Missão: o main tem a feijoada e o salgados tem a coxinha. Junte o salgados no main aceitando a mensagem pronta do merge, sem abrir editor. Depois, veja o commit de merge com git log --oneline --graph --all e os dois pais com git show --stat HEAD.

Formas diferentes

ComandoO que faz
git merge NOMEJunta; se precisar de commit de merge, abre o editor com a mensagem pronta
git merge NOME --no-editJunta aceitando a mensagem pronta (Merge branch 'NOME')
git merge NOME -m 'mensagem'Junta com a sua mensagem
git merge --no-ff NOMECria commit de merge mesmo quando daria fast-forward (Merge Fast-forward)
git merge --ff-only NOMESó junta se der fast-forward; senão, recusa (Merge Fast-forward)
git pullBusca o trabalho do GitHub e faz o merge dele (git pull)
Pull request mesclado no site do GitHubO merge feito pelo botão do site (Pull Request)

Qual usar? No começo, git merge NOME, lendo a mensagem que o editor mostra; quando já souber o que esperar, --no-edit. Existe ainda outra forma de juntar trabalho, o git rebase, assunto do nível avançado.

Quando dá errado

merge: naoexiste - not something we can merge 
$ git merge naoexiste
merge: naoexiste - not something we can merge

"naoexiste: não é algo que a gente consiga juntar". Não existe branch (nem commit) com esse nome. Como confirmar: git branch. Cuidado com maiúsculas e com branches que só existem no GitHub (para esses, veja git fetch).

error: Your local changes to the following files would be overwritten by merge

Outra situação: o branch ajuste muda o título do README.md, e a Ana, no main, estava mexendo no mesmo arquivo sem commitar:

$ echo '# Receitas favoritas da Ana' > README.md
$ git merge ajuste
Updating 0244251..6a5ec12
error: Your local changes to the following files would be overwritten by merge:
        README.md
Please commit your changes or stash them before you merge.
Aborting

"As suas mudanças locais nos arquivos abaixo seriam sobrescritas pelo merge. Faça commit ou guarde-as (stash) antes do merge. Abortando." Nada mudou. Como resolver: commite a sua mudança (aí o Git junta as duas versões, ou mostra um conflito), guarde com git stash, ou descarte com git restore README.md. Depois, rode o merge de novo.

error: The following untracked working tree files would be overwritten by merge 
$ echo 'Chá de camomila' > cha.txt
$ git merge chas
Updating 9547811..d0304a0
error: The following untracked working tree files would be overwritten by merge:
        cha.txt
Please move or remove them before you merge.
Aborting

O branch chas traz um cha.txt, e na pasta já existe um cha.txt novo, nunca commitado. "Mova ou apague esses arquivos antes do merge." Como resolver: renomeie (mv cha.txt camomila.txt) ou apague o seu, e rode o merge de novo.

CONFLITO (conteúdo): conflito de mesclagem em bolo.txt

Quando os dois branches mudaram a mesma linha do mesmo arquivo, o Git não tem como saber qual versão vale. No laboratório, com o bolo com "1 xícara" de açúcar no main e "3 xícaras" num branch mais-doce, saiu:

$ git merge mais-doce
Mesclagem automática de bolo.txt
CONFLITO (conteúdo): conflito de mesclagem em bolo.txt
Automatic merge failed; fix conflicts and then commit the result.

"O merge automático falhou; resolva os conflitos e depois faça commit do resultado." Não é um desastre: o merge fica parado no meio, esperando você escolher. Como ler e resolver: Conflitos de Merge e Resolvendo Conflitos. Para desistir e voltar a como estava: git merge --abort (Desistindo de um Merge).

"Abriu uma tela estranha e eu não sei sair"

É o editor com a mensagem do commit de merge (seção 3). No nano: Ctrl+X para sair aceitando a mensagem. Se o editor configurado for o vim, digite :wq e Enter. Para não ver mais o editor no merge, use --no-edit; para trocar o editor, veja git config.

Juntei na direção errada

A Ana queria levar o sobremesas para o main, mas estava no sobremesas e rodou git merge main. Como confirmar: o git log --oneline --graph --all mostra a etiqueta do sobremesas andando, e não a do main. Como resolver: nada se perdeu; o main não foi tocado. Vá para o main (git switch main) e faça git merge sobremesas. Se o merge errado criou um commit de merge que você não quer, veja git reset.

4. Complete

Juntar o branch salgados aceitando a mensagem pronta, sem abrir o editor:

git merge salgados --

A mensagem pronta do commit de merge será:

Merge branch ''

5. Depois de git merge salgados (no main), o que acontece com o branch salgados?

Resumo

  • git merge NOME traz o trabalho de NOME para o branch atual. Vá primeiro para quem recebe (git switch main).
  • Se o branch atual não andou desde a separação, o merge é fast-forward: Updating X..Y, Fast-forward, e só a etiqueta anda.
  • Se os dois andaram, o Git cria um commit de merge, com dois pais (Merge made by the 'ort' strategy.). Ele abre o editor com Merge branch 'NOME'; --no-edit ou -m evitam o editor.
  • O branch juntado não muda; depois do merge, ele pode ser apagado com git branch -d.
  • Mudanças não commitadas que estão no caminho fazem o merge recusar (would be overwritten by merge). Faça merge com o git status limpo.
  • Mesma linha mudada nos dois lados = conflito: resolva ou desista com git merge --abort.

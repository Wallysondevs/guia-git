Git Projeto: Uma Funcionalidade num Branch

O site de receitas da Ana já tem uma página inicial e um README. Agora ela quer uma coisa nova: uma página de contato. Ela podia escrever direto no main, mas aprendeu que o main é a versão "boa", a que vai para o ar. Então vai fazer do jeito profissional: criar um branch (ramo) só para essa funcionalidade, trabalhar nele com calma, e só no fim juntar tudo no main. No meio do caminho, ainda aparece uma correção urgente. Neste projeto você acompanha cada passo, com as saídas reais do Git, e faz cada etapa você mesmo no terminal do guia.

Você vai aprender (na prática)
  • Criar um branch para uma funcionalidade e trocar para ele com git switch -c.
  • Fazer commits no branch sem mexer no main, e conferir isso com git log --oneline --graph --all.
  • Largar o trabalho pela metade, voltar ao main para uma correção urgente e depois retomar.
  • Juntar o branch no main com git merge e ler o histórico que se forma.
  • Apagar o branch que já foi juntado com git branch -d, sem medo de perder nada.

Este projeto junta o que você viu em O que é um Branch, git switch, git merge e Renomeando e Apagando Branches. Se algum comando parecer estranho, a aula dele explica com mais calma. Todas as saídas abaixo saíram do Git 2.53 do Ubuntu, na máquina da Ana (usuária ana, computador notebook), com o sistema em português.

Português e inglês misturados? É assim mesmo. A tradução do Git para o português do Brasil que vem no Ubuntu é parcial: algumas mensagens saem traduzidas (No ramo main), outras continuam em inglês (Switched to a new branch, nothing to commit). Ao lado de cada mensagem em inglês, você encontra a tradução. Em outros sistemas (Windows, macOS, outras distribuições), as frases podem sair diferentes ou todas em inglês; o sentido é o mesmo.

A ideia: o rascunho fica no caderno de rascunho

Pense numa confeiteira que tem um caderno de receitas passado a limpo, aquele que ela mostra para as clientes. Quando quer inventar uma receita nova, ela não rabisca nesse caderno: pega um caderno de rascunho, testa, risca, testa de novo. Só quando a receita está boa ela copia para o caderno bonito.

  • O caderno passado a limpo é o branch main.
  • O caderno de rascunho é o branch da funcionalidade (aqui, contato).
  • "Copiar a receita pronta para o caderno bonito" é o git merge.

E se, no meio do rascunho, uma cliente avisa que tem um erro no caderno bonito? A confeiteira deixa o rascunho aberto na mesa, corrige o caderno bonito, e volta ao rascunho. É exatamente o que a Ana vai fazer.

O plano do projeto, em cinco etapas:

  1. Criar o branch contato e entrar nele.
  2. Criar a página contato.html e pôr o link na página inicial (dois commits).
  3. Voltar ao main e corrigir um erro de digitação urgente no README.
  4. Juntar o branch contato no main.
  5. Apagar o branch, que já cumpriu o seu papel.

O ponto de partida

A pasta ~/receitas da Ana já é um repositório com dois commits: o README (com um erro de digitação que ninguém viu ainda: "Recitas") e a página inicial index.html. Antes de começar qualquer coisa nova, a Ana confere duas coisas: se está tudo commitado e onde ela está.

$ git status
No ramo main
nothing to commit, working tree clean      « nada pendente: pode começar
$ git log --oneline
93f770a (HEAD -> main) Cria a página inicial
9f0c742 Cria o README
  • No ramo main: ela está no branch main ("ramo" é a tradução de branch que o Git usa em português).
  • nothing to commit, working tree clean: "nada para commitar, pasta de trabalho limpa". Tudo o que ela mudou já está guardado em commits.
  • O git log --oneline mostra os dois commits, o mais novo em cima. O (HEAD -> main) diz que o HEAD (o "você está aqui") aponta para o main.
Por que conferir antes? Começar um branch com mudanças pendentes não é proibido (elas vão junto para o branch novo), mas confunde: depois você não sabe se aquela mudança era do main ou da funcionalidade. Comece sempre com o git status limpo.

Etapa 1: criar o branch e entrar nele

Um comando faz as duas coisas:

git switch
"Trocar" de branch (git switch). git 2.23+
-c
De create, "criar": cria o branch antes de trocar para ele.
contato
O nome do branch novo. Escolha um nome curto que diga o que vai ser feito nele: contato, pagina-sobre, corrige-menu.
$ git switch -c contato
Switched to a new branch 'contato'      « "trocou para o novo branch 'contato'"
$ git branch
* contato
  main
$ git status
No ramo contato
nothing to commit, working tree clean
  • Switched to a new branch 'contato': "trocou para o novo branch 'contato'". O branch foi criado e a Ana já está nele.
  • O git branch lista os branches; o asterisco * marca o atual.
  • O git status confirma: No ramo contato. A pasta não mudou nada: o branch novo nasce apontando para o mesmo commit em que ela estava.

Desenhando o histórico neste momento (cada letra é um commit):

A---B   ← main, contato (HEAD)

Criar um branch é só colar uma etiqueta nova no commit atual. Não copia arquivos, não gasta espaço, é instantâneo.

Missão 1: você está na pasta receitas da Ana, no main. Crie o branch contato e troque para ele com um comando só. Confira com git branch.

Etapa 2: trabalhar no branch

Agora a Ana trabalha normalmente: cria arquivos, adiciona, commita. Tudo o que ela commitar vai para o branch contato. Primeiro, a página de contato:

$ printf '<h1>Contato</h1>\n<p>Escreva para ana@exemplo.com</p>\n' > contato.html
$ git status
No ramo contato
Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
        contato.html

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)
$ git add contato.html
$ git commit -m 'Cria a página de contato'
[contato 92f5aa8] Cria a página de contato      « entrou no branch contato
 1 file changed, 2 insertions(+)
 create mode 100644 contato.html

Repare na primeira linha da resposta do commit: [contato …]. O Git sempre diz em qual branch o commit entrou. Se ali aparecesse [main …], ela teria esquecido de trocar de branch (veja "Quando dá errado", mais abaixo).

Segundo passo da funcionalidade: um link para o contato na página inicial. A Ana acrescenta uma linha no fim do index.html e confere a diferença antes de commitar:

$ echo '<a href="contato.html">Contato</a>' >> index.html
$ git diff
diff --git a/index.html b/index.html
index 9090d6e..04ff494 100644
--- a/index.html
+++ b/index.html
@@ -1,2 +1,3 @@
 <h1>Receitas da Ana</h1>
 <p>Bolo de cenoura</p>
+<a href="contato.html">Contato</a>      « a linha nova
$ git add index.html
$ git commit -m 'Põe o link do contato na página inicial'
[contato edd32b4] Põe o link do contato na página inicial
 1 file changed, 1 insertion(+)

O git diff mostra a linha nova com + na frente. Dois commits no branch. E o main? Ficou onde estava. O --all no git log mostra todos os branches, não só o atual:

$ git log --oneline --graph --all
* edd32b4 (HEAD -> contato) Põe o link do contato na página inicial
* 92f5aa8 Cria a página de contato
* 93f770a (main) Cria a página inicial      « o main ficou aqui
* 9f0c742 Cria o README
  • (HEAD -> contato) está no commit mais novo: é ali que a Ana está.
  • main continua no commit "Cria a página inicial", dois commits atrás.
A---B           ← main
     \
      C---D     ← contato (HEAD)

(Por enquanto, o --graph desenha tudo numa linha reta, porque contato só "andou na frente" do main. O galho aparece de verdade quando o main também andar, na etapa 3.)

Missão 2: você já está no branch contato. Crie o arquivo contato.html (por exemplo, com echo '<h1>Contato</h1>' > contato.html), adicione e faça o commit. No fim, o git status tem de estar limpo. Depois, rode git log --oneline --all e veja que o main não andou.

Etapa 3: uma correção urgente no main

No meio do trabalho, o Bruno manda uma mensagem: "Ana, o título do README está escrito Recitas!". Isso tem de ser corrigido no main, agora, sem esperar a página de contato ficar pronta. A Ana troca de branch:

$ git switch main
Switched to branch 'main'
$ ls
README.md  index.html      « cadê o contato.html?
$ cat index.html
<h1>Receitas da Ana</h1>
<p>Bolo de cenoura</p>      « sem o link
$ cat README.md
# Recitas da Ana      « o erro de digitação

Olhe o que aconteceu com a pasta: o contato.html sumiu, e o index.html voltou a não ter o link. Calma, nada se perdeu! Ao trocar de branch, o Git deixa a pasta exatamente como ela é no commit para onde o branch aponta. O main ainda não conhece a página de contato; ela está guardada no branch contato e volta quando a Ana voltar para lá.

Agora a correção, com um commit pequeno e uma mensagem clara:

$ echo '# Receitas da Ana' > README.md
$ git diff
diff --git a/README.md b/README.md
index 5658f18..2644316 100644
--- a/README.md
+++ b/README.md
@@ -1 +1 @@
-# Recitas da Ana
+# Receitas da Ana
$ git add README.md
$ git commit -m 'Corrige erro de digitação no README'
[main d9426f7] Corrige erro de digitação no README      « agora no main
 1 file changed, 1 insertion(+), 1 deletion(-)

Agora sim, o histórico tem um galho de verdade: o main andou para um lado (a correção) e o contato para o outro (a página). O --graph desenha isso:

$ git log --oneline --graph --all
* edd32b4 (contato) Põe o link do contato na página inicial
* 92f5aa8 Cria a página de contato
| * d9426f7 (HEAD -> main) Corrige erro de digitação no README
|/
* 93f770a Cria a página inicial      « o ponto onde os galhos se separam
* 9f0c742 Cria o README
  • Cada * é um commit. As barras | e / mostram de onde cada um saiu.
  • O commit da correção (main) e os dois do contato saem do mesmo pai, "Cria a página inicial".
A---B---E           ← main (HEAD)
     \
      C---D         ← contato

A Ana pode voltar ao contato quando quiser. Repare que, lá, o README ainda tem o erro: a correção está só no main, por enquanto.

$ git switch contato
Switched to branch 'contato'
$ cat README.md
# Recitas da Ana      « aqui a correção ainda não chegou
$ git switch main
Switched to branch 'main'

Missão 3: você está no branch contato, com a página de contato já commitada. Volte ao main, corrija o título do README para # Receitas da Ana (com echo '# Receitas da Ana' > README.md) e faça o commit da correção no main. Rode ls no main e veja que o contato.html não está lá.

Etapa 4: juntar o branch no main

A página de contato ficou pronta. Hora de passar a limpo. A regra para lembrar: você vai para o branch que vai receber e, de lá, pede para juntar o outro.

git switch main
Primeiro, ir para quem recebe: o main.
git merge
"Mesclar": trazer para o branch atual os commits de outro branch (git merge).
contato
O branch que vai ser trazido.
$ git merge contato
Merge made by the 'ort' strategy.      « "merge feito pela estratégia 'ort'"
 contato.html | 2 ++
 index.html   | 1 +
 2 files changed, 3 insertions(+)
 create mode 100644 contato.html
  • Merge made by the 'ort' strategy. ("merge feito pela estratégia 'ort'"): como os dois branches andaram, o Git fez um merge de três vias e criou um commit de merge, que tem dois pais. "ort" é o nome do algoritmo de merge padrão do Git.
  • As linhas seguintes resumem o que entrou no main: o contato.html novo (create mode, "criado") e uma linha a mais no index.html.
E a mensagem do commit de merge? No seu terminal, o git merge pode abrir o editor de texto com a mensagem pronta (Merge branch 'contato'). Basta salvar e fechar (no nano: Ctrl+O, Enter, Ctrl+X). Para pular o editor e aceitar a mensagem pronta, use git merge --no-edit contato; para escrever a sua, git merge -m 'Junta a página de contato' contato.

O desenho do histórico agora mostra o galho se fechando:

$ git log --oneline --graph
*   a8b971a (HEAD -> main) Merge branch 'contato'      « o commit de merge
|\
| * edd32b4 (contato) Põe o link do contato na página inicial
| * 92f5aa8 Cria a página de contato
* | d9426f7 Corrige erro de digitação no README
|/
* 93f770a Cria a página inicial
* 9f0c742 Cria o README
A---B---E-------M     ← main (HEAD)
     \         /
      C---D---        ← contato

E a pasta do main tem as duas coisas: a página de contato e a correção do README.

$ ls
README.md  contato.html  index.html
$ cat index.html
<h1>Receitas da Ana</h1>
<p>Bolo de cenoura</p>
<a href="contato.html">Contato</a>
$ cat README.md
# Receitas da Ana

Missão 4: você está no main, que já tem a correção do README. Junte o branch contato no main. No fim, confira com git log --oneline --graph e ls: o main tem de ter o contato.html e o README corrigido.

Etapa 5: apagar o branch

O branch contato cumpriu o seu papel: tudo o que estava nele agora também está no main. Deixar branches velhos acumulando só atrapalha. Antes de apagar, a Ana confere quais branches já foram juntados no atual:

$ git branch --merged
  contato      « já está dentro do main
* main
$ git branch -d contato
Deleted branch contato (was edd32b4).      « "branch contato apagado (era edd32b4)"
$ git branch
* main
$ git log --oneline --graph
*   a8b971a (HEAD -> main) Merge branch 'contato'
|\
| * edd32b4 Põe o link do contato na página inicial      « os commits continuam aqui
| * 92f5aa8 Cria a página de contato
* | d9426f7 Corrige erro de digitação no README
|/
* 93f770a Cria a página inicial
* 9f0c742 Cria o README
$ git status
No ramo main
nothing to commit, working tree clean
  • git branch --merged lista os branches cujos commits já estão no branch atual. O contato aparece: pode apagar sem medo.
  • git branch -d contato apaga a etiqueta. A mensagem mostra o hash para onde ela apontava, caso você se arrependa (dá para recriar com git branch contato + esse hash).
  • O histórico continua igual: apagar um branch não apaga commits. Os commits C e D continuam lá, agora alcançáveis pelo main através do commit de merge.

Missão 5: o branch contato já foi juntado no main. Confira com git branch --merged e apague o branch com segurança.

Em equipe, no GitHub, a etapa 4 costuma ser feita por um pull request em vez de um git merge no seu computador: você envia o branch, alguém revisa, e o merge acontece no site. A ideia de "um branch por funcionalidade" é a mesma (veja O GitHub Flow).

Quando dá errado

"Your local changes … would be overwritten by checkout" ao trocar de branch 
$ git switch main
error: Your local changes to the following files would be overwritten by checkout:
        index.html
Please commit your changes or stash them before you switch branches.
Aborting

O que aconteceu: a Ana mudou o index.html no branch contato e não commitou. O index.html do main é diferente; trocar de branch apagaria a mudança dela. O Git recusou ("Aborting" = "desistindo") para proteger o trabalho. A mensagem diz: "as suas mudanças locais nestes arquivos seriam sobrescritas; faça commit ou stash delas antes de trocar de branch".

Como confirmar: git status mostra o index.html como modificado.

Como resolver: três caminhos. Se a mudança está boa, commite no contato e depois troque. Se ainda está pela metade, guarde-a com git stash, troque, e na volta use git stash pop. Se a mudança não presta, descarte com git restore index.html (cuidado: não tem volta).

"fatal: a branch named 'contato' already exists" 
$ git switch -c contato
fatal: a branch named 'contato' already exists

O que aconteceu: o -c pede para criar o branch, e ele já existe ("já existe um branch chamado 'contato'").

Como resolver: para só entrar num branch que já existe, tire o -c: git switch contato. Se queria um branch novo, escolha outro nome.

"cannot delete branch 'contato' used by worktree" 
$ git branch -d contato
error: cannot delete branch 'contato' used by worktree at '/home/ana/receitas'

O que aconteceu: a Ana tentou apagar o branch em que ela está. A mensagem diz "não dá para apagar o branch 'contato', usado pela pasta de trabalho em /home/ana/receitas".

Como resolver: troque para outro branch primeiro (git switch main) e apague de lá.

"the branch 'contato' is not fully merged" 
$ git switch main
Switched to branch 'main'
$ git branch -d contato
error: the branch 'contato' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D contato'
hint: Disable this message with "git config set advice.forceDeleteBranch false"

O que aconteceu: ela tentou apagar o contato antes do merge. O branch tem commits que o main não tem ("não foi totalmente juntado"); apagar a etiqueta deixaria esses commits sem nome. O -d minúsculo é seguro justamente por isso: ele se recusa.

Como confirmar: git log --oneline main..contato lista os commits que estão no contato e faltam no main.

Como resolver: faça o merge primeiro (etapa 4) e apague depois. A dica (hint) sugere o -D maiúsculo, que apaga assim mesmo: use só se você tem certeza de que não quer aqueles commits (e, se se arrepender, veja git reflog).

Esqueci de criar o branch e commitei no main

O que aconteceu: a primeira linha da resposta do git commit mostrou [main …] em vez de [contato …].

Como resolver: se ainda não enviou nada para o GitHub, crie o branch agora, no ponto em que está (git branch contato: o commit passa a estar nos dois), e depois volte o main um commit com git reset --hard HEAD~1, com o git status limpo (veja git reset antes, porque o --hard descarta mudanças não commitadas). Por fim, git switch contato e continue.

Resumo

  • Uma funcionalidade nova = um branch novo: git switch -c nome, sempre partindo de um git status limpo.
  • Os commits entram no branch atual; a primeira linha da resposta do git commit ([contato …]) confirma qual é.
  • Trocar de branch troca os arquivos da pasta. O que sumiu está guardado no outro branch.
  • Correção urgente? Commite (ou guarde) o que está no meio, git switch main, corrija, commite, e volte com git switch contato.
  • Para juntar: vá para quem recebe (git switch main) e rode git merge contato. Se os dois andaram, nasce um commit de merge.
  • git log --oneline --graph --all desenha os galhos; git branch --merged mostra o que já pode ser apagado com git branch -d.

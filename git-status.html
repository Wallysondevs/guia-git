Git status

Se você só puder decorar um comando do Git, decore este. O git status ("situação") responde à pergunta que você vai fazer o dia inteiro: "como estão as coisas agora?". Ele diz em que ramo você está, quais arquivos são novos, quais mudaram, quais já estão preparados para o próximo commit e, o melhor de tudo, sugere o próximo comando nas linhas entre parênteses. Ele nunca muda nada: só olha e conta. Por isso, na dúvida, rode git status.

Você vai aprender
  • A ler o git status em todos os estados: repositório sem commits, arquivo novo, arquivo modificado, arquivo preparado, o mesmo arquivo preparado e modificado ao mesmo tempo, arquivo apagado e a pasta limpa.
  • O que quer dizer cada linha e cada dica entre parênteses ((use "git add <arquivo>..." …)).
  • Os três "estados" de um arquivo: não rastreado, modificado e preparado.
  • O formato curto, git status -s, com as letras ??, A, M e D.
  • Os erros: not a git repository e o arquivo que "não aparece".

Todas as saídas desta aula são reais, do Git da máquina da Ana (Ubuntu 26.04, em português). Com o sistema em inglês, o Git mostra as mesmas linhas em inglês; a aula mostra a frase original quando ela aparece muito em tutoriais.

A ideia: o painel do carro

Antes de sair com o carro, você olha o painel: tem combustível? alguma luz acesa? a porta está aberta? O painel não dirige o carro; ele só mostra a situação, e às vezes diz o que fazer ("abasteça", "feche a porta"). O git status é o painel do Git. Ele olha os três lugares que você conheceu em Seu Primeiro Commit:

pasta de trabalho  ──git add──▶  área de preparo  ──git commit──▶  histórico
   (você edita)                  (a mesa da foto)                  (o álbum)

e compara uns com os outros:

  • o que está na pasta e o Git nunca viu → arquivo não rastreado;
  • o que está na pasta e é diferente do que está na área de preparo → mudança não preparada;
  • o que está na área de preparo e é diferente do último commit → mudança preparada (vai entrar no próximo commit).

Cada um desses grupos vira um bloco na saída do git status. Vamos ver todos, na ordem em que aparecem na vida de um projeto.

Anatomia

git
O programa Git.
status
O subcomando: "mostre a situação". Funciona em qualquer pasta dentro do repositório (na pasta principal ou numa subpasta).
-s / --short (opcional)
Formato curto, uma linha por arquivo (seção O formato curto).
-b / --branch (opcional)
No formato curto, mostra também a linha do ramo.
caminho (opcional)
Mostra só a situação daquele arquivo ou pasta: git status receitas/.

Estado 1: repositório novo, sem nenhum commit

A Ana acabou de criar a pasta receitas e rodou git init (aula git init). A pasta está vazia:

$ git status
No ramo main                                       « 1. em que ramo você está

No commits yet                                     « 2. o histórico está vazio

nada para enviar (crie/copie arquivos e use "git add" para registrar)   « 3. resumo + dica
No ramo main
"No ramo main". Todo git status começa dizendo em que ramo (branch) você está. Por enquanto só existe o main ("principal"); os ramos têm um capítulo próprio (O que é um Branch). Em inglês: On branch main.
No commits yet
"Nenhum commit ainda". Esta linha só aparece enquanto o repositório não tem nenhum commit.
nada para enviar (crie/copie arquivos e use "git add" para registrar)
O resumo: não há nada para commitar (a tradução do Git chama o commit de "envio" ou "submissão"). A dica: crie ou copie arquivos e use git add para o Git passar a rastreá-los.
Por que o painel mistura português e inglês?

A tradução brasileira do Git 2.53 (o do Ubuntu 26.04) está incompleta. Algumas frases saem em português, outras em inglês, e às vezes as duas coisas na mesma linha (use "git add" to registrar). É assim mesmo no seu terminal. Nesta aula, toda frase em inglês ganha tradução. Saber as frases em inglês também ajuda a pesquisar e a ler tutoriais, que quase sempre mostram o Git em inglês.

Estado 2: um arquivo novo (não rastreado)

A Ana cria o README.md:

$ echo '# Receitas da Ana' > README.md
$ git status
No ramo main

No commits yet

Arquivos não monitorados:                                                   « o título do bloco
  (utilize "git add <arquivo>..." para incluir o que será submetido)        « a dica
	README.md                                                                   « os arquivos

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)
Arquivos não monitorados:
"Arquivos não monitorados" = não rastreados (em inglês, Untracked files:). São arquivos que estão na pasta, mas que o Git nunca guardou. Ele só avisa que eles existem.
(utilize "git add <arquivo>..." para incluir o que será submetido)
A dica: "use git add e o nome do arquivo para incluí-lo no que vai ser commitado". Nas dicas, <arquivo> é um espaço para você pôr o nome (sem os sinais < >), e os ... querem dizer "um ou mais".
README.md
A lista de arquivos do bloco, cada um numa linha, recuada com uma tabulação. No terminal de verdade, os nomes deste bloco aparecem em vermelho (as cores ajudam a ver rápido: vermelho = ainda não vai entrar no commit).
nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)
A linha final resume: "nada foi adicionado ao commit, mas há arquivos não rastreados; use git add para rastreá-los". Se você rodar git commit agora, nada acontece.
Rastreado ou não rastreado?

Um arquivo rastreado (tracked) é um arquivo que o Git conhece: ele está no último commit ou na área de preparo. Só dos rastreados o Git guarda versões. Todo arquivo novo começa não rastreado (untracked), e só passa a ser rastreado com um git add.

Estado 3: o arquivo preparado, antes do primeiro commit

$ git add README.md
$ git status
No ramo main

No commits yet

Mudanças a serem submetidas:                                    « vai entrar no próximo commit
  (utilize "git rm --cached <arquivo>..." para não apresentar)    « como desfazer o add
	new file:   README.md                                         « arquivo novo
Mudanças a serem submetidas:
"Mudanças que vão ser commitadas" (em inglês, Changes to be committed:): é a área de preparo. Tudo o que está neste bloco entra no próximo git commit. No terminal, estes nomes aparecem em verde.
(utilize "git rm --cached <arquivo>..." para não apresentar)
A dica de como voltar atrás: git rm --cached README.md tira o arquivo da área de preparo e o devolve a "não rastreado" (o arquivo continua na pasta; o --cached quer dizer "só na área de preparo"). "Para não apresentar" é a tradução, meio torta, de "para tirar da área de preparo". Esta dica só aparece antes do primeiro commit; depois dele, a dica vira git restore --staged (Estado 6).
new file: README.md
A etiqueta diz que tipo de mudança é: new file = "arquivo novo". As outras etiquetas que você vai ver: modified (modificado), deleted (apagado), renamed (renomeado).
(a linha vazia no fim)
Quando há algo preparado, o Git não mostra linha de resumo: o bloco verde já diz que o próximo commit tem conteúdo.

Estado 4: tudo limpo

A Ana faz o primeiro commit e pergunta de novo:

$ git commit -m "Adiciona o README"
[main (root-commit) d84dc97] Adiciona o README
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
$ git status
No ramo main
nothing to commit, working tree clean
No ramo main
O ramo, como sempre. A linha No commits yet sumiu: agora existe um commit.
nothing to commit, working tree clean
"Nada a commitar, pasta de trabalho limpa" (working tree = "árvore de trabalho", a pasta de trabalho). Nenhum arquivo novo, nenhum modificado, nada preparado.

"Limpo" é o estado de descanso: tudo o que está na pasta é igual ao último commit. É uma boa hora para trocar de ramo, mandar para o GitHub ou desligar o computador tranquilo.

Missão: o repositório receitas tem um README.md não rastreado. Rode git status antes e depois de cada passo (git add README.md, depois git commit -m "Adiciona o README") e veja o painel mudar, até ele dizer que está tudo limpo.

Estado 5: um arquivo rastreado foi modificado

A Ana já tem dois commits (o README e o bolo.txt). Ela acrescenta uma linha na receita de bolo:

$ cat bolo.txt
Bolo de cenoura
3 cenouras
$ echo '2 xícaras de açúcar' >> bolo.txt
$ git status
No ramo main
Changes not staged for commit:                                            « rastreado, mudou, não preparado
  (utilize "git add <arquivo>..." para atualizar o que será submetido)     « dica para avançar
  (use "git restore <file>..." to discard changes in working directory)  « dica para desfazer
	modified:   bolo.txt

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
Changes not staged for commit:
"Mudanças não preparadas para o commit". O arquivo é rastreado (está no último commit), foi modificado na pasta, e a modificação ainda não foi para a área de preparo. Se você commitar agora, ela não entra. Os nomes saem em vermelho.
(utilize "git add <arquivo>..." para atualizar o que será submetido)
Dica para avançar: git add bolo.txt atualiza a área de preparo com a versão nova.
(use "git restore <file>..." to discard changes in working directory)
Dica para desfazer: "use git restore para descartar as mudanças na pasta de trabalho". Isso volta o arquivo ao que estava no último commit e apaga a sua edição para sempre (aula git restore). Use só quando quiser jogar a mudança fora.
modified: bolo.txt
"Modificado": o arquivo existe no último commit e mudou desde então.
nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
"Nenhuma mudança foi adicionada ao commit": prepare com git add, ou use git commit -a, que prepara e commita todos os rastreados de uma vez (aula git commit).

Estado 6: a modificação preparada

$ git add bolo.txt
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)       « como tirar da área de preparo
	modified:   bolo.txt
Mudanças a serem submetidas:
O bloco verde: a modificação do bolo.txt vai entrar no próximo commit.
(use "git restore --staged <file>..." to unstage)
"Use git restore --staged para tirar da área de preparo" (unstage). Ele desfaz só o git add: a sua edição continua no arquivo, e ele volta para o bloco "não preparadas" (aula Tirando da Área de Preparo). Em tutoriais antigos, essa dica aparece como git reset HEAD <file>: é o comando antigo para a mesma coisa.
modified: bolo.txt
A etiqueta agora é modified, e não new file, porque o bolo.txt já existia no último commit.

Repare na diferença com o Estado 3: lá, o arquivo era novo arquivo e a dica falava em git rm --cached; aqui, depois do primeiro commit, ele é modificado e a dica é git restore --staged. É o Git sugerindo o comando certo para cada situação.

Estado 7: o mesmo arquivo preparado e modificado

Este é o estado que mais confunde quem está começando. A Ana preparou o bolo.txt (Estado 6) e, antes de commitar, lembrou de mais uma coisa e editou o arquivo de novo:

$ echo '3 ovos' >> bolo.txt
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt                                            « a versão com o açúcar

Changes not staged for commit:
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   bolo.txt                                            « os ovos, ainda não preparados

O bolo.txt aparece duas vezes, e isso não é erro. A explicação:

em "Mudanças a serem submetidas"
A versão que está na área de preparo, a do momento do git add: com o açúcar, sem os ovos. É ela que entra no próximo commit.
em "Changes not staged for commit"
A diferença entre a pasta e a área de preparo: a linha dos ovos, escrita depois do git add.

Agora existem três versões do bolo.txt ao mesmo tempo:

LugarConteúdo do bolo.txt
Último commitBolo de cenoura / 3 cenouras
Área de preparoBolo de cenoura / 3 cenouras / 2 xícaras de açúcar
Pasta de trabalhoBolo de cenoura / 3 cenouras / 2 xícaras de açúcar / 3 ovos

O git add tira uma "cópia" do arquivo no momento em que você roda o comando. O que você muda depois não entra sozinho. Se ela commitar agora, o commit leva só a versão preparada; a linha nova fica para trás. Para levar as duas mudanças, prepare de novo:

$ git add bolo.txt
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt

A aula A Área de Preparo mostra esse caso com o git diff, que mostra exatamente qual linha está em qual lugar.

Missão: rode git status: o bolo.txt está preparado e modificado ao mesmo tempo. Faça um commit que leve as duas mudanças (o açúcar e os ovos). Dica: o que o git status sugere para a parte não preparada?

Estado 8: dois arquivos, três situações

Na vida real, o painel mistura tudo. A Ana preparou o bolo.txt, mexeu no README.md sem preparar e criou o pudim.txt:

$ echo 'Pudim de leite' > pudim.txt
$ echo 'Site com as receitas da família.' >> README.md
$ echo '1 xícara de óleo' >> bolo.txt
$ git add bolo.txt
$ git status
No ramo main
Mudanças a serem submetidas:                                      « 1º: preparado (verde)
  (use "git restore --staged <file>..." to unstage)
	modified:   bolo.txt

Changes not staged for commit:                                    « 2º: rastreado, não preparado (vermelho)
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   README.md

Arquivos não monitorados:                                         « 3º: não rastreado (vermelho)
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	pudim.txt

Os blocos aparecem sempre nesta ordem: primeiro o que vai entrar no próximo commit, depois o que mudou e não vai entrar, por último o que o Git nem conhece. Se ela rodar git commit agora, só o bolo.txt entra.

Estado 9: um arquivo apagado

A Ana apagou o pudim.txt (que já estava num commit) com o rm do terminal:

$ rm pudim.txt
$ git status
No ramo main
Changes not staged for commit:
  (utilize "git add/rm <arquivo>..." para atualizar o que será submetido)    « add/rm: os dois servem
  (use "git restore <file>..." to discard changes in working directory)
	deleted:    pudim.txt                                                      « apagado

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
$ git add pudim.txt
$ git status
No ramo main
Mudanças a serem submetidas:
  (use "git restore --staged <file>..." to unstage)
	deleted:    pudim.txt

Apagar também é uma mudança. A etiqueta é deleted ("apagado"), e a dica mudou para git add/rm: tanto git add pudim.txt quanto git rm pudim.txt preparam o apagamento (sim, dá para fazer git add de um arquivo que não existe mais: você está preparando a "falta" dele). E o git restore pudim.txt traz o arquivo de volta, do último commit: o rm do terminal não é o fim do mundo num arquivo que já estava num commit. Depois do git add, o apagamento vai para o bloco verde e entra no próximo commit. O jeito de apagar avisando o Git ao mesmo tempo é o git rm (aula Apagando Arquivos).

Estado 10: o ramo e o GitHub

Quando o repositório está ligado a um repositório remoto (o GitHub, por exemplo; veja O que é um Repositório Remoto), o git status ganha uma linha que compara o seu ramo com o de lá:

$ git status
No ramo main
Your branch is up to date with 'origin/main'.          « igual ao GitHub

nothing to commit, working tree clean

A Ana fez um commit novo e ainda não o enviou:

$ git status
No ramo main
Seu ramo está à frente de 'origin/main' por 1 submissão.      « você tem 1 commit que o GitHub não tem
  (use "git push" to publish your local commits)

nothing to commit, working tree clean

E, outro dia, o colega Bruno enviou um commit e a Ana baixou a novidade com git fetch:

$ git status
No ramo main
Seu ramo está atrás de 'origin/main' em 1 submissão, e pode ser avançado.    « o GitHub tem 1 commit que você não tem
  (use "git pull" to update your local branch)

nothing to commit, working tree clean

Por fim, os dois fizeram commits ao mesmo tempo:

$ git status
No ramo main
O seu branch e 'origin/main' divergiram-se,
e cada um tem 1 e 1 submissões, respectivamente.
  (use "git pull" if you want to integrate the remote branch with yours)

nothing to commit, working tree clean
'origin/main'
A última notícia que o seu Git tem do ramo main do GitHub (origin é o apelido do repositório remoto).
Your branch is up to date with 'origin/main'.
"O seu ramo está em dia com o origin/main": o mesmo histórico dos dois lados.
à frente … por 1 submissão / (use "git push" to publish your local commits)
Você tem 1 commit que o GitHub ainda não tem. Dica: "use git push para publicar os seus commits" (aula git push).
atrás … em 1 submissão, e pode ser avançado / (use "git pull" to update your local branch)
O GitHub tem 1 commit que você não tem, e o seu ramo pode simplesmente "andar para a frente" até ele. Dica: "use git pull para atualizar o seu ramo" (aula git pull).
divergiram-se, e cada um tem 1 e 1 submissões
Cada lado tem 1 commit que o outro não tem. Dica: "use git pull se quiser juntar o ramo remoto ao seu".

Atenção: o git status não pergunta nada ao GitHub. Ele compara com a última vez que o seu Git conversou com o GitHub (num push, fetch ou pull). "Up to date" pode ser notícia velha: rode git fetch antes, se quiser a situação de agora. Isso aparece em detalhe em Branch de Rastreamento. em detalhe em Branch de Rastreamento.

O formato curto: git status -s

Quando você já entende o painel, as frases longas cansam. O -s (de short, "curto") mostra uma linha por arquivo, com um código de duas letras na frente. Na situação do Estado 8:

$ git status -s
 M README.md       « 2ª coluna: modificado, não preparado
M  bolo.txt        « 1ª coluna: modificado e preparado
?? pudim.txt       « novo, não rastreado

A Ana prepara o pudim.txt e, logo depois, acrescenta uma linha nele:

$ git add pudim.txt
$ echo 'Leite condensado' >> pudim.txt
$ git status -s
 M README.md
M  bolo.txt
AM pudim.txt       « novo e preparado (A), e modificado depois (M)

As duas colunas do código são os dois "lugares" do painel:

  • a 1ª coluna compara a área de preparo com o último commit: é o que vai entrar no próximo commit;
  • a 2ª coluna compara a pasta com a área de preparo: é o que mudou e ainda não foi preparado.
CódigoQuer dizerBloco no git status normal
??Novo, não rastreadoArquivos não monitorados
A Novo, preparado (Added)Mudanças a serem submetidas: new file
M Modificado, preparadoMudanças a serem submetidas: modified
 MModificado, não preparadoChanges not staged: modified
MMModificado, preparado, e modificado de novoNos dois blocos (Estado 7)
AMNovo, preparado, e modificado depoisNos dois blocos
D Apagado, preparado (Deleted)Mudanças a serem submetidas: deleted
 DApagado, não preparadoChanges not staged: deleted

Saídas reais dos dois últimos casos, no Estado 9:

$ rm pudim.txt
$ git status -s
 D pudim.txt
$ git add pudim.txt
$ git status -s
D  pudim.txt

Existem outras letras, para situações que você vai ver mais adiante: R (renomeado, em git mv) e U (conflito, em Conflitos de Merge). Quando a pasta está limpa, o git status -s não mostra nada.

Com -sb (curto + ramo), aparece também a linha do ramo, começando com ##:

$ git status -sb
## main
 M README.md
M  bolo.txt
AM pudim.txt

Num repositório ligado ao GitHub, essa linha também mostra a comparação do Estado 10, bem resumida:

$ git status -sb
## main...origin/main [à frente 1]

Os outros casos saem como ## main...origin/main (em dia), [atrás 1] e [à frente 1, atrás 1].

Missão: rode git status -s e descubra qual arquivo é novo (??) e qual foi modificado ( M). Prepare só o arquivo novo e rode git status -s de novo: o ?? deve virar A.

Formas diferentes de ver a situação

ComandoQuando usar
git statusSempre que estiver em dúvida, e quando está aprendendo: as dicas ensinam.
git status -sPara uma olhada rápida, quando você já sabe ler as letras.
git status -sbOlhada rápida + o ramo atual e se está à frente ou atrás do GitHub.
git status pasta/Só a situação de uma pasta ou arquivo.
git diff e git diff --stagedQuando você quer ver o que mudou dentro dos arquivos, linha por linha, e não só quais arquivos (aulas git diff e git diff --staged).

Quando dá errado

"not a git repository" 
$ cd ~
$ git status
fatal: not a git repository (or any of the parent directories): .git

"Fatal: não é um repositório Git (nem nenhuma das pastas acima)". O Git procura a pasta escondida .git na pasta atual e nas de cima, e não achou. A Ana estava na pasta pessoal; o repositório é a receitas. Como resolver: cd receitas (confira onde está com pwd). Se a pasta do projeto nunca recebeu git init, veja git init.

Uma pasta vazia não aparece 
$ mkdir fotos
$ git status
No ramo main
nothing to commit, working tree clean

O Git guarda arquivos, não pastas: uma pasta vazia não existe para ele. Assim que ela ganha um arquivo, aparece, mas como a pasta inteira, com uma / no fim:

$ touch fotos/bolo.jpg
$ git status
No ramo main
Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	fotos/

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)

Quando a pasta inteira é nova, o Git resume: mostra só fotos/, não cada arquivo dentro dela. Para ver os arquivos um por um, use -u (de untracked):

$ git status -u
No ramo main
Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	fotos/bolo.jpg

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)
Mudei o arquivo e o commit não levou a mudança

É o Estado 7: o arquivo foi preparado e editado de novo antes do commit. O commit leva a versão que estava na área de preparo, e o git status depois do commit ainda mostra o arquivo em Mudanças não preparadas. Como resolver: git add arquivo e outro commit (ou, se o commit foi o último e ainda não foi para o GitHub, corrigi-lo com --amend).

Uma lista enorme de arquivos não rastreados

Se o painel mostra dezenas de arquivos que você nunca quer commitar (programas compilados, a pasta node_modules, arquivos temporários do editor), não use git add .: ensine o Git a ignorá-los com o .gitignore (aula Ignorando Arquivos). Arquivos ignorados somem do git status.

Missão final: arrume o painel

Missão: rode git status e leia o painel. Faça um commit que leve a mudança do bolo.txt e o arquivo novo pudim.txt, mas não o notas.tmp. Depois, acrescente uma linha no README.md (por exemplo, echo 'Site de receitas' >> README.md) e não prepare: o painel deve terminar com o README em "não preparadas" e o notas.tmp em "não monitorados".

Resumo

  • O git status mostra a situação e nunca muda nada. Rode antes e depois de cada add e de cada commit.
  • Os blocos, sempre nesta ordem: Mudanças a serem submetidas (vai entrar no próximo commit), Changes not staged for commit (rastreado, mudou, não vai entrar) e Arquivos não monitorados (o Git não conhece).
  • As linhas entre parênteses são dicas: elas dizem o comando para avançar (git add, git commit) e para voltar atrás (git restore, git restore --staged, git rm --cached).
  • Um arquivo pode estar preparado e modificado: o git add guarda a versão daquele momento.
  • nothing to commit, working tree clean quer dizer que a pasta é igual ao último commit.
  • git status -s: ?? novo, A novo preparado, M modificado, D apagado; 1ª coluna = preparado, 2ª coluna = não preparado.

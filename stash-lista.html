Git Vários Stashes (list, apply, pop, drop)

Na aula git stash, a Ana guardou uma coisa na gaveta e tirou logo depois. Mas a gaveta aceita vários itens: hoje o fermento do bolo, amanhã o leite do pudim, depois uma frase no README. Cada git stash põe um item novo em cima dos outros, como uma pilha de pratos. Nesta aula você vai ver a pilha inteira, escolher qual item aplicar, apagar os que não servem mais, e o que fazer quando um stash não "encaixa" mais no arquivo.

Você vai aprender
  • Como a pilha funciona: stash@{0}, stash@{1}, stash@{2}… e o git stash list.
  • Como espiar um item específico com git stash show.
  • A diferença entre apply (aplica e mantém) e pop (aplica e apaga); e como apagar com drop e clear.
  • O que fazer quando o pop dá conflito, e o atalho git stash branch.
  • Como recuperar um stash apagado sem querer.

Todas as saídas desta aula vieram do Git 2.53.0 da máquina da Ana (usuária ana, computador notebook), com o sistema em português. A tradução do Git no Ubuntu é incompleta, e as mensagens do stash saem quase todas em inglês: estão copiadas como saíram e ganham tradução na explicação.

A ideia: uma pilha de pratos

Numa pilha de pratos, o último que você põe fica em cima, e é o primeiro que você tira. O stash é igual:

  • cada git stash põe um item no topo;
  • o item do topo se chama stash@{0}; o de baixo dele, stash@{1}; e assim por diante;
  • quando você guarda um item novo, todos os outros descem uma posição (o que era stash@{0} vira stash@{1}), e quando você tira um, os de baixo sobem.

Diferente da pilha de pratos, você pode tirar um item do meio, dizendo o nome dele. Os comandos sem nome (pop, apply, drop, show) usam sempre o stash@{0}, o do topo.

1. Enchendo a pilha e listando: git stash list

A Ana tem um repositório com README.md, bolo.txt e pudim.txt. Ao longo do dia, ela começa três mudanças e guarda cada uma antes de terminar:

$ printf -- '- 1 colher de fermento\n' >> bolo.txt
$ git stash push -m 'fermento no bolo'
Saved working directory and index state On main: fermento no bolo
$ printf -- '- 1 lata de leite\n' >> pudim.txt
$ git stash push -m 'leite no pudim'
Saved working directory and index state On main: leite no pudim
$ printf 'Site de receitas da família.\n' >> README.md
$ git stash
Saved working directory and index state WIP on main: c36bc0c Primeiras receitas
$ git stash list
stash@{0}: WIP on main: c36bc0c Primeiras receitas
stash@{1}: On main: leite no pudim
stash@{2}: On main: fermento no bolo

(O printf … >> arquivo acrescenta uma linha no fim do arquivo; o -m dá um nome ao stash, como na aula anterior.) Leia a lista de cima para baixo:

stash@{0}: WIP on main: c36bc0c Primeiras receitas
O topo da pilha: o último guardado, a frase do README. Como foi guardado sem -m, ganhou o nome automático: WIP (work in progress, "trabalho em andamento") no main, a partir do commit c36bc0c.
stash@{1}: On main: leite no pudim
O segundo, com o nome que a Ana deu. Quando ele foi guardado, ele era o stash@{0}; desceu quando o do README chegou.
stash@{2}: On main: fermento no bolo
O primeiro que foi guardado, agora no fundo da pilha.

Viu por que vale a pena usar -m? Com três itens chamados WIP on main: c36bc0c Primeiras receitas, a Ana não saberia qual é qual.

2. Espiando um item: git stash show stash@{N}

$ git stash show stash@{1}
 pudim.txt | 1 +
 1 file changed, 1 insertion(+)
$ git stash show -p stash@{2}
diff --git a/bolo.txt b/bolo.txt
index 92e7eaf..84a5a0b 100644
--- a/bolo.txt
+++ b/bolo.txt
@@ -1,3 +1,4 @@
 Bolo de cenoura
 - 3 cenouras
 - 3 ovos
+- 1 colher de fermento
git stash show stash@{1}
O resumo do item 1: ele muda o pudim.txt, com uma linha a mais (1 +).
git stash show -p stash@{2}
Com -p (patch), as mudanças linha a linha, no formato do git diff: o item 2 acrescenta - 1 colher de fermento no bolo.txt (a linha com +).

Em vez de stash@{2}, dá para escrever só o número: git stash show -p 2. Sem número nenhum, é o topo (stash@{0}).

3. apply × pop

Os dois aplicam um stash na pasta. A diferença está no que acontece com o item depois:

ComandoAplica as mudanças?O item continua na lista?
git stash applySimSim: você pode aplicar de novo, em outro branch, por exemplo
git stash popSimNão: se aplicou sem problemas, o item é apagado

git stash apply stash@{1}

$ git stash apply stash@{1}
No ramo main
Changes not staged for commit:
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   pudim.txt

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
$ git status --short
 M pudim.txt
$ git stash list
stash@{0}: WIP on main: c36bc0c Primeiras receitas
stash@{1}: On main: leite no pudim
stash@{2}: On main: fermento no bolo

O leite voltou para o pudim.txt ( M pudim.txt, modificado), e a lista continua com três itens: o apply não apagou nada. Repare que o apply mostra um git status, mas não tem a linha Dropped … do pop.

Apagando um item: git stash drop

A Ana desiste do leite no pudim. Ela descarta a mudança da pasta (git restore) e apaga o item da lista:

$ git restore pudim.txt
$ git stash drop stash@{1}
Dropped stash@{1} (f07f80aa3a8bdfbb6f7fa0899e68a91e6a9cf83b)
$ git stash list
stash@{0}: WIP on main: c36bc0c Primeiras receitas
stash@{1}: On main: fermento no bolo

Dropped stash@{1}: "descartei o stash@{1}", com o hash dele entre parênteses. Olhe a lista: o fermento, que era o stash@{2}, subiu para stash@{1}. Os números mudam sempre que a pilha muda: confira o git stash list antes de usar um número.

git stash pop: aplica o topo e apaga

$ git stash pop
No ramo main
Changes not staged for commit:
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   README.md

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
Dropped refs/stash@{0} (20e40409a13c3d4ca38869dd539f3232b69a8ade)
$ git stash list
stash@{0}: On main: fermento no bolo

Sem número, o pop pegou o topo, a frase do README, e apagou o item (Dropped refs/stash@{0}). O fermento subiu para stash@{0}. Mais um pop, e a pilha esvazia:

$ git stash pop
No ramo main
Changes not staged for commit:
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   README.md
	modified:   bolo.txt

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
Dropped refs/stash@{0} (6f3bbdf30d8a343ebd70a4254599f742bbc5ec01)
$ cat bolo.txt
Bolo de cenoura
- 3 cenouras
- 3 ovos
- 1 colher de fermento
$ git stash list

Agora a pasta tem as duas mudanças juntas (o README do pop anterior e o fermento), e a lista está vazia. Dá para aplicar stashes um por cima do outro, desde que não mexam nas mesmas linhas.

Esvaziando tudo: git stash clear

$ git stash clear
$ git stash list
$ git log --oneline
c36bc0c (HEAD -> main) Primeiras receitas

O clear ("limpar") apaga todos os itens de uma vez, sem perguntar e sem mostrar nada. (Aqui a lista já estava vazia.) Use com cuidado. E repare no git log: depois de tudo isso, o histórico continua com um commit só. Os stashes nunca entram no histórico do branch.

Missão: a pilha tem três itens. Veja a lista, descubra qual é o do leite no pudim e aplique só ele, tirando-o da pilha (os outros dois devem continuar guardados).

4. Quando o pop dá conflito

Um stash guarda mudanças em relação a um commit. Se, enquanto ele estava guardado, o branch ganhou um commit que mexe nas mesmas linhas, aplicar o stash vira um pequeno merge, e pode dar conflito. A Ana guardou "4 ovos" no stash; depois, mudou a mesma linha para "2 ovos" e commitou:

$ sed -i 's/3 ovos/4 ovos/' bolo.txt
$ git stash push -m 'quatro ovos'
Saved working directory and index state On main: quatro ovos
$ sed -i 's/3 ovos/2 ovos/' bolo.txt
$ git commit -q -am 'Bolo com 2 ovos'
$ git stash pop
Mesclagem automática de bolo.txt
CONFLITO (conteúdo): conflito de mesclagem em bolo.txt
No ramo main
Caminhos não mesclados:
  (use "git restore --staged <file>..." to unstage)
  (usar "git add <arquivo>..." para marcar resolução)
	ambos modificados:   bolo.txt

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
The stash entry is kept in case you need it again.
CONFLITO (conteúdo): conflito de mesclagem em bolo.txt
A mesma mensagem de um merge (aula Conflitos de Merge): o commit e o stash mudaram a mesma linha.
ambos modificados: bolo.txt
O bolo.txt está em "Caminhos não mesclados", com marcadores.
The stash entry is kept in case you need it again.
"O item do stash foi mantido, caso você precise dele de novo." Importante: com conflito, o pop não apaga o stash. Não aparece a linha Dropped.
$ cat bolo.txt
Bolo de cenoura
- 3 cenouras
<<<<<<< Updated upstream
- 2 ovos
=======
- 4 ovos
>>>>>>> Stashed changes
$ git stash list
stash@{0}: On main: quatro ovos

Os marcadores têm nomes diferentes dos do merge: em cima, Updated upstream ("a versão atualizada", a do commit atual); embaixo, Stashed changes ("as mudanças guardadas", as do stash). Resolver é como num merge, com uma diferença no final, porque não há commit de merge a fazer:

  1. Edite o arquivo e deixe-o como deve ficar, sem marcadores (aula Resolvendo Conflitos).
  2. Marque como resolvido com git add bolo.txt (ou, se não quiser a mudança preparada, tire o conflito com git restore --staged bolo.txt).
  3. Como o stash foi mantido, apague-o quando tiver certeza: git stash drop.

A Ana preferiu outro caminho: desistir de aplicar o stash agora. Ela voltou o arquivo à versão do último commit (o --source=HEAD --staged --worktree diz "pegue do HEAD, e restaure a área de preparo e a pasta"; veja git restore). O stash continua lá:

$ git restore --source=HEAD --staged --worktree bolo.txt
$ git status --short
$ git stash list
stash@{0}: On main: quatro ovos

A saída elegante: git stash branch

O conflito aconteceu porque o branch andou depois do stash. O git stash branch cria um branch novo a partir do commit onde o stash foi feito, aplica o stash nele (lá não há conflito, porque é o mesmo ponto de partida) e o apaga da lista:

$ git stash branch quatro-ovos
Switched to a new branch 'quatro-ovos'
No ramo quatro-ovos
Changes not staged for commit:
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   bolo.txt

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
Dropped refs/stash@{0} (c7aeff9b7e4662b69976839f4a459c1e5b3f71f3)
$ git log --oneline --decorate --all
3bf0b65 (main) Bolo com 2 ovos
ed9221a (HEAD -> quatro-ovos) Receita de bolo
$ git stash list
Switched to a new branch 'quatro-ovos'
"Mudei para um branch novo, quatro-ovos." Ele começa no ed9221a, o commit em que a Ana estava quando guardou o stash, e não no main atual (o --decorate mostra os nomes dos branches ao lado dos commits).
modified: bolo.txt
As mudanças do stash, aplicadas sem conflito. Agora a Ana pode commitá-las nesse branch e, depois, juntá-lo ao main com um merge, resolvendo o conflito no lugar certo.
Dropped refs/stash@{0}
Como deu certo, o stash saiu da lista.

5. Apaguei um stash sem querer!

Lembra do hash entre parênteses no Dropped? Ele é a sua salvação. Um stash apagado não some na hora: ele continua guardado no repositório por um tempo (até o Git fazer uma faxina, normalmente semanas depois). Com o hash, dá para aplicá-lo de novo:

$ git stash push -m 'fermento no bolo'
Saved working directory and index state On main: fermento no bolo
$ git stash drop
Dropped refs/stash@{0} (42c430a515e7e35d6480de18d3cfc6c9180ea554)
$ git stash list
$ git stash apply 42c430a
No ramo main
Changes not staged for commit:
  (utilize "git add <arquivo>..." para atualizar o que será submetido)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   bolo.txt

nenhuma modificação adicionada à submissão (utilize "git add" e/ou "git commit -a")
$ cat bolo.txt
Bolo de cenoura
- 3 cenouras
- 3 ovos
- 1 colher de fermento

Os 7 primeiros caracteres do hash bastam (veja O Hash do Commit). Se o terminal já foi fechado e você não tem mais o hash, ainda há esperança: a aula Recuperando Commits Perdidos mostra como procurar o que se perdeu. Moral: não use drop e clear no automático.

Formas diferentes de fazer a mesma coisa

Você quer…Comando
Aplicar o do topo e tirá-lo da listagit stash pop
Aplicar o do topo e manter na lista (para usar em outro lugar também)git stash apply
Aplicar um do meiogit stash pop stash@{2} ou git stash pop 2 (o mesmo com apply)
Apagar um sem aplicargit stash drop stash@{1} (sem nome: o do topo)
Apagar todosgit stash clear
Aplicar num branch novo, a partir de onde o stash foi feitogit stash branch nome
Recuperar um apagadogit stash apply <hash do Dropped>

Na dúvida entre apply e pop, use apply, confira o resultado e só então drop. É um passo a mais, mas nada se perde.

Quando dá errado

Número que não existe: log for 'stash' only has 1 entries 
$ git stash list
stash@{0}: On main: fermento no bolo
$ git stash drop stash@{5}
fatal: log for 'stash' only has 1 entries

"Fatal: o registro do stash só tem 1 item." A Ana pediu o stash@{5}, mas a pilha só tem o stash@{0}. Lembre que os números mudam quando você guarda ou tira itens. Como resolver: git stash list e use um número que aparece lá.

Conflito no pop: The stash entry is kept in case you need it again.

Visto na seção 4: o stash e um commit mudaram as mesmas linhas. O stash não é apagado. Como resolver: resolva o arquivo e rode git stash drop; ou volte o arquivo ao último commit (git restore --source=HEAD --staged --worktree arquivo) e use git stash branch.

Hash errado: is not a valid reference 
$ git stash apply e1b1a1b
error: e1b1a1b is not a valid reference

"e1b1a1b não é uma referência válida." Não existe stash (nem commit) com esse hash: costuma ser erro de digitação. Como resolver: copie o hash da linha Dropped com cuidado.

A pilha virou um cemitério

Ninguém avisa, mas é comum: um git stash list com 15 itens chamados WIP on main: …, de meses atrás, e ninguém sabe o que tem em cada um. Como evitar: use -m sempre; trate o stash como algo de horas, não de semanas (para coisas longas, faça um commit num branch); e, de vez em quando, olhe a lista e apague o que não serve com drop, conferindo antes com git stash show -p.

Referência rápida

Resumo

  • O stash é uma pilha: o último guardado é o stash@{0}, e os números mudam quando você guarda ou tira itens. git stash list mostra tudo; use -m para saber o que é cada item.
  • git stash show -p stash@{N} mostra o conteúdo de um item.
  • apply aplica e mantém; pop aplica e apaga; drop apaga sem aplicar; clear apaga tudo.
  • Se o pop dá conflito, o stash é mantido: resolva e rode git stash drop, ou use git stash branch para aplicar no commit de origem.
  • Um stash apagado sem querer volta com git stash apply <hash>, usando o hash da linha Dropped.

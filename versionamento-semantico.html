Git Versionamento Semântico

Na aula Marcando Versões, a Ana marcou a v1.0. E a próxima? v1.1? v2.0? v1.0.1? O Git aceita qualquer nome; quem dá sentido aos números é uma convenção. A mais usada no mundo se chama Versionamento Semântico (em inglês, Semantic Versioning, ou SemVer): três números, MAJOR.MINOR.PATCH, e cada um conta uma coisa diferente sobre o que mudou. Esta aula explica a regra e mostra como o Git ajuda (e atrapalha) a trabalhar com esses números.

Você vai aprender
  • O que quer dizer cada número de 1.4.2, e quando subir cada um.
  • O que são as versões 0.x e os pré-lançamentos (2.0.0-beta.1).
  • Por que o git tag põe v1.10.0 antes de v1.2.0, e como corrigir com --sort=v:refname.
  • Como ver o que mudou entre duas versões e em que versão você está.

A regra vem da especificação Semantic Versioning 2.0.0, publicada em semver.org (há tradução para o português no próprio site). As saídas de terminal vieram do Git 2.53.0 da máquina da Ana (usuária ana, computador notebook).

A ideia: errata, edição ampliada e livro novo

Pense numa receita publicada num livro. Três coisas diferentes podem acontecer com ela:

  • Errata: estava escrito "3 xícaras de sla" e o certo é "sal". Quem já usava a receita não precisa mudar nada no jeito de fazer: só corrige o erro.
  • Edição ampliada: entrou uma sugestão de cobertura no fim. O que já existia continua igual; quem quiser, usa a novidade.
  • Livro novo: a receita agora é sem glúten, com outros ingredientes e outro forno. Quem seguia a antiga vai ter de se adaptar.

O Versionamento Semântico dá um número para cada um desses três tipos de mudança. Olhando só para o número da versão nova, quem usa o seu projeto já sabe se pode atualizar sem medo.

1. Os três números: MAJOR.MINOR.PATCH

     1  .  4  .  2
     │     │     └── PATCH (correção): consertou um defeito, nada muda para quem usa
     │     └──────── MINOR (novidade):  algo novo, e o que existia continua funcionando
     └────────────── MAJOR (ruptura):   mudou de um jeito que quebra o que funcionava antes
NúmeroEm inglêsSobe quando…Exemplo no projeto da Ana
1ºMAJOR ("maior")Há uma mudança incompatível: quem usava a versão anterior pode ter de mudar alguma coisaO site muda todos os endereços das páginas: os links antigos, salvos por outras pessoas, param de funcionar
2ºMINOR ("menor")Entra uma funcionalidade nova, compatível com o que existiaO site ganha uma busca de receitas
3ºPATCH ("remendo")Há só correções de defeitos, compatíveisCorrige um erro de digitação, um link quebrado

Na especificação, "quem usa" é a API pública do projeto: aquilo que outras pessoas ou programas usam dele (as funções de uma biblioteca, os comandos de um programa, os endereços de um site). A pergunta-chave é sempre: "quem usava a versão anterior vai ter algum problema com esta?"

As regras de subir os números

  1. Subiu o PATCH: só ele muda. 1.4.2 → 1.4.3.
  2. Subiu o MINOR: o PATCH volta a zero. 1.4.3 → 1.5.0.
  3. Subiu o MAJOR: MINOR e PATCH voltam a zero. 1.5.0 → 2.0.0.
  4. Os números são inteiros e crescem sem limite: depois de 1.9.0 vem 1.10.0, e não 2.0.0. (Não é um número decimal: 1.10 é maior que 1.9.)
  5. Uma versão lançada nunca muda. Achou um erro na 1.4.2? Lance a 1.4.3. (Por isso, uma tag publicada nunca é movida; veja Marcando Versões.)

2. Antes do 1.0.0: as versões 0.x

Enquanto o projeto está nascendo e tudo pode mudar a qualquer momento, use 0. no começo: 0.1.0, 0.2.0, 0.9.3. Pela especificação, numa versão 0.y.z qualquer coisa pode mudar, e ninguém deve contar com estabilidade. A 1.0.0 é a promessa: "a partir daqui, eu sigo as regras". A especificação sugere começar em 0.1.0.

3. Pré-lançamentos: -alpha, -beta, -rc

Antes de lançar a 2.0.0, a Ana quer que alguns amigos testem. Para isso existem as versões de pré-lançamento (em inglês, pre-release): um hífen e um identificador depois dos três números.

VersãoCostuma querer dizer
2.0.0-alpha.1Primeira versão de testes, ainda incompleta
2.0.0-beta.1Completa, mas ainda em teste; pode ter defeitos
2.0.0-rc.1Release candidate, "candidata a lançamento": se ninguém achar problema, vira a 2.0.0
2.0.0A versão final

Pela especificação, um pré-lançamento vem antes da versão final: 2.0.0-alpha.1 < 2.0.0-beta.1 < 2.0.0-rc.1 < 2.0.0. (Os nomes alpha, beta e rc são costume; a regra só exige o hífen e letras, números e pontos.) Existe também a informação de build, depois de um + (1.0.0+20261015), que não conta para a ordem; é bem menos comum.

E o v na frente?

A versão é 1.4.2; o v de v1.4.2 não faz parte do Versionamento Semântico. Mas pôr o v no nome da tag é um costume muito comum (o próprio FAQ do semver.org diz isso), e ajuda a separar tags de versão de outras tags. Escolha um jeito e use sempre o mesmo: misturar v1.0.0 e 1.0.0 atrapalha a ordenação (veja em Quando dá errado).

4. No Git: tags com números de versão

A Ana passou a usar o SemVer nas tags anotadas do site (aula Marcando Versões): v1.0.0, v1.0.1 e v1.1.0, cada uma num commit. Para mostrar o que acontece com muitas versões, ela criou mais algumas tags de teste, todas no mesmo commit (só para a demonstração; depois apagou):

$ git tag v1.2.0
$ git tag v1.9.0
$ git tag v1.10.0
$ git tag v2.0.0-beta.1
$ git tag v2.0.0
$ git tag
v1.0.0
v1.0.1
v1.1.0
v1.10.0
v1.2.0
v1.9.0
v2.0.0
v2.0.0-beta.1

Viu o problema? O git tag lista em ordem alfabética, letra por letra, como num dicionário: v1.1 e depois v1.10, porque "1.10" começa igual a "1.1"; o v1.2.0 só vem depois. Para o Git, v1.10.0 é só um texto.

Ordem de versão: --sort=v:refname

$ git tag --sort=v:refname
v1.0.0
v1.0.1
v1.1.0
v1.2.0
v1.9.0
v1.10.0
v2.0.0
v2.0.0-beta.1
$ git tag --sort=-v:refname
v2.0.0-beta.1
v2.0.0
v1.10.0
v1.9.0
v1.2.0
v1.1.0
v1.0.1
v1.0.0
--sort=v:refname
"Ordene pelo nome, tratando-o como versão" (o v: é de version). Agora os números são comparados como números: 1.2, 1.9, 1.10.
--sort=-v:refname
Com o - na frente, a ordem inversa: a versão mais nova primeiro. Útil para ver "qual é a última?".

Quase perfeito. Olhe o fim da primeira lista: o Git pôs a v2.0.0-beta.1 depois da v2.0.0, mas pela regra do SemVer o pré-lançamento vem antes. Para o Git entender que o que vem depois de um hífen é um pré-lançamento, há uma configuração:

$ git config versionsort.suffix -
$ git tag --sort=v:refname
v1.0.0
v1.0.1
v1.1.0
v1.2.0
v1.9.0
v1.10.0
v2.0.0-beta.1
v2.0.0

O versionsort.suffix - diz: "um nome com - depois da versão vem antes da versão sem nada". Agora a ordem é a do SemVer. E para não digitar o --sort toda vez, configure a ordem padrão do git tag:

$ git tag
v1.10.0
v1.2.0
v1.9.0
$ git config tag.sort v:refname
$ git tag
v1.2.0
v1.9.0
v1.10.0

(Num repositório de teste, com só três tags.) Com --global, as duas configurações valem para todos os seus repositórios (veja Configurações Úteis). O padrão do -l também combina com a ordem:

$ git tag -l 'v1.*' --sort=-v:refname
v1.10.0
v1.9.0
v1.2.0
v1.1.0
v1.0.1
v1.0.0

Só a família 1.x, da mais nova para a mais velha.

Missão: a última versão do site é a v1.0.0. Depois dela, a Ana só corrigiu um erro de digitação (veja com git log --oneline). Crie a tag anotada da próxima versão, seguindo o Versionamento Semântico, com uma mensagem que diga o que mudou.

5. O que mudou entre versões?

Com as versões marcadas, o Git responde perguntas como "o que entrou na 1.1.0?". Depois de apagar as tags de teste, a Ana fez mais um commit:

$ git log --oneline v1.0.1..v1.1.0
02645c6 (tag: v1.1.0) Adiciona a busca de receitas
$ git log --oneline v1.1.0..HEAD
a628093 (HEAD -> main) Muda o layout
$ git describe
v1.1.0-1-ga628093
$ git describe --abbrev=0
v1.1.0
git log --oneline v1.0.1..v1.1.0
Os commits que estão na v1.1.0 e não estavam na v1.0.1: o que entrou nessa versão. Os dois pontos querem dizer "de … até …" (mais em git log: Filtros e Formatos).
git log --oneline v1.1.0..HEAD
O que foi feito desde a última versão: o que vai entrar na próxima. É o rascunho das notas da versão.
git describe → v1.1.0-1-ga628093
"Um commit depois da v1.1.0, no commit a628093" (o g é de "git").
git describe --abbrev=0
Só o nome da última tag anotada: v1.1.0. Perfeito para responder "qual é a versão atual?".

Olhando o v1.1.0..HEAD, a Ana decide o próximo número: "Muda o layout" mudou só a aparência, sem quebrar nada nem acrescentar funcionalidade? v1.1.1. Acrescentou algo? v1.2.0. É aqui que as mensagens de commit bem escritas ajudam; a aula Conventional Commits mostra um padrão de mensagens feito para casar com o SemVer.

Formas diferentes de numerar versões

O SemVer é o mais comum, mas não é o único:

EsquemaExemploUsado por / quando
Versionamento Semântico2.4.1Bibliotecas, programas e sites que outras pessoas usam; o padrão de quase todo o mundo do código aberto
Por data (CalVer)2026.10, 26.04Projetos lançados em datas fixas. O Ubuntu da Ana, por exemplo, é o 26.04: ano 2026, mês 04
Um número sóv1, v2, v3Projetos pequenos e pessoais, sem ninguém dependendo deles

O Git não obriga nenhum deles. Qualquer que seja o esquema, o importante é usá-lo sempre do mesmo jeito e registrar cada versão com uma tag anotada.

Quando dá errado

v1.10.0 aparece antes de v1.2.0

É a ordem alfabética do git tag (seção 4). Nada está errado nas tags. Como resolver: git tag --sort=v:refname, ou de uma vez por todas, git config --global tag.sort v:refname.

Misturou tags com e sem v 
$ git tag v1.0
$ git tag 1.0.0
$ git tag --sort=-v:refname
v1.10.0
v1.9.0
v1.2.0
v1.0
1.0.0

Com as tags v1.2.0, v1.9.0 e v1.10.0 no repositório de teste, a Ana criou também v1.0 (com dois números) e 1.0.0 (sem v). A ordem por versão ficou estranha: a 1.0.0, sem o v, foi para o fim, separada das outras. Como evitar: escolha um formato (por exemplo, sempre v + três números) e não fuja dele.

"Lancei a 1.3.0, mas tinha um erro. Posso trocar o que está na 1.3.0?"

Não. Pela regra 5 da seção 1, uma versão lançada nunca muda: alguém já pode ter baixado a 1.3.0 com o erro. Como resolver: corrija num commit novo e lance a 1.3.1.

"Mudei uma coisa pequena, mas que quebra quem usava. É PATCH?"

Não: o tamanho da mudança não importa, o que importa é se ela é compatível. Mudar o nome de um único arquivo que outras páginas usam é pequeno e quebra: é MAJOR (ou, numa versão 0.x, pode ser só MINOR, porque lá tudo pode mudar).

Resumo

  • No Versionamento Semântico, a versão é MAJOR.MINOR.PATCH: MAJOR sobe com mudanças incompatíveis, MINOR com novidades compatíveis, PATCH com correções. Subir um número zera os da direita.
  • Versões 0.y.z são de desenvolvimento inicial; a 1.0.0 é a primeira estável. Pré-lançamentos (-alpha.1, -beta.1, -rc.1) vêm antes da versão final.
  • Uma versão lançada nunca muda: corrija lançando outra.
  • No Git, cada versão vira uma tag anotada (v1.2.0). O git tag ordena como texto; use --sort=v:refname (ou git config tag.sort v:refname) e versionsort.suffix - para a ordem certa.
  • git log v1.0.1..v1.1.0 mostra o que entrou numa versão; git describe --abbrev=0, a versão atual.

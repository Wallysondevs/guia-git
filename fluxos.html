Git Git Flow e Outros Fluxos

O Git não manda você trabalhar de um jeito ou de outro: ele deixa criar quantos branches quiser, com o nome que quiser. Por isso cada equipe combina um fluxo de trabalho (em inglês, workflow): quais branches existem, de onde cada um nasce, para onde ele volta e quem pode mexer em quê. Na aula anterior você viu o mais simples, o GitHub Flow. Nesta aula você conhece o mais famoso e mais detalhado, o Git Flow, e mais dois que você vai encontrar por aí.

Você vai aprender
  • O que é um fluxo de trabalho e por que a equipe precisa combinar um.
  • O Git Flow: os branches main e develop e os de apoio feature/, release/ e hotfix/, feitos com comandos de verdade.
  • O desenvolvimento baseado em tronco (trunk-based development) e o fluxo com fork.
  • Como escolher o fluxo certo para o tamanho do projeto.

Os comandos desta aula rodaram no Git do Ubuntu da Ana (usuária ana, computador notebook), com as mensagens em português.

A ideia: regras de trânsito

Uma rua pode ser de mão única ou de mão dupla, ter faixa só para ônibus ou não. Nenhuma dessas regras é "a certa"; o que não pode é cada motorista seguir uma regra diferente. Fluxo de trabalho é isso: a regra de trânsito dos branches da equipe. Ela responde a perguntas como:

  • Onde fica o código que está no ar? E o que vai para a próxima versão?
  • De onde eu crio o branch da minha tarefa, e para onde ele volta?
  • Como se corrige um erro urgente no que já está no ar, sem levar junto o que ainda não ficou pronto?

1. O Git Flow

O Git Flow foi descrito por Vincent Driessen num texto de janeiro de 2010, "A successful Git branching model" (nvie.com). Ele foi pensado para software que sai em versões numeradas (1.0, 1.1, 2.0…), como um aplicativo que você baixa e instala. Ele tem dois branches permanentes e três tipos de branch temporário:

BranchVidaNasce deVolta paraPara quê
main (no texto original, master)Permanente——Só o que já foi lançado. Cada merge nela é uma versão nova, com uma tag.
developPermanentemain—Onde se junta o trabalho para a próxima versão.
feature/…TemporáriodevelopdevelopUma funcionalidade nova.
release/…Temporáriodevelopmain e developPreparar o lançamento: número da versão, últimos ajustes.
hotfix/…Temporáriomainmain e developCorrigir com urgência o que já está no ar.

Um desenho simplificado de cada tipo de branch temporário (o histórico de verdade, como o Git mostra, está no item 1.5):

feature: nasce da develop e volta para ela

develop:        ──●─────────────M──
                   \           /
feature/pudim:      ●────●────●


release: nasce da develop e volta para a main (com tag) e para a develop

main:           ──●─────────────M  (tag v1.0)
                               /
release/1.0:              ●───●
                         /     \
develop:        ──●─────●───────M──


hotfix: nasce da main e volta para a main (com tag) e para a develop

main:           ──M (v1.0)──────M  (tag v1.0.1)
                   \           /
hotfix/1.0.1:       ●─────────●
                               \
develop:        ──●─────●───────M──

Parece muita coisa, mas cada branch faz um papel só. A Ana vai montar esse desenho inteiro, comando por comando, no site de receitas. O Git Flow usa git merge --no-ff em todos os merges: o --no-ff (no fast-forward) obriga o Git a criar um commit de merge mesmo quando daria para só "avançar o ponteiro" (veja Merge Fast-forward). Assim, cada funcionalidade fica visível no histórico como um "galho" que entrou de uma vez.

1.1 Criar o develop

O repositório receitas da Ana tem um commit na main. Primeiro, ela cria o branch permanente develop a partir dela:

$ git switch -c develop
Switched to a new branch 'develop'      « "trocou para um branch novo"
$ git branch
* develop
  main

Pronto: dois branches, apontando para o mesmo commit. A partir de agora, ninguém commita direto na main: ela só recebe merges de release/ e hotfix/. (Algumas mensagens do Git 2.53 do Ubuntu ainda não têm tradução e saem em inglês, como esta; a aula traduz cada uma.)

1.2 Uma funcionalidade: feature/pudim

Toda funcionalidade nasce da develop, nunca da main:

$ git switch -c feature/pudim develop
Switched to a new branch 'feature/pudim'
$ printf '# Pudim\n\n- 200 g de açúcar\n' > pudim.md
$ git add pudim.md
$ git commit -m "Adiciona receita de pudim"
[feature/pudim 539d9ef] Adiciona receita de pudim
 1 file changed, 3 insertions(+)
 create mode 100644 pudim.md
$ git switch develop
Switched to branch 'develop'
$ git merge --no-ff --no-edit feature/pudim
Merge made by the 'ort' strategy.              « "merge feito pela estratégia 'ort'": criou um commit de merge
 pudim.md | 3 +++
 1 file changed, 3 insertions(+)
 create mode 100644 pudim.md
$ git branch -d feature/pudim
Deleted branch feature/pudim (was 539d9ef).

Sem o --no-ff, esse merge seria um fast-forward (a develop não tinha andado), e a mensagem seria Fast-forward, sem commit de merge. O ort é o nome do jeito que o Git usa para juntar dois galhos (veja Merge de Três Vias).

git switch -c feature/pudim develop
Cria o branch feature/pudim a partir da develop (o último argumento diz de onde ele nasce) e entra nele. A barra no nome é só um costume para agrupar: feature/pudim, feature/busca…
git merge --no-ff feature/pudim
Junta a funcionalidade na develop criando um commit de merge, mesmo que fosse possível um fast-forward.
--no-edit
Aceita a mensagem padrão do commit de merge (Merge branch 'feature/pudim' into develop) sem abrir o editor.
git branch -d feature/pudim
A funcionalidade já está na develop: o branch temporário pode ir embora (veja Apagando Branches).

1.3 Preparar o lançamento: release/1.0

Quando a develop tem tudo o que a versão 1.0 precisa, a Ana abre um branch de release. Ali só entram ajustes finais (o número da versão, um erro de digitação); funcionalidades novas continuam indo para a develop, para a próxima versão.

$ git switch -c release/1.0 develop
Switched to a new branch 'release/1.0'
$ echo '1.0' > VERSAO
$ git add VERSAO
$ git commit -m "Prepara a versão 1.0"
[release/1.0 bce8224] Prepara a versão 1.0
 1 file changed, 1 insertion(+)
 create mode 100644 VERSAO
$ git switch main
Switched to branch 'main'
$ git merge --no-ff --no-edit release/1.0
Merge made by the 'ort' strategy.
 VERSAO   | 1 +
 pudim.md | 3 +++                         « a main recebe o pudim e o VERSAO de uma vez: é o lançamento
 2 files changed, 4 insertions(+)
 create mode 100644 VERSAO
 create mode 100644 pudim.md
$ git tag v1.0
$ git switch develop
Switched to branch 'develop'
$ git merge --no-ff --no-edit release/1.0
Merge made by the 'ort' strategy.
 VERSAO | 1 +                              « a develop só não tinha o VERSAO
 1 file changed, 1 insertion(+)
 create mode 100644 VERSAO
$ git branch -d release/1.0
Deleted branch release/1.0 (was bce8224).

O release voltou para dois lugares: para a main (é o lançamento, marcado com a tag v1.0) e para a develop (para os ajustes finais não se perderem na próxima versão).

1.4 Corrigir com urgência: hotfix/1.0.1

Um leitor avisou que a receita de pudim no ar diz "200 g de açúcar" em vez de "100 g". A develop já tem coisas novas que não podem ir ao ar ainda; por isso o hotfix nasce da main:

Enquanto isso, a develop já ganhou a receita de brigadeiro (commit Adiciona receita de brigadeiro), que é para a versão 1.1. O hotfix:

$ git switch -c hotfix/1.0.1 main
Switched to a new branch 'hotfix/1.0.1'
$ sed -i 's/200 g/100 g/' pudim.md
$ echo '1.0.1' > VERSAO
$ git commit -am "Corrige açúcar do pudim"
[hotfix/1.0.1 951613d] Corrige açúcar do pudim
 2 files changed, 2 insertions(+), 2 deletions(-)
$ git switch main
Switched to branch 'main'
$ git merge --no-ff --no-edit hotfix/1.0.1
Merge made by the 'ort' strategy.
 VERSAO   | 2 +-
 pudim.md | 2 +-                           « o brigadeiro NÃO veio junto: o hotfix nasceu da main
 2 files changed, 2 insertions(+), 2 deletions(-)
$ git tag v1.0.1
$ git switch develop
Switched to branch 'develop'
$ git merge --no-ff --no-edit hotfix/1.0.1
Merge made by the 'ort' strategy.
 VERSAO   | 2 +-
 pudim.md | 2 +-                           « a correção também vai para a próxima versão
 2 files changed, 2 insertions(+), 2 deletions(-)
$ git branch -d hotfix/1.0.1
Deleted branch hotfix/1.0.1 (was 951613d).

O sed -i só troca o texto no arquivo pelo terminal (você pode usar o editor). O ponto importante é a ordem: o hotfix volta primeiro para a main (com a tag) e depois para a develop. Se ele não voltasse para a develop, a versão 1.1 sairia com o erro do açúcar de novo (veja Quando dá errado).

1.5 O desenho completo

Depois de tudo isso, o histórico completo, com todos os branches:

$ git log --oneline --graph --all --decorate
*   da8ec74 (HEAD -> develop) Merge branch 'hotfix/1.0.1' into develop
|\
* | 3790835 Adiciona receita de brigadeiro
* |   2bc7651 Merge branch 'release/1.0' into develop
|\ \
| | | *   e8e767a (tag: v1.0.1, main) Merge branch 'hotfix/1.0.1'
| | | |\
| | | |/
| | |/|
| | * | 951613d Corrige açúcar do pudim
| | |/
| | *   13fdc37 (tag: v1.0) Merge branch 'release/1.0'
| | |\
| | |/
| |/|
| * | bce8224 Prepara a versão 1.0
|/ /
* |   c35d8d5 Merge branch 'feature/pudim' into develop
|\ \
| |/
|/|
| * 539d9ef Adiciona receita de pudim
|/
* 072d2e8 Primeira versão do site

Confuso? É normal: esse é o preço do Git Flow. Metade dos commits (5 de 10) são de merge, com cruzamentos para todo lado, o desenho fica difícil de ler mesmo num projeto pequeno. (Os galhos aqui se cruzam mais do que o normal porque, no laboratório, todos os commits têm a mesma data e hora.) Dois detalhes ajudam a enxergar a lógica:

  • As tags v1.0 e v1.0.1 estão nos commits de merge da main, como manda o fluxo.
  • Os merges na main têm a mensagem Merge branch 'release/1.0', sem o "into…": quando o destino é a main, o Git deixa de fora o "into main"; nos outros branches ele escreve, como em into develop.

Para ver só a "linha principal" de cada branch, use --first-parent ("só o primeiro pai"): o Git segue cada branch sem entrar nos galhos que foram mesclados nele.

$ git log --oneline --first-parent main
e8e767a (tag: v1.0.1, main) Merge branch 'hotfix/1.0.1'      « versão 1.0.1
13fdc37 (tag: v1.0) Merge branch 'release/1.0'             « versão 1.0
072d2e8 Primeira versão do site
$ git log --oneline --first-parent develop
da8ec74 (HEAD -> develop) Merge branch 'hotfix/1.0.1' into develop
3790835 Adiciona receita de brigadeiro
2bc7651 Merge branch 'release/1.0' into develop
c35d8d5 Merge branch 'feature/pudim' into develop
072d2e8 Primeira versão do site

Agora fica claro: a main só tem lançamentos, um por linha; a develop tem cada funcionalidade que entrou, cada release e cada hotfix que voltaram para ela.

A extensão git flow (ilustrativo)

Existe uma extensão que automatiza esses comandos: com ela, git flow feature start pudim cria o branch e git flow feature finish pudim faz o merge e apaga o branch. Ela não vem com o Git (é um programa à parte, instalado com o gerenciador de pacotes) e não rodou no laboratório desta aula. Tudo o que ela faz são os comandos comuns que você acabou de ver.

O próprio autor recomenda pensar antes de usar

Em março de 2020, Driessen acrescentou uma nota ao texto: o Git Flow virou quase um dogma, mas foi pensado para software com versões explícitas, ou que precisa manter várias versões em uso ao mesmo tempo. Para aplicações web que vão ao ar o tempo todo (entrega contínua), ele recomenda um fluxo mais simples, como o GitHub Flow.

Missão: o repositório receitas já tem os branches main e develop, e você está na develop. Siga o Git Flow para uma funcionalidade: crie feature/bolo a partir da develop, crie o arquivo bolo.md e faça um commit, volte para a develop, faça o merge com git merge --no-ff --no-edit feature/bolo e apague o branch feature/bolo.

2. O GitHub Flow, de novo, para comparar

O GitHub Flow tem um branch permanente só, a main, e um branch curto por tarefa, que entra por pull request. Não há develop nem release/: o que entra na main pode ir ao ar. É o fluxo do mesmo desenho da aula anterior:

main:    A───B───────M───N          « sempre pronta para ir ao ar
              \     /   /
tarefa-1:      C───D   /
                \     /
tarefa-2:        E───┘

3. Desenvolvimento baseado em tronco (trunk-based)

"Tronco" (trunk) é o branch principal, a main. No desenvolvimento baseado em tronco, todo mundo junta o trabalho na main com muita frequência: pelo menos uma vez por dia, em pedaços bem pequenos. Branches, quando existem, duram horas. É o GitHub Flow levado ao extremo.

  • Vantagem: quase não há conflito, porque ninguém fica dias longe da main.
  • O preço: precisa de testes automáticos fortes (cada merge é testado; veja GitHub Actions) e de um jeito de esconder o que ainda não está pronto. O mais comum são as feature flags ("chaves de funcionalidade"): o código novo vai para a main desligado por um if, e é ligado quando ficar pronto.

4. O fluxo com fork

Em projetos abertos (de código aberto), quem chega de fora não pode enviar nada para o repositório oficial. O caminho é o fork: a pessoa faz uma cópia do repositório na conta dela no GitHub, trabalha num branch dessa cópia e abre um pull request da cópia para o oficial. Dentro do fork, ela segue normalmente o GitHub Flow. O fork não é um fluxo diferente de branches: é uma forma de contribuir sem ter permissão de escrita.

Qual fluxo usar

SituaçãoFluxoPor quê
Projeto pessoal, TCC, site da AnaGitHub Flow (ou até só a main, se você trabalha sozinho)Simples; um branch por tarefa já organiza bem.
Site ou aplicativo web que vai ao ar várias vezes por semanaGitHub FlowA main é o que está no ar; não há versões numeradas para preparar.
Equipe com testes automáticos fortes, que integra o tempo todoTrunk-basedBranches de horas, quase sem conflito.
Aplicativo com versões numeradas (1.0, 1.1, 2.0) e várias versões em usoGit FlowSepara o que foi lançado (main), o que vem por aí (develop) e a correção urgente (hotfix/).
Projeto de código aberto com colaboradores de foraFork + pull requestQuem é de fora não tem permissão de push no oficial.

Na dúvida, comece pelo GitHub Flow. É mais fácil acrescentar regras quando a equipe sentir falta delas do que tirar regras que ninguém segue.

Quando dá errado

Apagou o hotfix antes de mesclar na develop

A Ana fez o hotfix 1.0.2, mesclou na main, mas apagou o branch antes de levá-lo para a develop:

$ git branch -d hotfix/1.0.2
Deleted branch hotfix/1.0.2 (was 6637138).
$ git switch develop
Switched to branch 'develop'
$ git merge --no-ff --no-edit hotfix/1.0.2
merge: hotfix/1.0.2 - not something we can merge

"hotfix/1.0.2 não é algo que dê para mesclar": o branch não existe mais. (O -d deixou apagar porque o trabalho estava mesclado na main, que era onde ela estava.) Como confirmar o que a main tem e a develop não tem: git log develop..main ("o que está na main e não está na develop"):

$ git log --oneline develop..main
6ae843b (main) Merge branch 'hotfix/1.0.2'
e8e767a (tag: v1.0.1) Merge branch 'hotfix/1.0.1'
6637138 Corrige versão                   « a correção que a develop não tem

Como resolver: mescle a própria main na develop. Isso leva tudo o que foi lançado, inclusive o hotfix esquecido:

$ git merge --no-ff --no-edit main
Merge made by the 'ort' strategy.
 VERSAO | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git log --oneline develop..main

O último git log não mostra nada: agora a develop tem tudo o que a main tem. (O e8e767a aparecia na lista porque os commits de merge da main nunca entram na develop; mesclar a main resolve isso também.)

O branch develop não existe 
$ git switch -c feature/busca develop
fatal: invalid reference: develop

"Referência inválida: develop". O repositório da lojinha da Ana ainda não segue o Git Flow: não há develop para servir de ponto de partida. Como resolver: confira com git branch -a; se a equipe usa Git Flow, crie a develop uma vez (git switch -c develop main) e envie (git push -u origin develop). Se ela existe só no GitHub, um git fetch traz a origin/develop e git switch develop cria a local.

A tag da versão já existe 
$ git tag v1.0
fatal: tag 'v1.0' already exists

"A tag v1.0 já existe": esse número já foi lançado. Como resolver: no Git Flow, cada release e cada hotfix ganham um número novo (v1.0.1, v1.1); veja Versionamento Semântico. Não mova uma tag publicada: quem já baixou a v1.0 teria duas versões diferentes com o mesmo nome.

A feature nasceu da main em vez da develop

Ninguém avisa: o git switch -c feature/busca estando na main funciona sem erro. O problema aparece depois: a feature não tem o que já está na develop, e o merge pode trazer conflitos ou levar coisas na ordem errada. Como evitar: sempre diga de onde o branch nasce, com o último argumento: git switch -c feature/busca develop. Como confirmar: git log --oneline --graph --all mostra de onde o galho saiu.

Faça um hotfix: crie hotfix/1.0.1 a partir da main, conserte o pudim.md (troque 200 g por 100 g, por exemplo com echo '100 g de açúcar' > pudim.md) e faça o commit; volte para a main, faça o merge com --no-ff --no-edit e crie a tag v1.0.1.

Resumo

  • Fluxo de trabalho é a regra combinada da equipe: quais branches existem, de onde nascem e para onde voltam. O Git não impõe nenhum.
  • Git Flow: main (o que foi lançado, com tags) e develop (a próxima versão) permanentes; feature/ nasce e volta para a develop; release/ nasce da develop e volta para as duas; hotfix/ nasce da main e volta para as duas. Todos os merges com --no-ff.
  • GitHub Flow: só a main permanente, um branch curto por tarefa, pull request.
  • Trunk-based: todos juntam na main pelo menos uma vez por dia, com testes automáticos e feature flags.
  • Fork: para contribuir sem permissão de escrita no repositório oficial.
  • Versões numeradas e várias versões em uso: Git Flow. O resto: comece pelo GitHub Flow.

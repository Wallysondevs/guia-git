Git Fork

Até aqui, a Ana e o Bruno trabalharam num repositório em que os dois podiam enviar commits. Mas e quando você quer contribuir com o projeto de outra pessoa, que não te deu permissão para escrever lá? É o caso de quase todo projeto de código aberto. A resposta do GitHub é o fork (em inglês, "garfo", ou "bifurcação", como uma estrada que se divide): uma cópia do repositório na sua conta, onde você pode fazer o que quiser, e de onde você depois propõe as suas mudanças ao original.

Você vai aprender
  • O que é um fork e como ele se diferencia de um clone e de um branch.
  • Como criar o fork no site do GitHub (passo a passo da documentação oficial).
  • Como clonar o seu fork e ligar o repositório original como o remoto upstream.
  • Como trazer para o seu fork as novidades do original (git fetch upstream + git merge).
  • Por que enviar direto para o repositório original dá erro 403.
O que é real e o que é ilustrativo nesta aula

Os passos no site do GitHub (o botão de fork, os campos da página) são ilustrativos: estão descritos conforme a documentação oficial, em docs.github.com, e o site pode mudar de aparência. O site do GitHub é em inglês; os nomes dos botões aparecem aqui como estão no site, com a tradução ao lado. Já todos os comandos (git clone, git remote, git fetch, git push…) rodaram de verdade no Git do Ubuntu, na máquina da Ana, com o "GitHub de mentira" do laboratório do guia. Lá, o fork foi imitado: o repositório ana-souza/cardapio foi criado com o mesmo conteúdo do original, que é o que o botão de fork faz. As mensagens do Git saem parte em português, parte em inglês: a tradução do Git no Ubuntu é parcial (veja a nota em Seu Primeiro Commit).

A ideia: o caderno de receitas da cantina

O Bruno mantém o cardápio da cantina num caderno. Todo mundo pode ler, mas só ele escreve. A Ana tem uma receita ótima para a sexta-feira e quer sugerir. Ela não pode escrever no caderno do Bruno. Então:

  1. Tira uma fotocópia do caderno inteiro e leva para casa. A cópia é dela: pode riscar, escrever, colar folhas. (Fork.)
  2. Escreve a receita de sexta na cópia dela.
  3. Leva a página para o Bruno e diz: "olha, que tal pôr isto no seu caderno?". Ele lê, comenta, pede um ajuste, e, se gostar, copia para o caderno oficial. (Pull request, a próxima aula.)
  4. De vez em quando, ela copia para a cópia dela as páginas novas que o Bruno escreveu, para não ficar desatualizada. (Sincronizar o fork.)

No GitHub, o caderno do Bruno é o repositório bruno-lima/cardapio; a fotocópia da Ana é o ana-souza/cardapio.

"Fork" é coisa do GitHub (e de sites parecidos, como GitLab e Codeberg), não do Git: não existe git fork. Na prática, você usa os três juntos: faz o fork no site, clona o fork no computador e trabalha num branch.

1. Criando o fork no site (ilustrativo)

Segundo a documentação do GitHub, com a sua conta aberta no site:

  1. Abra a página do repositório original (aqui, github.com/bruno-lima/cardapio).
  2. No canto superior direito, clique em Fork.
  3. Na página de criação do fork:
    • Owner ("Proprietário"): escolha a sua conta (ou uma organização em que você pode criar repositórios);
    • Repository name ("Nome do repositório"): por padrão, o mesmo do original; pode trocar se quiser;
    • Description ("Descrição"): opcional;
    • Copy the DEFAULT branch only ("Copiar somente o branch PADRÃO"): marcado, copia só o main; desmarcado, copia todos os branches.
  4. Clique em Create fork ("Criar fork").

Em instantes, aparece github.com/ana-souza/cardapio: um repositório da Ana, com todos os commits do original. Nada mudou no repositório do Bruno.

Pela linha de comando, com o GitHub CLI

Quem usa o GitHub CLI (gh) pode criar o fork sem abrir o site: gh repo fork bruno-lima/cardapio --clone=true cria o fork e já o clona (conforme a documentação; o gh não roda no laboratório do guia).

2. Clonando o fork

Agora é Git de verdade. A Ana clona o fork dela (e não o do Bruno), porque é para lá que ela vai poder enviar:

$ git clone https://github.com/ana-souza/cardapio.git
Cloning into 'cardapio'...
remote: Enumerating objects: 7, done.
remote: Counting objects: 100% (7/7), done.
remote: Compressing objects: 100% (7/7), done.
remote: Total 7 (delta 1), reused 0 (delta 0), pack-reused 0 (from 0)
Receiving objects: 100% (7/7), done.
Resolving deltas: 100% (1/1), done.
$ cd cardapio
$ git remote -v
origin  https://github.com/ana-souza/cardapio.git (fetch)
origin  https://github.com/ana-souza/cardapio.git (push)
$ git log --oneline
396f305 (HEAD -> main, origin/main, origin/HEAD) Adiciona a quarta-feira
2bc3f14 Cria o cardápio

O clone já está explicado em git clone. O que importa aqui: o git remote -v mostra um só remoto, origin, apontando para o fork da Ana. Os commits são os do Bruno (o fork copiou o histórico inteiro, com os mesmos hashes).

3. Ligando o original: o remoto upstream

O clone sabe do fork, mas não sabe nada do repositório do Bruno. Para receber as novidades dele, a Ana acrescenta um segundo remoto (veja git remote). O nome tradicional é upstream ("rio acima", de onde a água vem):

$ git remote add upstream https://github.com/bruno-lima/cardapio.git
$ git remote -v
origin  https://github.com/ana-souza/cardapio.git (fetch)
origin  https://github.com/ana-souza/cardapio.git (push)
upstream        https://github.com/bruno-lima/cardapio.git (fetch)
upstream        https://github.com/bruno-lima/cardapio.git (push)
$ git fetch upstream
From https://github.com/bruno-lima/cardapio
 * [new branch]      main       -> upstream/main
$ git branch -a
* main
  remotes/origin/HEAD -> origin/main
  remotes/origin/main
  remotes/upstream/HEAD -> upstream/main
  remotes/upstream/main
git remote add upstream URL
"Acrescente um remoto chamado upstream com este endereço." Não mostra nada quando dá certo.
origin … / upstream …
Agora são dois: origin = o fork da Ana (onde ela envia); upstream = o original do Bruno (de onde ela busca). Cada um aparece duas vezes, uma para buscar (fetch) e outra para enviar (push).
git fetch upstream
Busca o que o repositório do Bruno tem. Não mostrou progresso de download porque os commits já estavam no computador (vieram com o clone do fork).
* [new branch] main -> upstream/main
"Branch novo": o Git criou o upstream/main, a anotação de onde está o main do Bruno.
git branch -a
Lista todos os branches, os locais e os dos remotos (remotes/…). O remotes/upstream/HEAD -> upstream/main diz qual é o branch principal do upstream.
origin e upstream são só nomes

O Git não dá significado especial a nenhum dos dois: são apelidos para endereços. O origin é o nome que o git clone dá ao repositório de onde clonou; o upstream é uma convenção de quem usa forks (a própria documentação do GitHub usa esse nome). Seguir a convenção ajuda: qualquer tutorial vai falar em upstream.

Missão: o clone do fork da Ana já está pronto (com o origin apontando para https://github.com/ana-souza/cardapio.git). Confira com git remote -v e acrescente o repositório original do Bruno, https://github.com/bruno-lima/cardapio.git, como o remoto upstream. Confira de novo no fim.

4. Mantendo o fork atualizado

O fork é uma cópia tirada num momento. Depois disso, o Bruno continua trabalhando: acrescentou a quinta-feira no cardápio. O fork da Ana não recebe isso sozinho. E o git status da Ana não sabe de nada:

$ git status
No ramo main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean

"O seu branch está atualizado com origin/main": é verdade, mas o origin é o fork, que também está atrasado. O status compara com o branch de rastreamento (veja Branch de Rastreamento), e nunca com o repositório do Bruno. Para saber, é preciso buscar no upstream:

$ git fetch upstream
remote: Enumerating objects: 5, done.
remote: Counting objects: 100% (5/5), done.
remote: Compressing objects: 100% (3/3), done.
remote: Total 3 (delta 1), reused 0 (delta 0), pack-reused 0 (from 0)
Unpacking objects: 100% (3/3), 311 bytes | 311.00 KiB/s, done.
From https://github.com/bruno-lima/cardapio
   396f305..3e097d6  main       -> upstream/main
$ git log --oneline --graph --all
* 3e097d6 (upstream/main, upstream/HEAD) Adiciona a quinta-feira
* 396f305 (HEAD -> main, origin/main, origin/HEAD) Adiciona a quarta-feira
* 2bc3f14 Cria o cardápio
$ git merge upstream/main
Updating 396f305..3e097d6
Fast-forward
 cardapio.txt | 1 +
 1 file changed, 1 insertion(+)
$ git push origin main
Enumerating objects: 5, done.
Counting objects: 100% (5/5), done.
Delta compression using up to 4 threads
Compressing objects: 100% (3/3), done.
Writing objects: 100% (3/3), 331 bytes | 331.00 KiB/s, done.
Total 3 (delta 1), reused 0 (delta 0), pack-reused 0 (from 0)
To https://github.com/ana-souza/cardapio.git
   396f305..3e097d6  main -> main
  1. git fetch upstream: baixa o commit novo do Bruno (3e097d6) para o upstream/main. O main da Ana ainda não mudou.
  2. O log --graph --all mostra a situação: o upstream/main está um commit à frente do main da Ana e do origin/main (o fork).
  3. git merge upstream/main: traz o commit para o main da Ana. Como ela não tinha commits próprios no main, foi um fast-forward.
  4. git push origin main: atualiza o fork no GitHub. Sem este passo, só o computador da Ana estaria em dia.

Os dois primeiros passos podem ser um só: git pull upstream main (busca e junta). E o site também oferece um atalho (ilustrativo, conforme a documentação): na página do fork, acima da lista de arquivos, o menu Sync fork ("Sincronizar fork") e o botão Update branch ("Atualizar branch") atualizam o fork direto no GitHub. Depois disso, no computador, basta um git pull do origin.

Deixe o main do fork sempre igual ao original

Nunca commite direto no main do seu fork. Faça o seu trabalho em branches (git switch -c receita-sexta). Assim, o main sempre recebe as novidades do upstream por fast-forward, sem conflitos, e cada contribuição fica no seu branch, pronta para virar um pull request.

5. O caminho completo de uma contribuição

   bruno-lima/cardapio  (upstream)  ◀──── 5. pull request ────┐
          │                                                    │
          │ 1. Fork (no site)                                  │
          ▼                                                    │
   ana-souza/cardapio   (origin)    ◀──── 4. git push ─────┐   │
          │                                                │   │
          │ 2. git clone                                   │   │
          ▼                                                │   │
   ~/cardapio  (computador da Ana) ── 3. branch + commits ─┘───┘
  1. Fork no site: bruno-lima/cardapio → ana-souza/cardapio.
  2. Clone do fork e git remote add upstream ….
  3. Branch novo, commits.
  4. Push do branch para o fork: git push -u origin receita-sexta.
  5. Pull request do branch do fork para o main do original: próxima aula.

Quando dá errado

Tentou enviar direto para o repositório original: erro 403

A Ana commitou a sexta-feira no main e, por engano, mandou para o upstream. Nesta sessão o "GitHub de mentira" estava pedindo login (o token mostrado aqui é um exemplo inventado, e o terminal não mostra o que se digita na senha):

$ git push upstream main
Username for 'https://github.com': ana-souza
Password for 'https://ana-souza@github.com':
remote: Permission to bruno-lima/cardapio.git denied to ana-souza.
fatal: não foi possível acessar 'https://github.com/bruno-lima/cardapio.git/': The requested URL returned error: 403

"Permissão para bruno-lima/cardapio.git negada para ana-souza" e "não foi possível acessar …: o endereço pedido devolveu o erro 403" (403 é o código da web para "proibido"). A Ana é ela mesma, a senha (o token) está certa, mas o repositório é do Bruno e ele não deu permissão de escrita. É exatamente para isso que o fork existe. Como resolver: envie para o seu fork (git push origin …, de preferência num branch) e abra um pull request.

error: remote upstream already exists. 
$ git remote add upstream https://github.com/bruno-lima/cardapio.git
error: remote upstream already exists.

"O remoto upstream já existe": aparece se você rodar o git remote add upstream … duas vezes. Nada foi mudado. Como confirmar: git remote -v. Como resolver: se o endereço estiver errado, troque com git remote set-url upstream URL-CERTA (veja git remote).

"Meu fork está desatualizado, mas o git status diz que está tudo em dia"

O que aconteceu: o status compara com o origin/main (o fork), e não com o original (seção 4). Como resolver: git fetch upstream e git log --oneline --graph --all para ver a distância; depois git merge upstream/main e git push origin main.

Clonou o original em vez do fork

Se a Ana tivesse clonado bruno-lima/cardapio, o origin seria o repositório do Bruno, e o push daria o mesmo 403. Como resolver sem clonar de novo: renomeie os remotos: git remote rename origin upstream e git remote add origin https://github.com/ana-souza/cardapio.git. Confira com git remote -v.

Resumo

  • Um fork é uma cópia de um repositório de outra pessoa na sua conta do GitHub. Serve para contribuir quando você não tem permissão de escrita no original.
  • Fork é coisa do site (botão Fork); clone é a cópia no seu computador; branch é uma linha de trabalho dentro do repositório.
  • Clone o seu fork (origin) e ligue o original com git remote add upstream URL.
  • O fork não se atualiza sozinho: git fetch upstream, git merge upstream/main, git push origin main (ou Sync fork no site).
  • Enviar direto ao original dá 403: envie ao fork, num branch, e abra um pull request.
